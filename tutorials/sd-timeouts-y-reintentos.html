Timeouts, reintentos, backoff y jitter

Reintentar es la respuesta obvia a un fallo transitorio y la forma más común de convertir un problema pequeño en una caída general. La diferencia entre las dos cosas son tres detalles: cuándo reintentas, cuánto esperas y si todos tus servidores esperan lo mismo.

Sin timeout no hay nada que hablar #

Antes del reintento va el timeout, porque una llamada sin límite no falla: se queda esperando y bloquea un worker. Con suficientes peticiones así, el pool se agota y tu servicio deja de responder también a lo que no dependía de nadie.

Elige el timeout con datos, no con un número redondo

El criterio útil es el percentil 99 de esa llamada, con algo de margen: si el 99 % de las respuestas llega en menos de 300 ms, un timeout de 1 s corta lo anómalo sin castigar lo normal. «30 segundos porque es lo que venía puesto» no es una decisión, y en la práctica equivale a no tener timeout.

Y hay un presupuesto que respetar: si tu endpoint promete responder en 2 s, la suma de timeout × intentos de todo lo que llames por dentro tiene que caber ahí. Tres intentos de 1 s con esperas entre medias ya se te ha ido.

Qué se puede reintentar #

Reintentar a ciegas es peligroso. La regla depende de dos cosas: si el error es transitorio y si la operación es idempotente.

Respuesta¿Reintentar?Por qué
Timeout de conexiónSíNi siquiera llegó: es seguro
503, 502, 429SíEl servidor dice explícitamente «ahora no»
Timeout de lecturaSolo si es idempotentePuede haberse ejecutado ya
500Con cuidadoPuede haber dejado efectos a medias
400, 422, 404NoVa a fallar igual las diez veces
401, 403NoRefresca la credencial; reintentar no la arregla

Reintentar un 400 es gastar el doble para el mismo error

Un error de cliente es determinista: la petición está mal formada y lo va a estar en el segundo intento. Reintentarlo multiplica la carga sin ninguna posibilidad de éxito, y encima ensucia las métricas del otro servicio.

Backoff exponencial y jitter #

Reintentar inmediatamente es lo peor que puedes hacer: el servicio está saturado y le mandas el doble de tráfico. De ahí el backoff exponencial: esperar cada vez más entre intentos —100 ms, 200, 400, 800— para dar tiempo a que se recupere.

Pero el backoff solo no basta, y este es el detalle que casi todo el mundo se salta:

1 El servicio se cae un instante500 peticiones fallan a la vez
2 Las 500 reintentan en el mismo milisegundoBackoff sin jitter = todos sincronizados
3 Oleadas cada vez más separadasEl servicio no levanta cabeza entre ellas

La manada atronadora. El jitter la rompe: cada cliente espera un tiempo aleatorio.

php · EsperaConJitter.php 
<?php

declare(strict_types=1);

final class EsperaConJitter
{
    private const BASE_MS = 100;
    private const TOPE_MS = 10_000;

    public function milisegundosParaIntento(int $intento): int
    {
        $exponencial = min(self::BASE_MS * (2 ** $intento), self::TOPE_MS);

        return random_int(0, $exponencial);
    }
}

Sí, aleatorio entre cero y el máximo

Se llama full jitter y sorprende porque parece que desperdicia espera. Los estudios de AWS sobre el tema concluyen que reparte mejor la carga y termina antes que las variantes conservadoras que solo añaden un pequeño porcentaje aleatorio. Lo importante no es cuánto esperas: es que no esperes lo mismo que los demás.

La amplificación en cadena #

Este es el fallo que convierte un problema local en una caída general, y no se ve leyendo un servicio aislado. Si tienes cuatro capas y cada una reintenta tres veces:

bash · la cuenta 
API -> Pedidos -> Facturación -> Base de datos
 3   x    3     x      3        = 27 peticiones a la BD por cada una del usuario

Veintisiete. Con la base de datos ya saturada. La regla que evita esto es reintentar en una sola capa, normalmente la más cercana al fallo, y que las de arriba propaguen el error. Si necesitas reintentos en varias, usa un presupuesto compartido: un contador que viaje en una cabecera y limite el total.

Y respeta el Retry-After

Cuando un servicio devuelve 429 o 503 con esa cabecera, te está diciendo exactamente cuándo volver. Ignorarla y aplicar tu propio backoff es la forma más rápida de que te limiten más agresivamente o te bloqueen.

Cuándo aplicarlo #

Reintenta cuando…

  • El error es transitorio: red, 503, 429, saturación puntual
  • La operación es idempotente o llevas clave de idempotencia
  • Estás en la capa más cercana al fallo
  • El presupuesto de tiempo del endpoint da para ello

No reintentes cuando…

  • El error es de cliente: 400, 404, 422
  • La operación no es idempotente y no llevas clave
  • Otra capa por encima ya está reintentando
  • El usuario está esperando y ya has gastado su paciencia

Resumen #

Lo que te llevas

  • Sin timeout no hay reintento posible: una llamada sin límite no falla, bloquea un worker hasta agotar el pool.
  • Solo se reintenta lo transitorio. Un 400 va a fallar igual las diez veces: reintentarlo es gastar el doble para el mismo error.
  • Backoff sin jitter sincroniza a todos los clientes en oleadas que vuelven a tumbar el servicio. Lo importante no es cuánto esperas, sino no esperar lo mismo que los demás.
  • Reintentos en cuatro capas se multiplican: 3×3×3 son 27 peticiones por cada una del usuario, contra un sistema ya saturado.
  • Reintenta en una sola capa, la más cercana al fallo, y respeta el Retry-After cuando te lo manden.
