Máquina, contenedor o función: dónde corre tu código

Tres formas de ejecutar el mismo código con costes operativos muy distintos. La elección no va de moda ni de rendimiento: va de cuánto quieres administrar y cuánto atarte.

Máquina virtual, contenedor o función: tres formas de ejecutar el mismo código con costes operativos muy distintos. La elección no va de moda ni de rendimiento bruto, va de cuánto quieres administrar y de cuánto estás dispuesto a atarte a un proveedor.

El eje que las ordena #

Las tres se colocan sobre la misma recta: cuanto menos administras, menos controlas y más te atas.

EstadoPuedes guardarlo en discoEfímero salvo volúmenesNinguno, siempre

Qué es un contenedor, en una frase

Un proceso normal de Linux con la vista restringida: namespaces deciden qué ve —su propio sistema de ficheros, sus procesos, su red— y cgroups deciden cuánto puede usar. No hay máquina virtual dentro. El curso de Docker lo desarrolla; aquí importa la consecuencia: comparte núcleo con el anfitrión.

El contenedor como opción por defecto #

Para una aplicación web de negocio, el contenedor es la opción razonable casi siempre, por una razón que no es técnica: el artefacto que pruebas es el que despliegas. La misma imagen corre en el pipeline, en preproducción y en producción, y «en mi máquina funciona» deja de ser una frase posible.

Lo que resuelve

  • Entorno idéntico en todas partes
  • Despliegue reproducible y revertible: es cambiar de etiqueta
  • Varias versiones de PHP conviviendo sin dolor
  • Escalar es arrancar otra copia

Lo que te cobra

  • Un registro de imágenes que mantener
  • Aprender a depurar dentro del contenedor
  • Volúmenes y permisos, que dan más guerra de lo que parece
  • Si vas a orquestador, una plataforma entera

Funciones: el arranque en frío decide #

Una función es código que se ejecuta cuando llega un evento y desaparece. No pagas por estar encendido y no administras nada. La contrapartida tiene nombre: cuando no hay ninguna instancia caliente, la primera petición espera a que se cree el entorno, se cargue el runtime y arranque tu código.

1 Petición con instancia calienteDecenas de milisegundos: perfecto
2 Arranque en fríoCientos de milisegundos o segundos, según runtime y dependencias

Con tráfico constante casi no se nota. Con tráfico intermitente, lo nota justo el primer usuario de cada rato.

Las funciones escalan de golpe, y tu base de datos no

Es el fallo clásico: mil invocaciones simultáneas crean mil instancias, cada una abriendo su conexión a la base de datos. La función escala en segundos y la base de datos se cae. Por eso los proveedores venden poolers aparte: sin uno, lo asíncrono barato te sale carísimo.

Lo que las tres opciones te exigen igual #

Da igual dónde acabe corriendo tu código: hay una disciplina común que hace que moverse entre las tres sea barato, y no seguirla te ata a la que elegiste primero.

ReglaQué evita
Configuración por variables de entornoImágenes distintas por entorno, y secretos en el repositorio
Logs a la salida estándarDepender de que exista un disco donde escribir
Sin estado en el sistema de ficheros localQue reiniciar pierda datos y que no puedas escalar
El proceso puede morir en cualquier momentoQue un despliegue o un reescalado corrompa algo a medias

La parada limpia se olvida siempre

Al desplegar, el sistema manda SIGTERM y espera unos segundos antes de SIGKILL. Si tu worker no captura esa señal, se muere a mitad de procesar un mensaje. Symfony Messenger lo hace por ti; un bucle propio, no. Es la diferencia entre un despliegue transparente y un puñado de trabajos a medias en cada uno.

php · terminar el trabajo en curso y salir 
<?php

declare(strict_types=1);

final class BucleDeTrabajo
{
    private bool $debeParar = false;

    public function arrancar(): void
    {
        pcntl_async_signals(true);
        pcntl_signal(SIGTERM, fn () => $this->debeParar = true);
        pcntl_signal(SIGINT, fn () => $this->debeParar = true);

        while (!$this->debeParar) {
            $mensaje = $this->cola->siguiente();

            if ($mensaje === null) {
                usleep(200_000);
                continue;
            }

            $this->procesar($mensaje);
        }

        $this->registro->info('Parada limpia: no queda trabajo a medias');
    }
}

La señal solo marca una bandera; el bucle termina el mensaje que tenía entre manos y sale por su propio pie. Salir dentro del manejador de la señal sería justo el fallo que intentas evitar.

Cuándo aplicarlo #

Contenedor cuando…

  • Es una aplicación web con tráfico continuo
  • Quieres el mismo artefacto en todos los entornos
  • Necesitas control sobre versiones y extensiones
  • Puede que cambies de proveedor algún día

Función cuando…

  • Es esporádico y por eventos: un webhook, un procesado de imagen
  • El tráfico es muy irregular y no quieres pagar por estar encendido
  • Un arranque en frío ocasional no molesta a nadie
  • Asumes el acoplamiento al proveedor a cambio de no administrar

¿Y la máquina virtual sin más? Sigue siendo perfectamente válida: una aplicación estable, en un solo servidor, con despliegue automatizado y systemd por debajo, no necesita nada más. Meterle contenedores y orquestación «porque toca» es añadir plataforma sin resolver ningún problema que tuvieras.

Resumen #

Lo que te llevas

  • Las tres opciones están sobre el mismo eje: cuanto menos administras, menos controlas y más te atas al proveedor.
  • La razón principal para usar contenedores no es técnica: el artefacto que pruebas es exactamente el que despliegas.
  • Las funciones escalan en segundos y tu base de datos no: mil instancias son mil conexiones. Sin pooler, sale carísimo.
  • La disciplina común —config por entorno, logs a stdout, sin estado local, parada limpia— es lo que hace barato cambiar de opción.
  • Una máquina con systemd y despliegue automatizado sigue siendo una respuesta válida: añadir orquestación «porque toca» es plataforma sin problema.
