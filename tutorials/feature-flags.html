Feature flags: separar desplegar de lanzar

El código puede llegar a producción apagado y encenderse cuando toque, para quien toque. Tipos de flag, una interfaz propia en PHP, rollout por porcentaje que no cambia de bando al usuario, kill switch y la deuda que dejan las flags que nadie retira.

El viernes a las cinco nadie quiere desplegar, pero el miedo no es al deploy: es a que los usuarios vean algo roto. Si el código nuevo llega apagado, desplegar deja de ser un acontecimiento y lanzar pasa a ser una decisión que se toma con calma.

Desplegar no es lanzar #

En Despliegue continuo viste cómo llevar una imagen a producción sin cortar el servicio. Esas estrategias deciden qué versión del código corre. Lo que no deciden es qué funcionalidad ve cada usuario: si el checkout nuevo está en la imagen, lo ve todo el que llegue a esa versión.

Mientras vayan atadas, una funcionalidad a medias obliga a elegir: una rama que vive semanas (el integrar tarde de qué es CI/CD) o un merge a main que enseña algo sin terminar. Y deshacerla cuesta un despliegue entero.

Una feature flag corta ese nudo: es una condición en el código cuyo valor se decide fuera del código, en tiempo de ejecución. El código viaja a producción con cada deploy; la funcionalidad se enciende cuando producto lo decide, para quien lo decide.

1 DeployEl código nuevo llega a producción con la flag apagada
2 Release gradualEquipo interno, 5 %, 50 %, 100 %
3 RetiradaSe borra la flag y el camino viejo en otro deploy

El tercer paso es el que casi todos los equipos olvidan.

Cuatro tipos de flag #

Todas son un if, pero no se gestionan igual. Lo que las distingue es cuánto viven y quién tiene derecho a moverlas:

TipoPara quéVidaQuién la mueve
ReleaseEsconder algo a medias o lanzarlo por fasesDías o semanasEl equipo que lo desarrolla
ExperimentoComparar dos variantes con métricas (test A/B)Lo que dure el experimentoProducto o analítica
Operación (kill switch)Apagar una pieza cara o frágil cuando fallaPermanenteQuien esté de guardia
PermisoDar una función a un plan o a ciertos clientesPermanenteNegocio

La columna de vida es la importante: una flag de release que sigue ahí a los seis meses ya es deuda. Y una de permiso gestionada como temporal acaba siendo lógica de negocio escondida en la configuración, sin tests.

Evaluarlas detrás de una interfaz #

La primera flag de casi todos los proyectos tiene esta pinta: una variable de entorno, un correo de la persona que prueba y la decisión repartida por el controlador.

php · antes: la decisión pegada al controlador 
<?php

declare(strict_types=1);

final class CheckoutController
{
    public function __invoke(User $user): Response
    {
        if (getenv('NEW_CHECKOUT') === '1' || $user->email === 'ana@tienda.test') {
            return $this->checkoutV2($user);
        }

        return $this->checkoutV1($user);
    }
}

Cada flag nueva copia el patrón y nadie sabe cuántas hay ni dónde. Y cambiar NEW_CHECKOUT exige redesplegar, justo lo que querías evitar. La salida es una interfaz propia y pequeña de la que depende el negocio.

php · después: el controlador solo pregunta 
<?php

declare(strict_types=1);

final readonly class CheckoutController
{
    public function __construct(private FeatureFlags $flags) {}

    public function __invoke(User $user): Response
    {
        if ($this->flags->isEnabled('checkout-v2', new FlagContext($user->id))) {
            return $this->checkoutV2($user);
        }

        return $this->checkoutV1($user);
    }
}

El controlador no sabe de dónde sale la respuesta, así que el origen (un fichero, Redis, un servicio externo) cambia sin tocarlo. La implementación más simple lee un array: usuarios con acceso directo y un porcentaje.

php · src/flags.php 
<?php

declare(strict_types=1);

interface FeatureFlags
{
    public function isEnabled(string $flag, FlagContext $context): bool;
}

final readonly class FlagContext
{
    public function __construct(public string $userId) {}
}

final readonly class ConfigFeatureFlags implements FeatureFlags
{
    public function __construct(private array $flags) {}

    public function isEnabled(string $flag, FlagContext $context): bool
    {
        $rule = $this->flags[$flag] ?? null;

        if ($rule === null) {
            return false;
        }

        if (in_array($context->userId, $rule['users'] ?? [], true)) {
            return true;
        }

        return self::bucket($flag, $context->userId) < ($rule['percentage'] ?? 0);
    }

    public static function bucket(string $flag, string $userId): int
    {
        return crc32($flag . ':' . $userId) % 100;
    }
}

Una flag que no existe devuelve false. Es una decisión deliberada: si alguien borra la regla o el origen falla, el usuario cae en el camino conocido, no en el nuevo.

Rollout por porcentaje con un hash estable #

Encender una flag para el 10 % de los usuarios parece pedir random_int(0, 99) < 10. Error: cada petición tira el dado otra vez y el mismo usuario ve el checkout nuevo, recarga y ve el viejo. Lo que necesitas es que cada usuario caiga siempre en la misma cubeta del 0 al 99, y eso lo da un hash de su id.

bucket() calcula el CRC32 de flag:usuario y se queda con el resto entre 100. En PHP de 64 bits crc32() devuelve siempre un entero positivo, así que la cubeta cae entre 0 y 99. Meter el nombre de la flag en el hash importa: sin él, el mismo 10 % de usuarios sería el conejillo de indias de todas tus flags a la vez.

bash · el mismo usuario cae siempre en el mismo lado 
$ php rollout.php
u-4: cubeta 8, checkout-v2 = sí
u-1042: cubeta 61, checkout-v2 = no
u-4: cubeta 8, checkout-v2 = sí
u-1042: cubeta 61, checkout-v2 = no
Dentro al 10 %: 9871 de 100000
Salen al subir al 25 %: 0

El script (rollout.php) evalúa dos veces a cada usuario y cuenta cien mil ids ficticios. El reparto se acerca al porcentaje pedido y, al subir del 10 al 25 %, nadie sale: quien tenía cubeta menor que 10 también la tiene menor que 25. Con PHP 8.4 y 8.5 la salida es idéntica, así que todas las réplicas deciden lo mismo.

Canary y porcentaje no son lo mismo

El canary reparte peticiones entre dos versiones del código desplegadas. El rollout por flag reparte usuarios dentro de la misma versión. Se combinan bien: el canary vigila la imagen nueva, la flag decide quién ve la funcionalidad.

Kill switch: apagar sin desplegar #

Una flag de operación protege a la aplicación de sus dependencias. El servicio externo de recomendaciones tarda ocho segundos y arrastra la ficha de producto: quien está de guardia apaga la flag y la página sirve los más vendidos, sin esperar a un deploy.

php · el camino degradado ya está escrito 
<?php

declare(strict_types=1);

final readonly class ProductRecommendations
{
    public function __construct(
        private FeatureFlags $flags,
        private RecommenderClient $recommender,
        private BestSellers $bestSellers,
    ) {}

    public function forUser(string $userId): array
    {
        if (!$this->flags->isEnabled('ops-recomendaciones-externas', new FlagContext($userId))) {
            return $this->bestSellers->top(10);
        }

        return $this->recommender->forUser($userId);
    }
}

Dos condiciones: el camino degradado existe y está probado antes del incidente, y el valor se cambia en caliente. Si las reglas viven en un fichero dentro de la imagen, cambiarlas es desplegar; el origen de un kill switch es una base de datos, Redis o un servicio de flags, con una caché corta delante.

OpenFeature: el estándar #

Cuando las reglas crecen (segmentos, auditoría de quién cambió qué) toca un servicio de flags. OpenFeature es el estándar abierto de la CNCF para hablar con cualquiera de ellos con la misma API, y tiene SDK oficial de PHP: open-feature/sdk (versión 2.3 en octubre de 2026). Cada servicio se conecta con un provider, como open-feature/flagd-provider.

Como tu código ya depende de FeatureFlags, adoptarlo es escribir un adaptador más:

php · el adaptador de OpenFeature 
<?php

declare(strict_types=1);

use OpenFeature\implementation\flags\EvaluationContext;
use OpenFeature\interfaces\flags\Client;

final readonly class OpenFeatureFlags implements FeatureFlags
{
    public function __construct(private Client $client) {}

    public function isEnabled(string $flag, FlagContext $context): bool
    {
        return $this->client->getBooleanValue($flag, false, new EvaluationContext($context->userId));
    }
}

El cliente sale de OpenFeatureAPI::getInstance()->getClient(), y el provider se registra una vez con setProvider(). Sin provider, el SDK usa uno que no hace nada y devuelve el valor por defecto: el false del segundo argumento. Lo mismo ocurre si el provider lanza una excepción, así que el valor por defecto debe ser siempre el camino seguro.

La deuda: cada flag nace con fecha de retirada #

Cada flag duplica los caminos del código: con diez vivas hay más combinaciones de las que nadie prueba. Por eso una flag de release se crea con tres datos escritos en la misma pull request: dueño, fecha de retirada y el issue que la retira.

Retirarla tiene un orden: unos días al 100 % y, en otro deploy, se borran la condición, el camino viejo y la regla, como en expandir y contraer. Si grep -rn "checkout-v2" src/ tests/ config/ no devuelve nada, ya no queda código que la lea; el camino viejo no lleva su nombre y se comprueba aparte.

Errores típicos

  • Sortear en cada petición. random_int() o mt_rand() hacen que el usuario cambie de bando al recargar. La cubeta sale de un hash de su id.
  • Reutilizar el nombre de una flag retirada. El código viejo que aún corre en alguna réplica la lee y se enciende algo que nadie esperaba.
  • Un kill switch que nadie ha pulsado. El camino degradado nunca se ejecutó y falla justo en el incidente.
  • Flags dentro de flags. Un if de una flag dentro del de otra multiplica los casos y hace imposible saber qué ve un usuario.
  • Esconder un cambio de esquema tras una flag. La flag apaga código, no migraciones: la base de datos sigue necesitando expandir y contraer.

Cómo probar los dos caminos #

Mientras la flag viva, los dos caminos son producción. Gracias a la interfaz, en el test no hace falta ningún servicio: basta un fake que devuelva lo que pidas, como los de dobles de test, y un data provider que ejecute el mismo test con la flag encendida y apagada.

php · tests/CheckoutTest.php 
<?php

declare(strict_types=1);

use PHPUnit\Framework\Attributes\DataProvider;
use PHPUnit\Framework\TestCase;

final readonly class FixedFeatureFlags implements FeatureFlags
{
    public function __construct(private array $enabledFlags) {}

    public function isEnabled(string $flag, FlagContext $context): bool
    {
        return in_array($flag, $this->enabledFlags, true);
    }
}

final readonly class Checkout
{
    public function __construct(private FeatureFlags $flags) {}

    public function engine(string $userId): string
    {
        if ($this->flags->isEnabled('checkout-v2', new FlagContext($userId))) {
            return 'v2';
        }

        return 'v1';
    }
}

final class CheckoutTest extends TestCase
{
    #[DataProvider('bothPaths')]
    public function testUsesTheEngineTheFlagSelects(array $enabledFlags, string $expectedEngine): void
    {
        $checkout = new Checkout(new FixedFeatureFlags($enabledFlags));

        self::assertSame($expectedEngine, $checkout->engine('u-1042'));
    }

    public static function bothPaths(): iterable
    {
        yield 'flag encendida' => [['checkout-v2'], 'v2'];
        yield 'flag apagada' => [[], 'v1'];
    }
}
bash · los dos caminos, en verde 
$ vendor/bin/phpunit --testdox tests

Checkout
 ✔ Uses the engine the flag selects with data set "flag encendida"
 ✔ Uses the engine the flag selects with data set "flag apagada"

OK (2 tests, 2 assertions)

Al retirar la flag, el caso flag apagada se va con ella. Y para la cubeta, un test con dos o tres ids fijos impide cambiar el hash sin darse cuenta, que cambiaría de bando a todos los usuarios a la vez.

Cuándo aplicarlo #

Pon una flag cuando…

  • Una funcionalidad necesita varios merges a main antes de estar lista
  • Quieres lanzar a un porcentaje y mirar las métricas antes de seguir
  • Dependes de un servicio externo que puede caerse y tienes un camino degradado
  • El lanzamiento tiene fecha de negocio y no quieres atarlo a un deploy

No la pongas cuando…

  • El cambio es pequeño y cabe en un solo merge: la flag cuesta más que el riesgo
  • Es un arreglo urgente: un fix tras una flag apagada no arregla nada
  • El cambio es de esquema o de contrato de API: eso se resuelve con compatibilidad hacia atrás
  • Nadie va a apuntar fecha de retirada ni dueño

Entre una flag y una rama larga, gana casi siempre la flag: integras a diario con el riesgo apagado. Entre una flag y un canary, mira qué proteges: el canary cubre la versión nueva entera; la flag, una funcionalidad concreta. Para funciones por plan de pago, mejor un sistema de permisos con sus tests. Y si basta con un valor por entorno, Configuración y entornos lo resuelve sin servicio de flags.

Resumen #

Lo que te llevas

  • Una feature flag separa desplegar (qué código corre) de lanzar (qué ve cada usuario), y convierte muchas vueltas atrás en un cambio de configuración.
  • Release, experimento, operación y permiso se distinguen por su vida y por quién las mueve; solo las dos últimas son permanentes.
  • El código pregunta a una interfaz propia; el origen de las reglas (array, Redis, OpenFeature) cambia sin tocar el negocio, y una flag desconocida devuelve el camino seguro.
  • El rollout por porcentaje usa un hash estable de flag y usuario: el mismo usuario cae siempre en el mismo lado y subir el porcentaje solo añade gente.
  • Cada flag de release nace con dueño y fecha de retirada, y mientras vive se prueban los dos caminos.
