JSON, Protobuf y MessagePack

JSON ganó por una razón que no es técnica: se lee. Los formatos binarios ganan en tamaño y CPU, y lo pagan justo ahí.

JSON ganó por una razón que no es técnica: se lee. Puedes depurar una integración mirando el cuerpo con los ojos, y eso vale más de lo que parece. Los formatos binarios ganan en tamaño y velocidad, y lo pagan justo ahí — conviene saber cuándo el cambio compensa.

La comparación honesta es JSON comprimido

Casi todas las tablas comparan JSON en crudo contra binario, y así el binario gana por goleada. Pero JSON viaja con gzip o brotli, y ahí la diferencia se estrecha muchísimo: es texto muy repetitivo y comprime como pocas cosas. Si tu argumento para cambiar es el tamaño, mide con compresión antes de decidir.

La ventaja que no se reduce con compresión es el coste de CPU: parsear texto, convertir números y construir estructuras cuesta, y Protobuf lee campos binarios de longitud conocida. Con volúmenes altos eso se nota en la factura.

Lo que JSON no sabe representar #

Más allá del rendimiento, JSON tiene agujeros de tipos que producen bugs sutiles en la frontera entre servicios:

Los cuatro clásicos

  • No hay decimal: los importes en coma flotante pierden céntimos
  • No hay enteros de 64 bits fiables: JavaScript los redondea a partir de 2⁵³
  • No hay fechas: son cadenas, y cada uno elige su formato
  • No hay binario: hay que codificar en base64, con un 33 % más de peso

Cómo se esquivan

  • Dinero como entero de céntimos, o como cadena
  • Identificadores grandes como cadena, siempre
  • Fechas en ISO 8601 con zona horaria, sin excepción
  • Ficheros por su URL, no dentro del JSON

El bug de los identificadores grandes

Un identificador de 64 bits enviado como número JSON llega al navegador y JavaScript lo redondea, porque su tipo numérico no llega. El síntoma es desconcertante: el último dígito cambia, y las consultas por ese identificador no encuentran nada. Se manda como cadena y se acabó.

Protobuf: el esquema es la ventaja #

Lo que de verdad aporta Protobuf no es el tamaño: es que el contrato está escrito y es obligatorio. Un fichero .proto genera el código de las dos partes, y un campo mal escrito deja de ser un bug en producción para ser un error de compilación.

ini · pedido.proto 
syntax = "proto3"

message Pedido {
  string id = 1
  int64 importe_centimos = 2
  string estado = 3
  repeated Linea lineas = 4
}

Esos números no son el orden de los campos: son su identidad en el cable. El nombre no viaja; viaja el número. De ahí salen las reglas de compatibilidad: puedes renombrar un campo libremente —el nombre es cosa tuya— y nunca puedes reutilizar un número que estuvo asignado a otra cosa, porque un cliente viejo lo leería como el campo antiguo.

Y el binario no se puede depurar mirándolo

Sin el .proto correspondiente, un mensaje capturado es ruido. Se acabó abrir la pestaña de red y leer la respuesta, y se acabó reproducir una llamada con curl escribiendo el cuerpo a mano. Ese coste es diario y se paga durante toda la vida del sistema.

En colas la ecuación cambia #

Para mensajería hay un factor que no aplica en una API síncrona: los mensajes persisten. Un evento publicado hoy puede releerse dentro de seis meses por un consumidor que aún no existe, y para entonces el esquema habrá cambiado.

Eso hace que el esquema explícito valga más aquí que en HTTP, y explica por qué en el mundo de Kafka hay registros de esquemas: guardan las versiones y validan que un esquema nuevo sea compatible antes de dejar publicar con él. Es lo que evita que un cambio de un equipo rompa a consumidores que no conoce.

Cuándo aplicarlo #

Quédate en JSON cuando…

  • La consume un navegador o un tercero
  • El volumen es normal y comprimes
  • Valoras poder depurar mirando
  • La API es pública: JSON es el mínimo común denominador

Binario cuando…

  • Es tráfico interno de muy alto volumen
  • El coste de CPU en serialización es medible
  • Quieres el contrato verificado en compilación
  • Son eventos que persisten y evolucionarán

Resumen #

Lo que te llevas

  • La comparación honesta es contra JSON comprimido: es texto muy repetitivo y la ventaja de tamaño del binario se estrecha mucho.
  • Lo que no se reduce con compresión es la CPU de parsear: ahí el binario gana siempre.
  • JSON no tiene decimal, ni enteros de 64 bits fiables, ni fechas, ni binario. Dinero en céntimos e identificadores como cadena.
  • En Protobuf viaja el número del campo, no su nombre: renombrar es libre y reutilizar un número es un desastre silencioso.
  • En colas el esquema vale más que en HTTP: los mensajes persisten y los releerán consumidores que hoy no existen.
