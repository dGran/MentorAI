Skills de fase y contratos compartidos

Una skill aislada es fácil de escribir. Veinte skills que se llaman entre sí, comparten pasos y compiten por ser elegidas son un sistema, y como todo sistema necesitan diseño: interfaces claras, piezas reutilizables y alguna forma de comprobar que siguen cuadrando.

La lección skills del curso de Claude Code explicó la anatomía de una skill: descripción, cuerpo y ficheros de apoyo. Esta lección trata el catálogo entero de un método: cómo se reparten las fases, cómo se evita repetir normas entre skills y cómo se elige la skill correcta cuando el usuario no escribe ningún comando.

Una skill por fase #

El esqueleto de un método de entrega son sus fases, y cada fase es una skill: convertir una idea en issues, implementar un issue, revisar el PR, hacer el QA funcional, desplegar. Alrededor van skills de apoyo: auditorías, diagnóstico de un bug, ejecución de varios issues seguidos.

1 specDe la idea a issues con criterios verificables
2 implementDel issue a un PR, con el issue como contrato
3 reviewRevisar el PR contra los criterios y las rules
4 qaEjercitar cada criterio contra la app levantada
5 deployMergear, desplegar y verificar

Cada fase recibe lo que dejó la anterior y deja algo verificable para la siguiente.

Partir por fases tiene una ventaja que no es obvia: cada skill carga solo lo que su fase necesita. Quien implementa no necesita el procedimiento de despliegue, y quien revisa no necesita cómo se redacta un issue.

La descripción decide #

Cuando el usuario no invoca una skill por su nombre, el agente elige leyendo las descripciones. Con muchas skills, la descripción es lo único que distingue «revisar un PR» de «auditar un módulo» o de «triar comentarios de una revisión». Una buena descripción responde a tres preguntas:

Pregunta Ejemplo flojo Ejemplo útil
¿Qué hace?Revisa códigoRevisa un PR abierto contra los criterios del issue y las rules
¿Cuándo usarla?Para revisarTras implementar y antes del QA, o ante «échale un ojo a este PR»
¿Con qué no confundirla?—Para triar comentarios ya escritos, usar review-comments

La frontera con la vecina

La tercera pregunta es la que más se olvida y la que más errores evita. Si dos skills cubren terrenos cercanos, cada descripción nombra a la otra y dice dónde está el límite. El agente deja de dudar, y tú también.

Contratos compartidos #

Varias fases necesitan los mismos pasos: comprobar que el repositorio está limpio, localizar el tablero, leer las rules, ejecutar los checks del proyecto y reportarlos con un formato. Copiar esos pasos en cada skill garantiza que, con el tiempo, cada copia diga una cosa distinta.

La solución es la de cualquier código: extraer lo común. El método mantiene contratos compartidos —ficheros que varias skills referencian— y cada skill solo describe lo propio de su fase.

texto · estructura de skills con contratos compartidos (ficticia) 
skills/
├── comun/
│   ├── preflight.md     pasos previos comunes: remote, árbol limpio, rules, tablero
│   ├── gates.md         cómo se ejecutan y reportan los checks del proyecto
│   └── handoff.md       qué deja una fase en disco para la siguiente
├── implement/SKILL.md   «Ejecuta el preflight compartido (comun/preflight.md)…»
├── review/SKILL.md      «Ejecuta el preflight… Reporta los gates según comun/gates.md»
└── deploy/SKILL.md      «…»

Cuándo sí copiar

Hay una excepción razonable: un dato que una skill necesita tener a mano para poder ejecutarse sola, como la lista exacta de etiquetas que crea. Si se copia, se dice explícitamente en las dos copias, para que quien cambie una sepa que debe cambiar la otra.

Referencias bajo demanda #

El cuerpo de una skill entra completo al usarla, así que tampoco conviene que sea enorme. Lo que solo hace falta en un caso concreto —la plantilla de un documento, la configuración de un hook, el detalle de un caso raro— va a ficheros de referencia dentro de la propia skill, y el cuerpo los enlaza: «la plantilla completa está en references/plantilla.md».

Es el canal «bajo demanda» de la lección anterior aplicado dentro de la skill: el agente lee la referencia cuando la tarea la necesita, y no la paga cuando no.

Del lenguaje natural a la skill #

En el día a día nadie escribe /implement 42: escribe «avanza con el backlog esta noche» o «itera hasta que pasen los tests». Un método maduro incluye un pequeño router de intención: una tabla que traduce frases habituales a la skill o combinación de skills que corresponde.

Si el usuario dice… Se carga… Y no…
«Avanza el backlog», «trabaja esta noche»La skill de ejecutar varios issues bajo contratoImplementar uno solo sin contrato
«Repite hasta que pase»La skill de bucle con límites y estado en discoReintentar sin límite
«Explícame cómo funciona el bucle»Nada: es una preguntaArrancar el bucle

La última fila es tan importante como las demás: una pregunta sobre una skill no la ejecuta. Sin esa regla escrita, un «¿cómo funcionaría desplegar esto?» puede acabar desplegando.

El método se valida a sí mismo #

Un catálogo de skills tiene invariantes que se pueden comprobar con un script: que el nombre declarado coincide con la carpeta, que ninguna descripción supera un tamaño máximo, que todo contrato referenciado existe, que no hay enlaces rotos. El método ejecuta ese script antes de publicar cambios, igual que un proyecto ejecuta sus tests.

bash · comprobación mínima de un catálogo de skills 
for skill in ~/.metodo/skills/*/SKILL.md; do
  dir=$(basename "$(dirname "$skill")")
  name=$(grep -m1 '^name:' "$skill" | sed 's/^name: *//')
  [ "$name" = "$dir" ] || echo "NOMBRE: $dir declara '$name'"
done

Es el mismo principio de todo el curso aplicado al propio método: lo que importa no se confía a que alguien se acuerde, se comprueba.

Cuándo aplicarlo #

Diseña el catálogo así cuando…

  • Tienes más de cinco o seis skills y el agente elige mal
  • Varias skills repiten los mismos pasos previos
  • El equipo habla en lenguaje natural y no usa comandos
  • Las skills cambian a menudo y quieres detectar roturas

Basta con skills sueltas si…

  • Tienes dos o tres skills sin solapes entre ellas
  • Siempre las invocas por comando y sabes cuál usar
  • No comparten pasos y no esperas que crezcan

Resumen #

Lo que te llevas

  • El esqueleto de un método son sus fases, una skill por fase, y cada una carga solo lo que su fase necesita.
  • La descripción decide la elección: qué hace, cuándo usarla y con qué skill vecina no confundirla.
  • Los pasos comunes viven en contratos compartidos que las skills referencian, en lugar de copiarse.
  • El detalle ocasional va a referencias dentro de la skill, que solo se leen cuando hacen falta.
  • Un router de intención traduce el lenguaje natural a skills, una pregunta nunca ejecuta, y un script valida que el catálogo cuadra.
