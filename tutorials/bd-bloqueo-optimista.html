Bloqueo optimista con columna de versión

Dos personas abren el mismo producto, cambian el precio y guardan. La base de datos acepta las dos escrituras sin un solo error y la primera desaparece. Una columna de versión convierte esa pérdida silenciosa en un conflicto que puedes ver y tratar.

El bloqueo pesimista reserva la fila antes de tocarla. El optimista no reserva nada: deja que todos lean y trabajen, y solo al escribir comprueba que nadie se le ha adelantado. Es la única de las dos técnicas que sobrevive al hueco entre «abrir el formulario» y «pulsar guardar».

La escritura que se pierde sin error #

Ana abre la ficha del teclado a las 10:00 y ve 49,90 €. Luis la abre un minuto después y ve lo mismo. Ana aplica una rebaja y guarda 44,90. Luis, que no sabe nada de la rebaja, sube el precio por un cambio del proveedor y guarda 52,00. La última escritura gana, nadie recibe un error y la rebaja de Ana se ha esfumado. Es la lost update que ya viste en concepto en Transacciones y ACID y reproducida en dos terminales.

El SELECT ... FOR UPDATE de la lección anterior no sirve aquí, y el porqué es lo importante: la lectura y la escritura ocurren en dos peticiones HTTP distintas, separadas por minutos de alguien pensando delante de un formulario. Ninguna transacción vive tanto, y aunque pudiera, tendrías una fila bloqueada mientras Ana va a por un café. El bloqueo pesimista protege lo que pasa dentro de una transacción; el optimista protege lo que pasa entre peticiones.

Una versión que viaja con el dato #

Cada fila lleva una columna version. Quien lee se guarda el número; quien escribe pone una condición: «actualiza solo si la versión sigue siendo la que leí, y súbela».

sql · MySQL 8.4 y PostgreSQL 17 
CREATE TABLE productos (
  id INT PRIMARY KEY,
  nombre VARCHAR(50),
  precio DECIMAL(8,2),
  version INT NOT NULL DEFAULT 1
);
INSERT INTO productos VALUES (1, 'Teclado', 49.90, 1);

UPDATE productos SET precio = 44.90, version = version + 1 WHERE id = 1 AND version = 1;
UPDATE productos SET precio = 52.00, version = version + 1 WHERE id = 1 AND version = 1;

La primera es Ana, la segunda Luis con la versión que leyó. Lo que devuelve cada motor:

salida · MySQL 8.4 
Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0

Query OK, 0 rows affected
Rows matched: 0  Changed: 0  Warnings: 0
salida · PostgreSQL 17 
UPDATE 1
UPDATE 0

La comprobación y la escritura son una sola sentencia, y eso es lo que la hace segura: el motor bloquea la fila para ejecutar el UPDATE, así que dos escrituras con la misma versión nunca pueden coincidir las dos. Si Ana tiene su UPDATE sin confirmar, el de Luis espera; cuando Ana confirma, el de Luis vuelve a evaluar el WHERE con la fila nueva y afecta a 0 filas. Lo comprobé en los dos motores con el nivel por defecto (REPEATABLE READ en MySQL, READ COMMITTED en Postgres).

Tu código solo tiene que leer las filas afectadas: 1 es éxito, 0 significa que alguien se adelantó (o que la fila ya no existe).

En Postgres con REPEATABLE READ, el 0 puede llegar como error

Si la transacción de Luis está en REPEATABLE READ y Ana confirma después de que empiece, Postgres no devuelve UPDATE 0, sino ERROR: 40001: could not serialize access due to concurrent update y la transacción queda abortada. Significa lo mismo, pero llega por otro camino: tu código tiene que tratar las dos señales.

Cuando afecta a 0 filas #

Qué hacer con el conflicto depende de una pregunta: ¿alguien tomó una decisión mirando el valor viejo?

RespuestaCuándo encajaCómo
Recargar y reintentarLa operación se calcula desde el estado actual y nadie la decidió mirando el dato: sumar puntos, aplicar un cupónReleer en una transacción nueva y repetir, con un límite de intentos
FusionarLos cambios no se pisan: Ana tocó el precio y Luis la descripciónReaplicar solo los campos que cambió el usuario sobre la versión fresca
Devolver el conflictoUna persona decidió sobre un valor que ya no existe409 (o 412 si usas If-Match) con el estado actual para que decida otra vez

Para fusionar necesitas saber qué cambió el usuario respecto a la versión que leyó, no solo el formulario final. Sin ese diff no sabes si su 52,00 es una decisión o el valor que ya estaba en pantalla.

Doctrine: #[ORM\Version] #

Doctrine lo trae de serie: marcas un campo con #[ORM\Version] y el ORM escribe el WHERE version = ? y lee las filas afectadas por ti.

php · Producto.php 
<?php

declare(strict_types=1);

use Doctrine\ORM\Mapping as ORM;

#[ORM\Entity]
#[ORM\Table(name: 'productos')]
class Producto
{
    #[ORM\Id]
    #[ORM\Column]
    private int $id;

    #[ORM\Column(type: 'decimal', precision: 8, scale: 2)]
    private string $precio;

    #[ORM\Version]
    #[ORM\Column(type: 'integer')]
    private int $version;

    public function cambiarPrecio(string $precio): void
    {
        $this->precio = $precio;
    }

    public function version(): int
    {
        return $this->version;
    }
}

Con dos EntityManager cargando el mismo producto, este es el SQL que registró Doctrine ORM 3.7 al hacer flush() en cada uno:

sql · log de Doctrine contra MySQL 8.4 
UPDATE productos SET precio = ?, version = version + 1 WHERE id = ? AND version = ?
SELECT version FROM productos WHERE id = ?
UPDATE productos SET precio = ?, version = version + 1 WHERE id = ? AND version = ?

El primer flush() sube la versión y la relee para que la entidad quede al día. El segundo afecta a 0 filas y Doctrine lanza OptimisticLockException con el mensaje The optimistic lock on an entity failed; getEntity() te dice cuál. Ojo al detalle que más muerde: después de la excepción, isOpen() devuelve false. El EntityManager queda cerrado: su unit of work ya no sirve y reintentar exige uno nuevo.

También puedes comprobar la versión al leer, sin esperar al flush(), pasándole a find() la que trae el cliente:

php · CambiarPrecio.php 
<?php

declare(strict_types=1);

use Doctrine\DBAL\LockMode;
use Doctrine\ORM\EntityManagerInterface;

final class CambiarPrecio
{
    public function __construct(private readonly EntityManagerInterface $entityManager)
    {
    }

    public function __invoke(int $id, int $versionLeida, string $precio): int
    {
        $producto = $this->entityManager->find(Producto::class, $id, LockMode::OPTIMISTIC, $versionLeida)
            ?? throw new ProductoNoEncontrado($id);

        $producto->cambiarPrecio($precio);
        $this->entityManager->flush();

        return $producto->version();
    }
}

Si la versión no cuadra, find() lanza la misma excepción con un mensaje más útil: The optimistic lock failed, version 2 was expected, but is actually 3. Las dos comprobaciones se complementan: find() rechaza pronto lo que ya está viejo y el flush() cierra el hueco entre la lectura y la escritura.

Eloquent: hacerlo a mano #

Eloquent no trae columna de versión. Y save() no pregunta: si otro cambió la fila entre tu lectura y tu escritura, devuelve true igualmente y pisa su cambio. Lo comprobé con Laravel 13.

php · antes: la última escritura gana 
<?php

declare(strict_types=1);

$producto = Producto::findOrFail($id);
$producto->precio = $precio;
$producto->save();

La versión manual es el mismo UPDATE condicional a través del query builder. increment() genera el version = version + 1 y devuelve las filas afectadas:

php · después: escritura condicionada a la versión 
<?php

declare(strict_types=1);

$filasAfectadas = Producto::query()
    ->whereKey($id)
    ->where('version', $versionLeida)
    ->increment('version', 1, ['precio' => $precio]);

if ($filasAfectadas === 0) {
    throw new VersionObsoleta($id, $versionLeida);
}

El SQL que sale: update `productos` set `version` = `version` + 1, `precio` = ? where `productos`.`id` = ? and `version` = ?. El precio de hacerlo fuera de save() es que no se disparan los eventos del modelo; si dependes de ellos, encapsula esta escritura en un único método del repositorio y lanza ahí lo que necesites.

La versión en HTTP: ETag e If-Match #

La versión tiene que hacer el viaje completo: del servidor al cliente al leer y de vuelta al escribir. En un formulario HTML basta un campo oculto y responder 409 si no cuadra. En una API, HTTP ya tiene el mecanismo: el GET devuelve la versión en la cabecera ETag, el cliente la reenvía en If-Match, y si ya no coincide la respuesta es 412 Precondition Failed. Si el cliente ni siquiera la manda, 428 Precondition Required obliga a que la mande.

php · ProductoController.php 
<?php

declare(strict_types=1);

final class ProductoController extends AbstractController
{
    #[Route('/api/productos/{id}', methods: ['PATCH'])]
    public function cambiarPrecio(int $id, Request $request, CambiarPrecio $cambiarPrecio): JsonResponse
    {
        $ifMatch = $request->headers->get('If-Match');

        if ($ifMatch === null) {
            return new JsonResponse(null, Response::HTTP_PRECONDITION_REQUIRED);
        }

        try {
            $nuevaVersion = $cambiarPrecio($id, (int) trim($ifMatch, '"'), $request->getPayload()->getString('precio'));
        } catch (OptimisticLockException) {
            return new JsonResponse(['error' => 'El producto ha cambiado desde que lo leíste'], Response::HTTP_PRECONDITION_FAILED);
        }

        return new JsonResponse(null, Response::HTTP_NO_CONTENT, ['ETag' => sprintf('"%d"', $nuevaVersion)]);
    }
}

El ETag va entre comillas ("3"), y el éxito devuelve el nuevo para encadenar otra edición sin releer.

Errores típicos #

Recargar dentro de la misma transacción, en MySQL

Con REPEATABLE READ, tras el UPDATE que afecta a 0 filas, un SELECT normal en la misma transacción me devolvió la versión 2: la foto de su primera lectura. El mismo SELECT ... FOR SHARE devolvió la 3. Si reintentas, hazlo en una transacción nueva o reintentarás eternamente con el dato viejo.

  • La versión no viaja. Si el controlador carga la entidad al recibir el formulario y usa su propia versión, compara la fila consigo misma y nunca falla. La versión tiene que ser la que el usuario vio.
  • Reintentar a ciegas una edición humana. Recargar y volver a escribir el 52,00 de Luis es exactamente la lost update, con un paso más.
  • Escribir por detrás del ORM. Un UPDATE de DQL no toca la versión: lo ejecuté y siguió en 5. Lo mismo vale para SQL a mano, importaciones y comandos. Si escriben esa tabla, que incrementen la versión.
  • No subir la versión en MySQL. MySQL cuenta filas cambiadas, no encontradas: un UPDATE con el mismo valor da Rows matched: 1 Changed: 0 y 0 filas afectadas, donde Postgres responde UPDATE 1. Incrementar siempre la versión garantiza que la fila cambia.
  • Seguir usando el EntityManager cerrado tras la excepción, en un worker o un comando largo.

Cómo comprobarlo #

Dos terminales contra un contenedor desechable bastan para ver la espera y el 0:

bash · dos sesiones contra MySQL 8.4 
docker run -d --rm --name bd-mysql -e MYSQL_ROOT_PASSWORD=x mysql:8.4
docker exec -it bd-mysql mysql -uroot -px

Crea una base de datos con la tabla de arriba, abre otra sesión igual en una segunda terminal y sigue este orden:

1 Terminal ASTART TRANSACTION; UPDATE ... WHERE id = 1 AND version = 1;
2 Terminal BEl mismo UPDATE con version = 1: se queda esperando
3 Terminal BQuery OK, 0 rows affected

El UPDATE de B espera al de A y, al despertar, ya no encuentra la versión 1.

En el código, el test que lo atrapa es de integración: dos EntityManager cargan el mismo producto, el primero hace flush() y el test espera OptimisticLockException en el segundo. Si alguien quita el #[ORM\Version], el test falla.

Cuándo aplicarlo #

Optimista cuando…

  • La lectura y la escritura están en peticiones distintas: formularios, APIs, apps móviles
  • Los conflictos son raros: cada usuario suele editar cosas distintas
  • Ante un conflicto, una persona puede decidir

Pesimista cuando…

  • Muchas escrituras compiten por las mismas filas y los reintentos se dispararían
  • Todo ocurre dentro de una transacción corta del servidor
  • Repetir el trabajo es caro: cálculos largos o llamadas externas

La alternativa: que no haga falta ninguno

Si la escritura se expresa entera en una sentencia, no necesitas leer antes: UPDATE stock SET unidades = unidades - 1 WHERE id = 1 AND unidades > 0 afecta a 1 fila mientras queda stock y a 0 cuando se acaba. Es la misma idea condicional, sin versión. Y si el problema es que una operación llegue dos veces, lo que buscas es idempotencia, no un bloqueo; los locks entre servicios están en locks distribuidos.

Resumen #

Lo que te llevas

  • El bloqueo optimista protege el hueco entre peticiones, donde ninguna transacción llega: UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?.
  • 0 filas afectadas es el conflicto. En Postgres con REPEATABLE READ puede llegar como error 40001.
  • Reintenta lo que se calcula solo, fusiona lo que no se pisa y devuelve 409 o 412 cuando decidió una persona.
  • Doctrine lo hace con #[ORM\Version] y lanza OptimisticLockException, cerrando el EntityManager. En Eloquent, increment() condicionado y comprobar las filas.
  • En una API, la versión viaja como ETag y vuelve en If-Match.
