Migraciones sin caída: DDL online por motor

Lanzas un ALTER TABLE que MySQL ejecuta en una décima de segundo y, aun así, la tabla deja de responder durante un minuto. El cambio era instantáneo; lo que no lo era es la cola que se formó detrás de él.

Expandir y contraer resuelve que dos versiones del código convivan con el mismo esquema, no cuánto bloquea cada paso. Esta lección va de eso: qué cerrojo toma cada ALTER en MySQL 8.4 y PostgreSQL 17, y cómo mover un millón de filas sin que nadie lo note.

Instantáneo no significa sin esperas #

Despliegues sin caída enseña a partir un cambio destructivo en dos despliegues, y Migraciones de esquema, por qué versionarlas. La pregunta ahora es otra: aunque el cambio sea compatible, ¿cuánto tiempo deja la tabla sin servir?

Hay dos partes. Una es el trabajo: reescribir la tabla, construir un índice, validar filas. Otra, el cerrojo que el cambio necesita para empezar o terminar. La primera depende del algoritmo; la segunda, de lo que haga el resto de la aplicación en ese momento, y provoca casi todas las caídas.

El metadata lock de MySQL #

Cada sentencia que toca una tabla en MySQL toma un metadata lock (MDL), y la transacción lo conserva hasta el COMMIT. Un SELECT toma uno compartido; un ALTER TABLE necesita uno exclusivo, aunque sea un instante. La trampa: las peticiones de MDL hacen cola. Mientras el ALTER espera, todo lo que llega detrás, lecturas incluidas, espera detrás de él.

Con tres sesiones sobre un millón de filas: A abre una transacción, lee una fila y se queda 20 segundos parada; B lanza un ADD COLUMN con ALGORITHM=INSTANT; C solo quiere leer otra fila:

sql · MySQL 8.4 · sesión D, mientras A sigue abierta 
SELECT id, time, state, LEFT(info, 40) AS info
FROM information_schema.processlist
WHERE db = 'tienda' AND command = 'Query';

-- | 10 | 7 | User sleep                      | SELECT SLEEP(20)
-- | 11 | 5 | Waiting for table metadata lock | ALTER TABLE pedidos ADD COLUMN notas ...
-- | 12 | 3 | Waiting for table metadata lock | SELECT total FROM pedidos WHERE id = 2

SELECT lock_type, lock_status, owner_thread_id
FROM performance_schema.metadata_locks
WHERE object_name = 'pedidos';

-- | SHARED_READ       | GRANTED | 53 |
-- | SHARED_UPGRADABLE | GRANTED | 54 |
-- | EXCLUSIVE         | PENDING | 54 |
-- | SHARED_READ       | PENDING | 55 |

El SELECT de C tardó 16 segundos en leer una fila por clave primaria. Nada era lento: había una transacción olvidada y un ALTER esperando. Con tráfico real, en esos segundos se agota el pool de conexiones.

La defensa es no esperar. lock_wait_timeout limita cuánto aguarda una sentencia por un MDL, y su valor por defecto es 31.536.000 segundos: un año. Bájalo en la sesión de la migración y el ALTER se rinde antes de formar la cola:

sql · MySQL 8.4 · sesión B, con A todavía abierta 
SET SESSION lock_wait_timeout = 5;
ALTER TABLE pedidos ADD COLUMN canal VARCHAR(20) NULL, ALGORITHM=INSTANT;

-- ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction

Ese fallo es barato: reintentas luego. Pero esos cinco segundos sí hubo cola: que el margen sea corto.

INSTANT, INPLACE y COPY #

Resuelta la espera, queda el trabajo. InnoDB aplica un ALTER de tres formas, y LOCK dice qué permite a los demás mientras dura. Medido sobre el millón de filas:

CambioAlgoritmo que aceptóMedido
Añadir, borrar o renombrar columnaINSTANT: solo toca el diccionario0,09 s
La misma columna forzando INPLACEReconstruye la tabla, con escrituras permitidas4,2 s
Añadir un índiceINPLACE, LOCK=NONE; INSTANT da error1,7 s, un INSERT a la vez no esperó
VARCHAR(20) a VARCHAR(60)INPLACE, LOCK=NONE0,1 s
VARCHAR(20) a VARCHAR(64)Solo COPYerror con INPLACE
DECIMAL(10,2) a DECIMAL(12,2)Solo COPY, y LOCK=NONE no se admite15,5 s; un INSERT esperó 14,5 s

El salto de 60 a 64 no es caprichoso: en utf8mb4 cada carácter reserva hasta 4 bytes, y desde 256 bytes la longitud se guarda en dos bytes en vez de uno. Cambia el formato de la fila.

Escribe siempre ALGORITHM y LOCK. Con ellos, si el motor no puede, falla en el acto; sin ellos, elige el algoritmo más barato que pueda y, si es COPY, para las escrituras mientras copia:

sql · MySQL 8.4 · lo que responde el motor 
ALTER TABLE pedidos ADD INDEX idx_cliente (cliente_id), ALGORITHM=INSTANT;
-- ERROR 1845 (0A000): ALGORITHM=INSTANT is not supported for this operation.
--   Try ALGORITHM=COPY/INPLACE.

ALTER TABLE pedidos MODIFY total DECIMAL(12,2) NOT NULL, ALGORITHM=INPLACE, LOCK=NONE;
-- ERROR 1846 (0A000): ALGORITHM=INPLACE is not supported.
--   Reason: Cannot change column type INPLACE. Try ALGORITHM=COPY.

ALTER TABLE pedidos MODIFY total DECIMAL(12,2) NOT NULL, ALGORITHM=COPY, LOCK=NONE;
-- ERROR 1846 (0A000): LOCK=NONE is not supported.
--   Reason: COPY algorithm requires a lock. Try LOCK=SHARED.

INSTANT tiene cupo

Cada columna añadida o borrada con INSTANT crea una versión de fila, y una tabla admite 64; al llegar, ERROR 4092: Maximum row versions reached. Sin algoritmo fijado no hay error: reconstruye la tabla sin avisar. Lo cuenta total_row_versions en information_schema.innodb_tables.

Cuándo hace falta gh-ost o pt-osc #

Si el cambio solo admite COPY y la tabla es grande, las escrituras quedan paradas toda la copia. Tampoco INPLACE es gratis con réplicas: aplican el ALTER cuando el primario lo terminó, y se quedan atrás todo lo que dure.

Para eso están pt-online-schema-change, de Percona Toolkit, y gh-ost, de GitHub. Crean una tabla con el esquema final, copian las filas por trozos y siguen los cambios que llegan: pt-osc con triggers, gh-ost leyendo el binlog. Al final intercambian las tablas con un RENAME, que también pide su MDL exclusivo. A cambio, puedes pausarlas, frenarlas si las réplicas se retrasan y abortar sin dejar nada a medias.

Postgres: la misma cola y lock_timeout #

En Postgres el efecto es idéntico. Casi todo ALTER TABLE pide un AccessExclusiveLock, incompatible hasta con el AccessShareLock de un SELECT, y las peticiones hacen cola. El mismo experimento:

sql · PostgreSQL 17 · quién bloquea a quién 
SELECT pid, mode, granted FROM pg_locks WHERE relation = 'pedidos'::regclass;
--  92 | AccessShareLock     | t
--  99 | AccessExclusiveLock | f
-- 106 | AccessShareLock     | f

SELECT pid, pg_blocking_pids(pid) FROM pg_stat_activity WHERE wait_event_type = 'Lock';
--  99 | {92}
-- 106 | {99}

El SELECT del 106 tardó 10 segundos. Aquí lock_timeout vale 0 por defecto, espera indefinida; fíjalo justo antes de cada DDL:

sql · PostgreSQL 17 
SET lock_timeout = '2s';
ALTER TABLE pedidos ADD COLUMN canal text;
-- Time: 2000.595 ms
-- ERROR:  55P03: canceling statement due to lock timeout

Índices, defaults y NOT VALID #

Índices. Un CREATE INDEX normal toma un ShareLock, que deja leer pero no escribir: un INSERT lanzado a la vez esperó a que terminara el índice. CREATE INDEX CONCURRENTLY deja escribir, con tres condiciones. No puede ir dentro de una transacción (cannot run inside a transaction block), y muchas herramientas envuelven cada migración en una. Espera a todas las transacciones anteriores, aunque sean de otra tabla: aparece en pg_stat_activity con el evento virtualxid. Y si falla, por ejemplo un único con duplicados, deja el índice con indisvalid = false, inútil para leer pero mantenido en cada escritura: hay que borrarlo y repetir.

Columna con default. Si el default no es volátil, Postgres lo guarda en el catálogo sin tocar filas: DEFAULT 'pendiente' o now(), 2 ms y el mismo fichero. clock_timestamp() o gen_random_uuid(), 2 y 5 segundos reescribiendo la tabla con el cerrojo exclusivo.

Restricciones. Añadir una clave foránea o un CHECK comprueba todas las filas con el cerrojo puesto. NOT VALID la crea al momento, ya aplicada a las filas nuevas, y VALIDATE CONSTRAINT revisa las viejas después con un ShareUpdateExclusiveLock, que deja leer y escribir.

sql · PostgreSQL 17 · NOT NULL sin recorrer la tabla 
ALTER TABLE pedidos ADD CONSTRAINT chk_pais_no_nulo CHECK (pais IS NOT NULL) NOT VALID;
ALTER TABLE pedidos VALIDATE CONSTRAINT chk_pais_no_nulo;

SET client_min_messages = debug1;
ALTER TABLE pedidos ALTER COLUMN pais SET NOT NULL;
-- DEBUG:  existing constraints on column "pedidos.pais" are sufficient
--         to prove that it does not contain nulls

ALTER TABLE pedidos DROP CONSTRAINT chk_pais_no_nulo;

SET NOT NULL sigue pidiendo el cerrojo exclusivo, pero con el CHECK validado no recorre la tabla.

Rellenar datos por lotes #

Rellenar la columna con un único UPDATE es una transacción que bloquea cada fila que toca hasta el final. Lo medí en MySQL: el UPDATE del millón de filas tardó casi 11 segundos, y una actualización de una sola fila que llegó a mitad esperó 8,7.

La alternativa: recorrer la clave primaria por rangos y confirmar cada uno. En lotes de 5.000 filas cada UPDATE tardó unos 0,2 segundos; el total es mayor, pero ningún cerrojo dura más. El IS NULL lo hace reanudable.

La migración en PHP #

Así suele llegar a revisión una migración que añade el importe en céntimos:

php · AddAmountInCents.php (antes) 
<?php

declare(strict_types=1);

final class AddAmountInCents
{
    public function __construct(private readonly PDO $connection)
    {
    }

    public function up(): void
    {
        $this->connection->exec('ALTER TABLE pedidos ADD COLUMN total_centimos BIGINT NULL');
        $this->connection->exec('UPDATE pedidos SET total_centimos = total * 100');
    }
}

Tres problemas en dos líneas: sin lock_wait_timeout puede esperar un año formando cola; sin ALGORITHM puede reconstruir la tabla sin avisar; y el relleno es una sola transacción gigante. La versión corregida separa el esquema del relleno:

php · AddAmountInCents.php y BackfillAmountInCents.php (después) 
<?php

declare(strict_types=1);

final class AddAmountInCents
{
    private const int LOCK_WAIT_SECONDS = 3;

    public function __construct(private readonly PDO $connection)
    {
    }

    public function up(): void
    {
        $this->connection->exec(sprintf('SET SESSION lock_wait_timeout = %d', self::LOCK_WAIT_SECONDS));
        $this->connection->exec('ALTER TABLE pedidos ADD COLUMN total_centimos BIGINT NULL, ALGORITHM=INSTANT');
    }
}

final class BackfillAmountInCents
{
    private const int BATCH_SIZE = 5000;
    private const int PAUSE_MICROSECONDS = 50_000;

    public function __construct(private readonly PDO $connection)
    {
    }

    public function run(): void
    {
        $lastId = (int) $this->connection->query('SELECT COALESCE(MAX(id), 0) FROM pedidos')->fetchColumn();
        $update = $this->connection->prepare(
            'UPDATE pedidos SET total_centimos = total * 100
             WHERE id BETWEEN :first AND :last AND total_centimos IS NULL'
        );

        for ($firstId = 1; $firstId <= $lastId; $firstId += self::BATCH_SIZE) {
            $update->execute(['first' => $firstId, 'last' => $firstId + self::BATCH_SIZE - 1]);
            usleep(self::PAUSE_MICROSECONDS);
        }
    }
}

El relleno exige que el código desplegado ya escriba total_centimos en las filas nuevas, y que no haya una transacción alrededor, para que cada lote se confirme solo. En Postgres, la primera clase usaría SET lock_timeout, y un índice CONCURRENTLY iría en una migración no transaccional.

Errores típicos #

Los que tumban producción

  • Creer que INSTANT o un default constante no bloquean: no reescriben, pero piden el cerrojo exclusivo y forman cola detrás de cualquier transacción abierta.
  • Lanzar DDL sin lock_wait_timeout o lock_timeout, con los valores por defecto de un año y de espera infinita.
  • Omitir ALGORITHM y LOCK, y descubrir el COPY cuando las escrituras ya se han parado.
  • Dejar en Postgres un índice inválido tras un CONCURRENTLY fallido, que se paga en cada escritura.

Cómo comprobarlo #

Antes del DDL, busca transacciones largas: en MySQL, information_schema.innodb_trx por trx_started; en Postgres, pg_stat_activity por xact_start, sobre todo las idle in transaction.

Durante el cambio, performance_schema.metadata_locks y pg_blocking_pids dicen quién espera a quién. Después, en MySQL el COPY se delata porque responde con las filas copiadas en vez de 0 rows affected; en Postgres, que no quede ningún índice con indisvalid = false.

Y ensaya contra una copia con volumen real y una transacción abierta en otra terminal. Transacciones y ACID explica por qué esa transacción retiene sus cerrojos, y Índices compuestos y de cobertura, cuál merece la pena.

Cuándo aplicarlo #

Hazlo con este cuidado cuando…

  • La tabla recibe tráfico mientras despliegas
  • Tiene millones de filas o réplicas que no pueden retrasarse
  • Hay procesos con transacciones largas: colas, informes, exportaciones
  • El cambio es un tipo de columna, un índice o una restricción nueva

No hace falta cuando…

  • La tabla es pequeña y el ALTER tarda milisegundos incluso con COPY
  • Tienes una ventana de mantenimiento pactada y sin usuarios

La alternativa sencilla

Sin montar gh-ost, el mínimo que evita la mayoría de incidentes son dos líneas: timeout de cerrojo antes de cada DDL y algoritmo explícito en cada ALTER de MySQL. Lo que falle, falla rápido y sin cola.

Resumen #

Lo que te llevas

  • Un DDL rápido puede tumbar la tabla igual: espera su cerrojo exclusivo detrás de una transacción abierta y todo lo demás espera detrás de él.
  • Fija lock_wait_timeout en MySQL y lock_timeout en Postgres antes de cada DDL: fallar en segundos es mejor que una cola sin fin.
  • Escribe ALGORITHM y LOCK en cada ALTER de MySQL para que un COPY falle en vez de colarse.
  • Si el cambio solo admite COPY en una tabla grande, o las réplicas no aguantan el retraso, usa gh-ost o pt-online-schema-change.
  • En Postgres: índices con CONCURRENTLY, defaults no volátiles y restricciones con NOT VALID más VALIDATE CONSTRAINT.
  • Rellena por rangos de clave primaria, en transacciones cortas y reanudables.
