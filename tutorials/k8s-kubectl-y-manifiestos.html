kubectl y manifiestos

Se acabó la teoría: en esta lección montas un clúster Kubernetes en tu máquina (sí, en un minuto, con Docker que ya tienes), aprendes los seis comandos que cubren el 90% del día a día, y aplicas tu primer manifiesto viendo al bucle de reconciliación trabajar para ti.

Todo lo de esta lección es ejecutable en tu portátil con Docker instalado. Hazlo de verdad: la diferencia entre leer kubectl y haberlo tecleado es la que va de conocer Kubernetes a saber usarlo.

Un clúster en tu máquina: kind #

kind (Kubernetes IN Docker) levanta un clúster completo donde cada «nodo» es un contenedor Docker. Es el estándar para desarrollo y CI: idéntico en API a un clúster real, desechable en segundos.

bash · clúster local en un minuto 
# instalar kind y kubectl (Linux)
curl -Lo ./kind https://kind.sigs.k8s.io/dl/latest/kind-linux-amd64
chmod +x kind && sudo mv kind /usr/local/bin/
sudo snap install kubectl --classic

kind create cluster --name academia   # ~1 min
kubectl cluster-info                  # ¿responde? ya tienes Kubernetes

El clúster es desechable a propósito

kind delete cluster --name academia y no queda nada. Rompe sin miedo: la mejor forma de aprender k8s es destrozar un clúster que cuesta un minuto recrear. Es tu entorno de laboratorio, no una mascota.

kubectl: los seis del día a día #

kubectl habla con la API del clúster. Tiene cientos de subcomandos; estos seis son tu 90%:

Comando Para qué Equivalente mental
kubectl get pods Listar objetos y su estado (añade -w para verlos cambiar en vivo) docker ps / ls
kubectl describe pod X El detalle completo + los eventos: la primera parada cuando algo no arranca el historial clínico
kubectl logs X El stdout del contenedor (-f para seguirlo, --previous para el que murió) docker logs
kubectl exec -it X -- bash Una shell dentro del pod, para mirar desde dentro docker exec / ssh
kubectl apply -f fichero.yaml Declarar: «este es el estado que quiero» (crea o actualiza, da igual) el commit del clúster
kubectl delete -f fichero.yaml Retirar la declaración (y el bucle desmonta lo que había) el revert

Tu primer manifiesto #

Un manifiesto es la declaración de la lección anterior, en YAML. Todos comparten esqueleto — apiVersion, kind (qué objeto es), metadata (nombre y etiquetas) y spec (lo que quieres) — y este es el Deployment + Service mínimo honesto:

yaml · web.yaml — deployment y service 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:                # la plantilla de pod que el Deployment clona
    metadata:
      labels:
        app: web           # la etiqueta que lo une todo
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web               # "balancea hacia los pods con esta etiqueta"
  ports:
    - port: 80

Fíjate en el pegamento: el Service no conoce al Deployment — ambos se encuentran por la etiqueta app: web. Las etiquetas son el sistema de referencias de todo Kubernetes, y el 50% de los «no llega tráfico» de principiante son un selector que no casa con las labels de la plantilla.

apply y el bucle en acción #

bash · declarar y ver converger 
kubectl apply -f web.yaml
kubectl get pods -w        # miralos nacer: Pending → ContainerCreating → Running

# el experimento clave — mata un pod a proposito:
kubectl delete pod web-xxxxx-yyyyy
kubectl get pods           # ya hay otro nuevo: el bucle repuso la replica

# y el acceso rapido para probar sin Ingress:
kubectl port-forward service/web 8080:80   # http://localhost:8080

El experimento de matar el pod es la lección entera en diez segundos: tú no reiniciaste nada — declaraste 2 réplicas y el clúster defiende esa declaración contra ti mismo si hace falta. Cuando lo veas repuesto, el modelo mental habrá hecho clic.

El ritual de depuración #

Cuando algo no funciona, el orden siempre es el mismo — de la vista general al detalle:

  • 1. get pods — ¿en qué estado está? Pending (no cabe o no encuentra imagen que descargar), ImagePullBackOff (la imagen no existe o no hay permisos), CrashLoopBackOff (arranca y muere en bucle).
  • 2. describe pod — la sección Events del final te dice el porqué del estado en prosa: «Failed to pull image…», «Insufficient memory…».
  • 3. logs (con --previous si crashea) — el error de TU aplicación: el stack trace de siempre, la config que falta.
  • 4. exec — dentro del pod: ¿resuelve el DNS del Service? ¿están las variables de entorno? ¿existe el fichero?

Hábitos que te salvarán #

Dos, heredados de todo lo que ya sabes. Los manifiestos viven en git — son la declaración de tu infraestructura: se versionan, se revisan en PR y se aplican desde el repo, nunca editados a mano contra el clúster (la deriva entre lo que hay y lo que git dice es el infierno clásico; es el mismo argumento del IaC del curso de infra). Y cuidado con el contexto: kubectl apunta a un clúster a la vez (kubectl config current-context) — el clásico susto de aplicar en producción lo que iba al kind local se evita mirando el contexto antes de cada apply serio.

Cuándo aplicarlo #

Práctica con kind cuando…

  • Quieras probar cualquier cosa de k8s sin miedo ni coste
  • Reproduzcas en local un problema del clúster del trabajo
  • En CI: levantar un kind, desplegar, probar, destruir

Evita…

  • kubectl edit / cambios a mano en el clúster: la deriva respecto a git te perseguirá
  • Aplicar sin mirar el contexto: el susto clásico tiene prevención de un comando
  • Copiar YAMLs de internet sin entender su selector y sus labels

Resumen #

Lo que te llevas

  • kind te da un Kubernetes real y desechable sobre Docker: tu laboratorio para romper sin miedo.
  • Seis comandos cubren el día a día: get, describe, logs, exec, apply, delete — y describe → logs → exec es el ritual de depuración.
  • Todo manifiesto es apiVersion + kind + metadata + spec, y las etiquetas son el pegamento: selector que no casa = tráfico que no llega.
  • Mata un pod y míralo renacer: el clúster defiende tu declaración incluso contra ti. Ese es el clic del modelo declarativo.
  • Manifiestos en git (nunca ediciones a mano contra el clúster) y un ojo en current-context antes de cada apply serio.
