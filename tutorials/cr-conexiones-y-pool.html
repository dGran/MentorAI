Conexiones y el coste de abrir

Abrir una conexión a la base de datos parece gratis porque en local lo parece. En producción cuesta una ida y vuelta de red, un saludo del protocolo, una autenticación y memoria reservada en el servidor. Y en PHP, por cómo funciona su modelo de ejecución, ese coste se paga de una forma peculiar que conviene entender.

Qué cuesta abrir una conexión #

No es una operación: son cuatro, y la última es la que muerde de verdad cuando hay volumen.

1 Handshake TCPUna ida y vuelta. Más si hay TLS: dos o tres.
2 AutenticaciónOtra ida y vuelta, con hash de credenciales
3 Sesión inicializadaCharset, zona horaria, modo SQL
4 Memoria en el servidorCada conexión reserva sus buffers, la tenga ocupada o no

Los tres primeros cuestan milisegundos. El cuarto es el que pone un techo a cuántas puedes tener.

Más conexiones no es más rendimiento

Pasado el punto en que la base de datos tiene todos sus núcleos ocupados, añadir conexiones solo añade contención: más cambios de contexto, más competencia por los bloqueos y más memoria por conexión. El rendimiento sube hasta un punto y baja después. El error clásico es subir max_connections ante un error de «demasiadas conexiones», que es tratar el síntoma.

PHP no tiene pool (y por qué importa menos de lo que parece) #

En una aplicación Java o Go, el proceso vive largo y mantiene un pool compartido de, digamos, veinte conexiones para todos sus hilos. En PHP con FPM cada petición corre en un proceso que se limpia al terminar: no hay nada que compartir entre peticiones.

La compensación es que el modelo de FPM ya limita la concurrencia por sí mismo: si pm.max_children es 50, no puede haber más de 50 peticiones a la vez y, por tanto, no más de 50 conexiones desde ese servidor. El pool de PHP es el pool de procesos de FPM, y ahí es donde se dimensiona.

bash · la cuenta que hay que hacer 
servidores_web x pm.max_children
  + workers_de_cola
  + crons_simultaneos
  + margen_para_administracion
  = conexiones que la base de datos tiene que soportar

Esa suma se olvida casi siempre, y el resultado es el mismo: todo va bien hasta que escalas de tres a seis servidores web y la base de datos empieza a rechazar conexiones sin que nadie haya tocado nada de la aplicación.

Conexiones persistentes: la trampa #

PDO ofrece PDO::ATTR_PERSISTENT, que reutiliza la conexión entre peticiones del mismo proceso de FPM. Ahorra el saludo, y trae problemas que no compensan casi nunca:

Lo que ahorra

  • El handshake y la autenticación por petición
  • Notable si la base de datos está lejos o usa TLS

Lo que arrastra

  • Estado sucio: una transacción abierta sobrevive a la petición
  • Bloqueos y variables de sesión que se quedan puestos
  • Tablas temporales que ya no esperabas
  • Conexiones ocupadas por procesos inactivos

Un error a mitad de transacción se lleva por delante la siguiente petición

Si el script muere con una transacción abierta, la conexión persistente vuelve al pool con esa transacción viva. La siguiente petición que la coja hereda los bloqueos y un estado que no entiende. Son los bugs más difíciles de reproducir que vas a ver, porque dependen de qué proceso te tocó.

Si el coste de conexión es de verdad tu problema, la respuesta buena no es ATTR_PERSISTENT: es un pooler externo —PgBouncer en PostgreSQL, ProxySQL en MySQL— que mantiene un pool limpio delante de la base de datos y multiplexa las conexiones de todos tus procesos. Es una pieza más que operar, y resuelve el problema de verdad.

Ocupar la conexión el menor tiempo posible #

Con o sin pool, la regla que más rinde es la misma: una conexión ocupada es una que no tiene nadie más. Y la forma más habitual de ocuparla de más es tener una transacción abierta mientras haces algo que no es base de datos:

php · la transacción que dura demasiado 
<?php

$this->conexion->beginTransaction();

$pedido = $this->pedidos->crear($carrito);

$this->pasarela->cobrar($pedido);
$this->correo->enviarConfirmacion($pedido);

$this->conexion->commit();

Esa transacción dura lo que tarden la pasarela y el servidor de correo: puede ser un segundo, o treinta si van lentos. Durante todo ese rato mantiene bloqueos y ocupa una conexión. La regla es ninguna llamada de red dentro de una transacción: se confirma primero y el resto se hace fuera, con el outbox si hace falta garantizar que sale.

Cuándo aplicarlo #

Mira las conexiones cuando…

  • Aparecen errores de «demasiadas conexiones» bajo carga
  • Vas a añadir servidores web o workers
  • La base de datos está en otra red o usa TLS
  • Ves conexiones en sleep ocupando sitio

No es tu problema cuando…

  • El tiempo se va dentro de las consultas, no en abrirlas
  • La concurrencia real está muy por debajo del límite
  • Es una aplicación pequeña con un solo servidor

Resumen #

Lo que te llevas

  • Abrir una conexión son cuatro cosas, y la cara es la memoria que reserva el servidor: eso pone el techo.
  • Más conexiones no es más rendimiento: pasado el punto de saturación, sube la contención y baja el rendimiento.
  • En PHP el pool es el de procesos de FPM. La cuenta que se olvida es sumar servidores web, workers y crons.
  • Las conexiones persistentes de PDO arrastran estado sucio entre peticiones. Si el problema es real, la respuesta es un pooler externo.
  • Ninguna llamada de red dentro de una transacción: mantiene bloqueos y ocupa una conexión durante todo lo que tarde el tercero.
