CI para un proyecto PHP

La anatomía ya la conoces; ahora toca llenarla con las herramientas de tu stack: Composer, php-cs-fixer, PHPStan, PHPUnit y Docker. Al final de esta lección tendrás el workflow completo que valida un proyecto PHP de verdad.

Cada lenguaje tiene su ecosistema de validación, y el de PHP está muy maduro. La buena noticia: todas las herramientas de esta lección se ejecutan igual en tu máquina que en el runner, porque son binarios de vendor/bin/. El pipeline no hace nada que no puedas hacer tú en local; solo lo hace siempre.

Qué valida un pipeline PHP #

Un pipeline PHP maduro responde cinco preguntas, cada una con su herramienta y su coste, ordenadas de barata a cara:

PreguntaHerramientaCoste
¿Instala en limpio?composer install (+ composer validate)Segundos con caché
¿Sigue el estilo del equipo?php-cs-fixer / PHP_CodeSnifferSegundos
¿Tiene errores detectables sin ejecutar?PHPStan / Psalm~1 min
¿Se comporta como debe?PHPUnitMinutos
¿Se empaqueta para producción?docker buildMinutos

No hace falta empezar con las cinco. Un proyecto que hoy no tiene nada gana muchísimo solo con las dos primeras; las demás se añaden cuando el equipo se acostumbra al verde.

Composer, rápido y reproducible #

Todo empieza por instalar dependencias, y aquí mandan dos reglas. Primera: el runner instala exactamente lo que dice composer.lock — por eso el lock se versiona, para que CI, tus compañeros y producción usen las mismas versiones que tú. Segunda: con la caché de la lección anterior, la instalación baja de minutos a segundos.

yaml · PHP + Composer con caché 
- uses: shivammathur/setup-php@v2
  with:
    php-version: "8.3"
    extensions: pdo_mysql, intl
    coverage: none

- uses: actions/cache@v4
  with:
    path: ~/.cache/composer
    key: composer-${{ hashFiles('composer.lock') }}

- run: composer validate --strict
- run: composer install --prefer-dist --no-progress --no-interaction

Fíjate en extensions:: el runner es una máquina genérica, así que las extensiones que tu app necesita (las mismas que declaras en tu imagen de PHP) hay que pedirlas explícitamente. Y composer validate --strict es el chequeo más barato de todos: detecta un composer.json mal formado o un lock desincronizado antes de descargar nada.

Estilo y análisis estático #

Los dos siguientes controles no ejecutan tu código: lo leen. El primero, el estilo. En CI la herramienta no corrige, solo comprueba: php-cs-fixer check falla si algún fichero se desvía de las reglas del proyecto. El efecto colateral es el importante: las discusiones de formato desaparecen de las code reviews, porque las zanja una máquina antes de que nadie mire el diff.

El segundo es el análisis estático. PHPStan reconstruye los tipos de todo el proyecto y detecta, sin ejecutar nada, una categoría entera de errores: llamar a un método que no existe, pasar un string donde se espera un int, olvidar que algo puede ser null. En un lenguaje dinámico como PHP es lo más parecido a la fase de compilación de los lenguajes compilados — y con declare(strict_types=1) forman la pareja que convierte los tipos en garantías.

bash · los mismos comandos, en local y en CI 
# estilo: comprobar sin tocar nada (en local usarías "fix")
vendor/bin/php-cs-fixer check --diff

# análisis estático: nivel definido en phpstan.neon
vendor/bin/phpstan analyse

PHPStan se adopta por niveles

PHPStan tiene niveles de exigencia del 0 al 10. En un proyecto con historia, arrancar en el nivel máximo produce miles de errores y la tentación de rendirse. La estrategia sana: empieza en el nivel que ya pasa, fíjalo en phpstan.neon, y sube un nivel cuando el equipo tenga aire. El pipeline garantiza que nunca retrocedes.

PHPUnit con base de datos real #

Los tests unitarios no necesitan nada especial: vendor/bin/phpunit y listo. La pregunta interesante llega con los tests de integración: ¿de dónde sale la base de datos? De un service: un contenedor que la plataforma de CI levanta junto al job y descarta al terminar. Es la idea de docker-compose aplicada al pipeline: MySQL efímero, recién nacido para tus tests, destruido después.

yaml · job de tests con MySQL como service 
tests:
  runs-on: ubuntu-latest
  services:
    mysql:
      image: mysql:8.4
      env:
        MYSQL_DATABASE: app_test
        MYSQL_ROOT_PASSWORD: secret
      ports:
        - 3306:3306
      options: --health-cmd="mysqladmin ping" --health-interval=5s

  steps:
    # ... checkout, PHP, composer install ...
    - run: vendor/bin/phpunit
      env:
        DATABASE_URL: mysql://root:secret@127.0.0.1:3306/app_test

Dos detalles que ahorran tardes de depuración: el --health-cmd hace que el job espere a que MySQL esté listo de verdad (arrancar el contenedor no significa aceptar conexiones), y la conexión va por 127.0.0.1 con el puerto publicado, porque los steps no corren dentro de la red del service. La base de datos de test es app_test, nunca una compartida: cada ejecución parte de cero, ejecuta las migraciones y prueba sobre un esquema limpio.

Construir la imagen al final #

Cuando todo lo anterior está en verde, el pipeline construye el artefacto de despliegue: la imagen Docker. Aquí se juntan dos cosas que ya sabes. Del curso de Docker, el Dockerfile con multi-stage y buenas prácticas. De la lección anterior, el principio del artefacto: se construye una vez, etiquetada con el hash del commit, y esa imagen exacta es la que viajará por los entornos.

yaml · build solo si la validación pasó 
build:
  needs: [estilo, estatico, tests]
  if: github.ref == 'refs/heads/main'
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - run: docker build -t ghcr.io/mi-org/mi-app:${{ github.sha }} .
    - run: docker push ghcr.io/mi-org/mi-app:${{ github.sha }}

El needs encadena: este job ni arranca si algo falló. El if limita el build a main: las pull requests se validan pero no producen imagen. Y la etiqueta con github.sha hace cada imagen trazable hasta su commit — cuando algo falle en producción sabrás exactamente qué código contiene.

El workflow completo #

Todo junto: tres jobs de validación en paralelo (fallar rápido, cada uno con su pregunta) y el build esperándolos. Esta es la estructura que puedes llevarte a cualquier proyecto PHP:

yaml · .github/workflows/ci.yml completo (esqueleto) 
name: CI

on:
  pull_request:
  push:
    branches: [main]

jobs:
  estilo:
    runs-on: ubuntu-latest
    steps:
      # checkout + setup-php + composer (con caché)
      - run: vendor/bin/php-cs-fixer check

  estatico:
    runs-on: ubuntu-latest
    steps:
      # checkout + setup-php + composer (con caché)
      - run: vendor/bin/phpstan analyse

  tests:
    runs-on: ubuntu-latest
    services:
      mysql: # como en la sección anterior
    steps:
      # checkout + setup-php + composer (con caché)
      - run: vendor/bin/phpunit

  build:
    needs: [estilo, estatico, tests]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t ghcr.io/mi-org/mi-app:${{ github.sha }} .
      - run: docker push ghcr.io/mi-org/mi-app:${{ github.sha }}

Protege la rama con el verde

El último clic para cerrar el círculo no está en el YAML sino en la configuración del repo: marca los jobs como required status checks de main (branch protection). A partir de ahí, ninguna pull request se puede mezclar en rojo — el pipeline deja de ser un aviso y pasa a ser la puerta.

Resumen #

Lo que te llevas

  • Cinco controles ordenados de barato a caro: instala, estilo, análisis estático, tests, build. No hace falta empezar con todos.
  • CI instala lo que dice composer.lock, con la caché keyed por su hash; composer validate --strict es el chequeo más barato del pipeline.
  • cs-fixer saca el formato de las reviews; PHPStan detecta errores sin ejecutar código y se adopta subiendo de nivel, sin retroceder jamás.
  • Los tests de integración usan services efímeros (MySQL con healthcheck, por 127.0.0.1) y una BD de test que nace y muere con el job.
  • La imagen se construye una vez, etiquetada con el commit, solo tras el verde — y la protección de rama convierte el pipeline en la puerta de main.
