MCP: conectar herramientas

El agente trae de serie las herramientas del código: leer, editar, ejecutar. Pero tu mundo es más grande — tu gestor de tickets, tu base de datos, tu API interna. MCP es el enchufe estándar para conectarlo: un protocolo abierto que ya conoces a medias, porque es la idea de «tool» de la lección 1 sacada de la herramienta.

MCP apareció en el curso de fundamentos como concepto. Aquí lo usamos: qué expone exactamente un servidor, cómo se ve desde el bucle del agente, y el esqueleto de uno propio — porque montar uno mínimo es la forma más rápida de que el protocolo deje de ser humo.

El problema N×M y el enchufe estándar #

Sin estándar, cada herramienta de IA (N) tendría que integrar cada servicio (M) por su cuenta: N×M conectores, cada uno a su manera. El Model Context Protocol corta el nudo como lo han cortado siempre los protocolos: define un contrato único entre clientes (Claude Code y cualquier otra herramienta agéntica) y servidores (procesos que exponen capacidades). Escribes el servidor de tu API interna una vez; lo habla cualquier cliente MCP presente o futuro. Es el mismo movimiento que LSP hizo con editores y lenguajes.

Qué expone un servidor MCP #

Un servidor anuncia sus capacidades en categorías; las dos que importan el 95% del tiempo:

Pieza Qué es Ejemplo
Tools Acciones invocables: nombre + parámetros con esquema + resultado. Exactamente el contrato de la lección 1. crear_ticket(titulo, prioridad)
Resources Contenido legible identificado por URI, para meter en contexto sin ser una «acción». tickets://abiertos/backend

La distinción es la de siempre entre consulta y comando: un resource se lee (sin efectos), una tool hace cosas. Un buen servidor no lo mezcla — que listar tickets sea una tool con efectos secundarios es el equivalente MCP de un GET que borra.

Cómo encaja en el bucle #

Desde el punto de vista del modelo, no hay nada nuevo: las tools de los servidores MCP conectados aparecen en su catálogo junto a las nativas, con un prefijo que delata su origen. Cuando las pide, el harness enruta la llamada al proceso del servidor (por stdio si es local, por HTTP si es remoto), recoge el resultado y lo devuelve al contexto como cualquier otro resultado de herramienta. El bucle de la lección 1, intacto — solo que el brazo ejecutor ahora puede estar en otro proceso u otra máquina.

Un servidor mínimo, funcional #

Por debajo, MCP es JSON-RPC: mensajes con method y params. Con el SDK oficial, un servidor con una tool útil — consultar tu base de datos de desarrollo, con conexión de solo lectura — cabe en una pantalla:

js · servidor MCP con una tool (SDK oficial, esquema) 
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "mi-bd-dev", version: "1.0.0" });

server.tool(
  "consulta_solo_lectura",
  "Ejecuta un SELECT sobre la BD de desarrollo y devuelve las filas",
  { sql: z.string().describe("Consulta SELECT unica, sin ; multiples") },
  async ({ sql }) => {
    if (!/^\s*select\b/i.test(sql)) {
      return { content: [{ type: "text", text: "Solo se aceptan SELECT" }] };
    }

    const rows = await pool.query(sql);

    return { content: [{ type: "text", text: JSON.stringify(rows.slice(0, 50)) }] };
  }
);

await server.connect(new StdioServerTransport());

Dos detalles del ejemplo que son doctrina, no adorno: la descripción de la tool es prompt — el modelo decide usarla (o no, o mal) leyéndola, así que se escribe con el mismo cuidado que una rule. Y la validación dentro del servidor (solo SELECT, resultados acotados) es la frontera determinista: no confíes en que el modelo «no mandará un DELETE» — haz que el servidor no pueda ejecutarlo.

Conectarlo a Claude Code #

Los clientes MCP se configuran declarando cómo arrancar (o dónde encontrar) cada servidor. En Claude Code, un fichero .mcp.json en el repo lo deja configurado para todo el equipo:

.mcp.json 
{
  "mcpServers": {
    "mi-bd-dev": {
      "command": "node",
      "args": ["tools/mcp/bd-dev.js"],
      "env": { "DB_DSN": "mysql://dev@localhost/app" }
    }
  }
}

Al arrancar la sesión, el harness lanza el proceso, negocia capacidades y añade consulta_solo_lectura al catálogo del modelo. A partir de ahí, «mira si hay usuarios sin confirmar en la BD de dev» deja de ser un copy-paste tuyo y pasa a ser una herramienta más del bucle.

Seguridad: cada servidor es superficie #

Conectar un servidor MCP es dar manos nuevas al agente, y las manos de terceros merecen la desconfianza estándar de las dependencias — más una propia de esta tecnología:

  • Un servidor de terceros es código que ejecutas con tus credenciales: se audita como cualquier dependencia, y se le da la credencial mínima (la conexión de solo lectura del ejemplo no es decorativa).
  • Lo que el servidor devuelve entra al contexto. Si una tool trae contenido externo (una web, un ticket escrito por cualquiera), ese texto puede contener instrucciones dirigidas al modelo — la inyección de prompt del curso de fundamentos, ahora por la puerta de las herramientas. Tratar los datos como datos, y desconfiar de resultados que «piden cosas».
  • Menos es más: cada servidor conectado suma tools al catálogo (contexto) y superficie de fallo. Se conecta lo que se usa, no lo que mola.

Cuándo aplicarlo #

MCP encaja cuando…

  • El agente necesita un sistema externo de forma recurrente (BD, tickets, API interna)
  • Quieres el mismo acceso desde varias herramientas de IA
  • Puedes acotar la capacidad en el servidor (solo lectura, credencial mínima)

Sobra cuando…

  • Un comando CLI ya lo resuelve: el agente puede ejecutarlo con Bash
  • Es un uso puntual: copiar el dato a mano cuesta menos que mantener un servidor
  • No puedes auditar el servidor de terceros que ibas a conectar

Resumen #

Lo que te llevas

  • MCP es el enchufe estándar entre clientes agénticos y servicios: el conector se escribe una vez y lo habla cualquier herramienta.
  • Un servidor expone tools (acciones con esquema) y resources (contenido por URI): comando y consulta, sin mezclar.
  • Para el modelo no hay nada nuevo: las tools MCP entran al mismo catálogo y al mismo bucle; cambia quién ejecuta.
  • La descripción de una tool es prompt (se escribe con cuidado) y la validación va dentro del servidor: la frontera determinista, otra vez.
  • Cada servidor conectado es superficie: credencial mínima, terceros auditados, y ojo a la inyección que entra por los resultados.
