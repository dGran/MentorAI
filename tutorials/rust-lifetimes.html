Lifetimes: duración de referencias

Qué son los lifetimes, por qué el compilador los necesita, anotaciones explícitas, elision rules y lifetimes en structs.

El problema que resuelven #

El borrow checker garantiza que las referencias no sobreviven a los datos a los que apuntan. Para que pueda hacer esa verificación, necesita saber la duración de cada referencia. En la mayoría de casos, el compilador la deduce solo. Pero hay situaciones donde no puede:

rust 
fn la_mas_larga(x: &str, y: &str) -> &str {
    if x.len() > y.len() { x } else { y }
}
bash 
error[E0106]: missing lifetime specifier
 --> src/main.rs:1:36
  |
1 | fn la_mas_larga(x: &str, y: &str) -> &str {
  |                    ----     ----     ^ expected named lifetime parameter

El compilador no puede saber si la referencia retornada viene de x o de y (depende de la condición en runtime). Por tanto, no puede determinar cuánto debe vivir la referencia retornada: ¿debe vivir tanto como x? ¿tanto como y? La anotación de lifetime es la forma de decirle al compilador la relación entre las duraciones.

Los lifetimes no cambian el tiempo de vida de ningún dato: son anotaciones descriptivas que le dan al compilador información para verificar que el código es correcto. No afectan al binario generado.

Anotaciones explícitas de lifetime #

La sintaxis usa el apóstrofe: 'a, 'b, etc. Por convención, se usan letras minúsculas cortas:

rust 
fn la_mas_larga<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

Esta firma significa: "la referencia retornada vive al menos tanto como 'a, donde 'a es la intersección de los lifetimes de x e y". En la práctica: la referencia retornada vive tanto como la más corta de las dos entradas.

rust 
fn main() {
    let texto1 = String::from("cadena larga");
    let resultado;

    {
        let texto2 = String::from("xyz");
        resultado = la_mas_larga(texto1.as_str(), texto2.as_str());
        println!("{}", resultado); // OK: resultado se usa dentro del scope de texto2
    }

    // println!("{}", resultado); // error: texto2 ya no existe
}

El compilador verifica que resultado no se usa después de que texto2 (la más corta) sale de scope. Si intentas hacerlo, error en compilación. No en runtime, no en producción: en compilación.

La anotación 'a no define una duración concreta. Define una relación: "estas referencias tienen duraciones relacionadas de esta forma".

Elision rules #

En la mayoría de funciones no necesitas anotar lifetimes porque el compilador aplica las elision rules: reglas deterministas para inferir los lifetimes cuando la situación es no ambigua.

Las tres reglas (aplicadas en orden):

  1. Cada parámetro de referencia obtiene su propio lifetime implícito: fn f(x: &str, y: &str) → fn f<'a, 'b>(x: &'a str, y: &'b str).
  2. Si hay exactamente un parámetro de entrada con lifetime, ese lifetime se aplica a todas las referencias de salida: fn f(x: &str) -> &str → fn f<'a>(x: &'a str) -> &'a str.
  3. Si hay un parámetro &self o &mut self, su lifetime se aplica a todas las referencias de salida.

Cuándo el compilador puede inferir el lifetime solo (no necesitas anotación):

rust 
fn primera_palabra(s: &str) -> &str { // regla 2: un input, output same lifetime
    &s[..s.find(' ').unwrap_or(s.len())]
}

impl MiStruct {
    fn referencia(&self) -> &str { // regla 3: &self determina el output lifetime
        &self.campo
    }
}

Cuándo necesitas anotación explícita: cuando hay múltiples referencias de entrada y el compilador no puede determinar cuál corresponde al output sin tu ayuda.

Lifetimes en structs #

Si un struct guarda una referencia, necesita un parámetro de lifetime que exprese la relación entre la duración del struct y la del dato referenciado:

rust 
struct Fragmento<'a> {
    parte: &'a str,
}

impl<'a> Fragmento<'a> {
    fn mostrar(&self) {
        println!("{}", self.parte);
    }
}

fn main() {
    let texto = String::from("hola mundo");
    let fragmento = Fragmento { parte: &texto[0..4] };
    fragmento.mostrar(); // hola
} // texto y fragmento salen de scope juntos: OK

La anotación 'a en el struct dice: "una instancia de Fragmento<'a> no puede vivir más que 'a (el dato al que parte apunta)". El compilador verifica esto en cada uso.

Si intentas que el struct viva más que el dato al que apunta:

rust 
fn main() {
    let fragmento;
    {
        let texto = String::from("temporal");
        fragmento = Fragmento { parte: &texto }; // error: texto no vive suficiente
    }
    fragmento.mostrar(); // texto ya no existe
}
bash 
error[E0597]: `texto` does not live long enough

'static: el lifetime eterno #

'static es el lifetime especial que dura todo el programa. Los string literals tienen tipo &'static str porque están embebidos en el binario:

rust 
let saludo: &'static str = "hola mundo"; // vive en el binario

El compilador puede pedir 'static en algunos contextos, como al enviar datos entre threads (donde no hay garantía de cuándo terminará el thread):

rust 
use std::thread;

fn ejecutar_en_thread(f: impl Fn() + Send + 'static) {
    thread::spawn(f);
}

fn main() {
    ejecutar_en_thread(|| println!("hola desde otro thread"));
}

Evita 'static como atajo: cuando el compilador pide un lifetime y no sabes qué poner, la tentación es 'static porque "hace que compile". Esto enmascara el problema real: estás guardando una referencia que debería ser un valor poseído. Antes de usar 'static, pregúntate si deberías usar String en lugar de &str, o Vec<T> en lugar de &[T].

Resumen #

Lo que te llevas

  • Los lifetimes son anotaciones que describen relaciones de duración entre referencias. No cambian el comportamiento en runtime; son información para el compilador.
  • Las anotaciones explícitas ('a) son necesarias cuando el compilador no puede determinar la relación entre los lifetimes de entrada y salida de una función.
  • Las elision rules cubren la mayoría de casos: un parámetro de entrada, o el receptor &self, determinan automáticamente el lifetime de salida.
  • Los structs que contienen referencias necesitan un parámetro de lifetime que garantice que el struct no vive más que el dato referenciado.
  • 'static dura todo el programa; los string literals son &'static str. Usarlo como atajo para hacer compilar suele indicar que deberías poseer el dato en lugar de referenciarlo.
