Streaming sobre HTTP: chunked, NDJSON y respuestas largas

No todo lo que tarda necesita una cola. Entre «responder de golpe cuando esté todo» y «montar procesamiento asíncrono» hay una opción intermedia que HTTP soporta desde siempre: empezar a responder antes de haber terminado.

Responder sin saber cuánto ocupa #

Normalmente una respuesta lleva Content-Length, lo que obliga a tener el cuerpo entero antes de mandar nada. Con codificación por trozos no hace falta: se manda por partes y se marca el final con un trozo vacío.

Sin streaming

  • Generar el CSV entero en memoria
  • Un millón de filas = memoria agotada
  • El usuario espera sin ver nada
  • Y a menudo acaba en timeout

Con streaming

  • Se escribe fila a fila conforme se lee
  • Memoria constante, sea cual sea el tamaño
  • La descarga empieza al instante
  • El navegador la trata como un fichero normal
php · exportar sin cargar nada en memoria 
<?php

declare(strict_types=1);

final class ExportarPedidos
{
    public function __invoke(): StreamedResponse
    {
        $respuesta = new StreamedResponse(function (): void {
            $salida = fopen('php://output', 'wb');

            fputcsv($salida, ['id', 'fecha', 'total']);

            foreach ($this->pedidos->recorrerTodos() as $pedido) {
                fputcsv($salida, [$pedido['id'], $pedido['creado_en'], $pedido['total']]);
                flush();
            }

            fclose($salida);
        });

        $respuesta->headers->set('Content-Type', 'text/csv');
        $respuesta->headers->set('Content-Disposition', 'attachment; filename="pedidos.csv"');

        return $respuesta;
    }
}

El generador es la mitad del truco

recorrerTodos() tiene que devolver un generador que lea por lotes, no un array con el millón de filas. Si el repositorio carga todo antes de empezar, has puesto streaming en la salida y sigues agotando la memoria en la entrada: justo lo que querías evitar.

NDJSON: streaming de datos estructurados #

Un JSON grande no se puede consumir a trozos: hasta que no llega el corchete de cierre no es válido. NDJSON resuelve eso con una idea mínima — un objeto JSON por línea, sin array que los envuelva:

bash · application/x-ndjson 
{"id":"4871","total":4250}
{"id":"4872","total":1990}
{"id":"4873","total":8000}

El consumidor procesa cada línea en cuanto llega, con memoria constante, y si la conexión se corta a la mitad tiene válido todo lo recibido hasta la última línea completa. Es el formato de los volcados grandes y de las APIs de exportación por una razón.

El caso que lo ha puesto de moda #

Las respuestas de modelos de lenguaje son el ejemplo perfecto: tardan segundos en completarse y el primer token está listo en milisegundos. Mostrarlo conforme llega cambia por completo la sensación de velocidad sin que el total mejore ni un milisegundo.

La técnica es la misma que llevas viendo: la API del modelo te da un flujo, tú lo reenvías al navegador por SSE o por trozos, y la interfaz va pintando. Lo único que hay que cuidar es no acumular en ningún búfer intermedio — ni el tuyo, ni el de nginx.

Todo el camino tiene que dejar pasar

Basta con que una pieza acumule para que el streaming desaparezca sin dar ningún error: el buffer de salida de PHP, fastcgi_buffering en nginx, o la CDN, que por defecto suele acumular respuestas. El síntoma es desconcertante: funciona en local y en producción la respuesta llega entera de golpe al final.

El problema que no tiene solución bonita #

Una vez has mandado los primeros bytes, ya has mandado el código de estado. Si a la fila 400.000 revienta una consulta, no puedes cambiar el 200 por un 500: el cliente lleva un rato recibiendo un fichero que cree correcto.

1 200 OK y empieza el cuerpoEl cliente ya está guardando el fichero
2 Falla algoY no hay forma de rectificar el estado
3 Cortar la conexiónEl cliente detecta un cuerpo incompleto, si lo comprueba

Por eso las respuestas en flujo llevan a menudo una marca de fin explícita: sin ella, un truncamiento parece un final legítimo.

Con NDJSON eso se resuelve con una última línea que diga {"fin":true}, o con el trailer de HTTP para quien lo soporte. Es feo y es lo que hay: el protocolo no te deja retractarte de un estado que ya diste.

Cuándo aplicarlo #

Streaming cuando…

  • El resultado no cabe cómodamente en memoria
  • Los primeros datos son útiles antes de tener el resto
  • La respuesta tarda y quieres que se note menos
  • Exportaciones, volcados, respuestas de modelos

Mejor asíncrono cuando…

  • Tarda minutos: nadie mantiene una conexión abierta tanto
  • Quieres poder reintentar sin regenerar todo
  • El usuario debería poder cerrar e irse
  • → Un 202 con un enlace al resultado, como viste en rendimiento

Resumen #

Lo que te llevas

  • Entre responder de golpe y montar una cola está el streaming, que HTTP soporta desde siempre y cuesta muy poco.
  • Streaming en la salida no sirve de nada si el repositorio carga todo antes: hace falta un generador que lea por lotes.
  • Un JSON grande no se consume a trozos; NDJSON sí, con un objeto por línea y memoria constante.
  • Todo el camino tiene que dejar pasar: el buffer de PHP, el de nginx o la CDN pueden acumular y anular el streaming sin dar error.
  • Una vez mandado el 200 no puedes retractarte: por eso las respuestas en flujo llevan una marca de fin explícita.
