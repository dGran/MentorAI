PHPUnit: primeros pasos

Ya sabes por qué testear; ahora toca la herramienta con la que lo harás cada día. Instalar PHPUnit, escribir el primer test bien formado, leer lo que te dice cuando falla — y esquivar desde el principio la trampa de assertEquals.

PHPUnit es el framework de testing de facto en PHP: lo usan Symfony, Laravel y prácticamente todo el ecosistema. Este curso es la contraparte práctica del de TDD y fundamentos: allí el porqué y el cuándo; aquí, la herramienta a fondo.

Instalar y configurar #

PHPUnit es una dependencia de desarrollo: la necesitas para trabajar, no para que la aplicación funcione en producción. Por eso va a require-dev:

bash · instalar PHPUnit 
composer require --dev phpunit/phpunit

# el binario queda en vendor/bin
vendor/bin/phpunit --version

La configuración vive en phpunit.xml en la raíz del proyecto. Tres cosas hacen el 90 % del trabajo: dónde están los tests, qué bootstrap cargar (el autoloader de Composer) y un par de banderas de higiene:

xml · phpunit.xml mínimo y sano 
<phpunit bootstrap="vendor/autoload.php"
         colors="true"
         failOnRisky="true"
         failOnWarning="true">
    <testsuites>
        <testsuite name="unit">
            <directory>tests/Unit</directory>
        </testsuite>
        <testsuite name="integration">
            <directory>tests/Integration</directory>
        </testsuite>
    </testsuites>
</phpunit>

Fíjate en las dos suites separadas: es la pirámide de tests hecha configuración. Podrás ejecutar solo las unitarias (rápidas, a cada rato) o todo (antes de un push, y siempre en CI). La convención de nombres: la clase InvoiceCalculator se prueba en InvoiceCalculatorTest, espejo de src/ en tests/.

Anatomía de un test #

Un test de PHPUnit es una clase que extiende TestCase; cada método marcado con el atributo #[Test] (o cuyo nombre empieza por test) es un caso independiente. Por dentro, los buenos tests siguen siempre la misma partitura en tres actos — arrange, act, assert: preparar el escenario, ejecutar lo que pruebas, comprobar el resultado.

php · tests/Unit/InvoiceCalculatorTest.php 
<?php

declare(strict_types=1);

use PHPUnit\Framework\Attributes\Test;
use PHPUnit\Framework\TestCase;

final class InvoiceCalculatorTest extends TestCase
{
    #[Test]
    public function aplica_el_iva_al_subtotal(): void
    {
        $calculator = new InvoiceCalculator(vatRate: 21);

        $total = $calculator->totalFor(subtotalCents: 10000);

        $this->assertSame(12100, $total);
    }
}

Detalles que importan más de lo que parecen: el nombre del método describe el comportamiento, no el método que llama ("aplica el IVA al subtotal", no "testTotalFor") — cuando falle dentro de seis meses, el nombre es lo primero que leerás. Y las tres fases separadas por líneas en blanco hacen el test legible de un vistazo, exactamente el mismo criterio de legibilidad que pides al código de producción.

¿Atributo o prefijo test?

Ambos funcionan: #[Test] sobre el método (PHPUnit 10+) libera el nombre para escribir español natural; el prefijo public function testAplicaElIva() es la convención clásica que verás en miles de repos. Elige uno con tu equipo y sé consistente — el atributo es el camino moderno.

Ejecutar y leer la salida #

El día a día son tres comandos:

bash · ejecutar la suite 
# todo
vendor/bin/phpunit

# solo la suite rápida
vendor/bin/phpunit --testsuite unit

# solo lo que estás tocando ahora
vendor/bin/phpunit --filter InvoiceCalculatorTest

La salida usa un carácter por test: . pasó, F falló una aserción, E explotó con un error antes de llegar a la aserción, R arriesgado (no comprobó nada), S saltado. La distinción F/E orienta el diagnóstico: un failure significa "el código corrió y el resultado no es el esperado"; un error significa "el test ni siquiera pudo terminar" (excepción no prevista, clase que no existe). Se arreglan mirando sitios distintos.

Cuando una aserción falla, PHPUnit imprime el diff entre lo esperado y lo recibido. Ahí está la mitad del valor de la herramienta: un buen test que falla te dice qué se rompió sin abrir el depurador — es la razón por la que las aserciones específicas (siguiente sección) ganan a un assertTrue genérico que solo dice "false is not true".

Las aserciones esenciales #

PHPUnit trae decenas de aserciones; con estas cubres casi todo, y la regla para elegir es siempre la misma: la más específica que exprese tu intención, porque es la que mejor mensaje da al fallar.

AserciónComprueba
assertSame($esperado, $real)Identidad estricta (===). Tu aserción por defecto.
assertEquals($esperado, $real)Igualdad laxa (valores comparables). Solo cuando la laxitud es deliberada.
assertTrue($x) / assertFalse($x)Booleanos reales (no truthy/falsy).
assertNull($x)El valor es exactamente null.
assertCount(3, $coleccion)Número de elementos, con mensaje claro al fallar.
assertContains($aguja, $pajar)Un elemento está en el array/iterable.
assertInstanceOf(Clase::class, $x)El tipo del objeto.
assertStringContainsString($sub, $str)Subcadena en un string.

Todas aceptan un mensaje opcional como último argumento, pero si necesitas explicar la aserción con un mensaje, suele ser señal de que existe una aserción más específica que lo diría sola.

assertSame vs assertEquals #

El error típico del que arranca con PHPUnit merece su propia sección. assertEquals compara con la laxitud de ==: convierte tipos antes de comparar. assertSame usa ===: tipo y valor. La diferencia deja pasar bugs reales:

assertEquals — pasa (y miente)

  • assertEquals(1, '1') ✔ pasa
  • assertEquals(0, false) ✔ pasa
  • assertEquals(null, 0) ✔ pasa (PHPUnit 9)
  • Tu función devuelve string donde prometía int y el test no se entera.

assertSame — falla (y te avisa)

  • assertSame(1, '1') ✘ falla
  • assertSame(0, false) ✘ falla
  • El tipo forma parte del contrato, igual que con declare(strict_types=1).
  • El diff te muestra el tipo exacto recibido.

¿Cuándo sí assertEquals? Con objetos que quieres comparar por contenido: dos DateTimeImmutable con la misma fecha, dos value objects con el mismo estado. assertSame entre objetos exige que sean la misma instancia, que casi nunca es lo que quieres comprobar. La regla práctica: escalares con assertSame, objetos por contenido con assertEquals — y coherente con el tipado estricto que ya usas en el código de producción.

Desde el IDE también

PhpStorm integra PHPUnit: detecta phpunit.xml, ejecuta un test o una clase con el triángulo verde del margen y te deja saltar del fallo a la línea. Ideal para el ciclo rápido; la terminal y el CI ejecutan exactamente lo mismo.

Resumen #

Lo que te llevas

  • PHPUnit va en require-dev; phpunit.xml define bootstrap, suites separadas (unit/integration) y banderas de higiene como failOnRisky.
  • Un test = clase TestCase + método #[Test] con tres actos: arrange, act, assert. El nombre describe el comportamiento, no el método llamado.
  • F ≠ E: failure es resultado inesperado; error es que el test ni terminó. Se diagnostican mirando sitios distintos.
  • Usa siempre la aserción más específica: su mensaje de fallo trabaja por ti.
  • assertSame (===) para escalares; assertEquals solo para comparar objetos por contenido. La laxitud de == deja pasar bugs de tipo.
