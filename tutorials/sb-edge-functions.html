Edge Functions: tu código en el servidor

Hay cosas que no pueden pasar en el navegador ni caben en SQL: cobrar con Stripe, mandar un email con tu proveedor, llamar a un modelo de IA con una clave secreta, recibir el webhook de otro servicio. Para eso están las Edge Functions, pequeñas funciones TypeScript que despliegas con un comando y que ya saben quién es el usuario.

Con la Data API, RLS y las funciones de Postgres cubres casi todo lo que toca la base de datos. Esta lección es para lo que sale de ella: código de servidor con secretos, llamadas a APIs externas y trabajo que no debe hacer el cliente.

Qué son y dónde corren #

Una Edge Function es un fichero TypeScript que recibe una petición HTTP (Request) y devuelve una respuesta (Response), con las APIs estándar de la web. Corre en el Edge Runtime de Supabase, compatible con Deno: puedes importar paquetes de npm con el prefijo npm: y de JSR con jsr:.

«Edge» quiere decir que se despliegan en varias regiones y cada petición se atiende cerca de quien llama. Ojo con la intuición: si la función consulta la base de datos, que vive en una región, cada consulta cruza hasta ella. Para lógica que habla mucho con la base de datos, la cercanía al usuario importa menos que el número de consultas.

Crear, probar y desplegar #

bash · el ciclo de vida de una función 
npx supabase functions new share-note
npx supabase start
npx supabase functions serve share-note
npx supabase functions deploy share-note

new crea supabase/functions/share-note/index.ts. serve la ejecuta en local con recarga al guardar, servida en http://127.0.0.1:54321/functions/v1/share-note. deploy la sube al proyecto enlazado. Desde el cliente se llama con invoke, que adjunta solo la clave y el token del usuario:

ts · llamar a la función desde la app 
const { data, error } = await supabase.functions.invoke("share-note", {
  body: { noteId: 7, email: "luis@ejemplo.com" },
});

Saber quién llama #

Una función expuesta en internet tiene que decidir quién puede llamarla. Supabase da dos capas:

  • **verify_jwt** (activado por defecto): la plataforma rechaza la petición antes de ejecutar tu código si no trae un JWT válido en Authorization. Se desactiva por función en supabase/config.toml.
  • Tu código, que decide qué puede hacer ese usuario y con qué cliente consulta la base de datos.

La forma recomendada hoy es el envoltorio withSupabase del paquete @supabase/server, que valida la llamada según el modo que pidas y te da clientes ya configurados:

ts · supabase/functions/share-note/index.ts 
import { withSupabase } from "npm:@supabase/server@1";

export default {
  fetch: withSupabase({ auth: "user" }, async (req, ctx) => {
    const { noteId, email } = await req.json();

    const { data: note, error } = await ctx.supabase
      .from("notes")
      .select("id, title")
      .eq("id", noteId)
      .single();

    if (error) return Response.json({ error: "Nota no encontrada" }, { status: 404 });

    const { data: invited } = await ctx.supabaseAdmin
      .from("profiles")
      .select("id")
      .eq("email", email)
      .single();

    if (!invited) return Response.json({ error: "Usuario no encontrado" }, { status: 404 });

    await ctx.supabase.from("note_shares").insert({ note_id: note.id, shared_with: invited.id });

    return Response.json({ shared: true });
  }),
};

En el ejemplo, profiles tendría una columna email. Con la política de lectura de funciones y triggers la verían todos los usuarios con sesión, así que en una app real iría en una tabla aparte sin políticas de lectura, que solo supabaseAdmin puede consultar. Los dos clientes son la idea central de la lección:

ClienteActúa comoÚsalo para
ctx.supabaseEl usuario que llama: su token, sus políticasTodo lo que el usuario podría hacer por sí mismo. RLS te protege de bugs propios
ctx.supabaseAdminservice_role, con la clave secretaLo que el usuario no puede hacer solo, filtrando a mano por su id

El modo de auth decide quién puede llamar: "user" exige un usuario con sesión (te da sus claims en ctx.userClaims), "publishable" acepta la clave publicable sin usuario y "secret" solo acepta llamadas de servidor con la clave secreta, como las de una tarea programada.

El código que encontrarás en otros sitios

Muchos tutoriales y proyectos anteriores a este envoltorio escriben la función con Deno.serve(async (req) => ...) y crean el cliente a mano con createClient de npm:@supabase/supabase-js, reenviando la cabecera Authorization de la petición para actuar como el usuario. Es lo mismo por dentro y sigue funcionando. La forma de escribir funciones ha cambiado varias veces; la plantilla que genera functions new en tu versión de la CLI es la referencia.

Secretos y variables de entorno #

Las claves de terceros (Stripe, tu proveedor de email, un modelo de IA) se guardan como secretos del proyecto y se leen como variables de entorno:

bash · gestionar secretos 
npx supabase secrets set RESEND_API_KEY=re_xxxxxxxx
npx supabase secrets list
ts · leerlos en la función 
const apiKey = Deno.env.get("RESEND_API_KEY");

En local se cargan de supabase/functions/.env, que no se sube a git. La plataforma inyecta además variables propias, como SUPABASE_URL, y por eso los nombres que empiezan por SUPABASE_ están reservados.

CORS y webhooks de terceros #

Si la función se llama desde el navegador, el navegador mandará antes una petición OPTIONS (el preflight de CORS) y la función tiene que responderla con las cabeceras que permiten la llamada. Sin eso, invoke falla en el navegador aunque con curl funcione. La documentación de Edge Functions trae el bloque de cabeceras CORS que hay que devolver en el OPTIONS y en cada respuesta.

Recibir un webhook de un tercero es el caso contrario: quien llama es Stripe, que no tiene un JWT de tu proyecto. Hay que desactivar la verificación para esa función y verificar la firma del proveedor en tu código:

ini · supabase/config.toml 
[functions.stripe-webhook]
verify_jwt = false

Desactivar verify_jwt no deja la función abierta si tu código comprueba la firma: es el único control que tiene sentido para ese emisor. Firmar y verificar cuenta los cuatro detalles en que se estropea esa comprobación.

Responder rápido y seguir trabajando #

Una función que manda un email y luego responde hace esperar al usuario lo que tarde el proveedor. Con EdgeRuntime.waitUntil respondes al momento y el trabajo sigue en segundo plano:

ts · responder y seguir 
const sendEmail = fetch("https://api.resend.com/emails", { method: "POST", headers, body });

EdgeRuntime.waitUntil(sendEmail);

return Response.json({ shared: true });

El trabajo en segundo plano sigue sujeto a los límites de la función. Para trabajo largo o que no puede perderse, una cola es la herramienta.

Los límites deciden qué cabe #

LímiteValor
Memoria256 MB
Tiempo de CPU por petición2 s (sin contar la espera de red)
Duración máxima150 s en el plan gratuito, 400 s en los de pago
Sin respuestaA los 150 s sin responder, la plataforma devuelve un 504
Tamaño del paquete20 MB construido con la CLI
Puertos de salidaEl 25 y el 587 están bloqueados: el email va por la API HTTP de tu proveedor

Los 2 segundos de CPU son el límite que más sorprende: no cuentan esperas de red, pero sí cálculo puro. Redimensionar imágenes, generar PDFs grandes o recorrer un JSON de cien mil elementos puede pasarse. Las librerías nativas que usan varios hilos (como sharp) no funcionan.

Las funciones también tienen arranque en frío: la primera petición tras un rato sin uso tarda más, porque hay que cargar el código. Importar menos dependencias lo reduce.

Errores típicos #

  • **Usar supabaseAdmin para todo.** Funciona, y convierte cada bug de filtrado en una fuga de datos. Empieza siempre por el cliente del usuario.
  • Bucles de consultas. Una función que hace cien consultas a la base de datos en serie paga cien veces la latencia hasta la región. Una función SQL con rpc lo hace en una.
  • **Olvidar el OPTIONS de CORS** y depurar durante una hora un error que solo sale en el navegador.
  • **Webhooks con verify_jwt = false y sin verificar la firma.** Cualquiera puede llamarlos.
  • Trabajos largos dentro de la petición. Chocan con la duración máxima y con los 2 s de CPU.

Cuándo aplicarlo #

Una Edge Function encaja cuando…

  • Necesitas una clave secreta de un tercero (pagos, email, IA)
  • Recibes webhooks de otros servicios
  • La lógica es TypeScript con dependencias de npm, no SQL
  • Quieres una operación que el usuario no puede hacer solo, controlada por código

Mejor otra cosa si…

  • Es leer o escribir filas con permisos: la Data API directa
  • Son varias operaciones atómicas sobre la base de datos: una función SQL con rpc
  • Es trabajo pesado de CPU o de minutos: una cola con un worker, o tu propio servidor

Resumen #

Lo que te llevas

  • Las Edge Functions son TypeScript sobre un runtime compatible con Deno, con APIs web estándar y paquetes de npm.
  • functions new, serve y deploy son el ciclo completo; el cliente las llama con functions.invoke.
  • verify_jwt filtra en la plataforma; en tu código, un cliente actúa como el usuario (RLS aplica) y otro como service_role.
  • Los secretos se gestionan con supabase secrets y se leen con Deno.env.get; los webhooks de terceros desactivan verify_jwt y verifican la firma.
  • EdgeRuntime.waitUntil responde antes y sigue trabajando, dentro de los límites de 256 MB, 2 s de CPU y 150-400 s de duración.
