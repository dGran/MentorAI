Embeddings, RAG y fine-tuning

Tres formas de que un modelo responda con lo tuyo: ponérselo delante buscando por significado (RAG), dejar que lo busque él con herramientas (búsqueda agéntica) o reentrenarlo (fine-tuning). Esta lección explica cuándo usar cada una, y por qué la última casi nunca es la primera opción.

La idea que ordena toda la lección: el fine-tuning enseña comportamiento, no conocimiento. Para que el modelo sepa cosas de tu proyecto, RAG o búsqueda agéntica; para que se comporte de una manera, primero contexto, y fine-tuning solo si el contexto no basta.

Embeddings #

Un embedding es la representación de un texto como un vector de números (cientos o miles de dimensiones) que captura su significado. Textos con significado parecido tienen vectores cercanos, aunque no compartan palabras: «cancelar suscripción» y «darse de baja» quedan cerca.

  • Se generan con un modelo de embeddings, distinto del LLM y mucho más barato.
  • La cercanía se mide con similitud del coseno o distancia entre vectores.
  • Se guardan en una base de datos vectorial (pgvector en PostgreSQL, Qdrant, Weaviate, Pinecone…). MariaDB y MySQL también han añadido tipos vectoriales en versiones recientes.
  • Usos: búsqueda semántica, documentos similares, clasificación, detectar duplicados (por ejemplo, tickets de Jira repetidos).

Cómo se convierte el texto en esos vectores, en del texto a números.

RAG: buscar antes de responder #

RAG significa generación aumentada por recuperación: antes de responder, el sistema busca la información relevante en tus documentos y la mete en el contexto del modelo. El modelo responde con esos datos delante, en lugar de solo con lo que aprendió al entrenarse.

1 TrocearLos documentos en fragmentos (chunks) de unos cientos de palabras
2 Calcular el embeddingUn vector por fragmento
3 GuardarEn la base vectorial

Indexación: una vez, y al cambiar los documentos.

1 Embedding de la preguntaEl mismo modelo de embeddings
2 Fragmentos más cercanosLos más parecidos por significado
3 Al promptJunto a la pregunta del usuario
4 El LLM respondeBasándose en ellos, idealmente citando la fuente

Consulta: en cada pregunta.

Para qué sirve:

  • Responder sobre información privada o reciente que el modelo no conoce: documentación interna, normativa, wikis, tickets antiguos.
  • Reducir alucinaciones, porque el modelo tiene los datos delante.
  • Escalar a volúmenes que no caben en la ventana de contexto.

RAG vs. búsqueda agéntica #

Los agentes de código como Claude Code no suelen usar RAG con embeddings para el código: buscan con grep, leen archivos y siguen referencias, como haría un desarrollador. Para código esto suele funcionar mejor, porque los nombres exactos importan y el índice no se queda desactualizado.

RAG con embeddingsBúsqueda agéntica
Cómo buscaPor significado, en un índice previoCon herramientas: grep, leer archivos, MCP
Mejor paraMucha documentación en lenguaje naturalCódigo y datos estructurados
MantenimientoReindexar al cambiar los documentosNinguno: lee siempre lo actual
CosteBajo por consultaMás tokens y llamadas

Se pueden combinar: un MCP que haga búsqueda semántica sobre la documentación interna y que el agente use como una herramienta más.

¿Me afecta en el día a día? #

RAG no es algo que el modelo haga internamente: es una arquitectura que alguien construye alrededor del modelo. Usando Claude Code no hay nada que configurar, porque busca en el código con sus propias herramientas.

Saberlo sirve cuando:

  • Construyes algo: un asistente que responda sobre la documentación interna, un buscador de tickets parecidos, una funcionalidad de IA en tu producto. Ahí RAG es el patrón estándar y lo montas tú en PHP con una base vectorial.
  • Evalúas herramientas: muchos productos se anuncian «con RAG»; entender cómo funciona ayuda a saber sus límites.
  • Entiendes respuestas raras: un chatbot con RAG que responde mal suele fallar en la recuperación, no en el modelo.

Caso práctico: documentación funcional en Markdown #

Para consultar documentación funcional en Markdown con un agente no hace falta RAG: el agente busca con grep y lee los archivos que necesita, igual que con el código. Funciona bien mientras la documentación esté bien organizada.

Para que el agente encuentre bien:

  • Un índice: un README.md o INDEX.md que liste cada módulo con una línea de qué cubre y su ruta. Es lo primero que lee.
  • Estructura uniforme: todos los documentos con las mismas secciones (propósito, entidades, flujos, reglas de negocio, integraciones, dependencias con otros módulos).
  • Cabecera con metadatos: módulo, palabras clave, fecha de la última revisión.
  • Nombres reales: usar los nombres de clases, tablas y endpoints tal como están en el código, para que grep los encuentre.
  • Enlaces entre módulos: referencias explícitas a otros documentos cuando un flujo los cruza.
  • Mantenerlos al día: documentación vieja da respuestas incorrectas con total seguridad.

Para un chatbot sobre esa documentación:

OpciónCómoCuándo
Sin RAGUn agente (por ejemplo con el Claude Agent SDK) con herramientas de leer y buscar en esa carpeta. Mismo enfoque que una sesión de Claude CodePor defecto
Contexto completoCargar todo el conjunto en la ventana, con prompt cachingSi todo cabe en la ventana
RAGÍndice vectorial y recuperaciónSolo si el volumen crece mucho, si hay que responder muy rápido y barato a muchos usuarios, o si se mezcla con otras fuentes poco estructuradas

Fine-tuning: cambiar el propio modelo #

El fine-tuning es volver a entrenar un modelo ya existente con tus propios ejemplos, para que cambie su comportamiento de forma permanente. El resultado es un modelo nuevo, con sus pesos modificados.

Cómo funciona: preparas cientos o miles de ejemplos de entrada y salida esperada (por ejemplo, ticket → categoría) y el proveedor o tu propia máquina reentrena el modelo con ellos.

Contexto (rules, skills, prompt)RAGFine-tuning
Qué cambiaLo que el modelo ve en cada llamadaLo que se le busca y añade al contextoEl propio modelo
Mejor paraInstrucciones, convenciones, procedimientosConocimiento grande o cambianteEstilo, formato o tarea muy repetitiva y estrecha
ActualizarEditar un archivoReindexarVolver a entrenar
Coste y esfuerzoMuy bajoMedioAlto: datos, entrenamiento, evaluación

Cuándo compensa

  • Tareas muy repetidas y acotadas a gran volumen, donde un modelo pequeño ajustado sustituye a uno grande más caro.
  • Formatos o estilos muy específicos difíciles de conseguir con instrucciones.
  • Modelos locales de pesos abiertos especializados en una tarea (técnicas como LoRA lo abaratan mucho).

Cuándo no

  • Para el día a día con agentes de código: rules, skills y hooks dan casi siempre mejor resultado con mucho menos esfuerzo.
  • Cuando la información cambia a menudo: el modelo ajustado se queda desactualizado.
  • Cuando el modelo base mejora: cada nueva generación suele superar al modelo ajustado de la anterior, y hay que repetir el trabajo.

Ejemplos prácticos de fine-tuning #

¿Crear tests unitarios? No es buen caso. Aunque las reglas sean siempre las mismas, cada test depende de un código distinto y exige razonar sobre él. Eso lo hace mejor un modelo grande con una skill de tests y los ejemplos del proyecto. «Repetitivo» en fine-tuning significa misma forma de entrada y salida, mucho volumen y poco razonamiento.

CasoEntrada → salidaPor qué encaja
Clasificar tickets de JiraTexto del ticket → equipo, tipo y prioridadMiles al mes, categorías fijas, un modelo pequeño ajustado es rápido y barato
Triaje de errores de SentryTraza → módulo responsable y gravedadPatrón estable propio del proyecto
Extraer datos de documentosFactura o email → JSON con campos fijosFormato muy concreto y gran volumen
Lenguaje natural a consulta«Pedidos de marzo sin pagar» → SQL de un esquema fijoUn esquema concreto que el modelo aprende de memoria
Textos con el tono de la marcaFicha técnica → descripción de productoEstilo difícil de describir con reglas, miles de productos
Autocompletado de código localCódigo propio → sugerencias en el editorModelo pequeño local que aprende las convenciones de tu código

Patrón común: tarea estrecha, salida predecible, muchos ejemplos reales disponibles y volumen suficiente para que el ahorro frente a un modelo grande compense el esfuerzo. Aun así, primero hay que probar con un buen prompt y ejemplos (few-shot): muchas veces basta.

Disponibilidad

Los modelos de Claude más recientes no suelen ofrecerse para fine-tuning general; donde más se hace es con modelos de pesos abiertos (ver IA local).

Cuándo aplicarlo #

Úsalo cuando…

  • Construyes un asistente sobre mucha documentación en lenguaje natural: RAG con una base vectorial
  • Tu documentación funcional cabe en carpetas bien organizadas: búsqueda agéntica, sin RAG
  • Una tarea estrecha se repite miles de veces con la misma forma: fine-tuning de un modelo pequeño

No lo uses cuando…

  • Quieres que un agente de código entienda tu repo: ya busca con grep y lee lo actual
  • Quieres que el modelo sepa cosas de tu proyecto con fine-tuning: enseña comportamiento, no conocimiento
  • No has probado antes un buen prompt con ejemplos: muchas veces basta

Resumen #

Lo que te llevas

  • Un embedding es un vector que captura el significado; textos parecidos quedan cerca aunque no compartan palabras.
  • RAG trocea, indexa y recupera fragmentos para ponerlos delante del modelo; falla más en la recuperación que en el modelo.
  • Para código y documentación bien organizada, la búsqueda agéntica suele ganar: no hay índice que se quede viejo.
  • El fine-tuning enseña comportamiento, no conocimiento: compensa en tareas estrechas, repetidas y a gran volumen.
