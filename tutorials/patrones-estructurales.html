Patrones estructurales: Adapter, Decorator, Facade y Proxy

Los patrones estructurales organizan cómo se componen los objetos. No cambian lo que hacen, sino cómo se relacionan entre sí: adaptando interfaces, añadiendo capas, simplificando subsistemas o controlando el acceso.

La diferencia entre estos cuatro patrones está en la intención, no solo en la estructura. Un Adapter conecta dos interfaces incompatibles. Un Decorator añade responsabilidades. Una Facade oculta complejidad. Un Proxy controla el acceso. El código puede parecerse; el problema que cada uno resuelve es distinto.

Adapter #

El problema: tienes código que espera una interfaz concreta, y una librería externa (o un servicio legado) que hace exactamente lo que necesitas pero con una interfaz diferente. No puedes modificar ninguno de los dos.

Adapter envuelve el objeto incompatible y expone la interfaz que el código espera. Es el "enchufe de viaje" del diseño de software.

php · StripeAdapter.php 
<?php

declare(strict_types=1);

// La interfaz que tu aplicación espera
interface PaymentGateway
{
    public function charge(int $amountCents, string $currency): string;
}

// La librería externa con su propia interfaz (no la puedes cambiar)
class StripeClient
{
    public function createPaymentIntent(array $params): object { /* ... */ }
}

// El Adapter: habla el idioma de tu aplicación, delega en Stripe
class StripeAdapter implements PaymentGateway
{
    public function __construct(
        private readonly StripeClient $stripe
    ) {}

    public function charge(int $amountCents, string $currency): string
    {
        $intent = $this->stripe->createPaymentIntent([
            'amount'   => $amountCents,
            'currency' => $currency,
        ]);

        return $intent->id;
    }
}

// El código de aplicación solo conoce PaymentGateway — nunca StripeClient
class OrderService
{
    public function __construct(
        private readonly PaymentGateway $gateway
    ) {}

    public function pay(Order $order): void
    {
        $transactionId = $this->gateway->charge($order->totalCents(), 'EUR');
        $order->markAsPaid($transactionId);
    }
}

Cambiar de Stripe a PayPal es escribir un PaypalAdapter que implementa PaymentGateway y registrarlo en el contenedor. OrderService no sabe que ha cambiado nada.

Decorator #

El problema: quieres añadir comportamiento a un objeto sin modificarlo y sin usar herencia (que es rígida: no puedes combinar comportamientos en tiempo de ejecución). Decorator envuelve un objeto con otro que implementa la misma interfaz, añade su lógica y delega al objeto envuelto.

php · LoggingUserRepository.php 
<?php

declare(strict_types=1);

interface UserRepository
{
    public function findById(int $id): ?User;
    public function save(User $user): void;
}

class DatabaseUserRepository implements UserRepository
{
    public function findById(int $id): ?User { /* consulta a BD */ }
    public function save(User $user): void { /* persiste en BD */ }
}

// Decorator: añade logging sin tocar DatabaseUserRepository
class LoggingUserRepository implements UserRepository
{
    public function __construct(
        private readonly UserRepository $inner,
        private readonly LoggerInterface $logger
    ) {}

    public function findById(int $id): ?User
    {
        $this->logger->debug("findById({$id})");
        $user = $this->inner->findById($id);
        $this->logger->debug($user ? "encontrado" : "no encontrado");

        return $user;
    }

    public function save(User $user): void
    {
        $this->logger->info("guardando usuario {$user->id()}");
        $this->inner->save($user);
    }
}

// También puedes decorar con caché, métricas, reintentos...
// Cada decorator es independiente y se combina componiendo
$repository = new LoggingUserRepository(
    new CachingUserRepository(
        new DatabaseUserRepository($connection),
        $cache
    ),
    $logger
);

La clave del Decorator es que implementa la misma interfaz que envuelve. Desde fuera es indistinguible del objeto original. Puedes apilar varios decorators — logging encima de caché encima de la BD — y cada uno añade una sola responsabilidad. Esto es lo que OCP pedía: ampliar comportamiento sin modificar código existente.

Facade #

El problema: un subsistema complejo expone muchas clases con muchas responsabilidades. El código cliente que necesita orquestar ese subsistema para una tarea habitual acaba acoplado a muchos detalles internos.

Facade proporciona una interfaz simplificada para un conjunto de interfaces en un subsistema. No limita el acceso al subsistema — el código que lo necesita detallado puede seguir accediendo directamente — pero ofrece un atajo para el caso habitual.

php · OrderFacade.php 
<?php

declare(strict_types=1);

// Sin Facade: el controlador orquesta manualmente stock, pago, factura, email
class OrderController
{
    public function place(Request $request): Response
    {
        $this->stockService->reserve($request->items());
        $transactionId = $this->paymentGateway->charge($request->total(), 'EUR');
        $invoice = $this->invoiceGenerator->generate($request->items(), $transactionId);
        $this->emailService->send($request->email(), $invoice);

        return new Response(201);
    }
}

// Con Facade: una sola llamada para el caso habitual
class OrderFacade
{
    public function __construct(
        private readonly StockService      $stock,
        private readonly PaymentGateway    $gateway,
        private readonly InvoiceGenerator  $invoices,
        private readonly EmailService      $email
    ) {}

    public function placeOrder(array $items, int $totalCents, string $customerEmail): void
    {
        $this->stock->reserve($items);
        $transactionId = $this->gateway->charge($totalCents, 'EUR');
        $invoice = $this->invoices->generate($items, $transactionId);
        $this->email->send($customerEmail, $invoice);
    }
}

class OrderController
{
    public function place(Request $request): Response
    {
        $this->orderFacade->placeOrder(
            $request->items(),
            $request->total(),
            $request->email()
        );

        return new Response(201);
    }
}

El controlador ya no sabe nada de stock, pagos, facturas ni emails. Eso también facilita los tests: en el test del controlador inyectas un mock del OrderFacade y no necesitas mockear cuatro servicios distintos.

Proxy #

Proxy también envuelve un objeto e implementa su misma interfaz, como el Decorator. La diferencia está en la intención: el Decorator añade comportamiento; el Proxy controla el acceso al objeto real. El objeto real puede no crearse hasta que sea necesario (lazy proxy), puede estar en otro proceso o máquina (remote proxy), o puede verificar permisos antes de delegar (protection proxy).

php · LazyUserRepository.php 
<?php

declare(strict_types=1);

// Proxy de caché: no inicializa la conexión hasta la primera llamada,
// y memoriza el resultado para no repetir la consulta
class CachingUserRepository implements UserRepository
{
    private ?UserRepository $inner = null;
    private array $cache = [];

    public function __construct(
        private readonly Connection $connection
    ) {}

    public function findById(int $id): ?User
    {
        if (isset($this->cache[$id])) {
            return $this->cache[$id];
        }

        $this->inner ??= new DatabaseUserRepository($this->connection);
        $user = $this->inner->findById($id);
        $this->cache[$id] = $user;

        return $user;
    }

    public function save(User $user): void
    {
        $this->inner ??= new DatabaseUserRepository($this->connection);
        $this->inner->save($user);
        unset($this->cache[$user->id()]);
    }
}

Proxy en los contenedores DI

Symfony genera proxies automáticamente para los servicios marcados como lazy: true. El contenedor devuelve un proxy que implementa la misma interfaz pero no instancia el servicio real hasta que se llama al primer método. Es exactamente el lazy proxy del ejemplo anterior, generado en tiempo de compilación del contenedor.

Cuándo aplicarlo

Aplícalo cuando…

  • Adapter: necesitas usar una librería externa con una interfaz incompatible con la tuya.
  • Decorator: quieres añadir responsabilidades (logging, caché) sin modificar la clase ni usar herencia.
  • Facade: un subsistema complejo tiene una operación habitual que merece un acceso simplificado.

No lo uses cuando…

  • Adapter si puedes modificar la interfaz directamente sin coste.
  • Decorator si la responsabilidad adicional nunca va a cambiar ni combinarse con otras.
  • Facade si el código cliente ya es simple y el subsistema es reducido.

Resumen #

Lo que te llevas

  • Adapter: conecta dos interfaces incompatibles sin modificar ninguna. Imprescindible para integrar librerías externas sin acoplar el dominio.
  • Decorator: añade comportamiento envolviendo un objeto que implementa la misma interfaz. Apilable, sin herencia, abierto a extensión.
  • Facade: interfaz simplificada para un subsistema complejo. Reduce el acoplamiento del código cliente con los detalles internos.
  • Proxy: controla el acceso al objeto real (lazy init, caché, permisos). Mismo aspecto que Decorator; intención distinta.
