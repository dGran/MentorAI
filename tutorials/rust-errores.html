Sin excepciones en Rust

PHP usa excepciones para el manejo de errores: una función lanza una excepción, sube por el call stack hasta que alguien la captura con try/catch, o la aplicación muere. Los errores son invisibles en el tipo de retorno: mirando la firma de function leerArchivo(string $ruta): string, no sabes que puede lanzar una excepción.

Rust no tiene excepciones. Los errores son valores: una función que puede fallar lo dice en su tipo de retorno.

fn leer_archivo(ruta: &str) -> Result<String, io::Error> {
    fs::read_to_string(ruta)
}

Mirando la firma, sabes que esta función puede fallar con un io::Error. El compilador exige que el caller trate ese posible error. No se puede ignorar accidentalmente un fallo.

La ventaja en equipos: en PHP, es fácil olvidar que una función puede lanzar y no envolverla en try/catch. En Rust, si ignoras un Result (con un warning de variable no usada), el compilador te avisa. No puedes "olvidarte" de manejar un error.

Esta visibilidad tiene un coste: el código que llama a funciones fallibles necesita decidir qué hacer con el error. La herramienta que hace esto ergonómico es el operador ?.

El operador ?

El operador ? es la forma concisa de propagar un error: si el Result es Err, retorna inmediatamente ese error de la función actual. Si es Ok, extrae el valor y continúa.

use std::{fs, io};

fn leer_y_procesar(ruta: &str) -> Result<usize, io::Error> {
    let contenido = fs::read_to_string(ruta)?; // propaga si es Err
    let lineas = contenido.lines().count();
    Ok(lineas)
}

Sin ?, el código equivalente:

fn leer_y_procesar(ruta: &str) -> Result<usize, io::Error> {
    let contenido = match fs::read_to_string(ruta) {
        Ok(c) => c,
        Err(error) => return Err(error),
    };
    let lineas = contenido.lines().count();
    Ok(lineas)
}

El ? aplana esto a una sola línea. Puedes encadenar múltiples operaciones fallibles:

use std::{fs, io, num::ParseIntError};

fn leer_numero(ruta: &str) -> Result<i32, Box<dyn std::error::Error>> {
    let contenido = fs::read_to_string(ruta)?;
    let numero = contenido.trim().parse::<i32>()?;
    Ok(numero)
}

El ? también hace conversión de tipo de error automáticamente si existe una implementación de From<ErrorOrigen> para el tipo de error de la función. Esto es lo que permite mezclar diferentes tipos de error con ? en la misma función.

Errores personalizados con thiserror

Para librerías y servicios, defines tus propios tipos de error. La crate thiserror elimina el boilerplate:

use thiserror::Error;

#[derive(Error, Debug)]
pub enum AppError {
    #[error("usuario {id} no encontrado")]
    UsuarioNoEncontrado { id: u32 },

    #[error("error de base de datos: {0}")]
    BaseDeDatos(#[from] sqlx::Error),

    #[error("error de IO: {0}")]
    Io(#[from] std::io::Error),

    #[error("permiso denegado para {recurso}")]
    PermisoDenegado { recurso: String },
}

fn obtener_usuario(id: u32) -> Result<Usuario, AppError> {
    if id == 0 {
        return Err(AppError::UsuarioNoEncontrado { id });
    }
    Ok(Usuario { id, nombre: "Ana".to_string() })
}

El atributo #[from] genera automáticamente la implementación de From<sqlx::Error> for AppError, lo que permite usar ? con errores de sqlx directamente en funciones que retornan Result<_, AppError>.

Comparación con PHP: crear una excepción personalizada en PHP requiere extender \Exception, sobrescribir opcionalmente el constructor y el mensaje, y crear el árbol de herencia. En Rust, #[derive(Error)] más un par de atributos lo resuelve.

anyhow para aplicaciones

Mientras thiserror es para librerías (tipos de error bien definidos), anyhow es para el código de aplicación donde solo necesitas propagar errores de cualquier tipo sin definir el tuyo propio:

use anyhow::{Context, Result};

fn main() -> Result<()> {
    let config = leer_config("config.toml")
        .context("no se pudo cargar la configuración")?;

    let usuarios = obtener_usuarios(&config)
        .context("error al conectar con la base de datos")?;

    println!("Cargados {} usuarios", usuarios.len());
    Ok(())
}

fn leer_config(ruta: &str) -> Result<Config> {
    let contenido = std::fs::read_to_string(ruta)?;
    let config: Config = toml::from_str(&contenido)?;
    Ok(config)
}

anyhow::Result<T> es Result<T, anyhow::Error>, que acepta cualquier tipo de error que implemente std::error::Error. El ? convierte automáticamente.

.context("mensaje") añade contexto al error cuando se propaga, similar a encadenar excepciones en PHP con el parámetro $previous. El trace de errores resultante muestra toda la cadena de contextos.

? en código async

El operador ? funciona exactamente igual dentro de funciones async:

use anyhow::Result;
use tokio;

async fn llamar_api(url: &str) -> Result<String> {
    let respuesta = reqwest::get(url).await?;
    let texto = respuesta.text().await?;
    Ok(texto)
}

#[tokio::main]
async fn main() -> Result<()> {
    let datos = llamar_api("https://api.ejemplo.com/datos").await?;
    println!("{}", datos);
    Ok(())
}

La propagación de errores es transparente: ? en código sync y ? en código async funcionan igual. La única diferencia es que las funciones async retornan impl Future<Output = Result<T, E>>.

Cuando necesitas convertir entre tipos de error en una cadena async, la implementación de From funciona igual:

#[derive(thiserror::Error, Debug)]
pub enum ApiError {
    #[error("error HTTP: {0}")]
    Http(#[from] reqwest::Error),

    #[error("respuesta inválida: {0}")]
    Deserializacion(#[from] serde_json::Error),
}

async fn obtener_usuario(id: u32) -> Result<Usuario, ApiError> {
    let usuario: Usuario = reqwest::get(format!("/usuarios/{}", id))
        .await?           // convierte reqwest::Error → ApiError::Http
        .json()
        .await?;          // convierte reqwest::Error → ApiError::Http
    Ok(usuario)
}

panic! y cuándo usarlo

Un panic! detiene la ejecución del thread actual inmediatamente con un mensaje de error y el stack trace. Es para bugs irrecuperables, no para errores de usuario:

fn dividir(a: i32, b: i32) -> i32 {
    if b == 0 {
        panic!("división por cero: el denominador no puede ser 0");
    }
    a / b
}

Cuándo usar panic:

  • Tests: unwrap() y expect() son aceptables en tests porque un fallo debe detener el test.
  • Precondiciones violadas: cuando el caller viola un contrato que el compilador no puede verificar.
  • Código prototipo: todo!() y unimplemented!() son panics especiales para código que aún no está implementado.

Cuándo no usar panic:

  • Errores de usuario o de red: un archivo no encontrado, una petición fallida, input inválido. Retorna Result.
  • En código de librería: nunca hagas panic en código que otros van a usar. Retorna Result y deja que el caller decida.
unwrap() en producción: resultado.unwrap() entra en panic si el Result es Err. En código de producción, reemplázalo con ?, match, o .unwrap_or_else(|e| ...). El unwrap() es una señal de que no has pensado en el caso de error.

Resumen

  • En Rust los errores son valores en el tipo de retorno: el compilador exige que el caller los trate. No hay errores silenciosos como en PHP con excepciones no capturadas.
  • El operador ? propaga el error automáticamente si es Err, extrae el valor si es Ok. Hace el código de manejo de errores casi tan conciso como ignorarlos.
  • thiserror es para definir tipos de error en librerías; anyhow para código de aplicación donde cualquier error es válido. Son complementarios, no alternativos.
  • El ? funciona igual en código async: la semántica es idéntica, solo cambia el tipo de retorno de la función.
  • panic! es para bugs irrecuperables y precondiciones violadas, no para errores de usuario. unwrap() en producción es casi siempre un bug esperando ocurrir.
