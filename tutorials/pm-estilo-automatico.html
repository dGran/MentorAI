Estilo automático: PHP-CS-Fixer y GrumPHP

Cada comentario de review sobre una llave o un espacio es tiempo que no se dedica a la lógica. Si una máquina puede decidir el formato, que lo decida ella: antes del commit en tu equipo y otra vez en CI.

El formato del código importa, pero no merece una conversación. Lo que merece es una regla escrita, una herramienta que la aplique y un punto del flujo donde nadie pueda saltársela sin querer. Esta lección monta las tres piezas.

El estilo no se discute #

En un equipo sin reglas automáticas, el estilo se negocia en cada pull request. Uno pone la llave en la misma línea, otro la baja; uno ordena los use, otro no. El resultado es doble: reviews llenas de comentarios que no tratan de lo que hace el código, y diffs donde una línea de lógica viaja con veinte de reformateo que el editor de alguien aplicó sin preguntar.

Automatizar el estilo resuelve las dos cosas a la vez. La discusión se tiene una vez, al escribir la configuración, y a partir de ahí la herramienta decide. El diff solo enseña lo que cambió de verdad y quien revisa se concentra en nombres, diseño y errores. El paso del pipeline ya lo viste en CI para PHP; aquí va lo que hay antes y alrededor.

PER Coding Style, el sucesor de PSR-12 #

Durante años la referencia fue PSR-12, del PHP-FIG. El problema es que un PSR aceptado no se reescribe, y PSR-12 se cerró antes de PHP 8: no dice nada de cómo formatear un enum, un match, una propiedad readonly o un attribute.

Su sucesor es PER Coding Style (PER es PHP Evolving Recommendation): parte de PSR-12 y publica revisiones nuevas a medida que el lenguaje crece. Para un proyecto nuevo no hay mucho que pensar: adopta PER-CS y reserva tus propias reglas para lo que el estándar no cubre.

El fichero de configuración #

PHP-CS-Fixer busca en la raíz del proyecto un fichero .php-cs-fixer.dist.php, que se versiona y es la regla del equipo. Si alguien necesita retocarlo en su máquina, crea un .php-cs-fixer.php sin el .dist, que tiene prioridad y debe ir al .gitignore. El fichero es PHP y devuelve un objeto Config:

php · .php-cs-fixer.dist.php 
<?php

declare(strict_types=1);

use PhpCsFixer\Config;
use PhpCsFixer\Finder;
use PhpCsFixer\Runner\Parallel\ParallelConfigFactory;

$finder = (new Finder())
    ->in([__DIR__ . '/src', __DIR__ . '/tests']);

return (new Config())
    ->setRiskyAllowed(true)
    ->setParallelConfig(ParallelConfigFactory::detect())
    ->setCacheFile(__DIR__ . '/var/.php-cs-fixer.cache')
    ->setRules([
        '@PER-CS3x0' => true,
        '@PHP8x4Migration' => true,
        'declare_strict_types' => true,
        'strict_comparison' => true,
        'no_unused_imports' => true,
        'class_attributes_separation' => ['elements' => ['method' => 'one']],
    ])
    ->setFinder($finder);

Las claves con @ son conjuntos: paquetes de reglas con nombre. @PER-CS3x0 fija una revisión concreta del estándar, para que actualizar la herramienta no te cambie el estilo por sorpresa; @PER-CS a secas apunta siempre a la última. @PHP8x4Migration moderniza la sintaxis hasta lo que permite PHP 8.4, por ejemplo quita los paréntesis de (new Price(100))->equals(...), que en 8.4 ya no hacen falta. Debajo van las reglas sueltas, que añaden o ajustan lo que el conjunto no trae.

Los nombres de los conjuntos cambian

Desde la 3.88 son obsoletos los nombres de versión con punto o sin separador, como @PER-CS3.0 o @PHP84Migration, en favor de @PER-CS3x0 y @PHP8x4Migration. Antes de copiar una configuración, mira qué nombres conoce tu versión con php-cs-fixer list-sets.

Con esa configuración, este fichero:

php · src/Price.php (antes) 
<?php
namespace App;
use DateTimeImmutable;
use InvalidArgumentException;
final class Price {
    public function __construct(private int $cents){
        if($this->cents < 0) throw new InvalidArgumentException('negative');
    }
    public function equals(Price $other) : bool {
        return $this->cents == $other->cents;
    }
}

queda así tras un php-cs-fixer fix:

php · src/Price.php (después) 
<?php

declare(strict_types=1);

namespace App;

use InvalidArgumentException;

final class Price
{
    public function __construct(private int $cents)
    {
        if ($this->cents < 0) {
            throw new InvalidArgumentException('negative');
        }
    }

    public function equals(Price $other): bool
    {
        return $this->cents === $other->cents;
    }
}

Fíjate en lo que no es solo formato: ha aparecido declare(strict_types=1), el use que sobraba se ha ido y el == es ahora ===. El primero y el último alteran el significado del programa: son reglas risky.

Reglas risky #

Una regla risky puede cambiar el comportamiento del código, no solo su aspecto. PHP-CS-Fixer no las aplica salvo que lo autorices con setRiskyAllowed(true) o con --allow-risky=yes. declare_strict_types, strict_comparison, strict_param y native_function_invocation son risky, y los conjuntos que las agrupan llevan el sufijo :risky. Este es el tipo de cambio que provocan:

php · comparacion.php 
<?php

$allowedIds = [1, 2, 3];
$requestedId = '2';

var_dump(in_array($requestedId, $allowedIds));
var_dump(in_array($requestedId, $allowedIds, true));
var_dump($requestedId == 2);
var_dump($requestedId === 2);

Imprime true, false, true, false. Si el id llega como cadena desde una petición, añadir el true que exige strict_param o el === de strict_comparison convierte un acceso permitido en uno denegado. A veces eso destapa un bug; a veces lo crea. Y declare_strict_types hace que una función que espera int y recibía "5" lance un TypeError, como viste en tipado estricto.

Cuándo activarlas: cuando hay tests que cubren el código afectado, en un commit propio que solo contenga ese cambio y con el análisis de PHPStan en verde. En un proyecto nuevo, desde el primer día; en uno heredado sin tests, de una en una.

La caché #

PHP-CS-Fixer guarda una caché con un resumen de cada fichero ya revisado y solo vuelve a analizar los que cambiaron. La caché también registra la versión de PHP, la de la herramienta y las reglas; si cualquiera de las tres cambia, se descarta entera. Por eso basta con dos decisiones: ponerla en un directorio ignorado, como el var/ del ejemplo, y no versionarla nunca. En CI puedes conservarla entre ejecuciones o desactivarla con --using-cache=no.

En CI: comprobar, no corregir #

En el pipeline la herramienta no debe tocar ficheros: un commit que nadie ha revisado no puede salir de CI. Lo que hace es comprobar y fallar si algo no cumple:

bash · comprobación sin escribir 
vendor/bin/php-cs-fixer fix --dry-run --diff

vendor/bin/php-cs-fixer check --diff

echo $?

Las dos enseñan el diff que se aplicaría y salen con código 8 si hay ficheros por corregir, lo que basta para que el job falle. check es la forma corta, la que usa el workflow completo de CI para PHP; no hace falta repetirlo aquí. Sin --diff, quien ve el job en rojo sabe qué fichero falla pero no por qué.

GrumPHP: el gancho antes del commit #

CI avisa tarde: el commit y el push ya están hechos. Un gancho de git (hook) adelanta la comprobación al momento del commit, en la máquina de quien lo escribe. GrumPHP gestiona esos ganchos desde Composer: lo instalas como dependencia de desarrollo y él registra el pre-commit en .git/hooks.

bash · instalación 
composer config --no-plugins allow-plugins.phpro/grumphp-shim true
composer require --dev phpro/grumphp-shim

vendor/bin/grumphp git:init

Es un plugin de Composer, así que tiene que figurar en allow-plugins; sin esa línea, composer require se niega a instalarlo. Una vez permitido, el propio composer install registra los ganchos en cada clon, y git:init los vuelve a poner si alguien los borró. La versión -shim es la distribución en phar, que no mezcla sus dependencias con las tuyas. Las tareas se declaran en grumphp.yml:

yaml · grumphp.yml 
grumphp:
    stop_on_failure: true
    tasks:
        phpcsfixer:
            config: .php-cs-fixer.dist.php
        phpstan:
            configuration: phpstan.neon
            memory_limit: 1G
        phpunit: ~

Al hacer git commit, GrumPHP recibe los ficheros preparados y ejecuta las tres tareas sobre ellos: estilo, análisis estático y tests. Si alguna falla, el commit no se crea y la salida dice qué arreglar; en el caso de PHP-CS-Fixer, hasta el comando exacto. Se puede saltar con git commit --no-verify, y por eso el gancho no sustituye a CI: es la red rápida, y CI la que no se salta nadie.

La alternativa: CaptainHook

CaptainHook resuelve el mismo problema con otro enfoque: en lugar de tareas predefinidas, cada gancho es una lista de acciones en captainhook.json, normalmente comandos de consola. Si tu equipo ya tiene los comandos en los scripts de Composer, cualquiera de los dos solo tiene que llamarlos.

Errores típicos #

Lo que suele salir mal

Reformatear todo el proyecto en el mismo PR que un cambio funcional. El diff se vuelve ilegible y git blame apunta al reformateo. La primera pasada va sola, en su propio commit, y ese commit se puede listar en .git-blame-ignore-revs.

Activar reglas risky sin tests. Un === nuevo puede romper una comparación que dependía de la conversión de tipos, y nadie lo verá hasta producción.

Ejecutar fix en CI. Corrige en el runner y el job sale en verde, pero los ficheros del repositorio siguen igual.

Versionar la caché o dejarla en la raíz sin ignorarla: aparece en cada diff y provoca conflictos sin sentido.

Usar @PER-CS sin revisión fija. Al actualizar la herramienta llega un estilo nuevo, y con él cientos de ficheros cambiados en un PR que solo subía una versión.

Cómo comprobarlo #

Tres pruebas cortas te dicen si el montaje funciona. Primero, php-cs-fixer check --diff sobre el proyecto limpio tiene que salir con código 0. Segundo, estropea a propósito el formato de un fichero, haz git add e intenta el commit: GrumPHP tiene que pararlo y enseñarte el fallo. Tercero, haz push de una rama con ese fichero usando --no-verify: el job de estilo tiene que salir en rojo.

Cuándo aplicarlo #

Fixer y gancho cuando…

  • Más de una persona toca el mismo código
  • Las reviews se llenan de comentarios de formato
  • El proyecto ya tiene tests y PHPStan que el gancho pueda ejecutar
  • Empiezas un proyecto: es cuando menos cuesta

Mejor no, o todavía no, cuando…

  • Los tests tardan minutos: un gancho lento acaba en --no-verify
  • Hay ramas largas abiertas que el reformateo inicial llenaría de conflictos
  • Es un script de un solo uso que nadie va a revisar

La alternativa sencilla

Si el gancho resulta pesado, quita de él los tests y deja solo el estilo, que tarda segundos. O prescinde del gancho y quédate con el fixer configurado en el editor y la comprobación de CI: pierdes el aviso temprano, pero no la garantía.

Resumen #

Lo que te llevas

  • El estilo se discute una vez, en la configuración; después decide la máquina y la review se dedica a la lógica.
  • PER Coding Style sustituye a PSR-12; fija una revisión concreta del conjunto.
  • Las reglas risky cambian el comportamiento: actívalas con tests y en un commit propio.
  • La caché se invalida sola y va en un directorio ignorado.
  • En CI se comprueba con --dry-run --diff o check, nunca se corrige.
  • GrumPHP adelanta estilo, PHPStan y tests al commit; se puede saltar, así que CI sigue siendo la garantía.
