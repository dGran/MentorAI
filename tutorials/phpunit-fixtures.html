Fixtures y ciclo de vida del test

Cada test necesita su escenario montado antes de empezar y recogido al terminar. PHPUnit tiene un ciclo de vida preciso para eso — y entenderlo es la diferencia entre tests independientes y una suite que falla según el orden en que corre.

Al escenario que un test necesita montado —objetos, datos, dobles— se le llama fixture. PHPUnit ofrece ganchos para construirlo y desmontarlo, pero antes de usarlos conviene saber una cosa que sorprende a casi todo el mundo: cómo ejecuta PHPUnit tus tests por dentro.

El ciclo de vida por dentro #

El dato clave: PHPUnit crea una instancia nueva de tu clase de test para cada método. Si tu clase tiene cinco tests, se instancia cinco veces. Las propiedades del objeto no sobreviven de un test al siguiente — y eso es deliberado: es la primera línea de defensa del aislamiento.

1 setUpBeforeClass()Una vez, antes de todos los tests de la clase (estático)
2 new TuTest() → setUp() → el test → tearDown()Instancia nueva, montar, probar, desmontar
3 tearDownAfterClass()Una vez, después del último test (estático)

El paso 2 se repite entero por cada método de test: instancia limpia, escenario limpio.

Con ese mapa, los ganchos se explican solos: setUp() corre antes de cada test y tearDown() después de cada test; los métodos *Class son estáticos y corren una sola vez por clase.

setUp y tearDown en la práctica #

setUp() es el sitio del escenario común: lo que todos los tests de la clase necesitan igual. El caso típico, construir el objeto bajo prueba con sus dobles:

php · escenario común en setUp 
final class OrderServiceTest extends TestCase
{
    private InMemoryOrderRepository $repository;
    private OrderService $service;

    protected function setUp(): void
    {
        $this->repository = new InMemoryOrderRepository();
        $this->service = new OrderService($this->repository);
    }

    #[Test]
    public function guarda_el_pedido_confirmado(): void
    {
        $this->service->confirm(new Order(id: 7));

        $this->assertCount(1, $this->repository->all());
    }
}

tearDown() es el simétrico: limpiar lo que el test haya dejado fuera del objeto — cerrar un fichero temporal, restaurar una variable de entorno, vaciar una cola. Para objetos en memoria normalmente no hace falta: la instancia muere con el test y el recolector hace el resto.

setUp no es un trastero

Si el setUp monta cosas que solo usan dos de diez tests, los otros ocho pagan un escenario que no entienden ni necesitan — y quien lea un test tiene que subir al setUp para saber de dónde sale cada cosa. Regla práctica: al setUp va lo universal de la clase; lo particular de cada test, dentro del test (o en un método privado con nombre expresivo: $this->pedidoConDosLineas()).

Los métodos de clase #

setUpBeforeClass() y tearDownAfterClass() existen para recursos caros de crear y seguros de compartir: la conexión a la base de datos de test, un contenedor arrancado, un servidor fake. Crearlos una vez por clase en lugar de una vez por test puede ahorrar minutos de suite.

La palabra que importa es seguros: como son estáticos y viven entre tests, cualquier cosa mutable que guardes ahí es un canal de contaminación entre tests. Una conexión, sí; los datos que los tests escriben a través de ella, no — de limpiarlos se encarga cada test (en la lección de integración con BD verás el patrón de la transacción con rollback, que resuelve esto con elegancia).

Tests independientes #

Todo este ciclo de vida sirve a un principio que ya conoces de FIRST: cada test debe poder ejecutarse solo, en cualquier orden, y dar el mismo resultado. Un test que solo pasa si otro corrió antes no es un test: es una trampa retardada que explotará cuando alguien ejecute con --filter o cuando el orden cambie.

Hay una forma barata de comprobar que tu suite lo cumple: pedirle a PHPUnit que baraje el orden en cada ejecución.

bash · detectar dependencias ocultas entre tests 
vendor/bin/phpunit --order-by=random

# reproducir un fallo de orden concreto
vendor/bin/phpunit --order-by=random --random-order-seed=1234

Si la suite pasa en orden natural y falla barajada, tienes tests acoplados; la semilla te deja reproducir la combinación exacta que falló. Activarlo en el CI convierte la independencia de deseo en garantía.

El estado compartido, el enemigo #

Si la instancia se renueva por test, ¿por dónde se contaminan los tests entre sí? Por todo lo que vive fuera de la instancia. La lista de sospechosos habituales:

Canal de contaminaciónAntídoto
Propiedades y variables static (incl. singletons)Evitarlos en diseño; si no hay más remedio, resetear en setUp/tearDown.
La base de datos de testTransacción por test con rollback (próximas lecciones).
Ficheros y directorios temporalesNombre único por test + borrado en tearDown.
Variables de entorno y config globalGuardar el valor original y restaurarlo en tearDown.
El reloj (time(), new DateTime())Inyectar un reloj (DI): el tiempo real hace tests no repetibles.

El patrón de los cinco es el mismo: estado global mutable. El mismo enemigo que ya señalaban las funciones limpias (efectos secundarios) y la inyección de dependencias, visto ahora desde los tests: lo que hace difícil testear algo suele ser exactamente lo que lo hace frágil en producción. Los tests que se contaminan no son un problema de PHPUnit — son un síntoma de diseño que PHPUnit te está regalando.

Resumen #

Lo que te llevas

  • PHPUnit instancia tu clase de test una vez POR MÉTODO: las propiedades no sobreviven entre tests, a propósito.
  • setUp/tearDown corren por cada test (escenario común); setUpBeforeClass/tearDownAfterClass una vez por clase (recursos caros y seguros de compartir).
  • Al setUp va lo universal de la clase; lo particular de cada test, en el test. Un setUp trastero hace ilegibles los diez tests de abajo.
  • --order-by=random en CI convierte la independencia en garantía; la semilla reproduce el fallo exacto.
  • La contaminación viaja por el estado global mutable: statics, BD, ficheros, entorno y el reloj. Un test difícil de aislar es un aviso de diseño.
