Logging seguro: qué registrar y qué nunca

El día que te atacan, los logs son lo único que te cuenta qué pasó. El resto del tiempo son una base de datos copiada en cinco sitios y que lee medio equipo. Esta lección va de que sirvan para lo primero sin convertirse en una fuga por lo segundo.

Un log de seguridad tiene que contestar cuatro preguntas tras un incidente: quién, qué, cuándo y desde dónde. Y no debe contener nada que, si el log se filtra, le dé al atacante algo que no tenía.

Los dos fallos opuestos #

Los logs fallan en seguridad de dos formas que tiran en direcciones contrarias, y por eso cuesta acertar:

Registrar de menos

  • Te enteras del ataque por un cliente, semanas después.
  • No puedes saber qué cuentas se vieron afectadas.
  • Es Security Logging and Monitoring Failures (A09) del OWASP Top 10 2021.

Registrar de más

  • Contraseñas y tokens en texto plano en el agregador.
  • Datos personales con más copias y más lectores que la propia base de datos.
  • Una fuga del sistema de logs equivale a una fuga de producción.

La raíz es la misma: tratar el log como un volcado de lo que pasa por el código en vez de como un registro diseñado. Los fundamentos (niveles, JSON, request_id, PSR-3) ya están en Logs estructurados; aquí se mira todo eso con ojos de atacante.

Qué registrar: eventos que permiten investigar #

No hace falta registrarlo todo, sino las decisiones de seguridad que toma tu aplicación. Cada una con un nombre de evento estable, para poder contarlas y alertar sobre ellas:

EventoPor qué importaContexto mínimo
auth.login_failedFuerza bruta y relleno de credencialesIdentificador intentado, IP, motivo
auth.login_succeededSaber qué pasó después de una racha de fallosId de usuario, IP
authz.access_deniedAlguien probando recursos ajenosId de usuario, recurso, acción
user.role_changedEscalada de privilegiosQuién lo cambió, a quién, de qué a qué
auth.password_resetToma de cuentasId de usuario, IP
auth.mfa_disabledPaso previo típico a un abusoId de usuario, quién lo hizo

Fíjate en que ninguna fila lleva el valor de un secreto. Para investigar necesitas saber que alguien presentó un token caducado, no el token. Y el request_id de cada evento es lo que te permite enlazarlo con el resto de la petición.

Un canal propio para auditoría

Separar estos eventos en su propio canal (audit) permite darles otra retención y otro control de acceso que a los logs de depuración. En Symfony basta con declararlo en monolog.channels e inyectar LoggerInterface $auditLogger; en Laravel, un canal más en config/logging.php.

Qué no registrar nunca #

La lista es corta: contraseñas (tampoco hasheadas), tokens de sesión, de API o de restablecimiento, cabeceras Authorization y Cookie, secretos de configuración, números de tarjeta y datos personales que no necesites para investigar. Que la IP también es un dato personal no significa que no puedas guardarla, sino que su retención tiene que estar justificada.

El problema es que casi nunca se registran a propósito. Se cuelan por el camino del medio: el contexto que se pasa entero. Mira este listener de Laravel, que parece inofensivo:

php · vulnerable · app/Listeners/RegistrarLoginFallido.php 
<?php

declare(strict_types=1);

namespace App\Listeners;

use Illuminate\Auth\Events\Failed;
use Illuminate\Support\Facades\Log;

final class RegistrarLoginFallido
{
    public function handle(Failed $event): void
    {
        Log::warning('auth.login_failed', [
            'credentials' => $event->credentials,
            'request' => request()->all(),
        ]);
    }
}

$event->credentials lleva la contraseña tal cual la escribió el usuario, y request()->all() la vuelve a meter. Peor aún: una contraseña fallida suele ser la correcta con una errata, o la de otro servicio. La versión corregida elige los campos uno a uno:

php · corregido · app/Listeners/RegistrarLoginFallido.php 
<?php

declare(strict_types=1);

namespace App\Listeners;

use Illuminate\Auth\Events\Failed;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Log;

final class RegistrarLoginFallido
{
    private const EVENTO = 'auth.login_failed';
    private const CANAL = 'audit';

    public function __construct(private readonly Request $request) {}

    public function handle(Failed $event): void
    {
        Log::channel(self::CANAL)->warning(self::EVENTO, [
            'identificador' => hash('sha256', (string) ($event->credentials['email'] ?? '')),
            'usuario_id' => $event->user?->getAuthIdentifier(),
            'ip' => $this->request->ip(),
            'guard' => $event->guard,
        ]);
    }
}

El email va con hash por un motivo concreto: hay quien escribe la contraseña en el campo del usuario. Con el hash sigues pudiendo agrupar intentos contra la misma cuenta sin guardar lo que se tecleó. Es seudonimización, no anonimato: un SHA-256 de un email se revierte probando emails conocidos; si eso te preocupa, usa hash_hmac con una clave propia. Si el email existe, usuario_id ya identifica la cuenta.

Redactar campos en Monolog #

Elegir los campos a mano es la defensa principal, pero alguien acabará pasando un array entero. Para eso se pone una red de seguridad en el propio logger: un processor de Monolog que reescribe cada registro antes de que llegue a cualquier handler. En Monolog 3 el registro es un LogRecord inmutable, así que se devuelve una copia con with():

php · src/Logging/RedactarCamposSensibles.php 
<?php

declare(strict_types=1);

namespace App\Logging;

use Monolog\Attribute\AsMonologProcessor;
use Monolog\LogRecord;
use Monolog\Processor\ProcessorInterface;

#[AsMonologProcessor]
final class RedactarCamposSensibles implements ProcessorInterface
{
    private const MASCARA = '[REDACTADO]';
    private const CLAVES_SENSIBLES = ['password', 'token', 'secret', 'authorization', 'cookie', 'card'];

    public function __invoke(LogRecord $record): LogRecord
    {
        return $record->with(
            context: $this->redactar($record->context),
            extra: $this->redactar($record->extra),
        );
    }

    private function redactar(array $datos): array
    {
        foreach ($datos as $clave => $valor) {
            if ($this->esSensible((string) $clave)) {
                $datos[$clave] = self::MASCARA;

                continue;
            }

            if (is_array($valor)) {
                $datos[$clave] = $this->redactar($valor);
            }
        }

        return $datos;
    }

    private function esSensible(string $clave): bool
    {
        $claveNormalizada = strtolower($clave);

        foreach (self::CLAVES_SENSIBLES as $claveSensible) {
            if (str_contains($claveNormalizada, $claveSensible)) {
                return true;
            }
        }

        return false;
    }
}

En Symfony, el atributo #[AsMonologProcessor] lo registra en todos los canales con autoconfiguración. En Laravel se engancha con la clave tap de cada canal en config/logging.php ('tap' => [AplicarRedaccion::class]), que recibe el logger al crearlo:

php · app/Logging/AplicarRedaccion.php 
<?php

declare(strict_types=1);

namespace App\Logging;

use Illuminate\Log\Logger;

final class AplicarRedaccion
{
    public function __invoke(Logger $logger): void
    {
        $logger->pushProcessor(new RedactarCamposSensibles());
    }
}

Por qué es solo una red

Redactar por nombre de clave es una lista negra: no ve un token dentro del mensaje ni un campo llamado clave_api. Sirve para cazar el descuido habitual, no para sustituir la lista blanca de campos que pones en cada llamada.

Inyección en logs: el salto de línea #

Si concatenas entrada del usuario en un log de texto, el usuario escribe en tu log. Con un salto de línea (%0A en la URL) fabrica una línea entera que parece tuya: un email como x@x.es\n[2026-10-12] Login correcto para admin@empresa.es deja en el fichero un acceso que nunca ocurrió, y un investigador lo creerá. Arriba, la forma vulnerable; abajo, la corregida:

php · vulnerable frente a corregido 
<?php

declare(strict_types=1);

error_log('Login fallido para ' . $request->get('email'));

$logger->warning('auth.login_failed', ['identificador' => $identificadorConHash]);

La corrección no es escapar a mano, sino no concatenar: mensaje constante y datos en el contexto. Los formateadores de Monolog ya neutralizan los saltos de línea (JsonFormatter los escapa dentro del JSON; LineFormatter los sustituye salvo que actives allowInlineLineBreaks). El riesgo vuelve con error_log(), con file_put_contents o con ese formateador «para que se vean bien las trazas».

Hay una segunda cara: si tu visor de logs pinta HTML sin escapar, un <script> en el campo User-Agent se ejecuta en el navegador de quien investiga, que suele ser alguien con muchos permisos. Es el XSS almacenado de OWASP imprescindible, con el log como almacén.

Retención, acceso y alertas #

Un log de auditoría que el atacante puede borrar no vale para auditar. Tres decisiones lo convierten en evidencia:

1 Fuera de la máquinaEnvío continuo a un agregador: con root en el servidor no se reescribe la historia
2 Quién puede leerAuditoría solo para quien investiga; depuración para el equipo
3 Retención con fechaCorta para depuración; la de auditoría, la que fije tu política y la normativa

Cada copia de un log es una copia de los datos que contiene, con su propio riesgo.

El endurecimiento de la máquina que envía los logs está en Endurecer un servidor. Lo que toca a la aplicación son las alertas, y la regla es alertar sobre tasas y patrones, no sobre eventos sueltos: un login fallido es ruido; cientos contra cuentas distintas desde la misma IP es relleno de credenciales.

  • Picos de auth.login_failed por IP o por cuenta.
  • Ráfagas de authz.access_denied de un mismo usuario: alguien recorriendo ids ajenos.
  • Cualquier user.role_changed hacia administrador fuera del proceso habitual.
  • Que dejen de llegar logs: es lo primero que hace quien no quiere ser visto.

Errores típicos #

Los que más se repiten

  • Registrar el cuerpo de la petición «para depurar» y olvidarlo en producción: arrastra contraseñas, tokens y datos personales.
  • Registrar la excepción con su contexto entero: algunas llevan la consulta con parámetros o la URL con el token en la query string.
  • Tener redacción solo en un canal, mientras el del framework, el de colas o el de Sentry siguen escribiendo sin ella.
  • Mensajes variables ("Fallo para $email"): abren la inyección y además impiden agrupar y alertar.
  • No registrar los accesos denegados porque «ya devolvemos 403»: el 403 protege, pero sin el log nadie ve que alguien está probando.

Cómo detectarlo y testearlo #

El processor es una clase pura: se prueba como cualquier otra. Y el flujo completo se comprueba con el TestHandler de Monolog, que guarda en memoria lo que se habría escrito:

php · tests/Logging/RedactarCamposSensiblesTest.php 
<?php

declare(strict_types=1);

use App\Logging\RedactarCamposSensibles;
use Monolog\Handler\TestHandler;
use Monolog\Logger;
use PHPUnit\Framework\TestCase;

final class RedactarCamposSensiblesTest extends TestCase
{
    private const PASSWORD = 'MiClaveSecreta-2026';

    public function testNoEscribeLaPasswordAunqueVengaAnidada(): void
    {
        $handler = new TestHandler();
        $logger = new Logger('audit', [$handler], [new RedactarCamposSensibles()]);

        $logger->warning('auth.login_failed', ['credentials' => ['email' => 'a@b.es', 'password' => self::PASSWORD]]);

        $registro = $handler->getRecords()[0];
        self::assertStringNotContainsString(self::PASSWORD, json_encode($registro->context));
    }
}

Fuera de los tests, busca de vez en cuando en los logs de preproducción patrones que nunca deberían aparecer: Bearer , eyJ (el arranque en Base64 de casi todo JWT), password o "set-cookie". Si un barrido así encuentra algo, tienes un hueco que el processor no cubre.

Cuándo aplicarlo #

Sí

  • Cualquier aplicación con login, roles o datos de usuarios: los eventos de auditoría y la redacción desde el primer día.
  • Al añadir un endpoint que decide acceso: su access_denied se registra igual que se testea su 403.
  • Al integrar un SDK o un handler nuevo: comprobar que pasa por la redacción.

No hace falta

  • Un canal de auditoría separado en un script interno sin usuarios ni datos personales.
  • Registrar cada lectura correcta de cada recurso: es ruido caro que tapa lo que importa.

La alternativa a un sistema propio de auditoría, cuando el volumen o la normativa lo piden, es una tabla de auditoría en base de datos o un servicio dedicado con escritura de solo añadir. El principio es el mismo: eventos con nombre, campos elegidos, nada de secretos.

Resumen #

Lo que te llevas

  • Registra las decisiones de seguridad (login fallido, acceso denegado, cambio de rol) con nombre estable, quién, qué, cuándo y desde dónde.
  • Nunca contraseñas, tokens, cabeceras de autenticación ni cuerpos completos: elige los campos uno a uno.
  • Un processor de Monolog que redacta claves sensibles es la red de seguridad, no la defensa principal.
  • Mensaje constante y datos en el contexto: así no hay inyección por saltos de línea y puedes agrupar.
  • Logs fuera de la máquina, con acceso mínimo y retención con fecha; alertas sobre tasas, no sobre eventos sueltos.
