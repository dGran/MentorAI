Loki y LogQL

Loki aplica la misma filosofía que Prometheus al almacenamiento de logs: no indexa el contenido de cada línea, sino solo las etiquetas. Eso lo hace barato y rápido. El precio es que la consulta no es un grep libre sino LogQL — un lenguaje expresivo con el que, al terminarlo, sabrás escribir cualquier consulta avanzada que necesites.

Una consulta LogQL sigue siempre la misma estructura: empieza con un stream selector que elige qué logs ver, y luego se pueden encadenar filtros y transformaciones. Cada capa refina o transforma el resultado de la anterior — es un pipeline.

Loki: labels vs contenido #

Elasticsearch indexa el contenido de cada campo de cada log — por eso es potente pero también caro en CPU, memoria y disco. Loki solo indexa las etiquetas (labels) que defines en el colector (Promtail, Alloy o similar): app, env, container. El contenido de cada línea de log se comprime y almacena sin indexar.

Las consecuencias son importantes: las etiquetas de Loki deben ser, como las de Prometheus, de cardinalidad baja — los mismos valores que repetirías en miles de líneas. El nombre del contenedor, el servicio, el entorno. Nunca el request_id como etiqueta — eso es texto que va dentro de la línea y que LogQL filtrará en el pipeline.

Etiquetas de Loki y logs estructurados

Si seguiste el tutorial de logs estructurados, verás la conexión: los campos JSON que pusiste en el contexto del log (order_id, level, reason) son los que el parser json de LogQL extrae y convierte en etiquetas consultables — dentro del pipeline, no como etiquetas de indexación.

Stream selectors #

El stream selector es el punto de entrada obligatorio de cualquier consulta LogQL. Funciona exactamente igual que los selectores de Prometheus — con los mismos operadores:

LogQL · stream selectors 
# todos los logs de la app "api"
{app="api"}

# logs de api en producción
{app="api", env="production"}

# cualquier app que empiece por "worker-"
{app=~"worker-.+"}

# todos los servicios excepto el healthcheck
{app!="healthcheck"}

El stream selector solo opera sobre las etiquetas indexadas de Loki — es la parte "barata". Lo que viene después (filtros de línea, parsers) opera sobre el contenido de cada línea y es más costoso computacionalmente, por eso va después del selector que ya reduce el conjunto.

Line filters #

Los line filters buscan texto dentro de cada línea de log. Son rápidos porque actúan antes de parsear:

LogQL · line filters 
# líneas que contienen "error"
{app="api"} |= "error"

# líneas que NO contienen "health"
{app="api"} != "health"

# líneas que coinciden con una regex
{app="api"} |~ "order_id.*8[0-9]{3}"

# regex negativa
{app="api"} !~ "GET /metrics"

Los operadores son: |= (contiene), != (no contiene), |~ (regex), !~ (regex negativa). Úsalos para reducir el volumen de líneas antes de parsear — es el equivalente al grep que harías en la terminal, pero integrado en el pipeline.

Parsers de formato #

Los parsers extraen campos de la línea de log y los convierten en etiquetas disponibles para los filtros y funciones siguientes del pipeline:

LogQL · parsers disponibles 
# json: extrae todos los campos del JSON como etiquetas
{app="api"} | json

# logfmt: para logs en formato key=value
{app="nginx"} | logfmt

# pattern: extrae campos por posición con un patrón
{app="nginx"} | pattern ` - - [<_>] "  <_>"  <_>`

# regexp: extrae con grupos nombrados
{app="api"} | regexp `"order_id":(?P\d+)`

Tras parsear, los campos extraídos (level, order_id, method…) están disponibles como etiquetas en el resto del pipeline. Es ahí donde cobra valor el log estructurado que aprendiste a emitir.

Label filters #

Los label filters actúan sobre las etiquetas extraídas por el parser. Permiten filtros numéricos y comparaciones que un line filter no puede hacer:

LogQL · label filters tras parsear JSON 
# solo logs de nivel error o critical
{app="api"} | json | level =~ "error|critical"

# pagos fallidos de más de 100€
{app="api"} | json | reason = "card_declined" | amount_cents > 10000

# peticiones lentas: duration extraído por logfmt, mayor a 2s
{app="nginx"} | logfmt | duration > 2s

# combinar line filter + parser + label filter (pipeline completo)
{app="api"} |= "Payment" | json | level = "error" | amount_cents > 5000

Métricas sobre logs #

LogQL puede generar métricas a partir de logs — el puente entre el pilar de logs y el de métricas. Esto permite crear alertas o paneles de Grafana a partir de patrones en los logs sin necesitar Prometheus:

LogQL · métricas sobre logs 
# tasa de líneas de log por segundo (todas)
rate({app="api"}[5m])

# tasa de errores por segundo
rate({app="api"} | json | level = "error" [5m])

# conteo de eventos en la última hora
count_over_time({app="api"} |= "Payment failed" [1h])

# tasa de error desglosada por endpoint (tras parsear JSON)
sum by (endpoint) (
  rate({app="api"} | json | level = "error" [5m])
)

Estas expresiones de métricas se pueden usar directamente en paneles de Grafana tipo Time series o en reglas de alertas de Loki — exactamente igual que las expresiones PromQL en Prometheus.

Consultas avanzadas #

Combinando todo lo anterior, estas son las consultas que resuelven los escenarios reales más frecuentes:

LogQL · escenarios reales 
# todos los logs de una petición concreta (correlation por request_id)
{app="api"} | json | request_id = "req-a3f9b2"

# los 20 últimos errores de producción con contexto completo
{app="api", env="production"} | json | level = "error" | line_format "{{.message}} order={{.order_id}} reason={{.reason}}"

# top errores agrupados por mensaje en la última hora
topk(10,
  sum by (message) (
    count_over_time({app="api"} | json | level = "error" [1h])
  )
)

# usuarios afectados por pagos fallidos hoy
count_distinct_over_time(
  {app="api"} | json | reason = "card_declined" | unwrap user_id [24h]
)

# correlación: spikes de errores con deployments
{app="api"} | json | level = "error"
# (en Grafana, superpuesto con el panel de deploys de CI)

line_format para legibilidad

line_format "{{.campo}}" reformatea cada línea usando plantillas Go. Es útil cuando tienes logs JSON muy verbosos y quieres ver en el panel de Grafana solo los campos relevantes, sin el JSON completo. Puede ir al final de cualquier pipeline LogQL.

Cuándo aplicarlo #

Úsalo cuando…

  • Ya tienes el stack de Grafana y quieres una solución integrada sin cambiar de herramienta.
  • El volumen de logs es moderado y el bajo coste de almacenamiento es prioritario.
  • No necesitas búsqueda full-text sobre el contenido de cada línea, solo filtrado por etiquetas y campos estructurados.

No lo uses cuando…

  • Necesitas búsquedas full-text complejas sobre el contenido de los logs: ahí Elasticsearch/Kibana.
  • El volumen es masivo y la indexación total de Elasticsearch tiene sentido económico y operacional.
  • El equipo ya domina el stack ELK y la migración a Loki no aporta valor suficiente para justificarla.

Resumen #

Lo que te llevas

  • Loki indexa solo etiquetas, no contenido. Etiquetas de cardinalidad baja (app, env, container). El contenido — request_id, order_id — se filtra en el pipeline.
  • Pipeline LogQL: {stream selector} → |= line filter → | parser → | label filter. Orden importa: reducir primero (barato), parsear después (costoso).
  • Parser | json extrae todos los campos del JSON como etiquetas disponibles. | logfmt para key=value. | pattern y | regexp para formatos personalizados.
  • Label filters permiten comparaciones numéricas y de duración: | amount_cents > 10000, | duration > 2s. Imposibles con line filters de texto.
  • rate([5m]) y count_over_time([1h]) convierten logs en métricas. Se usan en paneles de Grafana y en alertas de Loki igual que PromQL.
  • Consulta de correlación: {app="api"} | json | request_id = "req-xyz" da todos los logs de una petición concreta — el uso más frecuente durante un incidente.
