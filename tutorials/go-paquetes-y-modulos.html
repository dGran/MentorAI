Paquetes y módulos: la unidad de organización

En Go el código se organiza en paquetes y los proyectos en módulos. go.mod y go.sum son el composer.json y el composer.lock de Go: declaran dependencias y fijan las versiones exactas que se usan.

En PHP, el namespace y el autoloader de Composer deciden dónde vive cada clase, y la visibilidad la marca cada método. Go traslada esas dos decisiones al paquete: qué ficheros van juntos y qué nombres ven los demás. Organizarlo bien desde el principio te ahorra el error que más frena a quien llega de PHP: los ciclos de importación.

Qué es un paquete #

Un paquete en Go es un directorio con ficheros .go que comparten la misma declaración package. El nombre del paquete suele coincidir con el nombre del directorio, aunque no es obligatorio.

La stdlib de Go está organizada en paquetes: fmt para formateo, net/http para HTTP, os para el sistema operativo, strings para manipulación de cadenas. Cada uno es un directorio en la instalación de Go.

go 
// fichero: matematicas/suma.go
package matematicas    // nombre del paquete

func Suma(a, b int) int {
    return a + b
}

func sumaInterna(a, b int) int {   // minúscula: solo visible dentro del paquete
    return a + b
}
go 
// fichero: main.go
package main

import (
    "fmt"
    "mi-proyecto/matematicas"
)

func main() {
    resultado := matematicas.Suma(3, 4)    // mayúscula: accesible
    fmt.Println(resultado)                  // 7
}

Visibilidad: mayúscula vs minúscula #

Go no tiene public, private ni protected. La regla es una sola: mayúscula inicial = exportado (visible desde fuera del paquete); minúscula inicial = no exportado (privado al paquete).

PHP

php 
class Calculadora {
    public function sumar(int $a, int $b): int {
        return $a + $b;
    }

    private function log(): void {}
}

Go

go 
// en el paquete calculadora
func Sumar(a, b int) int {    // exportada
    return a + b
}

func logear() {               // no exportada
}

La regla aplica a funciones, tipos, variables, constantes y campos de struct. Si el nombre empieza con mayúscula, es parte de la API pública del paquete.

Módulos: go.mod y go.sum #

Un módulo es la unidad de distribución de Go: un árbol de paquetes con un fichero go.mod en la raíz. El módulo tiene un nombre (su ruta de importación) y declara sus dependencias.

bash 
// go.mod
module github.com/usuario/mi-servicio

go 1.27

require (
    github.com/gin-gonic/gin v1.10.0
    github.com/lib/pq v1.12.3
)

PHP (composer.json)

bash 
{
  "name": "usuario/mi-servicio",
  "require": {
    "laravel/framework": "^11.0",
    "doctrine/orm": "^3.0"
  }
}

Go (go.mod)

bash 
module github.com/usuario/mi-servicio

go 1.27

require (
    github.com/gin-gonic/gin v1.10.0
    github.com/jmoiron/sqlx v1.3.5
)

go.sum fija los checksums criptográficos de cada dependencia y sus dependencias transitivas. Es el equivalente al composer.lock: garantiza que todos en el equipo (y el CI) usan exactamente los mismos binarios. Nunca se edita a mano.

Imports y alias #

Los imports usan la ruta completa del paquete pero se usan por el nombre corto final:

go 
import (
    "fmt"                           // uso: fmt.Println
    "net/http"                      // uso: http.Get
    "github.com/gin-gonic/gin"      // uso: gin.New
)

Cuando dos paquetes tienen el mismo nombre final, se usa un alias:

go 
import (
    pgx "github.com/jackc/pgx/v5"          // alias: pgx
    stdlib "github.com/jackc/pgx/v5/stdlib" // alias: stdlib
)

El import con guión bajo descarta el paquete pero ejecuta su función init() — útil para registrar drivers de base de datos:

go 
import (
    "database/sql"
    _ "github.com/lib/pq"    // registra el driver postgres, no se usa directamente
)

Errores típicos al organizar paquetes

  • Importar por el nombre de la carpeta. import "matematicas" falla con package matematicas is not in std: Go busca en la stdlib. La ruta es siempre la del módulo que declara go.mod más la carpeta: "mi-proyecto/matematicas".
  • Crear ciclos de importación. En PHP el autoloader deja que A use B y B use A; Go lo rechaza con import cycle not allowed. Se resuelve moviendo lo común a un tercer paquete, o haciendo que uno dependa de una interfaz que define él mismo.
  • Un paquete por clase. Trasladar la estructura de src/ de PHP crea decenas de paquetes diminutos que se importan entre sí y acaban en ciclos. Agrupa por responsabilidad.
  • Repetir el nombre del paquete en lo que exporta. usuarios.UsuarioService se lee «usuarios usuario service»; en Go es usuarios.Service. Y evita paquetes utils o common: no dicen qué contienen y acaban importados por todo.

Gestionar dependencias #

bash 
# Añadir una dependencia
go get github.com/gin-gonic/gin@v1.10.0

# Actualizar a la última versión compatible
go get github.com/gin-gonic/gin@latest

# Eliminar dependencias no usadas / añadir las que faltan
go mod tidy

# Ver el árbol de dependencias
go mod graph

# Descargar todas las dependencias al caché local
go mod download

go mod tidy no tiene equivalente exacto en Composer: añade a go.mod lo que importas y no estaba, quita lo que ya no usas y completa go.sum. Ejecútalo antes de cada commit para que go.mod y go.sum reflejen los imports reales.

El directorio internal #

Go tiene un mecanismo de encapsulamiento a nivel de módulo: el directorio internal/. La herramienta go impide importar un paquete de internal/ desde fuera del árbol que cuelga de su directorio padre; si internal/ está en la raíz, eso es el módulo entero. No es una convención: go build falla con use of internal package … not allowed.

bash 
mi-servicio/
├── cmd/
│   └── server/
│       └── main.go        # puede importar internal/
├── internal/
│   ├── auth/              # solo importable desde mi-servicio
│   └── db/                # solo importable desde mi-servicio
└── pkg/
    └── utils/             # importable desde cualquier módulo externo

La convención es: internal/ para código privado del módulo; pkg/ para código que quieres ofrecer a otros módulos.

Cuándo aplicarlo #

La pregunta de diseño en Go no es «¿en qué clase va esto?» sino «¿en qué paquete?», y la respuesta por defecto es: en menos de los que crees.

  • Un paquete nuevo por responsabilidad con API propia que otros consumen (internal/auth, internal/db), no uno por tipo como harías con PSR-4. Un paquete puede tener diez ficheros y está bien.
  • Exporta solo lo que otro paquete necesita llamar. Empieza en minúscula y súbelo cuando haga falta: añadir una exportación no rompe a nadie, quitarla rompe a quien la usaba.
  • internal/ por defecto en una aplicación. pkg/ solo si de verdad otros módulos van a importar ese código; en un servicio que nadie importa es una carpeta de más.
  • Una dependencia externa cuando ahorra trabajo real: un driver de base de datos, el cliente de un servicio concreto. Para HTTP, JSON, logs estructurados (log/slog) o tests, la stdlib suele bastar, y cada require es código que tendrás que auditar y actualizar.
  • Alias de import solo para resolver un choque de nombres, no por gusto: quien lee busca gin.New, no el apodo que le pusiste.

Resumen #

Lo que te llevas

  • Un paquete = un directorio de ficheros .go con la misma declaración package.
  • Visibilidad: mayúscula inicial = exportado; minúscula inicial = privado al paquete. Sin public/private.
  • go.mod declara el módulo y sus dependencias directas; go.sum fija los checksums. Nunca editar go.sum a mano.
  • go get añade dependencias, como composer require; go mod tidy deja go.mod y go.sum en línea con los imports reales.
  • El directorio internal/ es código privado: la herramienta go impide importarlo desde fuera del árbol de su directorio padre.
