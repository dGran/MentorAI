Row Level Security: la seguridad vive en la base de datos

En Supabase el navegador consulta tus tablas directamente. Lo único que impide que un usuario lea las notas de otro es una regla dentro de Postgres. Esta es la lección más importante del curso, porque un error aquí no se nota en las pruebas, se nota cuando alguien abre las herramientas de desarrollo.

En la Data API viste que cada petición se convierte en SQL ejecutado con el rol del usuario. Aquí entramos en qué hace Postgres con ese rol: cómo sabe quién eres, qué filas te deja tocar y cómo escribir reglas que sean a la vez correctas y rápidas.

De la petición al usuario: roles y claims #

Cada petición que llega a la Data API se ejecuta con uno de estos roles de Postgres:

RolCuándo¿RLS se aplica?
anonClave publicable y nadie ha iniciado sesiónSí
authenticatedClave publicable más el token de un usuario con sesiónSí
service_roleClave secretaNo: tiene el atributo BYPASSRLS
postgresConexión directa, SQL Editor, migracionesNo: es el dueño de las tablas

Antes de ejecutar tu consulta, PostgREST cambia al rol que toca y deja el contenido del token (sus claims) disponible para la transacción. Dos funciones lo leen:

  • auth.uid() devuelve el id del usuario (el claim sub), o null si no hay sesión.
  • auth.jwt() devuelve el token entero como jsonb: email, rol, app_metadata, nivel de autenticación…

Esto es lo que hace funcionar el modelo: las políticas pueden preguntar quién está consultando, y el token está firmado por Auth, así que el cliente no puede inventárselo.

Activar RLS: cerrado por defecto #

sql · cerrar la tabla 
alter table public.notes enable row level security;

Con RLS activado y ninguna política, la tabla devuelve cero filas a anon y authenticated y rechaza toda escritura. A partir de ahí, cada política abre una puerta concreta. Las políticas son permisivas: si hay varias para la misma operación, basta con que una se cumpla (se combinan con or).

Una tabla sin RLS es una tabla pública

Si una tabla de un esquema expuesto no tiene RLS, cualquiera con tu clave publicable (que está en el código de tu web) puede leerla entera, modificarla y borrarla con un curl. No hace falta saltarse nada: es el comportamiento documentado. El Security Advisor lo marca como error; trátalo como tal.

Anatomía de una política: using y with check #

sql · la forma general 
create policy "nombre descriptivo"
on public.notes
for select            -- select | insert | update | delete | all
to authenticated      -- a qué roles aplica
using ( ... )         -- qué filas existentes puede ver o tocar
with check ( ... );   -- qué filas nuevas o modificadas se aceptan

Las dos cláusulas responden a preguntas distintas, y confundirlas es el error más caro de RLS:

Operaciónusing (filas que ya existen)with check (cómo quedan después)
selectQué filas puedes verNo aplica
insertNo aplicaQué filas puedes crear
updateQué filas puedes modificarCómo pueden quedar tras modificarlas
deleteQué filas puedes borrarNo aplica

Las cuatro políticas de las notas privadas:

sql · notas: cada uno las suyas 
create policy "Ver mis notas"
on public.notes for select to authenticated
using ((select auth.uid()) = user_id);

create policy "Crear mis notas"
on public.notes for insert to authenticated
with check ((select auth.uid()) = user_id);

create policy "Editar mis notas"
on public.notes for update to authenticated
using ((select auth.uid()) = user_id)
with check ((select auth.uid()) = user_id);

create policy "Borrar mis notas"
on public.notes for delete to authenticated
using ((select auth.uid()) = user_id);

Si omites with check en un update, Postgres reutiliza la expresión de using. Escribirla explícita deja clara la intención, y obliga a pensar en lo que de verdad importa: cómo puede quedar la fila, que es donde se esconden los agujeros.

Un detalle de lo anterior que no es estético: (select auth.uid()) entre paréntesis con select. Lo explica la sección de rendimiento.

Compartir: políticas que miran otras tablas #

La app de notas permite compartir una nota con otra persona:

sql · tabla de comparticiones 
create table public.note_shares (
  note_id bigint not null references public.notes (id) on delete cascade,
  shared_with uuid not null references auth.users (id) on delete cascade,
  can_edit boolean not null default false,
  primary key (note_id, shared_with)
);

alter table public.note_shares enable row level security;

La política natural de lectura de notas sería «es mía o está compartida conmigo»:

sql · ver notas compartidas conmigo 
create policy "Ver notas compartidas conmigo"
on public.notes for select to authenticated
using (
  id in (
    select note_id from public.note_shares
    where shared_with = (select auth.uid())
  )
);

Y aquí aparece un clásico. Si la política de note_shares dice a su vez «puedes ver una compartición si eres el dueño de la nota» (consultando notes), cada tabla evalúa la política de la otra, que evalúa la de la primera… y Postgres corta con **infinite recursion detected in policy**.

La salida es una función security definer que consulta la tabla sin pasar por RLS, en un esquema que la API no expone:

sql · romper la recursión con una función privada 
create schema if not exists private;

create function private.owns_note(target_note_id bigint)
returns boolean
language sql
security definer
stable
set search_path = ''
as $$
  select exists (
    select 1 from public.notes
    where id = target_note_id and user_id = (select auth.uid())
  );
$$;

create policy "El dueño gestiona las comparticiones"
on public.note_shares for all to authenticated
using ((select private.owns_note(note_id)))
with check ((select private.owns_note(note_id)));

create policy "Veo lo que han compartido conmigo"
on public.note_shares for select to authenticated
using (shared_with = (select auth.uid()));

El editor invitado que se queda la nota

Supón una política que deja editar a quien tiene la nota compartida con can_edit: using (id in (select note_id from public.note_shares where shared_with = (select auth.uid()) and can_edit)), sin with check. Postgres reutiliza using como comprobación final: la fila editada tiene que seguir compartida con el editor… y lo sigue estando aunque cambie user_id por su propio id. El invitado acaba de quedarse la nota. RLS no ve el valor anterior de la fila, así que no puede expresar «esta columna no cambia». Eso se resuelve con permisos por columna, debajo.

sql · solo se pueden actualizar estas columnas 
revoke update on public.notes from authenticated;
grant update (title, body, notebook_id) on public.notes to authenticated;

La segunda política no es decorativa: la política de notas consulta note_shares con el rol del usuario, así que quien recibe una nota tiene que poder ver su propia fila de compartición. Sin ella, la subconsulta le devolvería vacío y la nota compartida seguiría invisible.

La función corre con los permisos de su dueño (se salta RLS al leer notes), pero solo responde una pregunta de sí o no sobre el usuario actual. Al estar en private, nadie puede llamarla desde la API. El mismo patrón sirve para apps multiempresa: private.is_member(org_id) sobre una tabla de membresías, y cada tabla de la organización usa esa función en sus políticas.

Políticas rápidas #

Una política es un where extra en cada consulta. Mal escrita, multiplica el coste de todo. Cuatro reglas cubren casi todos los casos:

ReglaPor qué
Envuelve las funciones en (select ...): (select auth.uid()) = user_idSin el select, Postgres puede llamar a la función una vez por fila. Con él, la evalúa una vez por consulta y reutiliza el resultado
Indexa las columnas de las políticas: create index on notes (user_id)La política filtra por user_id en cada consulta; sin índice, cada lectura recorre la tabla entera
Pon siempre to authenticated (o el rol que toque)Una política sin rol se evalúa también para anon, que nunca la va a cumplir
Prefiere columna in (select ...) a subconsultas correlacionadas con joinsLa forma in deja al planificador resolver la subconsulta una vez

Además, filtra también en la consulta aunque la política ya lo haga: .eq("user_id", userId) le da al planificador una condición que puede usar con el índice desde el principio, en vez de descubrir el filtro dentro de la política.

Mídelo

El Performance Advisor del panel detecta las políticas que llaman a auth.uid() sin envolver y las que duplican trabajo. Y explain analyze en el SQL Editor, ejecutado con el rol authenticated, enseña el coste real que añade cada política.

Probar las políticas #

Una política que no se prueba es una suposición. Tres formas, de más rápida a más seria:

  • El selector de rol del SQL Editor. Permite ejecutar una consulta como anon o como un usuario concreto. Ideal para comprobar a mano.
  • Simular el rol en SQL, dentro de una transacción que se deshace:
sql · ver lo que vería un usuario concreto 
begin;
set local role authenticated;
set local request.jwt.claims = '{"sub": "1b4e28ba-2fa1-11d2-883f-0016d3cca427", "role": "authenticated"}';

select id, title from public.notes;

rollback;
  • Tests automáticos con pgTAP. La CLI ejecuta los ficheros de supabase/tests/ con supabase test db. Un test de seguridad crea dos usuarios, inserta una nota de cada uno y comprueba que cada uno solo ve la suya. Es la única forma de que una migración futura no abra un agujero sin que nadie se entere.

Errores que abren agujeros #

  • **Usar user_metadata en una política.** El usuario puede modificar su propio user_metadata desde el cliente. Si una política dice «es admin si user_metadata.role = 'admin'», cualquiera se hace admin. Los datos de autorización van en app_metadata (solo se cambia desde el servidor) o en una tabla propia.
  • **using (true) en update o delete «para probar».** Se queda. Y abre la tabla a cualquier usuario autenticado.
  • **Vistas sin security_invoker** y funciones security definer en esquemas expuestos: las dos se saltan RLS.
  • Confiar en filtrar en el frontend. Ocultar un botón no es seguridad: la petición se puede hacer igual a mano.
  • **Políticas sin to.** Aparte del rendimiento, hacen que una regla pensada para usuarios con sesión se evalúe también para anónimos.

La capa de autorización de cualquier backend sigue estas mismas ideas; Autorización las cuenta fuera de Supabase, y te servirá para reconocer qué parte de tu lógica cabe en una política y cuál no.

Cuándo aplicarlo #

RLS es obligatorio cuando…

  • La tabla está en un esquema expuesto por la Data API (siempre que uses Supabase desde un cliente)
  • Varios usuarios comparten la base de datos y cada uno solo debe ver lo suyo
  • Una app multiempresa separa los datos por organización

RLS no es el sitio para…

  • Reglas de negocio complejas («solo se puede cancelar si el pedido no ha salido y faltan 24 h»): mejor una función con rpc o una Edge Function
  • Validar formatos: para eso están los check y los tipos de la tabla
  • Limitar cuántas veces se puede hacer algo por minuto: es rate limiting, no permisos

Resumen #

Lo que te llevas

  • Cada petición entra como anon, authenticated o service_role; solo este último se salta RLS, y auth.uid() y auth.jwt() dan acceso al token firmado.
  • Activar RLS cierra la tabla; cada política permisiva abre una puerta, y varias se combinan con or.
  • using decide qué filas existentes se ven o tocan; with check decide cómo pueden quedar. Un update necesita las dos.
  • La recursión entre políticas se rompe con funciones security definer en un esquema privado.
  • Rendimiento: (select auth.uid()), índice en las columnas de la política, to authenticated y el filtro repetido en la consulta.
  • Prueba las políticas con roles simulados y con pgTAP; nunca autorices con user_metadata.
