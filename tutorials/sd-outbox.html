El patrón outbox: guardar y publicar sin perder eventos

Guardar en la base de datos y publicar un evento son dos escrituras a dos sistemas. No hay forma de hacerlas atómicas, salvo dejando de ser dos sistemas.

Guardar en la base de datos y publicar un evento son dos escrituras a dos sistemas distintos. No hay forma de hacerlas atómicas… salvo dejando de ser dos sistemas. Esa es toda la idea del outbox, y es probablemente el patrón con mejor relación entre lo que cuesta y lo que resuelve de todo el curso.

El problema de la doble escritura #

Este código parece correcto y está mal. Da igual en qué orden pongas las dos líneas:

php · el bug que no se ve en local 
<?php

$this->pedidos->guardar($pedido);
$this->broker->publicar(new PedidoConfirmado($pedido->id()));

Si guardas primero

  • El broker está caído al publicar
  • El pedido existe, el evento no
  • Nadie manda el correo. Nunca.
  • Y no te enteras: la petición fue un 200

Si publicas primero

  • Falla el INSERT o revienta la transacción
  • El evento salió, el pedido no existe
  • Se manda un correo de un pedido fantasma
  • Y el consumidor peta al buscarlo en la BD

No es un caso raro: basta un despliegue del broker, un pico de red o que el proceso se muera entre las dos líneas. En local nunca pasa, y en producción pasa un puñado de veces al día en cuanto tienes volumen.

Meter el publicar dentro de la transacción no arregla nada

Es el primer intento de todo el mundo. Pero la transacción solo cubre la base de datos: si el publicar tiene éxito y el COMMIT falla después, el evento ya salió y no hay rollback que lo recoja. Encima ahora mantienes la transacción abierta durante una llamada de red, que es su propio problema.

La idea: una escritura, no dos #

Si el problema es escribir en dos sistemas, escribe en uno. El evento se guarda como una fila más en tu base de datos, en la misma transacción que el pedido. Ahí la atomicidad ya la tienes gratis: o se guardan los dos o ninguno. Después, un proceso aparte lee esa tabla y publica.

1 Una transacciónINSERT en pedidos + INSERT en outbox. Atómico.
2 Un proceso lee la outboxBusca filas sin publicar
3 Publica y marca la filaSi el broker está caído, lo intenta luego

El broker puede estar caído una hora: los eventos esperan en la tabla y salen al volver.

La tabla y el productor #

sql · outbox.sql 
CREATE TABLE outbox (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tipo VARCHAR(120) NOT NULL,
    clave_particion VARCHAR(64) NOT NULL,
    cuerpo JSON NOT NULL,
    creado_en DATETIME(6) NOT NULL,
    publicado_en DATETIME(6) NULL,
    INDEX idx_pendientes (publicado_en, id)
);

El id autoincremental da el orden de publicación. La clave_particion es lo que después mantiene el orden por entidad en el broker —el identificador del pedido, típicamente—. Y el índice sobre publicado_en es lo que hace que la consulta de pendientes no degrade cuando la tabla crezca.

php · ConfirmarPedido.php 
<?php

declare(strict_types=1);

final class ConfirmarPedido
{
    public function __invoke(Carrito $carrito): Pedido
    {
        return $this->conexion->transactional(function () use ($carrito): Pedido {
            $pedido = $this->pedidos->crear($carrito);

            $this->outbox->encolar(new PedidoConfirmado($pedido->id()));

            return $pedido;
        });
    }
}

El caso de uso ya no conoce al broker. Solo escribe en su propia base de datos, y la transacción garantiza que el pedido y su evento comparten destino.

El publicador y sus dos trampas #

php · PublicadorOutbox.php 
<?php

declare(strict_types=1);

final class PublicadorOutbox
{
    private const LOTE = 100;

    public function publicarPendientes(): int
    {
        $pendientes = $this->conexion->fetchAllAssociative(
            'SELECT * FROM outbox WHERE publicado_en IS NULL
             ORDER BY id LIMIT ' . self::LOTE . ' FOR UPDATE SKIP LOCKED'
        );

        foreach ($pendientes as $fila) {
            $this->broker->publicar($fila['tipo'], $fila['clave_particion'], $fila['cuerpo']);

            $this->conexion->update('outbox', ['publicado_en' => $this->ahora()], [
                'id' => $fila['id'],
            ]);
        }

        return count($pendientes);
    }
}

Trampa 1: dos publicadores a la vez

Si corres dos réplicas del publicador sin bloqueo, las dos leen las mismas filas y publican todo por duplicado. FOR UPDATE SKIP LOCKED hace que cada proceso se lleve un lote distinto sin esperar al otro. Es la forma barata; la otra es que solo haya una instancia, con la fragilidad que eso implica.

Trampa 2: el outbox es at-least-once, no exactly-once

Si el publicador muere entre publicar y marcar la fila, el evento sale dos veces. Es inevitable y es aceptable: el outbox garantiza que no se pierde ningún evento, y de los duplicados se encarga el consumidor idempotente de la lección anterior. Las dos piezas se necesitan.

Queda un detalle operativo: la tabla crece para siempre si nadie la limpia. Un borrado periódico de las filas publicadas hace semanas es suficiente, y conviene tener una métrica de la fila pendiente más antigua: si empieza a subir, el publicador está parado y los eventos se están quedando dentro sin que nadie lo note.

La variante sin publicador: CDC

En vez de consultar la tabla, puedes leer el registro de replicación de la base de datos con una herramienta de change data capture (Debezium es la habitual) y publicar desde ahí. Te ahorras el proceso y el polling, a cambio de una pieza de infraestructura más y de acoplarte al motor de base de datos. Con volúmenes normales, el publicador con polling sobra.

Cuándo aplicarlo #

Monta un outbox cuando…

  • Guardas algo y publicas un evento sobre ello en la misma operación
  • Perder ese evento tiene consecuencias: un cobro sin avisar, un envío que no sale
  • El consumidor es otro equipo o servicio y no puede consultarte «por si acaso»
  • Ya tienes base de datos transaccional: el coste es una tabla y un cron

No hace falta cuando…

  • El evento es informativo y perderlo no cambia nada: una métrica, un log
  • El consumidor puede reconstruir el estado consultando tu API
  • Emisor y consumidor comparten la misma base de datos y transacción

Resumen #

Lo que te llevas

  • Guardar y publicar son dos escrituras a dos sistemas: en cualquiera de los dos órdenes hay una ventana donde uno sale y el otro no.
  • Meter el publicar dentro de la transacción no lo arregla: si el COMMIT falla después, el evento ya salió y no hay rollback que valga.
  • El outbox convierte dos escrituras en una: el evento es una fila más de tu base de datos, y un proceso aparte lo publica.
  • Con varias réplicas del publicador hace falta FOR UPDATE SKIP LOCKED, o publicarás todo por duplicado.
  • El outbox garantiza que ningún evento se pierde, no que no se repita. Necesita al consumidor idempotente al otro lado.
