Tu primer proyecto: el panel, las claves y la primera consulta

En diez minutos tienes una base de datos en la nube con API, login y ficheros. Lo que cuesta no es crearla: es elegir bien las dos o tres cosas que luego no se cambian, y entender qué clave va en cada sitio antes de publicar ninguna.

En la lección anterior viste que Supabase es Postgres con servicios alrededor. Ahora lo tocas: creas el proyecto, das una vuelta por el panel, creas la primera tabla de la app de notas y la consultas desde fuera.

Crear el proyecto: lo que no se cambia después #

Te registras en supabase.com (con GitHub o con email) y creas una organización, que es la unidad de facturación: el plan se paga por organización y dentro caben varios proyectos. Al crear un proyecto te pide cuatro cosas:

CampoQué esLo que importa
NombreSolo una etiquetaSe cambia cuando quieras
Contraseña de la base de datosLa del usuario postgresGuárdala en tu gestor de contraseñas: la necesitarás para conectar con psql, PDO o la CLI. Se puede resetear, pero rompe lo que la use
RegiónDónde vive físicamente la base de datosNo se cambia sin migrar el proyecto. Elige la más cercana a tus usuarios (o a tu servidor, si lo hay)
PlanGratuito o de pagoSe cambia cuando quieras

Tras un par de minutos de aprovisionamiento, el proyecto tiene un identificador corto, el project ref (algo como abcdefghijklmnop), que aparece en todas las URLs: https://abcdefghijklmnop.supabase.co.

Región y latencia

Cada consulta viaja de tu usuario a la región de la base de datos y vuelve. Con la base de datos en Fráncfort y usuarios en España son unos 30-40 ms por ida y vuelta; con la base de datos en Virginia, más de 100. Una pantalla que hace cinco consultas seguidas multiplica esa diferencia.

Un paseo por el panel (Studio) #

El panel tiene muchas secciones, pero en el día a día usarás estas:

SecciónPara qué
Table EditorVer y editar filas como en una hoja de cálculo. Cómodo para mirar; peligroso para cambiar el esquema en producción
SQL EditorEscribir y guardar consultas SQL. Puede ejecutar como otro rol para probar permisos
DatabaseEsquemas, tablas, funciones, triggers, extensiones, índices, roles y backups
AuthenticationUsuarios, proveedores de login, plantillas de email, URLs de redirección y hooks
StorageBuckets y ficheros, con sus políticas
Edge FunctionsLas funciones desplegadas, sus logs y sus secretos
IntegrationsCron, Queues, Vault, Wrappers, GraphQL y webhooks de base de datos
AdvisorsAvisos automáticos de seguridad y rendimiento: tablas sin RLS, índices que faltan…
LogsLas peticiones a cada servicio y los logs de Postgres
Project SettingsClaves de API, cadenas de conexión, dominios y facturación

El Table Editor no deja rastro

Cada cambio de esquema hecho con clics (una columna nueva, un tipo cambiado) es un cambio que no está en ningún fichero. Funciona para trastear, pero en cuanto haya un segundo entorno o una segunda persona, el esquema tiene que vivir en migraciones versionadas. Es justo lo que cuenta la lección de la CLI.

La primera tabla #

Abre el SQL Editor y crea la tabla de notas. Escribirla en SQL en vez de con clics tiene una ventaja inmediata: este mismo texto será tu primera migración.

sql · notas.sql 
create table public.notes (
  id bigint generated always as identity primary key,
  user_id uuid not null default auth.uid() references auth.users (id) on delete cascade,
  title text not null check (char_length(title) between 1 and 200),
  body text not null default '',
  created_at timestamptz not null default now()
);

alter table public.notes enable row level security;

create policy "Cada usuario ve sus notas"
on public.notes for select
to authenticated
using ((select auth.uid()) = user_id);

Fíjate en tres detalles que irán apareciendo durante todo el curso:

  • auth.users es la tabla donde Auth guarda los usuarios. Tu tabla la referencia con una clave foránea, así que al borrar un usuario se borran sus notas.
  • auth.uid() es una función que devuelve el id del usuario que hace la petición, sacado de su token. Como default, rellena el dueño de la nota sin que el cliente lo mande.
  • enable row level security cierra la tabla y la política abre solo lo que dice. RLS a fondo lo explica entero; por ahora basta con saber que sin esas líneas la tabla quedaría abierta.

Las claves: cuál va en cada sitio #

En Project Settings → API Keys encuentras la URL del proyecto y las claves. Supabase está en plena transición de un sistema de claves a otro, así que verás dos familias:

ClaveFormatoRol en PostgresDónde puede ir
Publicablesb_publishable_...anon sin sesión, authenticated con sesiónNavegador, app móvil, código público. Está pensada para verse
Secretasb_secret_...service_role, que se salta RLSSolo en servidores, Edge Functions y tareas programadas
anon (antigua)JWT larguísimoIgual que la publicableIgual que la publicable
service_role (antigua)JWT larguísimoIgual que la secretaIgual que la secreta

La regla que no se rompe nunca: la clave secreta no sale de un servidor. Quien la tenga puede leer y borrar cualquier fila de cualquier tabla, porque el rol service_role ignora todas las políticas. Supabase incluso rechaza con un 401 las peticiones con clave secreta que vienen de un navegador, pero eso no protege una clave filtrada: con curl funciona igual. Si se filtra, se rota.

Por qué hay claves nuevas

Las antiguas anon y service_role eran JWT firmados con el mismo secreto que los tokens de usuario y con una caducidad de años: rotarlas obligaba a invalidar todas las sesiones de golpe. Las nuevas son claves opacas e independientes: se pueden crear varias secretas (una por servicio), revocar una sola y rotar sin cortar a nadie. Supabase anunció la retirada de las antiguas para finales de 2026: si tu proyecto aún las usa, migra a las nuevas y desactiva las antiguas en el panel.

La clave publicable no es un secreto ni un mecanismo de seguridad. Identifica tu proyecto y pone a la petición el rol anon. Lo que protege tus datos es RLS, no esconder la clave.

La primera consulta desde fuera #

Desde una app JavaScript se usa la librería oficial @supabase/supabase-js:

bash · terminal 
npm install @supabase/supabase-js
ts · supabase.ts 
import { createClient } from "@supabase/supabase-js";

export const supabase = createClient(
  "https://abcdefghijklmnop.supabase.co",
  "sb_publishable_xxxxxxxxxxxxxxxx",
);

const { data, error } = await supabase
  .from("notes")
  .select("id, title, created_at")
  .order("created_at", { ascending: false });

if (error) throw error;
console.log(data);

La librería no lanza excepciones: devuelve siempre { data, error }, y comprobar error es tu trabajo. Por debajo no hay magia, es una petición HTTP a la Data API que puedes repetir con curl:

bash · la misma consulta con curl 
curl "https://abcdefghijklmnop.supabase.co/rest/v1/notes?select=id,title,created_at&order=created_at.desc" \
  -H "apikey: sb_publishable_xxxxxxxxxxxxxxxx"

Un array vacío no es un error

Si ejecutas esa consulta sin haber iniciado sesión, la respuesta es [], no un error de permisos. La petición entra como anon, la política solo deja ver filas a authenticated, así que Postgres filtra todas. Es el comportamiento correcto de RLS: una fila que no puedes ver, para ti, no existe. Y es también la causa número uno de «Supabase no me devuelve nada».

Desde otros lenguajes: HTTP o Postgres directo #

No necesitas una librería oficial. Hay dos caminos, y conviene saber qué implica cada uno:

Por la Data API (HTTP)

  • Cualquier lenguaje con un cliente HTTP
  • Mandas la clave publicable y, si hay usuario, su token
  • RLS se aplica: ves lo que ese usuario puede ver
  • Lo natural para apps y para un backend que actúa en nombre del usuario

Por conexión directa a Postgres

  • PDO, psql, un ORM, una herramienta de BI
  • Te conectas con un usuario de base de datos (por defecto postgres)
  • RLS no te filtra: postgres es el dueño de las tablas
  • Lo natural para migraciones, tareas internas y backends de confianza

La cadena de conexión está en el botón Connect del panel. Para un script PHP que corre en un servidor, la conexión pasa por el pooler de conexiones (lo explica la lección de producción):

php · notas.php 
<?php

declare(strict_types=1);

$pdo = new PDO(
    'pgsql:host=aws-0-eu-central-1.pooler.supabase.com;port=5432;dbname=postgres;sslmode=require',
    'postgres.abcdefghijklmnop',
    getenv('SUPABASE_DB_PASSWORD'),
    [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION],
);

$notes = $pdo->query('select id, title from public.notes order by created_at desc limit 10')->fetchAll();

Fíjate en el usuario postgres.abcdefghijklmnop: el pooler es compartido entre muchos proyectos y usa el sufijo para saber a qué base de datos llevarte.

Errores típicos del primer día #

  • Poner la clave secreta en el frontend «para que funcione». Funciona porque se salta RLS, que es exactamente el problema. La solución es escribir la política que falta.
  • Crear tablas sin RLS. El panel avisa en Advisors, y el aviso no bloquea nada: la tabla queda accesible para cualquiera con la clave publicable.
  • No guardar la contraseña de la base de datos. Se puede resetear, pero todo lo que conectaba con la anterior deja de funcionar.
  • Elegir la región por defecto sin mirar. Moverla después exige migrar el proyecto.
  • Olvidar que el plan gratuito se pausa. Un proyecto sin actividad durante una semana se pausa. Para una demo o un proyecto de clase está bien; para algo que usan personas, no.

Cuándo aplicarlo #

Con lo de esta lección te basta para…

  • Prototipar una idea con datos reales y login en una tarde
  • Probar cómo responde la Data API a tus consultas
  • Conectar una herramienta de BI o un script de análisis a la base de datos

Todavía no es suficiente si…

  • Hay más de un entorno (local, pruebas, producción): necesitas migraciones
  • Varias personas tocan el esquema: los clics en el panel no se revisan en un PR
  • Vas a publicar la app: antes, RLS en todas las tablas expuestas

Resumen #

Lo que te llevas

  • La región y la contraseña de la base de datos se eligen con cuidado al crear el proyecto: la primera no se cambia y la segunda la usarán tus conexiones directas.
  • El SQL Editor es mejor punto de partida que el Table Editor: el SQL se convierte en tu primera migración.
  • La clave publicable (sb_publishable_) va en el cliente y entra con el rol anon o authenticated; la secreta (sb_secret_) se salta RLS y solo vive en servidores.
  • Las claves antiguas anon y service_role se retiran: los proyectos nuevos usan las nuevas.
  • supabase-js devuelve { data, error } sin lanzar excepciones, y un [] suele ser RLS filtrando, no un fallo.
  • Por la Data API se aplica RLS; por conexión directa como postgres, no.
