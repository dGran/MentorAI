Queues: trabajo en segundo plano con pgmq

Hay trabajo que no debe hacerse mientras el usuario espera ni puede perderse si algo falla: mandar emails, procesar un PDF, generar embeddings. Lo que necesitas es una cola. Supabase la mete en tu propia base de datos, con la ventaja que eso trae: encolar puede ir en la misma transacción que el cambio que lo provoca.

En funciones y triggers viste que un webhook con pg_net no reintenta, y en Cron que una tarea periódica no sabe qué trabajo hay pendiente. Una cola une las dos cosas: el trabajo se apunta en cuanto aparece y un consumidor lo procesa con reintentos.

Por qué una cola #

Cuando alguien comparte una nota hay que mandar un email al invitado. Hacerlo dentro de la petición tiene dos problemas: el usuario espera al proveedor de email, y si el proveedor falla en ese momento, el email se pierde. Una cola separa apuntar el trabajo de hacerlo:

1 Productorla transacción que comparte la nota encola { note_id, email }
2 Colael mensaje espera, guardado en una tabla
3 Consumidorlee un lote, lo oculta un tiempo y manda los emails
4 Archivoel mensaje procesado queda como historial

El productor no espera al trabajo y el trabajo no se pierde si el consumidor falla: el mensaje vuelve a la cola.

Si el concepto de cola, productor y consumidor es nuevo para ti, Colas y tópicos lo cuenta en general; aquí vamos a la implementación de Supabase.

pgmq: una cola es una tabla #

Supabase Queues es la extensión **pgmq**. Cada cola es una tabla en el esquema pgmq (pgmq.q_emails para la cola emails) y cada mensaje, una fila con un jsonb. Se crean desde Integrations → Queues o con SQL:

sql · crear la cola 
select pgmq.create('emails');

La operación que lo hace funcionar es la lectura con tiempo de invisibilidad (visibility timeout). Leer no borra el mensaje: lo esconde durante unos segundos. Si el consumidor termina, lo archiva o lo borra; si se cae a mitad, el tiempo vence y el mensaje vuelve a ser visible para otro consumidor.

sql · el ciclo de un mensaje 
select pgmq.send('emails', '{"note_id": 7, "to": "luis@ejemplo.com"}'::jsonb);

select msg_id, read_ct, message from pgmq.read('emails', 30, 10);

select pgmq.archive('emails', 42);
FunciónQué hace
pgmq.send(cola, mensaje, retraso)Encola un mensaje; con retraso, no será visible hasta pasados esos segundos
pgmq.send_batch(cola, mensajes)Encola varios de una vez
pgmq.read(cola, vt, n)Lee hasta n mensajes y los esconde vt segundos
pgmq.archive(cola, msg_id)Lo mueve a la tabla de archivo (pgmq.a_emails): procesado, con historial
pgmq.delete(cola, msg_id)Lo borra sin dejar rastro
pgmq.pop(cola)Lee y borra a la vez: si el consumidor falla, el mensaje se pierde
pgmq.metrics(cola)Longitud de la cola y edad del mensaje más antiguo

Cada lectura incrementa read_ct, el número de veces que se ha entregado el mensaje. Es la base para los reintentos.

Al menos una vez: consumidores idempotentes #

Con tiempo de invisibilidad, la garantía es al menos una vez: un mensaje nunca se pierde mientras no se archive, pero puede procesarse dos veces. Basta con que el consumidor mande el email y se caiga antes de archivar: el mensaje reaparece y el email sale otra vez.

No hay configuración que lo evite; se diseña el consumidor para que repetir no haga daño. Para el email, guardando en una tabla que ese envío ya se hizo (con una clave única por mensaje) y comprobándolo antes de mandar. Es la misma técnica de Idempotencia.

Y elige bien el tiempo de invisibilidad: tiene que ser mayor que lo que tarda en procesarse un lote. Si es menor, el mensaje reaparece mientras todavía se está procesando y otro consumidor lo coge.

Mensajes envenenados

Un mensaje con datos que siempre fallan (un email mal formado) volvería a la cola para siempre. La defensa es mirar read_ct: pasado un número de intentos, el consumidor lo manda a una cola aparte de mensajes muertos y lo archiva de la principal, para revisarlo a mano.

ts · en el consumidor: tras 5 intentos, a la cola de muertos 
if (message.read_ct > 5) {
  await queue.rpc("send", { queue_name: "emails_dead", message: message.message });
  await queue.rpc("archive", { queue_name: "emails", message_id: message.msg_id });
  continue;
}

La ventaja de vivir en Postgres: encolar en la transacción #

Con un broker externo (RabbitMQ, SQS) hay un problema clásico: guardas la compartición en la base de datos y luego publicas el mensaje en el broker. Si el proceso se cae entre las dos cosas, tienes la compartición sin email. O al revés: el mensaje sale y la transacción hace rollback.

Con pgmq, encolar es un insert más en la misma transacción. O se guardan los dos o ninguno. Un trigger lo hace automático:

sql · cada compartición encola su email, en la misma transacción 
create function private.enqueue_share_email()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
begin
  perform pgmq.send(
    'emails',
    jsonb_build_object('note_id', new.note_id, 'shared_with', new.shared_with)
  );

  return new;
end;
$$;

create trigger note_shares_enqueue_email
after insert on public.note_shares
for each row execute function private.enqueue_share_email();

Es el patrón outbox resuelto sin tabla extra: Outbox explica por qué la escritura doble es un problema y por qué esta es la solución.

El consumidor: Cron despierta a una Edge Function #

Falta quien procese la cola. El montaje habitual en Supabase combina tres piezas que ya conoces:

1 Cron, cada 10 segundosnet.http_post a la función con la clave secreta (como en Cron)
2 Edge Function workerlee un lote con read, procesa cada mensaje
3 Bien: archivemal: no hace nada y el mensaje reaparece al vencer el tiempo

Cada pieza hace una sola cosa: Cron marca el ritmo, la función trabaja y la cola guarda el estado.

Para que una Edge Function (o cualquier cliente) hable con la cola por la Data API, Supabase expone un esquema envoltorio, **pgmq_public**, con send, send_batch, read, pop, archive y delete. Se activa en los ajustes de Queues, y el acceso a cada cola se controla con políticas RLS sobre su tabla, como cualquier otra.

ts · supabase/functions/email-worker/index.ts (resumido) 
import { withSupabase } from "npm:@supabase/server@1";

export default {
  fetch: withSupabase({ auth: "secret" }, async (_req, ctx) => {
    const queue = ctx.supabaseAdmin.schema("pgmq_public");
    const { data: messages } = await queue.rpc("read", {
      queue_name: "emails",
      sleep_seconds: 60,
      n: 20,
    });

    for (const message of messages ?? []) {
      const delivered = await sendShareEmail(message.message);

      if (!delivered) continue;

      await queue.rpc("archive", { queue_name: "emails", message_id: message.msg_id });
    }

    return Response.json({ processed: messages?.length ?? 0 });
  }),
};

Si un email falla, el mensaje no se archiva y vuelve a la cola a los 60 segundos: los reintentos salen solos. Con un n moderado, cada ejecución cabe holgada en los límites de una Edge Function.

Vigilar la cola #

Una cola sana se vacía. Las dos cifras que hay que mirar son la longitud y la edad del mensaje más antiguo:

sql · estado de la cola 
select queue_length, oldest_msg_age_sec, total_messages from pgmq.metrics('emails');

Si la edad del más antiguo crece sin parar, el consumidor no da abasto o está fallando siempre con algo. Una tarea Cron que consulte esto y avise cuando pase de un umbral vale más que cualquier panel que nadie mira.

Cuándo aplicarlo #

pgmq en Supabase encaja cuando…

  • El trabajo nace de cambios en tu base de datos y quieres encolarlo en la misma transacción
  • Hablamos de cientos o miles de mensajes por minuto, no de cientos de miles por segundo
  • No quieres operar otro sistema (RabbitMQ, SQS, Redis) solo para esto
  • Te basta con colas punto a punto con reintentos

Un broker dedicado cuando…

  • El volumen es tan alto que la cola competiría con tus consultas por la base de datos
  • Necesitas enrutado complejo, fan-out a muchos consumidores o tópicos
  • Varios sistemas que no son tu base de datos publican y consumen (RabbitMQ)

Resumen #

Lo que te llevas

  • Supabase Queues es pgmq: cada cola es una tabla y cada mensaje una fila jsonb.
  • read esconde los mensajes durante el tiempo de invisibilidad; si no se archivan, reaparecen. La garantía es al menos una vez.
  • Consumidores idempotentes, tiempo de invisibilidad mayor que el procesado y cola de mensajes muertos a partir de read_ct.
  • Encolar desde un trigger mete el mensaje en la misma transacción que el cambio: el patrón outbox sin infraestructura extra.
  • El montaje típico es Cron que despierta a una Edge Function worker que lee y archiva por pgmq_public.
  • Vigila la longitud y la edad del mensaje más antiguo con pgmq.metrics.
