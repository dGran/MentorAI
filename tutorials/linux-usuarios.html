Linux: usuarios y grupos

Linux es un sistema multiusuario desde sus cimientos. Entender cómo se almacenan los usuarios, cómo se organizan en grupos y cómo funciona sudo es fundamental para trabajar con seguridad en cualquier servidor.

En un servidor real conviven varios usuarios: el tuyo, www-data (el servidor web), mysql, redis… Cada proceso corre con la identidad de un usuario, y eso determina a qué ficheros puede acceder.

Modelo de usuarios y grupos#

Cada usuario tiene un UID (User ID) numérico. El kernel usa UIDs, no nombres: los nombres son solo una conveniencia humana. Lo mismo para los grupos (GID).

Rango UIDTipoEjemplos
0rootEl superusuario; tiene acceso sin restricciones
1 – 999Usuarios del sistemawww-data (UID 33), mysql (UID 105), redis
1000+Usuarios humanosdavid, alice, deploy

Un usuario pertenece a un grupo primario (el que aparece en el inodo como grupo propietario de los ficheros que crea) y puede pertenecer a grupos secundarios adicionales. Por ejemplo, para que tu usuario pueda ejecutar Docker, se añade al grupo docker.

Los ficheros del sistema#

bash · /etc/passwd
cat /etc/passwd
# Cada línea: nombre:x:UID:GID:comentario:home:shell
# david:x:1000:1000:David Gran:/home/david:/bin/bash
# www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
# mysql:x:105:108:MySQL Server:/nonexistent:/bin/false
#
# La 'x' en el campo contraseña significa que está en /etc/shadow
# /usr/sbin/nologin y /bin/false = no pueden iniciar sesión interactiva
bash · /etc/shadow y /etc/group
# /etc/shadow: contraseñas hasheadas (solo root puede leer)
# david:$6$salt$hash...:19500:0:99999:7:::
# campos: nombre:hash:ultimo_cambio:min:max:warn:inactivo:expira

# /etc/group: definición de grupos
cat /etc/group
# docker:x:999:david,alice     (grupo:x:GID:miembros)
# www-data:x:33:
# sudo:x:27:david

Por qué las contraseñas se movieron a /etc/shadow

/etc/passwd necesita ser legible por todos (muchos programas necesitan resolver UID a nombre). Pero guardar hashes de contraseñas donde todos pueden leer es un riesgo: un atacante con acceso local podría intentar romperlos por fuerza bruta. /etc/shadow es solo legible por root, así que los hashes están protegidos.

Gestionar usuarios#

bash · useradd, usermod, userdel
# Crear usuario
useradd -m -s /bin/bash david     # -m crea home, -s asigna shell
useradd -r -s /bin/false deploy   # -r usuario de sistema (UID < 1000), sin login

# Establecer contraseña
passwd david                      # interactivo
echo "david:contraseña" | chpasswd   # para scripts (cuidado con el historial)

# Modificar usuario
usermod -aG docker david          # -a append: añade al grupo docker (no reemplaza)
usermod -aG sudo david            # añade al grupo sudo
usermod -s /bin/bash david        # cambia la shell
usermod -d /nuevo/home david      # cambia el directorio home
usermod -l nuevo_nombre david     # renombra el usuario
usermod -L david                  # Lock: deshabilita la cuenta
usermod -U david                  # Unlock: la reactiva

# Borrar usuario
userdel david                     # borra el usuario (conserva el home)
userdel -r david                  # borra el usuario Y su directorio home

usermod -aG: sin la -a se pierden los grupos

usermod -G docker david (sin -a) reemplaza todos los grupos secundarios de david por solo docker. El usuario perdería sudo y cualquier otro grupo. Siempre -aG para añadir.

Gestionar grupos#

bash
groupadd developers              # crea el grupo
groupdel developers              # borra el grupo
gpasswd -a david developers      # añade david al grupo (alternativa a usermod -aG)
gpasswd -d david developers      # elimina david del grupo
groups david                     # grupos a los que pertenece david
getent group docker              # miembros del grupo docker

Identidad actual#

bash
whoami              # nombre del usuario actual
id                  # uid, gid y todos los grupos
id david            # ídem para otro usuario
who                 # usuarios conectados ahora mismo
w                   # igual que who pero con más detalle (carga, comando)
last                # historial de inicios de sesión
lastlog             # último login de cada usuario del sistema

sudo y sudoers#

sudo permite ejecutar comandos con los privilegios de otro usuario (por defecto, root) sin conocer su contraseña. La configuración vive en /etc/sudoers y en /etc/sudoers.d/.

bash · uso de sudo
sudo comando                    # ejecuta como root (pide TU contraseña)
sudo -u www-data comando        # ejecuta como www-data
sudo -i                         # abre shell de root (root interactivo)
sudo su -                       # alternativa para abrir shell de root
sudo !!                         # repite el último comando como root

# Ver qué puede hacer tu usuario con sudo:
sudo -l
bash · /etc/sudoers (editar con visudo, nunca a mano)
visudo                    # editor seguro de sudoers (valida sintaxis antes de guardar)

# Formato de una regla:
# usuario   HOST=(usuario_destino) COMANDOS
# %grupo    HOST=(usuario_destino) COMANDOS

# Ejemplos en /etc/sudoers:
david   ALL=(ALL:ALL) ALL            # david puede hacer todo con sudo
%sudo   ALL=(ALL:ALL) ALL            # todos los del grupo sudo también
deploy  ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx   # sin contraseña, solo ese comando

# Ficheros en /etc/sudoers.d/ (mejor práctica: un fichero por usuario/rol):
echo "deploy ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx" \
  | sudo tee /etc/sudoers.d/deploy
sudo chmod 440 /etc/sudoers.d/deploy

Nunca edites /etc/sudoers directamente con nano/vim

Un error de sintaxis en /etc/sudoers puede dejarte sin acceso a sudo y bloqueado fuera del sistema. Usa siempre visudo: valida la sintaxis antes de guardar. Si el fichero está corrupto y tienes sesión de root abierta, corrígelo antes de cerrarla.

bash · su: cambiar de usuario
su - david              # cambia al usuario david (pide la contraseña de david)
su -                    # cambia a root (pide contraseña de root)
su -c "comando" david   # ejecuta un comando como david sin abrir shell
exit                    # vuelve al usuario anterior

Cuándo aplicarlo#

Úsalo cuando…

  • Creas un daemon o servicio que no necesita login interactivo: crea un usuario de sistema (--system)
  • Un desarrollador necesita acceder al servidor: crea un usuario normal con contraseña
  • Ejecutas un comando puntual con privilegios elevados: usa sudo (queda registrado en el log de auditoría)

No lo uses cuando…

  • No ejecutes servicios con el usuario root: amplía innecesariamente la superficie de ataque
  • No uses su para comandos puntuales: pierdes la trazabilidad de auditoría que sudo proporciona

Resumen#

Lo que te llevas

  • El kernel trabaja con UIDs numéricos; /etc/passwd traduce a nombres. /etc/shadow guarda los hashes y solo root puede leerlo.
  • Los usuarios de sistema (UID < 1000) como www-data o mysql tienen /bin/false o /usr/sbin/nologin como shell: no pueden abrir sesión interactiva.
  • usermod -aG grupo usuario para añadir a un grupo. Sin -a se pierden los grupos actuales. Los cambios de grupo requieren nueva sesión para que surtan efecto.
  • id muestra tu UID, GID y grupos; groups usuario lista los grupos de cualquier usuario.
  • sudo permite ejecutar como root con tu contraseña. Edita /etc/sudoers siempre con visudo, nunca directamente: un error te puede bloquear el acceso.
