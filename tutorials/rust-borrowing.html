Borrowing y referencias

Las reglas del borrow checker: referencias compartidas (&T) y exclusivas (&mut T), slices, y cómo Rust previene errores de memoria en compilación.

&T: referencias compartidas

El problema con el ownership puro es que mover un valor cada vez que quieres usarlo es tedioso. Las referencias son la solución: permiten que otra parte del código acceda al dato sin tomar su propiedad.

fn calcular_longitud(s: &String) -> usize {
    s.len()
} // s es un préstamo: el caller sigue siendo el dueño

fn main() {
    let nombre = String::from("Rust");
    let longitud = calcular_longitud(&nombre); // prestamos &nombre
    println!("{} tiene {} caracteres", nombre, longitud); // nombre sigue siendo válido
}

El & en &nombre crea una referencia: un puntero al dato de nombre. calcular_longitud puede leer el String pero no poseerlo ni destruirlo. Cuando la función termina, solo se destruye la referencia, no el String.

Puedes tener múltiples referencias compartidas simultáneas. Esto es seguro porque solo leen, no modifican:

fn main() {
    let datos = vec![1, 2, 3, 4, 5];
    let referencia_a = &datos;
    let referencia_b = &datos;
    let referencia_c = &datos;

    println!("{:?} {:?} {:?}", referencia_a, referencia_b, referencia_c);
}

&mut T: referencias exclusivas

Para modificar un dato a través de una referencia, necesitas una referencia mutable &mut T. La restricción fundamental: solo puede existir una &mut T a la vez, y mientras existe ninguna &T.

fn agregar_sufijo(s: &mut String) {
    s.push_str(" - editado");
}

fn main() {
    let mut mensaje = String::from("hola");
    agregar_sufijo(&mut mensaje);
    println!("{}", mensaje); // hola - editado
}

¿Por qué esta restricción? El ejemplo que lo ilustra: si tienes una referencia compartida a un Vec y alguien inserta un elemento a través de una referencia mutable, el Vec puede reubicar su buffer en el heap. Tu referencia compartida ahora apunta a memoria liberada. Esto es exactamente el tipo de bug que explota en C++ y que Rust hace imposible.

fn main() {
    let mut v = vec![1, 2, 3];
    let primera = &v[0];         // referencia compartida
    v.push(4);                    // error: no puede haber &mut mientras existe &
    println!("{}", primera);      // si esto compilara, primera podría ser inválida
}
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable

Las reglas del borrow checker

El borrow checker impone estas reglas en cada punto del código:

  • Puedes tener cualquier número de referencias compartidas (&T) simultáneas.
  • O puedes tener exactamente una referencia mutable (&mut T).
  • Nunca puedes tener ambas al mismo tiempo.
  • Las referencias siempre deben ser válidas (el dato al que apuntan debe vivir al menos tanto como la referencia).
El modelo de lectores-escritores: las reglas del borrow checker son exactamente las de un RwLock: múltiples lectores O un escritor exclusivo, nunca los dos a la vez. Rust garantiza esto en compilación incluso en código single-thread, lo que elimina bugs de lógica que en otros lenguajes solo aparecen bajo concurrencia.

El borrow checker es sofisticado: analiza el tiempo de uso real de la referencia, no solo el scope léxico. En Rust moderno (NLL, Non-Lexical Lifetimes), una referencia termina cuando se usa por última vez, no cuando sale del bloque:

fn main() {
    let mut v = vec![1, 2, 3];
    let primera = &v[0];
    println!("{}", primera); // última vez que se usa primera
    // aquí primera ya no está activa
    v.push(4); // OK: no hay referencias activas
    println!("{:?}", v);
}

Slices: referencias a partes

Un slice es una referencia a una porción contigua de una colección. No copia los datos; apunta a un rango dentro de la colección original.

fn main() {
    let texto = String::from("hola mundo");
    let hola = &texto[0..4];   // &str apuntando a los primeros 4 bytes
    let mundo = &texto[5..10]; // &str apuntando a los siguientes 5 bytes

    println!("{} {}", hola, mundo);
}

fn primera_palabra(s: &str) -> &str {
    let bytes = s.as_bytes();

    for (i, &byte) in bytes.iter().enumerate() {
        if byte == b' ' {
            return &s[0..i];
        }
    }

    &s[..]
}

El tipo &str es un slice de String. El tipo &[T] es un slice de array o Vec:

fn suma(numeros: &[i32]) -> i32 {
    numeros.iter().sum()
}

fn main() {
    let arr = [1, 2, 3, 4, 5];
    let v = vec![10, 20, 30];

    println!("{}", suma(&arr));       // funciona con arrays
    println!("{}", suma(&v));         // funciona con Vec
    println!("{}", suma(&v[1..3]));   // funciona con slices parciales
}

Usar &[T] en lugar de &Vec<T> como parámetro es más flexible: acepta arrays, Vecs y cualquier slice.

Dangling references: imposibles en Rust

En C, puedes retornar un puntero a una variable local. Cuando la función termina, la variable se destruye pero el puntero sigue existiendo apuntando a memoria inválida. Este bug (dangling pointer) es la fuente de innumerables CVEs.

En Rust, el compilador lo hace imposible:

fn retornar_referencia() -> &String { // el compilador pide lifetime annotation
    let s = String::from("hola");
    &s
} // s se destruye aquí, la referencia quedaría colgando
error[E0106]: missing lifetime specifier
 --> src/main.rs:1:30
  |
1 | fn retornar_referencia() -> &String {
  |                              ^ expected named lifetime parameter

El compilador detecta que la referencia retornada apuntaría a datos que ya no existen. La solución es retornar el String (mover el ownership al caller) en lugar de una referencia:

fn crear_string() -> String {
    String::from("hola") // movemos el String, no retornamos una referencia
}

Resumen

  • &T presta el dato sin moverlo: el dueño sigue siéndolo. Múltiples &T simultáneas están permitidas (solo lectura).
  • &mut T presta el dato para modificarlo: solo puede existir una a la vez, y excluye cualquier &T simultánea.
  • Las reglas del borrow checker son el modelo lectores-escritores aplicado en compilación, incluso en código single-thread.
  • Los slices (&str, &[T]) son referencias a porciones de colecciones: no copian datos, apuntan a rangos dentro del original.
  • Las dangling references son imposibles: el compilador verifica que la referencia no sobreviva al dato al que apunta.
