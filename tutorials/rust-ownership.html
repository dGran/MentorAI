Ownership: el corazón de Rust

El sistema de propiedad que hace a Rust único: una sola dueña por valor, move semantics, Copy vs Clone, y por qué elimina bugs de memoria sin GC.

En PHP nunca te preguntas quién libera la memoria de un string: el contador de referencias y el recolector lo hacen por ti, a cambio de algo de coste en runtime. Rust no tiene recolector, así que necesita saber en compilación quién es el responsable de cada valor. Esa regla, el ownership, explica la mayoría de errores que verás en tus primeras semanas con el compilador, y entenderla es lo que hace que dejen de parecer arbitrarios.

Las tres reglas del ownership #

El sistema de ownership de Rust se rige por tres reglas verificadas en compilación. Memorizarlas no es suficiente; entender por qué existen es lo que hace que el compilador deje de ser el enemigo:

  1. Cada valor tiene exactamente un propietario: una variable es la dueña de su valor.
  2. Solo puede haber un propietario a la vez: no se puede tener dos variables que sean dueñas del mismo dato.
  3. Cuando el propietario sale de scope, el valor se destruye: se llama al destructor automáticamente.
rust 
fn main() {
    {
        let s = String::from("hola"); // s entra en scope, es la dueña
        println!("{}", s);
    } // s sale de scope → String se destruye, memoria liberada
      // aquí s ya no existe
}

PHP libera memoria cuando el contador de referencias del valor llega a cero (GC con reference counting). Go tiene un GC tricolor que corre en background. Rust libera la memoria exactamente cuando el propietario sale de scope, sin contador de referencias, sin GC, sin pausas.

Move semantics #

Cuando asignas un valor a otra variable, Rust mueve la propiedad. La variable original deja de ser válida:

rust 
fn main() {
    let s1 = String::from("hola");
    let s2 = s1; // s1 se mueve a s2

    println!("{}", s2); // OK
    println!("{}", s1); // error[E0382]: borrow of moved value: `s1`
}

¿Por qué? Porque si ambas variables fueran dueñas del mismo dato en el heap, cuando salieran de scope las dos intentarían liberar la misma memoria: double-free, un bug de seguridad grave en C y C++. Rust lo hace imposible en compilación.

Comparación con PHP: en PHP, $s2 = $s1 con un string copia el valor (copy-on-write internamente). En Rust, un String se mueve (la propiedad se transfiere). El resultado es el mismo en uso básico, pero el mecanismo garantiza que nunca hay dos dueños del mismo heap allocation.

El move aplica también al pasar valores a funciones. Esto es un patrón que sorprende a todos al principio:

rust 
fn consumir(s: String) {
    println!("{}", s);
} // s se destruye aquí

fn main() {
    let mi_string = String::from("hola");
    consumir(mi_string); // mi_string se mueve dentro de consumir
    // println!("{}", mi_string); // error: valor ya fue movido
}

El trait Copy #

Algunos tipos implementan el trait Copy: en lugar de mover el valor, se copia automáticamente. La variable original sigue siendo válida después de la asignación.

rust 
fn main() {
    let x = 5;
    let y = x; // x se copia, no se mueve

    println!("{} y {}", x, y); // ambos válidos
}

Los tipos que implementan Copy son aquellos que viven completamente en el stack y cuya copia es trivial:

  • Todos los tipos numéricos: i32, u64, f64, etc.
  • bool y char.
  • Referencias inmutables &T (copiar la referencia, no el dato apuntado).
  • Tuplas y arrays de tipos Copy: (i32, bool), [f64; 4].

Los tipos que no pueden ser Copy:

  • String: tiene datos en el heap, copiar requiere alocar nueva memoria.
  • Vec<T>: mismo motivo.
  • Cualquier tipo que implemente Drop: si necesita un destructor personalizado, no puede ser Copy.

Regla práctica: si un tipo tiene datos en el heap, no es Copy. Si todo vive en el stack con tamaño fijo, probablemente sí. #[derive(Copy, Clone)] funciona si todos los campos son Copy.

Clone: copia explícita #

Cuando necesitas una copia real de un valor que no es Copy, usas .clone(). El clone es explícito: Rust no lo hace nunca automáticamente, porque puede ser costoso (en tipos como String implica alocar nueva memoria en el heap).

rust 
fn main() {
    let s1 = String::from("hola");
    let s2 = s1.clone(); // copia profunda: nuevo String en el heap

    println!("{} y {}", s1, s2); // ambos válidos
}

Clone puede ser arbitrariamente costoso. Un Vec<String> con miles de elementos clona todos los Strings y todos los datos que contienen. Rust te hace escribir .clone() para que seas consciente de eso. Ojo: lo que hace clone() lo decide cada tipo. En String o Vec es una copia profunda; en Rc/Arc solo copia el puntero e incrementa el contador de referencias: es barato, y ambos siguen apuntando al mismo dato.

En PHP, $s2 = $s1 hace una copia con copy-on-write: barata hasta que alguien modifica. En Rust, si quieres una copia, la declaras explícita con .clone(); si solo necesitas leer el dato, usas una referencia prestada (lo veremos en el siguiente tutorial).

Errores típicos al llegar de PHP

Esperar que la asignación copie. En PHP, $b = $a deja las dos variables usables. En Rust, con un String o un Vec, let b = a; mueve el valor y usar a después no compila (E0382). El error señala la línea del move: ahí está la decisión que revisar.

Recorrer un Vec y perderlo. for item in pedidos consume el vector: tras el bucle ya no existe. Si solo vas a leer, recorre &pedidos.

Poner .clone() hasta que compile. Funciona, pero oculta un diseño que pedía una referencia y paga una copia profunda en cada llamada. Antes de clonar, pregúntate si la función necesita ser dueña del dato.

Suponer que tu struct es Copy porque sus campos lo son. Rust no lo deduce: hay que pedirlo con #[derive(Clone, Copy)]. Sin eso, asignarlo también lo mueve.

Ownership y funciones #

Pasar un valor a una función mueve el ownership (igual que la asignación). La función se convierte en la nueva dueña. Esto obliga a pensar en el ciclo de vida de cada dato:

rust 
fn dar_longitud(s: String) -> (String, usize) {
    let longitud = s.len();
    (s, longitud) // retornamos s para devolver el ownership al caller
}

fn main() {
    let nombre = String::from("Rust");
    let (nombre, longitud) = dar_longitud(nombre);
    println!("{} tiene {} caracteres", nombre, longitud);
}

Retornar el valor para recuperar el ownership es tedioso. Por eso existen las referencias (borrowing): puedes prestar un valor a una función sin moverlo. Pero ese es el tema del siguiente tutorial.

Lo que Rust evita con todo esto:

  • Use-after-free: usar un puntero a memoria ya liberada. Imposible: el compilador sabe cuándo un valor se destruye.
  • Double-free: liberar la misma memoria dos veces. Imposible: solo hay un dueño.
  • Dangling pointers: punteros a memoria que ya no pertenece al programa. Imposible: la memoria se libera cuando el dueño sale de scope.

Drop: destrucción determinista #

Cuando un valor sale de scope, Rust llama automáticamente al método drop si el tipo implementa el trait Drop. Esto es RAII (Resource Acquisition Is Initialization): el recurso se libera cuando el objeto que lo posee se destruye.

rust 
struct ConexionBD {
    url: String,
}

impl Drop for ConexionBD {
    fn drop(&mut self) {
        println!("Cerrando conexión a {}", self.url);
    }
}

fn main() {
    let conexion = ConexionBD { url: "postgres://localhost/db".to_string() };
    println!("Usando la conexión");
} // aquí se llama drop automáticamente
// Output: Usando la conexión
//         Cerrando conexión a postgres://localhost/db

En PHP el momento también suele ser predecible: __destruct se ejecuta en cuanto el contador de referencias del objeto llega a cero. La excepción son los ciclos (dos objetos que se apuntan entre sí), que esperan al recolector de ciclos o al final de la petición. El ownership de Rust no cuenta referencias: el compilador sabe en qué línea muere el dueño, y el drop ocurre exactamente ahí, sin pausas de GC.

Por qué importa en servidores: una conexión de base de datos se devuelve al pool exactamente cuando el scope termina, no cuando el GC decida pasar. Esto hace que el comportamiento bajo carga sea más predecible y los recursos se reutilicen antes.

Cuándo aplicarlo #

El ownership no se activa o desactiva: está en todo el código. Lo que eliges en cada firma es cómo llega el valor a una función, y esa elección es el diseño.

Toma el valor (move) cuando…

  • La función lo guarda o lo consume: un constructor que lo mete en un struct, un hilo al que se lo envías, un método que lo transforma en otra cosa
  • Quien llama ya no lo va a necesitar, y así evitas una copia
  • El tipo es pequeño y Copy (ids, coordenadas, enums sin datos): pasarlo por valor es lo natural

No lo tomes cuando…

  • La función solo lee: pide una referencia (&str, &[T]), lo verás en la siguiente lección
  • Te ves devolviendo el valor solo para «devolver la propiedad»: es la señal de que querías prestarlo
  • Haces .clone() para callar al compilador: clona solo cuando de verdad necesitas dos copias independientes

Sobre Copy: derívalo en tipos de valor pequeños que nunca vayan a tener datos en el heap. Si mañana el tipo necesita un String y tienes que quitarle Copy, cada sitio que lo usaba tras asignarlo dejará de compilar.

Resumen #

Lo que te llevas

  • Las tres reglas del ownership garantizan que no hay use-after-free, double-free ni dangling pointers: todo verificado por el compilador sin coste en runtime.
  • La asignación mueve el ownership: la variable original deja de ser válida. Esto evita que dos variables sean dueñas del mismo dato en el heap.
  • Los tipos Copy (enteros, bool, char, referencias inmutables) se copian automáticamente en lugar de moverse.
  • .clone() hace una copia explícita de tipos no-Copy: profunda en String/Vec, solo un incremento del contador en Rc/Arc. El compilador no lo hace automáticamente para que el coste sea visible.
  • La destrucción es determinista: el drop ocurre exactamente cuando el dueño sale de scope, sin GC. RAII libera los recursos al salir de scope, con dos excepciones que Rust considera seguras: mem::forget y los ciclos de Rc; no garantiza que un destructor se ejecute siempre.
