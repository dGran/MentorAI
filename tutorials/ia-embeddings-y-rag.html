Embeddings y RAG desde PHP

El modelo no ha leído tus condiciones de devolución ni tu manual interno. RAG se los pone delante en cada pregunta: buscas los trozos que importan, los metes en el prompt y exiges que cite de dónde salen. Esta lección lo monta con pgvector, empezando por decidir si de verdad lo necesitas.

El asistente de soporte de la tienda tiene que responder con tus políticas de devoluciones y envíos, que nunca ha visto. Qué es RAG ya lo viste en conceptos de IA; aquí va cómo se construye desde PHP y, sobre todo, cómo se comprueba que trae lo que debe.

¿Hace falta RAG? #

RAG añade piezas que mantener: un proveedor más, una tabla de vectores, una ingesta que reindexa cuando cambian los documentos y una evaluación propia. Antes de montarlo, descarta las dos alternativas baratas:

  • Meterlo todo en el contexto. Los modelos actuales de Claude admiten un millón de tokens. Si tu documentación cabe con holgura, mándala entera con caché de prompts y te ahorras la tubería: Anthropic ya lo recomendaba para bases de conocimiento de menos de unos 200.000 tokens. El límite real es el coste por llamada, la latencia y que un contexto enorme diluye lo relevante.
  • Búsqueda clásica. Si buscan referencias exactas (un código de error, un SKU, el nombre de una función), el full-text de PostgreSQL o un motor con BM25 las encuentra mejor que un embedding, que compara significados y no cadenas.

RAG compensa cuando el corpus es grande o cambia a menudo, cuando las preguntas usan palabras distintas a las del documento («¿me devolvéis el dinero si llega roto?» frente a «reembolso por producto defectuoso») y cuando necesitas decir de dónde sale cada respuesta.

1 IngestaTrocear y embeber, una vez y al cambiar
2 Embeber la preguntaCon el mismo modelo que los documentos
3 RecuperarLos k fragmentos más cercanos en pgvector
4 GenerarClaude responde con los fragmentos delante y los cita

La ingesta va en un worker; solo los pasos 2 a 4 ocurren en cada pregunta.

Embeddings: cerca es parecido #

Un modelo de embeddings convierte un texto en un vector (1.024 números en los modelos de abajo) de forma que dos textos que hablan de lo mismo quedan cerca aunque no compartan palabras. Es la misma idea que viste con los tokens, aplicada a fragmentos enteros. «Cerca» se mide con una distancia; la del coseno, que compara la dirección de los vectores, es la habitual.

Primera sorpresa al montarlo con Claude: Anthropic no ofrece modelo de embeddings propio. Su documentación remite a Voyage AI, hoy de MongoDB: voyage-4 como opción equilibrada, voyage-4-lite si mandan el coste y la latencia y voyage-4-large para la máxima calidad. También aconseja evaluar varios proveedores para tu caso. Con cualquiera, el patrón es una llamada HTTP que devuelve vectores:

php · embeddings con Voyage 
<?php

declare(strict_types=1);

final class EmbeddingsVoyage
{
    private const string URL = "https://ai.mongodb.com/v1/embeddings";
    private const string MODELO = "voyage-4";

    public function __construct(private readonly string $apiKey)
    {
    }

    public function deDocumentos(array $textos): array
    {
        return $this->embeber($textos, "document");
    }

    public function deConsulta(string $pregunta): array
    {
        return $this->embeber([$pregunta], "query")[0];
    }

    private function embeber(array $textos, string $tipoDeEntrada): array
    {
        $peticion = curl_init(self::URL);
        curl_setopt_array($peticion, [
            CURLOPT_POST => true,
            CURLOPT_RETURNTRANSFER => true,
            CURLOPT_TIMEOUT => 30,
            CURLOPT_HTTPHEADER => [
                "Content-Type: application/json",
                "Authorization: Bearer {$this->apiKey}",
            ],
            CURLOPT_POSTFIELDS => json_encode([
                "input" => $textos,
                "model" => self::MODELO,
                "input_type" => $tipoDeEntrada,
            ], JSON_THROW_ON_ERROR),
        ]);

        $cuerpo = curl_exec($peticion);
        $estado = curl_getinfo($peticion, CURLINFO_RESPONSE_CODE);

        if ($cuerpo === false || $estado !== 200) {
            throw new RuntimeException("Embeddings fallidos: HTTP {$estado}");
        }

        $respuesta = json_decode($cuerpo, true, flags: JSON_THROW_ON_ERROR);

        return array_column($respuesta["data"], "embedding", "index");
    }
}

input_type distingue el documento que indexas de la pregunta que buscas: el proveedor antepone una instrucción distinta a cada uno y eso mejora la recuperación, así que no lo omitas. Y los vectores de Voyage llegan normalizados a longitud 1, así que coseno, producto escalar y distancia euclídea dan el mismo orden: elige una y úsala igual en el índice y en la consulta.

Trocear los documentos #

No se embebe un documento entero: se trocea. Un vector resume todo su texto, así que el de un manual de cuarenta páginas «habla de todo» y no se parece especialmente a ninguna pregunta. El trozo es además lo que acabará en el prompt: si es enorme, pagas tokens de relleno; si es diminuto, llega sin el contexto que lo hace entendible.

Un punto de partida razonable: cortar primero por la estructura (títulos, secciones) y, dentro de cada sección, en trozos de unos cientos de tokens con solape entre trozos consecutivos. El solape existe para que una idea partida justo en la frontera aparezca entera en al menos uno de los dos.

php · trocear una sección con solape 
<?php

declare(strict_types=1);

final class Troceador
{
    public function __construct(
        private readonly int $palabrasPorTrozo = 250,
        private readonly int $palabrasDeSolape = 40,
    ) {
    }

    public function trocear(string $textoDeLaSeccion): array
    {
        $palabras = preg_split('/\s+/u', trim($textoDeLaSeccion), flags: PREG_SPLIT_NO_EMPTY);
        $avance = $this->palabrasPorTrozo - $this->palabrasDeSolape;
        $trozos = [];

        for ($inicio = 0; $inicio < count($palabras); $inicio += $avance) {
            $trozos[] = implode(" ", array_slice($palabras, $inicio, $this->palabrasPorTrozo));

            if ($inicio + $this->palabrasPorTrozo >= count($palabras)) {
                break;
            }
        }

        return $trozos;
    }
}

Contar palabras es una aproximación: el límite real del modelo de embeddings va en tokens. Tamaño y solape no se adivinan: son parámetros que se ajustan con la evaluación del final de la lección.

Guardar y buscar con pgvector #

Si ya usas PostgreSQL, pgvector te ahorra otra base de datos: añade el tipo vector(n), operadores de distancia e índices de vecinos aproximados. Los fragmentos viven en una tabla corriente, junto a sus metadatos:

sql · la tabla de fragmentos 
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE fragmentos (
    id bigserial PRIMARY KEY,
    documento text NOT NULL,
    seccion text NOT NULL,
    contenido text NOT NULL,
    modelo text NOT NULL,
    embedding vector(1024) NOT NULL
);

CREATE INDEX ON fragmentos USING hnsw (embedding vector_cosine_ops);
OperadorDistanciaClase del índice
<->Euclídea (L2)vector_l2_ops
<#>Producto escalar en negativo (ordena como una distancia)vector_ip_ops
<=>Coseno (1 − similitud)vector_cosine_ops
<+>L1 (Manhattan)vector_l1_ops

Sin índice, cada búsqueda compara la pregunta con todas las filas: exacto, pero lineal. Los índices de pgvector son aproximados: cambian algo de exhaustividad (recall) por velocidad, y hay dos.

HNSW: el punto de partida

  • Mejor equilibrio entre velocidad y recall
  • Se puede crear con la tabla vacía: no tiene fase de entrenamiento
  • Más lento de construir y ocupa más memoria
  • Se ajusta al consultar con hnsw.ef_search (40 por defecto)

IVFFlat: si la memoria aprieta

  • Se construye antes y ocupa menos
  • Peor equilibrio entre velocidad y recall
  • Se crea con los datos ya cargados: reparte las filas en lists
  • Se ajusta al consultar con ivfflat.probes (1 por defecto)
php · guardar y buscar con PDO 
<?php

declare(strict_types=1);

final class FragmentosPgvector
{
    public function __construct(private readonly PDO $pdo)
    {
    }

    public function guardar(string $documento, string $seccion, string $contenido, array $embedding): void
    {
        $this->pdo->prepare(
            "INSERT INTO fragmentos (documento, seccion, contenido, modelo, embedding)
             VALUES (:documento, :seccion, :contenido, 'voyage-4', CAST(:embedding AS vector))"
        )->execute([
            "documento" => $documento,
            "seccion" => $seccion,
            "contenido" => $contenido,
            "embedding" => $this->literal($embedding),
        ]);
    }

    public function masCercanos(array $embeddingDeLaPregunta, int $cuantos): array
    {
        $consulta = $this->pdo->prepare(
            "SELECT documento, seccion, contenido
             FROM fragmentos
             ORDER BY embedding <=> CAST(:pregunta AS vector)
             LIMIT :cuantos"
        );
        $consulta->bindValue("pregunta", $this->literal($embeddingDeLaPregunta));
        $consulta->bindValue("cuantos", $cuantos, PDO::PARAM_INT);
        $consulta->execute();

        return $consulta->fetchAll(PDO::FETCH_ASSOC);
    }

    private function literal(array $embedding): string
    {
        return json_encode($embedding, JSON_THROW_ON_ERROR);
    }
}

El vector viaja como texto ([0.12,-0.03,…]) y CAST lo convierte. json_encode da el formato exacto que espera vector y no depende de la directiva precision, como implode. Y la consulta usa <=> porque el índice es vector_cosine_ops: con otro operador, PostgreSQL no puede usarlo y recorre la tabla entera.

Al prompt, con su fuente #

Con los fragmentos recuperados, falta ponérselos delante al modelo. La versión ingenua los pega en el system como un bloque de texto:

php · antes, contexto sin fuentes 
$contexto = implode("\n\n", array_column($fragmentos, "contenido"));

$message = $client->messages->create(
    model: "claude-opus-5-5",
    maxTokens: 2048,
    system: "Responde usando esta documentación:\n\n{$contexto}",
    messages: [["role" => "user", "content" => $pregunta]],
);

Funciona en la demo y falla en tres cosas: el modelo no sabe de qué documento sale cada párrafo, tú no puedes enseñar la fuente al usuario y nada separa lo recuperado de lo que el modelo «sabe». La API de Claude tiene un bloque pensado para RAG, search_result, con fuente, título y contenido. Con las citas activadas, los bloques de texto que se apoyan en un resultado indican cuál lo respalda:

php · después, resultados de búsqueda con citas 
$resultados = array_map(
    fn (array $fragmento): array => [
        "type" => "search_result",
        "source" => "{$fragmento["documento"]}#{$fragmento["seccion"]}",
        "title" => $fragmento["seccion"],
        "content" => [["type" => "text", "text" => $fragmento["contenido"]]],
        "citations" => ["enabled" => true],
    ],
    $fragmentos,
);

$message = $client->messages->create(
    model: "claude-opus-5-5",
    maxTokens: 2048,
    system: "Respondes dudas de clientes usando SOLO los resultados de búsqueda adjuntos. " .
        "Si no contienen la respuesta, dilo: no la completes con lo que sepas.",
    messages: [
        ["role" => "user", "content" => [...$resultados, ["type" => "text", "text" => $pregunta]]],
    ],
);

if ($message->stopReason !== "end_turn") {
    throw new UnexpectedValueException("Respuesta incompleta: {$message->stopReason}");
}

$respuesta = "";
$fuentes = [];

foreach ($message->content as $block) {
    if ($block->type !== "text") {
        continue;
    }

    $respuesta .= $block->text;

    foreach ($block->citations ?? [] as $cita) {
        $fuentes[$cita->source] = $cita->title;
    }
}

Cada cita devuelve la source y el title que pusiste tú y el texto citado, así que puedes enlazar la sección exacta de tu documentación. Las citas son todo o nada: se activan en todos los resultados de la petición o en ninguno, y mezclarlas da error. Lo que el bloque no hace es volver fiable lo recuperado: un documento con instrucciones escondidas es inyección indirecta, y se trata en la lección de seguridad.

Errores típicos #

Lo que rompe un RAG en silencio

  • Mezclar modelos de embeddings. Los vectores de modelos distintos no son comparables salvo que el proveedor lo garantice (la familia voyage-4 comparte espacio): cambiar a otro modelo obliga a re-embeber todo el corpus. Para eso está la columna modelo.
  • Filtrar después del índice. Con HNSW, el WHERE se aplica a los candidatos que devuelve el índice: con ef_search en 40 y un filtro que cumple el 10 % de las filas, llegan unos 4 resultados aunque pidas 40. Desde pgvector 0.8, activar hnsw.iterative_scan hace que siga buscando hasta llenar el LIMIT o llegar a hnsw.max_scan_tuples.
  • Recuperar sin permisos. Si el corpus mezcla clientes o niveles de acceso, el filtro por propietario va en la consulta, no en el prompt: es la comprobación de propiedad de siempre, y OWASP lo recoge como LLM08:2025 (debilidades de vectores y embeddings).
  • Pasarse de dimensiones. vector indexa hasta 2.000; por encima, halfvec (hasta 4.000) o pedir menos dimensiones al proveedor.
  • IVFFlat sobre la tabla vacía. Sus listas salen de los datos que hay al crearlo: créalo después de la carga.

¿Trae lo correcto? #

Un RAG falla de dos formas que desde fuera se parecen: la recuperación no trajo el fragmento correcto, o lo trajo y el modelo respondió mal. Si las mezclas, no sabrás qué tocar. La recuperación se evalúa sola, sin llamar a Claude, con el método del eval mínimo: preguntas reales y, para cada una, la sección que debería salir.

php · acierto en los k primeros 
function aciertoEnK(array $casos, Closure $buscar, int $k): float
{
    $aciertos = 0;

    foreach ($casos as $caso) {
        $recuperadas = array_map(
            fn (array $fragmento): string => "{$fragmento["documento"]}#{$fragmento["seccion"]}",
            $buscar($caso["pregunta"], $k),
        );

        if (array_intersect($caso["fuentesEsperadas"], $recuperadas) !== []) {
            $aciertos++;
        }
    }

    return $aciertos / count($casos);
}

$casos = [
    ["pregunta" => "¿Cuántos días tengo para devolver un pedido?", "fuentesEsperadas" => ["devoluciones.md#Plazos"]],
    ["pregunta" => "¿Me devolvéis el envío si el producto llegó roto?", "fuentesEsperadas" => ["devoluciones.md#Defectuosos", "envios.md#Incidencias"]],
];

$buscar = fn (string $pregunta, int $k): array => $fragmentos->masCercanos($embeddings->deConsulta($pregunta), $k);

printf("acierto@5: %.0f %%\n", aciertoEnK($casos, $buscar, 5) * 100);

El acierto@k cuenta en cuántas preguntas aparece al menos una fuente esperada entre los k primeros; si una respuesta necesita varias, mide también qué fracción llega (recall@k). Etiqueta por documento y sección, no por id de fragmento: los ids cambian cada vez que retocas el troceado, y el golden set tiene que sobrevivir a eso. Con ese número ya puedes comparar trozos de 250 y de 400 palabras, con y sin solape, o subir ef_search.

Y antes de fiarte de los tiempos, comprueba que el índice trabaja. En el plan tiene que salir Index Scan using fragmentos_embedding_idx con su Order By; si sale Seq Scan seguido de Sort, el operador no casa con la clase del índice:

sql · el índice, en el plan 
EXPLAIN SELECT documento, seccion
FROM fragmentos
ORDER BY embedding <=> (SELECT embedding FROM fragmentos WHERE id = 1)
LIMIT 5;

Cuándo aplicarlo #

RAG encaja cuando…

  • El corpus es grande o cambia a menudo y no compensa mandarlo entero
  • Las preguntas llegan en lenguaje natural, con palabras distintas a las del documento
  • Necesitas citar la fuente o limitar qué documentos ve cada usuario

No lo montes si…

  • La documentación cabe en el contexto: mándala entera con caché de prompts
  • Se buscan identificadores exactos: full-text o BM25, o una búsqueda híbrida que combine ambos
  • Aún no tienes golden set: sin él no sabrás si el RAG ayuda o estorba

Resumen #

Lo que te llevas

  • Antes de RAG, descarta lo barato: todo el corpus en contexto con caché de prompts, o búsqueda por palabras si buscan identificadores exactos.
  • Anthropic no tiene modelo de embeddings: su documentación remite a Voyage AI. Mismo modelo para documentos y preguntas, y input_type siempre.
  • Trocea por estructura, en trozos de unos cientos de tokens con solape, y ajusta ambos midiendo.
  • pgvector: vector(n), el operador que casa con la clase del índice y HNSW por defecto; ojo con los filtros que se aplican después del índice.
  • Los fragmentos entran como search_result con citas, y la recuperación se evalúa aparte con un acierto@k sobre preguntas etiquetadas por fuente.
