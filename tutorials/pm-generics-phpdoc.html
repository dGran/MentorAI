Generics con PHPDoc

Tu repositorio devuelve object, tu colección devuelve array y el IDE deja de autocompletar justo donde más falta hace. PHP no tiene generics, pero PHPStan y Psalm sí: viven en los comentarios y convierten «un array de algo» en un tipo que la máquina comprueba.

Un generic es un tipo con un hueco: «colección de algo», donde ese algo se decide al usarla. PHP no tiene sintaxis para ese hueco, así que PHPStan y Psalm la inventaron en PHPDoc. El resultado es raro de leer al principio, pero cierra la última gran zona ciega del análisis estático.

Un array de qué #

En tipado estricto viste que PHP comprueba en cada llamada los tipos que declaras. Esa comprobación tiene un límite: array, iterable y object no dicen qué llevan dentro. Una función que devuelve array puede devolver usuarios, strings o una mezcla, y para el motor es igual de correcta.

¿Por qué no añadir Collection<User> al lenguaje? Porque PHP comprueba los tipos en ejecución. Un generic real obligaría a cada instancia a recordar su T y a validar cada elemento que entra; con arrays grandes y tipos anidados, ese coste se paga en cada llamada. La alternativa de Java, borrar los tipos al compilar, dejaría una sintaxis que el motor no comprueba. Y eso, en PHP, ya existe: son los docblocks.

Hoy class Collection<T> es un error de sintaxis. Lo que sí tienes es un analizador, PHPStan o Psalm, que lee etiquetas como @template y razona con ellas antes de que el código se ejecute.

@template: el tipo como parámetro #

@template T declara una variable de tipo. Luego la usas donde iría un tipo normal: @param T, @return T. El analizador deduce T en cada llamada a partir de los argumentos.

php · firstOf.php 
<?php

declare(strict_types=1);

/**
 * @template T
 * @param list<T> $items
 * @return T|null
 */
function firstOf(array $items): mixed
{
    return $items[0] ?? null;
}

$name = firstOf(['Ana', 'Bruno']);
$price = firstOf([9.95, 12.5]);

\PHPStan\dumpType($name);
\PHPStan\dumpType($price);

\PHPStan\dumpType() pide al analizador el tipo que ha deducido. Responde 'Ana'|'Bruno'|null y 9.95|12.5|null: afina hasta los literales, pero lo que importa es que ya no es mixed.

La firma nativa sigue diciendo mixed, que es lo único que PHP sabe expresar. El docblock añade la relación entre entrada y salida: lo que sale es del mismo tipo que lo que entró. Esa relación es justo lo que mixed pierde.

@template T of Animal pone un límite superior: T puede ser Animal o cualquier subtipo, y dentro de la función puedes llamar a los métodos de Animal.

Una Collection<T> de verdad #

Si @template va en la clase, T vale para todos sus métodos. Este es el caso de uso estrella: una colección que sabe qué contiene, sin escribir UserCollection, OrderCollection y veinte clases idénticas más.

php · Collection.php 
<?php

declare(strict_types=1);

/**
 * @template T
 * @implements IteratorAggregate<int, T>
 */
class Collection implements IteratorAggregate
{
    /** @param list<T> $items */
    public function __construct(private array $items = [])
    {
    }

    /** @param T $item */
    public function add(mixed $item): void
    {
        $this->items[] = $item;
    }

    /** @return T|null */
    public function first(): mixed
    {
        return $this->items[0] ?? null;
    }

    /**
     * @template R
     * @param callable(T): R $transform
     * @return Collection<R>
     */
    public function map(callable $transform): Collection
    {
        return new Collection(array_map($transform, $this->items));
    }

    /** @return ArrayIterator<int, T> */
    public function getIterator(): ArrayIterator
    {
        return new ArrayIterator($this->items);
    }
}

final class User
{
    public function __construct(public readonly string $email)
    {
    }
}

$users = new Collection([new User('ana@example.com')]);
$emails = $users->map(fn (User $user): string => $user->email);

$users->add('bruno@example.com');

echo count(iterator_to_array($users)), PHP_EOL;

PHPStan deduce Collection<User> del constructor, sin anotar nada en la llamada, y a partir de ahí todo encaja: el foreach da User, first() da User|null y map() introduce su propio R de método, así que el resultado es Collection<string>. El add() con un string es lo que el analizador marca:

bash · salida de PHPStan 
$ vendor/bin/phpstan analyse src/Collection.php
  Line   Collection.php
  55     Parameter #1 $item of method Collection<User>::add() expects User,
         string given.

Fíjate en @implements IteratorAggregate<int, T>. Para los analizadores, IteratorAggregate es una interfaz genérica con dos parámetros, clave y valor, y hay que decir con qué tipos la implementas; si lo omites, PHPStan lo marca con missingType.generics.

class-string<T> en fábricas y repositorios #

Contenedores, fábricas y EntityManager::getRepository() reciben un nombre de clase y devuelven una instancia. Con class-string<T>, el analizador lee el T del propio Mailer::class:

php · Container.php 
<?php

declare(strict_types=1);

final class Container
{
    /** @var array<class-string, object> */
    private array $services = [];

    /**
     * @template T of object
     * @param class-string<T> $id
     * @return T
     */
    public function get(string $id): object
    {
        $service = $this->services[$id] ??= new $id();

        if (!$service instanceof $id) {
            throw new LogicException("Servicio mal registrado: {$id}");
        }

        return $service;
    }
}

final class Mailer
{
    public function send(string $to): bool
    {
        return true;
    }
}

$mailer = (new Container())->get(Mailer::class);

\PHPStan\dumpType($mailer);

Antes de esto, cada $container->get(Mailer::class) necesitaba un /** @var Mailer $mailer */ encima, una afirmación que nadie verifica. Ahora el tipo sale de la firma. Si te suena el patrón, es el que viste en inyección de dependencias; el instanceof sigue ahí porque el docblock no protege en ejecución.

list<T> y array shapes #

Los arrays de PHP son a la vez listas y diccionarios, y los analizadores distinguen los dos usos:

TipoQué promete
array<string, int>Claves string, valores int, en cualquier orden.
list<User>Claves 0, 1, 2… consecutivas, sin huecos.
non-empty-list<User>Lo mismo, con al menos un elemento.
array{id: int, email: string, nickname?: string}Claves fijas con su tipo; ? marca las opcionales.

list importa más de lo que parece. array_filter conserva las claves, así que su resultado ya no es una lista, y json_encode lo serializaría como objeto en vez de array. PHPStan lo ve desde el nivel 7:

php · listas y shapes 
<?php

declare(strict_types=1);

/** @param list<int> $ids */
function loadUsers(array $ids): void
{
}

/** @param list<int> $ids */
function loadActive(array $ids): void
{
    loadUsers(array_filter($ids, fn (int $id): bool => $id > 0));
    loadUsers(array_values(array_filter($ids, fn (int $id): bool => $id > 0)));
}

/** @return array{id: int, email: string, nickname?: string} */
function userRow(): array
{
    return ['id' => 7, 'email' => 'ana@example.com'];
}

$row = userRow();
echo $row['emial'];

Las array shapes documentan las filas que vienen de la base de datos o de un JSON. El analizador avisa si lees $row['emial'] y, desde el nivel 7, también si lees una clave opcional sin comprobarla. Cuando la shape pasa de cuatro o cinco claves, o viaja entre capas, es señal de que pide un objeto con propiedades readonly, como los de enums e inmutabilidad.

@extends e @implements #

Al heredar de una clase genérica tienes que decir qué vale su T. Es como llamar a un constructor: si no pasas el argumento, el analizador lo trata como mixed y toda la información se pierde por el camino.

php · UserCollection.php 
<?php

declare(strict_types=1);

/** @extends Collection<User> */
final class UserCollection extends Collection
{
    /** @return list<string> */
    public function emails(): array
    {
        $emails = [];

        foreach ($this as $user) {
            $emails[] = $user->email;
        }

        return $emails;
    }
}

/** @template T of object */
interface Repository
{
    /** @return T|null */
    public function find(int $id): ?object;
}

/** @implements Repository<User> */
final class UserRepository implements Repository
{
    public function find(int $id): ?User
    {
        return null;
    }
}

Desde el nivel 6, PHPStan exige ese dato y da missingType.generics en la clase que no lo pone: «extends generic class Collection but does not specify its types: T». Lo mismo con @implements al implementar una interfaz genérica, como el Repository de cada entidad.

@template-covariant #

Un perro es un animal. ¿Un refugio de perros es un refugio de animales? Parece que sí, hasta que alguien mete un gato:

php · Shelter.php 
<?php

declare(strict_types=1);

interface Animal
{
    public function name(): string;
}

final class Dog implements Animal
{
    public function name(): string
    {
        return 'Rex';
    }
}

final class Cat implements Animal
{
    public function name(): string
    {
        return 'Misi';
    }
}

/** @template T of Animal */
final class Shelter
{
    /** @var list<T> */
    private array $animals = [];

    /** @param T $animal */
    public function admit(Animal $animal): void
    {
        $this->animals[] = $animal;
    }

    public function count(): int
    {
        return count($this->animals);
    }
}

/** @template-covariant T of Animal */
final class Adoptions
{
    /** @param list<T> $animals */
    public function __construct(private readonly array $animals)
    {
    }

    /** @return list<T> */
    public function all(): array
    {
        return $this->animals;
    }
}

/** @param Shelter<Animal> $shelter */
function admitCat(Shelter $shelter): void
{
    $shelter->admit(new Cat());
}

/** @param Adoptions<Animal> $adoptions */
function printNames(Adoptions $adoptions): void
{
    foreach ($adoptions->all() as $animal) {
        echo $animal->name(), PHP_EOL;
    }
}

/** @var Shelter<Dog> $dogs */
$dogs = new Shelter();
admitCat($dogs);

printNames(new Adoptions([new Dog()]));

Por defecto, T es invariante: Shelter<Dog> y Shelter<Animal> son tipos sin relación, y PHPStan rechaza la llamada. Es lo correcto, porque admit() acepta un T y eso permite colar cualquier animal.

Si la clase solo devuelve T y nunca lo recibe después de construirse, el problema desaparece. Eso es @template-covariant: con Adoptions, inmutable, pasar Adoptions<Dog> donde se pide Adoptions<Animal> es válido. Y si declaras covariante una clase con un add(T), PHPStan da generics.variance: «declared as covariant, but occurs in contravariant position». Las colecciones inmutables pueden ser covariantes; las mutables, no.

Lo que el runtime ignora #

Todo lo anterior son comentarios. Ejecuta la colección con el add('bruno@example.com') dentro y PHP la llena sin protestar: dos elementos, uno de ellos un string. El fallo aparecería más tarde y lejos, en el primer sitio con un tipo nativo, como una closure que pide User. La garantía la da el análisis en CI, no el motor.

Lo entienden IDE y analizador

  • @template, of, covarianza
  • list, class-string, shapes
  • @extends e @implements
  • Autocompletado tras foreach y first()

Lo ignora PHP al ejecutar

  • Todo docblock: no valida ni lanza TypeError
  • Solo comprueba la firma nativa: mixed, array
  • Reflection solo lo ve como texto en getDocComment()

Por eso la firma nativa importa: un @param T con mixed debajo no protege a quien llama sin analizador. Pon el tipo nativo más estrecho que puedas y deja al docblock lo que PHP no sabe decir.

Errores típicos #

Lo que se cuela al anotar

  • El @var encima de cada llamada. Es una afirmación sin comprobar. Si el tipo debería salir de la firma, el arreglo es un @template o un class-string<T> en el método.
  • Heredar sin @extends. La subclase compila, pero sus elementos pasan a ser mixed y el analizador deja de ayudar donde más se usan.
  • Covarianza en una clase mutable. Si la hay, PHPStan la rechaza; no la silencies, porque es exactamente el gato en el refugio de perros.
  • Docblock y firma nativa en desacuerdo. @return T|null sobre ?object sin T of object da return.phpDocType: el docblock no puede prometer más de lo que permite la firma.
  • Creer que array_filter devuelve una lista. Conserva las claves; envuélvelo en array_values.

Cómo comprobarlo #

Cuando no sepas qué ha deducido el analizador, pregúntale. \PHPStan\dumpType() imprime el tipo como un error más del informe. Solo existe para el analizador: si el código se ejecuta con la llamada dentro, falla con «Call to undefined function», así que la quitas antes de hacer commit. En Psalm, el equivalente es la anotación /** @psalm-trace $variable */.

bash · preguntar al analizador 
$ vendor/bin/phpstan analyse --level 6 src/
  Line   Container.php
  37     Dumped type: Mailer
  Line   LooseCollection.php
  5      Class LooseCollection extends generic class Collection but does not
         specify its types: T

Psalm entiende las mismas etiquetas. Si alguna construcción solo la entiende una de las dos herramientas, o confunde a tu IDE, usa los prefijos @phpstan-template, @phpstan-param o @psalm-return: cada analizador da prioridad a su versión con prefijo sobre la etiqueta sin él. Para que el pipeline exija todo esto en cada push, el sitio es el de CI para PHP.

Cuándo aplicarlo #

Generics en PHPDoc cuando…

  • Escribes colecciones, repositorios base o contenedores reutilizables
  • Un método devuelve algo que depende de un argumento, como class-string<T>
  • El proyecto corre PHPStan en nivel 6 o más
  • Las filas de base de datos o JSON viajan como arrays

No compensa cuando…

  • No hay analizador en el proyecto: nadie comprobará las etiquetas
  • Solo hay un tipo concreto: list<User> basta, sin @template
  • La shape crece y se reutiliza: pide una clase

La alternativa sencilla

Si solo tienes dos o tres colecciones, una clase concreta con firmas nativas (add(User $user)) da la misma seguridad y además la comprueba PHP en ejecución. El generic se gana su sitio cuando el mismo código sirve para muchos tipos.

Resumen #

Lo que te llevas

  • PHP no tiene generics porque comprueba tipos en ejecución; PHPStan y Psalm los simulan en PHPDoc y los comprueban antes de ejecutar.
  • @template T declara el hueco y @param T / @return T conectan entrada y salida.
  • class-string<T> saca el tipo del nombre de clase: adiós al @var en cada get().
  • list<T> y las array shapes describen lo que array calla; array_filter rompe las listas.
  • Al heredar, @extends e @implements fijan el T; desde el nivel 6 PHPStan lo exige.
  • T es invariante por defecto; @template-covariant solo en clases que no reciben T, es decir, inmutables.
  • El runtime ignora los docblocks: la firma nativa sigue siendo tu única garantía sin analizador.
