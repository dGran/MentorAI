Fallos parciales: la respuesta que nunca llega

Una llamada local se hace o no se hace. Una remota tiene un tercer final sin nombre en ningún lenguaje: no sé. Diseñar para él separa los sistemas que se recuperan solos de los que necesitan a alguien mirando la base de datos un domingo.

En un monolito, una operación se hace o no se hace. En un sistema distribuido aparece un tercer estado que no tiene nombre en ningún lenguaje de programación: no sé. Aprender a diseñar para ese tercer estado es la diferencia entre un sistema que se recupera solo y uno que necesita a alguien mirando la base de datos un domingo por la noche.

Dos desenlaces frente a tres #

Cuando llamas a un método de tu propio proceso, el resultado es binario: o devuelve un valor o lanza una excepción. No hay más opciones, porque la llamada y su resultado viven en la misma memoria. Si el proceso muere, mueren los dos juntos.

Cuando la llamada cruza la red, la petición y la respuesta viajan por separado, y cada una puede perderse por su cuenta. Eso abre un desenlace nuevo:

Llamada local

  • Éxito: devuelve un valor. Se hizo.
  • Excepción: lanza. No se hizo.

Llamada remota

  • Éxito: respuesta 200. Se hizo.
  • Rechazo explícito: un 400 o un 409. No se hizo.
  • Silencio: timeout, conexión cortada, 502. No sé.

El error más caro del código distribuido

Tratar el silencio como si fuera un rechazo. catch (TimeoutException) seguido de «marca el pedido como fallido» es cómo se cobra dos veces a un cliente, o cómo se le dice que su pago falló mientras el dinero ya salió de su cuenta.

Los cuatro sitios donde se rompe #

Un timeout no te dice dónde se rompió. Y los cuatro puntos posibles se reparten en dos grupos con consecuencias opuestas:

A La petición no llegóSe perdió en la red. El trabajo NO se hizo.
B Llegó y el servidor murió antes de procesarlaEl trabajo NO se hizo.
C Se procesó y el servidor murió al responderEl trabajo SÍ se hizo.
D Se procesó y la respuesta se perdióEl trabajo SÍ se hizo.

Desde el cliente, los cuatro casos son idénticos: un timeout. Y en dos de ellos el trabajo está hecho.

Nada en el protocolo te permite distinguirlos. Ni un timeout más largo, ni un health check, ni mirar los logs del otro servicio en ese instante: en el momento de decidir qué haces, la información no existe. Este es el resultado que hay que interiorizar, porque no se arregla con más ingeniería en el cliente.

Las tres respuestas posibles #

Si no puedes saber qué pasó, solo te quedan tres caminos, y cada uno traslada el coste a un sitio distinto:

EstrategiaQué hacesQué te cuesta
Reintentar Repites la operación hasta tener una respuesta clara Puedes ejecutarla dos veces, salvo que sea idempotente
Preguntar Consultas al otro servicio si la operación consta Necesitas un identificador tuyo y un endpoint de consulta
Aplazar Dejas la operación «en curso» y la resuelves después El usuario espera y tú mantienes un proceso de conciliación

En la práctica se combinan: reintentas con una clave de idempotencia, y si tras N intentos sigues sin respuesta, dejas la operación en un estado intermedio y la resuelve un proceso aparte. Lo que nunca es una opción es decidir a ciegas.

El estado intermedio, en código #

El error de diseño de fondo suele estar en el modelo de datos, no en el cliente HTTP: un pedido con un booleano pagado no tiene dónde guardar «no sé». Un enum con un estado explícito, sí.

php · EstadoPago.php 
<?php

declare(strict_types=1);

enum EstadoPago: string
{
    case Pendiente = 'pendiente';
    case Confirmado = 'confirmado';
    case Rechazado = 'rechazado';
    case Incierto = 'incierto';

    public function necesitaConciliacion(): bool
    {
        return $this === self::Incierto;
    }
}

Con ese estado, el cliente puede ser honesto sobre lo que sabe y lo que no:

php · CobrarPedido.php 
<?php

declare(strict_types=1);

final class CobrarPedido
{
    public function __invoke(Pedido $pedido): EstadoPago
    {
        try {
            $this->pagos->cobrar($pedido->id(), $pedido->importeEnCentimos());

            return EstadoPago::Confirmado;
        } catch (PagoRechazado $rechazo) {
            return EstadoPago::Rechazado;
        } catch (RespuestaNoRecibida $silencio) {
            $this->registro->warning('Cobro sin respuesta, queda para conciliar', [
                'pedido' => $pedido->id(),
            ]);

            return EstadoPago::Incierto;
        }
    }
}

Dos excepciones, no una

Lo importante del bloque anterior no es el try: es que PagoRechazado y RespuestaNoRecibida son tipos distintos. Si tu cliente HTTP lanza la misma excepción para un 400 y para un timeout, la información que necesitas para decidir se pierde antes de llegar al caso de uso, y ya no hay forma de recuperarla.

El estado Incierto no es una derrota: es una promesa de que alguien lo va a mirar. Esa promesa la cumple un proceso de conciliación que recorre los pagos inciertos con cierta antigüedad, pregunta al proveedor por el identificador del pedido y los cierra en un sentido o en otro. Sin ese proceso, el estado nuevo solo es una forma más elegante de perder dinero.

Cuándo aplicarlo #

Modela el «no sé» cuando…

  • La operación mueve dinero, inventario o algo que no se puede deshacer solo
  • Ejecutarla dos veces tiene consecuencias visibles para el usuario
  • El otro extremo es un proveedor externo que no controlas
  • Ya tienes una tarea recurrente donde meter la conciliación

Basta con reintentar cuando…

  • La operación es idempotente por naturaleza: un PUT, un borrado
  • Es una lectura: repetirla no tiene efectos
  • El coste de equivocarse es un correo de más, no un cobro de más

Resumen #

Lo que te llevas

  • La llamada remota tiene un tercer desenlace que no existe en local: el silencio. No es un fallo, es falta de información.
  • Un timeout es indistinguible en cuatro escenarios, y en dos de ellos el trabajo ya está hecho. Tratarlo como fallo es cómo se cobra dos veces.
  • Solo hay tres respuestas posibles: reintentar, preguntar o aplazar. Decidir a ciegas no está entre ellas.
  • El fallo suele estar en el modelo de datos: un booleano pagado no tiene dónde guardar «no sé». Un enum con estado incierto, sí.
  • Un estado incierto sin proceso de conciliación que lo cierre es solo una forma más elegante de perder dinero.
