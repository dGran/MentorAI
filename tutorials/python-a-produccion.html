Python a producción

Uvicorn y Gunicorn con workers, logging estructurado con structlog, healthcheck endpoint, métricas con prometheus-client y Dockerfile production-ready.

Que tu API responda en uvicorn --reload no dice nada de cómo se comportará con cuatro núcleos, un orquestador que la reinicia y alguien de guardia preguntando por qué falla de madrugada. Pasar a producción es responder cuatro preguntas: cuántos procesos corren, qué cuentan los logs, cómo sabe el orquestador que estás sano y qué números miras para enterarte antes que tus usuarios.

Uvicorn y Gunicorn: cuándo usar cada uno #

Uvicorn es un servidor ASGI de alto rendimiento: implementa el protocolo ASGI y gestiona el event loop de asyncio. Es lo que ejecuta tu aplicación FastAPI. Solo tiene un proceso, lo que limita el uso de CPU en máquinas con varios núcleos.

Gunicorn es un gestor de procesos: no sabe de ASGI ni de async, pero sabe arrancar, monitorizar y reiniciar procesos hijo. La combinación Gunicorn + UvicornWorker aprovecha ambas fortalezas: Gunicorn gestiona N procesos, cada uno de los cuales es un Uvicorn con su propio event loop.

Por qué la combinación funciona: Gunicorn actúa como process manager (arranca N workers, los reinicia si mueren, gestiona señales del SO para graceful shutdown). Uvicorn actúa como servidor ASGI dentro de cada worker (maneja async, HTTP/1.1 y WebSockets). Separar las dos responsabilidades hace cada pieza más simple y reemplazable: si mañana aparece un servidor ASGI mejor que Uvicorn, cambias el worker sin tocar el proceso manager.

Instalar las dos piezas:

bash 
pip install uvicorn[standard] uvicorn-worker gunicorn

Uvicorn solo (desarrollo o un único proceso):

bash 
uvicorn main:app --host 0.0.0.0 --port 8000 --reload

Gunicorn con UvicornWorker (producción):

bash 
gunicorn main:app \
  --worker-class uvicorn_worker.UvicornWorker \
  --workers 4 \
  --bind 0.0.0.0:8000 \
  --timeout 30 \
  --keepalive 2 \
  --access-logfile -

El número de workers suele seguir la fórmula 2 * núcleos_cpu + 1. Con 2 núcleos, 5 workers. Con 4 núcleos, 9 workers. El margen extra sobre el número de núcleos compensa los momentos en que un worker está esperando I/O y otro puede usar el procesador.

Para el graceful shutdown, FastAPI usa el patrón lifespan: código que se ejecuta al arrancar y al parar la aplicación. Gunicorn envía SIGTERM, FastAPI termina las peticiones en curso y luego ejecuta el bloque de shutdown:

python 
from contextlib import asynccontextmanager
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    await database.connect()
    await cache.initialize()
    yield
    await database.disconnect()
    await cache.close()


app = FastAPI(lifespan=lifespan)

Logging estructurado con structlog #

El logging tradicional de Python escribe líneas de texto libre. En producción, esas líneas las procesa un sistema de agregación (Loki, Elasticsearch, CloudWatch) que necesita extraer campos con regex frágiles. El logging estructurado escribe directamente JSON: cada campo es una clave, no texto embebido en un mensaje.

bash 
pip install structlog
python 
import logging
import structlog


def configure_logging(is_development: bool) -> None:
    shared_processors = [
        structlog.contextvars.merge_contextvars,
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso"),
    ]

    if is_development:
        processors = shared_processors + [
            structlog.dev.ConsoleRenderer(),
        ]
    else:
        processors = shared_processors + [
            structlog.processors.dict_tracebacks,
            structlog.processors.JSONRenderer(),
        ]

    structlog.configure(
        processors=processors,
        wrapper_class=structlog.make_filtering_bound_logger(logging.INFO),
        context_class=dict,
        logger_factory=structlog.PrintLoggerFactory(),
    )

El uso en el código es el mismo independientemente de si el output es texto o JSON:

python 
import structlog

logger = structlog.get_logger()


async def procesar_pedido(pedido_id: int, usuario_id: int) -> dict:
    structlog.contextvars.bind_contextvars(
        pedido_id=pedido_id,
        usuario_id=usuario_id,
    )

    logger.info("pedido.procesando")

    try:
        resultado = await calcular_total(pedido_id)
        logger.info("pedido.completado", total=resultado["total"])
        return resultado
    except ValueError as error:
        logger.warning("pedido.datos_invalidos", error=str(error))
        raise
    except Exception as error:
        logger.exception("pedido.error_inesperado", error=str(error))
        raise

bind_contextvars añade campos al contexto del hilo o corrutina actual, de modo que todos los logs emitidos durante el procesamiento de esa petición incluyan automáticamente pedido_id y usuario_id sin tener que pasarlos manualmente.

Para que el contexto de cada petición HTTP se limpie entre peticiones, añade un middleware que llame a clear_contextvars() al inicio y vincule datos de la petición (request_id, ruta):

python 
import uuid
import structlog
from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def logging_middleware(request: Request, call_next):
    structlog.contextvars.clear_contextvars()
    structlog.contextvars.bind_contextvars(
        request_id=str(uuid.uuid4()),
        method=request.method,
        path=request.url.path,
    )
    response = await call_next(request)
    structlog.contextvars.bind_contextvars(status_code=response.status_code)
    return response

Healthcheck endpoint #

Un healthcheck le dice al orquestador (Docker, Kubernetes) si el proceso está vivo y si está listo para recibir tráfico. Son dos preguntas distintas con respuestas distintas:

Endpoint Pregunta Falla cuando
/health (liveness) ¿Está el proceso vivo? El proceso está bloqueado o en un estado irrecuperable
/ready (readiness) ¿Puede recibir peticiones? La BD no está disponible, el calentamiento no ha terminado
python 
from fastapi import FastAPI, HTTPException
from sqlalchemy import text
from sqlalchemy.ext.asyncio import AsyncSession
from fastapi import Depends

app = FastAPI()


@app.get("/health")
async def health() -> dict:
    return {"status": "ok"}


@app.get("/ready")
async def ready(session: AsyncSession = Depends(get_session)) -> dict:
    try:
        await session.execute(text("SELECT 1"))
    except Exception as error:
        raise HTTPException(status_code=503, detail=f"Base de datos no disponible: {error}")

    return {"status": "ready", "database": "ok"}

/health es intencionalmente trivial: si el proceso puede responder, está vivo. /ready verifica dependencias externas. Kubernetes usa liveness para reiniciar pods bloqueados y readiness para desviar el tráfico mientras el pod está arrancando o sus dependencias no están disponibles.

El HEALTHCHECK en el Dockerfile permite que Docker también monitorice el contenedor:

dockerfile 
HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"

Métricas con prometheus-client #

Prometheus es el estándar de facto para métricas en servicios backend. El cliente Python expone las métricas en el formato de texto que Prometheus entiende. Con un middleware en FastAPI, instrumentas automáticamente todas las rutas:

bash 
pip install prometheus-client
python 
import time
from prometheus_client import Counter, Histogram, generate_latest, CONTENT_TYPE_LATEST
from fastapi import FastAPI, Request, Response

app = FastAPI()

PETICIONES_TOTAL = Counter(
    "http_requests_total",
    "Total de peticiones HTTP recibidas",
    ["method", "path", "status_code"],
)

DURACION_PETICION = Histogram(
    "http_request_duration_seconds",
    "Duración de peticiones HTTP en segundos",
    ["method", "path"],
    buckets=[0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0],
)


@app.middleware("http")
async def metricas_middleware(request: Request, call_next):
    inicio = time.perf_counter()
    respuesta = await call_next(request)
    duracion = time.perf_counter() - inicio
    ruta = request.scope.get("route")
    plantilla = ruta.path if ruta else "sin-ruta"

    PETICIONES_TOTAL.labels(
        method=request.method,
        path=plantilla,
        status_code=respuesta.status_code,
    ).inc()

    DURACION_PETICION.labels(
        method=request.method,
        path=plantilla,
    ).observe(duracion)

    return respuesta


@app.get("/metrics")
async def metricas() -> Response:
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

Prometheus scrapeará /metrics periódicamente (normalmente cada 15 o 30 segundos). Con esos datos puedes construir alertas y dashboards en Grafana: latencia de percentil 99, tasa de errores por ruta, throughput total.

Para métricas de negocio (pedidos procesados, pagos completados, usuarios registrados), declara contadores adicionales y los incrementas en los puntos relevantes del dominio:

python 
from prometheus_client import Counter

PEDIDOS_COMPLETADOS = Counter(
    "pedidos_completados_total",
    "Total de pedidos completados",
    ["metodo_pago"],
)

PEDIDOS_FALLIDOS = Counter(
    "pedidos_fallidos_total",
    "Total de pedidos que fallaron",
    ["motivo"],
)


async def completar_pedido(pedido_id: int, metodo_pago: str) -> dict:
    try:
        resultado = await procesar_pago(pedido_id, metodo_pago)
        PEDIDOS_COMPLETADOS.labels(metodo_pago=metodo_pago).inc()
        return resultado
    except PagoRechazadoError as error:
        PEDIDOS_FALLIDOS.labels(motivo="pago_rechazado").inc()
        raise

Cuándo aplicarlo #

Aplícalo cuando…

  • Gunicorn + UvicornWorker: despliegas en una máquina o VM donde tú gestionas los procesos
  • Logging JSON: los logs acaban en un agregador (Loki, Elasticsearch, CloudWatch)
  • /health y /ready: hay un orquestador o un balanceador que decide a quién mandar tráfico
  • Métricas: el servicio lo va a operar alguien que necesita alertas, no intuiciones

Y elige otra cosa cuando…

  • Corres en Kubernetes con autoescalado: un solo proceso uvicorn por contenedor y más réplicas suele ser más simple, porque el orquestador ya gestiona los procesos
  • Estás en desarrollo: el JSON es ilegible en una terminal; usa la salida de consola de structlog
  • Ya tienes OpenTelemetry o un APM instrumentando: no dupliques las métricas HTTP con un middleware propio

La fórmula 2 * núcleos + 1 es un punto de partida, no un número cerrado: cada worker carga la aplicación entera, así que mide con carga real y vigila la memoria antes de subirla.

Errores típicos al operar en producción

Un /health que consulta la base de datos. Si la base de datos cae, falla el liveness y el orquestador reinicia todos los pods a la vez, que no arreglan nada y además tardan en volver. Las dependencias se comprueban solo en /ready.

Etiquetas de métricas con alta cardinalidad. Cada valor distinto de una etiqueta es una serie temporal nueva. Usar la URL real (/pedidos/8123) o un id de usuario como etiqueta crea una serie por pedido y acaba tumbando Prometheus: etiqueta con la plantilla de la ruta (/pedidos/{id}).

prometheus-client con varios workers sin modo multiproceso. Cada worker de Gunicorn guarda sus contadores en su memoria y cada scrape cae en uno distinto, así que los números saltan. Activa el modo multiproceso con PROMETHEUS_MULTIPROC_DIR.

Meter los datos en el mensaje del log. log.info(f"pedido {pedido_id} creado") te deja texto libre otra vez. Lo estructurado es log.info("pedido_creado", pedido_id=pedido_id): el campo se puede filtrar y agregar.

Resumen #

Lo que te llevas

  • Gunicorn gestiona procesos; Uvicorn ejecuta el event loop ASGI dentro de cada proceso. La combinación aprovecha múltiples núcleos de CPU con la misma aplicación async, sin código adicional.
  • El número de workers recomendado es 2 * núcleos + 1; el margen sobre los núcleos físicos compensa los workers esperando I/O.
  • structlog escribe JSON en producción y texto coloreado en desarrollo con la misma API de logging; bind_contextvars propaga automáticamente el contexto de la petición a todos los logs del request.
  • /health verifica que el proceso responde (liveness); /ready verifica que las dependencias están disponibles (readiness). Son conceptos distintos con consecuencias distintas en el orquestador.
  • prometheus-client con un middleware en FastAPI instrumenta todas las rutas automáticamente; las métricas de negocio se añaden con contadores adicionales en los puntos del dominio donde ocurren los eventos relevantes.
  • El HEALTHCHECK en el Dockerfile integra la monitorización de salud en el ciclo de vida del contenedor, independientemente de si hay un orquestador externo.
