PHPStan: niveles y por qué un baseline no es un arreglo

Tus tests pasan en verde y producción lanza un TypeError en una rama que nadie ejecutó. PHPStan lee todas las ramas sin ejecutar ninguna. Esta lección va de adoptarlo en un proyecto con historia sin parar al equipo, y de no confundir silenciar errores con arreglarlos.

Un test demuestra que un camino concreto funciona con unos datos concretos. El análisis estático demuestra algo distinto: que ningún camino del código viola los tipos que tú mismo declaraste. No sustituye a los tests; cubre justo el hueco que ellos dejan.

Lo que los tests no ejecutan #

PHP comprueba los tipos cuando la línea se ejecuta. Con declare(strict_types=1), que viste en tipado estricto, pasar null a un parámetro string lanza un TypeError, pero solo si esa línea llega a correr con ese valor. Si la rama es rara, un abono, una factura sin email o un error de red, tus tests probablemente no la recorren y el fallo espera a producción.

Un analizador estático no ejecuta nada. Lee el código, deduce el tipo de cada expresión en cada rama y te avisa cuando dos piezas no encajan. Es lo más parecido a un compilador que tiene PHP, y por eso pide algo a cambio: tipos declarados. Cuanto mejor tipado está el código, más ve.

Qué encuentra PHPStan #

Este servicio tiene dos fallos. Invoice::customerEmail() devuelve ?string, porque hay clientes sin email, y el método de los abonos tiene una errata. Un test con una factura normal y un email pasa en verde:

php · ReminderSender.php (antes) 
<?php

declare(strict_types=1);

final class ReminderSender
{
    public function recipientFor(Invoice $invoice): string
    {
        return strtolower($invoice->customerEmail());
    }

    public function amountFor(Invoice $invoice): string
    {
        if ($invoice->totalInCents() < 0) {
            return number_format($invoice->totalInCent() / 100, 2);
        }

        return number_format($invoice->totalInCents() / 100, 2);
    }
}

PHPStan los encuentra sin que exista un solo test:

bash · vendor/bin/phpstan analyse (nivel 8) 
 ------ -------------------------------------------------------------
  Line   ReminderSender.php
 ------ -------------------------------------------------------------
  9      Parameter #1 $string of function strtolower expects string,
         string|null given.
         🪪  argument.type
  15     Call to an undefined method Invoice::totalInCent().
         🪪  method.notFound
 ------ -------------------------------------------------------------

 [ERROR] Found 2 errors

Fíjate en la última línea de cada error: argument.type y method.notFound son sus identificadores. Volverán cuando toque ignorar algo. La corrección no es un cast ni un @var que tape el null: es decidir qué pasa cuando no hay email.

php · ReminderSender.php (después) 
<?php

declare(strict_types=1);

final class ReminderSender
{
    public function recipientFor(Invoice $invoice): ?string
    {
        $email = $invoice->customerEmail();

        if ($email === null) {
            return null;
        }

        return strtolower($email);
    }

    public function amountFor(Invoice $invoice): string
    {
        return number_format($invoice->totalInCents() / 100, 2);
    }
}

Ahora quien llama a recipientFor() recibe un ?string y PHPStan le obligará a tratar el null también. El problema sube hasta quien puede decidir.

Los niveles, de uno en uno #

PHPStan 2.x tiene niveles del 0 al 10, y cada uno incluye todos los anteriores. Existen porque un proyecto con años de historia en el nivel máximo devuelve miles de errores, y nadie arregla miles de errores un martes.

NivelQué añade
0Clases y funciones desconocidas, métodos desconocidos sobre $this, número de argumentos
1Variables que quizá no están definidas, métodos y propiedades mágicos
2Métodos desconocidos sobre cualquier expresión, no solo $this; PHPDoc válido
3–4Tipos de retorno y de propiedades; código muerto y comparaciones siempre ciertas o falsas
5Tipos de los argumentos que pasas a funciones y métodos
6Tipos que faltan en firmas y propiedades
7Uniones parcialmente incorrectas
8Nulos: llamar o pasar algo que puede ser null
9–10mixed explícito (9) y también el implícito, lo que no tiene tipo declarado (10)

El ejemplo anterior lo demuestra: con nivel 1 PHPStan no ve la errata, porque no se llama sobre $this; con nivel 2 la ve, y el null no aparece hasta el 8. La estrategia es empezar en el nivel más alto que ya pasa limpio, y subir de uno en uno. Cada salto se pide en un PR propio, el pipeline impide volver atrás, y el nivel 6 suele ser el que más trabajo da, porque pide tipar lo que nunca se tipó. Para los arrays, eso pasa por los tipos en PHPDoc de generics vía PHPDoc.

phpstan.neon #

El nivel y las rutas viven en un fichero versionado, no en la línea de comandos: así tu máquina, la de tu compañera y el CI analizan lo mismo. El formato es NEON, muy parecido a YAML.

neon · phpstan.neon 
includes:
    - phpstan-baseline.neon

parameters:
    level: 6
    paths:
        - src
        - tests

paths dice qué se analiza; los tests también son código y también se rompen. includes carga otros ficheros de configuración: el baseline, que veremos ahora, y las extensiones. Con eso, vendor/bin/phpstan analyse sin argumentos basta. Cómo encaja ese comando en el pipeline ya lo cuenta CI para PHP.

El baseline: adoptarlo sin parar #

Subir al nivel 6 en un proyecto heredado da 1.400 errores. Hay dos malas salidas: quedarse en el nivel 2 para siempre, o congelar el desarrollo un mes. El baseline es la tercera: un fichero que registra los errores que existen hoy para que PHPStan los ignore, y que solo los nuevos rompan el CI.

bash · generar el baseline 
vendor/bin/phpstan analyse --generate-baseline

Crea phpstan-baseline.neon, con una entrada por error, archivo y número de apariciones:

neon · phpstan-baseline.neon 
parameters:
	ignoreErrors:
		-
			message: '#^Call to an undefined method Invoice\:\:totalInCent\(\)\.$#'
			identifier: method.notFound
			count: 1
			path: src/ReminderSender.php

Desde ese momento el código nuevo se escribe al nivel 6 y el viejo se arregla cuando se toca. El equipo no se para.

Por qué no es un arreglo #

Cada línea del baseline es un fallo potencial que sigue en el código. El baseline no lo resuelve: lo congela. Es deuda con nombre y apellidos, y la deuda que no baja crece. Por eso PHPStan trae dos mecanismos que convierten el baseline en un trinquete, que solo gira hacia abajo:

1 Arreglas un error congeladola entrada del baseline ya no coincide con nada
2 PHPStan falla: ignore.unmatchedte obliga a borrar esa entrada
3 Si repites el mismo error en ese archivofalla con ignore.count: el contador no admite uno más

El baseline solo puede encoger. Las dos comprobaciones no se pueden ignorar.

reportUnmatchedIgnoredErrors viene activado por defecto. Apagarlo para que el CI deje de quejarse es lo que convierte el baseline en un cementerio: entradas obsoletas que nadie borra y que mañana taparán un error nuevo que coincida por casualidad.

La regla de equipo cabe en una frase: en un PR, el diff del baseline solo puede tener líneas rojas. Regenerarlo para que pase un error nuevo es escribir en el fichero de deuda sin que nadie lo decida.

Ignorar por identificador #

A veces PHPStan tiene razón en general y no en un caso concreto. Ignorarlo es legítimo, pero hay dos formas, y una envejece mal:

Por identificador

  • identifier: argument.type más una path
  • No depende del texto del mensaje
  • Renombrar una clase no lo rompe

Por mensaje

  • Una expresión regular sobre el texto
  • Cambia si cambia el nombre de una clase o el mensaje
  • Una regex amplia tapa errores que no pensabas tapar
neon · phpstan.neon 
parameters:
    ignoreErrors:
        -
            identifier: argument.type
            path: src/Legacy/*

Para una sola línea, el comentario en el propio código, con el identificador y el motivo entre paréntesis:

php · ignorar una línea 
<?php

declare(strict_types=1);

final class LegacyFormatter
{
    public function lower(?string $value): string
    {
        // @phpstan-ignore argument.type (el formulario garantiza que nunca llega null)
        return strtolower($value);
    }
}

Si un día esa línea deja de dar el error, PHPStan avisa con ignore.unmatchedIdentifier: el comentario tampoco se queda huérfano.

Extensiones de framework #

PHPStan lee código PHP, no la configuración de tu framework. No sabe qué servicio devuelve el contenedor de Symfony ni qué tipo tiene una columna de Doctrine, así que ahí ve mixed o se queja de cosas correctas. Las extensiones le enseñan esa magia:

  • phpstan/phpstan-symfony lee el contenedor compilado (containerXmlPath) y avisa si pides un servicio que no existe o es privado.
  • phpstan/phpstan-doctrine compara el mapeo de cada columna con el tipo de la propiedad y, con un objectManagerLoader, valida el DQL y deduce el tipo de sus resultados.
  • Para Laravel existe Larastan, que cumple el mismo papel con Eloquent y las facades.
neon · phpstan.neon 
includes:
    - vendor/phpstan/phpstan-symfony/extension.neon
    - vendor/phpstan/phpstan-doctrine/extension.neon
    - phpstan-baseline.neon

parameters:
    level: 6
    paths:
        - src
        - tests
    symfony:
        containerXmlPath: var/cache/dev/App_KernelDevDebugContainer.xml

Si instalas phpstan/extension-installer, esos includes se añaden solos al instalar cada extensión con Composer.

Errores típicos #

Silenciar en lugar de arreglar

  • Regenerar el baseline en cada PR. Cualquier error nuevo entra congelado y el análisis deja de proteger nada.
  • Un @var o un cast para callar un null. El error sigue ahí; solo has mentido al analizador.
  • @phpstan-ignore-next-line sin identificador. Calla cualquier error de esa línea, también los que aparezcan mañana.
  • Saltar del nivel 2 al máximo. Miles de errores, un baseline enorme y la sensación de que no sirve.
  • Analizar solo src. Los tests mal tipados ocultan fallos en los propios tests.

Cómo comprobarlo #

Antes de subir de nivel, mide cuánto cuesta sin tocar la configuración: --level en la línea de comandos manda sobre el fichero. Y vigila el tamaño del baseline como una métrica de deuda:

bash · medir antes de decidir 
vendor/bin/phpstan analyse --level=7

grep 'count:' phpstan-baseline.neon | awk '{ total += $2 } END { print total }'

Si ese número no baja de un mes a otro, el baseline ha dejado de ser un plan y se ha convertido en una alfombra.

Cuándo aplicarlo #

PHPStan en CI cuando…

  • El proyecto va a vivir más de unos meses o lo toca más de una persona
  • Vas a refactorizar o a migrar con Rector: el análisis te dice qué rompiste
  • Heredas código sin tests: es la red más barata que puedes tender

El baseline no cuando…

  • El proyecto es nuevo: empieza en el nivel alto, sin deuda que congelar
  • Solo quedan unas decenas de errores: arréglalos en un PR
  • Nadie va a revisar que encoja: entonces solo esconde

La alternativa sin baseline

En un proyecto mediano, fija el nivel que ya pasa y sube uno cada sprint arreglando lo que salga. Va más lento, pero no deja un fichero de deuda que mantener. El estilo del código, en cambio, no es cosa de PHPStan: eso lo resuelve el estilo automático.

Resumen #

Lo que te llevas

  • El análisis estático revisa todas las ramas sin ejecutarlas; los tests solo las que recorren. Se complementan.
  • Los niveles van del 0 al 10 y se suben de uno en uno, cada salto en su PR; el CI impide volver atrás.
  • phpstan.neon fija nivel, rutas e includes para que todos analicen lo mismo.
  • El baseline congela la deuda para adoptar PHPStan sin parar; no la arregla, y su diff en un PR solo puede restar.
  • No apagues reportUnmatchedIgnoredErrors: es lo que obliga a que el baseline encoja.
  • Ignora por identificador y con motivo, nunca por mensaje ni con un ignore genérico.
