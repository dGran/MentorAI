Desarrollo local con la CLI: migraciones, entornos y tipos

Cambiar el esquema con clics en el panel de producción funciona hasta el primer día en que algo se rompe y nadie sabe qué cambió. La CLI de Supabase te da lo que tiene cualquier proyecto serio: todo el stack en local, el esquema en ficheros versionados y un camino repetible hasta producción.

En el primer proyecto creaste la tabla de notas en el SQL Editor de la nube. Esta lección convierte ese SQL en una migración, la ejecuta en un Supabase local y la lleva a producción con un comando que también puede lanzar tu CI.

Por qué no basta con el panel #

El panel es cómodo, pero un cambio hecho con clics tiene tres problemas: no queda en git, no se revisa en un PR y no se puede repetir igual en otro entorno. El día que tengas un proyecto de pruebas y otro de producción, mantenerlos idénticos a mano es imposible.

La solución es la misma que en cualquier backend (la cuenta Migraciones de esquema): cada cambio de esquema es un fichero SQL con fecha, que se aplica en orden y una sola vez por entorno. Supabase guarda en cada base de datos qué migraciones ya se aplicaron, en la tabla supabase_migrations.schema_migrations.

Supabase entero en tu máquina #

La CLI levanta en contenedores Docker los mismos servicios de la plataforma: Postgres, Auth, Data API, Storage, Realtime, Edge Functions, Studio y un servidor de correo falso para ver los emails de registro sin enviarlos.

bash · arrancar un proyecto local 
npx supabase init
npx supabase start

init crea la carpeta supabase/ con su config.toml. start descarga las imágenes la primera vez (tarda) y al terminar imprime las direcciones y las claves locales:

bash · salida de supabase start (resumida) 
API URL: http://127.0.0.1:54321
DB URL: postgresql://postgres:postgres@127.0.0.1:54322/postgres
Studio URL: http://127.0.0.1:54323
Mailpit URL: http://127.0.0.1:54324
Publishable key: sb_publishable_...
Secret key: sb_secret_...
PuertoServicioPara qué lo usas
54321Pasarela de APILo que pones como URL en createClient en desarrollo
54322Postgrespsql, tu IDE de base de datos, PDO
54323StudioEl mismo panel que en la nube, contra tu base de datos local

Las claves locales son fijas y públicas: no protegen nada porque la base de datos solo existe en tu máquina. supabase stop lo para todo, conservando los datos.

Instálala en el proyecto

npx supabase funciona sin instalar nada, pero conviene fijar la versión de la CLI como dependencia de desarrollo del proyecto (o en la imagen de CI): dos personas con versiones distintas pueden generar migraciones distintas a partir del mismo cambio.

Escribir migraciones #

Una migración nueva es un fichero vacío con marca de tiempo en el nombre:

bash · crear una migración 
npx supabase migration new create_notes
bash · resultado 
supabase/migrations/20261115093000_create_notes.sql

Dentro va el SQL de la tabla de notas de la lección anterior. Para aplicarlo hay dos comandos, y la diferencia importa:

ComandoQué haceCuándo
supabase migration upAplica solo las migraciones pendientesTras crear una migración nueva
supabase db resetBorra la base de datos local, aplica todas las migraciones desde cero y carga supabase/seed.sqlPara comprobar que el historial completo funciona y volver a un estado limpio

db reset es tu mejor test: si una base de datos vacía no llega al esquema actual aplicando las migraciones en orden, producción tampoco llegaría si mañana tuvieras que recrearla.

Los datos de prueba van en el seed

supabase/seed.sql se ejecuta tras las migraciones en cada db reset local, y nunca en producción. Es el sitio para las libretas y notas de ejemplo con las que desarrollas. Los datos que sí deben existir en todos los entornos (una lista de categorías, por ejemplo) van en una migración.

Cambios hechos en el Studio local

Si prefieres diseñar con el Table Editor local, la CLI puede escribir la migración por ti comparando la base de datos local con lo que dicen las migraciones:

bash · generar la migración a partir de los cambios 
npx supabase db diff -f add_notebooks

Revisa siempre el fichero generado. Un diff detecta qué cambió, no cómo querías hacerlo: renombrar una columna puede salir como «borrar columna y crear otra», que en producción es perder los datos de esa columna.

Llevarlo a producción #

La CLI se conecta con tu cuenta y se enlaza a un proyecto de la nube:

bash · enlazar y desplegar 
npx supabase login
npx supabase link --project-ref abcdefghijklmnop
npx supabase migration list
npx supabase db push

migration list enseña en dos columnas qué migraciones hay en local y cuáles se aplicaron en remoto. db push aplica en el proyecto remoto las que faltan, en orden.

La deriva: cuando alguien tocó producción a mano

Si alguien cambió el esquema de producción con el panel, tus migraciones ya no describen la realidad. supabase db pull trae ese cambio como una migración nueva para que vuelva a estar en git. Lo sano es que el panel de producción sea de solo lectura para el esquema: cada cambio, por migración y PR.

En CI el mismo flujo se automatiza. Un ejemplo con GitHub Actions que aplica las migraciones al hacer merge en main:

yaml · .github/workflows/supabase.yml 
name: Migraciones
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    env:
      SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
      SUPABASE_DB_PASSWORD: ${{ secrets.SUPABASE_DB_PASSWORD }}
    steps:
      - uses: actions/checkout@v4
      - uses: supabase/setup-cli@v1
        with:
          version: latest
      - run: supabase link --project-ref ${{ vars.SUPABASE_PROJECT_REF }}
      - run: supabase db push

En un proyecto real, fija version a la versión que usáis en local en vez de latest. Y una migración que se aplica mientras la versión anterior de la app sigue sirviendo tiene que ser compatible con las dos: añadir una columna, sí; renombrarla de golpe, no. Migraciones sin caída cuenta cómo partir los cambios peligrosos.

Tipos de TypeScript generados del esquema #

La CLI lee el esquema y genera los tipos de cada tabla, vista y función:

bash · generar tipos 
npx supabase gen types typescript --local > src/database.types.ts
ts · cliente tipado 
import { createClient } from "@supabase/supabase-js";
import type { Database } from "./database.types";

const supabase = createClient<Database>(url, publishableKey);

const { data } = await supabase.from("notes").select("id, title");

Con el cliente tipado, data sabe que cada nota tiene id: number y title: string, y un select("titel") mal escrito falla al compilar en vez de en producción. Regenera los tipos en cada migración; muchos equipos lo comprueban en CI.

Otra forma: esquemas declarativos #

Las migraciones describen los pasos: crea esta tabla, añade esta columna. Los esquemas declarativos describen el resultado: en supabase/schemas/ escribes cómo debe quedar cada tabla, y la CLI calcula la migración que lleva la base de datos de su estado actual a ese.

Migraciones a mano

  • Controlas exactamente qué SQL corre en producción
  • Renombrados, movimientos de datos y cambios delicados se escriben como quieres
  • El estado actual de una tabla se reconstruye leyendo muchos ficheros

Esquemas declarativos

  • Cada tabla se lee en un solo fichero, como está hoy
  • Las migraciones se generan solas
  • Hay cosas que el diff no captura: datos (insert, update), objetos de auth y storage y algunos tipos de objeto, que siguen yendo en migraciones

Los dos caminos acaban en lo mismo: ficheros en supabase/migrations/ que db push aplica. La herramienta declarativa ha cambiado de comandos y de motor de diff más de una vez; consulta la guía «Declarative database schemas» de la documentación antes de adoptarla.

Entornos y ramas de previsualización #

El montaje mínimo sano tiene tres entornos con el mismo historial de migraciones:

1 Localsupabase start, datos del seed, se rompe y se rehace sin miedo
2 Pruebasun proyecto de Supabase aparte, con datos falsos
3 Producciónotro proyecto, nunca compartido con pruebas

Cada flecha es el mismo comando contra otro destino: las migraciones son las mismas en los tres.

Supabase ofrece además Branching: al abrir un PR en GitHub crea un entorno temporal con sus propias migraciones aplicadas y su seed, para probar la rama de verdad, y lo borra al cerrar el PR. Cada rama se cobra por horas de cómputo, así que compensa cuando hay varias personas revisando cambios de esquema a la vez.

Pruebas y producción en el mismo proyecto

Usar un único proyecto con tablas notes_test o un esquema de pruebas es tentador para ahorrar, y mezcla usuarios, ficheros, claves y logs de los dos mundos. Un proyecto gratuito de pruebas cuesta cero; un borrado accidental en producción, mucho más.

Errores típicos #

  • Editar una migración ya aplicada. El entorno donde ya corrió no la vuelve a ejecutar, así que los entornos divergen en silencio. Una migración aplicada no se toca: se escribe otra.
  • Datos de prueba en migraciones. Acaban en producción. Van en seed.sql.
  • **Secretos en config.toml.** El fichero va a git. Los valores sensibles (claves de proveedores OAuth, SMTP) se leen de variables de entorno con env(NOMBRE).
  • **Confiar en db diff sin leerlo.** Un renombrado puede salir como borrar y crear.
  • **No probar db reset nunca.** El día que lo necesitas descubres que una migración antigua dependía de algo hecho a mano.

Cuándo aplicarlo #

Usa CLI y migraciones desde el primer día si…

  • Hay o va a haber más de un entorno
  • Más de una persona toca el esquema
  • Quieres revisar los cambios de base de datos en un PR como el resto del código
  • Tu CI tiene que desplegar backend y frontend juntos

Puedes esperar si…

  • Es un prototipo de una tarde que vas a tirar
  • Solo estás explorando qué hace Supabase

Resumen #

Lo que te llevas

  • supabase start levanta todo el stack en local con Docker: API en el 54321, Postgres en el 54322, Studio en el 54323 y los emails en el 54324.
  • Cada cambio de esquema es un fichero en supabase/migrations/; migration up aplica lo pendiente y db reset reconstruye desde cero con el seed.
  • link y db push llevan las migraciones a un proyecto remoto; db pull recupera cambios hechos a mano en el panel.
  • gen types typescript convierte el esquema en tipos y hace que los errores de nombres fallen al compilar.
  • Los esquemas declarativos generan las migraciones a partir del estado deseado, pero datos y objetos de auth y storage siguen en migraciones.
  • Local, pruebas y producción son proyectos distintos con el mismo historial de migraciones.
