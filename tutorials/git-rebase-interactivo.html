Rebase interactivo: dejar el historial legible

Tu rama funciona, pero su historial cuenta cómo trabajaste, no qué cambiaste. Con git rebase -i juntas, renombras, reordenas y tiras commits antes de que nadie los herede, y aquí ves también cómo salir de un conflicto a mitad y cómo deshacer un rebase que salió mal.

Commitear a menudo te protege mientras trabajas, pero deja un rastro de «wip», «quita var_dump» y «ahora sí». El rebase interactivo convierte ese diario de trabajo en una historia que se lee: cada commit, un cambio con sentido. Todas las salidas de esta lección son reales, de git 2.53.

El historial que nadie lee #

El historial no es para ti hoy: es para quien revise tu PR, para quien haga git blame dentro de un año y para quien busque un fallo con git bisect. A los tres les estorban los pasos intermedios: un commit que mete un var_dump y otro que lo quita obligan a leer dos diffs para entender cero cambios, y un «wip» que no pasa los tests hace que bisect señale al culpable equivocado.

Un buen commit es una unidad: un cambio con su motivo, que deja el proyecto funcionando. El rebase interactivo es la herramienta para pasar de uno a otro, y como reescribe commits (hashes nuevos), la regla de oro del rebase aplica tal cual: solo sobre commits que únicamente tienes tú.

La lista de tareas #

git rebase -i main no toca nada al principio: abre tu editor con los commits que tu rama tiene y main no, uno por línea y con una acción delante. Al guardar y cerrar, Git lleva la rama a la base y vuelve a aplicar la lista de arriba abajo, obedeciendo cada acción. Reescribir el historial es editar ese fichero de texto.

AcciónQué hace con el commit
pick (p)Lo aplica tal cual.
reword (r)Lo aplica y te abre el editor para cambiar solo el mensaje.
edit (e)Lo aplica y se detiene: corriges con git commit --amend y sigues con git rebase --continue.
squash (s)Lo funde con el de la línea de encima y te deja combinar los dos mensajes.
fixup (f)Lo funde con el de encima y descarta su mensaje.
drop (d)Lo descarta. Borrar la línea hace lo mismo.
Mover la líneaCambia el orden en que se aplican los commits.

La lista va al revés que git log

git log pone arriba el commit más reciente; la lista de tareas, el más antiguo, porque es el orden en que se van a aplicar. Por eso squash y fixup funden con la línea de encima: el commit anterior en el tiempo.

Limpiar una rama #

Una rama feature/descuento tras una tarde normal:

bash · el historial de trabajo 
$ git log --oneline main..
16de30a quita var_dump
271b95a script para probar
c2c3be4 test: cover Descuento
ad112ad wip
1668dd9 feat: add Descuento

El primer commit entró con una traza de depuración que el último retira. Quien lea 1668dd9 verá código que nunca debió existir:

php · src/Descuento.php en 1668dd9 (antes) 
<?php

declare(strict_types=1);

final class Descuento
{
    public function aplicar(Precio $precio, int $porcentaje): Precio
    {
        var_dump($porcentaje);

        return new Precio(intdiv($precio->centimos * (100 - $porcentaje), 100));
    }
}

El plan: fundir la retirada del var_dump con su origen (fixup), tirar el script de pruebas (drop) y juntar «wip» con el test que lo completa (squash). Aquí la lista se edita con GIT_SEQUENCE_EDITOR, la variable que decide qué programa abre la lista de tareas, para que la salida sea reproducible; en tu día a día se abre tu editor.

bash · la lista, antes y después de editarla 
# Lo que abre git rebase -i main
pick 1668dd9 # feat: add Descuento
pick ad112ad # wip
pick c2c3be4 # test: cover Descuento
pick 271b95a # script para probar
pick 16de30a # quita var_dump

# Lo que guardas
pick 1668dd9 feat: add Descuento
fixup 16de30a quita var_dump
drop 271b95a script para probar
pick ad112ad wip
squash c2c3be4 test: cover Descuento

Al llegar al squash, Git abre el editor con los dos mensajes («This is a combination of 2 commits») y te quedas con uno. El resultado:

bash · salida real del rebase 
$ git rebase -i main
[detached HEAD 93091c7] test: cover Descuento
 Date: Mon Oct 12 10:00:00 2026 +0200
 1 file changed, 15 insertions(+)
 create mode 100644 tests/DescuentoTest.php
Successfully rebased and updated refs/heads/feature/descuento.

$ git log --oneline main..
93091c7 test: cover Descuento
9848aee feat: add Descuento

Dos commits que se revisan de un vistazo. Fíjate en que 1668dd9 ahora es 9848aee: el contenido cambió, así que es otro commit, y el viejo solo sigue alcanzable por el reflog.

fixup y --autosquash #

La revisión pide validar el porcentaje. Ese cambio pertenece a «feat: add Descuento», no a un commit nuevo, y la forma cómoda es marcarlo al commitear en vez de recordarlo después:

bash · el fixup se coloca solo 
$ git commit -a --fixup=9848aee
[feature/descuento 4bdd306] fixup! feat: add Descuento
 1 file changed, 4 insertions(+)

$ git rebase -i --autosquash main
# La lista llega ya ordenada; solo guardas
pick 9848aee # feat: add Descuento
fixup 4bdd306 # fixup! feat: add Descuento
pick 93091c7 # test: cover Descuento
Successfully rebased and updated refs/heads/feature/descuento.

--fixup=<sha> crea un commit titulado fixup! <título del original>, y --autosquash lo coloca bajo su destino con la acción fixup: solo te queda guardar. Para cambiar el mensaje existen --fixup=reword:<sha> (solo el mensaje) y --fixup=amend:<sha> (contenido y mensaje), que la lista convierte en fixup -C. El commit queda así, ya con la validación y sin rastro de depuración:

php · src/Descuento.php en el commit limpio (después) 
<?php

declare(strict_types=1);

final class Descuento
{
    public function aplicar(Precio $precio, int $porcentaje): Precio
    {
        if ($porcentaje < 0 || $porcentaje > 100) {
            throw new InvalidArgumentException("Porcentaje fuera de rango: {$porcentaje}");
        }

        return new Precio(intdiv($precio->centimos * (100 - $porcentaje), 100));
    }
}

Para no escribir --autosquash cada vez, actívalo en la configuración:

ini · ~/.gitconfig 
[rebase]
    autoSquash = true

rebase.autoSquash solo actúa con -i

Con la opción activada, un git rebase main sin -i deja los fixup! tal cual; pasar --autosquash a mano sí los funde también sin -i. Lo comprobamos con los dos comandos: si un día ves un fixup! en la PR, es esto.

Un conflicto a mitad #

Reordenar commits que tocan las mismas líneas obliga a Git a aplicar cada uno sobre un código que no conocía. La rama tiene «fix: round instead of truncating» y, encima, «refactor: name the percentage total», que cambia la misma línea. Al invertir su orden:

bash · el rebase se detiene (salida recortada) 
CONFLICT (content): Merge conflict in src/Descuento.php
error: could not apply 5feffa7... refactor: name the percentage total

$ git status
interactive rebase in progress; onto cef59f6
Next command to do (1 remaining command):
   pick 136ab09 # fix: round instead of truncating

$ grep -A4 '<<<<' src/Descuento.php
<<<<<<< HEAD
        return new Precio(intdiv($precio->centimos * (100 - $porcentaje), 100));
=======
        return new Precio((int) round($precio->centimos * (self::PORCENTAJE_TOTAL - $porcentaje) / self::PORCENTAJE_TOTAL));
>>>>>>> 5feffa7 (refactor: name the percentage total)

Ojo al sentido: en un rebase, HEAD es la rama que se está reconstruyendo y el otro lado es tu commit. Aquí lo correcto es la constante con intdiv, porque el redondeo llega en el siguiente commit. Editas, git add src/Descuento.php y git rebase --continue; y como el otro commit toca la misma línea, el siguiente paso vuelve a parar. Mover dos commits que se pisan cuesta un conflicto por cada uno.

Si te ves perdido, git rebase --abort devuelve la rama al estado de antes de empezar, incluido lo que ya hubieras resuelto:

bash · volver atrás a mitad 
$ git rebase --abort
$ git log --oneline main..
5feffa7 refactor: name the percentage total
136ab09 fix: round instead of truncating
54eeabb test: cover Descuento
7cd19b4 feat: add Descuento

Deshacer un rebase #

--abort solo sirve mientras el rebase está en curso. Repetimos el reordenado y resolvimos el segundo conflicto con git checkout --theirs, a toda prisa: el rebase terminó con «Successfully rebased», pero git diff feature/descuento@{1} enseñó que la constante había desaparecido. Ese lado era el commit del redondeo, anterior al refactor.

La salida es el reflog. El de la rama apunta una sola entrada por rebase, así que @{1} es justo el estado de antes:

bash · volver al estado previo al rebase 
$ git reflog -2 feature/descuento
b69ada3 feature/descuento@{0}: rebase (finish): refs/heads/feature/descuento onto cef59f68307332afa6375e05056e9695f4f0f842
5feffa7 feature/descuento@{1}: commit: refactor: name the percentage total

$ git reset --hard feature/descuento@{1}
HEAD is now at 5feffa7 refactor: name the percentage total

El reflog de HEAD (git reflog a secas) también sirve, pero apunta una entrada por cada paso del rebase: busca la línea justo debajo de rebase (start). Justo al terminar, ORIG_HEAD también señala el estado previo, aunque el siguiente reset lo sobrescribe.

Errores típicos #

Los que más historial han roto

  • Reescribir una rama que otros ya tienen. Si es solo tuya y ya está subida, publícala con git push --force-with-lease, que se niega si el remoto cambió desde la última vez que lo trajiste.
  • Leer la lista como git log. El squash acaba fundido con el commit equivocado.
  • Resolver con --ours o --theirs a ciegas. En un rebase el sentido es el contrario al de un merge, y quedarse un lado entero se come los cambios del otro sin un solo aviso.
  • Borrar una línea «para luego». Equivale a drop; la propia lista lo advierte: «If you remove a line here THAT COMMIT WILL BE LOST».
  • Empezar con cambios sin commitear. Git se niega («cannot rebase: You have unstaged changes»): commitea o haz stash antes.

Cómo comprobarlo #

Limpiar no debería cambiar el resultado. Si solo has reordenado, fundido o renombrado, git diff feature/descuento@{1} sale vacío; si tiraste algo a propósito, solo aparece eso. Para revisar commit a commit, git range-diff empareja la versión vieja y la nueva:

bash · tras un reword 
$ git range-diff main feature/descuento@{1} feature/descuento
1:  7cd19b4 = 1:  7cd19b4 feat: add Descuento
2:  54eeabb = 2:  54eeabb test: cover Descuento
3:  136ab09 ! 3:  22925e8 fix: round instead of truncating
    @@ Metadata
     Author: Ana <ana@example.com>
     
      ## Commit message ##
    -    fix: round instead of truncating
    +    fix: round discounts to the nearest cent
     
      ## src/Descuento.php ##
     @@ src/Descuento.php: final class Descuento
4:  5feffa7 = 4:  d4eedbb refactor: name the percentage total

= significa mismo cambio y !, que algo difiere. Y para asegurar que cada commit deja el proyecto en pie, que es lo que necesita bisect, --exec mete un comando tras cada pick y para el rebase si falla:

bash · los tests en cada commit 
git rebase -i --exec "vendor/bin/phpunit" main

Cuándo aplicarlo #

Limpia con rebase -i cuando…

  • La rama es solo tuya y vas a abrir la PR: que el revisor lea cambios, no tu proceso
  • El repositorio integra con merge commit o rebase merge: cada commit llega a main y lo leerán blame y bisect
  • La revisión pide cambios a un commit concreto: --fixup y --autosquash los dejan donde tocan

No te compensa cuando…

  • La rama la comparten varias personas: reescribirla rompe su copia
  • El repositorio integra con squash merge: main recibe un solo commit (por defecto, con el título de la PR) y tus commits intermedios se pierden igualmente
  • Solo hay que corregir el último commit: git commit --amend es más corto

La pregunta es quién va a leer tus commits. Si llegan a main uno a uno, límpialos antes de la PR. Si el equipo hace squash merge, el squash ya hace la limpieza final; pulir el historial solo compensa si la PR es grande y se revisa commit a commit.

Resumen #

Lo que te llevas

  • git rebase -i abre una lista de tareas, del commit más antiguo al más reciente: pick, reword, edit, squash, fixup, drop y el orden de las líneas.
  • git commit --fixup=<sha> más --autosquash coloca cada corrección bajo su commit; rebase.autoSquash lo activa solo en rebases interactivos.
  • Ante un conflicto: resuelve, git add y --continue, o --abort para volver al principio. En un rebase, HEAD es lo ya reconstruido.
  • Un rebase terminado se deshace con git reset --hard rama@{1}, y git diff rama@{1} te dice si la limpieza cambió algo que no debía.
  • Limpia antes de la PR si los commits llegan a main uno a uno; con squash merge, el squash ya lo hace por ti.
