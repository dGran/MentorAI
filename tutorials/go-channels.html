Channels: comunicación entre goroutines

El lema del equipo de Go: «Do not communicate by sharing memory; instead, share memory by communicating». Los channels son la implementación de ese lema: tuberías tipadas que permiten enviar datos entre goroutines sin necesidad de locks explícitos.

Lanzar goroutines es fácil; lo difícil es que se pasen datos y se avisen sin pisarse. Los channels son la respuesta de Go: en vez de proteger una variable compartida con un lock, una goroutine le entrega el dato a otra y ese traspaso ya es la sincronización. Bien usados, el flujo del programa se lee en el propio código.

Qué es un channel #

Un channel es una tubería tipada con dos extremos: quien envía (<-ch) y quien recibe (ch <-). Sincroniza automáticamente el acceso: si el receptor llega antes que el emisor, espera. Si el emisor llega antes, espera. Así se evitan race conditions sin locks.

go 
// Crear un channel de strings (sin buffer)
mensajes := make(chan string)

// Enviar en una goroutine
go func() {
    mensajes <- "hola"   // bloquea hasta que alguien reciba
}()

// Recibir en la goroutine actual
msg := <-mensajes   // bloquea hasta que alguien envíe
fmt.Println(msg)    // "hola"

Channels sin buffer #

El channel sin buffer es el más simple y el que garantiza sincronización más estricta: el envío bloquea hasta que hay un receptor, y el receptor bloquea hasta que hay un emisor. Son un punto de encuentro (rendezvous).

go 
func calcular(resultado chan<- int) {   // chan<-: solo puede enviar
    resultado <- 42
}

func main() {
    ch := make(chan int)

    go calcular(ch)

    valor := <-ch       // espera a que calcular envíe
    fmt.Println(valor)  // 42
}

Los tipos direccionales (chan<- y <-chan) documentan la intención y el compilador los verifica:

go 
// solo puede enviar
func productor(ch chan<- int) {
    ch <- 1
}

// solo puede recibir
func consumidor(ch <-chan int) {
    v := <-ch
    fmt.Println(v)
}

ch := make(chan int)
go productor(ch)
consumidor(ch)

Channels con buffer #

Un channel con buffer puede almacenar N valores sin bloquear al emisor. El emisor solo bloquea cuando el buffer está lleno; el receptor solo bloquea cuando el buffer está vacío.

go 
// buffer de 3 elementos
ch := make(chan int, 3)

ch <- 1   // no bloquea (buffer tiene espacio)
ch <- 2   // no bloquea
ch <- 3   // no bloquea
// ch <- 4   // BLOQUEARÍA: buffer lleno

fmt.Println(<-ch)   // 1
fmt.Println(<-ch)   // 2
fmt.Println(<-ch)   // 3

Los channels con buffer son útiles para desacoplar productores de consumidores cuando tienen velocidades distintas, y en el patrón worker pool que vimos en la lección anterior.

Range y close #

Iterar un channel con range recibe valores hasta que el channel se cierra:

go 
func generarNumeros(ch chan<- int, max int) {
    for i := 0; i < max; i++ {
        ch <- i
    }
    close(ch)   // señala que no hay más valores
}

ch := make(chan int)
go generarNumeros(ch, 5)

for n := range ch {   // recibe hasta que ch se cierra
    fmt.Println(n)    // 0, 1, 2, 3, 4
}

Reglas del close:

  • Solo el emisor cierra el channel, nunca el receptor.
  • Cerrar un channel ya cerrado provoca un panic.
  • Enviar a un channel cerrado provoca un panic.
  • Recibir de un channel cerrado devuelve el zero value del tipo inmediatamente.

Para distinguir un valor real de un zero value de channel cerrado:

go 
valor, abierto := <-ch

if !abierto {
    fmt.Println("channel cerrado")
    return
}

fmt.Println("valor recibido:", valor)

Select: multiplexar channels #

select es como un switch para channels: ejecuta el primer caso que esté listo. Si varios están listos, elige uno al azar.

go 
func main() {
    ch1 := make(chan string)
    ch2 := make(chan string)

    go func() { ch1 <- "uno" }()
    go func() { ch2 <- "dos" }()

    for i := 0; i < 2; i++ {
        select {
        case msg1 := <-ch1:
            fmt.Println("de ch1:", msg1)
        case msg2 := <-ch2:
            fmt.Println("de ch2:", msg2)
        }
    }
}

El caso default en un select hace que no bloquee (non-blocking channel operations):

go 
select {
case msg := <-ch:
    fmt.Println("recibido:", msg)
default:
    fmt.Println("nada disponible, continúo")
}

Patrones habituales #

Done channel: señalar a una goroutine que debe detenerse:

go 
func trabajar(done <-chan struct{}) {
    for {
        select {
        case <-done:
            fmt.Println("deteniendo")
            return
        default:
            // continuar trabajo
            fmt.Println("trabajando...")
        }
    }
}

done := make(chan struct{})
go trabajar(done)

// Cuando quieras detener:
close(done)   // todas las goroutines que escuchen done se enteran

chan struct{} es idiomático para señales que no llevan datos: struct{}{} ocupa 0 bytes.

Fan-out: distribuir trabajo a múltiples goroutines desde un channel:

go 
trabajos := make(chan int, 100)

for i := 0; i < 5; i++ {   // 5 workers leyendo del mismo channel
    go func() {
        for id := range trabajos {
            procesar(id)
        }
    }()
}

for i := 0; i < 100; i++ {
    trabajos <- i
}
close(trabajos)

Errores típicos con channels

  • Enviar a un channel que nadie va a leer. En uno sin buffer, el envío se queda bloqueado para siempre y la goroutine con él. Pasa mucho cuando el receptor sale antes por un error o un timeout: o das buffer suficiente, o el emisor también escucha un done o ctx.Done() en un select.
  • Cerrar desde el receptor, o cerrar dos veces. Cerrar dos veces da panic al instante. Cerrar desde el receptor no falla por sí mismo, pero el emisor no se entera y su siguiente envío al channel cerrado sí provoca panic. Cierra quien envía, y si hay varios emisores, cierra una única goroutine coordinadora después de esperarlos con un WaitGroup.
  • Un select con default dentro de un for sin nada que espere. El bucle gira sin parar y se come un core al 100 %. El default sirve para no bloquear una vez, no para esperar.
  • Usar un channel que vale nil. Si se declara con var ch chan int y nunca se hace make, enviar o recibir se bloquea para siempre, sin error.

Cuándo aplicarlo #

La duda real no es si usar channels, sino channel o mutex. El criterio: ¿estás pasando datos o un aviso de una goroutine a otra, o protegiendo un estado que varias consultan?

Usa un channel cuando…

  • Hay un flujo de trabajo: un productor genera tareas y uno o varios consumidores las procesan
  • Quieres repartir trabajo entre N workers o juntar sus resultados (fan-out / fan-in)
  • Necesitas señalar un evento: «para», «ya está listo», «ha vencido el tiempo» (con select)
  • Quieres limitar la concurrencia: un channel con buffer de N hace de semáforo

Usa otra cosa cuando…

  • Solo proteges un contador, un mapa o una caché que varias goroutines leen y escriben: sync.Mutex es más simple y más rápido
  • Solo esperas a que un grupo termine, sin recoger resultados: sync.WaitGroup
  • La cancelación debe cruzar varias capas del programa: context.Context, que por dentro ya es un channel
  • Todo ocurre en una sola goroutine: un channel ahí solo añade bloqueos posibles

Si al dibujar el diseño te salen cinco channels cruzados para un problema sencillo, probablemente era un mutex.

Resumen #

Lo que te llevas

  • Un channel es una tubería tipada: make(chan T) sin buffer, make(chan T, n) con buffer de n elementos.
  • Sin buffer: el envío bloquea hasta que hay receptor, y viceversa. Sincronización estricta (rendezvous).
  • Con buffer: el envío no bloquea mientras haya espacio; el receptor no bloquea mientras haya elementos.
  • close(ch) señala que no hay más valores. Solo el emisor cierra; iterar con range para sobre el close.
  • select multiplexa operaciones sobre varios channels: ejecuta el primer caso listo.
  • chan struct{} con close es el patrón idiomático para señales de cancelación o done.
