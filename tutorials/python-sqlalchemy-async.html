SQLAlchemy 2 async con PostgreSQL

SQLAlchemy 2 integra soporte async nativo. Aprenderás a configurar el engine y la session factory, definir modelos declarativos con la API moderna de Mapped, construir queries composicionales con select(), manejar relaciones sin romper el event loop, y gestionar el esquema con Alembic.

Engine async y session factory

El engine es el punto de entrada a la base de datos. La variante async usa asyncpg como driver de PostgreSQL, que implementa el protocolo de BD sin bloquear el event loop. Primero instalamos las dependencias:

pip install sqlalchemy asyncpg alembic

A continuación se configura el engine y la fábrica de sesiones. expire_on_commit=False evita que SQLAlchemy invalide los atributos de los objetos al hacer commit, lo que en async causaría accesos adicionales a BD desde fuera de la sesión:

from sqlalchemy.ext.asyncio import AsyncSession, create_async_engine, async_sessionmaker

DATABASE_URL = "postgresql+asyncpg://usuario:password@localhost:5432/mi_base"

engine = create_async_engine(DATABASE_URL, echo=True, pool_size=10, max_overflow=20)

SessionFactory = async_sessionmaker(
    engine,
    class_=AsyncSession,
    expire_on_commit=False,
)

En un proyecto FastAPI, la sesión se inyecta por petición mediante un generador async. Cada petición obtiene su propia sesión y la cierra al terminar, ya sea con éxito o con error:

from collections.abc import AsyncGenerator
from fastapi import Depends


async def obtener_sesion() -> AsyncGenerator[AsyncSession, None]:
    async with SessionFactory() as session:
        yield session


async def crear_usuario(
    session: AsyncSession = Depends(obtener_sesion),
) -> dict:
    ...

async with SessionFactory() as session abre la sesión y la cierra automáticamente al salir del bloque, con o sin excepción. No hace falta llamar a session.close() manualmente.

Modelos declarativos con DeclarativeBase

SQLAlchemy 2 introduce DeclarativeBase y la API Mapped[T] para declarar columnas con anotaciones de tipo estándar. Esto permite que los type checkers comprendan el esquema sin plugins adicionales:

from datetime import datetime
from sqlalchemy import String, DateTime, func
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    pass


class Usuario(Base):
    __tablename__ = "usuarios"

    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(255), unique=True, nullable=False)
    nombre: Mapped[str] = mapped_column(String(100))
    activo: Mapped[bool] = mapped_column(default=True)
    creado_en: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        server_default=func.now(),
    )

Mapped[int] es equivalente a decir "esta columna es de tipo entero y no es nullable". Para columnas opcionales, usa Mapped[str | None]. El argumento de mapped_column() añade metadatos de la columna (longitud, unicidad, restricciones) que no se pueden expresar solo con el tipo.

La clase Base centraliza el metadata del esquema. Se usa para crear y eliminar tablas en tests, y como fuente de verdad para Alembic. Todos los modelos deben heredar de ella.

Queries con select(), filtros y joins

select() construye la query de forma composicional. Cada método (.where(), .order_by(), .limit()) devuelve un nuevo objeto query sin modificar el original, igual que un query builder funcional:

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession


async def buscar_por_email(session: AsyncSession, email: str) -> Usuario | None:
    resultado = await session.execute(
        select(Usuario).where(Usuario.email == email)
    )
    return resultado.scalar_one_or_none()


async def listar_activos(session: AsyncSession, limite: int = 100) -> list[Usuario]:
    resultado = await session.execute(
        select(Usuario)
        .where(Usuario.activo.is_(True))
        .order_by(Usuario.nombre)
        .limit(limite)
    )
    return list(resultado.scalars().all())

Para joins, select() acepta múltiples entidades o usa .join() explícito:

from sqlalchemy import select, and_


async def buscar_pedidos_de_usuario(
    session: AsyncSession,
    usuario_id: int,
    solo_pagados: bool = False,
) -> list[Pedido]:
    query = (
        select(Pedido)
        .join(Usuario, Pedido.usuario_id == Usuario.id)
        .where(Pedido.usuario_id == usuario_id)
    )

    if solo_pagados:
        query = query.where(Pedido.pagado.is_(True))

    resultado = await session.execute(query)
    return list(resultado.scalars().all())

El patrón repository encapsula las queries en una clase cuya única dependencia es la sesión. Esto hace que el acceso a datos sea testeable inyectando una sesión de test sin tocar los servicios:

class UsuarioRepository:
    def __init__(self, session: AsyncSession) -> None:
        self._session = session

    async def buscar_por_id(self, usuario_id: int) -> Usuario | None:
        return await self._session.get(Usuario, usuario_id)

    async def buscar_por_email(self, email: str) -> Usuario | None:
        resultado = await self._session.execute(
            select(Usuario).where(Usuario.email == email)
        )
        return resultado.scalar_one_or_none()

    async def guardar(self, usuario: Usuario) -> Usuario:
        self._session.add(usuario)
        await self._session.flush()
        return usuario

    async def eliminar(self, usuario: Usuario) -> None:
        await self._session.delete(usuario)
        await self._session.flush()

session.flush() envía los cambios pendientes a la BD dentro de la transacción actual sin hacer commit. Usar flush después de add() permite que SQLAlchemy rellene el campo id autogenerado antes de que la sesión cierre.

Relaciones y lazy loading en async

Las relaciones entre modelos se declaran con relationship() junto a la clave foránea. En la API moderna, el tipo de la relación también usa Mapped[]:

from sqlalchemy import ForeignKey, String
from sqlalchemy.orm import Mapped, mapped_column, relationship


class Pedido(Base):
    __tablename__ = "pedidos"

    id: Mapped[int] = mapped_column(primary_key=True)
    usuario_id: Mapped[int] = mapped_column(ForeignKey("usuarios.id"))
    total: Mapped[float]
    pagado: Mapped[bool] = mapped_column(default=False)

    usuario: Mapped["Usuario"] = relationship(
        back_populates="pedidos",
        lazy="selectin",
    )


class Usuario(Base):
    __tablename__ = "usuarios"

    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(255))
    nombre: Mapped[str] = mapped_column(String(100))
    activo: Mapped[bool] = mapped_column(default=True)

    pedidos: Mapped[list["Pedido"]] = relationship(
        back_populates="usuario",
        lazy="selectin",
    )

Lazy loading y async no se mezclan

En SQLAlchemy con async, el lazy loading por defecto (lazy="select") lanza MissingGreenlet: greenlet_spawn has not been called en cuanto intentas acceder a una relación fuera del contexto de ejecución sync. La solución es siempre declarar las relaciones con lazy="selectin" o cargarlas explícitamente en la query con selectinload(). El modo selectin emite una segunda query IN para cargar los objetos relacionados de forma async antes de que los necesites.

Si prefieres no poner lazy="selectin" en el modelo (para no cargar siempre la relación), puedes optar por la carga explícita en la query con selectinload() o joinedload():

from sqlalchemy.orm import selectinload


async def listar_usuarios_con_pedidos(session: AsyncSession) -> list[Usuario]:
    resultado = await session.execute(
        select(Usuario)
        .where(Usuario.activo.is_(True))
        .options(selectinload(Usuario.pedidos))
        .order_by(Usuario.nombre)
    )
    return list(resultado.scalars().all())

selectinload() emite una segunda query SELECT ... WHERE id IN (...) para los usuarios encontrados. joinedload() usa un JOIN y es más eficiente cuando esperas pocos resultados, pero puede inflar el resultado si la relación tiene muchos elementos.

Migraciones con Alembic

Alembic gestiona el historial de cambios del esquema de la base de datos. Cada migración es un script Python versionado que describe cómo avanzar (upgrade) y revertir (downgrade) el esquema:

pip install alembic
alembic init alembic

El fichero alembic.ini generado configura la URL de conexión y la ubicación del directorio de migraciones:

[alembic]
script_location = alembic
sqlalchemy.url = postgresql+asyncpg://usuario:password@localhost/mi_base

En alembic/env.py, apuntas el metadata de tus modelos para que Alembic pueda comparar el esquema actual con lo que hay en la BD:

from app.models import Base

target_metadata = Base.metadata

Para usar async en las migraciones, env.py debe ejecutar las migraciones dentro de un contexto async. El comando --autogenerate detecta las diferencias entre los modelos y la BD y genera el script automáticamente:

alembic revision --autogenerate -m "crear tabla usuarios"
alembic upgrade head
alembic downgrade -1
alembic history --verbose

Cada revisión tiene un identificador único. upgrade head aplica todas las migraciones pendientes en orden. downgrade -1 revierte la última. El historial completo se guarda en la tabla alembic_version de la BD.

No confíes ciegamente en autogenerate: Alembic no detecta todos los cambios automáticamente. Los índices parciales, las restricciones personalizadas y algunas columnas computadas pueden requerir que escribas la migración a mano. Revisa siempre el script generado antes de aplicarlo en producción.

Resumen

  • create_async_engine con el driver asyncpg y async_sessionmaker configuran el pool de conexiones async; expire_on_commit=False evita recargas inesperadas después del commit.
  • DeclarativeBase + Mapped[T] + mapped_column() es la API declarativa moderna de SQLAlchemy 2: los tipos son comprensibles por los type checkers sin plugins.
  • Las queries se construyen con select() composicional y se ejecutan con await session.execute(); .scalars().all() extrae los objetos mapeados del resultado.
  • El lazy loading síncrono lanza MissingGreenlet en async: siempre usa lazy="selectin" en el modelo o selectinload() explícito en la query.
  • El patrón repository encapsula las queries en una clase con la sesión como única dependencia, haciendo el acceso a datos testeable de forma aislada.
  • Alembic gestiona el historial de migraciones con --autogenerate; revisa siempre el script antes de aplicarlo porque no detecta todos los cambios.
