Tests de integración con base de datos

El stub que finge tu repositorio es útil hasta cierto punto: no verifica que la query SQL devuelva los registros correctos, ni que la constraint de unicidad rechace el duplicado, ni que la migración que escribiste ayer sea compatible con el código de hoy. Para eso necesitas la base de datos real, pero de test.

En los tests unitarios con stubs y mocks alimentabas el servicio con colaboradores falsos: el repositorio devolvía lo que tú decías. Eso es correcto — aisla el comportamiento de la lógica de negocio del acceso a datos. Pero hay una capa que esa estrategia no puede tocar: la que vive dentro del repositorio real.

El límite del stub #

Cuando haces createStub(ProductRepository::class) y le dices qué devolver, tu test comprueba que el servicio usa bien lo que le llega. Bien. Pero nadie ha verificado que DoctrineProductRepository —el repositorio real— ejecute la query correcta. Esa query podría:

  • devolver los registros en el orden equivocado porque falta un ORDER BY,
  • ignorar un filtro porque hay un error en la cláusula WHERE,
  • explotar con un SQLSTATE[42S22] porque la columna fue renombrada en la migración de ayer y nadie actualizó la query.

El stub no puede detectar nada de esto: finge la interfaz, no la implementación. Para testear la implementación necesitas ejecutarla —y eso implica una base de datos.

Dos tipos de test, dos responsabilidades

El test unitario verifica que el servicio usa el repositorio correctamente. El test de integración verifica que el repositorio habla con la base de datos correctamente. No son redundantes: cubren capas distintas.

La base de datos de test #

La base de datos de test es idéntica en esquema a la de producción pero completamente separada: distinto nombre, sin datos reales, destruible y reconstruible en cualquier momento. Si usas Docker, añadirla es trivial:

docker-compose.yml · servicio de test 
services:
  mysql:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: secret
      MYSQL_DATABASE: app
      MYSQL_DATABASE_TEST: app_test   # creas la BD de test aquí
    ports:
      - "3306:3306"

La convención más habitual es sufijo _test: si la de desarrollo se llama app, la de test se llama app_test. Mismas migraciones, ejecutadas una vez al arrancar o en CI, y listo.

PHPUnit necesita saber la URL de conexión. La forma limpia es un parámetro de entorno en phpunit.xml que sobreescribe el valor del entorno real durante la suite:

phpunit.xml · suites + env de test 
<?xml version="1.0" encoding="UTF-8"?>
<phpunit bootstrap="vendor/autoload.php">

  <testsuites>
    <testsuite name="Unit">
      <directory>tests/Unit</directory>
    </testsuite>
    <testsuite name="Integration">
      <directory>tests/Integration</directory>
    </testsuite>
  </testsuites>

  <php>
    <env name="DATABASE_URL"
         value="mysql://root:secret@127.0.0.1:3306/app_test"
         force="true"/>
  </php>

  <source>
    <include><directory>src</directory></include>
  </source>

</phpunit>

El atributo force="true" asegura que el valor del XML gana aunque ya exista en el entorno del shell — imprescindible si tu .env apunta a la BD de desarrollo.

Nunca la base de datos de producción

Un test que inserta y revierte sigue siendo un test que ejecuta escrituras. Si por error apunta a producción, puede corromper datos aunque el rollback funcione, porque hay efectos secundarios (triggers, sequences de IDs) que no se deshacen. La BD de test vive en Docker local o en un servicio efímero de CI; nunca en el entorno real.

Fixtures: estado de partida #

Un test de integración necesita datos en la base de datos para poder probar algo. Esos datos se llaman fixtures: el estado inicial conocido y determinista desde el que parte cada test.

La clave es que cada test crea su propio estado, en lugar de depender de datos que ya pudieran existir. Si dos tests comparten filas insertadas globalmente, el orden de ejecución importa — y eso viola la independencia que viste en el ciclo de vida de los tests. El lugar natural para insertar fixtures es setUp():

php · base de integración con fixtures en setUp 
<?php

declare(strict_types=1);

namespace Tests\Integration\Infrastructure\Persistence;

use App\Infrastructure\Persistence\DoctrineProductRepository;
use Doctrine\DBAL\DriverManager;
use Doctrine\DBAL\Connection;
use PHPUnit\Framework\TestCase;
use PHPUnit\Framework\Attributes\Test;

final class DoctrineProductRepositoryTest extends TestCase
{
    private Connection $connection;
    private DoctrineProductRepository $repository;

    protected function setUp(): void
    {
        parent::setUp();

        $this->connection = DriverManager::getConnection([
            'url' => getenv('DATABASE_URL'),
        ]);

        $this->connection->beginTransaction();

        $this->connection->executeStatement(
            'INSERT INTO products (id, name, price_cents) VALUES (:id, :name, :price)',
            ['id' => 1, 'name' => 'Teclado mecánico', 'price' => 8990]
        );
        $this->connection->executeStatement(
            'INSERT INTO products (id, name, price_cents) VALUES (:id, :name, :price)',
            ['id' => 2, 'name' => 'Monitor 4K', 'price' => 45000]
        );

        $this->repository = new DoctrineProductRepository($this->connection);
    }

    protected function tearDown(): void
    {
        $this->connection->rollBack();
        parent::tearDown();
    }

    #[Test]
    public function finds_products_below_price(): void
    {
        $results = $this->repository->findBelowPrice(priceCents: 10000);

        $this->assertCount(1, $results);
        $this->assertSame('Teclado mecánico', $results[0]->name());
    }
}

Observa que beginTransaction() va en setUp(), antes de insertar los fixtures. Así la inserción también queda dentro de la transacción y se deshará junto con cualquier escritura que haga el test.

Transacción por test #

El patrón que acabas de ver — abrir transacción en setUp(), hacer rollback en tearDown() — tiene un nombre: rollback por test. Es la forma más rápida de mantener la BD limpia entre tests sin truncar tablas.

setUp() — beginTransaction()
↓
INSERT fixtures
↓
Ejecuta el test (puede INSERT, UPDATE, DELETE)
↓
tearDown() — rollBack()
↓
BD vuelve al estado anterior a setUp()

Comparado con truncar tablas en tearDown(), el rollback es más rápido (la BD descarta los cambios sin escribir nada en disco) y más seguro (cualquier error en el test provoca un rollback implícito igualmente). El siguiente test empieza desde cero, sin rastro del anterior.

Limitación: el SUT no puede hacer su propio commit

Si el código bajo test llama a commit() explícitamente, los cambios quedan escritos y el rollback de tearDown() no los deshace. En ese caso necesitas truncar tablas en lugar de usar este patrón. La solución habitual es que el caso de uso no gestione la transacción directamente — eso queda en la infraestructura o en un middleware — lo que, como efecto secundario, hace la lógica de negocio más testeable.

Cuando el patrón de rollback no es viable, la alternativa es truncar en tearDown():

php · alternativa: truncar en tearDown 
protected function tearDown(): void
{
    $this->connection->executeStatement('SET FOREIGN_KEY_CHECKS = 0');
    $this->connection->executeStatement('TRUNCATE TABLE products');
    $this->connection->executeStatement('SET FOREIGN_KEY_CHECKS = 1');

    parent::tearDown();
}

Más lento (escribe en disco), pero funciona cuando el SUT controla la transacción. El FOREIGN_KEY_CHECKS deshabilita temporalmente las claves foráneas para poder truncar en cualquier orden — recuérdalo si el esquema tiene relaciones.

La pirámide y las suites #

Los tests de integración con base de datos son inevitablemente más lentos que los unitarios: levantan una conexión, ejecutan queries reales, pasan por el disco. Por eso la pirámide de testing los pone en el nivel medio: más que los tests end-to-end, pero muchos menos que los unitarios.

E2E / UI — muy pocos, muy lentos
Tests de integración — algunos, más lentos
Tests unitarios — muchos, muy rápidos

Las dos suites en phpunit.xml no son solo organización: te permiten ejecutarlas de forma independiente según el momento del ciclo de desarrollo:

bash · ejecutar suites por separado 
# mientras desarrollas: feedback rápido
vendor/bin/phpunit --testsuite Unit

# antes de hacer push: todo
vendor/bin/phpunit --testsuite Unit,Integration

# en CI: unitarios primero (fallan rápido), integración después
vendor/bin/phpunit --testsuite Unit
vendor/bin/phpunit --testsuite Integration

El criterio de cuántos tests de integración escribir es pragmático: uno por cada query o comportamiento de persistencia que no puedas confiar sin verificar contra la BD real. No necesitas cubrir cada método del repositorio con múltiples variantes — eso es redundante si el unitario del servicio ya cubre los casos de negocio.

Lo que solo el test de integración cubre #

Esta tabla resume qué verifica cada nivel y por qué no son intercambiables:

¿Qué verificas?Test unitario (stub)Test de integración
El servicio usa el repositorio correctamente✔—
La query SQL devuelve los registros correctos✘ (fingida)✔
Un WHERE o ORDER BY funciona como se espera✘✔
Una constraint de unicidad rechaza duplicados✘✔
La migración reciente no rompió ninguna query✘✔
Un rollback de la BD funciona en el camino de error✘✔
La lógica de negocio aislada de infraestructura✔— (demasiado lento para eso)

La columna más valiosa es la del test de integración con "✔ La migración reciente no rompió ninguna query". En proyectos que evolucionan el esquema continuamente —columnas renombradas, tablas partidas, tipos cambiados— los tests de integración son la única red que detecta la rotura antes de que llegue a producción. El stub no puede detectar esto nunca, por diseño.

Los tests de integración también documentan

Un test que inserta un pedido con líneas, lo recupera y verifica el total es una especificación ejecutable de cómo funciona la persistencia. Cuando alguien refactoriza el repositorio seis meses después, ese test dice exactamente qué debe seguir funcionando — y lo comprueba contra la BD real en lugar de contra un stub que quizás nunca fue fiel a la implementación.

Resumen #

Lo que te llevas

  • El test unitario verifica la lógica; el de integración verifica la persistencia. No son redundantes: cubren capas distintas y el stub no puede reemplazar al segundo.
  • La BD de test: mismo esquema que producción, distinto nombre, datos propios. La URL va en phpunit.xml como env con force="true" para no contaminar el entorno real.
  • Fixtures en setUp(): cada test crea su propio estado inicial. Estado compartido entre tests = orden de ejecución importa = bugs silenciosos.
  • Rollback por test: beginTransaction() en setUp(), rollBack() en tearDown(). Más rápido y limpio que truncar — salvo que el SUT haga su propio commit.
  • Dos suites en phpunit.xml: unitarios para feedback rápido mientras desarrollas; integración antes del push y en CI, después de los unitarios.
  • El valor único del test de integración: detectar que una migración rompió una query, que un WHERE filtra mal o que una constraint rechaza lo que debe rechazar — todo lo que el stub finge y nunca puede verificar.
