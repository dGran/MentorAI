Streaming y latencia

Una respuesta de veinte segundos es inaceptable… servida de golpe. La misma respuesta apareciendo palabra a palabra desde el primer segundo se siente rápida. El streaming no reduce la latencia real — reduce la que importa para la experiencia: el tiempo hasta que algo pasa.

Ya tienes las piezas de cursos anteriores: SSE del curso de protocolos, percentiles del de rendimiento. Esta lección las junta para el caso concreto que domina los productos con IA: enseñar la respuesta del modelo mientras se genera.

La latencia que importa #

En una respuesta generativa hay dos números: el tiempo hasta el primer token (uno o dos segundos, normalmente) y el tiempo hasta el último (que crece con la longitud: decenas de segundos para una respuesta larga). Sin streaming, el usuario espera el segundo número mirando un spinner — y un spinner de veinte segundos es un usuario que se ha ido. Con streaming, percibe el primero, y la lectura va en paralelo con la generación: para cuando el modelo termina, el usuario ya iba por la mitad.

También es cuestión de timeouts

Hay una razón técnica además de la perceptiva: una conexión que calla durante un minuto entero es carne de timeout — del cliente HTTP, del proxy, del balanceador. El goteo constante del streaming mantiene la conexión viva. Para respuestas largas, los SDK directamente lo exigen.

Cómo llega: un flujo de eventos #

Con streaming activado, la API no devuelve un JSON al final: emite eventos sobre la misma conexión HTTP (el formato SSE que ya conoces) — el arranque del mensaje, el inicio de cada bloque, un goteo de deltas con fragmentos de texto, y el cierre con los totales de uso. Tu trabajo es consumir deltas y reenviarlos hacia quien pinta.

Consumirlo desde PHP #

php · consumir el stream y reemitirlo como SSE 
<?php

use Anthropic\Messages\RawContentBlockDeltaEvent;
use Anthropic\Messages\TextDelta;

header("Content-Type: text/event-stream");
header("Cache-Control: no-cache");
header("X-Accel-Buffering: no");

$stream = $client->messages->createStream(
    model: "claude-opus-5",
    maxTokens: 64000,
    system: $instrucciones,
    messages: $historial,
);

$respuestaCompleta = "";

foreach ($stream as $event) {
    if ($event instanceof RawContentBlockDeltaEvent && $event->delta instanceof TextDelta) {
        $respuestaCompleta .= $event->delta->text;

        echo "data: " . json_encode(["texto" => $event->delta->text]) . "\n\n";
        flush();
    }
}

$this->guardarEnHistorial($respuestaCompleta);

Tres decisiones dentro de ese código. Uno: el backend acumula la respuesta completa mientras la reenvía — el historial de la conversación (lección 1) se guarda en el servidor, no se reconstruye desde el navegador. Dos: la cabecera X-Accel-Buffering: no le dice a nginx que no haga buffering — sin ella, el proxy acumula el goteo y lo entrega de golpe, matando el streaming en silencio. Tres: los deltas se reempaquetan como JSON propio — el cliente no consume el formato crudo del proveedor, igual que no expones las filas de tu base de datos.

El puente hasta el navegador #

La arquitectura completa es una tubería de tres tramos: la API transmite a tu backend; tu backend reemite como SSE (el endpoint de arriba, que es exactamente el patrón de la lección de Server-Sent Events); el navegador consume con EventSource y va pintando. El backend en medio no es burocracia: ahí viven la clave de la API (que jamás baja al navegador), el guardado del historial, los límites por usuario y el recorte de lo que no quieres exponer.

Los detalles que muerden #

  • Un worker ocupado por conversación. El endpoint de streaming retiene un proceso PHP-FPM durante toda la generación. Con tráfico real, dimensiona el pool (curso de rendimiento) o mueve el streaming a infraestructura hecha para conexiones largas.
  • El corte a mitad. El usuario cierra la pestaña o la red se cae a medio stream: decide qué pasa con la mitad generada (¿se guarda en el historial? ¿se descarta?) y hazlo deliberadamente, no por accidente.
  • Markdown a medio cocer. Los deltas cortan por donde quieren — un bloque de código abierto y sin cerrar pinta raro. Los frontends serios renderizan con un parser tolerante o re-renderizan el acumulado en cada delta.

Cuándo el streaming sobra #

El streaming es para ojos humanos esperando. El clasificador de tickets de las lecciones anteriores corre en un worker de cola: nadie mira, y el JSON estructurado se consume entero o no se consume — ahí el streaming solo añade complejidad. La matriz es simple: humano esperando una respuesta larga → streaming; trabajo de fondo o salida estructurada → llamada normal en cola; y mucho volumen sin prisa → procesos por lotes, que la siguiente lección conecta con el coste.

Cuándo aplicarlo #

Streaming cuando…

  • Un humano espera una respuesta generativa larga (chat, redacción)
  • La respuesta puede superar el minuto: la conexión debe seguir viva
  • Quieres feedback inmediato aunque el total tarde

Llamada normal cuando…

  • Es un trabajo de fondo: nadie mira el goteo
  • La salida es estructurada y se consume entera
  • La respuesta es corta: el primer token y el último casi coinciden

Resumen #

Lo que te llevas

  • El streaming no acelera la generación: convierte la latencia total en latencia hasta el primer token, que es la que se percibe.
  • La API emite eventos con deltas; tu backend los consume, acumula la respuesta completa para el historial y reemite como SSE propio.
  • El backend en medio guarda la clave, el historial y los límites: el navegador nunca habla directo con el proveedor.
  • Los que muerden: el buffering del proxy, el worker retenido por conversación, y el corte a mitad sin política decidida.
  • Streaming para ojos humanos esperando; para trabajos de fondo y salida estructurada, llamada normal en cola.
