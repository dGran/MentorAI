Rules: las reglas del proyecto

Cada sesión, el agente llega de nuevas. Las rules — el CLAUDE.md o AGENTS.md de tu repo — son lo único que lee antes de empezar: su manual de bienvenida permanente. Escribirlas bien es la inversión con más retorno de todo este curso; escribirlas mal, un impuesto que pagas en cada sesión.

Ya sabes de la lección de contexto que las rules entran en la ventana al arrancar cada sesión, y del curso de fundamentos que el contexto permanente evita repetir correcciones. Esta lección va del oficio: qué contienen unas rules que funcionan, con qué forma, y cómo se mantienen vivas sin engordar hasta ser ruido.

El manual del recién llegado #

La prueba mental correcta: imagina que mañana se incorpora al proyecto alguien competente pero que no sabe nada de cómo se trabaja aquí, y solo puedes darle un documento. Eso son las rules. Claude Code lee el CLAUDE.md del repo (y el global de tu máquina) al empezar; otras herramientas leen AGENTS.md — muchos proyectos hacen de uno un enlace al otro para mantener una sola fuente.

Rules ≠ permisos

De la lección 1: una rule es una instrucción al modelo — se cumple casi siempre. Lo que deba cumplirse siempre (no tocar producción, no borrar X) va además a la capa de permisos del harness. Las rules dan criterio; los permisos dan garantías. Se complementan, no se sustituyen.

Qué va en las rules (y qué no) #

El criterio de admisión: lo que el agente no puede deducir del código y necesita en (casi) toda sesión. Lo que sí puede deducir — la estructura de directorios, qué hace cada clase — sobra: lo leerá cuando lo necesite, mejor actualizado que tu resumen.

Sí es material de rules

  • Invariantes de arquitectura («sin build, funciona por file://»)
  • Convenciones no evidentes («los datos entran como .js que asignan a un global»)
  • Cómo verificar («node scripts/validar.js tiene que salir limpio»)
  • Trampas que ya mordieron («emular offline no prueba el offline»)
  • Qué no proponer («no sugerir frameworks: decisión cerrada»)

No lo es

  • El árbol de ficheros (se lee mejor con ls)
  • Documentación de APIs públicas (ya está en el código)
  • El historial del proyecto (para eso está git y las notes)
  • Reglas genéricas de buen código que el modelo ya sabe («usa buenos nombres»)

Invariantes antes que preferencias #

No todas las reglas pesan igual, y mezclarlas sin jerarquía diluye las importantes. Separa mentalmente (y tipográficamente) dos niveles:

  • Invariantes: lo que rompe el proyecto si se viola. «Nada de fetch de JSON: CORS lo bloquea por file://». Merecen negrita, contexto y estar arriba.
  • Preferencias: lo que hace el código consistente. «Booleanos con prefijo is/has/should». Van en lista compacta, sin drama.

Un agente que se salta una preferencia produce un diff mejorable; uno que se salta un invariante rompe producción. Si tu documento no distingue entre ambas, estás pidiendo al lector — humano o modelo — que adivine cuáles son cuáles.

El porqué viaja con la regla #

La diferencia entre una regla que se obedece y una que se «interpreta» suele ser el porqué. Compara:

CLAUDE.md · la misma regla, dos formas 
# version fragil
- No usar fetch para cargar datos.

# version que se obedece
- **Nada de fetch de ficheros .json**: CORS lo bloquea al abrir por
  file://. Los datos se cargan como .js que asignan a un global
  (window.X), incluidos con <script>.

La versión frágil invita a la excepción («esto no es exactamente un fetch de datos…»). La segunda deja claro el mecanismo que protege, y de paso enseña el patrón correcto. Un modelo — como una persona — generaliza bien desde porqués y mal desde prohibiciones sueltas.

Cortas, porque se pagan siempre #

De la lección de contexto: las rules entran en la ventana en todas las sesiones, aplique o no su contenido a la tarea del día. Dos mil líneas de rules son miles de tokens de impuesto fijo — y, peor, diluyen las diez reglas que de verdad importan entre doscientas que casi nunca aplican.

Las válvulas de escape para no engordar el fichero principal:

  • Detalle bajo demanda: la regla corta vive en las rules y enlaza al documento largo («el detalle completo, en docs/arquitectura.md»), que el agente lee solo cuando toca.
  • Flujos empaquetados: los procedimientos paso a paso no son rules — son skills, que se cargan al invocarlas. Siguiente lección.
  • Ámbitos: reglas globales tuyas (tu estilo, en el CLAUDE.md de tu home) separadas de las del proyecto (en el repo, versionadas y compartidas con el equipo).

Reglas vivas: el ciclo de vuelta #

Las mejores rules no se escriben un día: se destilan. Cada vez que corriges al agente dos veces por lo mismo, eso es una regla pidiendo existir. Cada trampa que costó una tarde de depuración merece su línea («pkill -f se mata a sí mismo si el patrón aparece en su propia línea de comandos»). El ciclo:

1 Algo se aprende en sesiónUna corrección repetida, una trampa, una convención que emerge.
2 Vuelve a las rulesRegla corta + porqué. Si se deja para luego, se pierde con el contexto.
3 Las sesiones futuras la heredanLa corrección no vuelve a hacer falta: el agente «conoce la casa».

La disciplina clave es el paso 2 en caliente: lo aprendido vuelve a las reglas en la misma sesión, o se pierde con el contexto.

Y el mantenimiento inverso: una regla que ya no aplica, se borra. Un documento con reglas muertas entrena al lector a ignorarlo — el mismo principio que los validadores ruidosos o los tests flaky.

Cuándo aplicarlo #

Toca escribir/tocar rules cuando…

  • Corriges al agente por segunda vez por lo mismo
  • Una depuración descubre una trampa del proyecto
  • Tomas una decisión que no se debe reabrir («no usamos X»)
  • Arrancas un repo nuevo: los 4-5 invariantes, aunque sea todo

Señales de rules enfermas

  • Crecen y nunca encogen: nadie borra lo muerto
  • Documentan lo que el código ya dice
  • El agente las «ignora»: quizá son tantas que las importantes se diluyen
  • Prohibiciones sin porqué que invitan a la excepción

Resumen #

Lo que te llevas

  • Las rules son el manual del recién llegado: lo que el agente no puede deducir del código y necesita en casi toda sesión.
  • Invariantes (rompen el proyecto) separados de preferencias (consistencia): sin jerarquía, las importantes se diluyen.
  • El porqué viaja con la regla: se generaliza bien desde mecanismos y mal desde prohibiciones sueltas.
  • Se pagan en cada sesión: cortas, con el detalle enlazado bajo demanda y los flujos empaquetados como skills.
  • Reglas vivas: lo aprendido vuelve a las rules en la misma sesión, y lo muerto se borra — un documento ignorable acaba ignorado.
