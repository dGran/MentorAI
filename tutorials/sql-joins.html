JOINs a fondo: combinar tablas con criterio

INNER, LEFT, self-join, el error clásico de contar con LEFT JOIN y cuándo una subconsulta le gana a un JOIN. El vocabulario para razonar sobre consultas, no solo escribirlas.

Un JOIN no es magia: es un producto cartesiano filtrado por una condición. Entender eso explica por qué hay distintos tipos, cuándo cada uno y qué pasa cuando mezclas JOINs con agregaciones.

El modelo mental #

Cuando escribes FROM pedidos JOIN clientes ON clientes.id = pedidos.cliente_id, el motor toma cada fila de pedidos, la combina con cada fila de clientes y descarta las que no cumplen el ON. El tipo de JOIN decide qué pasa con las filas que no tienen pareja.

1 Producto cartesianoTodas las combinaciones posibles entre ambas tablas
2 Filas con parejaLas que cumplen la condición del ON
3 Resultado final¿Qué hacemos con las filas sin pareja?

El tipo de JOIN solo afecta al tercer paso: qué incluir cuando no hay match.

INNER JOIN #

El más común. Solo devuelve filas que tienen correspondencia en ambas tablas. Si un pedido tiene un cliente_id que no existe en clientes, esa fila desaparece del resultado. Si un cliente no tiene pedidos, tampoco aparece.

sql 
SELECT p.id, p.total, c.nombre
FROM pedidos p
INNER JOIN clientes c ON c.id = p.cliente_id;

-- INNER es opcional: JOIN a secas es INNER JOIN
SELECT p.id, p.total, c.nombre
FROM pedidos p
JOIN clientes c ON c.id = p.cliente_id;

-- USING cuando el nombre de columna coincide en ambas tablas
SELECT p.id, p.total, c.nombre
FROM pedidos p
JOIN clientes c USING (cliente_id);

La palabra INNER es optativa: JOIN a secas es siempre INNER JOIN. USING es azúcar sintáctico para cuando la columna tiene el mismo nombre en ambas tablas; produce la misma consulta.

Alias de tabla

Pon siempre alias cortos (p, c) y califica cada columna con su tabla (p.id, c.nombre). En consultas con más de una tabla, las columnas sin alias son ambiguas para el lector y, si hay nombres repetidos, para el motor.

LEFT JOIN #

Devuelve todas las filas de la tabla izquierda (la que va en FROM), independientemente de si tienen pareja en la derecha. Las columnas de la tabla derecha salen NULL cuando no hay match.

sql 
-- Todos los clientes, tengan o no pedidos
SELECT c.nombre, p.id AS pedido_id, p.total
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id;

-- Los clientes sin ningún pedido (filtro sobre NULL de la derecha)
SELECT c.nombre
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id
WHERE p.id IS NULL;

El patrón LEFT JOIN ... WHERE derecha.id IS NULL es la forma estándar de encontrar filas huérfanas: registros de la tabla izquierda que no tienen correspondencia en la derecha.

RIGHT, FULL OUTER y self-join #

RIGHT JOIN es el espejo del LEFT: devuelve todas las filas de la tabla derecha. En la práctica casi nadie lo usa porque siempre puedes reescribirlo como LEFT JOIN invirtiendo el orden de las tablas. Mantenerlos ambos en una base de código genera confusión sin ninguna ganancia.

FULL OUTER JOIN devuelve todas las filas de ambos lados, con NULL donde no hay match en el lado opuesto. Es útil para detectar inconsistencias en cualquier dirección: "qué hay en A que no está en B, y qué hay en B que no está en A".

MySQL no tiene FULL OUTER JOIN nativo

MySQL y MariaDB no implementan FULL OUTER JOIN. El workaround es un UNION de un LEFT JOIN y un RIGHT JOIN. PostgreSQL y SQL Server sí lo soportan directamente.

Self-join es unir una tabla consigo misma, con alias distintos. El caso más frecuente en backend: una tabla con una clave foránea que apunta a la misma tabla, como empleados con su manager o categorías con subcategorías.

sql 
-- empleados con su manager (LEFT para incluir el CEO que no tiene manager)
SELECT e.nombre AS empleado, m.nombre AS manager
FROM empleados e
LEFT JOIN empleados m ON m.id = e.manager_id;

El truco es tratarla como dos tablas distintas mediante alias: empleados e (el empleado) y empleados m (el manager). El motor resuelve la misma tabla dos veces sin problema.

El error clásico con COUNT #

La trampa más frecuente al combinar LEFT JOIN con agregación: usar COUNT(*) en lugar de COUNT(columna).

COUNT(*) — incorrecto

sql 
SELECT c.nombre, COUNT(*) AS pedidos
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id
GROUP BY c.id, c.nombre;

Un cliente sin pedidos devuelve 1, no 0: COUNT(*) cuenta la fila aunque las columnas de pedidos sean todas NULL.

COUNT(columna) — correcto

sql 
SELECT c.nombre, COUNT(p.id) AS pedidos
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id
GROUP BY c.id, c.nombre;

COUNT(p.id) ignora los NULL: un cliente sin pedidos devuelve 0, que es lo correcto.

El segundo error clásico aparece cuando haces dos LEFT JOINs con relaciones independientes: si un cliente tiene 3 pedidos y 2 teléfonos, el JOIN de ambas tablas produce 6 filas (el producto). La solución es COUNT(DISTINCT p.id) o mover una de las relaciones a una subconsulta.

sql 
-- Dos JOINs independientes: los conteos se inflan mutuamente
-- (3 pedidos × 2 teléfonos = 6 filas por cliente)
SELECT c.nombre,
       COUNT(DISTINCT p.id)  AS pedidos,
       COUNT(DISTINCT t.id)  AS telefonos
FROM clientes c
LEFT JOIN pedidos   p ON p.cliente_id = c.id
LEFT JOIN telefonos t ON t.cliente_id = c.id
GROUP BY c.id, c.nombre;

JOIN vs subconsulta #

Regla práctica: usa JOIN cuando necesitas columnas de ambas tablas en el resultado. Usa una subconsulta (o EXISTS) cuando solo necesitas filtrar por existencia.

sql 
-- "Clientes que tienen al menos un pedido"

-- Con JOIN: puede devolver duplicados si hay varios pedidos
SELECT DISTINCT c.nombre
FROM clientes c
JOIN pedidos p ON p.cliente_id = c.id;

-- Con EXISTS: más explícito y sin riesgo de duplicados
SELECT c.nombre
FROM clientes c
WHERE EXISTS (
    SELECT 1 FROM pedidos p WHERE p.cliente_id = c.id
);

EXISTS cortocircuita en cuanto encuentra una fila: no importa cuántos pedidos tenga el cliente, el motor para al primero. IN con subconsulta funciona igual para conjuntos pequeños, pero EXISTS escala mejor y deja la intención más clara: "comprueba si existe, no me traigas los datos".

Los optimizadores son listos, pero tú más

Los optimizadores modernos (MySQL 8+, PostgreSQL) frecuentemente convierten un IN (subconsulta) en un semi-join internamente, igualando el rendimiento. Aun así, escribe EXISTS cuando la intención sea "¿existe?": el código comunica mejor y no dependes del optimizador para evitar duplicados.

Cuándo aplicarlo

Úsalo cuando…

  • INNER JOIN cuando solo necesitas registros con coincidencia en ambas tablas.
  • LEFT JOIN cuando necesitas todos los registros de la tabla izquierda aunque no haya coincidencia.
  • JOIN en lugar de subconsulta cuando el planner puede optimizarlo mejor y necesitas columnas de ambas tablas.

No lo uses cuando…

  • LEFT JOIN cuando en realidad quieres solo los que coinciden: usa INNER JOIN para dejar clara la intención.
  • JOIN cuando una subconsulta escalar es más legible y el uso es único.
  • Mezclas JOINs con COUNT sin aplicar DISTINCT o GROUP BY correctamente: produces conteos inflados.

Resumen #

Lo que te llevas

  • Un JOIN es un producto cartesiano filtrado por ON. El tipo decide qué hacer con las filas sin pareja.
  • INNER JOIN: solo los que tienen correspondencia en ambos lados. LEFT JOIN: todo el izquierdo, NULLs donde no hay match.
  • Con LEFT JOIN y agregación, usa COUNT(p.id), no COUNT(*): los NULLs deben contar cero, no uno.
  • Dos JOINs independientes inflan los conteos. Usa COUNT(DISTINCT id) o separa en subconsultas.
  • Self-join: dos alias de la misma tabla para relaciones jerárquicas (empleado→manager, categoría→padre).
  • Necesitas columnas de ambas tablas → JOIN. Solo filtras por existencia → EXISTS o subconsulta.
