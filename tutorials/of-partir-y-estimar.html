Partir el trabajo y estimar

«¿Cuánto te queda?» «Casi está.» Tres semanas después sigue casi. El problema rara vez es la velocidad de quien programa: es el tamaño del trozo que se intentó estimar y una cifra exacta que nunca debió serlo.

Partir y estimar son la misma habilidad vista desde dos lados. Un trozo pequeño y bien cortado se estima casi solo; uno grande no se estima, se adivina. Por eso esta lección empieza por el cuchillo y termina por la cifra.

Por qué «casi está» dura semanas #

En la tienda ficticia de este curso llega una petición: «queremos cupones de descuento en el checkout». Alguien dice «una semana» y se pone a ello. A los cuatro días hay tabla, entidad y repositorio, pero nada que un usuario pueda probar. Al octavo aparecen las preguntas que nadie hizo: ¿se acumulan dos cupones?, ¿qué pasa si el pedido se devuelve?, ¿el descuento entra antes o después del envío?

Fallan dos cosas a la vez. El trabajo se cortó en un bloque que no entrega nada hasta el final, así que no hay señal de avance real. Y la cifra se dio como un punto, «una semana», cuando lo honesto era un rango con lo desconocido a la vista.

Rebanadas verticales, no capas #

Hay dos formas de partir los cupones. Por capas: un PR con la migración, otro con el repositorio, otro con el servicio y otro con el controlador. En rebanadas verticales: cada PR atraviesa todas las capas que necesita y deja algo que funciona, aunque sea mínimo.

Por capas

  • PR 1: migración y entidad Coupon
  • PR 2: repositorio con todas las consultas
  • PR 3: servicio con todas las reglas
  • PR 4: controlador y formulario

En rebanadas

  • R1: un cupón de importe fijo se aplica a un pedido
  • R2: cupones de porcentaje
  • R3: caducidad por fecha
  • R4: límite de usos por cliente

Por capas, hasta el PR 4 no se sabe si el diseño aguanta un pedido real, y los PR intermedios son código muerto que nadie puede probar de punta a punta. En rebanadas, R1 ya responde a la pregunta más cara: ¿dónde entra el descuento en el cálculo del total? Si la respuesta obliga a cambiar el diseño, lo descubres al tercer día, no al octavo. Y cada rebanada se puede priorizar: si R4 no llega, el negocio tiene cupones igualmente.

Cuánto debe abarcar cada rebanada lo resuelve la regla de un issue, un PR razonable: que se implemente, se pruebe y se revise de una vez. Dos señales prácticas de que una rebanada aún es grande: su título necesita una «y» («cupones de porcentaje y caducidad»), o sus criterios de aceptación no caben en una pantalla.

Entregar no es lo mismo que publicar

Una rebanada puede llegar a main oculta tras una feature flag y activarse cuando el conjunto tenga sentido para el usuario. Así el código se integra pronto, sin ramas que viven semanas (lo que el flujo de ramas desaconseja), y la decisión de publicar queda separada de la de mergear.

Cómo se ve en el código #

El primer PR por capas trae un repositorio con todo lo que algún día se necesitará. Nadie lo llama todavía, así que la revisión solo puede opinar de su forma, no de si sirve:

php · CouponRepository.php (PR 1 de 4, por capas) 
<?php

declare(strict_types=1);

namespace Tienda\Pedidos\Cupones;

final class CouponRepository
{
    public function __construct(private readonly \PDO $connection)
    {
    }

    public function findActiveByCode(string $code, \DateTimeImmutable $now): ?array
    {
        $statement = $this->connection->prepare(
            'SELECT * FROM coupons WHERE code = :code AND (expires_at IS NULL OR expires_at > :now)'
        );
        $statement->execute(['code' => $code, 'now' => $now->format('Y-m-d H:i:s')]);

        return $statement->fetch(\PDO::FETCH_ASSOC) ?: null;
    }

    public function countUsesByCustomer(int $couponId, int $customerId): int
    {
        $statement = $this->connection->prepare(
            'SELECT COUNT(*) FROM coupon_uses WHERE coupon_id = :coupon AND customer_id = :customer'
        );
        $statement->execute(['coupon' => $couponId, 'customer' => $customerId]);

        return (int) $statement->fetchColumn();
    }
}

La rebanada R1 es más estrecha pero llega hasta el pedido. Solo importe fijo, sin caducidad ni límites, y apagada hasta que se decida publicar:

php · ApplyCouponToOrder.php (rebanada R1) 
<?php

declare(strict_types=1);

namespace Tienda\Pedidos\Cupones;

use Tienda\Pedidos\Order;
use Tienda\Plataforma\FeatureFlags;

final class ApplyCouponToOrder
{
    private const FLAG = 'checkout-cupones';

    public function __construct(
        private readonly FixedAmountCoupons $coupons,
        private readonly FeatureFlags $flags,
    ) {
    }

    public function __invoke(Order $order, string $code): Order
    {
        if (!$this->flags->isEnabled(self::FLAG)) {
            return $order;
        }

        $discountInCents = $this->coupons->discountInCentsFor($code);

        if ($discountInCents === null) {
            throw new UnknownCoupon($code);
        }

        return $order->withDiscountInCents(min($discountInCents, $order->totalInCents()));
    }
}

Este PR se puede probar con un pedido de verdad y ya fija la decisión que importa: el descuento se aplica sobre el total y nunca lo deja en negativo. R2, R3 y R4 añaden reglas a algo que funciona, en lugar de esperar a que todo encaje al final.

Estimar con rangos y por comparación #

Una cifra exacta, «32 horas», transmite una precisión que nadie tiene. Dos cambios la hacen honesta:

  • Rangos. «Entre 2 y 4 días» dice cuánto crees y cuánto dudas. Un rango ancho no es un fallo: es información. Avisa de que hay algo por descubrir antes de que se convierta en retraso.
  • Comparación. Las personas juzgamos mal las horas en abstracto y bastante mejor el tamaño relativo. «Se parece al #41, envío gratis por código, que llevó 4 días; esto tiene más reglas» es un ancla real. Técnicas como el planning poker se apoyan en esa idea: comparar tareas entre sí en vez de contar horas.

Esta plantilla cabe en el comentario del issue. Lo que más ayuda no es el rango, sino que los supuestos y los desconocidos queden escritos:

yaml · estimación en el issue (tienda, ficticio) 
issue: "R1 · cupón de importe fijo en el checkout"
rango: "2-6 días"
referencia: "#41 envío gratis por código, 4 días"
supuestos:
  - "Un solo cupón por pedido"
  - "El descuento se aplica antes del envío"
desconocidos:
  - "Si el cálculo de impuestos admite un descuento antes del envío"
revisar_cuando: "termine el spike de impuestos (máx. medio día)"
real: ""

Por qué fallan y qué hacer #

Las estimaciones fallan casi siempre en la misma dirección, y no por optimismo de carácter. Fallan por dos razones estructurales:

  • Lo desconocido. Se estima lo que se ve. Lo que no se ve (la API de pagos que no admite reembolsos parciales, el campo que en producción llega nulo) no está en la cifra porque nadie sabía que existía.
  • La cola de imprevistos. Una tarea puede salir algo antes de lo previsto, pero puede salir muchísimo después. El retraso no tiene techo y el adelanto sí. Sumar diez tareas estimadas «a lo probable» da un total que casi nunca se cumple, porque los retrasos no se compensan con los adelantos.

Contra lo desconocido sirve un spike: una investigación con tiempo acotado («máximo medio día») y una pregunta concreta («¿el cálculo de impuestos acepta un descuento antes del envío?»). Su entregable es una respuesta y una estimación revisada, no código para producción: lo que se escribe en un spike se tira o se rehace.

Contra la cola sirve revisar la estimación con lo aprendido, y decirlo en cuanto pasa. Si al segundo día descubres que la estimación ya no vale, el aviso tiene valor ese día; el viernes por la tarde ya no. Revisar no es fallar: es la estimación haciendo su trabajo.

1 Rango inicial2-6 días: ancho porque hay un desconocido
2 Desconocido resueltoImpuestos admiten el descuento
3 Rango estrecho2-3 días

El rango se estrecha a medida que lo desconocido pasa a conocido. Cada salto se comunica.

Estimación no es compromiso #

Una estimación es una previsión con incertidumbre: «con lo que sé hoy, 2-4 días». Un compromiso es una promesa: «el jueves está R1 en producción». Mezclarlas tiene un coste conocido: si cada estimación se trata como promesa, la gente infla las cifras para protegerse, y la estimación deja de informar.

El compromiso se decide a partir de la estimación, mirando el riesgo. Si la fecha importa, comprométete con el extremo alto del rango o con menos alcance. Y cuando la fecha es fija y no llega, la palanca sana es el alcance (sale R1 sin R4), no la calidad: recortar tests para cumplir es deuda que se paga con intereses, y cómo negociarla lo verás en la deuda técnica. Explicar ese reparto a quien decide es parte de comunicar trade-offs.

Errores típicos #

Cinco formas de volver a «casi está»

  • Partir por capas y llamarlo rebanadas. Si un PR no se puede probar de punta a punta, es una capa.
  • Dar un número al vuelo. «¿Cuánto es?» admite «te lo digo en una hora, tras mirar el código».
  • Sumar estimaciones probables y prometer el total. La cola de imprevistos se acumula; el total necesita margen o menos alcance.
  • Spikes sin tiempo ni pregunta. Un spike abierto es una tarea más sin estimar.
  • Callar el desvío hasta el final. Revisar tarde equivale a no revisar.

Cómo comprobarlo #

Dos comprobaciones baratas. La primera, antes de abrir el PR: ¿cuánto ocupa la rebanada?

bash · tamaño de la rama frente a main 
git diff --shortstat main...HEAD
git diff --stat main...HEAD -- src/

No hay un número mágico de líneas, pero si el diff toca muchos ficheros sin relación entre sí, o no sabrías explicarlo en dos frases, probablemente son dos rebanadas.

La segunda, al cerrar el issue: rellena el campo real de la plantilla. Al cabo de unas semanas tendrás algo más útil que cualquier técnica: tu propio historial de cuánto te desvías y en qué tipo de tareas. Si el real cae fuera del rango a menudo, tus rangos son estrechos; si siempre cae en el extremo alto, tu ancla está sesgada.

Cuándo aplicarlo #

SituaciónQué hacer
Una funcionalidad que tardará más de un PRPartir en rebanadas verticales y estimar cada una con rango
Hay una pieza que nadie del equipo conoceSpike acotado antes de dar una cifra
Alguien necesita una fecha para coordinarEstimar con rango y decidir aparte el compromiso
Un arreglo de una línea o una tarea repetidaNo hace falta ceremonia: la comparación con la anterior basta
Un experimento cuyo resultado decide si se sigueNo estimes el final: acota el tiempo del experimento y decide con lo que salga

La alternativa cuando estimar cuesta más que hacer es acotar por tiempo: «le dedico hasta el miércoles y vemos dónde está». Funciona si el corte es real y el resultado se revisa.

Resumen #

Lo que te llevas

  • Parte en rebanadas verticales que funcionan de punta a punta; las capas sueltas esconden el riesgo hasta el final.
  • Estima con rangos y por comparación con trabajo ya hecho, y deja escritos los supuestos y lo desconocido.
  • Lo desconocido se ataca con spikes acotados; la cola de imprevistos, revisando y avisando en cuanto cambia algo.
  • La estimación prevé; el compromiso promete. Si la fecha no llega, se recorta alcance, no calidad.
