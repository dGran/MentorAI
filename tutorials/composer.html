Composer a fondo: dependencias, lock y autoload

Lo usas todos los días y probablemente nunca te ha exigido entenderlo: ese es el mérito de Composer. Pero saber qué hace por debajo —qué es el lock, qué promete un ^, de dónde sale el autoload— es lo que separa usarlo de depender de la suerte.

Antes de 2012, usar una librería PHP era descargar un zip, descomprimirlo en lib/ y encadenar require a mano — y rezar para que sus dependencias no chocaran con las tuyas. Composer resolvió las dos mitades del problema de golpe: conseguir el código (gestión de dependencias) y cargarlo (autoload). Este artículo recorre ambas.

Qué resuelve Composer #

El corazón del asunto es que las dependencias forman un grafo: tú dependes de cinco paquetes, cada uno depende de otros, y varios pueden exigir versiones distintas del mismo paquete. Resolver qué conjunto de versiones satisface a todo el mundo a la vez es un problema computacionalmente serio, y eso —no descargar zips— es el trabajo de Composer: lee las restricciones de tu composer.json, consulta el registro central (Packagist), resuelve el grafo completo y materializa el resultado en vendor/.

Un paquete se identifica como vendor/nombre (symfony/console, phpunit/phpunit) y se declara en una de dos listas, y la distinción importa:

BloqueQué contieneEjemplos
requireLo que la aplicación necesita para funcionar.El framework, el ORM, el cliente HTTP
require-devLo que solo se usa para desarrollarla.PHPUnit, PHPStan, php-cs-fixer

La recompensa de mantener la frontera limpia llega en el despliegue: composer install --no-dev deja fuera de la imagen de producción todo el utillaje de desarrollo — menos peso y menos superficie de ataque, como pedían las buenas prácticas de Docker.

composer.json vs composer.lock #

Aquí vive el malentendido más común del ecosistema. Son dos ficheros con papeles opuestos:

composer.json — la intención

  • Lo escribes tú.
  • "Quiero symfony/console, versión 7 o compatible".
  • Restricciones flexibles: ^7.1.

composer.lock — la foto exacta

  • Lo escribe Composer al resolver.
  • "Quedó instalada exactamente la 7.1.4, con este hash".
  • Todo el grafo, clavado a versiones concretas.

Y de ahí la diferencia entre los dos comandos que más se confunden. composer install obedece al lock: instala exactamente lo que dice, sin resolver nada; es el comando de CI, de producción y del compañero que acaba de clonar. composer update re-resuelve: busca las versiones más nuevas que cumplan el composer.json y reescribe el lock; es una acción deliberada de actualización, con su PR y su pipeline.

El lock SE COMMITEA. vendor/, no.

Sin el lock en el repo, cada composer install resuelve por su cuenta y cada máquina acaba con versiones distintas: el "en mi máquina funciona" de las dependencias. El lock garantiza que tú, el CI y producción usan el mismo grafo al byte. En cambio vendor/ va al .gitignore: es regenerable desde el lock, y versionarlo es meter miles de ficheros ajenos en cada diff.

Semver: qué promete un ^ #

Las restricciones del composer.json se apoyan en un contrato social: el versionado semántico. Una versión MAYOR.MENOR.PARCHE (por ejemplo 7.1.4) comunica el tipo de cambio con cada número:

NúmeroSube cuando…Puedo actualizar sin tocar código
MAYOR (7.x.x)Hay cambios incompatibles: algo que usabas cambia o desaparece.❌ Requiere migración
MENOR (x.1.x)Se añade funcionalidad compatible.✅ En teoría, sí
PARCHE (x.x.4)Se corrigen bugs, sin API nueva.✅ Sí

Las dos restricciones que escribirás el 95 % de las veces expresan cuánta confianza depositas en ese contrato:

RestricciónSignificaAceptaRechaza
^7.1 (caret, la habitual)"Cualquier 7.x desde la 7.1"7.1.4, 7.2, 7.98.0
~7.1.0 (tilde, conservadora)"Solo parches de la 7.1"7.1.4, 7.1.97.2
7.1.4 (exacta, excepcional)"Esta y ninguna otra"7.1.4Todo lo demás

El caret dice: "confío en que el paquete respeta semver — dame mejoras y parches, pero jamás una mayor". Por eso es el default sano. La versión exacta clavada en el json es casi siempre una mala señal (esa rigidez ya te la da el lock); se reserva para esquivar temporalmente una versión rota.

Semver es una promesa, no una ley física

Nada impide técnicamente que una versión menor rompa algo (a veces por accidente, a veces porque dependías de un detalle no documentado). Por eso composer update se trata como cualquier cambio: rama, PR y pipeline en verde antes de mezclar. La restricción define el riesgo que aceptas; los tests comprueban que la apuesta salió bien.

El autoload PSR-4 #

La segunda mitad del invento. En PHP, usar una clase exige que su fichero se haya cargado; encadenar require a mano murió con los autoloaders: PHP permite registrar una función que, al encontrarse una clase desconocida, averigüe qué fichero cargarla. Lo que estandarizó el ecosistema fue la convención para ese "averiguar": PSR-4, que mapea prefijos de namespace a directorios.

json · composer.json — el mapeo de tu propio código 
{
    "autoload": {
        "psr-4": { "App\\": "src/" }
    },
    "autoload-dev": {
        "psr-4": { "App\\Tests\\": "tests/" }
    }
}

Con ese mapeo, la clase App\Billing\InvoiceCalculator vive —sin excepción posible— en src/Billing/InvoiceCalculator.php: se sustituye el prefijo por su directorio y el resto del namespace se convierte en carpetas. La clase se encuentra calculando, no buscando. Y el vendor/autoload.php que tu index.php incluye al principio es simplemente el autoloader que Composer genera con los mapeos de tu proyecto más los de cada paquete instalado: por eso "instalar y usar" funciona sin ningún require intermedio.

En producción: autoloader optimizado

El cálculo namespace→fichero se puede precomputar: composer install --no-dev --optimize-autoloader genera un mapa clase→fichero completo (un array gigante) y la resolución pasa a ser una consulta O(1). En producción es gratis y siempre conviene; junto con OPcache, deja el coste de cargar clases prácticamente en cero.

Comandos del día a día #

La referencia rápida, en la línea de la chuleta de Git:

ComandoQué hace
composer installInstala exactamente lo que dice el lock. El comando de clonar, de CI y de producción.
composer require vendor/paqueteAñade la dependencia al json, resuelve, actualiza el lock e instala. Con --dev, a require-dev.
composer remove vendor/paqueteLa operación inversa: quita del json y del lock, y desinstala.
composer updateRe-resuelve todo el grafo al máximo que permita el json y reescribe el lock. Acción deliberada.
composer update vendor/paqueteActualiza solo ese paquete (y sus dependencias). Mucho más quirúrgico.
composer outdatedQué paquetes tienen versión más nueva; en rojo, las mayores (rompen).
composer show vendor/paqueteFicha del paquete instalado: versión, dependencias, ruta.
composer why vendor/paqueteQuién exige este paquete. Oro para entender el grafo.
composer validate¿El json está bien formado y el lock sincronizado? El primer paso del pipeline.
composer auditCruza el lock con las bases de datos de vulnerabilidades conocidas.
composer dump-autoloadRegenera el autoloader (tras crear clases en carpetas nuevas, p. ej.).

Mención aparte para los scripts: alias de proyecto definidos en el json ("test": "phpunit", "lint": "php-cs-fixer check") que se lanzan con composer test. Dan un vocabulario común al equipo y al pipeline: todo el mundo ejecuta lo mismo, se llame como se llame la herramienta por debajo.

Errores típicos #

Editar algo en vendor/. Funciona hasta el siguiente composer install, que lo pisa sin avisar. Si un paquete necesita un arreglo: repórtalo, usa un fork mientras tanto, o aplica un parche gestionado — nunca la edición directa.

composer update en el deploy. El clásico doloroso: producción resolviendo versiones nuevas que nadie probó, en el peor momento posible. En deploy y en CI, siempre install; update es una tarea de desarrollo con su propia PR.

Resolver el conflicto del lock a mano. Dos ramas actualizaron dependencias y git marca conflicto en composer.lock. Editar sus miles de líneas a mano corrompe los hashes: se resuelve el conflicto del composer.json (si lo hay) y se deja que Composer regenere la parte del lock con composer update --lock o re-ejecutando el require.

Ignorar composer audit. Una dependencia con CVE conocida es una puerta abierta documentada públicamente — el atacante no tiene ni que buscarla. El audit cuesta segundos en el pipeline y te avisa el día que se publica, no el día que te toca.

Cuándo aplicarlo#

Úsalo cuando…

  • Cualquier proyecto PHP con dependencias externas: Composer es siempre la respuesta
  • Producción estable donde la reproducibilidad importa: fija versiones exactas en lugar de rangos
  • Herramientas que no van a producción (PHPUnit, PHPStan, Rector): declara en require-dev

No lo uses cuando…

  • No uses rangos amplios (* o >=) en producción: introducen cambios incompatibles sin avisar
  • No instales paquetes de desarrollo en producción: usa composer install --no-dev

Resumen #

Lo que te llevas

  • Composer resuelve el grafo completo de dependencias contra Packagist; require es para funcionar, require-dev para desarrollar (y fuera de producción con --no-dev).
  • El json declara la intención; el lock clava la foto exacta y SE COMMITEA. install obedece al lock; update lo reescribe y es una acción deliberada.
  • Semver es un contrato: mayor rompe, menor añade, parche corrige. ^ acepta todo menos la mayor; los tests validan la apuesta.
  • PSR-4 mapea namespaces a carpetas: la clase se encuentra calculando su ruta. En producción, --optimize-autoloader lo convierte en una consulta O(1).
  • Nunca edites vendor/, nunca update en el deploy, nunca resuelvas el lock a mano — y deja que composer audit vigile los CVE por ti.
