Subida de ficheros sin sustos

Un formulario de avatar parece la funcionalidad más inocente de la aplicación. Es también la única puerta por la que un desconocido deja un fichero entero en tu servidor y luego le pide a tu dominio que se lo sirva a otros.

Casi todos los fallos de subida de ficheros salen de la misma confusión: tratar el nombre y el tipo que manda el cliente como si fueran hechos. Son texto escrito por quien sube el fichero, y vale exactamente lo mismo que cualquier otro campo del formulario.

Por qué es tan peligroso #

Un campo de texto mal validado te deja un dato raro en la base de datos. Un fichero mal validado puede acabar en tres sitios mucho peores, y conviene tenerlos presentes porque cada defensa de esta lección tapa uno:

  • Ejecutarse en tu servidor. Un .php guardado dentro del docroot es código que el servidor web ejecutará cuando alguien pida su URL.
  • Ejecutarse en el navegador de otro usuario. Un HTML o un SVG con script servido desde tu dominio es un XSS almacenado con tus cookies a su alcance.
  • Tumbarte. Un fichero de varios gigas, una imagen de 50.000 × 50.000 píxeles o un zip que se descomprime a terabytes agotan disco, memoria o CPU.

Lo tercero tiene nombre en el OWASP API Security Top 10 2023: API4, consumo de recursos sin restricciones. Lo segundo es el mismo XSS de los fundamentos de OWASP, solo que la carga útil no llega en un parámetro sino dentro de un fichero que tú mismo publicas.

Validar por contenido, no por nombre #

Este es el código que aparece en demasiados proyectos. Tiene tres fallos, y ninguno se ve en una prueba manual con una foto normal:

php · vulnerable 
<?php

$upload = $_FILES['avatar'];

if ($upload['type'] === 'image/jpeg' || str_ends_with($upload['name'], '.jpg')) {
    move_uploaded_file($upload['tmp_name'], __DIR__ . '/public/uploads/' . $upload['name']);
}

$upload['type'] es la cabecera Content-Type de esa parte del formulario: la pone el cliente y se falsifica con una línea de curl. La extensión también la elige él. Y el nombre original acaba en una ruta pública, así que shell.php pasa si declara image/jpeg, y un nombre con ../ intenta salir del directorio.

La única fuente fiable es el propio contenido. finfo lee los primeros bytes del fichero (los magic bytes) y deduce el tipo real. Con eso se decide contra una lista de permitidos, nunca de prohibidos, y la extensión final la pones tú a partir del tipo detectado:

php · AvatarUploader.php 
<?php

declare(strict_types=1);

final class AvatarUploader
{
    private const MAX_BYTES = 5 * 1024 * 1024;
    private const EXTENSION_BY_MIME_TYPE = [
        'image/jpeg' => 'jpg',
        'image/png' => 'png',
        'image/webp' => 'webp',
    ];

    public function __construct(private readonly string $privateStorageDirectory)
    {
    }

    public function store(string $temporaryPath): string
    {
        if (filesize($temporaryPath) > self::MAX_BYTES) {
            throw new FileTooLarge();
        }

        $mimeType = (new finfo(FILEINFO_MIME_TYPE))->file($temporaryPath);
        $extension = self::EXTENSION_BY_MIME_TYPE[$mimeType] ?? throw new UnsupportedFileType($mimeType);
        $storedName = bin2hex(random_bytes(16)) . '.' . $extension;

        if (!move_uploaded_file($temporaryPath, $this->privateStorageDirectory . '/' . $storedName)) {
            throw new UploadFailed();
        }

        return $storedName;
    }
}

Los frameworks ya traen esto resuelto, y conviene saber qué método mira qué. En Symfony, UploadedFile::getMimeType() y guessExtension() miran el contenido; getClientMimeType() y getClientOriginalExtension() repiten lo que dijo el cliente. En Laravel, las reglas mimes y mimetypes también deducen el tipo del contenido.

php · Symfony 7 y Laravel 11 
<?php

#[Assert\File(maxSize: '5M', mimeTypes: ['image/jpeg', 'image/png', 'image/webp'])]
public ?UploadedFile $avatar = null;

$request->validate([
    'avatar' => ['required', 'file', 'max:5120', 'mimetypes:image/jpeg,image/png,image/webp'],
]);

El tipo real no garantiza que sea inofensivo

Un fichero puede ser un JPEG válido y llevar PHP en sus metadatos: es un políglota. finfo te dice que es una imagen, no que sea inocua. Por eso la validación es la primera capa y no la única: lo que de verdad lo neutraliza es dónde lo guardas y cómo lo sirves.

Dónde y con qué nombre se guarda #

El nombre lo generas tú. Un identificador aleatorio elimina de golpe el path traversal, las colisiones, los caracteres raros y las extensiones dobles. El nombre original, si lo necesitas para la descarga, va a la base de datos como dato, nunca a una ruta. Laravel ya lo hace así: store() genera un nombre aleatorio con la extensión deducida del contenido.

Fuera del docroot. Si el fichero no está bajo public/, el servidor web no puede ejecutarlo ni servirlo directamente: cualquier acceso pasa por tu código, que es donde viven la autorización y las cabeceras. La alternativa natural es un almacenamiento de objetos (S3 o compatible), que además saca los ficheros de la máquina y no ejecuta nada.

Guardar así

  • Nombre aleatorio y extensión según el tipo detectado
  • Fuera del docroot o en almacenamiento de objetos
  • Nombre original y tipo en la base de datos
  • Cada descarga pasa por una comprobación de permisos

No guardar así

  • Con el nombre que mandó el cliente
  • En public/uploads con PHP activo
  • Con la extensión copiada del original
  • Con una URL pública adivinable

Servirlo sin que el navegador lo ejecute #

Al devolver el fichero, dos cabeceras deciden qué hace el navegador con él. Content-Type debe ser el tipo que validaste y guardaste, no uno deducido otra vez del nombre. Content-Disposition: attachment fuerza la descarga en vez de pintarlo en tu dominio; reserva inline para los tipos que de verdad quieres mostrar, como imágenes rasterizadas o PDF. Súmale X-Content-Type-Options: nosniff, que ya viste en las cabeceras que importan, para que el navegador no reinterprete el contenido por su cuenta.

php · DocumentDownloadController.php (Symfony 7) 
<?php

$this->denyAccessUnlessGranted('DOCUMENT_VIEW', $document);

$response = new BinaryFileResponse($this->privateStorage->absolutePathOf($document));
$response->headers->set('Content-Type', $document->mimeType());
$response->headers->set('X-Content-Type-Options', 'nosniff');
$response->setContentDisposition(
    ResponseHeaderBag::DISPOSITION_ATTACHMENT,
    $document->originalName(),
    $document->asciiFallbackName(),
);

return $response;

Con almacenamiento de objetos, en vez de pasar los bytes por PHP generas una URL firmada: válida unos minutos, para un objeto concreto, y emitida solo después de comprobar los permisos. El bucket sigue siendo privado; la firma es el permiso temporal. Laravel la genera con temporaryUrl(), y en S3 puedes fijar en la propia firma la cabecera de descarga:

php · URL firmada (Laravel 11) 
<?php

Gate::authorize('view', $document);

$url = Storage::disk('s3')->temporaryUrl($document->path, now()->addMinutes(5), [
    'ResponseContentDisposition' => 'attachment',
]);

La misma idea sirve en sentido contrario: una URL firmada de subida deja que el cliente mande el fichero directamente al bucket sin pasar por tu servidor. Solo que entonces la validación no ha ocurrido todavía: sube a una zona de cuarentena, y un proceso tuyo lo valida antes de moverlo a su sitio definitivo.

Imágenes, SVG y comprimidos #

Imágenes: reprocésalas. Decodificar y volver a codificar con GD o Imagick produce un fichero nuevo, con solo los píxeles: se van los metadatos (y con ellos la geolocalización de la foto) y casi cualquier carga escondida. Antes de decodificar, comprueba las dimensiones con getimagesize(), que solo lee la cabecera: una imagen pequeña en bytes puede ocupar gigas al descomprimirse en memoria.

SVG: no es una imagen, es un documento. Es XML, admite <script> y manejadores de eventos, y si lo abres desde tu dominio ejecuta JavaScript con tu origen. Las salidas razonables son no aceptarlo, convertirlo a PNG al subirlo o servirlo siempre como attachment desde un dominio aparte. Mostrarlo con <img> no ejecuta scripts, pero nada impide que alguien abra la URL directamente.

Comprimidos: no te fíes de lo que dicen. Una zip bomb ocupa kilobytes y se expande a gigas. Y cada entrada lleva un nombre que puede contener ../ para escribir fuera del destino (zip slip). Revisa el índice antes de extraer:

php · ZipInspector.php 
<?php

declare(strict_types=1);

final class ZipInspector
{
    private const MAX_ENTRIES = 1_000;
    private const MAX_UNCOMPRESSED_BYTES = 200 * 1024 * 1024;

    public function assertSafe(ZipArchive $archive): void
    {
        if ($archive->numFiles > self::MAX_ENTRIES) {
            throw new ArchiveTooLarge();
        }

        $uncompressedBytes = 0;

        for ($index = 0; $index < $archive->numFiles; $index++) {
            $entry = $archive->statIndex($index);

            if (str_contains($entry['name'], '..') || str_starts_with($entry['name'], '/')) {
                throw new UnsafeArchiveEntry($entry['name']);
            }

            $uncompressedBytes += $entry['size'];

            if ($uncompressedBytes > self::MAX_UNCOMPRESSED_BYTES) {
                throw new ArchiveTooLarge();
            }
        }
    }
}

El tamaño del índice lo declara el propio zip, así que también puede mentir: al extraer, cuenta los bytes que escribes y corta al pasar el límite.

Errores típicos #

Validar bien y servir mal

El fallo más común no está en la subida sino en la descarga: el fichero se valida con cuidado y luego se publica en una URL pública, sin Content-Type fijado ni attachment, y sin comprobar quién lo pide. Cualquiera que adivine o reciba la URL lo ve, y el navegador decide cómo interpretarlo.

Límites que no coinciden

El tamaño máximo se aplica en tres capas: el proxy (client_max_body_size en nginx), PHP (upload_max_filesize y post_max_size) y tu validación. Si la de PHP es menor que la tuya, el fichero llega vacío con un error de subida y tu código lo trata como «no se envió nada». Ajusta las tres y comprueba siempre el campo error de la subida.

  • Lista de extensiones prohibidas en vez de permitidas: siempre falta alguna (.phtml, .phar, .htaccess).
  • Procesar ficheros pesados dentro de la petición: el reprocesado de imágenes va mejor en una cola, con límites de memoria y tiempo.
  • URLs firmadas de horas o días: son credenciales al portador, y se comparten, se cachean y acaban en logs.

Cómo testearlo #

Cada defensa tiene un test que la rompe si alguien la quita. Los imprescindibles: un PHP disfrazado de JPEG, un fichero un byte por encima del límite, un SVG con script y un zip con una entrada ../. Con los fakes de Laravel cuesta pocas líneas:

php · AvatarUploadTest.php (Laravel 11) 
<?php

public function test_rejects_php_disguised_as_jpeg(): void
{
    Storage::fake('s3');
    $disguisedScript = UploadedFile::fake()->createWithContent('foto.jpg', '<?php system($_GET["c"]);');

    $this->actingAs(User::factory()->create())
        ->postJson('/api/avatar', ['avatar' => $disguisedScript])
        ->assertUnprocessable();

    Storage::disk('s3')->assertDirectoryEmpty('avatars');
}

Y desde fuera, lo que decide si un fichero se ejecuta en el navegador son las cabeceras de la descarga. Míralas sobre un fichero real:

bash · cabeceras de una descarga 
curl -sI https://app.example.com/documents/42/download | grep -iE 'content-type|content-disposition|nosniff'

Cuándo aplicarlo #

Aplícalo entero cuando…

  • Cualquier usuario externo puede subir ficheros
  • Lo subido se sirve a otros usuarios desde tu dominio
  • Procesas el contenido: miniaturas, extracción, importación
  • Aceptas comprimidos o formatos documentales

Puedes aligerarlo cuando…

  • Solo suben administradores autenticados de confianza
  • El fichero solo lo vuelve a descargar quien lo subió
  • Nunca se descomprime ni se interpreta en el servidor
  • Es una herramienta interna sin acceso desde fuera

Aligerar no es quitar lo básico: nombre generado, fuera del docroot y límite de tamaño son baratos y van siempre. Si no quieres mantener nada de esto, la alternativa es delegarlo en un servicio gestionado de ficheros o imágenes que valide y transforme por ti, y quedarte solo con la autorización.

Resumen #

Lo que te llevas

  • El nombre y el tipo que manda el cliente son texto suyo: el tipo real se saca del contenido con finfo, contra una lista de permitidos.
  • El nombre lo generas tú y el fichero vive fuera del docroot o en un bucket privado: así ni se ejecuta ni se sirve sin pasar por tu código.
  • Al servir, Content-Type fijado, nosniff y attachment salvo lo que quieras mostrar; con S3, URLs firmadas de pocos minutos tras comprobar permisos.
  • Las imágenes se reprocesan, el SVG se trata como documento con script y los zip se inspeccionan antes de extraer: tamaño total, número de entradas y rutas.
  • El límite de tamaño vive en tres capas, proxy, PHP y aplicación, y las tres tienen que cuadrar.
