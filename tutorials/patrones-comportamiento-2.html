Template Method, Command y Chain of Responsibility

Template Method fija la estructura de un algoritmo y deja los detalles a las subclases. Command convierte una operación en un objeto — la clave para deshacer, encolar y auditar. Chain of Responsibility es el patrón detrás del middleware que llevas usando desde el día uno.

Los tres patrones de esta lección tienen algo en común: organizan operaciones en estructuras reutilizables. Template Method reutiliza la secuencia. Command reutiliza la operación como objeto. Chain of Responsibility reutiliza el flujo de procesamiento.

Template Method #

El problema: tienes varios procesos que comparten la misma secuencia de pasos pero difieren en la implementación de alguno de ellos. Sin un patrón, duplicas la estructura en cada variante.

Template Method define el esqueleto del algoritmo en un método de la clase base y deja que las subclases implementen los pasos que varían. Los pasos fijos se heredan; los variables se sobreescriben.

php · ReportGenerator.php 
<?php

declare(strict_types=1);

abstract class ReportGenerator
{
    // El template method: fija la secuencia
    final public function generate(DateRange $range): string
    {
        $data   = $this->fetchData($range);
        $rows   = $this->formatRows($data);
        $header = $this->buildHeader($range);

        return $this->render($header, $rows);
    }

    // Paso fijo: igual para todos los reportes
    private function buildHeader(DateRange $range): string
    {
        return "Reporte del {$range->from()} al {$range->to()}";
    }

    // Pasos variables: cada subclase los implementa a su manera
    abstract protected function fetchData(DateRange $range): array;
    abstract protected function formatRows(array $data): array;
    abstract protected function render(string $header, array $rows): string;
}

class CsvReportGenerator extends ReportGenerator
{
    protected function fetchData(DateRange $range): array { /* consulta SQL */ }
    protected function formatRows(array $data): array { /* mapea a filas CSV */ }
    protected function render(string $header, array $rows): string { /* genera CSV */ }
}

class HtmlReportGenerator extends ReportGenerator
{
    protected function fetchData(DateRange $range): array { /* misma consulta */ }
    protected function formatRows(array $data): array { /* mapea a <tr> */ }
    protected function render(string $header, array $rows): string { /* genera HTML */ }
}

El final en el template method es deliberado: la secuencia no se debe sobreescribir, solo los pasos variables. Template Method es uno de los pocos casos donde la herencia tiene sentido: la relación es genuinamente "es un tipo de", y la lógica compartida es la secuencia, no el estado.

Template Method vs Strategy

Ambos varían partes de un algoritmo. La diferencia: Template Method usa herencia (la variación ocurre en subclases, en tiempo de compilación). Strategy usa composición (la variación ocurre inyectando un objeto, en tiempo de ejecución). En código moderno se prefiere Strategy cuando la variación puede cambiar en runtime o necesitas combinar variantes.

Command #

El problema: quieres desacoplar el objeto que solicita una operación del objeto que la ejecuta, o quieres tratar operaciones como objetos de primera clase para encolarlas, registrarlas o deshacerlas.

Command encapsula una solicitud como un objeto que contiene toda la información necesaria para ejecutarla: qué hacer, sobre qué objeto y con qué parámetros.

php · Command.php 
<?php

declare(strict_types=1);

// El comando: una operación encapsulada como objeto
interface Command
{
    public function execute(): void;
}

// Un comando concreto
class ActivateUserCommand implements Command
{
    public function __construct(
        private readonly UserRepository $users,
        private readonly int $userId
    ) {}

    public function execute(): void
    {
        $user = $this->users->findById($this->userId);
        $user->activate();
        $this->users->save($user);
    }
}

// El invoker: ejecuta comandos sin saber qué hace cada uno
class CommandBus
{
    private array $history = [];

    public function dispatch(Command $command): void
    {
        $command->execute();
        $this->history[] = $command;
    }
}

Usos del Command #

La potencia del Command no está en ejecutar una operación simple, sino en lo que se puede hacer cuando la operación es un objeto:

Caso de usoCómo lo habilita el Command
Deshacer (undo) Cada Command implementa también un método undo(). El histórico de commands ejecutados permite revertirlos en orden inverso.
Cola de operaciones Los commands se serializan y enolan en una cola (Redis, RabbitMQ). Un worker los consume y ejecuta de forma asíncrona.
Auditoría Cada command que pasa por el bus queda registrado con su tipo, parámetros y usuario que lo disparó.
Command Bus de CQRS El Command del patrón GoF es la base del Command Bus que separa escrituras de lecturas en CQRS.

Command en frameworks PHP

Los comandos de consola de Symfony (Command::execute()), los jobs de Laravel (handle()), los mensajes de Messenger — todos implementan Command. La diferencia con el GoF puro es que en Symfony/Laravel el CommandBus es el framework: él resuelve qué handler ejecuta qué mensaje.

Chain of Responsibility #

El problema: una solicitud necesita pasar por varios manejadores en secuencia. Cada manejador decide si procesa la solicitud, la transforma y la pasa al siguiente, o la corta. El emisor no sabe cuántos manejadores hay ni en qué orden están.

Este es exactamente el patrón middleware que Symfony, Laravel y prácticamente cualquier framework HTTP implementan.

php · Middleware.php 
<?php

declare(strict_types=1);

interface RequestHandler
{
    public function handle(Request $request): Response;
}

interface Middleware
{
    public function process(Request $request, RequestHandler $next): Response;
}

// Cada middleware decide si pasa al siguiente o corta la cadena
class AuthMiddleware implements Middleware
{
    public function process(Request $request, RequestHandler $next): Response
    {
        if (!$request->hasValidToken()) {
            return new Response(401);
        }

        return $next->handle($request);
    }
}

class RateLimitMiddleware implements Middleware
{
    public function process(Request $request, RequestHandler $next): Response
    {
        if ($this->isRateLimited($request->ip())) {
            return new Response(429);
        }

        return $next->handle($request);
    }

    private function isRateLimited(string $ip): bool { /* ... */ }
}

class LoggingMiddleware implements Middleware
{
    public function process(Request $request, RequestHandler $next): Response
    {
        $start    = microtime(true);
        $response = $next->handle($request);
        $duration = microtime(true) - $start;

        $this->logger->info("{$request->method()} {$request->path()} {$response->status()} {$duration}ms");

        return $response;
    }
}

La cadena se construye componiendo middlewares. Cada uno envuelve al siguiente — es un Decorator de la solicitud. La diferencia con el Decorator puro: en Chain of Responsibility, cada eslabón puede cortar la cadena (devolver directamente sin llamar al siguiente), lo que lo hace adecuado para autenticación, rate limiting y validación.

Sin cadena

El controlador verifica autenticación, rate limit y logging antes de ejecutar la lógica. Todo acoplado, imposible de reutilizar, difícil de testear por separado.

Con cadena

Cada responsabilidad en su propio middleware. El controlador solo tiene lógica de negocio. La cadena se configura en el framework y se puede reordenar sin tocar el código.

Cuándo aplicarlo

Aplícalo cuando…

  • Chain of Responsibility: la solicitud debe pasar por varios handlers y cada uno puede cortarla o pasarla.
  • Command: quieres encapsular operaciones para encolarlas, deshacerlas o auditarlas.
  • State: el comportamiento cambia radicalmente según el estado y los condicionales por estado crecen.

No lo uses cuando…

  • Chain of Responsibility si la solicitud siempre va al mismo handler: usa la llamada directa.
  • Command si la operación es simple y no necesita cola, undo ni auditoría.
  • State si el objeto solo tiene dos o tres estados simples: un enum con un switch es suficiente.

Resumen #

Lo que te llevas

  • Template Method: la clase base fija la secuencia; las subclases implementan los pasos variables. Usa herencia para reutilizar la estructura.
  • Template Method usa herencia; Strategy usa composición. Prefiere Strategy cuando la variación puede cambiar en runtime.
  • Command: encapsula una operación como objeto. Habilita colas, auditoría, undo y el Command Bus de CQRS.
  • Chain of Responsibility: la solicitud pasa por una cadena de manejadores. Cada uno procesa y pasa, o corta. Es el patrón middleware que usan todos los frameworks HTTP.
