Rules, skills, subagentes, MCP y hooks: las piezas del agente

Un agente sin configurar es un recién llegado en cada sesión. Cinco piezas cambian eso: las rules dicen lo que se cumple siempre, las skills enseñan procedimientos cuando hacen falta, los subagentes aíslan trabajo, MCP conecta sistemas y los hooks ejecutan comprobaciones sin depender de que el modelo se acuerde. Esta lección explica qué es cada una y cuál elegir.

Las cinco piezas se diferencian sobre todo en cuándo entran en el contexto y quién decide usarlas: el harness, el modelo o un evento. Elegir bien es decidir qué tiene que estar siempre, qué solo a veces y qué no puede depender de la memoria del modelo.

El contexto del repositorio #

El agente puede leer tu código, pero no adivina tus convenciones ni tus decisiones. Por eso casi todos los harnesses leen un fichero de instrucciones del proyecto (CLAUDE.md, AGENTS.md o similar) donde dejas escritas las reglas: estilo, arquitectura, qué no tocar, cómo correr los tests. Es contexto permanente que no tienes que repetir en cada sesión.

Invierte en el contexto permanente

Cada regla que escribes una vez en el fichero del proyecto es una corrección que no tendrás que repetir mil veces. Un buen documento de convenciones convierte al agente en alguien que «conoce la casa», en vez de un recién llegado en cada sesión.

Las cinco piezas de un vistazo #

PiezaQué aportaCuándo se cargaQuién decide
Rules (CLAUDE.md, .claude/rules/)Contexto y reglas del proyectoSiempre al inicio, o al tocar ciertos archivosEl harness
SkillConocimiento o procedimiento para un tipo de tareaSolo cuando la tarea lo requiereEl modelo, por la descripción
SubagenteTrabajo delegado y aislado en otra ventanaCuando el principal le hace un encargoEl modelo principal

HookUn script que se ejecuta en un eventoSiempre que ocurre el eventoEl harness, sin preguntar al modelo

Una forma de verlo

El MCP le da manos para tocar sistemas; la skill le enseña cómo hacer bien una tarea concreta; la rule le dice lo que no se negocia; el hook lo comprueba pase lo que pase.

Rules: lo que se cumple siempre #

Las rules son instrucciones persistentes que el harness carga en el contexto sin que el modelo tenga que decidirlo: normas, convenciones y restricciones que deben cumplirse siempre (o siempre que se toquen ciertos archivos). Son lo contrario de una skill: la skill se carga cuando el modelo la considera útil; la regla está ahí de entrada.

Buenas prácticas:

  • Cortas e imperativas: «usa X», «nunca Y». Cada línea ocupa contexto en todas las sesiones.
  • Lo general en usuario, lo del stack en proyecto: tu CLAUDE.md global con estilo y principios; el del repo con el stack y sus convenciones.
  • Partir por temas con paths: las reglas de tests no necesitan estar cargadas mientras se edita una migración.
  • Si una regla crece y se convierte en procedimiento, pásala a skill y deja en la regla solo la referencia.

Dónde vive cada nivel en Claude Code, la carpeta .claude/rules/ con paths y los imports, en rules: las reglas del proyecto, que además explica qué merece ser regla y por qué el porqué viaja con ella.

Rules que apuntan a skills #

Como las reglas están siempre en contexto, son el mejor sitio para obligar a usar una skill. La descripción de una skill hace que el modelo pueda elegirla; una regla hace que deba usarla.

markdown · .claude/rules/flujo.md (proyecto «tienda») 
# Reglas de flujo

- Para cualquier commit, usa siempre la skill `git-commits`.
- Antes de crear o modificar tablas, usa la skill `nueva-migracion`.
- Nunca escribas una migración a mano sin esa skill.

Como con las skills entre sí, es una referencia por nombre en lenguaje natural, no un vínculo técnico. Si la skill no existe, la regla no falla: simplemente el modelo no la encuentra.

Va en…Qué
ReglaLo que debe cumplirse siempre y es corto (convenciones, prohibiciones, «usa la skill X para Y»)
SkillEl cómo detallado de una tarea concreta, que solo hace falta a veces
Regla + skillLa regla garantiza que se use; la skill contiene el procedimiento

Caso práctico: tests unitarios, ¿rule o skill? #

Lo mejor es combinarlas: las normas cortas e innegociables, en una regla limitada a los archivos de test; el procedimiento, las plantillas y los ejemplos, en una skill.

Diferencia clave: una regla con paths se activa por archivos (cuando se tocan archivos de tests/). Una skill se activa por intención (cuando el modelo entiende que la tarea es escribir tests). Son disparadores distintos y se complementan.

Va en la regla (.claude/rules/testing.md)Va en la skill (tests-unitarios/)
Convenciones que se aplican siempre: nombres, estructura Arrange-Act-Assert, un concepto por testEl procedimiento paso a paso para crear un test nuevo
Prohibiciones: no tocar la BD real, no mockear lo que se está probandoPlantillas de clase de test y ejemplos buenos y malos
«Para crear tests, usa la skill tests-unitarios»Scripts: lanzar PHPUnit, medir cobertura
Unas pocas líneasTodo el detalle que haga falta

Criterio rápido:

  • Si cabe en unas pocas líneas y debe cumplirse siempre que se toque un test: regla con paths.
  • Si es largo, tiene pasos, plantillas o scripts, o se necesita antes de que exista el archivo (crear un test desde cero): skill.
  • Si se repite en las dos: déjalo solo en la skill y que la regla apunte a ella.

Caso práctico: convenciones de equipo #

Las convenciones de equipo van en rules a nivel de proyecto (.claude/rules/ dentro del repo, versionado en Git), no en skills. Una convención debe cumplirse siempre, y una skill solo se carga si el modelo decide que encaja: si no la elige, la convención se ignora.

  • Partir por temas con paths: php.md para src/, testing.md para tests/, migraciones.md para migrations/. Así cada convención solo ocupa contexto cuando toca.
  • Lo transversal, sin paths: nombres de ramas, formato de commits, idioma del código. Esto se carga siempre.
  • Las skills, para procedimientos: cuando una convención implica un proceso con pasos o plantillas (crear un endpoint, una migración), el cómo va a una skill y la regla apunta a ella.
  • Documentación larga ya existente: no copiarla; importarla con @ruta o dejar que la skill la referencie en su carpeta de referencias.
  • Tus preferencias personales, en tu ~/.claude/CLAUDE.md, no en el repo, para no imponérselas al equipo.

Caso práctico: convenciones por capa #

¿Una regla por tipo de clase? Sí: una regla por capa, cada una con su patrón de paths, más una regla corta de arquitectura sin paths que explique cómo se relacionan las capas. Las reglas de capa dicen cómo es cada pieza; la de arquitectura, cómo encajan entre sí. En la tienda de ejemplo, las capas son controllers, casos de uso y repositorios:

texto · .claude/rules/ de la tienda 
.claude/rules/
├── arquitectura.md   # sin paths: siempre cargada
├── controllers.md    # paths: src/**/Controller/**/*.php
├── casos-de-uso.md   # paths: src/**/UseCase/**/*.php
└── repositorios.md   # paths: src/**/Repository/**/*.php

Por qué la de arquitectura va sin paths: para decidir dónde va la lógica al crear un controller, el modelo necesita saber qué es un caso de uso y qué no puede hacer un controller. Si esa relación solo está en casos-de-uso.md, no la verá mientras trabaja en un controller.

markdown · arquitectura.md 
# Arquitectura de la tienda

- Los controllers solo traducen HTTP: reciben la petición, la convierten en un comando y devuelven la respuesta.
- Cada operación de negocio es un caso de uso con un único método público, `__invoke`.
- Los casos de uso hablan con la base de datos solo a través de repositorios; nunca con el EntityManager directamente.
- Flujo permitido: Controller → UseCase → Repository. Nunca al revés ni saltando capas.
markdown · controllers.md 
---
paths:
  - "src/**/Controller/**/*.php"
---

# Controllers

- Un controller invocable por ruta; sin lógica de negocio ni acceso a repositorios.
- Dependencias solo por constructor.
- La entrada se mapea a un DTO con el serializer; nunca se lee `$request` a mano.

Notas:

  • Patrones con ** (src/**/Controller/**) sirven tanto si el proyecto está organizado por capas (src/Controller/) como por módulos (src/Pedidos/Controller/).
  • Alternativa equivalente: un CLAUDE.md dentro de cada carpeta. La carpeta rules/ con paths tiene la ventaja de concentrar todas las convenciones en un solo sitio.
  • Los ejemplos de reglas concretas son ilustrativos; cada equipo pone las suyas.

Skills: procedimientos bajo demanda #

Una skill es un paquete de instrucciones y recursos que el agente carga solo cuando le hace falta. Es una carpeta con un archivo SKILL.md (nombre, descripción e instrucciones) y, opcionalmente, scripts, plantillas o documentación de apoyo.

Cómo funciona (carga progresiva): al empezar la sesión, el modelo solo ve el nombre y la descripción de cada skill, unas pocas líneas. Cuando una tarea encaja con una descripción, carga el SKILL.md completo y, si hace falta, los archivos que este referencia. Así puedes tener muchas skills sin llenar la ventana de contexto.

Ejemplo: en la tienda, una skill nueva-migracion con las convenciones de base de datos del proyecto y un script que genera el esqueleto. Claude solo la lee cuando le pides una migración.

La anatomía completa —estructura de carpetas, el frontmatter de SKILL.md, las tres capas de carga y cómo se escribe una descripción que se active bien— está en skills: flujos empaquetados.

Subagentes: trabajo en otra ventana #

Un subagente es un agente que el principal lanza para una tarea concreta, con su propia ventana de contexto limpia. Trabaja por su cuenta y devuelve solo un resumen del resultado, de modo que el contexto de la sesión principal no se llena con todo lo que el subagente ha leído o probado.

  1. El agente principal decide delegar y escribe un encargo: qué hacer y qué devolver.
  2. El subagente arranca con su prompt de sistema y ese encargo. No ve la conversación principal.
  3. Trabaja con sus herramientas: lee archivos, busca, ejecuta.
  4. Devuelve un resumen final. Solo eso entra en el contexto principal.

La comunicación es en una sola dirección por tarea

Encargo y resultado. Si el encargo es pobre, el subagente trabaja a ciegas; si el resumen es pobre, el principal pierde información.

UsoEjemplo
Explorar sin ensuciar el contexto«Busca dónde se calcula el IVA en todo el proyecto y dime los archivos y métodos»
Trabajo en paraleloVarios subagentes investigando partes distintas a la vez
Revisión con ojos nuevosUn revisor de código o un QA que no ha visto la implementación
EspecializaciónHerramientas restringidas o un modelo más barato (Haiku) para tareas mecánicas

Subagente vs. skill

SkillSubagente
Dónde se ejecutaEn el contexto principalEn un contexto aparte
Qué aportaConocimiento o procedimientoTrabajo delegado y aislado
Coste en contexto principalTodo lo que carga y haceSolo el resumen final
Cuándo usarloCuando el principal necesita saber cómo hacer algoCuando la tarea genera mucho ruido o necesita ojos nuevos

Se combinan: un subagente puede usar skills, igual que el principal. Cómo se define uno en .claude/agents/, sus límites, los patrones habituales y cómo escribir el encargo, en subagentes y delegación.

MCP: conectar sistemas #

MCP (Model Context Protocol) es un protocolo estándar y abierto para conectar un harness con herramientas y datos externos. Lo creó Anthropic en 2024 y hoy lo soportan la mayoría de harnesses.

Analogía: es el USB-C de la IA. Sin MCP, cada harness tendría que programar su propia integración con GitHub, con MySQL, con Gmail… Con MCP, alguien escribe un servidor una vez y funciona en cualquier harness compatible (Claude Code, Cursor, la app de Claude, etc.).

PiezaQué es
HostLa aplicación de IA, es decir, el harness (Claude Code, por ejemplo)
Cliente MCPEl componente del host que habla con cada servidor
Servidor MCPUn programa que expone capacidades de un sistema concreto (una base de datos, una API, el sistema de archivos)

Qué expone un servidor:

  • Tools: acciones que el modelo puede invocar («ejecuta esta consulta», «crea una issue»).
  • Resources: datos que se pueden leer (archivos, esquemas, documentos).
  • Prompts: plantillas predefinidas que el usuario puede lanzar.

Cómo se comunica: JSON-RPC, en local por stdio (el host arranca el servidor como un proceso) o en remoto por HTTP.

Cómo encaja con lo anterior: el harness pregunta al servidor qué herramientas tiene, mete sus descripciones en la ventana de contexto y, cuando el modelo decide usar una, el harness se la pide al servidor y le devuelve el resultado al modelo. Es el bucle del agente, con herramientas que vienen de fuera.

Ojo con el contexto

Cada servidor conectado añade sus descripciones de herramientas a la ventana, así que conectar muchos la llena y puede empeorar el rendimiento.

Ejemplos prácticos: servidores MCP para GitHub, MySQL o PostgreSQL, Docker, Playwright (para controlar un navegador), Gmail o Google Drive. También puedes escribir el tuyo propio; hay SDKs oficiales en varios lenguajes, incluido PHP. Un servidor mínimo funcional, cómo conectarlo y cuándo compensa uno para una herramienta interna, en MCP: conectar herramientas.

Hooks: lo que no depende de la memoria del modelo #

Un hook es un comando o script que el harness ejecuta automáticamente cuando ocurre un evento concreto: antes de usar una herramienta, después de editar un archivo, al terminar una respuesta… A diferencia de una rule, no depende de que el modelo se acuerde: se ejecuta siempre.

Rule

  • «Pasa PHPStan después de editar.»
  • El modelo puede olvidarlo.
  • Para convenciones que no se pueden comprobar con código.

Hook

  • Ejecuta PHPStan él mismo tras cada edición.
  • No depende de la memoria del modelo.
  • Para lo que sí se comprueba con código.

Los eventos, cómo se configuran y cómo devuelven el error al agente para que lo corrija solo, en hooks y permisos.

Cuándo aplicarlo #

Úsalo cuando…

  • Corriges lo mismo al agente por segunda vez: es una rule (si es corta) o una skill (si es un procedimiento)
  • Una tarea exploratoria va a leer mucho: delégala a un subagente y quédate con el resumen
  • Algo se puede comprobar con código: ponlo en un hook, no en una rule

No lo uses cuando…

  • La instrucción es solo de esta tarea: va en el prompt, no en una rule que se paga en cada sesión
  • Una convención debe cumplirse siempre: no la escondas en una skill que el modelo puede no elegir
  • La tarea es pequeña: explicar el encargo a un subagente cuesta más que hacerla

Resumen #

Lo que te llevas

  • Rules para lo que se cumple siempre, cortas y partidas con paths; una regla puede obligar a usar una skill.
  • Skills para procedimientos: el modelo solo ve su descripción hasta que la tarea encaja.
  • Subagentes para aislar ruido, paralelizar o revisar con ojos nuevos: solo vuelve el resumen.
  • MCP conecta sistemas de forma estándar, a cambio de contexto; los hooks comprueban sin depender de que el modelo se acuerde.
