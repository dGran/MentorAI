Por qué tipar Python

Python es dinámicamente tipado en runtime: una variable puede contener cualquier tipo sin que el intérprete se queje. Las anotaciones de tipo son solo metadatos que Python ignora durante la ejecución. La diferencia la pone una herramienta externa como mypy, que analiza el código estáticamente y detecta inconsistencias antes de que lleguen a producción.

El valor es concreto. mypy encuentra errores que los tests no cubren: pasar un None donde se espera un str, llamar a un método que no existe en un tipo, o devolver el tipo incorrecto desde una función. Además, las anotaciones son documentación ejecutable: un IDE con soporte de tipos autocompletará basándose en ellas y te avisará al instante si algo no cuadra.

Las anotaciones no cambian el comportamiento en runtime. def suma(a: int, b: int) -> int acepta strings en runtime si se los pasas; Python no valida. La validación la hace mypy en tiempo de análisis, no Python al ejecutar. Para validación en runtime usa Pydantic o beartype.

Anotaciones básicas

Las anotaciones se aplican a variables, parámetros y valores de retorno. La sintaxis es la misma en los tres casos:

nombre: str = "Ana"
edad: int = 30
es_activo: bool = True
precio: float = 9.99

usuarios: list[str] = ["Ana", "Luis"]
config: dict[str, int] = {"timeout": 30, "reintentos": 3}
coordenadas: tuple[float, float] = (40.416, -3.703)

Para funciones, las anotaciones van en los parámetros y el retorno:

def saludar(nombre: str, veces: int = 1) -> str:
    return (nombre + "\n") * veces


def registrar_evento(
    tipo: str,
    payload: dict[str, object],
    es_critico: bool = False,
) -> None:
    pass


def cargar_ids(ruta: str) -> list[int]:
    with open(ruta) as fichero:
        return [int(linea.strip()) for linea in fichero]

El tipo None en el retorno indica que la función no devuelve valor útil (equivalente a void en otros lenguajes). Si una función puede retornar sin un return explícito, mypy infiere None como tipo de retorno implícito cuando usas --strict.

mypy infiere los tipos de las expresiones locales, así que no necesitas anotar cada variable dentro de una función. Anota los límites del módulo: los parámetros de las funciones públicas y sus retornos. Es donde los contratos importan.

Tipos genéricos, Optional, Union, Literal

Opcional y unión. Cuando una función puede devolver None, el tipo de retorno es str | None (Python 3.10+) o Optional[str]. mypy fuerza a comprobar el None antes de usar el valor:

from typing import Optional


def buscar_usuario(identificador: int) -> str | None:
    if identificador == 1:
        return "Ana"
    return None


resultado = buscar_usuario(42)
print(resultado.upper())        # Error: Item "None" of "str | None" has no attribute "upper"

if resultado is not None:
    print(resultado.upper())    # OK: mypy sabe que aquí es str

Union[str, int] (o str | int en Python 3.10+) indica que el valor puede ser de varios tipos. mypy te obliga a discriminar antes de usar operaciones específicas de cada tipo:

def convertir_a_euros(valor: str | int | float) -> float:
    if isinstance(valor, str):
        return float(valor.replace(",", "."))
    return float(valor)

Literal. Restringe un parámetro a un conjunto fijo de valores conocidos en tiempo de análisis. mypy detecta llamadas con valores fuera del conjunto:

from typing import Literal

Direccion = Literal["norte", "sur", "este", "oeste"]
Nivel = Literal["debug", "info", "warning", "error", "critical"]


def mover(pasos: int, direccion: Direccion) -> None:
    pass


def registrar(mensaje: str, nivel: Nivel = "info") -> None:
    pass


mover(3, "norte")       # OK
mover(3, "arriba")      # Error: Argument 2 has incompatible type "str"; expected Literal[...]

TypeVar. Para funciones que reciben un tipo y devuelven el mismo tipo sin conocerlo de antemano:

from typing import TypeVar

T = TypeVar("T")


def primero(elementos: list[T]) -> T:
    return elementos[0]


valor: int = primero([1, 2, 3])     # mypy infiere T = int
nombre: str = primero(["a", "b"])   # mypy infiere T = str

Protocols: tipado estructural

Python usa duck typing: si un objeto tiene los métodos necesarios, se puede usar aunque no herede de ninguna clase en particular. Protocol formaliza ese contrato sin exigir herencia explícita:

from typing import Protocol


class Serializable(Protocol):
    def to_dict(self) -> dict[str, object]: ...


class Usuario:
    def __init__(self, nombre: str, edad: int) -> None:
        self._nombre = nombre
        self._edad = edad

    def to_dict(self) -> dict[str, object]:
        return {"nombre": self._nombre, "edad": self._edad}


class Producto:
    def __init__(self, referencia: str, precio: float) -> None:
        self._referencia = referencia
        self._precio = precio

    def to_dict(self) -> dict[str, object]:
        return {"referencia": self._referencia, "precio": self._precio}


def guardar_en_bd(entidad: Serializable) -> None:
    datos = entidad.to_dict()
    pass


guardar_en_bd(Usuario("Ana", 30))          # OK
guardar_en_bd(Producto("REF-001", 9.99))   # OK: tiene to_dict compatible

Ni Usuario ni Producto heredan de Serializable. mypy comprueba estructuralmente que ambas clases implementan el método con la firma correcta. Si una clase tuviera to_dict con retorno str en lugar de dict[str, object], mypy lo rechazaría.

Protocol frente a ABC. Usa Protocol cuando no controlas las clases que implementan la interfaz (librerías de terceros, clases ya existentes) o cuando el contrato es de comportamiento, no de jerarquía. Usa ABC cuando quieras forzar herencia explícita y aprovechar métodos concretos de la clase base.

mypy en CI y configuración

La instalación es directa:

pip install mypy
mypy src/

La configuración va en mypy.ini o en la sección [tool.mypy] de pyproject.toml. El flag más importante es strict, que activa todas las comprobaciones relevantes de una vez:

[mypy]
python_version = 3.12
strict = true
ignore_missing_imports = true

ignore_missing_imports = true silencia los errores de librerías de terceros que no tienen stubs de tipos. Para añadir stubs manualmente busca el paquete types-<nombre> en PyPI (por ejemplo, types-requests para requests).

En GitHub Actions, mypy se añade como paso antes del paso de tests para fallar rápido:

- name: Verificar tipos
  run: mypy src/ --config-file mypy.ini

- name: Ejecutar tests
  run: pytest

Errores comunes y cómo resolverlos:

def procesar(valor: str | None) -> str:
    return valor.upper()
    # Error: Item "None" of "str | None" has no attribute "upper"

def procesar(valor: str | None) -> str:
    if valor is None:
        return ""
    return valor.upper()   # OK: narrowing
elementos: list[int] = []
elementos.append("texto")
# Error: Argument 1 to "append" of "list" has incompatible type "str"; expected "int"

Cuando mypy produce un falso positivo que no tiene solución limpia, usa # type: ignore[<código>] en la línea concreta, nunca en el fichero completo. El código entre corchetes es el identificador del error (mypy lo muestra con --show-error-codes):

resultado = libreria_sin_tipos.operacion()  # type: ignore[no-untyped-call]

Resumen

  • Las anotaciones de tipo son solo hints: Python las ignora en runtime, pero mypy las verifica en tiempo de análisis y detecta errores antes de que lleguen a producción.
  • str | None (Python 3.10+) equivale a Optional[str]; mypy obliga a comprobar el None antes de usar el valor, eliminando una clase entera de NullPointerException.
  • Literal["norte", "sur"] restringe un parámetro a valores conocidos y permite a mypy detectar valores inválidos en tiempo de análisis, no en runtime.
  • Protocol permite tipado estructural (duck typing tipado): cualquier clase que implemente los métodos con la firma correcta satisface el contrato, sin necesidad de herencia explícita.
  • strict = true en mypy.ini activa todas las comprobaciones relevantes de una vez; es el nivel de partida recomendado para proyectos nuevos.
  • # type: ignore[código] existe para silenciar falsos positivos puntuales; debe ser excepcional, específico al código de error e ir acompañado de un comentario que justifique por qué.
