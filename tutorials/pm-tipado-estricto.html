Tipado estricto y tipos compuestos

Pasas 15,5 euros a una función que espera céntimos enteros y PHP cobra 15, sin quejarse. Los tipos de PHP moderno pueden cerrar ese hueco, pero solo si sabes qué fichero manda y qué expresa cada tipo.

Una firma con tipos parece un contrato. En PHP lo es a medias: por defecto el motor intenta convertir lo que le llega antes de rendirse. Esta lección explica cuándo convierte, cómo apagar esa conversión y qué tipos tienes para describir con precisión lo que entra y lo que sale.

Un tipo que no te protege #

La lección de tipos de clases repasa qué clase usar para cada cosa. Aquí bajamos un nivel: los tipos de los parámetros, los retornos y las propiedades. La pasarela de pagos declara int $centimos y el checkout, un fichero antiguo sin declaración, la llama así:

php · Pasarela.php 
<?php

declare(strict_types=1);

function cobrar(int $centimos): string
{
    return "Cobrados {$centimos} céntimos";
}
php · checkout.php (sin declare) 
<?php

require __DIR__ . '/Pasarela.php';

echo cobrar("1500"), PHP_EOL;
echo cobrar(true), PHP_EOL;
echo cobrar(15.5), PHP_EOL;

Las tres llamadas funcionan. El "1500" se convierte a entero, true pasa a ser 1 céntimo y 15,5 se trunca a 15 con un aviso de deprecación (desde PHP 8.1) que en producción nadie lee. Esto es el modo coercitivo, el que PHP usa por defecto: si el valor se puede convertir sin perder su sentido aparente, lo convierte. El problema es que «aparente» lo decide el motor, no tú, y el error real aparece tres capas más abajo con un importe equivocado.

Qué hace de verdad strict_types #

declare(strict_types=1) apaga esa conversión para los escalares (int, float, string, bool): si el tipo no coincide, lanza TypeError. Lo que casi nadie recuerda es a qué afecta. La declaración no protege las funciones definidas en ese fichero; cambia cómo se comportan las llamadas hechas desde ese fichero.

Por eso Pasarela.php, con su declare arriba, no evitó nada: quien llamaba era checkout.php. Basta con declararlo en el fichero que llama:

php · checkout.php (con declare) 
<?php

declare(strict_types=1);

require __DIR__ . '/Pasarela.php';

echo cobrar("1500"), PHP_EOL;

Ahora la primera llamada ya rompe con cobrar(): Argument #1 ($centimos) must be of type int, string given. La regla completa tiene tres piezas:

Qué se compruebaQué fichero decide el modo
Argumentos de una llamada, también a funciones nativas como strlen(123)El fichero donde está la llamada
Valor de retornoEl fichero donde está declarada la función
Asignación a una propiedad tipadaEl fichero donde está la asignación

Hay una sola conversión que sobrevive al modo estricto: un int se acepta donde se espera un float, porque ensancharlo no pierde información. Y la declaración debe ser la primera sentencia del fichero; si va después de cualquier otra cosa, PHP ni siquiera lo compila.

Por qué se diseñó así

Si strict_types dependiera del fichero que declara, una librería que lo activara rompería a todos sus usuarios de golpe. Al depender de quien llama, cada proyecto decide su modo sin imponérselo a nadie. La contrapartida es que solo te protege si está en todos tus ficheros.

Union, intersection y DNF #

Un tipo simple dice «esto es un int». Los tipos compuestos permiten decir algo más preciso sin caer en dejarlo sin tipo:

  • Union (int|string, PHP 8.0): el valor es de uno de los tipos. Útil en fronteras donde llegan identificadores numéricos o textuales.
  • Intersection (Countable&IteratorAggregate, PHP 8.1): el valor cumple todos los tipos a la vez. Solo admite clases e interfaces; int&string no compila.
  • DNF ((A&B)|null, PHP 8.2): una unión de intersecciones. Los paréntesis son obligatorios; A&B|null es un error de sintaxis.
php · compuestos.php 
<?php

declare(strict_types=1);

function normalizarId(int|string $id): string
{
    return (string) $id;
}

function contarYRecorrer(Countable&IteratorAggregate $coleccion): int
{
    foreach ($coleccion as $elemento) {
        echo $elemento, PHP_EOL;
    }

    return count($coleccion);
}

function resumen((Countable&IteratorAggregate)|null $coleccion): string
{
    if ($coleccion === null) {
        return 'sin datos';
    }

    return count($coleccion) . ' elementos';
}

function buscarCupon(?string $codigo): ?string
{
    return $codigo;
}

echo normalizarId(42), PHP_EOL;
echo contarYRecorrer(new ArrayObject(['a', 'b'])), PHP_EOL;
echo resumen(null), PHP_EOL;
var_dump(buscarCupon(null));

Nullable o unión con null. ?string y string|null significan lo mismo. La diferencia es de sintaxis: el ? solo se aplica a un tipo simple, así que ?int|string no compila y debes escribir int|string|null. Una regla práctica: ?T para un solo tipo, |null en cuanto haya dos.

void, never, mixed, static y compañía #

Hay tipos que no describen un valor concreto, sino una promesa sobre cómo termina la función o qué se devuelve:

TipoQué promete
voidLa función no devuelve nada. Solo como retorno y siempre solo: ?void no compila, y return null; tampoco.
neverLa función no vuelve nunca: lanza una excepción o termina el proceso. Si llega al final, PHP lanza TypeError.
mixedCualquier valor, null incluido, por eso ?mixed no compila. Es explícito, pero no restringe nada.
staticComo retorno, la clase sobre la que se llamó el método, no la que lo declara. La base de las interfaces fluidas heredables.
true, false, nullValores literales como tipo. false solo dentro de una unión desde PHP 8.0; los tres como tipo propio desde 8.2. true|false no compila: es bool.
php · especiales.php 
<?php

declare(strict_types=1);

abstract class Consulta
{
    protected array $filtros = [];

    public static function nueva(): static
    {
        return new static();
    }

    public function donde(string $campo, mixed $valor): static
    {
        $this->filtros[$campo] = $valor;

        return $this;
    }
}

final class ConsultaDePedidos extends Consulta
{
}

function registrar(string $mensaje): void
{
    echo $mensaje, PHP_EOL;
}

function fallar(string $motivo): never
{
    throw new DomainException($motivo);
}

function borrarCache(): true
{
    return true;
}

$consulta = ConsultaDePedidos::nueva()->donde('estado', 'pagado');
registrar($consulta::class);
var_dump(borrarCache());

try {
    fallar('Pedido sin líneas');
} catch (DomainException $exception) {
    registrar($exception->getMessage());
}

Fíjate en static: ConsultaDePedidos::nueva() devuelve una ConsultaDePedidos, y el análisis estático lo sabe, de modo que el autocompletado sigue funcionando tras encadenar donde(). Con self perderías esa información.

Propiedades tipadas y su estado vacío #

Una propiedad tipada (PHP 7.4) no empieza valiendo null: empieza sin inicializar. Es un tercer estado, distinto de cualquier valor, y leerla en ese estado lanza un Error. Ocurre incluso si el tipo es nullable: ?string $cupon sin valor por defecto no es null.

php · propiedades.php 
<?php

declare(strict_types=1);

final class Pedido
{
    public int $id;
    public ?string $cupon;
    public ?string $nota = null;
}

$pedido = new Pedido();
var_dump($pedido->nota);

try {
    echo $pedido->cupon;
} catch (Error $error) {
    echo $error->getMessage(), PHP_EOL;
}

try {
    $pedido->id = '7';
} catch (TypeError $error) {
    echo $error->getMessage(), PHP_EOL;
}

Este estado existe a propósito: obliga a que el constructor asigne lo que el objeto necesita, en vez de dejar un null que nadie pidió. Si una propiedad puede faltar de verdad, dilo con ?string $nota = null. Si no puede faltar, asígnala en el constructor, que es justo lo que hacen los value objects de la lección de enums e inmutabilidad.

El TypeError como red #

TypeError hereda de Error, no de Exception: un catch (Exception $exception) no lo atrapa. Es una decisión deliberada. Un tipo que no cuadra es un fallo de programación, no una situación de negocio, y lo sano es que reviente, salga en el log con su fichero y línea, y se arregle.

Lo que sí es negocio es la entrada del usuario. Un formulario o un JSON siempre traen texto, y ahí no conviene apoyarse en el TypeError: valida en la frontera, convierte a propósito y deja que el resto del código trabaje con tipos limpios.

php · frontera.php 
<?php

declare(strict_types=1);

final class Cantidad
{
    public function __construct(public readonly int $unidades)
    {
    }
}

function cantidadDesdeFormulario(array $datos): Cantidad
{
    $unidades = filter_var($datos['unidades'] ?? null, FILTER_VALIDATE_INT);

    if ($unidades === false) {
        throw new InvalidArgumentException('Las unidades deben ser un entero');
    }

    return new Cantidad($unidades);
}

var_dump(cantidadDesdeFormulario(['unidades' => '3'])->unidades);

try {
    cantidadDesdeFormulario(['unidades' => '3,5']);
} catch (InvalidArgumentException $exception) {
    echo $exception->getMessage(), PHP_EOL;
}

Ojo con el cast a mano

(int) '3,5' devuelve 3 sin quejarse. Convertir con un cast para «satisfacer» el modo estricto reintroduce la coerción que acabas de apagar, solo que escrita por ti. Valida primero y convierte después.

Errores típicos #

Lo que se cuela en las revisiones

  • Declararlo solo en las clases «importantes». Como manda quien llama, un controlador sin declare sigue colando conversiones en tu dominio estricto.
  • Creer que ?string $x empieza en null. Sin = null, la propiedad está sin inicializar y leerla lanza Error.
  • El parámetro string $x = null. Lo hace nullable de forma implícita y está deprecado desde PHP 8.4: escribe ?string $x = null.
  • Usar mixed para salir del paso. Compila, pero no dice nada; si caben dos tipos, escribe la unión.
  • Atrapar Throwable en un controlador genérico y devolver un 400. Así un fallo de tipos se disfraza de error del cliente y nadie lo arregla.

Cómo comprobarlo #

Lo primero es saber qué ficheros siguen en modo coercitivo. Un grep que liste los que no tienen la declaración te da la cifra en un segundo:

bash · terminal 
grep -rL --include='*.php' 'declare(strict_types=1)' src/ tests/

php -d error_reporting=-1 -d display_errors=1 bin/console about

En CI, una regla de estilo puede añadir la declaración y fallar si falta; la lección de estilo automático la configura y CI para PHP la mete en el pipeline. Los deprecados del modo coercitivo, como el truncado de 15,5, solo se ven si tus tests corren con error_reporting=-1 y fallan ante ellos.

El tiempo de ejecución, eso sí, solo comprueba el camino que se ejecuta. Para saber, sin ejecutar nada, que una unión no se usa como si fuera un solo tipo o que un ?Pedido se comprueba antes de usarlo, está el análisis estático: PHPStan lee estas mismas firmas, y la lección de generics cubre lo que el lenguaje todavía no sabe expresar, como un array de Pedido.

Cuándo aplicarlo #

strict_types y tipos precisos cuando…

  • Es código nuevo: la declaración en todos los ficheros desde el primer commit
  • Manejas dinero, cantidades o identificadores donde un truncado es un bug
  • Publicas una librería o un módulo que otros llaman
  • Vas a apoyarte en análisis estático, que razona mejor con firmas exactas

Con cuidado cuando…

  • Es código heredado sin tests: activarlo de golpe convierte coerciones silenciosas en errores en producción
  • Una plantilla o un script de un solo uso no justifica la conversión manual
  • La entrada es texto por naturaleza: valida en la frontera, no confíes en el TypeError

La alternativa en código heredado

Activa la declaración fichero a fichero, empezando por los que ya tienen tests, y antes sube error_reporting en staging para ver qué deprecados de conversión aparecen. Cada uno es una llamada que romperá: arréglala antes de declarar el fichero.

Resumen #

Lo que te llevas

  • Sin declare(strict_types=1), PHP convierte escalares en silencio: "1500", true y 15.5 pasan por un int.
  • Los argumentos los decide el fichero que llama; el retorno, el que declara. Solo protege si está en todos tus ficheros.
  • Union para «uno de», intersection para «todos a la vez», DNF para combinarlas con paréntesis. ?T para un tipo, |null para varios.
  • void no devuelve, never no vuelve, static conserva la subclase y mixed no restringe nada.
  • Una propiedad tipada sin valor está sin inicializar, no a null, aunque sea nullable.
  • TypeError es un Error: señala un bug que se arregla, no una entrada que se valida.
