Skills: flujos empaquetados

Hay tareas que haces igual cada vez: revisar un PR, desplegar, escribir un tutorial de esta academia. Explicárselo al agente en cada sesión es repetirse; meterlo en las rules es pagarlo siempre. Una skill es la tercera vía: el procedimiento empaquetado con nombre, que se carga solo cuando se invoca.

La lección anterior terminó con una válvula de escape: «los procedimientos paso a paso no son rules — son skills». Esta lección abre esa caja: qué forma tienen, cómo decide el agente usarlas y qué convierte un texto en un buen procedimiento ejecutable.

Qué es una skill #

Mecánicamente, una skill de Claude Code es un fichero Markdown con nombre (en .claude/skills/ del proyecto, o global) que contiene instrucciones para una tarea concreta. Se activa de dos maneras: tú la invocas por nombre (/deploy, /tutorial) o el agente la carga al reconocer que la tarea encaja con su descripción. Al activarse, su contenido entra en el contexto en ese momento — no antes.

Carga bajo demanda: esa es toda la magia

Con lo que sabes de contexto, la idea se explica sola: en la sesión solo vive permanentemente la lista de skills con una línea de descripción cada una. El procedimiento completo — que puede ser largo — solo ocupa ventana cuando de verdad se usa. Es el «detalle bajo demanda» de las rules, sistematizado.

La frontera con las rules #

La pregunta que decide dónde va cada cosa: ¿esto aplica siempre, o aplica cuando hago X?

Rules Skill
Naturaleza Criterio permanente: convenciones, invariantes Procedimiento puntual: pasos, en orden, con salida definida
Cuándo entra al contexto Siempre, al arrancar la sesión Solo al invocarla o reconocer la tarea
Coste de que crezca Alto: impuesto en cada sesión Bajo: solo paga quien la usa
Ejemplo «Los booleanos llevan prefijo is/has/should» «Cómo se publica un tutorial: plantilla → manifest → validar»

Anatomía de una buena skill #

Una skill es documentación operativa, y hereda las virtudes de la buena documentación — con un lector que ejecuta. Las piezas que no pueden faltar:

  • Descripción con disparador: la línea que ve el agente para decidir si la carga. «Usar al añadir un tutorial nuevo, al refinar uno existente o al revisar calidad» — casos concretos, no un eslogan.
  • Los pasos, con sus comandos exactos: qué se hace, en qué orden, con el comando literal cuando lo hay. La ambigüedad que en un README molesta, en una skill produce ejecuciones distintas cada vez.
  • El checklist de calidad: qué tiene que ser verdad al terminar, en forma verificable («el validador sale sin errores», no «el resultado es correcto»).
  • Los límites: qué queda fuera de alcance y qué no debe hacer. Es la parte que evita que la skill se use como excusa para tocar lo que no toca.

Un ejemplo real, entero #

Esta academia se mantiene con skills, y la que escribió esta lección es un buen espécimen. Reducida a su esqueleto:

.claude/skills/tutorial/SKILL.md (esqueleto) 
# Tutorial — Autoria y refinado
Descripcion: crear o refinar un tutorial respetando el sistema
de diseño y el manifest. Usar al añadir o revisar contenido.

## Pasos
1. cp tutorials/_PLANTILLA.html tutorials/<slug>.html
2. Rellenar title, hero, TOC y secciones con los componentes existentes
3. Añadir la entrada a tutorials/manifest.js

## Checklist (bloqueante)
- Escapar &lt; &gt; &amp; dentro de code
- Cada h2 con id enlazado desde el TOC
- node scripts/validar.js sin errores

## Fuera de alcance
- El catalogo se auto-genera: no tocarlo a mano
- El sistema de diseño es otra tarea, no "un tutorial"

Fíjate en que cada sección responde a un fallo que ocurrió de verdad: el checklist de escapado existe porque hubo tutoriales rotos por un < sin escapar; el «fuera de alcance» existe porque algún día alguien editó el catálogo a mano. Una skill madura es un historial de lecciones aprendidas con forma de procedimiento.

Cuándo crear una (y cuándo no) #

La regla de las dos veces, otra vez: la primera vez que haces un flujo, lo haces; la segunda, sospechas; la tercera vez que le explicas lo mismo al agente, ya te ha costado más que escribir la skill. Señales a favor: el flujo tiene pasos fijos, un criterio de calidad claro y lo repetirás. Señales en contra: es una tarea única, o el «procedimiento» cambia cada vez — entonces es criterio, no flujo, y quizá era una rule (o nada).

Mantenerlas: el mismo ciclo que las rules #

Una skill se desactualiza en cuanto el proyecto cambia por debajo (un comando renombrado, un paso que ya no hace falta). El ciclo de vida es el de las rules: cuando la ejecución de una skill tropieza — el agente sigue el paso 3 y el paso 3 ya no funciona así — la corrección va a la skill, en la misma sesión. Y las skills viven en el repo, versionadas: un cambio de skill se revisa en el diff como cualquier otro cambio, porque programa el comportamiento de todas las sesiones futuras.

Cuándo aplicarlo #

Empaqueta como skill…

  • Flujos con pasos fijos que repites (publicar, desplegar, revisar)
  • Procedimientos con checklist de calidad verificable
  • Lo que hoy explicas al agente por tercera vez
  • Flujos que el equipo entero debería ejecutar igual

No lo empaquetes si…

  • Aplica siempre: eso es una rule, no una skill
  • Es una tarea única que no volverá
  • Cada ejecución es distinta: ahí hace falta criterio, no pasos
  • Sería tan genérica que no diría nada («haz buen código»)

Resumen #

Lo que te llevas

  • Una skill es un procedimiento con nombre que entra al contexto solo al invocarse: detalle bajo demanda, sistematizado.
  • La frontera con las rules es temporal: lo que aplica siempre es rule; lo que aplica «cuando hago X» es skill.
  • Anatomía: descripción con disparador, pasos con comandos exactos, checklist verificable y límites explícitos.
  • La tercera explicación del mismo flujo ya costó más que escribir la skill: regla de las dos veces.
  • Las skills viven versionadas en el repo y se corrigen en caliente: programan el comportamiento de las sesiones futuras.
