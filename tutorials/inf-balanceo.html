Balanceo de carga y health checks

Un balanceador reparte peticiones entre servidores. Tiene dos decisiones que se pagan caras si se toman mal, y la de los health checks es donde está casi todo el dolor.

Un balanceador reparte peticiones entre varios servidores. Suena trivial y tiene dos decisiones que se pagan caras si se toman mal: cómo elige a quién mandar cada petición, y cómo decide que un servidor está sano. La segunda es donde está casi todo el dolor.

Capa 4 y capa 7 #

Capa 4 (transporte)

  • Reparte conexiones TCP sin mirar dentro
  • Rapidísimo y barato
  • No sabe de rutas, cabeceras ni cookies
  • No puede terminar TLS ni reintentar una petición

Capa 7 (aplicación)

  • Entiende HTTP: rutas, cabeceras, métodos
  • Termina TLS, comprime, reescribe
  • Puede reintentar en otro servidor si uno falla
  • Cuesta más CPU y añade algo de latencia

Para tráfico web quieres capa 7 casi siempre: reintentar una petición fallida en otro servidor y enrutar por ruta son cosas que solo se pueden hacer entendiendo HTTP.

Round robin castiga al servidor lento

Si un servidor va lento pero responde, round robin le sigue mandando su turno completo y las peticiones se acumulan allí. «Menos conexiones» lo evita sin configurar nada: un servidor lento acumula conexiones abiertas y deja de recibir automáticamente. Es un mecanismo de contrapresión gratis.

La sesión pegajosa es una tirita #

Si tu aplicación guarda la sesión en el disco de cada servidor, un usuario que caiga en otro pierde su sesión. La respuesta rápida es la sesión pegajosa: atar cada usuario a un servidor. Funciona, y trae tres problemas:

El reparto se desequilibra —unos servidores acumulan más usuarios que otros—; al quitar un servidor todos sus usuarios pierden la sesión aunque el resto de la flota esté perfecta; y el autoescalado deja de servir de mucho, porque los servidores nuevos solo reciben usuarios nuevos.

El arreglo de verdad: sacar el estado del servidor

Sesiones en Redis o en base de datos, ficheros subidos en almacenamiento de objetos, caché compartida. Con eso, cualquier servidor puede atender a cualquier usuario y todo lo demás —balanceo, escalado, despliegues sin caída— se vuelve trivial. La sesión pegajosa es lo que haces mientras tanto, no el destino.

Los health checks, que es donde está el problema #

Un balanceador solo es útil si sabe qué servidores están sanos. Y ahí hay dos errores opuestos, los dos frecuentes.

Comprobar demasiado poco. Un check que solo mira que el puerto 443 acepta conexiones da por sano un servidor cuyo PHP está roto: nginx acepta, devuelve 502, y el balanceador sigue mandándole tráfico.

Comprobar demasiado. Un check que verifica la base de datos, Redis y tres APIs externas es peor: cuando la base de datos parpadea, todos los servidores fallan el check a la vez y el balanceador los saca a todos. Has convertido una degradación en una caída total.

php · dos endpoints, no uno 
<?php

declare(strict_types=1);

final class SaludController
{
    #[Route('/salud/vivo')]
    public function vivo(): Response
    {
        return new JsonResponse(['estado' => 'ok']);
    }

    #[Route('/salud/listo')]
    public function listo(): Response
    {
        if (!$this->baseDeDatos->responde()) {
            return new JsonResponse(['estado' => 'no_listo'], 503);
        }

        return new JsonResponse(['estado' => 'listo']);
    }
}
EndpointQué compruebaQué se hace si falla
/salud/vivoQue el proceso responde. Nada másReiniciar el proceso: está colgado
/salud/listoQue puede atender tráfico útilSacarlo del balanceo, sin reiniciarlo

La distinción es la que usan los orquestadores (liveness y readiness) y resuelve el dilema anterior: la comprobación cara está en «listo», y una caída de base de datos saca los servidores del balanceo sin reiniciarlos en bucle. Cuando la base de datos vuelve, vuelven solos.

Y el health check no debe autenticarse ni loguearse

Un check cada dos segundos por cada servidor genera miles de líneas de log al día que tapan lo que importa. Y si pide autenticación, el balanceador no puede comprobarlo. Excluye esas rutas del log de acceso y déjalas abiertas — pero sin revelar versiones ni estado interno a quien pregunte desde fuera.

Cuándo aplicarlo #

Pon un balanceador cuando…

  • Tienes más de un servidor de aplicación
  • Quieres desplegar sin cortar el servicio
  • Necesitas sobrevivir a la caída de una máquina
  • Vas a escalar horizontalmente

Aún no hace falta cuando…

  • Es un solo servidor y aguanta de sobra
  • El estado sigue atado a la máquina: arregla eso primero
  • Lo que buscas es rendimiento y el cuello es la base de datos

Resumen #

Lo que te llevas

  • Para tráfico web quieres capa 7: reintentar en otro servidor y enrutar por ruta exigen entender HTTP.
  • «Menos conexiones» da contrapresión gratis: un servidor lento acumula conexiones y deja de recibir sin configurar nada.
  • La sesión pegajosa es una tirita: desequilibra el reparto y hace que quitar un servidor tire las sesiones de todos sus usuarios.
  • Un health check que comprueba la base de datos saca todos los servidores a la vez cuando esta parpadea: conviertes una degradación en caída total.
  • Por eso hay dos endpoints: «vivo» decide si reiniciar el proceso, «listo» decide si mandarle tráfico.
