Autorización: quién puede tocar qué

Tu API comprueba que el usuario ha iniciado sesión. Lo que casi nunca comprueba es si la factura 1043 es suya. Ese hueco, cambiar un número en la URL y leer datos ajenos, es el fallo más repetido en las APIs de hoy.

Autenticar responde a «¿quién eres?». Autorizar responde a «¿puedes tocar esto?». La primera pregunta la resuelve un framework con dos líneas de configuración; la segunda depende de tus datos y nadie la resuelve por ti. Por eso es donde más fallan las APIs reales.

El login no es la puerta de cada habitación #

Si ya leíste Autenticación: sesiones, JWT y OAuth, sabes que el login entrega una credencial con la que el servidor reconoce al usuario en cada petición. Eso es la puerta del edificio. Lo que esta lección trata es la puerta de cada habitación: con la credencial en la mano, ¿qué objetos concretos puede leer, cambiar o borrar?

El fallo nace de una suposición cómoda: «si ha llegado hasta aquí, es de los nuestros». Un #[IsGranted('ROLE_USER')] o un middleware auth garantizan que hay alguien autenticado, pero no dicen nada de la relación entre ese alguien y el registro que pide. Y la URL, el cuerpo y las cabeceras los controla el cliente.

IDOR y BOLA: cambiar un número #

IDOR (Insecure Direct Object Reference) es el nombre clásico: el servidor usa un identificador que llega del cliente para cargar un objeto y no comprueba si ese cliente puede verlo. El OWASP API Security Top 10 de 2023 lo llama BOLA (Broken Object Level Authorization) y lo pone en el primer puesto, API1. En el Top 10 web general, el control de acceso roto ocupa el número uno desde 2021. El repaso de OWASP cubre inyección, XSS y CSRF; esto es lo que queda fuera.

El ataque no requiere ninguna herramienta: te registras, ves tu factura en /api/invoices/1042 y pruebas con 1043. Este controlador lo permite:

php · InvoiceController.php (vulnerable) 
<?php

declare(strict_types=1);

#[Route('/api/invoices/{id}', methods: ['GET'])]
#[IsGranted('ROLE_USER')]
public function show(int $id, InvoiceRepository $invoices): JsonResponse
{
    $invoice = $invoices->find($id);

    if ($invoice === null) {
        throw $this->createNotFoundException();
    }

    return $this->json($invoice);
}

Todo parece correcto: hay control de rol, se devuelve 404 si no existe. Pero find($id) busca en todas las facturas de la base de datos. Cualquier usuario registrado lee las de cualquier otro.

Hay tres niveles, no uno

OWASP separa el fallo por objeto (API1, BOLA), por propiedad (API3: el usuario puede ver la factura, pero no debería poder cambiar su campo owner o total) y por función (API5: un usuario normal llama a DELETE /api/admin/users/7). Esta lección se centra en el primero, que es el más frecuente, pero la misma disciplina cubre los tres.

Comprobar la propiedad en cada acceso #

La regla es simple de enunciar: cada acceso a un objeto comprueba la relación entre el usuario y ese objeto, en el servidor y en el momento del acceso. No basta con hacerlo en la pantalla de listado, ni en el front que esconde el botón, ni en el endpoint de lectura si el de edición no lo repite.

La forma más robusta es que la consulta ya lleve al dueño. Si la factura no es tuya, para tu consulta no existe:

php · InvoiceController.php (corregido) 
<?php

declare(strict_types=1);

#[Route('/api/invoices/{id}', methods: ['GET'])]
#[IsGranted('ROLE_USER')]
public function show(int $id, InvoiceRepository $invoices): JsonResponse
{
    $invoice = $invoices->findOneBy(['id' => $id, 'owner' => $this->getUser()]);

    if ($invoice === null) {
        throw $this->createNotFoundException();
    }

    return $this->json($invoice);
}

Con el filtro dentro de la consulta, el fallo deja de ser posible por construcción: no hay un objeto ajeno cargado en memoria que alguien pueda olvidarse de comprobar. En Laravel el equivalente es pasar por la relación, $request->user()->invoices()->findOrFail($id), y lo mismo vale para los listados: WHERE owner_id = :user siempre, también en búsquedas y exportaciones.

El segundo principio es denegar por defecto. Si ninguna regla dice que sí, la respuesta es no. Un sistema que enumera lo prohibido falla en cuanto aparece un caso que nadie pensó; uno que enumera lo permitido falla cerrado, y un permiso olvidado se nota enseguida porque alguien se queja de un 403, no meses después en un informe de incidente.

¿403 o 404?

Un 403 confirma que el recurso existe; con identificadores secuenciales, eso ya es información. Para objetos de otro usuario suele ser mejor responder 404, igual que si no existiera. El 403 encaja cuando el usuario sabe que el recurso está ahí y le falta un permiso, como editar un documento compartido en modo lectura.

RBAC frente a ABAC #

Para decidir el «sí» hay dos modelos, y casi todas las apps acaban mezclándolos.

RBAC (por rol)ABAC (por atributos)
Pregunta¿Qué rol tiene el usuario?¿Qué relación hay entre usuario, objeto y contexto?
EjemploROLE_ADMIN puede ver el panel de usuariosPuedes editar la factura si es tuya y aún no está emitida
ResuelveAcceso a funciones (API5)Acceso a objetos concretos (API1)
Se rompe cuandoLos roles se multiplican para cubrir casos: ROLE_EDITOR_FACTURAS_EMPRESA_BLas reglas se dispersan por el código sin un sitio único

El rol sirve para decidir a qué zonas entra alguien, como la de administración. La propiedad es un atributo, y ningún rol la expresa: «dueño de esta factura» no es un rol, es una relación con un registro. Por eso BOLA aparece en apps con un RBAC impecable.

Voters de Symfony y policies de Laravel #

Las dos reglas anteriores tienen un problema práctico: si cada controlador escribe su propia comprobación, alguno la olvidará. Symfony y Laravel ofrecen el mismo remedio con nombres distintos, que es concentrar las reglas de cada tipo de objeto en una clase y que los controladores solo pregunten.

En Symfony es un voter. supports() dice si el voter opina sobre ese permiso y ese objeto, y voteOnAttribute() decide:

php · InvoiceVoter.php 
<?php

declare(strict_types=1);

final class InvoiceVoter extends Voter
{
    public const VIEW = 'INVOICE_VIEW';
    public const EDIT = 'INVOICE_EDIT';

    protected function supports(string $attribute, mixed $subject): bool
    {
        return in_array($attribute, [self::VIEW, self::EDIT], true)
            && $subject instanceof Invoice;
    }

    protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token, ?Vote $vote = null): bool
    {
        $user = $token->getUser();

        if (!$user instanceof User) {
            return false;
        }

        $isOwner = $subject->getOwner() === $user;

        return match ($attribute) {
            self::VIEW => $isOwner || $user->isAccountantOf($subject->getCompany()),
            self::EDIT => $isOwner && !$subject->isIssued(),
            default => false,
        };
    }
}

#[Route('/api/invoices/{id}', methods: ['GET'])]
#[IsGranted(InvoiceVoter::VIEW, subject: 'invoice', statusCode: 404)]
public function show(Invoice $invoice): JsonResponse
{
    return $this->json($invoice);
}

Si ningún voter se pronuncia, la estrategia por defecto de Symfony deniega (allow_if_all_abstain vale false): es denegar por defecto ya incorporado. El default => false del match aplica la misma idea dentro del voter.

En Laravel es una policy, una clase con un método por acción que recibe el usuario y el modelo. Laravel la asocia al modelo por convención de nombres, y Gate::authorize() lanza la excepción que acaba en 403, o en 404 si la policy responde con denyAsNotFound():

php · InvoicePolicy.php 
<?php

declare(strict_types=1);

final class InvoicePolicy
{
    public function view(User $user, Invoice $invoice): Response
    {
        return $user->id === $invoice->user_id
            ? Response::allow()
            : Response::denyAsNotFound();
    }

    public function update(User $user, Invoice $invoice): bool
    {
        return $user->id === $invoice->user_id && $invoice->issued_at === null;
    }
}

final class InvoiceController extends Controller
{
    public function show(Invoice $invoice): InvoiceResource
    {
        Gate::authorize('view', $invoice);

        return new InvoiceResource($invoice);
    }
}

En Laravel 11 el Controller base viene vacío, sin el trait AuthorizesRequests, así que $this->authorize() no existe salvo que lo añadas; Gate::authorize() funciona siempre. También puedes ponerlo en la ruta con el middleware can:view,invoice.

Errores típicos #

Lo que se cuela en las revisiones

  • Proteger la lectura y olvidar la escritura. GET pasa por el voter; PATCH y DELETE, escritos otro día, no.
  • Confiar en el id del cuerpo. Compruebas la factura de la URL, pero el cuerpo trae un owner_id o un invoice_id distinto que se guarda tal cual.
  • Creer que un UUID es una defensa. Dificulta adivinar, pero los identificadores se filtran en logs, enlaces y respuestas. Ocultar no es autorizar.
  • Esconder el botón en el front. La interfaz no es una frontera de seguridad: el atacante habla con la API directamente.
  • Olvidar los caminos laterales. Exportaciones a CSV, endpoints de búsqueda, adjuntos servidos por ruta y relaciones anidadas como /invoices/7/lines.

El test de B contra A #

BOLA no se ve leyendo un controlador aislado, porque el código vulnerable funciona perfectamente para su dueño. Se ve con un test que crea dos usuarios: A es dueño del recurso, B lo pide, y la respuesta tiene que ser 404 (o 403, según tu convención). Es barato y atrapa justo lo que los tests del camino feliz nunca tocan.

php · InvoiceAccessTest.php (Symfony) 
<?php

declare(strict_types=1);

public function testUserCannotReadAnotherUsersInvoice(): void
{
    $client = static::createClient();
    $owner = $this->createUser('ana@example.com');
    $intruder = $this->createUser('bruno@example.com');
    $invoice = $this->createInvoiceOwnedBy($owner);

    $client->loginUser($intruder);
    $client->request('GET', '/api/invoices/' . $invoice->getId());

    self::assertResponseStatusCodeSame(404);
}
php · InvoiceAccessTest.php (Laravel) 
<?php

declare(strict_types=1);

public function test_user_cannot_read_another_users_invoice(): void
{
    $owner = User::factory()->create();
    $intruder = User::factory()->create();
    $invoice = Invoice::factory()->for($owner)->create();

    $this->actingAs($intruder)
        ->getJson("/api/invoices/{$invoice->id}")
        ->assertNotFound();
}

Escribe uno por cada verbo que toca un objeto, no solo para la lectura. En revisión de código, la pregunta útil ante cualquier find($id) con un id del cliente es una sola: ¿dónde se comprueba que este usuario puede tocar este objeto? Si la respuesta es «en ningún sitio», ya tienes el hallazgo.

Cuándo aplicarlo #

Voters o policies cuando…

  • Hay recursos con dueño: facturas, pedidos, documentos, cuentas
  • La misma regla se pregunta desde varios controladores o comandos
  • La regla mezcla propiedad, estado del objeto y rol
  • Es una API multiusuario o multiempresa

No hace falta cuando…

  • El dato es público para cualquiera, sin dueño
  • Solo hay una regla por rol, que ya resuelve IsGranted o can
  • Es una herramienta interna de un solo usuario sin datos ajenos

La alternativa sencilla

Si todos tus recursos son del usuario y la regla es siempre «solo el dueño», no necesitas un voter por entidad: basta con que el repositorio filtre por dueño en cada consulta. Cuando aparezcan excepciones, como contables o miembros de un equipo, ese es el momento de mover la regla a un voter o una policy.

Resumen #

Lo que te llevas

  • Autenticar no autoriza: estar logueado no dice nada de si este objeto es tuyo. BOLA es el primer fallo del OWASP API Security Top 10 de 2023.
  • Comprueba la relación usuario-objeto en cada acceso y en cada verbo, en el servidor. Mejor aún, filtra por dueño en la propia consulta.
  • Deniega por defecto: si ninguna regla permite, la respuesta es no. Symfony lo hace al abstenerse todos los voters.
  • RBAC resuelve funciones; la propiedad es un atributo y necesita ABAC, aunque sea mínimo.
  • Concentra las reglas en voters o policies y que los controladores solo pregunten.
  • El test de dos usuarios, B pide lo de A y recibe 404 o 403, es el que atrapa BOLA.
