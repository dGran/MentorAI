¿Qué es Python y para qué proyectos?

Por qué Python domina data science, scripting y backend moderno, para qué proyectos es la elección obvia y una tabla comparativa con PHP, Go y Rust.

Si vienes de PHP, la pregunta útil no es si Python es mejor, sino para qué trabajo concreto compensa meter un segundo lenguaje en tu equipo. Esta lección te da ese mapa: dónde juega en casa, dónde sufre y cómo se compara con lo que ya conoces, para que la decisión no dependa de la moda.

El origen y la filosofía #

Guido van Rossum creó Python en 1991 en el CWI de Ámsterdam con una hipótesis concreta: un lenguaje puede ser legible y a la vez potente. El nombre viene de Monty Python, no de la serpiente, y eso ya dice algo de la cultura del proyecto.

La filosofía oficial vive en The Zen of Python, accesible desde el intérprete:

python 
>>> import this
Beautiful is better than ugly.
Explicit is better than implicit.
Simple is better than complex.
Readability counts.
There should be one-- and preferably only one --obvious way to do it.

"Readability counts" no es marketing: Python obliga a indentar el código (la indentación es la sintaxis), no permite llaves opcionales ni escribir todo en una línea. Es opinionado por diseño.

Python tiene tipado dinámico y fuerte. Dinámico: la variable no declara tipo, el objeto sí. Fuerte: no hay coerciones implícitas entre tipos incompatibles. En PHP, 1 + "2" devuelve 3 (coerción silenciosa). En Python lanza TypeError: unsupported operand type(s) for +: 'int' and 'str'. Son reglas distintas con consecuencias distintas.

GIL (Global Interpreter Lock): CPython, en su build por defecto, tiene un lock global que impide que más de un hilo ejecute bytecode Python simultáneamente. Simplifica el modelo de memoria pero limita el paralelismo CPU. Para I/O-bound (la mayoría de backends web), async/await lo rodea completamente sin necesidad de threads.

Para qué proyectos encaja #

  • Data science y ML: NumPy, pandas, PyTorch, scikit-learn, Jupyter. El ecosistema científico de Python no tiene rival. Si trabajas con datos, no hay alternativa real.
  • Scripting y automatización: pipelines de CI, cron jobs, procesamiento de ficheros, glue entre sistemas. Python se instala en cualquier servidor y la stdlib cubre el 80% de los casos sin dependencias externas.
  • Backend web moderno: FastAPI compite en benchmarks de I/O con Go. Django sigue siendo la opción batteries-included para proyectos grandes con décadas de madurez.
  • CLIs y herramientas: con typer o click se construyen CLIs con type hints. Los paquetes se distribuyen con pip/uv sin fricciones.
  • Glue code entre sistemas: conecta APIs, transforma datos entre formatos, orquesta herramientas que no hablan entre sí. Python es el lenguaje de integración por excelencia.

Para qué no encaja #

  • Código de sistema y kernel: sin punteros, sin gestión manual de memoria. Para drivers o partes del kernel, C o Rust son las opciones.
  • Latencia extrema: el GC de CPython (reference counting) añade trabajo no determinista. Para servicios donde el P99 es un requisito duro, Go o Rust son mejores elecciones. Rust elimina el GC completamente.
  • Apps móviles: CPython corre en iOS y Android (plataformas oficiales desde 3.13), pero no hay un ecosistema maduro de UI nativa: para una app móvil, Swift, Kotlin o Flutter siguen siendo la elección.
  • CPU-bound con threads: en la build por defecto, el GIL significa que aunque lances 8 threads, solo uno ejecuta Python a la vez. Para workloads CPU-bound paralelos necesitas multiprocessing o ProcessPoolExecutor, que tienen overhead de serialización entre procesos. Desde 3.14 hay además una build free-threaded sin GIL con soporte oficial (python3.14t), pero es opcional y no todas las librerías con extensiones C la soportan aún.

Regla práctica: si el cuello de botella es I/O (red, base de datos, disco), Python con async es una elección excelente. Si el cuello de botella es CPU pura con paralelismo real de threads, Go o Rust ganan.

Errores típicos al llegar desde PHP

  • Leer «dinámico» como «débil». Python no convierte por ti: 1 + "2" lanza TypeError y "3" * 2 devuelve "33", no 6. Las conversiones van explícitas con int() o str().
  • Descartarlo por el GIL para un backend web. El GIL limita a los hilos que calculan, no a los que esperan: durante una consulta a la base de datos o una llamada HTTP el hilo lo suelta. Para I/O, async o un servidor con varios workers rinden bien.
  • Elegirlo para CPU pura porque se escribe rápido. Un servicio que procesa imágenes o cifra en bucle se queda en un núcleo con hilos, y pasar a multiprocessing obliga a serializar datos entre procesos. Si eso es el núcleo del servicio, el ahorro de escritura se paga en producción.

PHP y Python comparten el tipado dinámico, pero PHP lo heredó de sus raíces como lenguaje de plantillas web (con coerciones que aún sorprenden), mientras Python lo diseñó fuerte desde el principio. Go y Rust ofrecen garantías en compilación que Python no puede dar, pero a costa de curvas de aprendizaje significativamente mayores.

Por qué Python ahora #

Python lleva décadas existiendo, pero el backend Python actual no se parece al de 2015. Tres cambios lo renovaron:

FastAPI + Pydantic: declarar una API con type hints y obtener validación automática, serialización y documentación OpenAPI sin configuración es algo que ningún framework PHP logra con tanta limpieza. La ergonomía es comparable a lo mejor de TypeScript.

async/await maduro: desde Python 3.7 el modelo async es estable. En 3.12 el rendimiento del event loop mejoró significativamente. Las bibliotecas core (httpx, SQLAlchemy 2.0, asyncpg) son async-first.

uv como gestor moderno: escrito en Rust por Astral (los mismos de Ruff). Es 10-100× más rápido que pip, maneja virtual environments, y reemplaza pip + venv + pip-tools en un solo binario.

bash 
uv init --no-package my-api && cd my-api
uv add fastapi uvicorn
uv run uvicorn main:app --reload

uv init deja un main.py de ejemplo: crea en él tu app = FastAPI() antes del último comando. Sin --no-package, uv genera un paquete en src/my_api/ y el módulo pasa a ser otro.

Cuándo aplicarlo #

El coste de adoptar Python casi nunca es aprenderlo: es operar dos stacks. Otro runtime en las imágenes, otro gestor de dependencias, otro pipeline de CI y alguien de guardia que entienda ambos. Por eso la decisión se toma por el tipo de trabajo, no por gusto.

Elige Python cuando…

  • El proyecto toca datos o ML: pandas, NumPy o PyTorch no tienen equivalente en PHP y montar un puente entre lenguajes sale más caro
  • Hay scripts de automatización que hoy son bash frágil y empiezan a necesitar tests y estructuras de datos
  • Arrancas una API nueva, I/O-bound, y quieres validación y documentación salidas de los tipos (FastAPI con Pydantic)
  • Hay al menos otra persona en el equipo dispuesta a mantenerlo

Busca otra opción cuando…

  • La funcionalidad cabe en el monolito PHP que ya tienes y funciona: un servicio aparte solo añade despliegue y red
  • El cuello de botella es CPU en paralelo: Go o Rust lo aprovechan sin depender de una build sin GIL
  • El P99 de latencia es un requisito duro: Go o Rust dan tiempos más predecibles
  • Necesitas repartir un binario único sin runtime: Go lo resuelve de serie

Resumen #

Lo que te llevas

  • Python nació con la filosofía de que la legibilidad es una característica de diseño: la indentación obligatoria es la manifestación más visible de esa decisión.
  • El tipado dinámico fuerte significa que no hay coerciones implícitas entre tipos incompatibles: 1 + "2" es un error, no una conversión silenciosa.
  • Encaja de forma natural en data science, ML, scripting y backend web; no es la elección para sistemas de bajo nivel ni workloads CPU-bound que necesiten paralelismo real de threads.
  • En la build por defecto, el GIL limita el paralelismo de CPU en threads (la build free-threaded lo quita, de forma opcional); para I/O-bound, async/await lo elimina como problema real.
  • FastAPI, Pydantic y uv han renovado el panorama: Python moderno es tipo-seguro en desarrollo, rápido de iterar y comparable a Go en rendimiento de I/O.
