Testear excepciones y medir cobertura

La mitad del valor de tu código está en cómo falla: validaciones que rechazan, límites que protegen. Esa mitad también se testea. Y para saber qué te queda sin probar existe la cobertura — una herramienta magnífica que se estropea en cuanto la conviertes en objetivo.

Si tu código sigue el criterio de manejo de errores —excepciones específicas, fail fast, validar en el constructor—, entonces lanzar es parte del contrato de tus clases. Y el contrato entero se prueba: lo que devuelve cuando va bien y lo que lanza cuando no debe seguir.

El camino triste también se testea #

Piensa en un value object Money que no admite importes negativos, o en un OrderService que rechaza confirmar dos veces el mismo pedido. Esas negativas son comportamiento: alguien las diseñó, el dominio depende de ellas, y una regresión que las silencie (el pedido se confirma dos veces sin quejarse) es de los bugs más caros que existen — porque no rompe nada visible, solo corrompe datos.

Un test de excepción responde tres preguntas, de más a menos importante: ¿lanza? ¿lanza la excepción correcta? ¿con la información correcta? La primera sin la segunda vale poco: si esperabas ImporteNegativo y el código lanza TypeError por un bug anterior, un test que solo compruebe "lanza algo" da verde a un error.

expectException y compañía #

La API se declara antes de ejecutar el código que debe lanzar — es una expectativa, no una aserción a posteriori:

php · primero la expectativa, después el acto 
#[Test]
public function rechaza_importes_negativos(): void
{
    $this->expectException(ImporteNegativo::class);
    $this->expectExceptionMessage('-100');

    new Money(amountCents: -100, currency: 'EUR');
}

El orden importa por una razón mecánica: en cuanto la excepción se lanza, la ejecución del método de test se corta ahí. Cualquier línea posterior al acto no se ejecuta jamás — una expectativa (o aserción) colocada después es código muerto que da sensación de seguridad. De ahí también una regla de higiene: un test de excepción prueba una sola llamada que lanza; si necesitas comprobar más cosas después, son dos tests.

Las variantes: expectExceptionMessage() comprueba que el mensaje contiene el texto (no igualdad exacta — no acoples el test a la redacción completa), expectExceptionCode() para códigos, y expectExceptionMessageMatches() con una regex cuando el mensaje lleva partes variables.

Excepciones específicas, tests específicos

Aquí cobra sentido práctico la regla de no lanzar \Exception genérica: expectException(ImporteNegativo::class) documenta el contrato con precisión. Si todo lanza \Exception, el test no puede distinguir tu negativa deliberada de un fallo accidental — y dará verde a ambos.

Medir cobertura: pcov o Xdebug #

La cobertura registra qué líneas de tu código ejecutaron los tests. PHPUnit no la mide solo: necesita una extensión que instrumente el intérprete (una extensión de PHP, literalmente). Hay dos opciones y la elección es fácil:

ExtensiónQué esCuándo
pcovExtensión mínima, solo cobertura de líneas. Apenas ralentiza la suite.La elección por defecto para CI y uso diario.
XdebugEl depurador completo, con cobertura entre sus modos (XDEBUG_MODE=coverage). Más lento, pero mide también ramas y caminos.Si ya lo tienes para depurar, o quieres cobertura de ramas.
bash · generar el informe 
# resumen rápido en la terminal
vendor/bin/phpunit --coverage-text

# informe navegable completo
vendor/bin/phpunit --coverage-html build/coverage

# con Xdebug hay que activar el modo
XDEBUG_MODE=coverage vendor/bin/phpunit --coverage-text

Falta decirle a PHPUnit qué código medir (tu src/, no vendor/), en phpunit.xml: el elemento <source> con un <include> del directorio. Sin eso, el porcentaje mezcla tu código con el ajeno y no significa nada.

Leer el informe #

El informe HTML pinta cada fichero con sus líneas en verde (ejecutadas) o rojo (nunca ejecutadas). La forma correcta de leerlo no es mirar el porcentaje: es pasear por el rojo preguntando "¿me importa esto?". Un getter trivial en rojo da igual; el catch del pago fallido en rojo significa que el camino más delicado de tu facturación no lo ha ejecutado nadie nunca — ni tus tests ni, con suerte, producción todavía.

Segunda lectura importante: línea cubierta no es línea probada a fondo. La cobertura de líneas dice que la línea se ejecutó; si una condición tiene dos salidas y tus tests solo pasan por una, la línea luce verde igual. Para eso existe la cobertura de ramas (Xdebug): mide salidas de cada decisión, no líneas. No hace falta usarla siempre — basta saber que el verde de líneas es un techo optimista, no una garantía.

Por qué el 100% no es el objetivo #

La cobertura mide ejecución, no verificación. Un test sin aserciones que llame a todo tu código da 100% de cobertura y comprueba exactamente nada — es la cobertura engañosa que ya viste en fundamentos, y la razón de fondo por la que perseguir la cifra corrompe la métrica: en cuanto el 100% es la meta, aparecen tests que ejecutan sin verificar, escritos para pintar verde.

Cobertura como objetivo

  • "No baja del 95%" como regla ciega.
  • Tests sin aserciones para pintar verde.
  • Tests de getters para subir la cifra.
  • La métrica manda sobre el criterio.

Cobertura como linterna

  • El rojo como mapa de riesgo: ¿qué no probé que importa?
  • Caminos tristes y fronteras primero.
  • Vigilar la tendencia (¿el código nuevo llega testeado?).
  • El criterio manda sobre la métrica.

¿Un número razonable? El que salga de testear lo que importa: en dominio y servicios suele acabar alto (85-95%) sin perseguirlo; en código pegamento (controladores finos, adaptadores) es naturalmente más bajo y no pasa nada. Si en CI quieres una red, ponla como suelo que evite retrocesos (el PR no baja la cobertura existente), no como listón que obligue a inflarla.

Resumen #

Lo que te llevas

  • Las negativas de tu código son contrato: se testean con expectException + expectExceptionMessage, declaradas ANTES del acto.
  • Tras la excepción el test se corta: nada de aserciones después del acto, y una sola llamada que lanza por test.
  • Cobertura: pcov para el día a día y CI; Xdebug si quieres ramas. Define el source en phpunit.xml o el porcentaje no significa nada.
  • El informe se lee paseando por el rojo ("¿me importa esto?"), no mirando el porcentaje; línea verde ≠ comportamiento verificado.
  • La cobertura es linterna, no objetivo: como meta produce tests que ejecutan sin verificar. En CI, como suelo anti-retroceso.
