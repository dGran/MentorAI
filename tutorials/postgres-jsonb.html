Postgres para quien viene de MySQL: JSONB e índices GIN

Postgres guarda JSON como un tipo de primera clase y sabe indexarlo entero, no solo una ruta. Esa potencia tiene letra pequeña: operadores que chocan con PDO, índices que sirven unas consultas y otras no, y un puñado de costumbres de MySQL que aquí dan error.

Un catálogo con camisetas, portátiles y libros no comparte columnas: la talla no le importa al libro y el ISBN no le importa a la camiseta. En MySQL acabas con una columna JSON y una columna generada por cada campo que quieres filtrar. En Postgres hay otro camino: una columna JSONB y un solo índice que responde a preguntas sobre cualquier clave.

El problema #

En Modelado relacional viste que cada atributo merece su columna. Funciona mientras los atributos son los mismos para todas las filas. Cuando cada fila trae los suyos (atributos de producto, el payload de un webhook, la configuración de un cliente), tienes tres salidas y dos son malas: cien columnas casi siempre a NULL, o una tabla clave-valor (EAV) que obliga a un JOIN por cada atributo que filtras.

La tercera es guardar el documento tal cual y pedirle a la base de datos que lo entienda. MySQL lo hace a medias: el tipo JSON no se indexa directamente, solo a través de una ruta concreta. Lo comprobamos en MySQL 8.4:

sql · mysql 8.4 
CREATE INDEX p_atr ON p (atributos);
-- ERROR 3152: JSON column 'atributos' supports indexing only
-- via generated columns on a specified JSON path.

CREATE INDEX p_color ON p ((CAST(atributos ->> '$.color' AS CHAR(20))));
CREATE INDEX p_tags  ON p ((CAST(atributos -> '$.tags' AS CHAR(20) ARRAY)));

Un índice por ruta: si mañana filtras por material, toca migración. Postgres resuelve ese caso con un índice que cubre el documento entero.

JSON frente a JSONB #

Postgres tiene dos tipos. json guarda el texto tal cual llega y lo vuelve a analizar en cada consulta. jsonb lo descompone al escribir en un formato binario: escribir cuesta un poco más, leer y buscar mucho menos, y solo jsonb admite índices GIN. Salida real de Postgres 17:

sql · postgres 17 
SELECT '{"b":1, "a":2, "a":3}'::json  AS j,
       '{"b":1, "a":2, "a":3}'::jsonb AS jb;
--            j           |        jb
-- {"b":1, "a":2, "a":3}  | {"a": 3, "b": 1}

Fíjate en lo que hace jsonb: no conserva el orden de las claves (las reordena por longitud y luego alfabéticamente), quita espacios y, ante claves duplicadas, se queda con la última. Si necesitas el texto exacto (firmar un payload, auditar lo que llegó), json o un text; para todo lo demás, jsonb. El JSON de MySQL se parece más a jsonb que a json: también es binario y también normaliza (la misma consulta en MySQL 8.4 devuelve {"a": 3, "b": 1}). La diferencia real no está en el almacenamiento, está en los índices.

Operadores: ->, ->>, @> y ? #

Las flechas existen en los dos motores, pero en Postgres no llevan ruta $.: reciben la clave.

OperadorQué haceDevuelve
atributos -> 'color'Extrae el valor de la clavejsonb ("azul", con comillas)
atributos ->> 'color'Extrae el valor como textotext (azul)
atributos @> '{"color":"rojo"}'¿Contiene este fragmento?boolean
atributos ? 'garantia'¿Existe esta clave en el primer nivel?boolean

Dos matices que cuestan horas. ->> siempre da texto, así que atributos ->> 'talla' > '100' compara cadenas: con talla 42 devuelve true, porque '4' va después de '1'. Hay que convertir: (atributos ->> 'talla')::int > 100. Y ? solo mira el primer nivel: '{"a":{"b":1}}'::jsonb ? 'b' es false.

@> es el operador que más rinde: compara estructura, también dentro de arrays. atributos @> '{"tags":["t7"]}' encuentra las filas cuyo array tags contiene "t7", y es la forma de escribirlo que un índice GIN puede aprovechar.

Índices GIN: jsonb_ops y jsonb_path_ops #

Qué es un índice invertido ya lo viste en Búsqueda full-text: GIN apunta de cada elemento a las filas que lo contienen. Con jsonb los elementos son claves y valores del documento. Un B-tree ordena valores completos y no sabe preguntar «¿contiene?»; GIN sí. Hay dos clases de operadores, y cada una sirve a operadores distintos:

jsonb_ops (por defecto)

  • Sirve @>, ?, ?|, ?&, @? y @@.
  • Indexa cada clave y cada valor por separado.
  • Más grande: 2128 kB en la prueba.

jsonb_path_ops

  • Sirve @>, @? y @@; no sirve ?.
  • Indexa un hash de cada ruta hasta un valor.
  • Más pequeño: 1456 kB con los mismos datos.

Probado con 200.000 productos y EXPLAIN en Postgres 17. Con jsonb_path_ops, la contención usa el índice y la existencia de clave no:

sql · postgres 17 
CREATE INDEX productos_atributos_path
    ON productos USING GIN (atributos jsonb_path_ops);

EXPLAIN SELECT id FROM productos WHERE atributos @> '{"garantia": true}';
-- Bitmap Heap Scan on productos
--   ->  Bitmap Index Scan on productos_atributos_path

EXPLAIN SELECT id FROM productos WHERE atributos ? 'garantia';
-- Seq Scan on productos
--   Filter: (atributos ? 'garantia'::text)

Con el índice por defecto (CREATE INDEX productos_atributos_gin ON productos USING GIN (atributos)) las dos consultas salen por Bitmap Index Scan. Lo que ninguno de los dos sirve es atributos ->> 'color' = 'rojo': eso es una igualdad sobre una expresión, y la resuelve un B-tree de expresión, CREATE INDEX ON productos ((atributos ->> 'color')). Es lo mismo que la columna generada de MySQL, solo que sin columna.

En PHP: antes y después #

El primer choque al portar un repositorio es con PDO: ? es también el marcador de parámetro posicional. Esta consulta parece correcta y no lo es:

php · antes 
<?php

declare(strict_types=1);

final readonly class ProductRepository
{
    public function __construct(private PDO $pdo)
    {
    }

    public function findIdsWithWarrantyByColor(string $color): array
    {
        $statement = $this->pdo->prepare(
            "SELECT id FROM productos WHERE atributos ? 'garantia' AND atributos ->> 'color' = ?"
        );
        $statement->execute([$color]);

        return $statement->fetchAll(PDO::FETCH_COLUMN);
    }
}

PDO convierte los dos ? en parámetros y Postgres recibe atributos $1 'garantia': SQLSTATE[42601]: Syntax error ... syntax error at or near "$1". PDO permite escaparlo como ?? (desde PHP 7.4), pero hay una salida mejor: expresar el filtro entero como contención y pasar el fragmento como parámetro con nombre.

php · después 
<?php

declare(strict_types=1);

final readonly class ProductRepository
{
    public function __construct(private PDO $pdo)
    {
    }

    public function findIdsWithWarrantyByColor(string $color): array
    {
        $statement = $this->pdo->prepare('SELECT id FROM productos WHERE atributos @> :filter');
        $statement->execute([
            'filter' => json_encode(['garantia' => true, 'color' => $color], JSON_THROW_ON_ERROR),
        ]);

        return $statement->fetchAll(PDO::FETCH_COLUMN);
    }
}

Ganas tres cosas: no hay ? ambiguo, el valor viaja como parámetro y no concatenado, y @> lo sirven las dos clases de GIN. El plan real de esta consulta es Bitmap Index Scan on productos_atributos_gin, y devuelve las mismas 66 filas que la versión con ??.

Lo que muerde al venir de MySQL #

Todo esto se ejecutó en postgres:17 y mysql:8.4. Lo de la izquierda funciona en MySQL; lo de la derecha es lo que dice Postgres.

En MySQLEn Postgres
SELECT "hola" devuelve una cadenaLas comillas dobles son identificadores: column "hola" does not exist. Las cadenas, con comilla simple.
`Clientes` con backticksLos backticks son un syntax error. Los identificadores sin comillas pasan a minúsculas (Clientes es clientes), y "Clientes" entre comillas dobles es otro nombre, que no existe. Si creas la tabla con comillas, tendrás que citarla siempre.
AUTO_INCREMENTGENERATED ALWAYS AS IDENTITY (estándar) o el veterano SERIAL. Con ALWAYS, insertar un id explícito falla salvo con OVERRIDING SYSTEM VALUE.

BOOLEAN es tinyint(1); WHERE activo = 1 valeboolean de verdad: operator does not exist: boolean = integer. Escribe WHERE activo.

Errores típicos #

Índice creado, índice ignorado

Cambiar ? por jsonb_exists() para esquivar a PDO: da el mismo resultado, pero es una función y no un operador, y el plan pasa a Seq Scan aunque haya GIN.

Filtrar con -> antes de ?: atributos -> 'tags' ? 't7' no usa el índice de atributos, porque el índice es de la columna y no de esa expresión. atributos @> '{"tags":["t7"]}' sí.

Elegir jsonb_path_ops por pequeño y descubrir después que las consultas con ? recorren la tabla.

Comparar números como texto con ->> sin convertir.

Cómo comprobarlo #

Con un Postgres desechable y EXPLAIN, que ya sabes leer desde Leer un EXPLAIN. Busca Bitmap Index Scan on <tu índice>; si ves Seq Scan con Filter en una tabla grande, el índice no sirve a ese operador.

bash · terminal 
docker run -d --name pg-jsonb -e POSTGRES_PASSWORD=secret postgres:17
docker exec -it pg-jsonb psql -U postgres

# dentro de psql
CREATE TABLE productos (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, atributos jsonb NOT NULL);
INSERT INTO productos (atributos)
SELECT jsonb_build_object('color', (ARRAY['rojo','azul','verde','negro'])[1 + i % 4], 'garantia', i % 100 = 0)
FROM generate_series(1, 200000) AS i;
CREATE INDEX productos_atributos_gin ON productos USING GIN (atributos);
ANALYZE productos;
\d productos
EXPLAIN SELECT id FROM productos WHERE atributos @> '{"color": "rojo"}';
SELECT pg_size_pretty(pg_relation_size('productos_atributos_gin'));

Mide con un volumen parecido al real: con pocas filas el planificador elige Seq Scan aunque el índice valga, y sacarías la conclusión contraria. Lo mismo aplica a los índices que sobran: un GIN que no sale en ningún plan solo encarece cada escritura.

Cuándo aplicarlo #

JSONB es buena idea

  • Atributos que cambian por fila: fichas de producto, preferencias, metadatos.
  • Payloads externos que guardas para reprocesar o auditar.
  • Datos que se leen enteros y se filtran por contención.

JSONB es un esquema escondido

  • Todas las filas llevan las mismas claves.
  • Haces JOIN o pones claves foráneas sobre valores del JSON.
  • Necesitas NOT NULL, tipos o unicidad en un campo interno.

La prueba rápida: si cada consulta extrae la misma clave, esa clave quiere ser columna. La alternativa no es todo o nada; lo habitual es un híbrido: columnas para lo que todas las filas comparten y consultas a diario, y un jsonb para la cola larga de atributos. Si aun así una clave del JSON se filtra por igualdad o rango, un índice de expresión sobre ->> la cubre sin mover datos.

Resumen #

Lo que te llevas

  • jsonb normaliza y se indexa; json conserva el texto exacto y no admite GIN.
  • -> devuelve jsonb y ->> texto; @> es el filtro que mejor aprovecha el índice.
  • jsonb_ops sirve también ?; jsonb_path_ops es más pequeño pero solo sirve contención y jsonpath.
  • En PDO, ? es un marcador: escápalo con ?? o reescribe con @> y un parámetro con nombre.
  • Comillas dobles, minúsculas, boolean, ON CONFLICT y UPDATE sin LIMIT: lo que falla primero al portar SQL de MySQL.
