Attributes: metadatos que el código lee

Rutas, reglas de validación, listeners: los frameworks modernos los declaran con #[...] encima del código. PHP los guarda, pero no los ejecuta. Quién los lee, cuándo y qué pasa si están mal es lo que separa usarlos de entenderlos.

Un #[Route('/invoices')] encima de un método no hace nada por sí solo. Es una etiqueta pegada al código que PHP guarda y no ejecuta, hasta que alguien la pide por Reflection. Entender ese «hasta que alguien la pide» explica casi todo lo que sorprende de los attributes.

Comentarios que el código obedece #

Antes de PHP 8.0, los frameworks querían declarar la ruta, la validación o el mapeo de una entidad junto al código al que se refiere, y no en un YAML aparte. Como el lenguaje no tenía dónde guardar ese dato, lo metieron en el único sitio libre: el docblock.

php · antes: anotación en docblock 
<?php

declare(strict_types=1);

final class InvoiceController
{
    /**
     * @Route("/invoices/{id}", methods={"GET"})
     */
    public function show(int $id): Response
    {
    }
}

Para PHP eso es un comentario. Una librería lo lee en tiempo de ejecución, parsea el texto con su propia gramática y adivina a qué clase se refiere @Route. Si escribes @Rute, nadie se queja: la ruta simplemente no existe. Si renombras la clase, el IDE no actualiza el comentario. El problema de fondo es que el dato más importante del método vivía fuera del lenguaje.

La sintaxis: #[...] #

Un attribute es un nombre de clase con argumentos, entre #[ y ]. El motor lo parsea, resuelve el nombre con tus use como cualquier otra clase y lo guarda junto al elemento.

php · después: attribute nativo 
<?php

declare(strict_types=1);

use Symfony\Component\Routing\Attribute\Route;

final class InvoiceController
{
    #[Route('/invoices/{id}', methods: ['GET'])]
    public function show(int $id): Response
    {
    }
}

Se pueden poner en clases, métodos, funciones, closures, propiedades, constantes de clase y parámetros. Varios se apilan en líneas separadas o se agrupan con comas: #[A, B]. Los argumentos admiten argumentos con nombre, pero deben ser expresiones constantes: literales, constantes y operaciones entre ellas. Una llamada como strtolower('/X') da Constant expression contains invalid operations al compilar.

Declarar un attribute propio #

Un attribute propio es una clase normal marcada con #[Attribute]. Su constructor define qué argumentos acepta, y el argumento de #[Attribute] dice dónde se puede usar:

php · Route.php 
<?php

declare(strict_types=1);

#[Attribute(Attribute::TARGET_METHOD | Attribute::IS_REPEATABLE)]
final readonly class Route
{
    public function __construct(
        public string $path,
        public string $method = 'GET',
    ) {
    }
}
ConstantePermite el attribute en…
TARGET_CLASSClases, interfaces, traits y enums
TARGET_FUNCTIONFunciones y closures
TARGET_METHODMétodos
TARGET_PROPERTYPropiedades
TARGET_CLASS_CONSTANTConstantes de clase y casos de enum
TARGET_PARAMETERParámetros
TARGET_ALLTodo lo anterior; es el valor por defecto
IS_REPEATABLEFlag: el mismo attribute puede aparecer varias veces en un elemento

PHP 8.5 añade TARGET_CONSTANT para las constantes globales declaradas con const. Una clase final readonly encaja bien: un attribute es metadato, no tiene por qué cambiar después de construirse. Si vienes de readonly y value objects, es el mismo patrón.

Leerlos con Reflection #

Toda la API de Reflection tiene getAttributes(): clases, métodos, funciones, propiedades, constantes y parámetros. Devuelve objetos ReflectionAttribute, con el nombre y los argumentos tal como se escribieron. Para tener la instancia real hay que pedirla con newInstance(). Este es un enrutador mínimo, completo y ejecutable:

php · router.php 
<?php

declare(strict_types=1);

#[Attribute(Attribute::TARGET_METHOD | Attribute::IS_REPEATABLE)]
final readonly class Route
{
    public function __construct(
        public string $path,
        public string $method = 'GET',
    ) {
    }
}

final class InvoiceController
{
    #[Route('/invoices')]
    public function list(): string
    {
        return 'listado';
    }

    #[Route('/invoices/{id}')]
    #[Route('/facturas/{id}')]
    public function show(): string
    {
        return 'detalle';
    }

    #[Route('/invoices', method: 'POST')]
    public function create(): string
    {
        return 'creada';
    }
}

function routesOf(string $controllerClass): array
{
    $routes = [];
    $controller = new ReflectionClass($controllerClass);

    foreach ($controller->getMethods() as $action) {
        foreach ($action->getAttributes(Route::class) as $attribute) {
            $route = $attribute->newInstance();
            $routes[] = sprintf('%-4s %-16s -> %s', $route->method, $route->path, $action->getName());
        }
    }

    return $routes;
}

echo implode(PHP_EOL, routesOf(InvoiceController::class)), PHP_EOL;
bash · salida 
$ php router.php
GET  /invoices        -> list
GET  /invoices/{id}   -> show
GET  /facturas/{id}   -> show
POST /invoices        -> create

getAttributes(Route::class) filtra por nombre exacto. Si pasas también ReflectionAttribute::IS_INSTANCEOF, filtra por herencia: así un validador pide «todo lo que implemente mi interfaz Constraint» sin conocer cada regla concreta.

Cuándo se instancian, y cuándo fallan #

Aquí está la sorpresa. Con tus attributes, al compilar PHP solo comprueba la sintaxis y que los argumentos sean constantes. La clase del attribute, su target y si se repite no se validan hasta newInstance(), y su constructor no se ejecuta hasta ese momento:

php · lazy.php 
<?php

declare(strict_types=1);

#[Attribute(Attribute::TARGET_METHOD)]
final readonly class Route
{
    public function __construct(public string $path)
    {
    }
}

#[Route('/en-una-clase')]
#[ClaseQueNoExiste]
final class Report
{
}

$attributes = (new ReflectionClass(Report::class))->getAttributes();

foreach ($attributes as $attribute) {
    echo $attribute->getName(), ': ';

    try {
        $attribute->newInstance();
        echo 'ok', PHP_EOL;
    } catch (Error $error) {
        echo $error->getMessage(), PHP_EOL;
    }
}
bash · salida 
$ php lazy.php
Route: Attribute "Route" cannot target class (allowed targets: method)
ClaseQueNoExiste: Attribute class "ClaseQueNoExiste" not found

El fichero carga sin errores con un attribute de una clase que no existe. Repetir uno sin IS_REPEATABLE da must not be repeated, y usar como attribute una clase sin #[Attribute] da Attempting to use non-attribute class, ambos también al instanciar. Por eso un error de attribute aparece tarde: cuando el framework recorre tus clases, no cuando escribes el código.

Lo que hacen los frameworks con ellos #

Rutas, validación, eventos, mapeo de Doctrine o tests de PHPUnit siguen el mismo esquema que el enrutador de arriba. Lo que añade el framework es la caché: Reflection no es gratis, así que no se recorre en cada petición.

1 Tu código lleva #[...]rutas, reglas, listeners
2 El framework lee con ReflectiongetAttributes y newInstance
3 Genera PHP plano en cachétabla de rutas, mapa de listeners
4 Se usa la cachésin volver a tocar Reflection

Los attributes se leen al construir la caché; en producción se ejecuta el resultado.

php · Symfony: rutas, validación y eventos 
<?php

declare(strict_types=1);

use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\Routing\Attribute\Route;
use Symfony\Component\Validator\Constraints as Assert;

final class SignUpRequest
{
    #[Assert\NotBlank]
    #[Assert\Length(max: 20)]
    public string $username = '';
}

final class AccountController
{
    #[Route('/accounts', methods: ['POST'])]
    public function create(): Response
    {
    }
}

#[AsEventListener]
final class SendWelcomeEmail
{
    public function __invoke(AccountCreated $event): void
    {
    }
}

Es la misma idea que el autowiring de el contenedor: el framework lee metadatos de tus clases y genera el cableado. Por eso, tras añadir una ruta en producción, hay que regenerar la caché.

Attributes del núcleo que conviene usar #

PHP trae algunos attributes que el propio motor sí interpreta, sin Reflection de por medio:

AttributeDesdeQué hace
#[\ReturnTypeWillChange]8.1Silencia el aviso de tipo de retorno al sobrescribir un método de una clase o interfaz interna sin declararlo. Es un parche de migración.
#[\SensitiveParameter]8.2Oculta el valor del parámetro en las trazas de excepción.
#[\AllowDynamicProperties]8.2Permite propiedades dinámicas en una clase, deprecadas desde 8.2.
#[\Override]8.3Error fatal si el método no sobrescribe nada del padre o de una interfaz.
#[\Deprecated]8.4Emite un aviso E_USER_DEPRECATED al llamar a la función, el método o la constante.
#[\NoDiscard]8.5Avisa si se ignora el valor de retorno; se descarta a propósito con (void).

#[\Override] es el más rentable: protege contra la errata y contra el padre que renombra su método. Sin él, el hijo se queda con un método huérfano que nadie llama.

php · override.php 
<?php

declare(strict_types=1);

class Notifier
{
    protected function deliver(string $message): void
    {
    }
}

final class SlackNotifier extends Notifier
{
    #[\Override]
    protected function delivr(string $message): void
    {
    }
}
bash · salida 
$ php override.php
PHP Fatal error:  SlackNotifier::delivr() has #[\Override] attribute, but no matching parent method exists

#[\SensitiveParameter] es el otro imprescindible: una contraseña que llega a una traza acaba en los logs o en tu herramienta de errores. Con él, si la traza incluye argumentos, muestra connect('admin', Object(SensitiveParameterValue)) en lugar del valor.

Attributes frente a anotaciones en docblock #

Attribute #[...]

  • Lo parsea el motor: una errata de sintaxis rompe la compilación
  • El nombre es una clase real, resuelta con use
  • El IDE y PHPStan la siguen al renombrar y la validan
  • Se lee con Reflection, sin parsear texto

Anotación @Route en docblock

  • Es un comentario: los errores no avisan
  • Necesita una librería que parsee el texto en ejecución
  • Renombrar la clase no actualiza el comentario
  • Depende de que el docblock no se elimine

El docblock no muere: sigue siendo el sitio de los tipos que PHP no expresa, como list<Invoice> o @template, que verás en generics con PHPDoc. La regla es simple: si lo lee el analizador estático, PHPDoc; si lo lee tu código en ejecución, attribute. Pasar un proyecto antiguo de anotaciones a attributes es trabajo mecánico, el que hace Rector.

Errores típicos #

Lo que se cuela en las revisiones

  • Creer que el attribute actúa solo. Poner #[Length(max: 20)] en una propiedad no impide asignar 30 caracteres. Valida quien lo lee, cuando lo lee.
  • La errata o el use que falta. #[Rout('/x')] carga sin error y el framework, que filtra por Route::class, nunca lo ve. La ruta no existe y nada avisa.
  • Lógica en el constructor del attribute. Es metadato: no recibe servicios ni toca base de datos. Lo que hace falta ejecutar va en el código que lo lee.
  • Leer con Reflection en cada petición. Si construyes tu propio lector, guarda el resultado en caché como hacen los frameworks.
  • Usar #[\ReturnTypeWillChange] como solución. Es un parche temporal; lo correcto es declarar el tipo de retorno.

Cómo comprobarlo #

Como PHP valida tarde, quien valida pronto es el análisis estático. PHPStan comprueba los attributes desde el nivel 0: clase inexistente, target incorrecto y repetición indebida. Los tipos de los argumentos los revisa a partir del nivel 5.

bash · PHPStan sobre attributes mal puestos 
$ vendor/bin/phpstan analyse --level=5 --error-format=raw src/Report.php
src/Report.php:13:Attribute class Route does not have the class target. [identifier=attribute.target]
src/Report.php:16:Attribute class Rout does not exist. [identifier=attribute.notFound]
src/Report.php:22:Attribute class Route is not repeatable but is already present above the method. [identifier=attribute.nonRepeatable]
src/Report.php:27:Parameter $path of attribute class Route constructor expects string, int given. [identifier=argument.type]

Y para tus propios attributes, el mejor test es el del enrutador de arriba: un test unitario que recorre las clases con Reflection, llama a newInstance() sobre todo lo que encuentra y comprueba el resultado. Si algún attribute está mal declarado, falla ahí y no en producción. El pipeline que ya tienes en CI para PHP ejecuta las dos cosas.

Cuándo aplicarlo #

Attributes cuando…

  • El metadato pertenece a un elemento concreto: la ruta de un método, la regla de una propiedad
  • Lo va a leer código en ejecución: un framework, un validador, un serializador
  • Quieres que el motor marque un contrato: #[\Override], #[\SensitiveParameter]

No hacen falta cuando…

  • La información es de tipos y solo la lee PHPStan: va en PHPDoc
  • La configuración cambia por entorno: va en configuración, no en el código
  • Lo que quieres es ejecutar lógica: eso es un método o un decorador, no un metadato

La alternativa sencilla

Si solo tienes cinco rutas, un array ['/invoices' => [InvoiceController::class, 'list']] se lee de un vistazo y no necesita Reflection ni caché. Los attributes compensan cuando las piezas crecen y quieres que cada una declare lo suyo.

Resumen #

Lo que te llevas

  • Un attribute es metadato: PHP lo guarda y no hace nada hasta que alguien lo lee con Reflection.
  • Se declara con #[Attribute], con los targets permitidos y IS_REPEATABLE si puede repetirse.
  • getAttributes() no valida nada; la clase, el target y la repetición se comprueban en newInstance().
  • Los frameworks leen los attributes una vez y cachean el resultado; en producción no se recorre Reflection.
  • Usa #[\Override] y #[\SensitiveParameter] siempre que apliquen: los interpreta el propio motor.
  • PHPDoc para lo que lee el analizador estático; attributes para lo que lee tu código en ejecución. PHPStan los valida desde el nivel 0.
