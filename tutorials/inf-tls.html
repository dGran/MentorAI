TLS y certificados en la práctica

TLS resuelve tres problemas a la vez y solo se habla de uno. Cifra —nadie lee lo que pasa por el cable—, pero también autentica —hablas con quien crees— y da integridad —nadie ha cambiado nada por el camino—. El segundo es el que hace falta entender para no meter la pata al configurarlo.

Qué prueba un certificado #

Un certificado no dice que un sitio sea de fiar. Dice una cosa mucho más concreta: que quien lo presenta controla ese nombre de dominio. Nada más. Un sitio fraudulento puede tener un certificado válido perfectamente; lo que no puede es presentar el de otro dominio.

1 El navegador confía en un puñado de raícesVienen en el sistema operativo
2 Certificados intermediosDe la autoridad certificadora
3 El tuyo, para ejemplo.comVálido si la cadena entera verifica

Si falta un intermedio, el navegador puede apañárselas y muchos clientes de API no: es el fallo de configuración más común.

«En el navegador va bien y desde cURL falla»

Casi siempre es la cadena incompleta. Los navegadores traen un mecanismo para buscar el intermedio que falta; curl, PHP y la mayoría de clientes de API no. Se sirve el fullchain, no solo el certificado del dominio, y se comprueba con openssl s_client -connect ejemplo.com:443 -showcerts.

Certificados que se renuevan solos #

Let's Encrypt emite certificados de 90 días, gratis y automatizables. La duración corta es deliberada: obliga a que la renovación esté automatizada, y una renovación automatizada no se olvida.

bash · certbot con nginx 
sudo certbot --nginx -d ejemplo.com -d www.ejemplo.com

sudo certbot renew --dry-run

systemctl list-timers | grep certbot

El --dry-run es el paso que separa «lo configuré» de «funciona»: ensaya la renovación completa sin gastar cuota. Y el timer es lo que confirma que alguien lo hará dentro de 60 días, cuando ya nadie se acuerde.

Renovar no es recargar

Certbot escribe los ficheros nuevos, y nginx sigue sirviendo en memoria el certificado viejo hasta que se le dice. Si el hook de recarga no está puesto, el certificado caduca con el nuevo ya en disco: renovó bien y el sitio da error igual. Es de los incidentes más frustrantes que existen.

La configuración que importa #

ini · lo esencial de TLS en nginx 
ssl_certificate = /etc/letsencrypt/live/ejemplo.com/fullchain.pem
ssl_certificate_key = /etc/letsencrypt/live/ejemplo.com/privkey.pem
ssl_protocols = TLSv1.2 TLSv1.3
ssl_session_cache = shared:SSL:10m
ssl_stapling = on
add_header = Strict-Transport-Security "max-age=31536000; includeSubDomains"
DirectivaQué aporta
ssl_protocolsSolo 1.2 y 1.3. Las versiones anteriores están rotas, no obsoletas
ssl_session_cacheReanudar sesiones evita repetir el handshake completo: mucha latencia menos
ssl_staplingEl servidor adjunta la prueba de que el certificado no está revocado, y el cliente se ahorra una consulta
Strict-Transport-SecurityEl navegador recuerda que este dominio es solo HTTPS y no vuelve a intentar por HTTP

HSTS no se puede deshacer rápido

Con max-age=31536000 le estás diciendo al navegador que durante un año no acepte HTTP para tu dominio, y esa instrucción vive en el navegador del usuario. Si luego tienes un problema con el certificado, no puedes volver a HTTP mientras lo arreglas: los visitantes recurrentes no podrán entrar. Empieza con un max-age pequeño y súbelo cuando estés seguro.

Cifrar también dentro #

«Es tráfico interno» era una de las ocho falacias. Terminar TLS en el balanceador y que el resto viaje en claro es aceptable dentro de una red que controlas de verdad, y deja de serlo en cuanto hay varias zonas, varios equipos o una nube compartida.

Para tráfico entre servicios propios, la respuesta es TLS mutuo: no solo el cliente verifica al servidor, también el servidor verifica al cliente con su propio certificado. Eso convierte el certificado en la identidad del servicio y quita de en medio las claves de API compartidas, que acaban en variables de entorno, repositorios y capturas de pantalla.

Cuándo aplicarlo #

TLS obligatorio cuando…

  • Hay tráfico por internet, sin excepción
  • Viajan credenciales, cookies de sesión o datos personales
  • Cruza zonas o proveedores distintos
  • Quieres HTTP/2 o /3: en la práctica exigen TLS

Puedes terminar en el borde cuando…

  • Detrás hay una red privada que controlas del todo
  • Los saltos internos son dentro de la misma máquina
  • Es desarrollo local

Resumen #

Lo que te llevas

  • Un certificado no prueba que un sitio sea de fiar: prueba que quien lo presenta controla ese dominio.
  • «En el navegador va y desde cURL falla» es casi siempre la cadena incompleta: se sirve el fullchain.
  • Los 90 días de Let's Encrypt son deliberados: obligan a automatizar, y lo automatizado no se olvida.
  • Renovar no es recargar: sin el hook, el certificado caduca con el nuevo ya en disco.
  • HSTS vive en el navegador del usuario y no se puede deshacer rápido: empieza con un max-age pequeño.
