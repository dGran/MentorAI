Smart pointers: Box, Rc, Arc y RefCell

Cuándo necesitas un puntero inteligente: heap con Box, conteo de referencias con Rc y Arc, y mutabilidad interior con RefCell y Mutex.

Box<T>: alojar en el heap

Box<T> es el puntero inteligente más simple: aloja un valor en el heap y libera la memoria cuando el Box sale de scope. Implementa Deref, así que puedes usarlo como si fuera el tipo interno directamente.

El caso de uso más común: tipos recursivos. Rust necesita saber el tamaño de cada tipo en compilación. Un tipo recursivo tiene tamaño infinito teórico:

enum ListaEnlazada {
    Nodo(i32, Box<ListaEnlazada>),
    Fin,
}

fn main() {
    let lista = ListaEnlazada::Nodo(
        1,
        Box::new(ListaEnlazada::Nodo(
            2,
            Box::new(ListaEnlazada::Fin),
        )),
    );
}

Con Box, el nodo siguiente vive en el heap y el campo en la estructura es solo un puntero (tamaño fijo). El compilador puede calcular el tamaño del tipo.

El segundo uso frecuente: Box<dyn Trait> para colecciones heterogéneas con polimorfismo en runtime (lo vimos en el tutorial de traits).

Coste de Box: una sola indirección de puntero por acceso. Para la mayoría de aplicaciones, es insignificante. El compilador puede optimizarlo en muchos casos.

Rc<T>: múltiples dueños en un thread

Rc<T> (Reference Counted) permite que múltiples partes del código sean dueñas del mismo dato. Implementa conteo de referencias, similar a cómo PHP gestiona la memoria internamente para valores escalares.

use std::rc::Rc;

fn main() {
    let datos = Rc::new(vec![1, 2, 3]);
    let referencia_a = Rc::clone(&datos);
    let referencia_b = Rc::clone(&datos);

    println!("Referencias activas: {}", Rc::strong_count(&datos)); // 3

    println!("{:?}", referencia_a);
    println!("{:?}", referencia_b);
} // cuando todos los Rc salen de scope, el contador llega a 0 y se destruye el Vec

Rc::clone no clona el dato: incrementa el contador de referencias. Es una operación barata. Cuando el último Rc sale de scope, el contador llega a 0 y el dato se destruye.

La limitación crítica: Rc<T> no implementa Send. No puede cruzar límites de thread. Si intentas moverlo a otro thread, el compilador lo rechaza. Para concurrencia, necesitas Arc<T>.

Ciclos de referencias: Rc<T> puede crear memory leaks si dos Rc se apuntan mutuamente. El contador nunca llega a 0. Para ciclos, usa Weak<T> (referencia débil que no incrementa el contador).

Arc<T>: Rc atómico para múltiples threads

Arc<T> (Atomically Reference Counted) es la versión de Rc que puede compartirse entre threads. Las operaciones sobre el contador son atómicas, lo que garantiza que no hay data races en el conteo.

use std::sync::Arc;
use std::thread;

fn main() {
    let datos = Arc::new(vec![1, 2, 3, 4, 5]);

    let handles: Vec<_> = (0..3).map(|i| {
        let datos = Arc::clone(&datos);
        thread::spawn(move || {
            println!("Thread {}: {:?}", i, datos);
        })
    }).collect();

    for handle in handles {
        handle.join().unwrap();
    }
}

El coste adicional respecto a Rc: las operaciones atómicas son ligeramente más caras que las no atómicas. En la práctica, la diferencia es despreciable para aplicaciones web; solo importa en código de altísimo rendimiento con miles de incrementos por segundo.

RefCell<T>: mutabilidad interior

El borrow checker verifica las reglas de préstamo en compilación. Hay situaciones donde el compilador no puede determinar en compilación que el código es correcto, pero tú sabes que lo es. RefCell<T> mueve la verificación de las reglas a runtime.

use std::cell::RefCell;

fn main() {
    let datos = RefCell::new(vec![1, 2, 3]);

    {
        let mut prestamo_mutable = datos.borrow_mut();
        prestamo_mutable.push(4);
    } // borrow_mutable se libera aquí

    let prestamo_inmutable = datos.borrow();
    println!("{:?}", *prestamo_inmutable); // [1, 2, 3, 4]
}

.borrow() retorna un Ref<T> (préstamo inmutable). .borrow_mut() retorna un RefMut<T> (préstamo mutable). Si en runtime intentas violar las reglas del borrow checker (dos mutables simultáneos, o mutable e inmutable simultáneos), el programa entra en panic.

El caso de uso más típico: Rc<RefCell<T>> para datos compartidos mutables en un solo thread:

use std::rc::Rc;
use std::cell::RefCell;

fn main() {
    let contador = Rc::new(RefCell::new(0));

    let c1 = Rc::clone(&contador);
    let c2 = Rc::clone(&contador);

    *c1.borrow_mut() += 1;
    *c2.borrow_mut() += 1;

    println!("{}", contador.borrow()); // 2
}

Mutex<T> y RwLock<T>

Mutex<T> es el equivalente de RefCell para múltiples threads: garantiza acceso exclusivo al dato protegiendo con un mutex del sistema operativo.

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let contador = Arc::new(Mutex::new(0));

    let handles: Vec<_> = (0..10).map(|_| {
        let contador = Arc::clone(&contador);
        thread::spawn(move || {
            let mut bloqueo = contador.lock().unwrap();
            *bloqueo += 1;
        }) // bloqueo se libera aquí (RAII)
    }).collect();

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Resultado: {}", *contador.lock().unwrap()); // 10
}

El MutexGuard retornado por .lock() se libera automáticamente cuando sale de scope (RAII). No hay unlock() explícito.

RwLock<T> permite múltiples lectores simultáneos o un escritor exclusivo, igual que el modelo de referencias de Rust pero en runtime entre threads. Más eficiente que Mutex cuando los lectores son frecuentes y los escritores raros.

Deadlocks: Rust previene los data races pero no los deadlocks. Si thread A tiene el lock de X y espera el lock de Y, mientras thread B tiene el de Y y espera el de X, ambos se bloquean para siempre. El compilador no puede detectar esto. Diseña el orden de adquisición de locks cuidadosamente.

Árbol de decisión

La pregunta "¿qué smart pointer necesito?" tiene una respuesta estructurada:

  1. ¿Necesito solo un dueño? → Ownership normal o Box<T> si el tipo es recursivo o necesitas trait object.
  2. ¿Necesito múltiples dueños en un solo thread? → Rc<T>.
  3. ¿Necesito múltiples dueños entre varios threads? → Arc<T>.
  4. ¿Necesito mutabilidad del dato compartido en un solo thread? → Rc<RefCell<T>>.
  5. ¿Necesito mutabilidad del dato compartido entre threads? → Arc<Mutex<T>> o Arc<RwLock<T>>.
El caso más común en servidores web: estado de la aplicación compartido (pool de BD, config, caché) entre handlers async. La respuesta es Arc<T> si el estado es inmutable, o Arc<RwLock<T>> si necesita mutarse.

Resumen

  • Box<T> aloja en el heap con un solo dueño; necesario para tipos recursivos y trait objects (Box<dyn Trait>).
  • Rc<T> permite múltiples dueños en un solo thread con conteo de referencias; Rc::clone incrementa el contador, no clona el dato.
  • Arc<T> es Rc con contador atómico: seguro entre threads; ligeramente más caro que Rc.
  • RefCell<T> mueve las reglas del borrow checker a runtime; panic si las violas. Útil cuando el compilador no puede verificar correctitud en compilación.
  • Arc<Mutex<T>> es el patrón para estado mutable compartido entre threads; el MutexGuard se libera automáticamente por RAII.
  • Rust previene data races pero no deadlocks: el orden de adquisición de locks sigue siendo responsabilidad del programador.
