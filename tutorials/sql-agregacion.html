GROUP BY y HAVING: agregar con criterio

GROUP BY colapsa filas, las funciones de agregado las resumen, y HAVING filtra los grupos resultantes. Entender el orden de evaluación evita el 90% de los errores.

Sin GROUP BY, una consulta devuelve una fila por registro. Con GROUP BY, devuelve una fila por grupo. El resto de la cláusula (SELECT, HAVING, ORDER BY) opera sobre esos grupos, no sobre filas individuales.

Qué hace GROUP BY #

GROUP BY toma todas las filas del resultado hasta ese punto y las colapsa en grupos: cada combinación única de los valores especificados forma un grupo. El resultado tiene una fila por grupo.

sql 
-- Sin GROUP BY: una fila por pedido
SELECT estado, total FROM pedidos;

-- Con GROUP BY: una fila por estado, el total es un agregado
SELECT estado, COUNT(*) AS cantidad, SUM(total) AS importe_total
FROM pedidos
GROUP BY estado;

La regla que deriva de esto: después de GROUP BY, en el SELECT solo puedes poner columnas que formen parte del agrupador (están en el GROUP BY) o expresiones de agregado sobre las demás. Cualquier otra columna es ambigua: el grupo tiene varias filas con valores distintos, ¿cuál devuelves?

MySQL en modo permisivo: la trampa silenciosa

MySQL sin ONLY_FULL_GROUP_BY acepta columnas no agregadas en el SELECT aunque no estén en el GROUP BY. Devuelve un valor arbitrario del grupo. El resultado parece correcto hasta que los datos cambian. PostgreSQL y MySQL 5.7+ con la configuración por defecto rechazan esto con error.

Funciones de agregado #

Función Qué hace Con NULL
COUNT(*) Cuenta filas del grupo Los cuenta (una fila con todo NULL suma 1)
COUNT(expr) Cuenta filas donde expr no es NULL Ignora los NULL
COUNT(DISTINCT expr) Cuenta valores únicos no-NULL Ignora los NULL
SUM(expr) Suma los valores Ignora los NULL; grupo vacío → NULL
AVG(expr) Promedio Ignora los NULL; grupo vacío → NULL
MIN(expr) / MAX(expr) Mínimo / máximo Ignoran los NULL

El matiz de AVG: ignora los NULL al calcular la media, lo que no siempre es lo que quieres. Si tienes 10 filas y 4 tienen NULL en el campo medido, el promedio se calcula sobre 6, no sobre 10. Considera si los NULL deben tratarse como cero o como ausencia de dato.

sql 
-- Estadísticas de pedidos por cliente
SELECT
    c.nombre,
    COUNT(p.id)           AS total_pedidos,
    COUNT(DISTINCT p.id)  AS pedidos_unicos,
    SUM(p.total)          AS importe_total,
    AVG(p.total)          AS ticket_medio,
    MIN(p.total)          AS pedido_minimo,
    MAX(p.total)          AS pedido_maximo
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id
GROUP BY c.id, c.nombre;

WHERE vs HAVING: el orden importa #

El motor ejecuta una consulta en este orden lógico, independientemente del orden en que lo escribas:

1 FROM + JOINConstruye el conjunto de filas de trabajo
2 WHEREFiltra filas individuales antes de agrupar
3 GROUP BYColapsa filas en grupos
4 HAVINGFiltra grupos completos
5 SELECTProyecta las columnas del resultado
6 ORDER BY + LIMITOrdena y recorta

WHERE opera sobre filas; HAVING opera sobre grupos. No son intercambiables.

La consecuencia práctica: si puedes filtrar en WHERE, hazlo. El motor agrupa menos filas y la consulta es más eficiente. HAVING solo tiene sentido cuando la condición depende del resultado de una función de agregado.

sql 
-- Clientes con más de 3 pedidos en el último mes
SELECT c.nombre, COUNT(p.id) AS total
FROM clientes c
JOIN pedidos p ON p.cliente_id = c.id
WHERE p.fecha >= '2026-06-01'     -- filtra filas antes de agrupar (eficiente)
GROUP BY c.id, c.nombre
HAVING COUNT(p.id) > 3;           -- filtra grupos: solo cuando la condición usa un agregado

-- Mala práctica: mover el filtro de fecha al HAVING
-- HAVING p.fecha >= '2026-06-01' AND COUNT(p.id) > 3
-- El motor agrupa TODOS los pedidos históricos y luego descarta; mucho más lento.

Errores típicos #

Alias de SELECT en HAVING. El SELECT se evalúa después del HAVING, así que el alias definido en SELECT no existe aún en el momento en que HAVING se ejecuta. PostgreSQL da error. MySQL lo acepta como extensión, pero es una dependencia del motor que evitar.

No funciona en PostgreSQL

sql 
SELECT cliente_id, COUNT(*) AS total
FROM pedidos
GROUP BY cliente_id
HAVING total > 5;

Portátil entre motores

sql 
SELECT cliente_id, COUNT(*) AS total
FROM pedidos
GROUP BY cliente_id
HAVING COUNT(*) > 5;

Columnas ambiguas en el GROUP BY. Cuando agrupas por id de una tabla y necesitas el nombre, incluye ambos en el GROUP BY o usa ANY_VALUE(nombre) en MySQL si el nombre es funcionalmente dependiente del id. En PostgreSQL, si el id es clave primaria del FROM, puedes agrupar solo por id y seleccionar cualquier columna de esa tabla.

sql 
-- MySQL y PostgreSQL: incluir todas las columnas no agregadas en GROUP BY
SELECT c.id, c.nombre, COUNT(p.id) AS pedidos
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id
GROUP BY c.id, c.nombre;

-- PostgreSQL: si c.id es PK de clientes, agrupar solo por c.id es suficiente
-- GROUP BY c.id;

GROUP BY con expresiones #

El agrupador no está limitado a columnas: puede ser cualquier expresión. El caso más habitual en backend es agrupar por fecha truncada para generar informes por día, semana o mes.

sql 
-- Pedidos por mes (MySQL/MariaDB)
SELECT DATE_FORMAT(fecha, '%Y-%m') AS mes, COUNT(*) AS total, SUM(importe) AS facturado
FROM pedidos
WHERE fecha >= '2026-01-01'
GROUP BY DATE_FORMAT(fecha, '%Y-%m')
ORDER BY mes;

-- Equivalente en PostgreSQL con DATE_TRUNC
SELECT DATE_TRUNC('month', fecha) AS mes, COUNT(*) AS total, SUM(importe) AS facturado
FROM pedidos
WHERE fecha >= '2026-01-01'
GROUP BY DATE_TRUNC('month', fecha)
ORDER BY mes;

GROUP BY sobre múltiples columnas forma grupos por la combinación única de todos los valores. Si agrupas por estado y categoria, obtienes una fila por cada par (estado, categoria) que exista en los datos.

sql 
-- Una fila por cada combinación (estado, categoria)
SELECT estado, categoria, COUNT(*) AS total
FROM pedidos
GROUP BY estado, categoria
ORDER BY estado, categoria;

Cuándo aplicarlo

Úsalo cuando…

  • GROUP BY en SQL siempre que puedas: mueve menos datos que agregar en la aplicación.
  • HAVING para filtrar el resultado del agregado (p.ej. grupos con más de N elementos).
  • WHERE para filtrar filas antes de agrupar: más eficiente porque reduce el conjunto antes del GROUP BY.

No lo uses cuando…

  • HAVING en lugar de WHERE para condiciones sobre columnas no agregadas: WHERE filtra antes y es más eficiente.
  • GROUP BY en la aplicación cuando la BD puede hacerlo y el conjunto de datos es grande.
  • Seleccionas columnas no incluidas en GROUP BY sin función de agregado: produce resultados no deterministas.

Resumen #

Lo que te llevas

  • GROUP BY colapsa filas. En el SELECT solo puedes usar columnas del agrupador o funciones de agregado.
  • Orden lógico: WHERE → GROUP BY → HAVING → SELECT. WHERE filtra filas; HAVING filtra grupos ya formados.
  • Si puedes filtrar en WHERE, hazlo: agrupa menos filas y la consulta es más eficiente.
  • COUNT(*) cuenta filas (incluye NULLs). COUNT(columna) cuenta no-NULLs. COUNT(DISTINCT columna) cuenta únicos.
  • AVG y SUM ignoran los NULL. Un grupo vacío devuelve NULL, no cero.
  • En HAVING, repite la expresión de agregado en lugar de usar el alias del SELECT: es más portable y correcto.
