QA funcional: evidencias, no afirmaciones

Los tests automáticos dicen que el código hace lo que el programador pensó. El QA funcional comprueba que la aplicación, levantada de verdad, hace lo que pedía el issue. Y en un método con agentes, su resultado no es un «funciona», sino un dossier que cualquiera puede abrir y repetir.

En la lección anterior el PR pasó la revisión: alguien comprobó el código contra los criterios. Falta la comprobación que nadie puede hacer leyendo código: usar la aplicación. Esta lección explica cómo hace un método esa fase para que sus resultados sean evidencias y no afirmaciones.

Contra la aplicación levantada #

El QA funcional tiene una regla que lo distingue de todo lo anterior: se ejercita la aplicación levantada, como la usaría alguien. Según el criterio, el vehículo cambia:

Criterio Vehículo Evidencia
Visible en pantallaNavegador automatizado (Playwright o similar)Captura del estado que demuestra el criterio
De una APIPetición HTTP real al puerto donde corre la appComando, código de estado y cuerpo de la respuesta, tal cual
Técnico (tests, estilo)Los checks del proyectoSu salida, citada; no requiere navegador

El cliente de test del framework no es QA

Los clientes de test que levantan la aplicación en memoria contra una base de datos de pruebas no pasan por el servidor web, ni por el contenedor, ni por la configuración real. Además, esa suite ya la ejecutaron la implementación y la revisión: volver a lanzarla en el QA no aporta información nueva. Es la forma más común de convertir el QA en un trámite.

El bug, lo primero #

Si el issue es un bug y trae su reproducción (la de la lección del issue), el QA empieza por ella, antes que por ningún criterio. Es el único paso que demuestra que el fallo se fue: los criterios describen el comportamiento correcto, y pasarlos todos es compatible con que el bug siga ahí por otro camino.

1 Reproducir en la rama baseLa reproducción del issue sobre el código sin el arreglo: el fallo aparece
2 Verificar en la rama del PRExactamente el mismo comando sobre el código con el arreglo: el fallo no aparece
3 CriteriosCada criterio de aceptación, uno a uno, con su evidencia

Si el comando cambia entre el antes y el después, la comparación deja de valer.

El dossier: reproducir y verificar #

Las evidencias se organizan en un dossier por issue: un índice, el comando que lo repite todo y una carpeta por ejecución, marcada con el commit sobre el que se hizo.

texto · estructura de un dossier (ficticio) 
.qa-evidence/issue-42/
├── INFORME.md                 índice: objetivo, tabla de ejecuciones, veredicto
├── command.sh                 la reproducción exacta, sin secretos
└── runs/
    ├── 01-reproduce-9f3e2a1/  sobre la rama base: el fallo aparece
    │   ├── run.md             fecha, commit, entorno, resultado
    │   └── assets/            salida cruda, capturas
    └── 02-verify-a1b2c3d/     sobre la rama del PR: el fallo no aparece
        ├── run.md
        └── assets/

Cada ejecución usa un solo vehículo (navegador, HTTP, línea de comandos o base de datos) y registra commit, entorno y datos de partida. «Probado en local» no identifica nada; «commit a1b2c3d, servidor en :8080, base restaurada del snapshot de esta mañana», sí.

Reglas de una evidencia #

  • La captura se abre antes de citarla. Una captura tomada en el momento equivocado (antes de que cargue, con un error en pantalla) prueba lo contrario de lo que se cita. Cada fichero lleva una frase de qué demuestra.
  • Salida cruda, nunca parafraseada. «Devuelve 403 correctamente» es una afirmación; la respuesta literal del curl -i es una evidencia.
  • Lo no probado se enumera. Un caso que no se pudo ejecutar se dice como bloqueado, no se convierte en verde provisional.
  • Los datos de prueba no son los reales. Si el escenario escribe datos, se usan datos de prueba o una copia restaurable; si no hay ninguna de las dos cosas, se declara lo que quedó escrito.
  • Se sanean los secretos, no el resultado. Se ocultan tokens y datos personales sin cambiar lo que se está probando.

Publicar sin ensuciar #

Las evidencias tienen que poder verse desde el PR, pero no deben acabar en la rama principal. La técnica: se suben en un commit propio a la rama del PR, el comentario de QA las enlaza por el identificador de ese commit (enlaces permanentes que sobreviven aunque se borre la rama), y antes del merge ese commit se revierte.

1 Commit de evidenciasEl dossier entra en la rama del PR como último commit, separado del código
2 Comentario de QATabla criterio, resultado y enlace a la evidencia por el commit exacto
3 RevertirAntes del merge se revierte ese commit: el código entra limpio

Los enlaces siguen funcionando después: el commit sigue existiendo en el historial del PR.

Cuando no hay nada que ejercitar #

Hay cambios sin superficie funcional: un script de validación, una regla del proyecto, la configuración de CI. Para ellos, el issue lleva una etiqueta que indica que el QA no se ejecuta, con una línea que lo justifica. La fase de QA no desaparece: comprueba que de verdad ningún criterio es verificable en la aplicación y documenta con qué se verificó en su lugar.

Sin pantalla no es sin superficie

Un endpoint sin interfaz se ejercita por HTTP: no justifica saltarse el QA. Y si un solo criterio se puede ver en la aplicación —aunque sea un texto en una página—, el QA se hace. La etiqueta es para cambios que de verdad no tocan nada que un usuario pueda observar.

Cuándo aplicarlo #

Haz QA con dossier cuando…

  • El cambio lo implementó un agente y va a producción
  • Es un bug: hay que demostrar que se fue, no que el camino feliz funciona
  • Alguien tiene que poder repasar después lo que se comprobó
  • El trabajo se hizo de forma desatendida

Puedes aligerarlo si…

  • El cambio no tiene superficie funcional y está justificado
  • Es un experimento local que no va a producción
  • Una persona prueba el cambio a mano y lo documenta igual

Resumen #

Lo que te llevas

  • El QA funcional ejercita la aplicación levantada: navegador para lo visible, HTTP real para las APIs; el cliente de test del framework no cuenta.
  • Si es un bug, primero se ejecuta su reproducción, con el mismo comando antes y después del arreglo.
  • Las evidencias forman un dossier con un índice, el comando que lo repite y una ejecución por commit y vehículo.
  • Las capturas se abren antes de citarlas, la salida va cruda y lo no probado se enumera.
  • Las evidencias se publican en un commit propio enlazado por su identificador y se revierten antes del merge.
