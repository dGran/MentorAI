La Data API: consultar Postgres por HTTP sin escribir backend

Creas una tabla y ya tienes una API REST para leerla, filtrarla, paginarla y escribir en ella, con joins incluidos. No es magia ni un ORM: es un traductor de URLs a SQL. Saber qué SQL sale de cada llamada es lo que separa una app rápida de una que hace cien consultas por pantalla.

Ya tienes la tabla de notas versionada con migraciones. Ahora le añadimos libretas y aprendemos a sacarle partido a la API que Supabase genera sola: qué se puede pedir, cómo se pagina y cuándo conviene salirse de ella hacia una función SQL.

Cómo funciona: URL entra, SQL sale #

La Data API es PostgREST, un servidor que lee el esquema de tu base de datos al arrancar y expone cada tabla, vista y función de los esquemas expuestos (por defecto, public). Cada petición se convierte en una sola consulta SQL, que se ejecuta con el rol del usuario que llama:

1 GET /rest/v1/notes?select=id,title&title=ilike.recetalo que manda supabase-js por debajo
2 SQLselect id, title from notes where title ilike '%receta%'
3 Rol del usuarioanon o authenticated, con su token disponible para las políticas
4 Filas que la política deja veren JSON

Una petición, una consulta y un rol: por eso RLS se aplica a todo lo que entra por la Data API.

Que una tabla esté en public no basta para que la API la sirva: el rol tiene que tener permisos (grant) sobre ella, y RLS decide qué filas. Durante años, Supabase daba esos permisos automáticamente a cada tabla nueva de public; ahora hay un ajuste, «Automatically expose new tables», en la configuración de la Data API, y Supabase está cambiando el comportamiento por defecto para que exponer sea una decisión explícita.

sql · exponer una tabla de forma explícita 
grant select, insert, update, delete on public.notes to authenticated;

Dato que caduca

Si en tu proyecto la API responde que no encuentra una tabla que sí existe, revisa dos cosas: que su esquema esté en la lista de esquemas expuestos y que el rol tenga grant sobre ella. Escribir los grant en tus migraciones hace que funcione igual con cualquiera de los dos comportamientos por defecto.

Leer y filtrar #

Añadimos libretas para tener una relación con la que jugar:

sql · migración: libretas 
create table public.notebooks (
  id bigint generated always as identity primary key,
  user_id uuid not null default auth.uid() references auth.users (id) on delete cascade,
  name text not null
);

alter table public.notes add column notebook_id bigint references public.notebooks (id) on delete set null;
create index on public.notes (notebook_id);

Cada método de supabase-js añade un trozo a la URL, y cada trozo es un trozo de SQL:

Pide solo las columnas que usas. select("*") sobre una tabla con un campo de texto largo (el cuerpo de la nota) trae ese texto en cada fila del listado aunque la pantalla solo muestre el título.

Relaciones: el join que no escribes #

PostgREST lee las claves foráneas y te deja embeber las filas relacionadas en la misma consulta:

ts · notas con su libreta, en una sola petición 
const { data, error } = await supabase
  .from("notes")
  .select("id, title, notebook:notebooks ( id, name )")
  .order("created_at", { ascending: false });
ts · forma de la respuesta 
[
  { id: 7, title: "Pan de masa madre", notebook: { id: 2, name: "Recetas" } },
  { id: 6, title: "Ideas charla", notebook: null },
]

Funciona en los dos sentidos (una libreta con sus notas: notebooks.select("name, notes ( title )")) y a través de tablas intermedias en relaciones muchos a muchos. Por defecto es un left join: las notas sin libreta salen con notebook: null. Para filtrar por la tabla relacionada se marca el embebido como !inner:

ts · solo las notas de la libreta «Recetas» 
supabase
  .from("notes")
  .select("id, title, notebooks!inner ( name )")
  .eq("notebooks.name", "Recetas");

El N+1 de siempre, ahora desde el navegador

Pedir la lista de notas y luego, en un bucle, la libreta de cada una, es una petición HTTP por fila: veinte notas, veintiuna idas y vueltas de red. Embeber la relación lo resuelve en una. Es el mismo problema que con un ORM, solo que cada consulta además cruza internet.

Paginar: range, count y cursor #

La API nunca devuelve filas sin límite: hay un máximo por petición (1.000 por defecto, configurable en los ajustes de la Data API). Para paginar hay dos estrategias, y son las mismas que en cualquier API (Paginación las compara a fondo):

ts · paginación por desplazamiento, con total 
const pageSize = 20;
const page = 3;

const { data, count } = await supabase
  .from("notes")
  .select("id, title", { count: "exact" })
  .order("created_at", { ascending: false })
  .range((page - 1) * pageSize, page * pageSize - 1);

range(40, 59) pide las filas de la 40 a la 59, ambas incluidas. Con count: "exact" la respuesta trae además el total, que sirve para pintar «página 3 de 12». Ese total es un count(*) completo sobre la tabla filtrada: en tablas grandes cuesta, y count: "estimated" usa la estimación del planificador cuando no necesitas la cifra exacta.

ts · paginación por cursor (keyset) 
const { data } = await supabase
  .from("notes")
  .select("id, title")
  .lt("id", lastSeenId)
  .order("id", { ascending: false })
  .limit(20);

La paginación por cursor no salta filas: pide «las 20 siguientes a la última que vi». Es estable aunque se inserten notas mientras paginas y no se degrada en la página 500, que es lo que pide un scroll infinito.

Escribir: insert, update, upsert y delete #

ts · las cuatro escrituras 
const { data: created, error } = await supabase
  .from("notes")
  .insert({ title: "Lista de la compra", notebook_id: 2 })
  .select()
  .single();

await supabase.from("notes").update({ title: "Compra del sábado" }).eq("id", created.id);

await supabase.from("notebooks").upsert({ id: 2, name: "Recetas de casa" }, { onConflict: "id" });

await supabase.from("notes").delete().eq("id", created.id);

Tres detalles que muerden:

  • **Sin .select() no hay fila de vuelta.** Un insert devuelve solo el estado HTTP. Si quieres el id generado, encadena .select(), y entonces la fila tiene que pasar también tu política de lectura.
  • Un update o delete sin filtro afecta a todo lo que RLS te deje. supabase-js exige un filtro en update y delete para evitar sustos, pero un filtro mal puesto sigue siendo un filtro.
  • **No mandes user_id desde el cliente.** Lo rellena el default auth.uid() de la tabla, y la política de inserción comprobará que coincide con quien escribe. Un cliente que manda el dueño puede mandar el de otro.

Cuando la API se queda corta: funciones con rpc #

Una petición es una consulta. Cuando necesitas varias operaciones en una transacción, una agregación compleja o lógica que no se expresa con filtros, escribes una función de Postgres y la llamas con rpc:

sql · mover una nota de libreta comprobando que las dos son tuyas 
create function public.move_note(note_id bigint, target_notebook_id bigint)
returns void
language plpgsql
security invoker
set search_path = ''
as $$
begin
  if not exists (
    select 1 from public.notebooks
    where id = target_notebook_id and user_id = (select auth.uid())
  ) then
    raise exception 'La libreta no existe o no es tuya';
  end if;

  update public.notes set notebook_id = target_notebook_id where id = note_id;
end;
$$;
ts · llamarla 
const { error } = await supabase.rpc("move_note", { note_id: 7, target_notebook_id: 3 });

Con security invoker la función corre con los permisos de quien la llama, así que RLS sigue aplicándose dentro. La alternativa, security definer, la verás en funciones y triggers, junto con por qué ese set search_path = '' no es opcional.

Vistas: cómodas y con una trampa #

Una vista se expone como una tabla más y es una forma limpia de ofrecer una consulta compleja (la nota con su número de adjuntos, por ejemplo; la tabla attachments llega con Storage). La trampa: por defecto, una vista de Postgres se ejecuta con los permisos de su dueño, que es postgres, y se salta RLS de las tablas que lee.

sql · vista que respeta RLS 
create view public.notes_with_counts
with (security_invoker = true)
as
select n.id, n.title, count(a.id) as attachments
from public.notes n
left join public.attachments a on a.note_id = n.id
group by n.id;

security_invoker = true (desde Postgres 15) hace que la vista consulte con el rol de quien la pide. Sin esa línea, cualquiera con la clave publicable vería los títulos de todas las notas de todos los usuarios. El Security Advisor del panel marca las vistas que no la llevan.

Resumen #

Lo que te llevas

  • La Data API es PostgREST: cada petición HTTP se traduce a una consulta SQL que se ejecuta con el rol del usuario y pasa por RLS.
  • Una tabla necesita estar en un esquema expuesto y tener grant para el rol; escribir los grant en las migraciones evita depender del comportamiento por defecto.
  • Las relaciones se embeben con la sintaxis de select aprovechando las claves foráneas; !inner filtra por la tabla relacionada y evita el N+1.
  • range pagina por desplazamiento (con count para el total) y los filtros por id permiten paginar por cursor.
  • Un insert no devuelve la fila sin .select(), y el dueño de la fila lo pone la base de datos, no el cliente.
  • rpc llama a funciones de Postgres para lo que no cabe en una consulta; las vistas expuestas llevan security_invoker = true.
