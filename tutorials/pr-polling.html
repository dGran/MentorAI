Polling y long polling: la línea base

Antes de montar WebSockets conviene mirar la opción aburrida, porque resuelve más casos de los que se admite en público. Preguntar cada X segundos no tiene nada de elegante y tiene tres virtudes difíciles de batir: funciona en todas partes, se depura con la pestaña de red y no mantiene nada abierto.

Polling: el suelo del que partimos #

El cliente pregunta cada cierto tiempo si hay algo nuevo. La crítica evidente es el desperdicio: la mayoría de las respuestas son «nada». Pero ese coste depende de dos cosas que puedes controlar, y suele ser menor de lo que la gente supone.

A favor

  • Funciona con cualquier infraestructura, sin excepción
  • Sin estado: cualquier servidor atiende cualquier petición
  • Se cachea, se limita por tasa y se depura como todo lo demás
  • Si el cliente se va, deja de preguntar. No hay que limpiar nada

En contra

  • Latencia media = la mitad del intervalo
  • Peticiones inútiles cuando no hay novedades
  • Cada una paga cabeceras, autenticación y arranque
  • Con muchos clientes y poco intervalo, se nota

Un polling bien hecho cuesta muy poco

Con ETag, una consulta que no ha cambiado devuelve un 304 sin cuerpo, y si el ETag se calcula sobre algo barato ni siquiera toca la base de datos. Añade un intervalo adaptativo —más lento cuando no pasa nada— y pausar cuando la pestaña está en segundo plano, y el coste real se desploma.

php · un endpoint de polling barato 
<?php

declare(strict_types=1);

final class EstadoPedidoController
{
    #[Route('/pedidos/{id}/estado')]
    public function __invoke(string $id, Request $peticion): Response
    {
        $version = $this->pedidos->versionDe($id);
        $respuesta = new JsonResponse(null);

        $respuesta->setEtag((string) $version);
        $respuesta->setPrivate();

        if ($respuesta->isNotModified($peticion)) {
            return $respuesta;
        }

        return $respuesta->setData($this->pedidos->estadoDe($id));
    }
}

La clave está en el orden: primero se obtiene una versión barata —un SELECT de una columna, o un contador en Redis—, y solo si ha cambiado se monta la respuesta completa. Sin ese detalle, el ETag ahorra ancho de banda y no trabajo.

Long polling: esperar en el servidor #

La variante: el servidor no responde inmediatamente. Retiene la petición hasta que haya novedades o hasta agotar un plazo, y el cliente vuelve a preguntar en cuanto recibe respuesta.

1 El cliente preguntaY el servidor no contesta
2 Ocurre algoEl servidor responde en ese instante
3 Respuesta vacía y vuelta a empezarEl plazo existe para que proxies y balanceadores no corten

Latencia casi inmediata sin conexión persistente. El precio lo paga el servidor.

En PHP con FPM, long polling es una mala idea

Cada petición retenida ocupa un proceso de FPM entero durante 25 segundos. Con pm.max_children = 50, cincuenta usuarios esperando dejan el sitio sin capacidad para nada más — incluido el resto de la web. Es un caso donde el modelo de ejecución de PHP decide la arquitectura, y la salida es SSE con un runtime asíncrono, o una pieza en otro lenguaje.

Cuánta latencia necesitas de verdad #

La pregunta que decide todo el módulo, y que casi nunca se hace antes de elegir la tecnología:

CasoLatencia aceptableBasta con
Estado de un pedido10-30 sPolling con ETag
Notificaciones de la aplicación5-10 sPolling
Progreso de una tarea larga1-2 sPolling rápido o SSE
Panel que se actualiza solo1-5 sSSE
Chat< 1 sSSE o WebSocket
Edición colaborativa, juego< 100 msWebSocket

Las cuatro primeras filas son la mayoría de las funcionalidades «en tiempo real» que se piden en una aplicación de negocio, y ninguna necesita una conexión persistente. Empezar por polling y subir de escalón cuando el número lo exija ahorra una infraestructura entera.

Cuándo aplicarlo #

Polling cuando…

  • Unos segundos de retraso no molestan a nadie
  • Son pocos clientes concurrentes por recurso
  • No quieres infraestructura nueva que operar
  • Tu stack es PHP con FPM y no quieres piezas extra

Sube de escalón cuando…

  • Necesitas por debajo del segundo de forma consistente
  • El volumen de peticiones vacías ya es un coste medible
  • Hay miles de clientes mirando lo mismo a la vez
  • La interacción es continua, no puntual

Resumen #

Lo que te llevas

  • El polling no tiene nada de elegante y funciona en todas partes, sin estado y sin nada que limpiar cuando el cliente se va.
  • Con ETag calculado sobre algo barato, una respuesta sin novedades es un 304 que ni toca la base de datos.
  • El long polling da latencia casi inmediata sin conexión persistente, y en PHP con FPM ocupa un proceso entero por cliente en espera.
  • La pregunta que decide todo es cuánta latencia necesitas de verdad, y casi nunca se hace antes de elegir tecnología.
  • La mayoría de lo que se pide «en tiempo real» en una aplicación de negocio tolera segundos, y no necesita conexión persistente.
