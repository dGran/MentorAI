Logs estructurados

Un log de texto libre es útil para leer; un log estructurado en JSON es útil para buscar, filtrar, agregar y correlacionar. La diferencia entre "grep en un fichero de 200GB" y "dame todos los errores del tenant 42 en los últimos 10 minutos" es el formato de lo que logueaste.

El primer pilar de la observabilidad son los logs, pero un log mal diseñado es ruido. Este tutorial cubre los fundamentos para que tus logs sean señal: qué nivel usar, cómo estructurarlos, qué no incluir nunca y cómo conectar eventos de una misma petición con un request id.

Niveles de severidad #

El nivel de un log indica su importancia y filtra el ruido. PSR-3 define ocho niveles, de mayor a menor severidad:

NivelCuándoAcción esperada
emergencySistema inutilizable.Despertar a todo el equipo ahora.
alertAcción inmediata requerida.Llamada de madrugada.
criticalCondición crítica. Componente fallido.Intervención urgente.
errorError de ejecución. No requiere acción inmediata.Revisar en cuanto sea posible.
warningSituación inesperada pero manejada. Algo a vigilar.Revisar en horario laboral.
noticeEvento normal pero significativo.Sin acción, solo registro.
infoInformación de operación normal.Sin acción.
debugInformación detallada para desarrollo.No en producción.

En la práctica, el error más frecuente es inflar el nivel: loguear como error algo que es un warning, o como warning algo que es info. Cuando todo es error, nada lo es — la señal se pierde en el ruido y las alertas dejan de ser útiles. Regla de oro: error solo para cosas que requieren atención de alguien; warning para cosas que no rompen pero indican un problema latente.

Debug solo en desarrollo

Los logs de debug en producción llenan disco y ralentizan la aplicación. Configura el nivel mínimo por entorno: debug en local, info o warning en producción. Monolog y la mayoría de frameworks lo soportan con un parámetro de entorno.

Texto plano vs log estructurado #

Un log de texto libre se escribe rápido pero se consulta mal:

texto plano · difícil de parsear y filtrar 
[2026-07-04 12:34:56] ERROR: Payment failed for order 8421, amount 99.90, reason: card_declined

Para filtrar todos los errores del pedido 8421 tienes que usar grep y esperar que el formato sea consistente. El log estructurado emite JSON: cada campo es clave-valor y el almacén de logs puede indexarlos e interrogarlos directamente:

json · filtrable, indexable, correlacionable 
{
  "timestamp": "2026-07-04T12:34:56Z",
  "level": "error",
  "message": "Payment failed",
  "order_id": 8421,
  "amount_cents": 9990,
  "reason": "card_declined",
  "request_id": "req-a3f9b2",
  "user_id": 1042
}

Con este formato, Loki o Elasticsearch pueden responder en segundos: "dame todos los logs donde reason=card_declined y amount_cents > 5000 en la última hora".

En PHP, Monolog con el JsonFormatter lo hace automáticamente:

php · Monolog con JsonFormatter 
<?php

use Monolog\Logger;
use Monolog\Handler\StreamHandler;
use Monolog\Formatter\JsonFormatter;

$handler = new StreamHandler('php://stdout');
$handler->setFormatter(new JsonFormatter());

$logger = new Logger('app');
$logger->pushHandler($handler);

$logger->error('Payment failed', [
    'order_id'    => $order->id(),
    'amount_cents' => $order->totalCents(),
    'reason'      => $reason,
]);

El array de contexto (segundo parámetro) es el lugar de todos los campos estructurados. El mensaje es corto y constante — algo que puedas agrupar —; los datos variables van en el contexto.

Qué loguear y qué no #

La lista de qué nunca debe aparecer en un log es corta pero crítica:

Nunca loguear esto

  • Contraseñas y tokens en ningún formato, ni hasheados.
  • Números de tarjeta completos (los últimos 4 dígitos sí son habituales).
  • PII sensible: DNI, número de seguridad social, datos de salud.
  • Secretos de configuración: API keys, credenciales de BD.
  • Payloads completos de peticiones si contienen alguno de los anteriores.

Los logs viajan por varios sistemas (stdout → agregador → almacén → dashboards) y son accesibles por varios equipos. Un secreto en un log tiene el radio de exposición de todos esos sistemas.

La regla para el resto: loguea los eventos que necesitas para depurar o auditar, con el contexto suficiente para entender el estado del sistema en ese momento. Los errores deben tener el contexto completo (qué entidad, qué operación, qué valores relevantes). Los eventos info deben ser suficientemente descriptivos pero concisos.

Qué loguearNivel
Excepción no controlada con stack traceerror / critical
Excepción de negocio esperada (pago rechazado, stock agotado)warning o info
Inicio y fin de jobs / workers de larga duracióninfo
Acciones de usuario importantes (login, compra, baja)info
Llamadas a servicios externos (con duración y código de respuesta)info / debug
Cada petición HTTP (habitualmente lo hace el framework)info

Correlación con request id #

En un sistema concurrente, los logs de distintas peticiones se entrelazan en la salida. Sin un identificador compartido, reconstruir el hilo de una petición concreta es buscar una aguja en un pajar.

El patrón es sencillo: al inicio de cada petición HTTP generas un request id (UUID o id aleatorio corto), lo añades como campo a todos los logs de esa petición y lo devuelves en la respuesta como cabecera (X-Request-Id) para que el cliente pueda reportarlo si algo falla:

php · middleware que inyecta el request id en el logger 
<?php

final class RequestIdMiddleware
{
    public function __construct(private readonly LoggerInterface $logger) {}

    public function process(Request $request, RequestHandler $handler): Response
    {
        $requestId = $request->headers->get('X-Request-Id') ?? bin2hex(random_bytes(8));

        $this->logger->pushProcessor(
            fn(array $record) => array_merge($record, ['extra' => ['request_id' => $requestId]])
        );

        $response = $handler->handle($request);
        $response->headers->set('X-Request-Id', $requestId);

        return $response;
    }
}

Con esto, todos los logs de la petición comparten el mismo request_id. Cuando alguien reporta un error, pide el valor de la cabecera X-Request-Id y búscalo en Loki o en tu almacén de logs: obtienes toda la secuencia de eventos de esa petición exacta.

PSR-3: el contrato en PHP #

PSR-3 define la interfaz Psr\Log\LoggerInterface con un método por nivel más el genérico log(). El motivo de usarla es el mismo de siempre: no acoplarte a la implementación concreta.

php · depender de la interfaz PSR-3, no de Monolog 
<?php

use Psr\Log\LoggerInterface;

final class PaymentService
{
    public function __construct(
        private readonly PaymentGateway $gateway,
        private readonly LoggerInterface $logger,
    ) {}

    public function charge(Order $order): void
    {
        try {
            $this->gateway->charge($order->totalCents(), $order->paymentMethod());
            $this->logger->info('Payment processed', ['order_id' => $order->id()]);
        } catch (CardDeclinedException $exception) {
            $this->logger->warning('Card declined', [
                'order_id' => $order->id(),
                'reason'   => $exception->reason(),
            ]);
            throw $exception;
        }
    }
}

Si mañana cambias de Monolog a otro logger, o en los tests inyectas un NullLogger o un TestLogger para verificar qué se logueó, el código de dominio no cambia. Monolog, Symfony y Laravel implementan LoggerInterface, así que en la práctica siempre tienes una implementación disponible.

Este tutorial prepara el de Loki

Cuando llegues a Loki y LogQL, los logs que aprendiste a estructurar aquí son exactamente lo que Loki indexa y LogQL consulta. El parser json de LogQL extrae los campos del JSON — order_id, level, request_id — y permite filtrar y agregar sobre ellos.

Cuándo aplicarlo #

Úsalo cuando…

  • Los logs van a Loki, Elasticsearch o cualquier sistema que filtre o agregue por campo.
  • Necesitas queries como "todos los errores del order_id 1234" o "latencia media por endpoint".
  • El equipo procesa logs con herramientas automatizadas o dashboards de Grafana.

No lo uses cuando…

  • La salida es para leer directamente en la terminal durante desarrollo: el texto plano es más legible.
  • El evento que quieres registrar es ruido que nadie consultará jamás: no loguees por defecto, loguea con criterio.

Resumen #

Lo que te llevas

  • Usa el nivel correcto: error solo para lo que requiere atención; inflar niveles destruye la señal. debug nunca en producción.
  • Log estructurado en JSON: mensaje corto y constante, datos variables en el contexto. Permite filtrar y agregar sin parsear texto.
  • Nunca en un log: contraseñas, tokens, números de tarjeta completos, PII sensible ni secretos de configuración.
  • Request id propagado como campo en todos los logs de la petición: permite reconstruir el hilo exacto de cualquier incidente con un solo filtro.
  • Depende de Psr\Log\LoggerInterface, no de Monolog. El dominio no sabe qué logger usa; en tests inyectas un NullLogger o un TestLogger.
