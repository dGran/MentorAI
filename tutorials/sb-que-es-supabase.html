Qué es Supabase: Postgres con todo lo de alrededor

Supabase se vende como «la alternativa open source a Firebase», y esa frase confunde más de lo que explica. Lo que es de verdad cabe en una línea: una base de datos Postgres completa, con todo lo que una app necesita alrededor ya montado. Entender esa línea es entender el resto del curso.

Para hacer una app con usuarios necesitas, como mínimo, una base de datos, una API que la exponga, un sistema de login, un sitio donde guardar ficheros y un servidor donde correr la lógica que no puede ir en el navegador. Montar y operar cada pieza es trabajo. Supabase te las da hechas, y lo interesante es cómo: todas giran alrededor de la misma base de datos.

La idea en una frase #

Un proyecto de Supabase es, antes que nada, una base de datos PostgreSQL entera y tuya: no una versión recortada, no una base de datos «de documentos» con otro nombre. Puedes conectarte a ella con psql, crear tablas, índices, vistas, funciones, triggers y extensiones como en cualquier Postgres. Si mañana te vas, te llevas un volcado de Postgres estándar.

Alrededor de esa base de datos, Supabase levanta una serie de servicios que leen y escriben en ella:

ServicioQué te daCómo se apoya en Postgres
Data APIUna API REST generada sola a partir de tus tablasTraduce cada petición HTTP a una consulta SQL
AuthRegistro, login, OAuth, enlaces mágicos, MFALos usuarios viven en la tabla auth.users
StorageSubida y descarga de ficheros, con permisosLos metadatos de cada fichero son filas de storage.objects
RealtimeAvisos en vivo de cambios, mensajes y presenciaEscucha los cambios de la base de datos
Edge FunctionsCódigo TypeScript en el servidorSe conecta a la base de datos como un cliente más
Cron y QueuesTareas programadas y colas de trabajoSon extensiones que corren dentro de Postgres
VectorBúsqueda semántica para IALa extensión pgvector en tu misma base de datos

Y por encima de todo, Studio: el panel web desde el que ves tus tablas, escribes SQL, gestionas usuarios y ficheros y lees los logs.

La comparación con Firebase, bien hecha

Firebase es una base de datos de documentos propietaria: modelas los datos como colecciones de documentos y las reglas de seguridad son un lenguaje propio de Google. Supabase es SQL relacional (con joins, transacciones y restricciones) y open source: cada pieza se puede instalar en tu propio servidor. Se parecen en lo que te ahorran, no en cómo lo hacen.

Las piezas por dentro #

Cuando tu app hace una petición, no habla directamente con Postgres. Pasa por una pasarela de API que comprueba la clave del proyecto y reparte cada petición al servicio que le toca según la ruta de la URL:

1 Tu appnavegador, móvil o servidor, con la librería supabase-js o HTTP a pelo
2 Pasarela de APIcomprueba la clave y enruta por prefijo de URL
3 ServicioPostgREST, Auth, Storage, Realtime o Edge Functions
4 Postgrestus tablas, más los esquemas auth, storage, realtime, cron…

Todas las rutas acaban en la misma base de datos. Por eso un usuario creado por Auth se puede usar en una consulta de la Data API, y un fichero de Storage, en una política de seguridad.

Cada servicio es un proyecto open source con nombre propio, y conviene reconocerlos porque aparecen en los mensajes de error y en la documentación:

  • PostgREST es el servidor que genera la Data API. Lee el esquema de tu base de datos y expone cada tabla y vista como un recurso REST.
  • Auth (antes llamado GoTrue) emite los tokens de sesión de tus usuarios: JWT firmados que luego entienden todos los demás servicios.
  • Storage guarda el contenido de los ficheros en un almacenamiento de objetos compatible con S3 y sus metadatos en Postgres.
  • Realtime es un servidor en Elixir que mantiene las conexiones WebSocket abiertas y reparte mensajes.
  • Edge Functions corren sobre un runtime basado en Deno, desplegado cerca de tus usuarios.
  • Supavisor es el pooler de conexiones: reparte un número limitado de conexiones reales a Postgres entre muchos clientes.

La idea que lo explica todo: la base de datos manda #

En una app clásica, el navegador nunca habla con la base de datos: habla con tu backend, y tu backend decide qué puede ver cada usuario antes de consultar. Supabase le da la vuelta. El navegador consulta (casi) directamente las tablas a través de la Data API, sin código tuyo en medio.

Backend clásico

  • El navegador llama a tu API (/api/pedidos)
  • Tu código comprueba quién es el usuario
  • Tu código hace WHERE user_id = ? antes de consultar
  • La base de datos confía en tu backend

Supabase

  • El navegador consulta la tabla pedidos vía Data API
  • El token del usuario viaja en la petición
  • Postgres aplica una política que filtra las filas de ese usuario
  • La seguridad vive dentro de la base de datos

Ese cambio es la clave de todo el curso. Si el navegador puede pedir cualquier tabla, la única barrera real es la base de datos, y la herramienta de Postgres para eso es la Row Level Security (RLS): reglas por tabla que deciden qué filas puede leer o modificar cada usuario. Sin RLS, una tabla expuesta es una tabla pública. Tiene su propia lección, RLS a fondo, y es la más importante del curso.

La consecuencia que más brechas ha causado

Crear una tabla sin activar RLS y publicar la app es dejar la tabla abierta a cualquiera que abra las herramientas de desarrollo del navegador y copie la clave pública. Supabase avisa en el panel, pero el aviso no bloquea nada. Hay que entender el modelo, no confiar en el aviso.

La misma idea se repite en todas las piezas: los permisos de los ficheros son políticas sobre storage.objects, los de los canales en tiempo real son políticas sobre realtime.messages y las tareas programadas son filas de cron.job. Aprendes un modelo y te sirve para todo.

Lo que Supabase no es #

Saber qué no hace evita meses de dar vueltas:

  • No aloja tu web. Supabase es el backend. Las páginas de tu app (React, Next.js, Vue, HTML estático…) se publican en otro sitio: Vercel, Netlify, Cloudflare Pages o GitHub Pages. La lección Una app completa monta las dos mitades juntas.
  • No elimina el backend: lo cambia de sitio. La lógica de negocio sigue existiendo. Parte va en SQL (políticas, funciones, triggers), parte en Edge Functions y parte, si la tienes, en tu propio servidor. Decidir qué va dónde es buena parte del oficio.
  • No es una base de datos NoSQL. Si te pide el cuerpo guardar documentos JSON, Postgres tiene jsonb (lo cuenta JSONB en Postgres), pero el modelo de base es relacional.
  • No es solo para JavaScript. Hay librerías oficiales para JavaScript, Flutter, Swift, Kotlin, Python y C#, y como todo es HTTP o Postgres, cualquier lenguaje puede hablar con él. Desde PHP, por ejemplo, puedes llamar a la Data API con un cliente HTTP o conectarte directamente a Postgres con PDO.
  • No es una caja negra. Al ser Postgres, todo lo que sabes de SQL, índices y transacciones sigue valiendo, y todo lo que hagas mal también: una consulta sin índice es igual de lenta aquí.

El modelo de uso: plataforma, local y autoalojado #

Supabase se usa de tres formas, y el código de tu app es el mismo en las tres:

FormaQué esPara qué
Plataforma (supabase.com)Supabase te lo opera: backups, actualizaciones, escaladoLo habitual en producción
Local (CLI + Docker)Todo el stack en tu máquina con un comandoDesarrollar y probar sin tocar producción
AutoalojadoTú despliegas los contenedores en tu infraestructuraRequisitos de soberanía de datos o coste a gran escala

La plataforma tiene un plan gratuito generoso para aprender (dos proyectos activos, 500 MB de base de datos, 50.000 usuarios activos al mes), con una pega que conviene saber desde el principio: un proyecto gratuito sin actividad durante una semana se pausa, y hay que reactivarlo desde el panel. Los planes de pago empiezan en 25 dólares al mes por organización.

Dato que caduca

Precios, cuotas y límites del plan gratuito cambian con el tiempo. Las cifras de este curso son de finales de 2026; la fuente de verdad es la página de precios de Supabase.

Cuándo aplicarlo #

Supabase encaja cuando…

  • Quieres una app con usuarios funcionando en días, no semanas
  • Tus datos son relacionales y te sientes cómodo con SQL
  • Un equipo pequeño no quiere operar base de datos, auth y ficheros por separado
  • Necesitas tiempo real, ficheros o búsqueda vectorial sin montar más infraestructura
  • Te importa poder irte: es Postgres estándar y todo es open source

Piénsalo dos veces si…

  • Ya tienes un backend maduro con su base de datos y su login: añadir Supabase duplica piezas
  • Tu lógica de negocio es compleja y vive mejor en un dominio rico en tu lenguaje que en SQL
  • Nadie del equipo quiere aprender RLS: es obligatorio, no opcional
  • Necesitas control total de la versión de Postgres, extensiones exóticas o del hardware

Resumen #

Lo que te llevas

  • Supabase es una base de datos Postgres completa con servicios alrededor: Data API, Auth, Storage, Realtime, Edge Functions, Cron, Queues y Vector.
  • Todas las piezas leen y escriben en la misma base de datos: los usuarios, los ficheros y las tareas programadas son filas de tablas.
  • El cliente consulta las tablas casi directamente, así que la seguridad vive en Postgres: RLS no es opcional.
  • Supabase no aloja tu frontend ni elimina la lógica de negocio: la reparte entre SQL, Edge Functions y, si lo tienes, tu servidor.
  • Se usa como plataforma gestionada, en local con la CLI o autoalojado, con el mismo código de app.
