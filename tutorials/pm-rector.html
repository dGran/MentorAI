Rector: migrar de versión sin hacerlo a mano

Tienes cien mil líneas escritas para PHP 7.4 y producción ya corre 8.4. Hacer la migración a mano son semanas de cambios mecánicos que nadie quiere revisar. Rector los hace en minutos y te entrega un diff que sí se puede revisar.

Las lecciones anteriores enseñan qué escribir en PHP moderno. Esta trata de cómo llevar ahí el código que ya existe.

El problema de migrar a mano #

Subir de versión de PHP casi nunca exige pensar. Exige repetir. Convertir propiedades en promoción de constructor, cambiar strpos(...) === 0 por str_starts_with, pasar switch a match, marcar como readonly lo que nunca se reasigna. Cada cambio es trivial; el problema es que hay miles.

Hecho a mano, ese trabajo es lento, así que se aplaza; es irregular, porque cada persona moderniza a su manera; y es difícil de revisar, porque un PR de 4.000 líneas tocadas a mano obliga a leerlas todas. Necesitas una herramienta que aplique la misma transformación siempre igual y te enseñe el resultado antes de escribirlo.

Qué es Rector: cambios sobre el AST #

Rector es una herramienta de refactorización automática. No busca y reemplaza texto: parsea cada fichero a un árbol de sintaxis (AST) con nikic/php-parser, le pasa una lista de reglas que modifican nodos concretos y vuelve a imprimir solo lo que cambió. Para decidir si una regla aplica usa la información de tipos de PHPStan, que es dependencia suya, así que distingue un $invoice->send() de un $mailer->send().

1 Código fuenteLos ficheros de withPaths
2 AST con tiposPHPStan resuelve qué es cada variable
3 AST modificadoCada regla toca solo los nodos que entiende
4 Diff o fichero escritoSegún uses --dry-run o no

Rector trabaja sobre estructura y tipos, no sobre texto.

Rector

  • Entiende que un switch con return en cada caso equivale a un match
  • Renombra un método en la declaración y en cada llamada de esa clase
  • Si una regla no está segura, no toca el nodo

Buscar y reemplazar

  • No sabe dónde acaba una expresión ni qué tipo tiene
  • Renombra también el método homónimo de otra clase
  • Falla en silencio con saltos de línea o comentarios

rector.php con la configuración fluida #

Se instala como dependencia de desarrollo (composer require --dev rector/rector, y el porqué de require-dev está en Composer a fondo). Rector 2 se configura con un constructor fluido, RectorConfig::configure(), que devuelve el fichero entero en una expresión:

php · rector.php 
<?php

declare(strict_types=1);

use Rector\Config\RectorConfig;

return RectorConfig::configure()
    ->withPaths([
        __DIR__ . '/src',
        __DIR__ . '/tests',
    ])
    ->withSkip([
        __DIR__ . '/src/Legacy',
    ])
    ->withPhpSets(php81: true)
    ->withComposerBased(phpunit: true, symfony: true)
    ->withPreparedSets(deadCode: true, typeDeclarations: true);
MétodoPara qué sirve
withPathsQué directorios procesa. Nada fuera de ellos se toca.
withSkipRutas o reglas que se excluyen, también una regla solo en una ruta.
withPhpSetsModernización hasta una versión de PHP.
withComposerBasedReglas de frameworks según la versión instalada en vendor/.
withPreparedSetsSets de calidad que no dependen de versión: código muerto, tipos, early return…
withRules / withConfiguredRuleReglas sueltas, sin configurar o con parámetros.

Sets de PHP y de frameworks #

Un set es una lista de reglas con un objetivo común. withPhpSets(php81: true) aplica todas las reglas de modernización hasta PHP 8.1, no solo las de 8.1: es acumulativo. Por eso solo admite una versión y solo se puede llamar una vez; si pasas dos, Rector se niega a arrancar. Sin argumentos, withPhpSets() toma la versión de require.php en tu composer.json, lo que lo mantiene alineado con lo que el proyecto declara soportar.

Para frameworks, withComposerBased lee la versión instalada de PHPUnit, Symfony, Doctrine o Twig y aplica solo las reglas que le corresponden: al subir Symfony, la siguiente pasada trae las reglas de la nueva. Laravel no viene incluido: tiene su propio paquete de reglas, mantenido por la comunidad.

Rector corre en PHP 7.4

El paquete admite PHP 7.4, así que lo instalas en el proyecto antiguo sin subir antes el intérprete: primero migras el código y después la versión de producción.

--dry-run: el diff antes que el cambio #

La primera ejecución siempre lleva --dry-run: Rector imprime el diff de cada fichero y las reglas que lo produjeron, sin escribir nada. Léelo como el PR de un compañero.

bash · ver el cambio sin aplicarlo 
vendor/bin/rector process --dry-run
vendor/bin/rector process

Con withPhpSets(php80: true), esta clase escrita para PHP 7.4:

php · src/Invoice.php (antes) 
<?php

declare(strict_types=1);

namespace App;

final class Invoice
{
    private string $number;
    private int $totalInCents;
    private ?Customer $customer;

    public function __construct(string $number, int $totalInCents, ?Customer $customer)
    {
        $this->number = $number;
        $this->totalInCents = $totalInCents;
        $this->customer = $customer;
    }

    public function customerName(): ?string
    {
        return $this->customer !== null ? $this->customer->name() : null;
    }

    public function statusLabel(string $status): string
    {
        switch ($status) {
            case 'paid':
                return 'Pagada';
            case 'pending':
                return 'Pendiente';
            default:
                return 'Desconocido';
        }
    }

    public function isProforma(): bool
    {
        return strpos($this->number, 'PRO-') === 0;
    }
}

queda así, con cuatro reglas aplicadas que el informe nombra una a una:

php · src/Invoice.php (después) 
<?php

declare(strict_types=1);

namespace App;

final class Invoice
{
    public function __construct(private string $number, private int $totalInCents, private ?Customer $customer)
    {
    }

    public function customerName(): ?string
    {
        return $this->customer?->name();
    }

    public function statusLabel(string $status): string
    {
        return match ($status) {
            'paid' => 'Pagada',
            'pending' => 'Pendiente',
            default => 'Desconocido',
        };
    }

    public function isProforma(): bool
    {
        return str_starts_with($this->number, 'PRO-');
    }
}

No añadió readonly, que es PHP 8.1: el set marca el techo. Si lo subes a php81, la siguiente pasada añade readonly a las propiedades promocionadas; con php82, convierte la clase en final readonly class.

Un set cada vez, con red #

La tentación es poner php84: true y lanzar: un diff de miles de líneas que mezcla seis versiones de cambios y que nadie revisa en serio. Si algo se rompe, no sabes qué regla fue. Lo que funciona es subir una versión cada vez, con los tests y PHPStan como red:

1 Sube un escalónphp80, luego php81, luego php82…
2 --dry-run y lee el diffSi una regla no te convence, withSkip
3 Aplica y pasa la redPHPUnit y PHPStan en verde
4 Un commit por escalónSolo cambios de Rector, sin mezclar

Cada escalón es un commit revisable y revertible por separado.

Rector produce código válido, pero no prueba que el comportamiento sea el mismo: lo que se decide en tiempo de ejecución, como la reflexión o un método invocado por su nombre desde configuración, le queda fuera de la vista. Los tests cazan el cambio de comportamiento; PHPStan caza el tipo que dejó de cuadrar. Un commit por escalón te permite revertir solo el que falló.

Los sets de calidad, también por niveles

withDeadCodeLevel, withTypeCoverageLevel y withCodeQualityLevel reciben un número y activan las reglas de ese set de la más segura a la más invasiva. Empieza en 0 y súbelo de uno en uno, igual que harías con los niveles de PHPStan.

Primero Rector, después PHP-CS-Fixer #

Rector imprime el código que cambia, pero no conoce tus reglas de estilo. En el ejemplo dejó el constructor con el cuerpo vacío en dos líneas; con @PER-CS, PHP-CS-Fixer lo reescribe como {}. Por eso el orden es fijo: Rector cambia la estructura y el fixer normaliza la forma. Al revés, el commit sale con un estilo que tu CI rechaza.

bash · un escalón completo 
vendor/bin/rector process
vendor/bin/php-cs-fixer fix
vendor/bin/phpstan analyse
vendor/bin/phpunit
git commit -am "refactor: apply Rector PHP 8.1 set"

¿Una regla propia? #

Antes de escribir una regla, mira si existe una configurable. Renombrar un método, una clase o una función en todo el proyecto ya está resuelto:

php · rector.php (regla configurable) 
<?php

declare(strict_types=1);

use Rector\Config\RectorConfig;
use Rector\Renaming\Rector\MethodCall\RenameMethodRector;
use Rector\Renaming\ValueObject\MethodCallRename;

return RectorConfig::configure()
    ->withPaths([__DIR__ . '/src'])
    ->withConfiguredRule(RenameMethodRector::class, [
        new MethodCallRename('App\Mailer', 'sendMail', 'send'),
    ]);

Una regla propia compensa cuando el cambio necesita lógica que ninguna regla configurable expresa y aparece en muchos sitios: por ejemplo, pasar Money::fromFloat(4.95) a Money::fromCents(495), que exige calcular el nuevo argumento. Es una clase que extiende AbstractRector, declara qué nodos le interesan y devuelve el nodo cambiado o null si no aplica:

php · utils/Rector/MoneyFromFloatToCentsRector.php 
<?php

declare(strict_types=1);

namespace Utils\Rector;

use PhpParser\Node;
use PhpParser\Node\Identifier;
use PhpParser\Node\Expr\StaticCall;
use PhpParser\Node\Scalar\Float_;
use PhpParser\Node\Scalar\Int_;
use Rector\Rector\AbstractRector;
use Symplify\RuleDocGenerator\ValueObject\RuleDefinition;

final class MoneyFromFloatToCentsRector extends AbstractRector
{
    private const int CENTS_PER_UNIT = 100;

    public function getRuleDefinition(): RuleDefinition
    {
        return new RuleDefinition('Money::fromFloat(12.5) pasa a Money::fromCents(1250)', []);
    }

    public function getNodeTypes(): array
    {
        return [StaticCall::class];
    }

    public function refactor(Node $node): ?Node
    {
        if (! $this->isName($node->class, 'App\Money') || ! $this->isName($node->name, 'fromFloat')) {
            return null;
        }

        $amount = $node->getArgs()[0]->value ?? null;

        if (! $amount instanceof Float_) {
            return null;
        }

        $node->name = new Identifier('fromCents');
        $node->args[0]->value = new Int_((int) round($amount->value * self::CENTS_PER_UNIT));

        return $node;
    }
}

Se registra con withRules([MoneyFromFloatToCentsRector::class]) y el namespace Utils\ en el autoload-dev. La llamada con una variable, Money::fromFloat($amount), se queda como está: la regla solo toca lo que puede transformar con certeza.

Para diez ficheros no compensa: el IDE lo hace antes de que termines de probar la regla. Y si lo que buscas es prohibir un patrón en el futuro, eso es trabajo de PHPStan, que avisa sin reescribir.

Errores típicos #

Lo que convierte una migración en un incendio

  • Todos los sets a la vez. Un único diff imposible de revisar y de bisecar.
  • Aplicar sin red. Sin tests, nada garantiza que el comportamiento siga igual. El primer paso es cubrir lo crítico.
  • Mezclar cambios a mano con los de Rector. El revisor ya no puede fiarse del diff mecánico.
  • El fixer antes que Rector. El código que Rector reimprime queda con su formato, no con el tuyo.
  • Sacar Rector de CI al terminar. El siguiente PR vuelve a escribir strpos(...) === 0 y la migración se deshace poco a poco.

Cómo comprobarlo #

Terminada la migración, en CI rector process --dry-run termina con un código de salida distinto de cero si queda algún cambio pendiente, igual que php-cs-fixer check. Añádelo al paso de análisis estático que ya describe CI para un proyecto PHP y nadie podrá reintroducir lo que ya migraste.

bash · en CI y para depurar una regla 
vendor/bin/rector process --dry-run --no-progress-bar
vendor/bin/rector process --dry-run --only="Rector\Php80\Rector\Switch_\ChangeSwitchToMatchRector"

La opción --only ejecuta una única regla del set; sirve para aislar cuál produce un cambio sospechoso antes de excluirla con withSkip.

Cuándo aplicarlo #

Rector cuando…

  • Subes de versión de PHP, PHPUnit o Symfony
  • Una deprecación o un cambio de API interna afecta a cientos de llamadas
  • Quieres que el código nuevo no vuelva a la sintaxis vieja
  • Tienes tests y PHPStan que hagan de red

No lo necesitas cuando…

  • El cambio toca un puñado de ficheros
  • Es un cambio de diseño: repartir responsabilidades o extraer clases
  • El proyecto no tiene ni un test que proteja el comportamiento

La alternativa sencilla

Para renombrar algo en pocos ficheros, el refactor del IDE basta y no añade una dependencia. Si lo que quieres es detectar el patrón viejo sin reescribirlo, PHPStan avisa y deja la decisión a quien escribe el código.

Resumen #

Lo que te llevas

  • Rector reescribe código sobre el AST y con los tipos de PHPStan, no con buscar y reemplazar.
  • withPhpSets es acumulativo y marca un techo: todas las reglas hasta esa versión, y sin argumentos lee composer.json.
  • --dry-run primero; un escalón de versión por commit, con PHPUnit y PHPStan en verde entre medias.
  • Rector cambia la estructura y PHP-CS-Fixer la forma, en ese orden.
  • Regla propia solo si el cambio necesita lógica y se repite mucho; antes busca una configurable.
  • Tras migrar, --dry-run en CI impide que vuelva el código viejo.
