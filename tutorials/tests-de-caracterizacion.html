Tests de caracterización para tocar código sin tests

Para cambiar código sin tests necesitas tests, y para ponerle tests necesitas cambiarlo. Los tests de caracterización rompen el círculo: fijan lo que el código hace hoy, sea correcto o no, y te dan la red para refactorizar antes de tocar la regla.

Te piden cambiar una regla en una clase de 300 líneas que nadie ha probado nunca. No sabes qué hace exactamente, solo que lleva años en producción y que alguien depende de ella. Antes de arreglar nada, necesitas saber qué hace hoy y enterarte si dejas de hacerlo.

Cambiar código sin red #

En code smells y refactoring viste la regla: no se refactoriza sin tests. El código heredado la pone a prueba, porque casi nunca los tiene y casi nunca se deja probar: crea su propia conexión a la base de datos, lee la fecha del sistema y escribe con echo en vez de devolver un valor.

Michael Feathers lo resumió en Working Effectively with Legacy Code: código heredado es código sin tests. Y añadió el dilema que lo bloquea todo: para cambiarlo con seguridad necesitas tests, y para ponerle tests necesitas cambiarlo. La salida es hacer el mínimo cambio mecánico que permita probarlo y, a partir de ahí, avanzar siempre con red. Antes de tocar nada, aterriza en el código heredado.

php · src/ShippingQuote.php (heredado) 
<?php

declare(strict_types=1);

namespace Demo\Legacy;

class ShippingQuote
{
    public function printQuote(int $orderId): void
    {
        $lines = Database::connection()
            ->query("SELECT weight, country FROM order_lines WHERE order_id = {$orderId}")
            ->fetchAll();
        $total = 0;

        foreach ($lines as $line) {
            if ($line['country'] == 'ES') {
                $total += $line['weight'] * 1.2;
            } elseif ($line['country'] == 'PT') {
                $total += $line['weight'] * 1.5 + 3;
            } else {
                $total += 25;
            }
        }

        if ((int) date('N') >= 6) {
            $total = $total * 1.1;
        }

        echo "Pedido {$orderId}\n";
        echo 'Envío: ' . round($total, 2) . " EUR\n";
    }
}

Esta clase calcula el coste de envío de un pedido. Para ejecutarla en un test hace falta una base de datos con datos concretos, y el resultado cambia según el día de la semana. Ni siquiera sabes si 'es' en minúsculas llega alguna vez desde la base de datos ni qué pasa entonces.

Fijar lo que hace, no lo que debería #

Un test de caracterización describe el comportamiento real del código, no el deseado. No partes de una especificación: ejecutas el código con una entrada, miras qué sale y escribes una aserción que fija exactamente eso. Si sale algo raro, también lo fijas.

Test de caracterización

  • La fuente de verdad es el código que hay en producción
  • Un resultado raro se fija y se anota, no se corrige
  • Detecta cualquier cambio, deseado o no
  • Es provisional: dura lo que dura el refactor

Test de comportamiento

  • La fuente de verdad es la regla de negocio
  • Un resultado raro es un fallo que hay que arreglar
  • Solo se rompe si cambia lo que la regla exige
  • Se queda mientras exista la regla

¿Por qué fijar un posible bug? Porque no sabes si lo es. Puede que un cliente ya cuente con esa tarifa plana, o que un informe dependa de ese redondeo. Tu tarea ahora es no cambiar nada sin enterarte; decidir qué es correcto llega después, como un cambio aparte y consciente.

Puntos de corte para aislar dependencias #

Feathers llama seam (punto de corte) a un sitio donde puedes cambiar lo que hace el código sin editarlo en ese punto. El tipo más útil en PHP heredado es el seam de objeto, que se abre con subclass and override method: sacas cada dependencia rebelde a un método protected y, en el test, una subclase lo sobrescribe.

Extraer esos dos métodos es el único cambio que haces sin red, así que tiene que ser mecánico: el refactor «extraer método» del IDE, sin tocar una sola condición.

php · los dos seams extraídos en ShippingQuote 
    protected function linesOf(int $orderId): array
    {
        return Database::connection()
            ->query("SELECT weight, country FROM order_lines WHERE order_id = {$orderId}")
            ->fetchAll();
    }

    protected function isWeekend(): bool
    {
        return (int) date('N') >= 6;
    }
}
php · el doble: una clase anónima que sobrescribe los seams 
private function quoteWith(array $lines, bool $isWeekend): ShippingQuote
{
    $quote = new class extends ShippingQuote {
        public array $fakeLines = [];
        public bool $isFakeWeekend = false;

        protected function linesOf(int $orderId): array
        {
            return $this->fakeLines;
        }

        protected function isWeekend(): bool
        {
            return $this->isFakeWeekend;
        }
    };
    $quote->fakeLines = $lines;
    $quote->isFakeWeekend = $isWeekend;

    return $quote;
}

Fíjate en que la clase anónima no declara constructor y recibe los datos por propiedades. Si declarase uno propio sin llamar al padre, el día que el refactor añada un constructor a ShippingQuote los tests se romperían por la herramienta, no por el comportamiento. Es la técnica manual que generalizan los dobles de test.

Capturar la salida con PHPUnit #

Como el código escribe con echo, la aserción va contra la salida. PHPUnit trae expectOutputString(), que captura todo lo que se imprime durante el test y lo compara al terminar. Para un caso suelto es lo más directo.

php · tests/ShippingQuoteCharacterizationTest.php 
public function test_un_pedido_espanol_entre_semana(): void
{
    $quote = $this->quoteWith([['weight' => 10, 'country' => 'ES']], isWeekend: false);

    $this->expectOutputString("Pedido 7\nEnvío: 12 EUR\n");

    $quote->printQuote(7);
}

public function test_el_pais_en_minusculas_cobra_tarifa_plana(): void
{
    $quote = $this->quoteWith([['weight' => 10, 'country' => 'es']], isWeekend: false);

    $this->expectOutputString("Pedido 7\nEnvío: 25 EUR\n");

    $quote->printQuote(7);
}

El segundo test es el importante: el nombre dice lo que pasa, no lo que debería pasar. Un pedido a 'es' paga 25 € de tarifa plana en vez de 12 €, y queda escrito. El método para dar con esos valores es dejar la aserción vacía o con un valor absurdo, ejecutar y copiar lo que PHPUnit dice que salió.

Snapshots: muchas entradas de golpe #

Escribir a mano un test por combinación no escala. El snapshot testing (o approval testing) automatiza el paso de copiar lo que salió: la primera ejecución guarda la salida en un fichero y las siguientes la comparan. En PHP la librería de referencia es spatie/phpunit-snapshot-assertions, que en su versión 5.4 funciona con PHPUnit 9.6 a 13. También existe ApprovalTests.php, pero en Packagist no tiene versiones publicadas, solo la rama de desarrollo.

php · un snapshot con todas las combinaciones 
public function test_combinaciones_de_pais_peso_y_dia(): void
{
    $report = '';

    foreach (['ES', 'PT', 'FR', 'es', ''] as $country) {
        foreach ([0, 1, 2.5, 10] as $weight) {
            foreach ([false, true] as $isWeekend) {
                $quote = $this->quoteWith([['weight' => $weight, 'country' => $country]], $isWeekend);
                ob_start();
                $quote->printQuote(1);
                $report .= sprintf("%-2s %4s %-5s → %s", $country, $weight, $isWeekend ? 'finde' : 'lab', ob_get_clean());
            }
        }
    }

    $this->assertMatchesTextSnapshot($report);
}

Cinco países, cuatro pesos y dos tipos de día dan 40 casos en un solo fichero de texto bajo tests/__snapshots__/. Ese fichero se sube al repositorio: es la red. Un extracto de lo que se guardó:

texto · extracto del snapshot 
es    1 lab   → Pedido 1
Envío: 25 EUR
es    1 finde → Pedido 1
Envío: 27.5 EUR
PT  2.5 finde → Pedido 1
Envío: 7.43 EUR
bash · ciclo de vida del snapshot 
composer require --dev spatie/phpunit-snapshot-assertions

vendor/bin/phpunit
vendor/bin/phpunit --display-incomplete

vendor/bin/update-snapshots tests/ShippingQuoteCharacterizationTest.php

CREATE_SNAPSHOTS=false vendor/bin/phpunit

La primera ejecución marca el test como incompleto («Snapshot created for…») en vez de pasarlo. update-snapshots reescribe los ficheros cuando el cambio es deseado, y CREATE_SNAPSHOTS=false hace que en CI un snapshot que falta sea un fallo, no un fichero nuevo que nadie revisa.

Caracterizar, refactorizar, cambiar #

1 CaracterizarSeams mínimos y tests que fijan lo que sale hoy
2 RefactorizarPasos pequeños; los tests no se tocan
3 CambiarTest de comportamiento nuevo y caracterización sustituida

Cada paso en un commit propio: si algo se pone rojo, sabes cuál fue.

Con la red puesta, el refactor saca el cálculo a una clase pura, sin base de datos ni reloj. Los tres tests de caracterización siguen en verde sin tocar una línea: es la prueba de que el comportamiento no se movió.

php · src/ShippingCost.php (después) 
<?php

declare(strict_types=1);

namespace Demo\Legacy;

final class ShippingCost
{
    private const float SPAIN_RATE_PER_KILO = 1.2;
    private const float PORTUGAL_RATE_PER_KILO = 1.5;
    private const float PORTUGAL_FIXED_FEE = 3;
    private const float FLAT_RATE = 25;
    private const float WEEKEND_SURCHARGE = 1.1;

    public function forLines(array $lines, bool $isWeekend): float
    {
        $total = array_sum(array_map($this->forLine(...), $lines));

        return $isWeekend ? $total * self::WEEKEND_SURCHARGE : $total;
    }

    private function forLine(array $line): float
    {
        return match ($line['country']) {
            'ES' => $line['weight'] * self::SPAIN_RATE_PER_KILO,
            'PT' => $line['weight'] * self::PORTUGAL_RATE_PER_KILO + self::PORTUGAL_FIXED_FEE,
            default => self::FLAT_RATE,
        };
    }
}
php · ShippingQuote delega el cálculo 
public function __construct(private ShippingCost $cost = new ShippingCost())
{
}

public function printQuote(int $orderId): void
{
    $total = $this->cost->forLines($this->linesOf($orderId), $this->isWeekend());

    echo "Pedido {$orderId}\n";
    echo 'Envío: ' . round($total, 2) . " EUR\n";
}

Ahora sí toca el cambio: aceptar el país en minúsculas. Lo haces en ShippingCost con un test de comportamiento normal, que no necesita salida ni subclases. Al cambiarlo, el test de las minúsculas y el snapshot se ponen rojos, y es justo lo que esperabas: el diff muestra qué casos cambiaron y confirmas que son solo esos.

Ese es el momento de borrar la caracterización. Ya no fija un comportamiento dudoso: fija detalles, como el formato del echo, que la lógica ya no necesita. Cuando los tests de ShippingCost cubren cada regla, el snapshot solo estorba, como explica tests que no estorban. Si el formato de salida es un contrato que alguien consume, se queda un test que lo fije, no los 40 casos.

Errores típicos #

Lo que convierte la red en una trampa

  • Corregir mientras caracterizas. Ves el bug de las minúsculas y lo arreglas «ya que estás». Has mezclado dos cambios y el test ya no describe producción.
  • Aceptar el snapshot sin leerlo. update-snapshots en verde no significa correcto: significa que el fichero dice lo mismo que el código.
  • Entradas que no cubren las ramas. Cuarenta casos de España no prueban Portugal. Elige valores que pasen por cada if y por los bordes, como el peso cero.
  • Dejar dentro lo no determinista. Si el reloj o un aleatorio llegan a la salida, el snapshot falla a ratos. Sácalos a un seam antes de capturar.
  • Convertir la red en permanente. Un snapshot de 40 casos que nadie borra se rompe con cada cambio legítimo de formato.

Cómo comprobarlo #

Que los tests pasen no prueba que vigilen algo. Comprueba que la red detecta: estropea a propósito una rama (cambia el 1.5 de Portugal por 1.6) y ejecuta. Si nada se pone rojo, a tus entradas les falta un caso. La versión automática de este truco es el mutation testing, que hace lo mismo con cientos de cambios.

La cobertura como mapa

Antes de refactorizar, mira la cobertura de la clase (necesita pcov o Xdebug) con los tests de caracterización. Una rama sin ejecutar es una rama que podrías romper sin enterarte: añade una entrada que pase por ella.

Cuándo aplicarlo #

Caracteriza cuando…

  • Vas a tocar código sin tests que está en producción y no tienes especificación fiable
  • La salida es compleja (un informe, un HTML, un CSV) y escribir cada aserción a mano no compensa
  • Vas a migrar una pieza (de versión de PHP, de framework) y quieres saber si algo cambió de rebote

No hace falta cuando…

  • El código ya tiene tests de comportamiento que cubren lo que vas a tocar
  • Escribes código nuevo: ahí el test sale de la regla, con el ciclo de TDD
  • Vas a reescribir la pieza entera con otra interfaz y nadie consume su salida actual

Si la pieza es tan grande que no admite seams baratos, la alternativa es caracterizar más arriba: un test de integración o end-to-end que fije la respuesta de toda la página (los niveles los viste en la pirámide de tests). Es más lento, pero da la misma red mientras partes la pieza.

Resumen #

Lo que te llevas

  • Un test de caracterización fija lo que el código hace hoy, incluso lo raro; decidir qué es correcto es un cambio aparte.
  • Los seams (métodos protected sobrescritos en una subclase) aíslan base de datos y reloj con el mínimo cambio mecánico.
  • expectOutputString() para casos sueltos; spatie/phpunit-snapshot-assertions para muchas combinaciones, con CREATE_SNAPSHOTS=false en CI.
  • El orden es caracterizar, refactorizar y cambiar, cada paso en su commit; al final, los tests de comportamiento sustituyen a la caracterización.
