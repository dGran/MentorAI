Anatomía de un pipeline

Todos los pipelines del mundo, sea cual sea la herramienta, se componen de las mismas cuatro piezas: algo que lo dispara, máquinas que lo ejecutan, trabajos que se reparten y pasos que se encadenan. Aprende la anatomía una vez y leerás cualquier YAML de CI.

En la lección anterior vimos el pipeline como idea; ahora lo abrimos por dentro. Usaremos la terminología de GitHub Actions porque es la que verás en la mayoría de repos, pero la estructura es idéntica en GitLab CI, Jenkins o Bitbucket: cambian los nombres, no las piezas.

Las cuatro piezas #

Un pipeline se describe en un fichero YAML versionado junto al código (en GitHub Actions, dentro de .github/workflows/). Ese fichero declara una jerarquía de cuatro niveles:

PiezaQué esEjemplo
WorkflowEl pipeline completo: un fichero YAML con nombre, disparadores y trabajos.ci.yml: "validar cada push"
TriggerEl evento que lo pone en marcha.Un push, una pull request, un horario
JobUn trabajo que corre en una máquina limpia. Los jobs de un workflow corren en paralelo salvo que declares dependencias.tests, estilo, build
StepCada paso de un job, en orden: un comando o una acción reutilizable. Si un step falla, el job falla.composer install, vendor/bin/phpunit

Falta un actor: el runner, la máquina que ejecuta cada job. GitHub te presta una máquina virtual limpia por job (runs-on: ubuntu-latest) que nace, ejecuta los steps y muere. Esa esterilidad es una virtud enorme: el pipeline instala todo desde cero cada vez, así que si pasa en CI, no depende de nada mágico que solo exista en tu portátil. Es el antídoto oficial contra el "en mi máquina funciona" — el mismo problema que los contenedores atacan por otro flanco en Docker.

Cuándo se dispara #

El bloque on: declara qué eventos arrancan el workflow. Los cuatro que cubren casi todos los casos:

TriggerCuándo correPara qué se usa
pushAl subir commits a una rama.Validar la rama principal tras cada merge.
pull_requestAl abrir o actualizar una PR.Validar el cambio antes de mezclarlo. El más importante.
scheduleCon un cron, sin cambio de código.Detectar deriva: dependencias que caducan, tests que se pudren.
workflow_dispatchA mano, con un botón.El deploy de la entrega continua: verde + decisión humana.

Lo habitual es afinar el trigger con filtros: validar las pull requests contra main, y el push solo en main (las ramas ya se validan vía PR). Así no pagas dos ejecuciones por el mismo cambio.

Un workflow línea a línea #

Con las piezas nombradas, un workflow real se lee solo. Este valida cada pull request con dos jobs en paralelo:

yaml · .github/workflows/ci.yml 
name: CI

on:
  pull_request:
  push:
    branches: [main]

jobs:
  tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: "8.3"
      - run: composer install --prefer-dist --no-progress
      - run: vendor/bin/phpunit

  estilo:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: "8.3"
      - run: composer install --prefer-dist --no-progress
      - run: vendor/bin/php-cs-fixer check

Dos detalles de vocabulario. run: ejecuta un comando de shell, tal cual lo escribirías tú. uses: invoca una acción: un step empaquetado y reutilizable que alguien publicó (descargar el repo, instalar PHP, subir un fichero). Las acciones se fijan a una versión (@v4) por lo mismo que fijas versiones de dependencias: builds reproducibles.

Cada job empieza de cero

Los jobs tests y estilo corren en máquinas distintas: por eso cada uno repite el checkout y el composer install. Nada de lo que un job deje en disco existe para el otro. Para pasar cosas entre jobs hay dos mecanismos: artefactos y caché — justo lo que viene ahora.

Artefactos: lo que el pipeline produce #

Un pipeline no solo responde sí o no: produce cosas. El informe de cobertura, los logs de un fallo, el binario compilado, la imagen Docker. A esos productos se les llama artefactos, y las plataformas de CI permiten guardarlos al final de un job (actions/upload-artifact) para descargarlos desde la interfaz o recogerlos en un job posterior.

El artefacto tiene un papel conceptual importante en la entrega continua: se construye una vez y se despliega tal cual. Si el job de build produce el artefacto (por ejemplo, una imagen etiquetada con el hash del commit) y el deploy se limita a moverlo, lo que llega a producción es exactamente lo que pasó los tests — no una reconstrucción posterior que podría salir distinta.

La caché de dependencias #

La esterilidad del runner tiene un precio: descargar todas las dependencias en cada ejecución. La solución es la caché: guardar un directorio (por ejemplo, la caché local de Composer) bajo una clave, y restaurarlo al principio de la siguiente ejecución si la clave coincide.

La pregunta clave es qué usar de clave, y la respuesta es elegante: el hash del lockfile. Mientras composer.lock no cambie, las dependencias son las mismas y la caché vale; cuando cambie, la clave cambia y se descarga de nuevo. Es exactamente la misma lógica que la caché de capas de Docker: invalidar solo cuando cambia la entrada.

yaml · cachear las dependencias de Composer 
- uses: actions/cache@v4
  with:
    path: ~/.cache/composer
    key: composer-${{ hashFiles('composer.lock') }}

- run: composer install --prefer-dist --no-progress

Caché ≠ artefacto

Se confunden porque ambos "guardan ficheros". La diferencia es el propósito: la caché es una optimización descartable (si se pierde, solo tardas más); el artefacto es un producto del pipeline (si se pierde, pierdes el resultado). Nunca metas en caché algo que no puedas regenerar.

Barato primero: fallar rápido #

Última pieza de diseño: el orden. Si un cambio está mal, quieres saberlo en el paso más barato posible. Comprobar el estilo tarda segundos; los tests unitarios, un par de minutos; los de integración con base de datos, varios más; construir la imagen, otros tantos. La regla: ordena de lo barato a lo caro y corta al primer fallo.

1 Lint y estiloSegundos · corta los errores tontos
2 Tests unitarios1-2 min · el grueso de la validación
3 Tests de integraciónMinutos · con BD y servicios reales
4 Build del artefactoSolo se construye lo que ya validó

La pirámide de tests que ya conoces, convertida en orden de ejecución.

Hay dos formas de materializarlo: steps en secuencia dentro de un job (lo barato arriba), o jobs separados con dependencias explícitas (needs: [tests]) que además te dan paralelismo entre iguales. En la práctica se combinan: los checks rápidos en paralelo, y el build caro esperando con needs a que todos pasen. La proporción de cada tipo de test ya la tienes de la pirámide de tests; el pipeline solo la pone en fila.

Resumen #

Lo que te llevas

  • Cuatro piezas universales: workflow (el fichero), triggers (cuándo), jobs (trabajos paralelos en máquinas limpias) y steps (pasos en orden).
  • El runner nace limpio y muere tras cada job: todo se instala desde cero, y eso es lo que hace la validación fiable.
  • pull_request valida antes de mezclar; workflow_dispatch es el botón de la entrega continua.
  • Artefacto = producto (se construye una vez, se despliega tal cual); caché = optimización descartable con el hash del lockfile como clave.
  • Ordena de lo barato a lo caro y corta al primer fallo: el feedback rápido se diseña.
