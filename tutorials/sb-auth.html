Auth: usuarios, sesiones y JWT

Un login hecho a mano son semanas: hashear contraseñas, confirmar emails, recuperar cuentas, OAuth con cada proveedor, sesiones que caducan. Supabase Auth te lo da en unas llamadas. Lo que no te da es entender qué token viaja en cada petición, y sin eso no sabrás por qué un usuario «pierde la sesión» ni qué puedes meter en una política.

Hasta ahora auth.uid() aparecía en las políticas como algo dado. Esta lección cuenta de dónde sale: qué guarda Auth, qué tokens emite, cómo se renuevan y qué métodos de login puedes ofrecer. Si los conceptos de sesión, JWT y OAuth te suenan pero no los tienes claros, Autenticación: sesiones, JWT y OAuth los explica sin Supabase de por medio.

Dos tokens: uno corto y otro de un solo uso #

Cuando un usuario inicia sesión, Auth le da una sesión formada por dos tokens:

TokenQué esVidaPara qué
Access tokenUn JWT firmado por Auth con los datos del usuarioCorta: 1 hora por defectoViaja en cada petición (Authorization: Bearer ...) y es lo que leen auth.uid() y auth.jwt()
Refresh tokenUna cadena opaca guardada en la base de datos de AuthLarga, pero de un solo usoPedir un access token nuevo cuando el anterior caduca

Cada vez que se usa el refresh token, Auth lo invalida y entrega uno nuevo junto con el access token: es la rotación de refresh tokens. Si un atacante roba uno y lo usa, el legítimo deja de funcionar en el siguiente refresco (y al revés), y Auth puede detectar la reutilización y cerrar la sesión.

supabase-js hace todo esto solo: guarda la sesión (en el navegador, en localStorage por defecto), adjunta el access token en cada llamada y lo refresca antes de que caduque. Lo único que te toca es reaccionar a los cambios:

ts · escuchar el estado de la sesión 
supabase.auth.onAuthStateChange((event, session) => {
  if (event === "SIGNED_OUT") showLogin();
  if (event === "SIGNED_IN") showNotes(session.user);
});

Qué lleva el access token

Un JWT es un JSON firmado; cualquiera puede leerlo, nadie puede modificarlo sin invalidar la firma. Estos son los claims que más usarás en políticas:

ClaimContenido
subEl id del usuario: lo que devuelve auth.uid()
roleauthenticated (o anon): el rol de Postgres de la petición
email, phoneDatos de contacto
app_metadataDatos que solo el servidor puede cambiar: proveedor de login, roles de tu app
user_metadataDatos que el propio usuario puede cambiar: nombre, preferencias
aalNivel de autenticación: aal1 (un factor) o aal2 (con MFA)
is_anonymousSi es un usuario anónimo
session_id, expLa sesión a la que pertenece y cuándo caduca

Un token sigue valiendo hasta que caduca

Banear a un usuario o cerrar su sesión impide que refresque, pero el access token que ya tiene sigue siendo válido hasta su exp. Con la vida por defecto de una hora, eso es como mucho una hora de margen. Si te importa más, baja la duración del token; si te importa mucho, comprueba el estado del usuario en la propia política consultando una tabla tuya.

Métodos de login #

ts · los métodos más comunes 
await supabase.auth.signUp({
  email: "ana@ejemplo.com",
  password: "una contraseña larga y única",
  options: { data: { display_name: "Ana" } },
});

await supabase.auth.signInWithPassword({ email, password });

await supabase.auth.signInWithOtp({
  email,
  options: { emailRedirectTo: "https://notas.ejemplo.com/bienvenida" },
});

await supabase.auth.signInWithOAuth({
  provider: "github",
  options: { redirectTo: "https://notas.ejemplo.com/auth/callback" },
});

await supabase.auth.signInAnonymously();

await supabase.auth.signOut();
MétodoCómo funcionaCuándo encaja
Email y contraseñaRegistro con confirmación por email (activable)El clásico; exige recuperación de contraseña
Enlace mágico / OTP por emailLlega un enlace o un código de un solo usoSin contraseñas que olvidar ni filtrar
OTP por SMS o WhatsAppCódigo al teléfono, con un proveedor de SMS configuradoApps móviles; cada mensaje cuesta dinero
OAuth socialGoogle, GitHub, Apple, Microsoft y muchos másMenos fricción en el registro
AnónimoUn usuario real sin email, con is_anonymous: trueDejar probar antes de registrarse y convertirlo después
SSO con SAMLEl proveedor de identidad de una empresaClientes corporativos (planes de pago)

Los usuarios anónimos merecen un comentario: tienen rol authenticated, así que pasan las políticas escritas para usuarios con sesión. Si una política no debe aplicarse a ellos, compruébalo con (select (auth.jwt() ->> 'is_anonymous')::boolean) is false. Y como cualquiera puede crear miles, actívalos con CAPTCHA.

URLs de redirección y el email en producción #

Los enlaces mágicos, la confirmación de email y OAuth terminan redirigiendo al usuario a tu app. Auth solo redirige a direcciones que conozca, configuradas en Authentication → URL Configuration:

  • Site URL: la dirección principal de tu app, usada cuando no se indica otra.
  • Redirect URLs: la lista de direcciones permitidas, con comodines. Aquí van http://localhost:3000/** para desarrollo y las URLs de previsualización de tu hosting.

Si una redirección no está en la lista, Auth manda al usuario a la Site URL. El síntoma típico: «en producción, el enlace del email me lleva a localhost».

El correo por defecto no es para producción

El servidor de email que trae Supabase está para probar: tiene un límite muy bajo de envíos por hora y solo entrega a direcciones del equipo del proyecto. Antes de abrir la app a usuarios reales, configura un SMTP propio (Resend, Postmark, Amazon SES…) en Authentication → Emails. Sin él, los registros se quedan sin email de confirmación.

Las plantillas de cada email (confirmación, enlace mágico, cambio de email, recuperación) se editan en el mismo sitio. En local, la CLI los captura en Mailpit, como viste en la lección de la CLI.

Los datos del usuario: dónde va cada cosa #

Hay tres sitios donde guardar datos de un usuario, y elegir mal crea agujeros de seguridad:

SitioQuién lo escribeÚsalo para
user_metadataEl usuario, con supabase.auth.updateUser({ data })Preferencias y datos de presentación. Nunca para autorizar
app_metadataSolo el servidor, con la clave secretaRoles, plan contratado, flags que decide tu app
public.profiles (tabla tuya)Quien dejen tus políticasDatos que otros usuarios ven o que consultas con joins

La tabla auth.users no se expone por la API ni se le añaden columnas: el perfil que ven los demás va en public.profiles, creado con el trigger de funciones y triggers.

MFA: el segundo factor en las políticas #

Auth soporta un segundo factor con apps de autenticación (TOTP) y por teléfono. Tras el primer factor, la sesión tiene aal1; al verificar el segundo, sube a aal2. Lo interesante es que puedes exigir el segundo factor en la base de datos. Con una columna is_sensitive boolean not null default false en las notas:

sql · solo con MFA se ven las notas marcadas como sensibles 
create policy "Notas sensibles solo con MFA"
on public.notes
as restrictive
for select to authenticated
using (not is_sensitive or (select auth.jwt() ->> 'aal') = 'aal2');

Fíjate en as restrictive: las políticas restrictivas se combinan con and en lugar de or. Las permisivas dicen qué notas son tuyas; esta, encima, exige el segundo factor para las sensibles. Si fuera permisiva, abriría las notas no sensibles de todo el mundo.

Defensas que vienen activables #

  • Límites de peticiones por IP para registros, logins, emails y OTP, configurables en el panel.
  • CAPTCHA (hCaptcha o Cloudflare Turnstile) en registro, login y usuarios anónimos.
  • Políticas de contraseña: longitud mínima, caracteres exigidos y, en planes de pago, rechazo de contraseñas filtradas en brechas conocidas.
  • Confirmación de email antes de permitir el login.

Son las mismas defensas que cuenta Fuerza bruta y límites, ya montadas.

Auth Hooks: personalizar el flujo #

Los Auth Hooks dejan que una función de Postgres o una Edge Function intervenga en momentos concretos del flujo de Auth:

HookMomentoEjemplo
Custom Access TokenAntes de emitir cada access tokenAñadir el rol del usuario como claim
Send Email / Send SMSAl enviar un email o SMSUsar tu propio proveedor y tus plantillas
Before User CreatedAntes de crear un usuarioPermitir solo emails de tu empresa
MFA / Password Verification AttemptTras un intento fallidoBloquear tras N fallos

El más usado es el de access token: con él, el rol de un usuario viaja en el JWT y las políticas lo leen sin consultar ninguna tabla. Lo montamos en Auth en el servidor.

Cuándo aplicarlo #

Supabase Auth encaja cuando…

  • Usas la Data API o RLS: el token de Auth es lo que hace funcionar las políticas
  • Quieres OAuth, enlaces mágicos o MFA sin mantener la integración tú
  • Tus usuarios son personas finales de tu app

Considera otra opción si…

  • Ya tienes un proveedor de identidad (Auth0, Clerk, Cognito, Firebase Auth): Supabase acepta sus tokens como third-party auth y las políticas siguen funcionando
  • Tu organización exige un IdP corporativo central para todo
  • Necesitas flujos de identidad muy específicos que los hooks no cubren

Resumen #

Lo que te llevas

  • La sesión son dos tokens: un access token JWT de vida corta que viaja en cada petición y un refresh token de un solo uso que rota en cada renovación.
  • El access token sigue valiendo hasta que caduca aunque cierres la sesión: su duración es tu margen de revocación.
  • Contraseña, enlace mágico, OTP, OAuth, anónimos y SSO se activan en el panel; los anónimos tienen rol authenticated.
  • Las redirecciones solo van a URLs permitidas, y en producción hace falta un SMTP propio.
  • user_metadata lo escribe el usuario y nunca autoriza; los roles van en app_metadata o en tablas tuyas.
  • aal2 en una política restrictiva exige MFA desde la base de datos; los Auth Hooks personalizan tokens, emails y registros.
