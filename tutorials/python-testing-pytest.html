Testing con pytest

pytest elimina el boilerplate de unittest y hace que escribir tests sea tan sencillo como escribir funciones. Aprenderás a usar fixtures con diferentes scopes, parametrizar casos de prueba, reemplazar dependencias con pytest-mock, escribir tests async con anyio y organizar la suite con conftest.py.

Fixtures: setup sin clases

Una fixture es una función decorada con @pytest.fixture que devuelve (o produce con yield) un objeto que los tests pueden usar. pytest inyecta la fixture en el test cuando el nombre del parámetro coincide con el nombre de la fixture, sin necesidad de herencia ni setUp:

import pytest


@pytest.fixture
def usuario_valido():
    return {"id": 1, "nombre": "Ana", "email": "ana@example.com"}


def test_nombre_usuario(usuario_valido):
    assert usuario_valido["nombre"] == "Ana"


def test_email_tiene_arroba(usuario_valido):
    assert "@" in usuario_valido["email"]

Convención de naming y descubrimiento automático

pytest descubre tests buscando ficheros test_*.py o *_test.py dentro del directorio configurado en testpaths. Dentro de esos ficheros, descubre funciones test_* y métodos test_* en clases Test*. La convención más expresiva para el nombre de un test es test_<qué_se_prueba>_cuando_<condición>, por ejemplo test_crear_usuario_cuando_email_duplicado.

El scope de una fixture controla cuántas veces se crea. Por defecto es "function": se recrea en cada test. Para recursos costosos como conexiones a base de datos, usa "module" o "session":

import pytest


@pytest.fixture(scope="session")
def engine_base_de_datos():
    motor = crear_engine()
    yield motor
    motor.dispose()


@pytest.fixture(scope="function")
def sesion(engine_base_de_datos):
    sesion = engine_base_de_datos.nueva_sesion()
    yield sesion
    sesion.rollback()
    sesion.close()

El bloque después del yield actúa como teardown: se ejecuta siempre al finalizar el test, incluso si el test falla. Para fixtures de scope="session", el teardown ocurre al final de toda la suite.

Una fixture puede depender de otras fixtures. pytest resuelve el grafo de dependencias automáticamente, respetando los scopes. No puedes usar una fixture de scope más estrecho dentro de una de scope más amplio (por ejemplo, una fixture de función dentro de una de módulo).

@pytest.mark.parametrize

@pytest.mark.parametrize ejecuta el mismo test con múltiples conjuntos de entrada y salida esperada. Cada conjunto se convierte en un caso de prueba independiente con su propio estado de pass o fail. Esto hace visible cada caso en la salida del runner:

import pytest
from app.utils import es_primo


@pytest.mark.parametrize("numero,esperado", [
    (2, True),
    (3, True),
    (4, False),
    (1, False),
    (17, True),
    (100, False),
])
def test_es_primo(numero, esperado):
    assert es_primo(numero) == esperado

Para casos con múltiples parámetros de entrada:

from app.utils import normalizar_email


@pytest.mark.parametrize("entrada,esperada", [
    ("ANA@EXAMPLE.COM", "ana@example.com"),
    ("  juan@test.es  ", "juan@test.es"),
    ("MARIA@GMAIL.COM", "maria@gmail.com"),
])
def test_normalizar_email(entrada, esperada):
    assert normalizar_email(entrada) == esperada

Puedes combinar parametrize con fixtures: el test recibe tanto los valores parametrizados como los objetos de las fixtures. Si apilas dos decoradores @pytest.mark.parametrize, pytest genera el producto cartesiano de todos los casos.

Para dar nombre explícito a cada caso y que la salida del runner sea más legible, usa el argumento ids:

@pytest.mark.parametrize(
    "descuento,precio_base,precio_final",
    [
        (0.0, 100.0, 100.0),
        (0.1, 100.0, 90.0),
        (0.5, 200.0, 100.0),
    ],
    ids=["sin_descuento", "descuento_10_pct", "descuento_50_pct"],
)
def test_aplicar_descuento(descuento, precio_base, precio_final):
    assert aplicar_descuento(precio_base, descuento) == precio_final

Mocking con pytest-mock

pytest-mock envuelve unittest.mock y lo expone como la fixture mocker. El mock se limpia automáticamente al finalizar el test, sin necesidad de contextos with patch(...):

pip install pytest-mock
from app.servicios import ServicioUsuario


def test_notifica_al_crear_usuario(mocker):
    enviar_mock = mocker.patch("app.notificaciones.NotificadorEmail.enviar")
    repositorio_mock = mocker.MagicMock()
    repositorio_mock.guardar.return_value = None

    servicio = ServicioUsuario(
        repositorio=repositorio_mock,
        notificador=mocker.MagicMock(),
    )
    servicio.crear(nombre="Ana", email="ana@example.com")

    enviar_mock.assert_called_once_with(
        destinatario="ana@example.com",
        asunto="Bienvenida",
    )

mocker.patch() reemplaza el objeto en la ruta indicada durante la ejecución del test. La ruta debe apuntar al módulo donde el objeto se usa, no donde se define. Si el servicio importa enviar con from app.notificaciones import enviar, la ruta de patch es app.servicios.enviar.

Para simular el valor de retorno de un método o el estado de un objeto completo, MagicMock es suficiente. Puedes combinar return_value para llamadas simples y side_effect para simular errores o comportamientos que cambian con cada llamada:

def test_reintenta_si_falla_conexion(mocker):
    llamadas = [ConnectionError("timeout"), ConnectionError("timeout"), "OK"]
    cliente_mock = mocker.MagicMock()
    cliente_mock.obtener.side_effect = llamadas

    resultado = servicio_con_reintentos.obtener_dato(cliente=cliente_mock)

    assert resultado == "OK"
    assert cliente_mock.obtener.call_count == 3

assert_called_once_with(), assert_called_with() y call_count comprueban cómo fue llamado el mock. assert_not_called() verifica que no fue invocado.

Tests async con anyio

Para testear funciones async def necesitas un runner que ejecute el event loop. anyio es el más flexible porque soporta tanto asyncio como trio y se integra con pytest mediante el decorador @pytest.mark.anyio:

pip install anyio pytest-anyio
import pytest
from app.repositorios import UsuarioRepository


@pytest.mark.anyio
async def test_buscar_usuario_existente(session):
    repositorio = UsuarioRepository(session)
    usuario = await repositorio.buscar_por_id(1)

    assert usuario is not None
    assert usuario.email == "ana@example.com"


@pytest.mark.anyio
async def test_guardar_usuario_nuevo(session):
    repositorio = UsuarioRepository(session)
    nuevo = Usuario(nombre="Carlos", email="carlos@example.com")

    guardado = await repositorio.guardar(nuevo)

    assert guardado.id is not None
    assert guardado.nombre == "Carlos"

La fixture session en estos tests es una fixture async definida en conftest.py (veremos su definición en la siguiente sección). Para que anyio ejecute las fixtures async, la fixture anyio_backend debe declararse en el mismo conftest:

@pytest.fixture(scope="session")
def anyio_backend():
    return "asyncio"

Con esta fixture, anyio sabe que debe usar el backend de asyncio para todos los tests de la sesión. Si prefieres trio, cambia el valor a "trio".

anyio_mode = auto: si añades anyio_mode = auto en pytest.ini, no necesitas decorar cada test con @pytest.mark.anyio. Todas las funciones async def test_* se ejecutan automáticamente con anyio.

conftest.py y cobertura con pytest-cov

conftest.py es el fichero donde defines fixtures compartidas entre múltiples módulos de test. pytest lo carga automáticamente para todos los tests del directorio y subdirectorios donde esté ubicado, sin necesidad de importarlo:

import pytest
from sqlalchemy.ext.asyncio import create_async_engine, AsyncSession, async_sessionmaker
from app.models import Base

TEST_DATABASE_URL = "postgresql+asyncpg://user:pass@localhost/test_db"


@pytest.fixture(scope="session")
def anyio_backend():
    return "asyncio"


@pytest.fixture(scope="session")
async def engine():
    motor = create_async_engine(TEST_DATABASE_URL, echo=False)

    async with motor.begin() as conexion:
        await conexion.run_sync(Base.metadata.create_all)

    yield motor

    async with motor.begin() as conexion:
        await conexion.run_sync(Base.metadata.drop_all)

    await motor.dispose()


@pytest.fixture
async def session(engine):
    async with AsyncSession(engine) as sesion:
        yield sesion
        await sesion.rollback()

El rollback() en el teardown garantiza que cada test comienza con un estado limpio sin necesidad de limpiar las tablas manualmente. La BD de test se crea al inicio de la sesión y se destruye al final.

La configuración de pytest va en pytest.ini o en la sección [tool.pytest.ini_options] de pyproject.toml:

[pytest]
addopts = --strict-markers -q
testpaths = tests
anyio_mode = auto

Para medir la cobertura de código instala pytest-cov y pásale el paquete a analizar:

pip install pytest-cov
pytest --cov=app --cov-report=term-missing tests/
pytest --cov=app --cov-report=html tests/

--cov-report=term-missing imprime en consola las líneas no cubiertas. --cov-report=html genera un informe HTML en htmlcov/index.html que muestra el código coloreado por cobertura.

Para excluir del análisis código que no merece cobertura (scripts de arranque, migraciones, stubs de tipos), añade comentarios # pragma: no cover en las líneas o configura omit en la sección [coverage:run] del pyproject.toml.

Resumen

  • Las fixtures eliminan setUp/tearDown y se comparten solo donde se usan; el scope controla cuántas veces se crean: function (por defecto), module o session.
  • @pytest.mark.parametrize convierte cada caso de prueba en una entrada separada con su propio estado de pass/fail, evitando loops y código repetido en los tests.
  • mocker.patch() de pytest-mock reemplaza dependencias externas en el ámbito del test y las restaura automáticamente al finalizar; la ruta de patch apunta a donde se usa el objeto, no donde se define.
  • @pytest.mark.anyio habilita tests async def con soporte para asyncio y trio; la fixture anyio_backend selecciona el backend para toda la sesión.
  • conftest.py centraliza fixtures compartidas sin importaciones explícitas; la fixture de sesión con rollback() en el teardown aísla cada test de los cambios del anterior.
  • pytest-cov mide la cobertura línea a línea; apunta al menos al 80% en código de negocio y al 100% en funciones puras sin efectos secundarios.
