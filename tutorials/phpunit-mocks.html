Stubs y mocks en la práctica

La teoría de los dobles ya la tienes; esta lección es la API concreta con la que PHPUnit los fabrica. Dos métodos, dos intenciones: createStub para programar respuestas, createMock para verificar conversaciones — y saber cuándo estás usando demasiados.

En test doubles viste la taxonomía —dummy, stub, spy, mock, fake— y la distinción de fondo: verificar estado (qué devuelve o en qué queda algo) vs verificar comportamiento (qué llamadas se hicieron). PHPUnit condensa esa teoría en una API pequeña, y elegir bien el método es elegir qué tipo de test estás escribiendo.

De la teoría a la API #

Dos puntos de entrada, cada uno con su intención:

MétodoFabricaLo usas cuando…
createStub(Interfaz::class)Un stub: responde lo que le programes, no verifica nada.El colaborador solo alimenta al código bajo prueba; la aserción va sobre el resultado.
createMock(Interfaz::class)Un mock: además de responder, espera llamadas concretas y falla si no ocurren.La llamada al colaborador ES el efecto que pruebas (enviar el email, publicar el evento).

Ambos generan al vuelo una clase que implementa la interfaz (o extiende la clase) con todos los métodos vacíos. Y aquí reaparece un viejo conocido: esto funciona bien porque tus servicios dependen de interfaces inyectadas por constructor — los dobles son la recompensa práctica de ese diseño. Interfaces pequeñas (ISP) = dobles baratos.

Stubs: programar respuestas #

El caso más frecuente: pruebas un servicio que lee de un colaborador. El stub le da al servicio el mundo que necesita ver:

php · el stub alimenta; la aserción va al resultado 
#[Test]
public function el_total_convierte_a_la_moneda_del_cliente(): void
{
    $rates = $this->createStub(ExchangeRateProvider::class);
    $rates->method('rateFor')->willReturn(1.10);

    $converter = new PriceConverter($rates);

    $this->assertSame(1100, $converter->convert(1000, to: 'USD'));
}

La secuencia se lee sola: method('rateFor') selecciona el método, willReturn(1.10) programa la respuesta. El test no comprueba nada sobre el stub — le da igual cuántas veces se llame o con qué argumentos. Esa indiferencia es una virtud: el test queda acoplado al resultado, no a cómo el servicio conversa por dentro, así que sobrevivirá a refactorizaciones internas.

Mocks: verificar la conversación #

A veces el efecto que pruebas no es un valor devuelto sino una orden dada: "al confirmar el pedido, se envía el email". No hay resultado que asertar — la llamada es el comportamiento. Ahí entra el mock con sus expectativas:

php · la llamada es lo que se prueba 
#[Test]
public function confirmar_el_pedido_notifica_al_cliente(): void
{
    $mailer = $this->createMock(OrderMailer::class);
    $mailer->expects($this->once())
        ->method('sendConfirmation')
        ->with($this->callback(
            fn (Order $order): bool => $order->id() === 7
        ));

    $service = new OrderService(new InMemoryOrderRepository(), $mailer);

    $service->confirm(new Order(id: 7));
}

Las tres piezas de una expectativa: expects() dice cuántas veces ($this->once(), $this->never(), $this->exactly(2)), method() dice qué método, y with() dice con qué argumentos (valores literales, o un callback para comprobar lo que importa del argumento). Si al terminar el test la expectativa no se cumplió, falla solo — la verificación está implícita.

$this->never(): la expectativa negativa

Tan valioso como comprobar que algo se llama es comprobar que no se llama: "si el pedido ya estaba confirmado, NO se reenvía el email". expects($this->never())->method('sendConfirmation') lo deja escrito como regla ejecutable.

Respuestas avanzadas #

Además de willReturn, hay tres programaciones que cubren el resto de escenarios reales:

php · excepciones, respuestas según argumento y callbacks 
// simular que el colaborador falla: ¿mi servicio lo gestiona bien?
$gateway->method('charge')
    ->willThrowException(new PaymentDeclined('fondos insuficientes'));

// respuesta distinta según el argumento (mapa entrada -> salida)
$rates->method('rateFor')->willReturnMap([
    ['USD', 1.10],
    ['GBP', 0.85],
]);

// lógica arbitraria cuando el mapa no basta
$repository->method('find')->willReturnCallback(
    fn (int $id): ?Order => $id === 7 ? new Order(id: 7) : null
);

willThrowException es la más importante de las tres: es la puerta a testear los caminos tristes — qué hace tu servicio cuando la pasarela rechaza el pago, cuando la API externa da timeout. En producción esos escenarios son difíciles de provocar; con un stub cuestan una línea. La lección siguiente (excepciones) completa ese frente.

Sobre-mockear #

La API es tan cómoda que el peligro es el exceso. Dos reglas de contención:

Primera: no verifiques conversaciones que no son el comportamiento. Si usas expects() para cada llamada interna —que consultó el repositorio, que llamó al validador, que pidió el tipo de cambio— tu test es una fotografía de la implementación: cualquier refactor que cambie el cómo sin tocar el qué lo rompe. Es el test frágil de manual (comportamiento, no implementación). La pregunta que ordena: ¿esta llamada es un efecto prometido del servicio (email enviado, evento publicado) o un detalle de fontanería? Mock para lo primero; stub indiferente para lo segundo.

Segunda: no mockees lo que no es tuyo. Doblar la interfaz de un cliente HTTP de terceros acopla tus tests a una API ajena que cambiará. El patrón sano: define tu puerto (una interfaz tuya, pequeña, con el lenguaje de tu dominio), envuelve la librería en un adaptador, y mockea tu puerto — exactamente la jugada de la arquitectura hexagonal. Y para colaboradores con lógica de consulta rica (un repositorio), a menudo un fake escrito a mano (como el InMemoryOrderRepository de estos ejemplos) da tests más legibles que una pila de stubs.

Resumen #

Lo que te llevas

  • createStub para alimentar (aserción sobre el resultado); createMock + expects cuando la llamada misma es el comportamiento prometido.
  • Expectativa = expects (cuántas: once/never/exactly) + method (cuál) + with (con qué); se verifica sola al acabar el test.
  • willThrowException abre los caminos tristes; willReturnMap y willReturnCallback cubren respuestas dependientes del argumento.
  • Mock solo los efectos prometidos; expectativas sobre la fontanería interna = test frágil que castiga cada refactor.
  • No mockees lo ajeno: envuélvelo en tu puerto y mockea el puerto. Para colaboradores ricos, un fake en memoria gana en legibilidad.
