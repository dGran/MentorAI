El handshake de TLS y su coste en latencia

Antes de que viaje un byte de tu petición, cliente y servidor han negociado cómo cifrar. Con usuarios lejos son cientos de milisegundos que no salen en ningún perfil.

Antes de que viaje un solo byte de tu petición, cliente y servidor han negociado cómo van a cifrar. Ese saludo cuesta idas y vueltas de red, y cuando hay usuarios lejos son cientos de milisegundos que no aparecen en ningún perfil de tu aplicación.

Qué se negocia #

El handshake resuelve tres cosas a la vez, y esa es la razón de que cueste:

1 Qué algoritmos usamosCliente y servidor tienen que coincidir en una suite
2 Quién eres túEl servidor manda su certificado y el cliente verifica la cadena
3 Una clave compartidaDerivada de forma que nadie que escuche pueda deducirla

El paso 3 usa intercambio de claves efímero, que es lo que da forward secrecy: si mañana roban la clave privada del servidor, el tráfico grabado ayer sigue siendo indescifrable.

El coste en idas y vueltas #

EscenarioIdas y vueltas antes del primer byte útil
TCP + TLS 1.23: una de TCP, dos de TLS
TCP + TLS 1.32: una de TCP, una de TLS
TLS 1.3 reanudando sesión1, y los datos pueden ir en la primera (0-RTT)
QUIC (HTTP/3)1, porque transporte y cifrado se negocian juntos

Multiplica por tu latencia real

Una ida y vuelta Madrid–Virginia son unos 90 ms. Con TLS 1.2 eso son 270 ms antes de que tu servidor lea la primera línea de la petición. Ninguna optimización de tu código toca ese número: solo se reduce acercando el punto de terminación al usuario, que es a lo que se dedica una CDN.

Cómo se reduce #

Reutilizar conexiones. El handshake se paga una vez y luego la conexión sirve para muchas peticiones. Es gratis en el navegador y hay que activarlo en los clientes de servidor: un cliente HTTP que abre y cierra conexión en cada llamada paga el saludo completo cada vez.

php · un cliente que reutiliza 
<?php

declare(strict_types=1);

final class ClienteDePrecios
{
    public function __construct(private readonly HttpClientInterface $http)
    {
    }

    public function precio(int $idProducto): int
    {
        return $this->http
            ->request('GET', "/precios/{$idProducto}")
            ->toArray()['centimos'];
    }
}

La clave está en que el cliente se inyecta y vive lo que viva el proceso, en vez de construirse dentro del método. En PHP con FPM la reutilización dura lo que la petición —que ya es algo si haces varias llamadas—; en un worker de larga vida, dura horas.

Reanudar sesiones. Con ssl_session_cache en nginx, un cliente que vuelve se salta la parte cara del handshake. Y terminar cerca: una CDN hace el saludo con el usuario a 20 ms y mantiene conexiones ya calientes hasta tu origen.

0-RTT tiene una trampa seria

Mandar datos en el primer paquete es rapidísimo y no protege contra repetición: un atacante que capture ese paquete puede reenviarlo y el servidor lo procesará otra vez. Por eso 0-RTT solo debe llevar peticiones idempotentes —un GET—, nunca un POST que cobre algo. Los servidores serios lo restringen por método.

Verificar el certificado no es opcional #

La línea que más veces se ha escrito «temporalmente» y se ha quedado para siempre:

php · lo que nunca debe llegar a producción 
<?php

$respuesta = $this->http->request('GET', $url, [
    'verify_peer' => false,
    'verify_host' => false,
]);

Con eso el tráfico sigue cifrado y deja de estar autenticado: cualquiera que se ponga en medio puede presentar su propio certificado y leerlo todo. Has conservado uno de los tres beneficios de TLS y tirado el más importante. Si el problema es un certificado interno, la solución es añadir tu autoridad al almacén de confianza, no desactivar la comprobación.

Cuándo aplicarlo #

Preocúpate del handshake cuando…

  • Tus usuarios están lejos del servidor
  • Haces muchas llamadas salientes a terceros
  • Hay clientes móviles con latencia alta
  • El presupuesto de latencia va justo

Es irrelevante cuando…

  • Es tráfico local con latencias de microsegundos
  • Son pocas conexiones de larga duración
  • El trabajo por petición domina sobre el transporte

Resumen #

Lo que te llevas

  • El handshake negocia algoritmos, identidad y clave compartida: por eso cuesta idas y vueltas antes del primer byte útil.
  • TLS 1.2 sobre TCP son tres idas y vueltas: con 90 ms de latencia, 270 ms antes de que tu código vea nada.
  • Un cliente HTTP que se construye dentro del método paga el handshake en cada llamada: se inyecta y se reutiliza.
  • 0-RTT no protege contra repetición: solo para peticiones idempotentes, nunca para un POST que cobre.
  • Desactivar la verificación deja el tráfico cifrado y sin autenticar: conservas el beneficio menor y tiras el importante.
