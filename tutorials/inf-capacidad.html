Capacidad y escalado: dónde está tu acantilado

«¿Aguantará el pico?» tiene dos respuestas: una intuición y un número. Entre las dos hay una tarde de pruebas, y saber que el sistema no se degrada: se despeña.

«¿Aguantará el Black Friday?» tiene dos respuestas: una intuición y un número. La diferencia entre las dos es una tarde de pruebas de carga, y saber que el sistema no se degrada suavemente — se comporta bien hasta un punto y a partir de ahí se cae por un acantilado.

El rendimiento no baja: se despeña #

Es lo más contraintuitivo de dimensionar. Uno espera que al doble de carga el sistema vaya el doble de lento, y no funciona así:

1 Hasta el 70 % de capacidadLa latencia apenas se mueve
2 Entre el 70 % y el 90 %Empieza a subir, todavía suavemente
3 Por encima del 90 %La latencia se dispara y el rendimiento total baja

Es teoría de colas: cuando la utilización se acerca a 1, el tiempo de espera tiende a infinito. Por eso se dimensiona para el 60-70 %, no para el 95 %.

Y el rendimiento baja de verdad, no solo la latencia

Pasado el punto de saturación, el sistema gasta cada vez más recursos en gestionar la contención —cambios de contexto, competencia por bloqueos, reintentos de clientes impacientes— y menos en trabajo útil. Atiende menos peticiones por segundo que cuando estaba al 80 %.

Vertical, horizontal y lo que impide la segunda #

Vertical: una máquina mayor

  • Inmediato y sin cambiar código
  • La opción sensata cuando aún cabes
  • Tiene techo, y arriba se paga muy caro
  • Implica reiniciar: hay corte

Horizontal: más máquinas

  • Sin techo práctico
  • Y además te da tolerancia a fallos
  • Exige que la aplicación no tenga estado local
  • Multiplica conexiones contra la base de datos

La observación importante: escalar horizontalmente los servidores web es fácil, y casi nunca es donde está el problema. El cuello suele ser la base de datos, que es justo lo que peor escala en horizontal. Añadir servidores web contra una base de datos saturada empeora las cosas, porque le mandan más consultas.

Probar antes de que llegue el pico #

Hay tres pruebas distintas y responden a preguntas distintas:

PruebaQué responde
De carga¿Cumplo el objetivo con la carga esperada?
De estrés¿Dónde está mi acantilado, y qué se rompe primero?
De resistencia¿Aguanto ocho horas seguidas, o tengo una fuga de memoria?
bash · una prueba de carga sencilla 
k6 run --vus 200 --duration 5m escenario.js

ab -n 10000 -c 100 https://ejemplo.com/api/productos

Golpear un solo endpoint no prueba nada

Diez mil peticiones al mismo producto se sirven todas de caché caliente y te dan un número precioso que no significa nada. Una prueba útil recorre un escenario: entrar, buscar con términos variados, ver fichas distintas, añadir al carrito. Con datos variados, o solo estás midiendo tu caché.

El autoescalado tiene letra pequeña #

Suena a solución total y tiene tres límites que conviene conocer antes de confiarle la campaña de Navidad.

Tarda. Detectar la carga, arrancar la instancia, pasar el health check y entrar en el balanceo son minutos. Un pico de treinta segundos ya ha terminado para cuando la instancia nueva está lista.

Escala lo fácil, no lo que sufre. Añade servidores web, que era la parte que aguantaba, mientras la base de datos —que es la que se ahoga— sigue igual. Y encima recibe más conexiones.

Puede oscilar. Con umbrales mal puestos, arranca instancias, baja la carga, las apaga, sube la carga, las arranca otra vez. Se calma con periodos de enfriamiento y con histéresis —subir con un umbral y bajar con otro más bajo—.

Para un pico previsible, escala programado

Si sabes que la campaña empieza el viernes a las nueve, no esperes a que el autoescalado reaccione: levanta la capacidad a las ocho. El escalado reactivo es para lo imprevisto; para lo que está en el calendario, se programa. Es más barato, más fiable y no depende de que los umbrales estén finos.

Cuándo aplicarlo #

Prueba la capacidad cuando…

  • Viene un pico conocido: campaña, lanzamiento, migración
  • Vas a comprometerte a un SLA
  • Has cambiado algo estructural: base de datos, caché, arquitectura
  • Quieres saber qué se rompe primero, antes de que se rompa solo

No hace falta cuando…

  • Vas sobradísimo y el uso es estable
  • Es una herramienta interna con usuarios contados
  • El coste de la prueba supera al del incidente que evitas

Resumen #

Lo que te llevas

  • El rendimiento no se degrada suavemente: hay un acantilado. Por eso se dimensiona al 60-70 % de capacidad, no al 95 %.
  • Pasado el punto de saturación se atienden menos peticiones por segundo: los recursos se van en gestionar la contención.
  • Escalar servidores web es fácil y casi nunca es el problema: el cuello suele ser la base de datos, que es lo que peor escala en horizontal.
  • Golpear un endpoint con el mismo parámetro mide tu caché, no tu sistema: hace falta un escenario con datos variados.
  • El autoescalado tarda minutos, escala lo que ya aguantaba y puede oscilar. Para un pico previsible, escala programado.
