Endurecer un servidor: SSH, cortafuegos y usuarios

Un servidor con IP pública recibe intentos de acceso a los minutos de encenderse. La buena noticia es que casi todo se corta con tres decisiones que se toman una vez.

Un servidor con IP pública recibe intentos de acceso a los pocos minutos de encenderse. No porque alguien te haya elegido: hay escáneres recorriendo el direccionamiento entero todo el rato. La buena noticia es que el 95 % de eso se corta con tres decisiones que se toman una vez.

Las tres decisiones que más rinden #

1 SSH solo con claveSin contraseñas, no hay fuerza bruta que valga
2 Cortafuegos que deniega por defectoSolo se abre lo que hace falta
3 Nada corre como rootUn fallo en la aplicación no es un fallo de la máquina

El resto —fail2ban, cambiar el puerto, endurecer el kernel— son mejoras marginales sobre esta base.

SSH: quitar la contraseña #

Mientras exista autenticación por contraseña, hay un ataque posible que solo depende de tiempo. Con claves, no: no hay nada que adivinar.

ini · /etc/ssh/sshd_config.d/endurecer.conf 
PasswordAuthentication = no
KbdInteractiveAuthentication = no
PermitRootLogin = no
AllowUsers = despliegue admin
MaxAuthTries = 3

Antes de recargar SSH, abre una segunda sesión

Es el error que todo el mundo comete una vez: aplicar la configuración, cerrar la terminal y descubrir que tu clave no estaba donde creías. Con una sesión abierta en paralelo puedes deshacerlo; sin ella, necesitas la consola del proveedor —si la hay—. Comprueba con sshd -t antes de recargar, y prueba a entrar desde otra terminal antes de cerrar la que tienes.

Cambiar el puerto 22 a otro reduce el ruido en los logs, no el riesgo: un escaneo de puertos lo encuentra igual. Es cosmética útil, no seguridad. Lo que sí aporta, si puedes, es limitar el acceso por IP de origen o entrar por una VPN, de modo que SSH no esté expuesto en absoluto.

Cortafuegos: denegar por defecto #

La regla es abrir lo que necesitas y cerrar todo lo demás, no al revés. Cuatro comandos:

bash · ufw 
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp
sudo ufw allow 443/tcp
sudo ufw enable

Docker se salta tu cortafuegos

Docker escribe sus propias reglas de iptables y las coloca antes que las de ufw. Un -p 3306:3306 publica MySQL a internet aunque ufw diga que ese puerto está cerrado, y ufw te seguirá diciendo que está cerrado. La defensa es publicar solo en la interfaz local (-p 127.0.0.1:3306:3306) y comprobar desde fuera con nmap qué se ve de verdad, no fiarte de lo que dice el cortafuegos.

Ni la aplicación ni tú sois root #

El principio es el de mínimo privilegio, y en la práctica se traduce en unas pocas reglas concretas:

Cómo debería estar

  • Un usuario de sistema por servicio, sin shell de acceso
  • El código en propiedad de un usuario distinto al que lo ejecuta
  • sudo nominal, con las órdenes concretas permitidas
  • Directorios de escritura contados: var/, uploads/

Lo que se ve a menudo

  • Todo como www-data, incluidos los crons
  • chmod -R 777 «hasta que funcione»
  • Una clave SSH compartida por todo el equipo
  • El servidor web con permiso de escritura sobre el código

El último de la derecha es el que más se subestima: si el proceso que sirve la web puede escribir en su propio código, una vulnerabilidad de subida de ficheros pasa de ser molesta a ser ejecución remota de código. Que el código lo posea un usuario distinto del que ejecuta, y en solo lectura, corta esa cadena entera.

Lo aburrido que evita la mayoría de los incidentes #

La gran mayoría de las intrusiones no usan un ataque nuevo: usan uno conocido contra una versión sin actualizar. Las actualizaciones de seguridad desatendidas son de las pocas cosas que se configuran una vez y siguen dando valor años:

bash · debian y derivadas 
sudo apt install unattended-upgrades
sudo dpkg-reconfigure --priority=low unattended-upgrades

Solo seguridad, y con reinicio decidido por ti

Actualizar automáticamente todo puede meterte un cambio de versión mayor sin avisar. Limítalo a los repositorios de seguridad. Y algunas actualizaciones —del núcleo, sobre todo— no surten efecto hasta reiniciar: revisa /var/run/reboot-required y elige tú el momento en vez de dejar Automatic-Reboot puesto.

Y la parte que no es del sistema operativo: tus dependencias. Un composer audit en el pipeline avisa de vulnerabilidades conocidas en los paquetes, que es exactamente el mismo problema una capa más arriba.

Cuándo aplicarlo #

Haz esto siempre cuando…

  • La máquina tiene IP pública, sin excepción
  • Es el primer día del servidor: cuesta minutos y luego cuesta semanas
  • Hay datos de personas dentro
  • Varias personas tienen acceso

Puedes relajarlo cuando…

  • Es una máquina de desarrollo local sin exposición
  • Vive en una red privada sin salida a internet
  • Es efímera: se crea y se destruye en el mismo pipeline

Resumen #

Lo que te llevas

  • Tres decisiones cubren el 95 %: SSH solo con clave, cortafuegos que deniega por defecto y nada corriendo como root.
  • Antes de recargar SSH, deja una segunda sesión abierta y verifica desde otra terminal. Es el error que se comete una vez.
  • Docker escribe reglas por delante de ufw: un puerto publicado se ve desde internet aunque el cortafuegos diga que está cerrado.
  • Si el proceso web puede escribir en su propio código, una subida de ficheros vulnerable pasa de molesta a ejecución remota.
  • Casi ninguna intrusión usa un ataque nuevo: usa uno conocido contra algo sin actualizar. Las actualizaciones de seguridad desatendidas se configuran una vez.
