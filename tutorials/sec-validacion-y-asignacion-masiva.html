Validación de entrada y asignación masiva

Tu endpoint de «editar perfil» espera un nombre y un idioma. Alguien le manda también "is_admin": true y tu ORM, muy servicial, lo guarda. Esta lección va de decidir qué entra y qué sale, campo a campo.

Un formulario web es una sugerencia, no un contrato. El navegador envía los campos que pinta tu HTML, pero cualquiera con curl puede mandar los que quiera, con el tipo que quiera. La pregunta no es «¿qué campos envía mi front?», sino «¿qué campos acepta mi backend?». Si la respuesta es «los que lleguen», tienes un problema.

El campo que nadie pidió #

La asignación masiva (mass assignment) es copiar el cuerpo de la petición directamente sobre un objeto del dominio. Es cómodo: una línea y el modelo queda actualizado. El precio es que el cliente elige qué propiedades tocas, y tu entidad User tiene más propiedades de las que tu pantalla muestra: role, is_admin, email_verified_at, credit, tenant_id.

El caso clásico lo protagonizó GitHub en 2012: un usuario usó asignación masiva en una aplicación Rails para añadir su clave pública a un repositorio ajeno. No hizo falta ningún exploit sofisticado, solo un campo de más en un formulario.

1 JSON de entradaname, locale… y is_admin
2 DTO de entradatipos, rangos y listas permitidas
3 Entidad de dominioel código decide qué se modifica
4 DTO de salidanada de hashes ni flags internos

Dos fronteras con lista explícita: la de entrada y la de salida.

Validar en el borde, no sanear #

Validar es rechazar lo que no cumple el contrato; sanear es transformar la entrada para que «parezca» buena. La validación gana por una razón sencilla: si rechazas, el dato malo nunca entra; si saneas, apuestas a que tu transformación cubre todos los casos, y suele haber uno que no.

El borde es el primer punto donde tu código recibe la petición: el controlador o lo que haya justo antes. Ahí se comprueban tres cosas:

  • Tipo: un entero es un entero, no "5 OR 1=1" ni un array.
  • Rango y longitud: una cantidad entre 1 y 100, un nombre de como mucho 100 caracteres.
  • Lista permitida: el idioma es es, en o fr; cualquier otro valor se rechaza.
TécnicaQué haceDónde va
ValidarRechaza la petición con un 422 si no cumple el contrato.En la entrada, siempre.
NormalizarAjusta forma sin cambiar significado: trim, minúsculas en el email.En la entrada, antes de validar.
EscaparCodifica para el contexto de destino: HTML, SQL, shell.En la salida, según el destino.

Fíjate en que «sanear contra XSS» no aparece. Pasar strip_tags a la entrada no protege una salida que acaba en un atributo o en JavaScript: el escapado depende del destino y se hace al pintar, como se explica en OWASP Top 10.

BOPLA: aceptar o exponer propiedades de más #

El OWASP API Security Top 10 de 2023 unió dos riesgos de su edición de 2019 en uno: API3:2023 Broken Object Property Level Authorization, BOPLA. La idea es que la autorización no termina en el objeto («¿puedes tocar este usuario?»), también llega a cada propiedad («¿puedes cambiar su rol?, ¿puedes ver su hash?»). Tiene dos caras:

Aceptar de más (escritura)

  • La antigua mass assignment
  • El cliente fija role, price o tenant_id
  • Se corrige con un DTO de entrada cerrado

Exponer de más (lectura)

  • La antigua excessive data exposure
  • La respuesta incluye hash, tokens o notas internas
  • Se corrige con un DTO de salida explícito

La segunda cara es traicionera porque el front «no lo usa»: el campo no se pinta, pero viaja en el JSON y cualquiera lo lee en las herramientas del navegador. Filtrar en el cliente no es filtrar.

En Laravel: $fillable, FormRequest y Resources #

Eloquent protege de serie: create() y update() solo asignan los atributos listados en $fillable. El agujero aparece cuando alguien lo desactiva para no pelearse con él y además pasa el cuerpo entero:

php · vulnerable 
<?php

final class User extends Authenticatable
{
    protected $guarded = [];
}

final class ProfileController
{
    public function update(Request $request): JsonResponse
    {
        $request->user()->update($request->all());

        return response()->json($request->user());
    }
}

Con $guarded = [] todo es asignable, y $request->all() trae lo que el cliente quiera. La versión corregida cierra las dos fronteras:

php · corregido 
<?php

final class User extends Authenticatable
{
    protected $fillable = ['name', 'locale'];

    protected $hidden = ['password', 'remember_token'];
}

final class UpdateProfileRequest extends FormRequest
{
    public function rules(): array
    {
        return [
            'name' => ['required', 'string', 'max:100'],
            'locale' => ['required', Rule::in(['es', 'en', 'fr'])],
        ];
    }
}

final class ProfileController
{
    public function update(UpdateProfileRequest $request): UserResource
    {
        $request->user()->update($request->validated());

        return new UserResource($request->user());
    }
}

final class UserResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        return [
            'id' => $this->id,
            'name' => $this->name,
            'locale' => $this->locale,
        ];
    }
}

Son tres capas, y cada una cubre un fallo distinto: validated() devuelve solo las claves con regla, $fillable frena lo que se cuele por otro camino y el JsonResource decide qué sale. $hidden es una red, no la lista de salida: si mañana añades una columna sensible, el Resource no la expone sin que nadie la escriba.

En Symfony: DTO con #[MapRequestPayload] #

En Symfony el riesgo típico es deserializar el JSON directamente sobre la entidad con OBJECT_TO_POPULATE: el Serializer llama a todo setter que encuentre, setRoles() incluido. Los formularios son más seguros, porque solo mapean los campos declarados en el FormType y rechazan los extra mientras no actives allow_extra_fields. Para una API JSON, lo limpio es un DTO:

php · corregido 
<?php

final readonly class UpdateProfileInput
{
    public function __construct(
        #[Assert\NotBlank]
        #[Assert\Length(max: 100)]
        public string $name,
        #[Assert\Choice(choices: ['es', 'en', 'fr'])]
        public string $locale,
    ) {
    }
}

final class ProfileController extends AbstractController
{
    #[Route('/api/me', methods: ['PATCH'])]
    public function update(
        #[CurrentUser] User $user,
        #[MapRequestPayload] UpdateProfileInput $input,
        EntityManagerInterface $entityManager,
    ): JsonResponse {
        $user->rename($input->name);
        $user->changeLocale($input->locale);
        $entityManager->flush();

        return $this->json(ProfileOutput::fromUser($user));
    }
}

#[MapRequestPayload] deserializa el cuerpo al DTO, lo valida y responde con un 422 si falla. Un is_admin en el JSON no tiene dónde caer porque el DTO no lo declara. Si prefieres que un campo desconocido sea un error en vez de ignorarse, pasa allow_extra_attributes a false en el contexto de serialización. Y la salida usa su propio DTO, ProfileOutput, en vez de serializar la entidad.

Errores típicos #

Lo que se cuela en revisión

  • Validar y luego usar all(). La FormRequest pasa, pero se persiste el cuerpo completo, con los campos sin regla.
  • Lista de prohibidos. $guarded = ['is_admin'] funciona hasta que alguien añade la columna plan. Las listas permitidas fallan cerradas; las prohibidas, abiertas.
  • Arrays anidados sin forma. Con la regla 'address' => 'array', validated() devuelve el array entero con cualquier subclave. Usa 'array:street,city' y valida cada clave.
  • Devolver la entidad tal cual. Funciona, pero cualquier columna nueva sale en la API sin que nadie lo decida.
  • Confiar en la validación del front. Es comodidad para el usuario, no seguridad.

Validar no es autorizar

Un role válido de la lista permitida sigue siendo un problema si quien lo cambia no es administrador. Que un campo sea correcto y que este usuario pueda tocarlo son dos comprobaciones distintas; la segunda tiene su propia lección en este curso.

Cómo detectarlo y testearlo #

Busca primero los patrones que abren la puerta. No todos son fallos, pero cada aparición merece una mirada:

bash · búsqueda en el repo 
grep -rnE 'guarded = \[\]|unguard\(|->all\(\)|OBJECT_TO_POPULATE' src app

Después, fija el comportamiento con un test que haga lo que haría el atacante: mandar el campo prohibido y comprobar que no cambió nada ni sale en la respuesta.

php · tests/Feature/ProfileUpdateTest.php 
<?php

public function test_profile_update_ignores_admin_flag(): void
{
    $user = User::factory()->create(['is_admin' => false]);

    $this->actingAs($user)
        ->patchJson('/api/me', ['name' => 'Ana', 'locale' => 'es', 'is_admin' => true])
        ->assertOk()
        ->assertJsonMissingPath('data.is_admin');

    $this->assertFalse($user->fresh()->is_admin);
}

En Laravel hay además una alarma gratuita para desarrollo: Model::preventSilentlyDiscardingAttributes() lanza una MassAssignmentException cuando intentas asignar un atributo que no está en $fillable, en vez de descartarlo en silencio. Actívalo fuera de producción y verás enseguida qué endpoints reciben campos que no esperabas.

Cuándo aplicarlo #

DTO de entrada y salida cuando…

  • El endpoint escribe en una entidad con campos sensibles: rol, precio, tenant
  • La API es pública o la consumen terceros
  • La entidad tiene columnas que el cliente no debe ver
  • El mismo modelo se edita desde pantallas con permisos distintos

Basta con algo más ligero cuando…

  • Es un panel interno donde todos los campos son editables por igual
  • La entidad es plana y sin campos sensibles: una etiqueta, una nota
  • Es un prototipo que no va a ver tráfico real

La alternativa ligera no es «sin protección»: en Laravel, una FormRequest con validated() y un $fillable bien puesto; en Symfony, un FormType con los campos justos. Lo que nunca está justificado es $guarded = [] combinado con $request->all(). Para lo que pasa después, sesiones y tokens, sigue en autenticación.

Resumen #

Lo que te llevas

  • El cliente puede enviar cualquier campo: tu backend decide cuáles acepta, con una lista permitida.
  • Valida en el borde tipo, rango y lista permitida, y rechaza; el escapado va en la salida, según el destino.
  • BOPLA (API3:2023) tiene dos caras: aceptar propiedades de más y exponer propiedades de más.
  • Laravel: validated(), $fillable y un JsonResource. Symfony: DTO con #[MapRequestPayload] y DTO de salida.
  • Un test que manda is_admin: true y comprueba que no cambió nada vale más que cualquier revisión.
