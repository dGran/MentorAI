Cron: tareas programadas dentro de Postgres

Limpiar datos viejos cada noche, mandar un resumen semanal, recalcular estadísticas cada cinco minutos. En un backend clásico necesitas un servidor con crontab o un planificador externo. En Supabase la base de datos programa sus propias tareas, sin nada más que mantener.

Ya sabes ejecutar código bajo demanda con Edge Functions. Esta lección lo ejecuta a una hora fija: tareas que corren solas dentro de Postgres, ya sean SQL puro o una llamada HTTP a una función.

Qué es Supabase Cron #

Supabase Cron es la extensión **pg_cron** de Postgres con una interfaz en el panel (Integrations → Cron). Al activarla, crea el esquema cron, y un proceso de fondo dentro de Postgres lanza cada tarea cuando le toca.

Que el planificador viva en la base de datos tiene ventajas claras: no hay otro servidor que se pueda caer o quedarse sin desplegar, una tarea SQL corre sin latencia de red, y las tareas son filas de una tabla que puedes consultar y versionar. El precio es que cada tarea consume recursos de tu base de datos: una tarea pesada a las 9 de la mañana compite con tus usuarios.

Cuándo: la sintaxis de cron #

Cada tarea tiene un nombre, una programación y un comando. La programación usa los cinco campos clásicos de cron, en UTC:

ProgramaciónSignifica
*/5 * * * *Cada 5 minutos
0 3 * * *Todos los días a las 03:00 UTC
30 3 * * 6Los sábados a las 03:30 UTC
0 9 * * 1-5De lunes a viernes a las 09:00 UTC
0 0 1 * *El día 1 de cada mes a medianoche UTC
30 secondsCada 30 segundos (de 1 a 59 segundos)

Los cinco campos son minuto, hora, día del mes, mes y día de la semana. La forma N seconds no es cron estándar: es una extensión de pg_cron para intervalos por debajo del minuto.

La hora es UTC

0 9 * * * son las 9:00 UTC, que en España son las 10 en invierno y las 11 en verano. Si una tarea tiene que correr a una hora local fija todo el año, o asumes ese desfase o compruebas la hora local dentro de la tarea.

Tareas en SQL #

La forma más directa: la tarea ejecuta SQL dentro de la base de datos. Si las notas tienen una papelera (una columna deleted_at que se rellena al borrar), vaciarla es una línea:

sql · vaciar la papelera cada noche 
select cron.schedule(
  'purge-trashed-notes',
  '0 3 * * *',
  $$ delete from public.notes where deleted_at < now() - interval '30 days' $$
);
sql · llamar a una función o procedimiento 
select cron.schedule('refresh-stats', '*/10 * * * *', 'select private.refresh_notebook_stats()');

Las tareas corren como el usuario que las creó (normalmente postgres), así que RLS no se aplica: la tarea ve y modifica todas las filas. Es lo que quieres para mantenimiento, y es una razón más para que el SQL de una tarea sea corto y revisado.

Tareas que llaman a una Edge Function #

Cuando la tarea necesita algo que no es SQL (mandar emails, llamar a una API), la tarea hace una petición HTTP a una Edge Function con pg_net. La función la llama un servidor, no un usuario, así que se autentica con la clave secreta, que no debe quedar escrita en el texto de la tarea: va en Vault, el almacén cifrado de secretos de Supabase.

sql · guardar la URL y la clave en Vault (una vez) 
select vault.create_secret('https://abcdefghijklmnop.supabase.co', 'project_url');
select vault.create_secret('sb_secret_xxxxxxxx', 'cron_secret_key');
sql · la tarea: resumen semanal cada lunes a las 7:00 UTC 
select cron.schedule(
  'weekly-digest',
  '0 7 * * 1',
  $$
  select net.http_post(
    url := (select decrypted_secret from vault.decrypted_secrets where name = 'project_url')
           || '/functions/v1/weekly-digest',
    headers := jsonb_build_object(
      'Content-Type', 'application/json',
      'apikey', (select decrypted_secret from vault.decrypted_secrets where name = 'cron_secret_key')
    ),
    body := jsonb_build_object('scheduled_at', now()),
    timeout_milliseconds := 5000
  );
  $$
);

En la función, el modo auth: "secret" del envoltorio de Edge Functions acepta solo llamadas con la clave secreta, y hay que desactivar verify_jwt para ella porque no llega un JWT de usuario. Puedes crear una clave secreta dedicada solo a Cron y revocarla sin afectar al resto.

Que la tarea «salga bien» no significa que la función funcionara

net.http_post solo encola la petición y devuelve un id; la tarea termina en milisegundos y queda registrada como correcta. Si la función respondió un 500, eso está en net._http_response, no en el historial de Cron. Para tareas importantes, la propia función debe registrar su resultado o avisar cuando falla.

Vigilar y gestionar las tareas #

Las tareas son filas de cron.job y cada ejecución deja una fila en cron.job_run_details:

sql · últimas ejecuciones de una tarea 
select status, return_message, start_time, end_time
from cron.job_run_details
where jobid = (select jobid from cron.job where jobname = 'purge-trashed-notes')
order by start_time desc
limit 10;
sql · cambiar, pausar y borrar 
select cron.alter_job(
  job_id := (select jobid from cron.job where jobname = 'refresh-stats'),
  schedule := '*/15 * * * *'
);

select cron.alter_job(job_id := (select jobid from cron.job where jobname = 'refresh-stats'), active := false);

select cron.unschedule('refresh-stats');

El historial no se limpia solo. Una tarea cada 30 segundos genera casi 3.000 filas al día; al cabo de meses, la tabla pesa. La solución es, cómo no, otra tarea:

sql · limpiar el historial de Cron 
select cron.schedule(
  'purge-cron-history',
  '0 4 * * *',
  $$ delete from cron.job_run_details where end_time < now() - interval '7 days' $$
);

Solapes, límites y tareas idempotentes #

pg_cron no lanza dos ejecuciones de la misma tarea a la vez: si una ejecución no ha terminado cuando toca la siguiente, la siguiente espera a que acabe. Así no se pisan, pero una tarea que tarda más que su intervalo va acumulando retraso.

Supabase recomienda no tener más de 8 tareas ejecutándose a la vez y que ninguna dure más de 10 minutos. Si una tarea necesita más, divídela: procesa un lote por ejecución en lugar de todo de golpe.

Y escribe cada tarea para que ejecutarla dos veces no haga daño: borrar lo que tiene más de 30 días se puede repetir sin problema; «mandar el resumen de esta semana» necesita guardar que ya se mandó. Un reinicio de la base de datos en mal momento, o una ejecución manual para probar, no deben duplicar emails. Idempotencia cuenta las técnicas.

Las tareas también van en migraciones #

Una tarea creada a mano en el panel de producción es un cambio que no está en git, igual que una columna creada con clics. Escribe cron.schedule en una migración: si se llama con un nombre que ya existe, actualiza esa tarea en lugar de crear otra, así que la migración se puede aplicar en cada entorno sin duplicados. Los secretos de Vault, en cambio, no van en migraciones (acabarían en git): se crean a mano en cada entorno o desde tu CI.

Cuándo aplicarlo #

NecesidadSolución
Mantenimiento de datos: borrar, archivar, recalcularTarea Cron con SQL
Algo periódico que sale de la base de datos: emails, informes, APIsTarea Cron que llama a una Edge Function
Procesar trabajos a medida que llegan, con reintentosUna cola, con Cron como despertador del worker
Algo que debe pasar justo cuando cambia una filaUn trigger o un webhook, no un Cron que pregunta cada minuto
Tareas de minutos u horasDivididas en lotes, o fuera de la base de datos

Resumen #

Lo que te llevas

  • Supabase Cron es pg_cron: las tareas viven en cron.job, su historial en cron.job_run_details, y la programación va en UTC.
  • Las tareas SQL corren como su dueño y no pasan por RLS; las que salen fuera llaman a una Edge Function con pg_net y la clave secreta guardada en Vault.
  • net.http_post solo encola la petición: el éxito de la tarea no dice nada de la respuesta de la función.
  • Una tarea no se solapa consigo misma; la siguiente ejecución espera. Máximo recomendado: 8 a la vez y 10 minutos cada una.
  • Tareas idempotentes, historial que se limpia con otra tarea y cron.schedule en migraciones.
