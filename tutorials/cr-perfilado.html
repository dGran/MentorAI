Perfilado: dónde se va el tiempo de verdad

Ya sabes que el p95 de un endpoint son 2 segundos. Ahora falta la pregunta cara: ¿en qué se van? La intuición acierta menos de la mitad de las veces, y el perfilador es la herramienta que convierte «yo creo que es la consulta de productos» en «el 42 % del tiempo está en deserializar el JSON de la caché».

Dos formas de perfilar #

Todos los perfiladores caen en una de dos categorías, y la diferencia decide cuál puedes enchufar en producción:

Instrumentado

  • Registra cada entrada y salida de función
  • Datos exactos: cuentas y tiempos reales
  • Sobrecarga enorme, a veces ×10 o más
  • Xdebug en modo profile
  • Para local o un entorno de pruebas

Por muestreo

  • Interrumpe cada X ms y anota la pila
  • Datos estadísticos: aproximados pero fiables
  • Sobrecarga pequeña, del orden del 1-2 %
  • Excimer, SPX, los perfiladores continuos
  • Se puede dejar puesto en producción

El perfilador instrumentado distorsiona lo que mide

Al cobrar un coste fijo por llamada, hincha desproporcionadamente las funciones pequeñas que se llaman muchas veces y disimula las que hacen esperas de red. Un perfil de Xdebug puede señalarte un getter trivial como culpable mientras la consulta de 800 ms parece barata. Sirve para ver la forma del código, no para repartir culpas de tiempo real.

Tiempo propio y tiempo total #

Es la distinción que hace útil un perfil, y la que más gente ignora al mirarlo por primera vez:

ColumnaQué mideCuándo mirarla
Tiempo total (inclusive)La función y todo lo que llama por debajoPara saber por dónde bajar
Tiempo propio (self / exclusive)Solo lo que ejecuta ella mismaPara saber qué arreglar

Tu controlador siempre tendrá el 100 % del tiempo total y casi nada de propio: es un reparto, no un culpable. Se navega el árbol por tiempo total hasta encontrar el punto donde el tiempo se concentra, y ahí se mira el propio. Y si una función tiene poco tiempo propio pero un número de llamadas absurdo, el problema no es ella: es quien la llama en un bucle.

El gráfico de llamas se lee a lo ancho

En un flame graph, el eje horizontal no es el tiempo: es la proporción. Lo alto solo significa pilas profundas. Lo que buscas son las mesetas anchas: bloques que ocupan mucho a lo ancho y no se subdividen, porque ahí se está yendo el tiempo de verdad.

Los cuatro sospechosos #

Después de mirar unos cuantos perfiles, los hallazgos se repiten. Estos cuatro cubren la gran mayoría:

1 Lo que se llama 400 vecesCasi siempre un N+1: consultas, llamadas HTTP o lecturas de caché en bucle
2 La espera que no es tuyaUna llamada de red o una consulta: no hay micro-optimización que la arregle
3 Lo que se recalcula cada vezSerializar, parsear, construir el contenedor: candidato natural a caché
4 Lo que no debería estar ahíTrabajo que se hace y se descarta, o que no hacía falta en esta petición

El cuarto es el más rentable y el que menos se busca: no optimizar, sino no hacerlo.

Perfilar solo lo que interesa #

No hace falta un producto de pago para empezar. Con un perfilador por muestreo puedes activar la captura solo para las peticiones lentas, que son las que quieres estudiar:

php · PerfiladorDeLentas.php 
<?php

declare(strict_types=1);

final class PerfiladorDeLentas
{
    private const UMBRAL_MS = 500;
    private const PERIODO_MUESTREO_MS = 10;

    public function alEmpezar(): void
    {
        $this->perfilador = new ExcimerProfiler();
        $this->perfilador->setPeriod(self::PERIODO_MUESTREO_MS / 1000);
        $this->perfilador->start();
        $this->inicio = hrtime(true);
    }

    public function alTerminar(string $ruta): void
    {
        $this->perfilador->stop();

        $duracionMs = (hrtime(true) - $this->inicio) / 1e6;

        if ($duracionMs < self::UMBRAL_MS) {
            return;
        }

        $this->almacen->guardar($ruta, $this->perfilador->getLog()->formatCollapsed());
    }
}

Ese formatCollapsed() produce el formato que comen los generadores de gráficos de llamas. Guardando solo lo que pasa de medio segundo tienes un archivo de casos interesantes sin llenar el disco con las diez mil peticiones que fueron bien.

El perfilador no ve lo que pasa fuera de PHP

Si el tiempo está en la base de datos, el perfil te dirá «800 ms en PDOStatement::execute» y ahí se acaba su historia. Para saber por qué esa consulta tarda hace falta la otra herramienta, que es EXPLAIN: la lección siguiente del curso.

Cuándo aplicarlo #

Perfila cuando…

  • Sabes que algo es lento pero no dónde
  • La lentitud no está en una consulta obvia
  • Has optimizado lo evidente y sigue sin cuadrar
  • Quieres saber qué se ejecuta de más antes de refactorizar

No hace falta cuando…

  • El log de consultas lentas ya te señala una con nombre y apellidos
  • Las trazas distribuidas ya localizan el tramo culpable
  • El problema es de red o de espera en cola, no de CPU

Resumen #

Lo que te llevas

  • Instrumentado da datos exactos y distorsiona el reparto; por muestreo da datos aproximados y se puede dejar en producción.
  • Se navega por tiempo total para bajar por el árbol y se mira el tiempo propio para saber qué arreglar.
  • Un gráfico de llamas se lee a lo ancho: buscas mesetas, no picos. Lo alto solo significa pilas profundas.
  • El hallazgo más rentable no es qué optimizar, sino qué trabajo no hacía falta hacer en esa petición.
  • Guardar el perfil solo de las peticiones que pasan de un umbral te da un archivo de casos interesantes sin llenar el disco.
