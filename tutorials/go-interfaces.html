Interfaces: duck typing estático

Qué es una interfaz en Go

Una interfaz es un conjunto de firmas de método. Cualquier tipo que tenga esos métodos implementa la interfaz — automáticamente, sin declararlo.

type Notificador interface {
    Enviar(destinatario, mensaje string) error
}

Cualquier tipo con un método Enviar(string, string) error implementa Notificador. El compilador verifica esto en tiempo de compilación; no hay que declarar nada extra.

Implementación implícita

Tres implementaciones distintas de la misma interfaz:

type EmailNotificador struct {
    Host string
    Port int
}

func (e *EmailNotificador) Enviar(destinatario, mensaje string) error {
    // lógica de envío por email...
    return nil
}

type SMSNotificador struct {
    ApiKey string
}

func (s *SMSNotificador) Enviar(destinatario, mensaje string) error {
    // lógica de envío por SMS...
    return nil
}

type LogNotificador struct{}   // para tests

func (l LogNotificador) Enviar(destinatario, mensaje string) error {
    fmt.Printf("[LOG] Para: %s — %s\n", destinatario, mensaje)
    return nil
}

Ninguna de las tres declara implements Notificador. Las tres lo implementan porque tienen el método correcto. El polimorfismo llega solo:

func notificarPedido(n Notificador, pedidoId int) error {
    mensaje := fmt.Sprintf("Tu pedido #%d está listo", pedidoId)

    return n.Enviar("cliente@ejemplo.com", mensaje)
}

// Funciona con cualquier implementación:
notificarPedido(&EmailNotificador{Host: "smtp.gmail.com"}, 42)
notificarPedido(&SMSNotificador{ApiKey: "xxx"}, 42)
notificarPedido(LogNotificador{}, 42)   // en tests

Comparación con PHP

PHP: implementación explícita

interface Notificador {
    public function enviar(string $dest, string $msg): void;
}

class EmailNotificador implements Notificador {
    public function enviar(string $dest, string $msg): void {
        // ...
    }
}

// El consumidor declara la interfaz como tipo:
function notificar(Notificador $n, int $id): void {
    $n->enviar("c@e.com", "Pedido #$id listo");
}

Go: implementación implícita

type Notificador interface {
    Enviar(dest, msg string) error
}

type EmailNotificador struct{ Host string }

// Sin "implements": el método es suficiente
func (e *EmailNotificador) Enviar(dest, msg string) error {
    return nil
}

func notificar(n Notificador, id int) error {
    return n.Enviar("c@e.com", fmt.Sprintf("Pedido #%d listo", id))
}

La diferencia práctica más importante: en Go puedes hacer que tipos de librerías externas (que no controlas) implementen tus interfaces, porque la implementación no requiere que el tipo lo declare. Defines la interfaz donde la necesitas, no donde defines el tipo.

Principio de diseño en Go: define las interfaces donde las consumes, no donde defines la implementación. Las interfaces pequeñas (1-2 métodos) son más reutilizables y fáciles de satisfacer que las grandes.

Las interfaces de la stdlib

La biblioteca estándar de Go está construida sobre interfaces pequeñas y precisas. Las más importantes que verás continuamente:

InterfazMétodoQué significa
io.ReaderRead(p []byte) (n int, err error)Cualquier fuente de bytes legible
io.WriterWrite(p []byte) (n int, err error)Cualquier destino de bytes
errorError() stringCualquier error
fmt.StringerString() stringRepresentación de texto del tipo
http.HandlerServeHTTP(w ResponseWriter, r *Request)Cualquier manejador HTTP

Ejemplo: implementar fmt.Stringer hace que tu tipo se imprima de forma personalizada con fmt.Println:

type Producto struct {
    Nombre string
    Precio float64
}

func (p Producto) String() string {
    return fmt.Sprintf("%s (%.2f€)", p.Nombre, p.Precio)
}

p := Producto{"Mesa", 299.99}
fmt.Println(p)   // Mesa (299.99€) — gracias a Stringer

Type assertion y type switch

Cuando tienes un valor de tipo interfaz y necesitas acceder al tipo concreto subyacente, usas una type assertion:

var n Notificador = &EmailNotificador{Host: "smtp.gmail.com"}

// Forma segura (recomendada)
email, esEmail := n.(*EmailNotificador)

if esEmail {
    fmt.Println("puerto:", email.Port)
}

Cuando el tipo concreto puede ser uno de varios, el type switch es más limpio:

func describir(n Notificador) string {
    switch impl := n.(type) {
    case *EmailNotificador:
        return fmt.Sprintf("email vía %s", impl.Host)
    case *SMSNotificador:
        return "SMS"
    case LogNotificador:
        return "log (solo para tests)"
    default:
        return "implementación desconocida"
    }
}

La interfaz vacía: any

Una interfaz sin métodos la implementa cualquier tipo. Go la llama any (alias de interface{} desde Go 1.18):

func imprimir(v any) {
    fmt.Println(v)
}

imprimir(42)
imprimir("hola")
imprimir([]string{"a", "b"})   // todo funciona

any es el equivalente del tipado dinámico de PHP: flexible pero sin seguridad de tipos en tiempo de compilación. Úsala cuando genuinamente necesitas tratar valores de tipos arbitrarios (serialización, logging genérico). Si te encuentras usándola con frecuencia, suele indicar que el diseño con tipos concretos o interfaces específicas sería más robusto.

Resumen

  • Una interfaz es un conjunto de firmas de método. Un tipo la implementa si tiene esos métodos: sin implements, sin declaración explícita.
  • Define interfaces donde las consumes (en el paquete que las necesita), no donde defines la implementación. Preferir interfaces pequeñas.
  • La stdlib usa interfaces de 1-2 métodos: io.Reader, io.Writer, error, fmt.Stringer. Implementarlas conecta tu tipo con el ecosistema de Go.
  • Type assertion (v.(Tipo)) extrae el valor concreto de una interfaz; usa la forma de dos valores (v, ok := i.(T)) para evitar panics.
  • any (interfaz vacía) acepta cualquier tipo pero pierde seguridad de tipos. Usarla con moderación.
