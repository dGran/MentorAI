Enums e inmutabilidad a fondo

El enum de tres casos y la clase readonly ya los conoces. Lo difícil empieza cuando el estado llega mal escrito desde la base de datos, cuando añades un caso nuevo y cuando quieres cambiar un objeto que no se puede cambiar.

Un enum que solo sustituye a tres constantes es la mitad del trabajo. La otra mitad es decidir qué pasa cuando llega un valor que no existe, quién sabe las reglas de cada caso y cómo cambia un objeto que no puede cambiar. Ahí es donde el código moderno se separa del que solo lo parece.

Donde acaba la versión básica #

En Tipos de clases en PHP viste qué es un enum, que puede tener métodos y que una clase readonly sirve para un value object como Dinero. Esta lección empieza justo ahí.

El estado de un pedido llega como texto de la base de datos, de un formulario o de una API ajena. Si lo tratas como string, un 'pendng' con una errata viaja por cinco capas y falla lejos de donde entró. La idea de fondo es convertir en la frontera: el texto se vuelve enum al entrar y vuelve a texto al salir. Dentro, solo circulan tipos que no admiten valores imposibles.

Backed enums: from frente a tryFrom #

Un backed enum asocia a cada caso un valor escalar, string o int, que es lo que se guarda y se envía. Para convertir ese valor en caso hay dos métodos, y la diferencia entre ellos es una decisión de diseño, no de estilo:

php · OrderStatus.php 
<?php

declare(strict_types=1);

enum OrderStatus: string
{
    case Pending = 'pending';
    case Paid = 'paid';
    case Shipped = 'shipped';
    case Cancelled = 'cancelled';
}

$fromDatabase = OrderStatus::from('paid');

$input = 'pendng';
$fromRequest = OrderStatus::tryFrom($input);

if ($fromRequest === null) {
    echo "Estado desconocido: {$input}\n";
}

$allowedValues = array_map(fn (OrderStatus $status) => $status->value, OrderStatus::cases());

echo implode(', ', $allowedValues), "\n";
MétodoSi el valor no existeÚsalo cuando
from()Lanza ValueErrorEl valor tiene que ser válido: viene de tu propia base de datos. Si no lo es, hay un bug y quieres enterarte.
tryFrom()Devuelve nullEl valor puede ser inválido de forma legítima: entrada del usuario o de un tercero. Lo tratas como error de validación.

cases() devuelve todos los casos en el orden en que se declaran. Úsalo para el desplegable o el mensaje de error con los valores admitidos: si añades un caso, se actualizan solos. Con strict_types activo (lo tienes en Tipado estricto), from(1) sobre un enum de string es un TypeError, no una conversión silenciosa.

Métodos, constantes e interfaces #

Un enum no puede tener propiedades, pero sí métodos, métodos estáticos, constantes e interfaces. Eso basta para que las reglas de cada estado vivan junto al estado, en vez de repartidas en if por los servicios:

php · OrderStatus.php (con comportamiento) 
<?php

declare(strict_types=1);

interface HasLabel
{
    public function label(): string;
}

enum OrderStatus: string implements HasLabel
{
    case Pending = 'pending';
    case Paid = 'paid';
    case Shipped = 'shipped';
    case Cancelled = 'cancelled';

    public const INITIAL = self::Pending;

    public function label(): string
    {
        return match ($this) {
            self::Pending => 'Pendiente de pago',
            self::Paid => 'Pagado',
            self::Shipped => 'Enviado',
            self::Cancelled => 'Cancelado',
        };
    }

    public function canTransitionTo(self $next): bool
    {
        return in_array($next, $this->allowedTransitions(), true);
    }

    /** @return list<self> */
    private function allowedTransitions(): array
    {
        return match ($this) {
            self::Pending => [self::Paid, self::Cancelled],
            self::Paid => [self::Shipped, self::Cancelled],
            self::Shipped, self::Cancelled => [],
        };
    }
}

var_dump(OrderStatus::INITIAL->canTransitionTo(OrderStatus::Shipped));

La constante INITIAL da nombre propio al estado inicial. La interfaz HasLabel deja que una vista pinte cualquier enum etiquetable sin conocerlo. Y la máquina de estados cabe en un método privado que se lee de un vistazo.

match exhaustivo, sin default #

Los dos match de arriba no tienen rama default, y es a propósito. Si mañana alguien añade case Refunded, un match que no lo cubre lanza UnhandledMatchError en cuanto llega ese caso, en vez de devolver una etiqueta equivocada sin avisar. Un default se tragaría el caso nuevo para siempre.

Esperar a que falle en producción no es el plan: el análisis estático lo detecta antes. PHPStan, a partir del nivel 4, informa de cada match sobre un enum que deja casos sin cubrir. Esto es lo que dice tras añadir case Refunded al enum de arriba:

bash · salida de PHPStan 2.x 
vendor/bin/phpstan analyse src --level=4

         OrderStatus::Refunded
         🪪  match.unhandled
  38     Match expression does not handle remaining value:
         OrderStatus::Refunded
         🪪  match.unhandled
 ------ ---------------------------------------------------

Añadir un caso se convierte en una lista de tareas que te da la herramienta. Cómo subir de nivel sin ahogarte en errores lo verás en PHPStan a fondo.

Persistir un enum: columna y mapeo #

Lo que se guarda es el value, nunca el name. El nombre del caso es código y lo renombrarás algún día; el valor es un contrato con la base de datos y con quien consuma tu API. Por eso json_encode() de un backed enum emite su valor, y por eso un enum sin valor no se puede serializar a JSON.

Para la columna, un VARCHAR corto es la opción menos frágil. El ENUM nativo de MySQL obliga a un ALTER TABLE por cada caso nuevo; si quieres que la base de datos también rechace valores, un CHECK también pide un ALTER, pero es estándar y no reordena ni convierte valores (MySQL lo aplica desde la 8.0.16).

sql · migración 
ALTER TABLE orders
    ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'pending';

Los dos ORM habituales convierten en la frontera por ti. En Doctrine, la columna declara el enum con enumType y la entidad recibe el caso, no el texto. En Laravel, un cast hace lo mismo con Eloquent:

php · Doctrine y Laravel 
#[ORM\Column(type: 'string', length: 20, enumType: OrderStatus::class)]
private OrderStatus $status = OrderStatus::Pending;

protected function casts(): array
{
    return [
        'status' => OrderStatus::class,
    ];
}

Un dato desconocido en la base de datos es un bug

Ambos mapeos usan from(): si una fila trae 'refunded' antes de desplegar ese caso, la carga falla: Laravel lanza el ValueError y Doctrine lo envuelve en una MappingException. Es lo correcto, y obliga a desplegar primero el código y después los datos.

readonly a fondo #

Una propiedad readonly se asigna una sola vez, desde el ámbito de la clase (o de una hija, desde PHP 8.4), y después cualquier escritura lanza Error. Lleva siempre tipo y no admite valor por defecto. Una clase readonly (PHP 8.2) solo ahorra repetir la palabra en cada propiedad.

Lo que readonly congela es la referencia, no lo que hay detrás. Un array readonly no admite $bag->items[] = 2, pero si la propiedad guarda un objeto mutable, como un DateTime o un ArrayObject, ese objeto sigue cambiando por dentro. Solo es inmutable de verdad si todo lo que contiene lo es: DateTimeImmutable, otros value objects, escalares.

El método with que clona #

Un objeto inmutable no cambia: produce otro, con un método withX() que devuelve una copia con un campo distinto. La versión intuitiva, clonar y reasignar, choca con readonly:

php · Money.php (no funciona) 
<?php

declare(strict_types=1);

final readonly class Money
{
    public function __construct(
        public int $amount,
        public string $currency,
    ) {
    }

    public function withAmount(int $amount): self
    {
        $copy = clone $this;
        $copy->amount = $amount;

        return $copy;
    }
}

(new Money(100, 'EUR'))->withAmount(250);

Falla con Cannot modify readonly property Money::$amount: la copia ya nace con la propiedad inicializada. Hay tres salidas, cada una con su letra pequeña:

  • Construir uno nuevo: return new self($amount, $this->currency);. Funciona en cualquier versión y pasa otra vez por el constructor, así que la validación se repite. Es la opción por defecto.
  • Reinicializar en __clone(): desde PHP 8.3, una propiedad readonly se puede reasignar dentro de __clone(). Sirve para la copia profunda de un objeto interno, pero __clone() no recibe argumentos, así que no resuelve el with.
  • Clonar con propiedades: PHP 8.5 acepta clone($this, ['amount' => $amount]), que modifica la copia mientras se crea. Ojo: no llama al constructor, así que la validación que vivía allí no se ejecuta.

Comparar por valor #

Dos value objects con los mismos datos son el mismo valor, aunque sean instancias distintas. === compara identidad, así que dos Money(100, 'EUR') recién creados no son idénticos. == compara clase y propiedades, pero con comparación débil:

php · ProductCode.php 
<?php

declare(strict_types=1);

final readonly class ProductCode
{
    public function __construct(public string $value)
    {
    }

    public function equals(self $other): bool
    {
        return $this->value === $other->value;
    }
}

$first = new ProductCode('1e1');
$second = new ProductCode('10');

var_dump($first == $second);
var_dump($first->equals($second));

El primer var_dump dice true: con ==, dos strings numéricos se comparan como números. Un método equals() explícito decide qué significa «igual» para ese valor (mayúsculas, normalización, moneda). Los enums no lo necesitan: cada caso es una instancia única y === basta.

Errores típicos #

Lo que se cuela en las revisiones

  • from() con entrada del usuario. Un valor raro en la petición acaba en un 500 en vez de en un 422.
  • Guardar el name. Renombrar Paid a Settled rompe todas las filas existentes.
  • default en un match sobre enum. El caso nuevo cae en la rama genérica y nadie se entera.
  • readonly sobre un objeto mutable. Un DateTime dentro de un value object «inmutable» se puede seguir modificando.
  • Validar solo en el constructor y usar clone con propiedades. La copia se salta la validación.
  • Comparar value objects con ==. Funciona en los tests con datos limpios y falla con los raros.

Cómo comprobarlo #

PHPStan en nivel 4 o superior detecta los match incompletos y las escrituras sobre propiedades readonly fuera de la clase. Un test que recorre cases() y llama a label() en cada caso falla en cuanto un caso nuevo no tiene etiqueta. Y un test de ida y vuelta que guarda y recarga una entidad por cada caso confirma que la columna y el mapeo aceptan todos los valores, incluido el último que añadiste.

Cuándo aplicarlo #

Enum o value object cuando…

  • El conjunto de valores es cerrado y lo controla tu código: estados, tipos, canales
  • Cada valor arrastra reglas propias, como transiciones o etiquetas
  • Un dato con reglas viaja por varias capas: importes, emails, códigos
  • Quieres que un valor inválido no pueda ni construirse

No compensa cuando…

  • Los valores los dan de alta usuarios o administradores: provincias, categorías del catálogo
  • El dato es un escalar sin reglas que solo se muestra
  • Es una entidad con identidad y ciclo de vida: eso no es un value object

La alternativa sencilla

Si los valores cambian sin desplegar, una tabla de referencia con su clave foránea es mejor que un enum: añadir un caso no debería exigir un pull request. Y si un dato no tiene reglas, un string tipado basta hasta que aparezca la primera; ese es el momento de envolverlo, como propone Object Calisthenics.

Resumen #

Lo que te llevas

  • Convierte en la frontera: el texto se vuelve enum al entrar y vuelve a value al salir; dentro solo circulan casos.
  • from() para datos que tienen que ser válidos, tryFrom() para entrada que puede no serlo.
  • match sin default sobre un enum, y PHPStan nivel 4 para que un caso nuevo no pase desapercibido.
  • Persiste el value en un VARCHAR; el name es código y cambiará.
  • readonly congela la referencia; para un with, construye con new self, y si usas clone con propiedades (PHP 8.5) recuerda que no pasa por el constructor.
  • Compara value objects con un equals() explícito, no con ==.
