OpenTelemetry en PHP

El identificador de correlación te dice qué líneas de log son de la misma petición, pero no cuánto tardó cada salto. OpenTelemetry te da la línea de tiempo completa con un estándar que no te ata a ningún proveedor: instrumentas una vez y decides después dónde mirar.

En trazas distribuidas te quedaste a propósito en el identificador de correlación. Aquí das el paso siguiente: spans de verdad, exportados por un protocolo estándar a un backend que puedes levantar en tu portátil. Todo lo que verás se ha ejecutado con PHP 8.5, un collector y Jaeger en Docker.

Un SDK por proveedor #

Hasta hace poco, trazar significaba elegir proveedor primero: el agente de Datadog, el de New Relic, el SDK de Sentry. Cada uno con su API, sus nombres de atributo y su formato de envío. Cambiar de herramienta era reinstrumentar la aplicación entera, y mezclar dos (Sentry para errores, otra para latencia) era instrumentar dos veces.

OpenTelemetry separa esas dos decisiones. Tu código habla con una API neutral; un SDK la implementa; un protocolo común, OTLP, transporta los datos; y el destino se elige por configuración. Es el estándar de la CNCF que ya nombraba los tres pilares.

API, SDK, OTLP y collector #

Las piezas son cuatro y cada una tiene un motivo:

PiezaQué hacePor qué existe
APICrea spans y propaga contextoLas librerías instrumentan sin depender del SDK; sin SDK, todo es no-op
SDKMuestrea, agrupa en lotes y exportaLa política vive aquí, configurable con variables OTEL_*
OTLPEl protocolo de envío (HTTP o gRPC)Un solo formato para cualquier destino
CollectorRecibe, procesa y reenvíaSaca de tu proceso PHP el muestreo, los reintentos y la elección de backend
1 PHP con el SDKSpans manuales o autoinstrumentados
2 OpenTelemetry CollectorLotes, muestreo por cola, métricas
3 Jaeger o TempoAlmacena y te deja buscar trazas

Cambiar de backend es tocar el collector, no la aplicación.

Spans manuales #

El SDK y el exportador son paquetes de Composer. Con OTEL_PHP_AUTOLOAD_ENABLED el SDK se configura solo a partir de variables de entorno, sin código de arranque:

bash · instalar y configurar 
composer require open-telemetry/sdk open-telemetry/exporter-otlp

export OTEL_PHP_AUTOLOAD_ENABLED=true
export OTEL_SERVICE_NAME=checkout
export OTEL_TRACES_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318

Antes tenías esto: un identificador inventado, una cabecera propia y nada de tiempos.

php · antes 
<?php

declare(strict_types=1);

$idTraza = $_SERVER['HTTP_X_TRACE_ID'] ?? bin2hex(random_bytes(16));
$logger->info('Consultando inventario', ['trace_id' => $idTraza]);
$cliente->get('http://inventario/stock/ABC-1', ['headers' => ['X-Trace-Id' => $idTraza]]);

Después, cada operación es un span con padre, duración y estado, y la cabecera es la estándar:

php · checkout.php 
<?php

declare(strict_types=1);

require __DIR__ . '/vendor/autoload.php';

use GuzzleHttp\Client;
use OpenTelemetry\API\Globals;
use OpenTelemetry\API\Trace\SpanKind;
use OpenTelemetry\API\Trace\StatusCode;

$tracer = Globals::tracerProvider()->getTracer('checkout');

$raiz = $tracer->spanBuilder('POST /checkout')
    ->setSpanKind(SpanKind::KIND_SERVER)
    ->startSpan();
$scopeRaiz = $raiz->activate();

try {
    $llamada = $tracer->spanBuilder('GET inventario')
        ->setSpanKind(SpanKind::KIND_CLIENT)
        ->startSpan();
    $scopeLlamada = $llamada->activate();

    try {
        $cabeceras = [];
        Globals::propagator()->inject($cabeceras);
        (new Client())->get('http://127.0.0.1:8099/stock/ABC-1', ['headers' => $cabeceras]);
    } finally {
        $scopeLlamada->detach();
        $llamada->end();
    }
} catch (Throwable $error) {
    $raiz->recordException($error);
    $raiz->setStatus(StatusCode::STATUS_ERROR, $error->getMessage());
    throw $error;
} finally {
    $scopeRaiz->detach();
    $raiz->end();
}

Fíjate en el patrón: activate() convierte el span en el contexto actual, así el siguiente que crees cuelga de él sin pasarlo a mano. El finally no es opcional: un scope sin detach() deja el contexto cambiado para el resto de la petición, y un span sin end() nunca se exporta.

Autoinstrumentación #

Escribir un span por cada consulta y llamada HTTP no escala. La extensión opentelemetry engancha funciones de PHP por fuera, y unos paquetes por librería usan esos ganchos para crear spans sin tocar tu código:

bash · extensión y paquete de Guzzle 
pecl install opentelemetry
docker-php-ext-enable opentelemetry
php --ri opentelemetry

composer require open-telemetry/opentelemetry-auto-guzzle

Con eso, un script de dos líneas que solo hace $cliente->get(...) produjo en Jaeger un span GET de tipo cliente con url.full, server.address y el código de estado, y el servicio de destino recibió su traceparent sin que nadie lo inyectara. Hay paquetes equivalentes para Symfony, Laravel, PDO y clientes PSR-18.

Autoinstrumentación

  • Cubre HTTP, base de datos y framework en minutos
  • Nombres y atributos según las convenciones semánticas
  • Necesita la extensión en todas las imágenes

Spans manuales

  • Solo ven lo que tú escribes
  • Son los únicos que conocen tu dominio: pedido, pasarela, regla de negocio
  • Funcionan sin extensión, solo con el SDK

No compiten: la autoinstrumentación pone el esqueleto y los spans manuales añaden lo que solo tu código sabe, como el id del pedido en un atributo.

Collector y Jaeger en Docker #

Jaeger 2 acepta OTLP directamente, así que el collector no es imprescindible para probar. Lo pones igual: en producción ahí vivirán el muestreo y las métricas.

yaml · compose.yaml 
services:
  jaeger:
    image: jaegertracing/jaeger:2.22.0
    ports:
      - "16686:16686"

  otel-collector:
    image: otel/opentelemetry-collector-contrib:0.162.0
    volumes:
      - ./otel-collector.yaml:/etc/otelcol-contrib/config.yaml:ro
    ports:
      - "4317:4317"
      - "4318:4318"
    depends_on:
      - jaeger
yaml · otel-collector.yaml 
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch: {}

exporters:
  otlp_grpc/jaeger:
    endpoint: jaeger:4317
    tls:
      insecure: true

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp_grpc/jaeger]

Con docker compose up -d, el script de arriba y un segundo servicio PHP escuchando en el 8099, la interfaz de Jaeger en http://localhost:16686 mostró una traza de tres spans de dos servicios:

bash · lo que se vio en Jaeger 
checkout   | POST /checkout   | 62a3e8e68b6a0d75 | sin padre        | 159 ms
checkout   | GET inventario   | db6adc0dc819bc98 | 62a3e8e68b6a0d75 | 158 ms
inventario | GET /stock/{sku} | 068a1a00c82f8be4 | db6adc0dc819bc98 | 120 ms

Con el stack de Grafana, Tempo ocupa el lugar de Jaeger: cambia el exportador del collector, no la aplicación.

Nombres que han cambiado

En el collector 0.162 el exportador otlp y el conector spanmetrics siguen funcionando, pero el arranque avisa de que son alias obsoletos de otlp_grpc y span_metrics. Muchos ejemplos de internet usan los nombres viejos.

traceparent entre servicios #

El formato de la cabecera ya lo viste en trazas distribuidas. Lo nuevo es quién la escribe: Globals::propagator(), que por defecto usa W3C Trace Context y Baggage. En la prueba, el checkout envió 00-5ff963b1…e290-db6adc0dc819bc98-01 y el inventario recibió exactamente eso: el segundo campo es el id de traza y el tercero el del span cliente, que pasa a ser el padre del span de servidor.

php · inventario/index.php 
<?php

declare(strict_types=1);

require __DIR__ . '/../vendor/autoload.php';

use OpenTelemetry\API\Globals;
use OpenTelemetry\API\Trace\SpanKind;

$contextoEntrante = Globals::propagator()->extract(getallheaders());

$span = Globals::tracerProvider()
    ->getTracer('inventario')
    ->spanBuilder('GET /stock/{sku}')
    ->setParent($contextoEntrante)
    ->setSpanKind(SpanKind::KIND_SERVER)
    ->startSpan();
$scope = $span->activate();

try {
    echo json_encode(['sku' => 'ABC-1', 'stock' => 3]);
} finally {
    $scope->detach();
    $span->end();
}

En una cola es lo mismo con otro transporte: inject() sobre las cabeceras del mensaje al publicar y extract() al consumir.

Muestreo #

La diferencia entre decidir al principio y al final ya está en trazas distribuidas. En OpenTelemetry cada una vive en un sitio: la decisión al principio, en el SDK; la de al final, en el collector.

bash · muestreo en el SDK 
export OTEL_TRACES_SAMPLER=parentbased_traceidratio
export OTEL_TRACES_SAMPLER_ARG=0.1

Con 10.000 spans raíz se quedaron 969, el 10 % previsto. Lo importante es el prefijo parentbased_: un span hijo de un traceparent con flag 01 se muestreó siempre. Con traceidratio a secas, ese mismo hijo se descartó aunque el servicio anterior ya hubiera guardado su parte: trazas con agujeros. Sin configurar nada, el SDK guardó las 10.000.

El muestreo por cola lo hace el procesador tail_sampling del collector. Con esta política, de 400 trazas lanzadas en dos tandas Jaeger guardó 31: los dos errores, las dos lentas y unas cuantas normales al azar:

yaml · otel-collector.yaml (procesador) 
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: errores
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: lentas
        type: latency
        latency:
          threshold_ms: 500
      - name: resto
        type: probabilistic
        probabilistic:
          sampling_percentage: 5

Para que funcione, todos los spans de una traza tienen que llegar al mismo collector. Con varias réplicas, eso exige repartir por id de traza delante.

SLI desde las trazas #

Qué es un SLO, el error budget y cómo alertar por ritmo de consumo está en Alerting. Las trazas aportan la materia prima: cada span de servidor es una petición con duración y estado, medida donde la vive el usuario.

El conector span_metrics del collector convierte spans en métricas de Prometheus. La trampa está en el orden: si cuentas después del muestreo por cola, guardas el 100 % de los errores y el 5 % del resto, y la tasa de error sale inflada. Por eso va en un pipeline propio que recibe todos los spans:

yaml · otel-collector.yaml (pipelines) 
connectors:
  span_metrics:
    histogram:
      explicit:
        buckets: [100ms, 300ms, 500ms, 1s, 2s]

exporters:
  prometheus:
    endpoint: 0.0.0.0:8889

service:
  pipelines:
    traces:
      receivers: [otlp]
      exporters: [span_metrics]
    traces/muestreadas:
      receivers: [otlp]
      processors: [tail_sampling, batch]
      exporters: [otlp_grpc/jaeger]
    metrics:
      receivers: [span_metrics]
      exporters: [prometheus]

En :8889/metrics aparecen traces_span_metrics_calls_total y el histograma traces_span_metrics_duration_milliseconds, con etiquetas service_name, span_name, span_kind y status_code. De ahí salen los dos SLI clásicos, siempre sobre spans de servidor:

PromQL · disponibilidad y latencia 
sum(rate(traces_span_metrics_calls_total{service_name="checkout", span_kind="SPAN_KIND_SERVER", status_code!="STATUS_CODE_ERROR"}[5m]))
/
sum(rate(traces_span_metrics_calls_total{service_name="checkout", span_kind="SPAN_KIND_SERVER"}[5m]))

sum(rate(traces_span_metrics_duration_milliseconds_bucket{service_name="checkout", span_kind="SPAN_KIND_SERVER", le="500"}[5m]))
/
sum(rate(traces_span_metrics_duration_milliseconds_count{service_name="checkout", span_kind="SPAN_KIND_SERVER"}[5m]))

Elige como SLI lo que el usuario nota: la proporción de peticiones correctas y la de peticiones por debajo de un umbral. Los spans internos, como una consulta SQL, sirven para diagnosticar, no para el objetivo. Y ojo con span_name: si lleva ids en vez de la plantilla de ruta, cada pedido crea una serie nueva, la misma trampa de la cardinalidad.

Errores típicos #

Lo que se ve en cuanto lo montas

  • Olvidar OTEL_PHP_AUTOLOAD_ENABLED. Sin ella, Globals devuelve un NoopTracerProvider: todo compila, nada falla y el id de traza es una ristra de ceros.
  • traceidratio sin parentbased_. Cada servicio tira su propio dado y las trazas llegan a Jaeger con huecos.
  • Calcular el SLI con trazas ya muestreadas. El muestreo por cola guarda todos los errores y unas pocas correctas: la tasa de error sale disparada.
  • Exportar lejos del proceso. Con el destino caído, un script que tardaba 0,09 s tardó 0,6 s en terminar mientras el exportador reintentaba. Un collector cerca de la aplicación absorbe eso.
  • Instalar los paquetes auto-* sin la extensión. PHP solo da un aviso y no crea ningún span.

Cómo comprobarlo #

  • Imprime $span->getContext()->getTraceId() una vez: si son ceros, el SDK no está cargado.
  • Añade el exportador debug del collector mientras pruebas: su log dice cuántos spans recibe en cada lote.
  • Busca en Jaeger por id de traza y comprueba que el span de servidor de cada servicio cuelga del span cliente del anterior. Si aparece como raíz, alguien no propaga.
  • Con el muestreo activo, genera un error a propósito y confirma que esa traza está en Jaeger.

Cuándo aplicarlo #

OpenTelemetry cuando…

  • Una petición cruza varios servicios o colas y la lentitud no se localiza
  • Quieres SLI medidos en la petición real, no en el balanceador
  • No quieres atarte a un proveedor o ya usas dos

No hace falta cuando…

  • Es un monolito y el perfilado y los logs ya te dicen dónde se va el tiempo
  • No tienes dónde guardar trazas ni quien las mire
  • No puedes instalar la extensión y solo te cabrían spans a mano

La alternativa sencilla

El identificador de correlación en los logs estructurados y las métricas de Prometheus resuelven buena parte del dolor. Si migras más tarde, usa ya la cabecera traceparent en vez de una propia: OpenTelemetry la continuará sin cambios.

Resumen #

Lo que te llevas

  • OpenTelemetry separa instrumentar de elegir backend: API y SDK en PHP, OTLP como transporte y el collector decidiendo el destino.
  • Sin OTEL_PHP_AUTOLOAD_ENABLED o un SDK configurado, todo es no-op y no avisa.
  • La extensión y los paquetes auto-* ponen el esqueleto; los spans manuales, el dominio.
  • El propagador escribe y lee traceparent; en colas, lo llamas tú al publicar y al consumir.
  • Muestrea con parentbased_ en el SDK y por cola en el collector.
  • Los SLI salen de los spans de servidor, contados antes del muestreo.
