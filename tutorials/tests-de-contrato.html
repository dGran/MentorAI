Tests de contrato entre servicios

Dos servicios, dos suites en verde y una integración rota en producción. Un test de contrato pone por escrito lo que el consumidor espera y obliga al proveedor a demostrarlo, sin levantar el sistema entero.

Dos equipos, dos servicios y dos suites en verde. El lunes se despliega el catálogo, el martes el checkout empieza a cobrar cero euros y nadie entiende cómo: cada lado probó su parte contra lo que creía que hacía el otro. Un test de contrato convierte esa creencia en algo que se comprueba en ambos extremos.

Verde por separado, rojo al hablar #

El checkout pide al catálogo el precio de un producto. Su cliente HTTP es pequeño y está bien probado: un test unitario con un doble que devuelve el JSON que el equipo vio en la documentación hace seis meses.

php · src/CatalogClient.php 
<?php

declare(strict_types=1);

namespace Checkout;

use GuzzleHttp\Client;

final readonly class CatalogClient
{
    public function __construct(private Client $http)
    {
    }

    public function priceInCents(int $productId): int
    {
        $response = $this->http->get("/products/{$productId}", [
            'headers' => ['Accept' => 'application/json'],
        ]);
        $product = json_decode((string) $response->getBody(), true, flags: JSON_THROW_ON_ERROR);

        return $product['price_cents'];
    }
}
php · antes: el test con mock 
<?php

declare(strict_types=1);

namespace Checkout\Tests\Consumer;

use Checkout\CatalogClient;
use GuzzleHttp\Client;
use GuzzleHttp\Handler\MockHandler;
use GuzzleHttp\HandlerStack;
use GuzzleHttp\Psr7\Response;
use PHPUnit\Framework\TestCase;

final class CatalogClientMockTest extends TestCase
{
    public function test_reads_the_price_of_a_product(): void
    {
        $catalog = new MockHandler([
            new Response(200, ['Content-Type' => 'application/json'], '{"id": 42, "price_cents": 1999}'),
        ]);
        $client = new CatalogClient(new Client(['handler' => HandlerStack::create($catalog)]));

        $this->assertSame(1999, $client->priceInCents(42));
    }
}

Mientras tanto, el equipo del catálogo renombra price_cents a price y lo pasa a decimal. Sus tests comprueban su nueva respuesta y pasan. Los del checkout siguen devolviendo el JSON antiguo desde el mock y también pasan. Nadie miente: cada suite prueba su lado contra una copia del otro, y las copias no se actualizan solas.

El e2e lo habría pillado, pero levantar los dos servicios con sus bases de datos para cada cambio es lento, y con diez servicios deja de ser viable. Hace falta algo con la velocidad del mock y la honestidad de la llamada real.

Qué es un contrato y quién lo escribe #

Un contrato es la descripción de las peticiones y respuestas que dos servicios se comprometen a intercambiar. El truco está en usarla dos veces: el consumidor la usa para levantar su doble y el proveedor para comprobarse contra ella. Si el doble del consumidor y la verificación del proveedor salen del mismo fichero, ya no pueden divergir sin que algo se ponga rojo. Lo que cambia entre enfoques es quién escribe ese fichero.

Dirigido por el consumidor

  • Cada consumidor declara solo lo que usa de verdad
  • El proveedor sabe qué campos puede tocar sin romper a nadie
  • Hace falta código en los dos lados y un sitio donde compartir contratos
  • Herramienta de referencia: Pact

Esquema del proveedor (OpenAPI)

  • El proveedor publica todo lo que ofrece
  • No sabe qué campos usa cada consumidor ni cuáles puede retirar
  • Encaja si la especificación ya existe, que es lo habitual en una API pública
  • Basta un validador en los tests del proveedor

La diferencia importa al cambiar cosas. Con un esquema sabes que tu respuesta cumple lo publicado; con contratos de consumidor sabes además a quién romperías quitando un campo, que es justo la pregunta de versionar sin romper.

Pact: el consumidor escribe, el proveedor verifica #

1 Test del consumidorHabla con un mock server de Pact, no con un doble a mano
2 Fichero de contratocheckout-catalog.json, con las interacciones usadas
3 BrokerGuarda contratos y resultados por versión
4 Verificación del proveedorReproduce cada petición contra el servicio real

El mismo contrato alimenta el doble del consumidor y la prueba del proveedor.

En PHP la librería es pact-foundation/pact-php. La rama estable es la 10 (la 11 sigue en alfa): pide PHP 8.1 o superior y la extensión ffi habilitada, porque por debajo llama a la librería en Rust que comparten todos los lenguajes de Pact. Al instalarla, un plugin de Composer descarga ese binario.

bash · instalar en el consumidor y en el proveedor 
composer config allow-plugins.pact-foundation/composer-downloads-plugin true
composer require --dev pact-foundation/pact-php
php -m | grep -i ffi

El test del consumidor sustituye el MockHandler por una interacción declarada. Fíjate en los matchers: integer(1999) no exige ese valor, exige un entero. Así el contrato fija la forma y no los datos de ejemplo.

php · después: el test del consumidor con Pact 
<?php

declare(strict_types=1);

namespace Checkout\Tests\Consumer;

use Checkout\CatalogClient;
use GuzzleHttp\Client;
use PhpPact\Consumer\InteractionBuilder;
use PhpPact\Consumer\Matcher\Matcher;
use PhpPact\Consumer\Model\ConsumerRequest;
use PhpPact\Consumer\Model\ProviderResponse;
use PhpPact\Standalone\MockService\MockServerConfig;
use PHPUnit\Framework\TestCase;

final class CatalogClientPactTest extends TestCase
{
    public function test_reads_the_price_of_an_existing_product(): void
    {
        $matcher = new Matcher();

        $request = (new ConsumerRequest())
            ->setMethod('GET')
            ->setPath('/products/42')
            ->addHeader('Accept', 'application/json');

        $response = (new ProviderResponse())
            ->setStatus(200)
            ->addHeader('Content-Type', 'application/json')
            ->setBody([
                'id' => $matcher->integer(42),
                'price_cents' => $matcher->integer(1999),
            ]);

        $config = (new MockServerConfig())
            ->setConsumer('checkout')
            ->setProvider('catalog')
            ->setPactDir(__DIR__ . '/../../pacts');

        $builder = new InteractionBuilder($config);
        $builder
            ->given('product 42 exists')
            ->uponReceiving('a request for the price of product 42')
            ->with($request)
            ->willRespondWith($response);

        $client = new CatalogClient(new Client(['base_uri' => (string) $config->getBaseUri()]));

        $this->assertSame(1999, $client->priceInCents(42));
        $this->assertTrue($builder->verify());
    }
}

willRespondWith() va la última porque es la que registra la interacción y arranca el mock server; verify() comprueba que el cliente hizo exactamente las peticiones declaradas y, si todo cuadra, escribe pacts/checkout-catalog.json. El given() es un provider state: el nombre de una situación que el proveedor tendrá que preparar antes de recibir la petición.

En el lado del catálogo, un único test reproduce el contrato contra el servicio levantado:

php · la verificación del proveedor 
<?php

declare(strict_types=1);

namespace Catalog\Tests\Provider;

use GuzzleHttp\Psr7\Uri;
use PhpPact\Standalone\ProviderVerifier\Model\VerifierConfig;
use PhpPact\Standalone\ProviderVerifier\Verifier;
use PHPUnit\Framework\TestCase;

final class CatalogPactVerificationTest extends TestCase
{
    public function test_honours_every_consumer_contract(): void
    {
        $config = new VerifierConfig();
        $config->getProviderInfo()
            ->setName('catalog')
            ->setHost('localhost')
            ->setPort(8080);
        $config->getProviderState()
            ->setStateChangeUrl(new Uri('http://localhost:8080/_pact/provider-states'));

        $verifier = new Verifier($config);
        $verifier->addFile(__DIR__ . '/../../pacts/checkout-catalog.json');

        $this->assertTrue($verifier->verify());
    }
}

Con el catálogo ya renombrado, la verificación dice exactamente qué se rompió y para quién:

Los campos de más no rompen

Si el catálogo devuelve price_cents y además price y name, la verificación pasa: el consumidor solo declaró lo que lee. Por eso expandir y contraer funciona con Pact sin tocar ningún contrato.

El broker y can-i-deploy #

Compartir el JSON copiándolo entre repositorios funciona una semana. El Pact Broker (o PactFlow, su versión gestionada) guarda cada contrato asociado a la versión del consumidor que lo generó y cada verificación asociada a la versión del proveedor. Con esa matriz responde la pregunta que importa antes de desplegar: ¿esta versión es compatible con lo que ya hay en producción?

bash · el ciclo con la CLI del broker 
pact-broker publish pacts/ --consumer-app-version "$GIT_SHA" --branch main \
  --broker-base-url "$PACT_BROKER_BASE_URL"

pact-broker can-i-deploy --pacticipant checkout --version "$GIT_SHA" \
  --to-environment production --broker-base-url "$PACT_BROKER_BASE_URL"

pact-broker record-deployment --pacticipant checkout --version "$GIT_SHA" \
  --environment production --broker-base-url "$PACT_BROKER_BASE_URL"

can-i-deploy falla si falta una verificación en verde contra lo desplegado, y record-deployment le dice al broker qué hay en cada entorno para la siguiente consulta. Un webhook del broker (evento contract_requiring_verification_published) puede lanzar la verificación del proveedor en cuanto un consumidor publica un contrato nuevo.

La alternativa ligera: validar contra OpenAPI #

Si el proveedor ya publica una especificación OpenAPI, puedes sacarle partido sin broker ni FFI: sus propios tests validan cada respuesta real contra el esquema. Con league/openapi-psr7-validator (OpenAPI 3.0) cualquier respuesta PSR-7 vale:

yaml · openapi.yaml (fragmento) 
/products/{id}:
  get:
    responses:
      '200':
        description: A product
        content:
          application/json:
            schema:
              type: object
              required: [id, name, price_cents]
              properties:
                id: { type: integer }
                name: { type: string }
                price_cents: { type: integer }
php · el test del proveedor 
<?php

declare(strict_types=1);

namespace Catalog\Tests;

use GuzzleHttp\Client;
use League\OpenAPIValidation\PSR7\OperationAddress;
use League\OpenAPIValidation\PSR7\ValidatorBuilder;
use PHPUnit\Framework\TestCase;

final class ProductEndpointMatchesSpecTest extends TestCase
{
    public function test_product_response_matches_the_published_spec(): void
    {
        $validator = (new ValidatorBuilder())
            ->fromYamlFile(__DIR__ . '/../openapi.yaml')
            ->getResponseValidator();

        $response = (new Client(['base_uri' => 'http://localhost:8080']))->get('/products/42');

        $validator->validate(new OperationAddress('/products/{id}', 'get'), $response);

        $this->addToAssertionCount(1);
    }
}

Con el renombrado, el test falla con InvalidBody y la causa: Required property 'price_cents' must be present in the object. El límite es el que ya viste en la comparativa: protege la promesa del proveedor, no lo que lee el consumidor. Si el checkout lee un campo que la especificación nunca prometió, este test no se entera; para cerrar ese hueco, el consumidor también debe validar sus dobles contra el mismo fichero.

Dónde encaja en CI #

PipelineQué correQué bloquea
Consumidor, en cada pushTests de Pact junto a los unitarios; publica el contrato con el SHA y la ramaUn cliente que no cumple su propio contrato
Proveedor, en cada pushVerifica los contratos de la rama principal y de lo desplegadoRomper a un consumidor que ya está en producción
Proveedor, por webhookVerifica el contrato nuevo de un consumidorQue el consumidor despliegue algo que el proveedor aún no ofrece
Antes de cada desplieguecan-i-deploy y, tras desplegar, record-deploymentSubir una versión sin verificación en verde

Son tests rápidos: no levantan el otro servicio, solo el que se prueba. Por eso caben en cada push, a diferencia del e2e, que se queda para los pocos caminos críticos.

Errores típicos #

Lo que convierte el contrato en otro mock

  • Valores exactos en vez de matchers. El contrato exige 1999 y el proveedor tiene que sembrar ese precio para pasar. Fija tipos y formatos, no datos.
  • Probar la lógica del proveedor en el contrato. Que un descuento se calcule bien es un test del proveedor; el contrato solo comprueba la forma del intercambio.
  • Declarar la respuesta entera. Si copias todos los campos aunque leas dos, el proveedor ya no puede retirar ninguno sin pelearse contigo.
  • Provider states que no preparan nada. Si el endpoint de estados no crea el producto 42, la verificación depende de lo que haya en la base de datos ese día.
  • Generar el contrato y no publicarlo. Un JSON que se queda en el repositorio del consumidor no lo verifica nadie.

Cómo comprobarlo #

Un test de contrato que nunca has visto fallar no demuestra nada. Antes de fiarte, rómpelo a propósito por los dos lados:

  • En el proveedor, renombra el campo en la respuesta: la verificación debe señalar la clave que falta y el consumidor afectado.
  • En el consumidor, cambia la ruta que pide el cliente: el mock server de Pact responde 500 con Unexpected-Request y el test cae, porque la petición real no coincide con la declarada.
  • En el broker, lanza can-i-deploy con un SHA sin verificar: tiene que negarse.

Cuándo aplicarlo #

Compensa cuando…

  • Varios servicios se despliegan por separado y los mantienen equipos distintos
  • Ya te ha mordido un campo renombrado que ninguna suite detectó
  • El e2e entre servicios es tan lento o frágil que nadie lo corre antes de subir
  • Quieres retirar un campo y necesitas saber quién lo usa

No compensa cuando…

  • Es un monolito, o los dos servicios se despliegan siempre juntos
  • Consumes una API de terceros que nunca verificará tu contrato
  • Hay un solo consumidor y lo mantiene el mismo equipo en el mismo repositorio

La alternativa sencilla

Si el proveedor ya tiene su OpenAPI, empieza por validarla en sus tests: es una dependencia de desarrollo y un test. Da el salto a Pact cuando necesites saber qué usa cada consumidor. Con una API de terceros, envuelve el cliente en un adaptador y prueba ese adaptador contra su sandbox en un test de integración. Y si dudas de si deberías tener servicios separados, lee antes cuándo no distribuir.

Resumen #

Lo que te llevas

  • Un mock escrito a mano es una copia del otro servicio que no se actualiza sola: dos suites en verde no garantizan que hablen el mismo idioma.
  • El contrato sirve dos veces: genera el doble del consumidor y verifica al proveedor real.
  • Con Pact el consumidor declara solo lo que usa, con matchers de tipo; el broker y can-i-deploy deciden si una versión puede salir.
  • Validar contra OpenAPI es más ligero y protege la promesa del proveedor, pero no ve lo que lee cada consumidor.
  • Compensa con despliegues independientes y equipos distintos; en un monolito o con una API de terceros, no.
