Manejo de errores: errores como valores

Go no tiene excepciones. Los errores son valores que las funciones devuelven explícitamente como segundo (o último) valor de retorno. El compilador obliga a manejarlos, lo que hace que ignorarlos sea una decisión consciente, no un olvido.

En PHP, la excepción que nadie captura sube hasta el handler global, y descubres de dónde venía leyendo una traza. En Go el error es un valor que tienes en la mano en cada llamada, y decides ahí qué contexto añadirle y si sigue subiendo. Parece verbosidad; es la razón de que el log de un servicio Go cuente qué pasó sin abrir el código.

El patrón (valor, error) #

La convención de Go es devolver el resultado junto al error como último valor de retorno. nil significa sin error; cualquier otro valor significa que algo falló.

go 
func dividir(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("división por cero")
    }

    return a / b, nil
}

resultado, err := dividir(10, 2)

if err != nil {
    fmt.Println("error:", err)
    return
}

fmt.Println(resultado)   // 5

El compilador obliga a asignar todos los valores de retorno. Si no quieres usar el error, tienes que descartarlo explícitamente con _, lo que hace visible la decisión de ignorarlo:

go 
resultado, _ := dividir(10, 2)   // descarto el error conscientemente

Comparación con excepciones PHP #

PHP: excepciones

php 
function dividir(float $a, float $b): float {
    if ($b === 0.0) {
        throw new \DivisionByZeroError("División por cero");
    }
    return $a / $b;
}

// El try/catch puede olvidarse fácilmente
try {
    $resultado = dividir(10, 2);
} catch (\DivisionByZeroError $e) {
    echo "Error: " . $e->getMessage();
}

Go: error como valor

go 
func dividir(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("división por cero")
    }
    return a / b, nil
}

// El compilador obliga a manejar el error o descartarlo con _
resultado, err := dividir(10, 2)

if err != nil {
    fmt.Println("error:", err)
    return
}

Las excepciones pueden propagarse silenciosamente por el call stack si nadie las captura. En Go, un error es un valor que tienes en la mano: o lo manejas, o lo subes explícitamente con return ..., err.

Crear errores: errors.New y fmt.Errorf #

go 
import (
    "errors"
    "fmt"
)

// error simple
err1 := errors.New("algo salió mal")

// error con formato (como sprintf)
usuario := "ana"
err2 := fmt.Errorf("usuario %q no encontrado", usuario)

fmt.Println(err1)   // algo salió mal
fmt.Println(err2)   // usuario "ana" no encontrado

El patrón idiomático al propagar errores es añadir contexto con fmt.Errorf:

go 
func obtenerPerfil(id int) (*Perfil, error) {
    perfil, err := db.BuscarPerfil(id)

    if err != nil {
        return nil, fmt.Errorf("obtenerPerfil(%d): %w", id, err)
    }

    return perfil, nil
}

El %w es wrapping de error: preserva el error original para que pueda inspeccionarse después.

Errores tipados #

Para errores que el llamador puede necesitar diferenciar, crea un tipo que implemente la interfaz error:

go 
type ErrorNoEncontrado struct {
    Recurso string
    ID      int
}

func (e *ErrorNoEncontrado) Error() string {
    return fmt.Sprintf("%s con id %d no encontrado", e.Recurso, e.ID)
}

func buscarProducto(id int) (*Producto, error) {
    // simulando que no existe
    return nil, &ErrorNoEncontrado{Recurso: "Producto", ID: id}
}

El llamador puede comprobar el tipo con errors.As:

go 
producto, err := buscarProducto(42)

if err != nil {
    var errNE *ErrorNoEncontrado

    if errors.As(err, &errNE) {
        fmt.Printf("el %s %d no existe, devolviendo 404\n", errNE.Recurso, errNE.ID)
        return
    }

    fmt.Println("error inesperado:", err)
    return
}

Wrapping y unwrapping #

Go 1.13 introdujo el wrapping de errores para preservar la cadena de causas mientras se añade contexto:

go 
// Wrapping con %w
err := fmt.Errorf("capa de servicio: %w", errOriginal)

// Comprobar si un error en la cadena es de un tipo concreto
var errNE *ErrorNoEncontrado
errors.As(err, &errNE)   // busca en toda la cadena de wrapping

// Comprobar si un error en la cadena es igual a un valor centinela
var ErrNoAutorizado = errors.New("no autorizado")
errors.Is(err, ErrNoAutorizado)   // también busca en la cadena

Regla de uso:

  • errors.Is: para errores centinela (valores concretos como ErrNoAutorizado).
  • errors.As: para errores tipados (tipos como *ErrorNoEncontrado).
  • Nunca uses comparación directa (err == ErrAlgo) si el error puede haber sido wrapeado.

Panic y recover #

Go tiene panic para situaciones genuinamente irrecuperables: errores de programación, invariantes rotos. No es el equivalente a lanzar una excepción de negocio.

go 
// Panic: para bugs de programación
func obtenerElemento(slice []int, i int) int {
    if i < 0 || i >= len(slice) {
        panic(fmt.Sprintf("índice %d fuera de rango [0, %d)", i, len(slice)))
    }
    return slice[i]
}

recover captura un panic en curso, pero solo funciona dentro de una función llamada con defer:

go 
func ejecutarConSeguridad(fn func()) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("panic recuperado: %v", r)
        }
    }()

    fn()
    return nil
}

Usa panic solo para bugs de programación (índices fuera de rango, nil dereferences, invariantes imposibles). Para errores de negocio o de red, devuelve un error. Los frameworks web suelen usar recover en su middleware para evitar que un panic derrumbe el servidor entero.

Cuándo aplicarlo #

Todo fallo que se puede esperar es un error: entrada inválida, registro que no existe, red caída, timeout de la base de datos. La decisión real está en qué forma darle para quien lo recibe.

Elige así…

  • Centinela (var ErrNoEncontrado = errors.New(...)) cuando al llamador le basta saber qué pasó
  • Error tipado cuando necesita datos para reaccionar: el recurso, el campo que falló validación
  • %w cuando quieres que el llamador pueda inspeccionar la causa con errors.Is o errors.As
  • panic para invariantes imposibles o fallos al arrancar, como regexp.MustCompile con un patrón fijo

Evita…

  • panic y recover como un try/catch de negocio
  • Loguear el error y además devolverlo: acaba apareciendo varias veces en el log, una por capa
  • Comparar textos con err.Error() == "...": se rompe al cambiar el mensaje
  • %w sobre errores internos de una dependencia que no quieres convertir en parte de tu API: ahí, %v

Regla práctica: cada capa añade lo que sabe y la anterior no («cargando pedido 42»), y solo la capa que decide qué hacer con el error lo loguea o lo traduce a un código HTTP.

Resumen #

Lo que te llevas

  • Los errores en Go son valores que se devuelven como último argumento de retorno. La convención es (resultado, error).
  • Propaga errores con contexto: fmt.Errorf("contexto: %w", err). El %w preserva el error original para inspección.
  • Usa errors.Is para comparar con errores centinela; errors.As para errores tipados. Ambos buscan en la cadena de wrapping.
  • Los errores tipados (structs que implementan Error() string) permiten al llamador distinguir entre distintas clases de fallo.
  • panic es para bugs de programación, no para errores de negocio. recover solo funciona dentro de un defer.
