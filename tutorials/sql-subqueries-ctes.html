Subconsultas y CTEs: SQL legible y eficiente

Una subconsulta es una consulta dentro de otra. Una CTE es lo mismo con nombre y estructura. Saber cuándo usar cada forma —y cuándo la subconsulta correlacionada te mete en un O(n)— marca la diferencia entre SQL que funciona y SQL que escala.

Una subconsulta es simplemente una consulta SQL dentro de otra. El motor la resuelve primero y usa su resultado como si fuera un valor, un conjunto o una tabla. CTEs (Common Table Expressions) son el mismo concepto con nombre, lo que las hace reutilizables y mucho más fáciles de leer.

Tipos de subconsulta #

Tipo Devuelve Dónde se usa
Escalar 1 fila, 1 columna SELECT, WHERE, SET
De tabla (derived table) N filas, N columnas FROM (necesita alias)
De conjunto N filas, 1 columna WHERE … IN (…)
Correlacionada Cualquier forma WHERE EXISTS, SELECT

Subconsulta en WHERE #

El uso más frecuente: filtrar filas en función de datos de otra tabla sin necesitar columnas de esa tabla en el resultado.

sql 
-- Escalar: productos más caros que la media de su categoría
SELECT nombre, precio
FROM productos
WHERE precio > (SELECT AVG(precio) FROM productos);

-- IN: clientes de España con pedidos
SELECT nombre
FROM clientes
WHERE id IN (
    SELECT DISTINCT cliente_id
    FROM pedidos
    WHERE pais_envio = 'ES'
);

-- EXISTS: clientes que tienen al menos un pedido (cortocircuita en la primera coincidencia)
SELECT nombre
FROM clientes c
WHERE EXISTS (
    SELECT 1 FROM pedidos p WHERE p.cliente_id = c.id
);

IN — cuidado con conjuntos grandes

Materializa todo el conjunto antes de filtrar. Con millones de filas en la subconsulta el rendimiento cae. Y si la subconsulta devuelve un NULL, IN nunca es TRUE para la fila (el NULL envenena la comparación).

EXISTS — más predecible

Para en cuanto encuentra la primera fila que cumple. No le afectan los NULL de la subconsulta. Es el idioma natural para "¿existe al menos uno?".

NOT EXISTS vs NOT IN con NULLs

NOT IN (subconsulta) devuelve cero filas si la subconsulta contiene algún NULL, porque x != NULL es UNKNOWN, no TRUE. NOT EXISTS no tiene ese problema. Cuando la columna puede tener NULLs, usa NOT EXISTS.

Subconsulta en FROM #

Cuando necesitas operar sobre datos ya agregados —filtrar, calcular porcentajes, unir con otra tabla— puedes poner una subconsulta en el FROM y tratarla como si fuera una tabla. Necesita obligatoriamente un alias.

sql 
-- Porcentaje de pedidos por estado sobre el total
SELECT
    resumen.estado,
    resumen.cantidad,
    ROUND(resumen.cantidad * 100.0 / totales.total, 1) AS porcentaje
FROM (
    SELECT estado, COUNT(*) AS cantidad
    FROM pedidos
    GROUP BY estado
) AS resumen
CROSS JOIN (
    SELECT COUNT(*) AS total FROM pedidos
) AS totales
ORDER BY resumen.cantidad DESC;

Esta es exactamente la situación que las CTEs resuelven con más elegancia. La subconsulta en FROM se puede leer, pero con CTEs el nombre de cada parte aparece antes de su definición y la consulta final queda mucho más limpia.

Subconsulta correlacionada #

Una subconsulta correlacionada referencia una columna de la consulta exterior. Esto la hace dependiente de cada fila de fuera: se ejecuta una vez por cada fila del resultado exterior.

sql 
-- La fecha del último pedido de cada cliente (correlacionada)
SELECT c.nombre, (
    SELECT MAX(p.fecha)
    FROM pedidos p
    WHERE p.cliente_id = c.id   -- referencia a la fila exterior
) AS ultimo_pedido
FROM clientes c;

-- Equivalente con JOIN + GROUP BY (una sola pasada sobre pedidos)
SELECT c.nombre, MAX(p.fecha) AS ultimo_pedido
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id
GROUP BY c.id, c.nombre;

La correlacionada es O(n): escala mal

Con 10.000 clientes, la versión correlacionada ejecuta 10.000 subqueries. La versión con JOIN ejecuta una sola. Los optimizadores modernos a veces transforman la correlacionada en un join internamente, pero no siempre. Si puedes reescribirla como JOIN o CTE, hazlo.

CTEs con WITH #

Una CTE define una "tabla temporal con nombre" que existe solo durante la ejecución de esa consulta. Se declara antes del SELECT principal con la cláusula WITH.

sql 
-- Una sola CTE
WITH pedidos_recientes AS (
    SELECT cliente_id, COUNT(*) AS total, SUM(importe) AS facturado
    FROM pedidos
    WHERE fecha >= '2026-01-01'
    GROUP BY cliente_id
)
SELECT c.nombre, pr.total, pr.facturado
FROM clientes c
JOIN pedidos_recientes pr ON pr.cliente_id = c.id
WHERE pr.facturado > 1000
ORDER BY pr.facturado DESC;

-- Múltiples CTEs: se separan por coma, cada una puede usar las anteriores
WITH
clientes_activos AS (
    SELECT id, nombre
    FROM clientes
    WHERE activo = 1
),
pedidos_por_cliente AS (
    SELECT cliente_id, SUM(importe) AS total_anual
    FROM pedidos
    WHERE YEAR(fecha) = 2026
    GROUP BY cliente_id
)
SELECT ca.nombre, ppc.total_anual
FROM clientes_activos ca
JOIN pedidos_por_cliente ppc ON ppc.cliente_id = ca.id
ORDER BY ppc.total_anual DESC;

La ventaja sobre las subconsultas en FROM no es de rendimiento —la mayoría de motores las tratan igual internamente— sino de legibilidad: cada pieza tiene nombre, el orden de lectura es natural (defines primero, usas después) y puedes aislar una CTE para probarla por separado.

CTE recursiva #

Una CTE puede referenciar su propio nombre, lo que permite iterar sobre datos jerárquicos sin procedimientos almacenados. Tiene dos partes unidas por UNION ALL: el caso base (las filas iniciales) y el caso recursivo (que lee de la CTE y añade más filas).

sql 
-- Árbol de organización: todos los subordinados de un manager
WITH RECURSIVE subordinados AS (
    -- Caso base: el punto de partida
    SELECT id, nombre, manager_id, 0 AS nivel
    FROM empleados
    WHERE id = 5

    UNION ALL

    -- Caso recursivo: subordinados directos de cada fila ya en la CTE
    SELECT e.id, e.nombre, e.manager_id, s.nivel + 1
    FROM empleados e
    INNER JOIN subordinados s ON s.id = e.manager_id
)
SELECT nombre, nivel
FROM subordinados
ORDER BY nivel, nombre;

El motor ejecuta el caso base, añade las filas al resultado, luego ejecuta el caso recursivo usando esas filas como entrada, y repite hasta que el caso recursivo no devuelve filas nuevas.

Ciclos en los datos → recursión infinita

Si los datos tienen un ciclo (A es manager de B, B es manager de A), la CTE recursiva no termina. Protégete añadiendo un límite de profundidad con WHERE nivel < 50, o usa la cláusula CYCLE de PostgreSQL 14+ que detecta ciclos automáticamente.

Otros usos habituales de la CTE recursiva: categorías con subcategorías anidadas, generar series de fechas sin tablas auxiliares, recorrer grafos acíclicos.

sql 
-- Serie de fechas del mes actual (sin tabla calendario)
WITH RECURSIVE calendario AS (
    SELECT CAST('2026-07-01' AS DATE) AS dia

    UNION ALL

    SELECT dia + INTERVAL 1 DAY
    FROM calendario
    WHERE dia < '2026-07-31'
)
SELECT dia
FROM calendario;

Cuándo aplicarlo

Úsalo cuando…

  • CTE cuando la lógica se reutiliza varias veces en la misma query o la legibilidad importa en queries de múltiples pasos.
  • Subconsulta cuando el uso es único y el optimizador puede inlinearla sin penalización.
  • WITH MATERIALIZED cuando el optimizador ejecuta la CTE más de una vez sin necesidad.

No lo uses cuando…

  • CTE recursiva para recorridos simples que un JOIN resuelve: la recursión añade complejidad sin beneficio.
  • Subconsulta correlacionada dentro de un SELECT de muchas filas: se ejecuta una vez por fila y puede ser lenta.
  • Subconsulta en FROM cuando una CTE haría el mismo trabajo con más claridad.

Resumen #

Lo que te llevas

  • Subconsulta escalar → un valor; en FROM → tabla temporal nombrada; en WHERE → EXISTS o IN para filtrar por existencia.
  • Usa EXISTS en lugar de IN para "¿existe al menos uno?": cortocircuita y no tiene el problema de los NULL.
  • Subconsulta correlacionada: referencia la fila exterior, se ejecuta O(n) veces. Reescríbela como JOIN si puedes.
  • CTE (WITH nombre AS (…)) es una subconsulta nombrada y reutilizable. Igual de eficiente que en FROM, pero mucho más legible.
  • Múltiples CTEs: separadas por coma; cada una puede referenciar las anteriores. Ideal para consultas con varias etapas de preparación de datos.
  • CTE recursiva: caso base UNION ALL caso recursivo. Para jerarquías y árboles. Añade límite de profundidad para protegerte de ciclos.
