Configuración y entornos en Python

pydantic-settings, ficheros .env por entorno, settings como singleton, secretos y validación al arranque.

En PHP lo habitual es un getenv() aquí y un $_ENV allá, y un .env que carga el framework: el día que falta una variable te enteras en producción, en la petición que la usa. En Python la idea es la contraria: toda la configuración declarada en una clase y validada al arrancar, de modo que un despliegue mal configurado ni siquiera llega a levantarse.

pydantic-settings: el estándar moderno #

La configuración de una aplicación tiene dos fuentes: el código (valores por defecto) y el entorno (lo que varía por despliegue). El patrón anterior era leer os.environ directamente, con el problema de que cualquier variable ausente lanzaba un error en tiempo de ejecución difícil de diagnosticar.

pydantic-settings resuelve esto con una clase que declara la configuración completa con tipos, valores por defecto y validación. Si falta una variable requerida o tiene un tipo incorrecto, el proceso falla al arrancar con un error claro, no en mitad de una petición:

bash 
pip install pydantic-settings
python 
from pydantic import PostgresDsn, RedisDsn, field_validator
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        case_sensitive=False,
    )

    database_url: PostgresDsn
    redis_url: RedisDsn = "redis://localhost:6379/0"
    secret_key: str
    debug: bool = False
    allowed_hosts: list[str] = ["localhost", "127.0.0.1"]
    cors_origins: list[str] = []
    max_connections: int = 10

    @field_validator("secret_key")
    @classmethod
    def secret_key_must_be_long(cls, value: str) -> str:
        if len(value) < 32:
            raise ValueError("secret_key debe tener al menos 32 caracteres")
        return value

PostgresDsn y RedisDsn son tipos de pydantic que validan el formato de la URL. field_validator permite añadir validación adicional: aquí, una clave secreta demasiado corta es un error de configuración que vale la pena detectar en el arranque.

pydantic-settings sigue esta jerarquía de prioridad para leer valores: variables de entorno del sistema > fichero .env > valores por defecto de la clase. Esto significa que en producción puedes sobreescribir cualquier valor del .env simplemente exportando la variable en el shell.

Ficheros .env por entorno #

La convención más extendida es tener un .env por entorno. El fichero que carga la aplicación depende de una variable de entorno que indica el entorno activo:

python 
import os
from pydantic_settings import BaseSettings, SettingsConfigDict


def env_file_for_environment() -> str:
    environment = os.getenv("APP_ENV", "development")
    return f".env.{environment}"


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=env_file_for_environment(),
        env_file_encoding="utf-8",
    )

    database_url: str
    redis_url: str = "redis://localhost:6379/0"
    secret_key: str
    debug: bool = False

Estructura de ficheros en el repositorio:

text 
.env.example          ← commitear: muestra las variables necesarias sin valores reales
.env.development      ← no commitear: valores locales de cada desarrollador
.env.test             ← puede commitearse si los valores son seguros (BD de test local)
.env.production       ← nunca commitear: gestionado por el sistema de despliegue

Nunca commitees un .env con secretos reales. Añade siempre estos patrones a tu .gitignore:

.env
.env.*
!.env.example

La excepción explícita !.env.example permite commitear el fichero de ejemplo. Si un secreto llega a un commit, no basta con eliminarlo: queda en el historial de git y hay que rotarlo.

El fichero .env.example documenta qué variables necesita la aplicación y con qué formato, sin exponer valores reales:

ini 
DATABASE_URL=postgresql+asyncpg://user:password@localhost:5432/myapp
REDIS_URL=redis://localhost:6379/0
SECRET_KEY=cambia-esto-por-una-clave-de-al-menos-32-caracteres
DEBUG=false
ALLOWED_HOSTS=["localhost","127.0.0.1"]

Settings como singleton con lru_cache #

Instanciar Settings() en cada punto donde se necesita la configuración es ineficiente y dificulta los tests: cada instancia lee el fichero .env de nuevo. El patrón correcto es una función con @lru_cache que garantiza que solo se crea una instancia por proceso:

python 
from functools import lru_cache
from app.config import Settings


@lru_cache
def get_settings() -> Settings:
    return Settings()

@lru_cache sin argumentos memoiza el resultado para cada combinación de argumentos. Como get_settings() no tiene argumentos, siempre devuelve la misma instancia. La primera llamada construye y valida el objeto; todas las siguientes devuelven el mismo objeto cacheado.

En FastAPI, get_settings funciona directamente como dependencia con Depends:

python 
from fastapi import Depends, FastAPI
from app.config import Settings
from app.dependencies import get_settings

app = FastAPI()


@app.get("/info")
async def info(settings: Settings = Depends(get_settings)) -> dict:
    return {
        "debug": settings.debug,
        "allowed_hosts": settings.allowed_hosts,
    }

Para tests, sobreescribir la dependencia es limpio y no requiere variables de entorno reales:

python 
from app.config import Settings
from app.dependencies import get_settings
from app.main import app


def override_settings() -> Settings:
    return Settings(
        database_url="postgresql+asyncpg://user:pass@localhost:5432/test",
        redis_url="redis://localhost:6379/1",
        secret_key="clave-de-test-que-tiene-32-caracteres-exactos",
    )


app.dependency_overrides[get_settings] = override_settings

Secretos: variables de entorno vs vault #

Las variables de entorno son el mínimo viable para gestionar secretos, y funcionan bien en la mayoría de proyectos. Sus limitaciones aparecen a escala: no tienen control de acceso granular, no tienen historial de rotaciones, y cualquier proceso del mismo entorno puede leerlas.

Mecanismo Ventajas Limitaciones
Variables de entorno Simple, universal, soportado en cualquier plataforma Sin auditoría, sin rotación automática, visibles a todo el proceso
Docker secrets Montados como ficheros, no en el entorno del proceso Solo disponibles en Docker Swarm (no en compose estándar)
HashiCorp Vault / AWS Secrets Manager Rotación automática, auditoría, control de acceso por rol Infraestructura adicional, complejidad operacional

Un patrón compatible con todas las opciones es leer secretos desde ficheros en el sistema de ficheros además de desde variables de entorno. En Kubernetes, los secretos se montan como ficheros; en local, usas el .env:

python 
import os
from pathlib import Path
from pydantic_settings import BaseSettings, SettingsConfigDict


def read_secret_file(path: str) -> str | None:
    secret_path = Path(path)

    if not secret_path.exists():
        return None

    return secret_path.read_text().strip()


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env")

    database_url: str
    secret_key: str = ""

    def model_post_init(self, context) -> None:
        if not self.secret_key:
            from_file = read_secret_file("/run/secrets/secret_key")

            if from_file:
                object.__setattr__(self, "secret_key", from_file)

        if not self.secret_key:
            raise ValueError("secret_key no está configurada")

Cuándo aplicarlo #

Aplícalo cuando…

  • El servicio se despliega en más de un entorno y cada uno tiene sus valores
  • Hay valores con formato que conviene validar: URLs de conexión, puertos, listas de orígenes
  • Manejas secretos que no deben aparecer en logs ni en trazas: SecretStr
  • La configuración se lee desde muchos sitios y quieres sustituirla en tests: el singleton con lru_cache

Evítalo cuando…

  • Quieres valores que cambien en caliente, como feature flags: la configuración se lee al arrancar; eso va en un servicio de flags o en la base de datos
  • Pones valores por defecto a secretos o a la URL de la base de datos: un default «de desarrollo» que llega a producción es peor que un arranque fallido
  • Montas un vault para un único servicio sin necesidad de rotación ni auditoría: las variables del orquestador bastan

El criterio de fondo: el código define qué configuración existe y con qué tipo; el entorno decide sus valores. Si para cambiar de entorno tienes que tocar código, la frontera está mal puesta.

Resumen #

Lo que te llevas

  • pydantic-settings valida la configuración al arrancar la aplicación: un campo requerido ausente o con tipo incorrecto falla en el inicio, no en mitad de una petición.
  • El orden de prioridad es variables del sistema > fichero .env > valores por defecto; en producción, las variables del sistema siempre ganan sin tocar el código.
  • @lru_cache convierte get_settings() en un singleton por proceso: un único objeto Settings construido una vez y compartido por toda la aplicación.
  • Nunca commitear ficheros .env con secretos reales: si llegan al historial de git, hay que rotar los secretos. El fichero .env.example sí se commitea como documentación.
  • Las variables de entorno son suficientes para la mayoría de proyectos; un gestor de secretos (Vault, AWS Secrets Manager) aporta valor cuando necesitas auditoría, rotación automática o control de acceso por rol.
