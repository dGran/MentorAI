Async/await y Tokio

Cómo funciona la asincronía en Rust: el trait Future, el runtime Tokio, tareas con tokio::spawn, select! y por qué async en Rust es diferente a otros lenguajes.

El trait Future

La diferencia más importante entre async en Rust y async en otros lenguajes: Rust no tiene runtime async integrado. En Go, las goroutines tienen el scheduler del runtime de Go. En Node.js, el event loop de libuv siempre está corriendo. En Rust, nada corre automáticamente.

Un Future en Rust es un valor que representa un cálculo que puede completarse en el futuro:

pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

Un Future es perezoso: no hace nada hasta que algo lo pollea (lo ejecuta paso a paso). Si creas un Future y no lo awaitas, no corre. Este diseño es distinto a JavaScript donde una Promise empieza a ejecutarse en el momento de crearse.

Futures perezosos vs Promises eager: en JS, fetch(url) inicia la petición inmediatamente. En Rust, reqwest::get(url) retorna un Future que no inicia la petición hasta que lo awaitas. Esto permite componer Futures sin efectos secundarios no deseados.

async fn y .await

async fn es azúcar sintáctico: transforma la función en una que retorna impl Future. El cuerpo de la función se convierte en una máquina de estados que el runtime puede pausar y reanudar.

async fn obtener_usuario(id: u32) -> Result<String, reqwest::Error> {
    let url = format!("https://api.ejemplo.com/usuarios/{}", id);
    let respuesta = reqwest::get(&url).await?;
    let texto = respuesta.text().await?;
    Ok(texto)
}

.await suspende la función actual en ese punto hasta que el Future se completa. Durante la suspensión, el thread puede hacer otro trabajo (procesar otra tarea async). Esto es la concurrencia cooperativa: las tareas ceden el control en los puntos de .await.

La diferencia crucial con bloques síncronos: .await no bloquea el thread. thread::sleep(Duration::from_secs(1)) bloquea el thread un segundo. tokio::time::sleep(Duration::from_secs(1)).await suspende la tarea un segundo pero el thread puede procesar otras tareas durante ese tiempo.

Tokio: el runtime

Tokio es el runtime async más usado en Rust. Proporciona el scheduler que pollea los Futures y un conjunto de primitivas async (sockets, timers, canales, etc.).

use tokio;

#[tokio::main]
async fn main() {
    println!("Iniciando servidor");
    tokio::time::sleep(tokio::time::Duration::from_secs(1)).await;
    println!("Listo");
}

La macro #[tokio::main] crea el runtime de Tokio y ejecuta la función main async dentro de él. Sin esta macro (o sin crear un runtime manualmente), no hay nadie para pollear los Futures.

Cargo.toml:

[dependencies]
tokio = { version = "1", features = ["full"] }

Tokio ofrece dos configuraciones de runtime:

  • Multi-thread scheduler (por defecto): crea un pool de threads, uno por CPU. Las tareas se distribuyen entre threads. Necesario para aplicaciones que usan todos los cores.
  • Current-thread scheduler: todo en un único thread. Para código que no necesita multi-threading o que tiene restricciones de thread-local.
#[tokio::main(flavor = "current_thread")]
async fn main() {
    // todo en un thread
}

tokio::spawn: tareas concurrentes

tokio::spawn lanza una tarea async en el scheduler de Tokio. A diferencia de thread::spawn, es muy barato: las tareas Tokio son tasks ligeras multiplexadas sobre el pool de threads del runtime.

use tokio;

async fn procesar_usuario(id: u32) -> String {
    tokio::time::sleep(tokio::time::Duration::from_millis(100)).await;
    format!("usuario_{}", id)
}

#[tokio::main]
async fn main() {
    let handles: Vec<_> = (1..=5).map(|id| {
        tokio::spawn(async move {
            procesar_usuario(id).await
        })
    }).collect();

    for handle in handles {
        let resultado = handle.await.unwrap();
        println!("{}", resultado);
    }
}

Los 5 procesar_usuario corren concurrentemente: el tiempo total es ~100ms, no 500ms. El Future pasado a tokio::spawn debe ser Send (porque Tokio puede moverlo entre threads del pool).

Para esperar múltiples handles a la vez (en lugar de secuencialmente):

let (r1, r2, r3) = tokio::join!(
    procesar_usuario(1),
    procesar_usuario(2),
    procesar_usuario(3)
);

tokio::select!

tokio::select! espera al primero de varios Futures que se complete y cancela los demás. Es el mecanismo principal para timeouts y cancelación:

use tokio::time::{timeout, Duration};

async fn operacion_lenta() -> &'static str {
    tokio::time::sleep(Duration::from_secs(5)).await;
    "completado"
}

#[tokio::main]
async fn main() {
    tokio::select! {
        resultado = operacion_lenta() => {
            println!("Terminó: {}", resultado);
        }
        _ = tokio::time::sleep(Duration::from_secs(2)) => {
            println!("Timeout: la operación tardó demasiado");
        }
    }
}

Cuando el sleep de 2 segundos completa primero, el brazo del timeout gana y operacion_lenta se cancela. La cancelación en Rust async es drop-based: soltar el Future es cancelarlo.

join! vs select!:

  • join!(a, b, c): espera a que todos terminen. El resultado contiene los valores de todos.
  • select!(a, b, c): espera al primero. Los demás se cancelan.

Cuándo usar async vs threads

La elección entre async y threads depende de la naturaleza del trabajo:

Tipo de trabajoElección correctaPor qué
I/O bound (HTTP, BD, archivos)Async + TokioMuchas operaciones I/O concurrentes con pocos threads
CPU bound (cálculos intensivos)Threads + RayonAsync bloquearía el scheduler; usa todos los cores
I/O + CPUAsync + spawn_blockingCombinar: async para I/O, offload CPU a thread pool

El antipatrón más común: hacer trabajo CPU-intensivo dentro de una tarea async. Bloquea el thread del scheduler y degrada el rendimiento de todas las demás tareas. La solución:

async fn handler() -> String {
    let resultado = tokio::task::spawn_blocking(|| {
        calcular_hash_intensivo() // corre en un thread del blocking pool
    }).await.unwrap();

    formato_del_resultado(resultado).await
}

tokio::task::spawn_blocking envía la tarea a un pool de threads dedicado a operaciones bloqueantes, liberando el runtime async para continuar con otras tareas.

Resumen

  • Rust no tiene runtime async integrado: los Futures son perezosos y no hacen nada hasta que un runtime los pollea. Tokio proporciona ese runtime.
  • async fn transforma la función en una que retorna impl Future. .await suspende la tarea actual sin bloquear el thread.
  • #[tokio::main] crea el runtime de Tokio y ejecuta la función main async. El runtime multi-thread usa un pool de threads, uno por CPU.
  • tokio::spawn lanza tareas async ligeras; tokio::join! espera a todas; tokio::select! espera a la primera y cancela las demás.
  • Async es para I/O bound; threads/rayon para CPU bound. Mezcla con tokio::task::spawn_blocking para código bloqueante dentro de contexto async.
