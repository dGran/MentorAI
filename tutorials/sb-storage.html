Storage: ficheros con permisos de base de datos

Los ficheros son el sitio donde más apps se dejan una puerta abierta: un bucket público con documentos privados, URLs que se pueden adivinar, subidas sin límite de tamaño. Supabase Storage resuelve los permisos con la misma herramienta que ya conoces, RLS, porque cada fichero es una fila más.

La app de notas ya tiene usuarios (Auth) y permisos por fila (RLS). Ahora cada nota puede llevar adjuntos: imágenes, PDFs, audios. Esta lección cuenta dónde acaban esos ficheros, quién puede verlos y cómo servirlos rápido.

Buckets, objetos y rutas #

Storage separa los ficheros en dos sitios:

  • El contenido (los bytes) va a un almacenamiento de objetos compatible con S3.
  • Los metadatos (nombre, bucket, tamaño, tipo, dueño, fechas) son una fila de la tabla **storage.objects** en tu Postgres.

Los ficheros se agrupan en buckets, y dentro de cada uno se identifican por su ruta: adjuntos/3f2a.../17/receta.pdf. Las carpetas no existen como tal; son prefijos de la ruta. Pero esos prefijos son la herramienta principal de permisos, así que diseñarlos bien es la mitad del trabajo.

Una ruta que se pueda autorizar

Empieza la ruta por lo que decide el acceso: {user_id}/{note_id}/{nombre}. Así una política puede leer el primer segmento y compararlo con el usuario, sin consultar ninguna otra tabla. Una ruta como receta-final-v2.pdf no le dice nada a una política.

Bucket público o privado #

Al crear un bucket eliges si es público, y la diferencia es solo sobre la descarga:

Bucket público

  • Cualquiera con la URL descarga el fichero, sin token
  • URL estable: /storage/v1/object/public/avatars/ruta.png
  • La CDN lo cachea sin problemas
  • Subir, sobrescribir y borrar siguen necesitando políticas

Bucket privado

  • Descargar exige una política de lectura y un token, o una URL firmada
  • Sin políticas, nadie puede hacer nada (salvo la clave secreta)
  • Lo que hay que usar para cualquier cosa que no deba ver todo el mundo

Los avatares encajan en un bucket público. Los adjuntos de una nota, no: «la URL es muy larga y nadie la va a adivinar» no es un control de acceso, porque las URLs se reenvían, quedan en historiales y se filtran en logs.

sql · crear el bucket en una migración, con límites 
insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
values (
  'attachments',
  'attachments',
  false,
  10485760,
  array['image/png', 'image/jpeg', 'image/webp', 'application/pdf']
);

file_size_limit (10 MB aquí) y allowed_mime_types se aplican en el servidor: el cliente no puede saltárselos. Ponlos siempre; un bucket sin límite acepta lo que le manden hasta el máximo del plan.

Políticas sobre storage.objects #

Los permisos de Storage son políticas RLS sobre storage.objects. Cada operación de la API necesita la suya:

OperaciónPolítica necesaria
Subir (upload)insert
Sobrescribir (upload con upsert: true)insert, select y update
Descargar, listar, crear URL firmadaselect
Mover o renombrarupdate (y select)
Borrardelete

La función storage.foldername(name) parte la ruta en un array de carpetas, y con eso se escriben las políticas de «cada uno en su carpeta»:

sql · cada usuario gestiona los adjuntos de su carpeta 
create policy "Subir a mi carpeta"
on storage.objects for insert to authenticated
with check (
  bucket_id = 'attachments'
  and (storage.foldername(name))[1] = (select auth.uid()::text)
);

create policy "Leer de mi carpeta"
on storage.objects for select to authenticated
using (
  bucket_id = 'attachments'
  and (storage.foldername(name))[1] = (select auth.uid()::text)
);

create policy "Borrar de mi carpeta"
on storage.objects for delete to authenticated
using (
  bucket_id = 'attachments'
  and (storage.foldername(name))[1] = (select auth.uid()::text)
);

Fíjate en el bucket_id de cada política: sin él, la regla se aplicaría a todos los buckets del proyecto. Y como son políticas normales, pueden consultar tus tablas: «puedo leer el adjunto si puedo leer la nota» es una política de select que extrae el note_id del segundo segmento de la ruta y mira note_shares, igual que en RLS.

Subir y descargar desde el cliente #

ts · subir un adjunto y registrarlo 
const path = `${userId}/${noteId}/${crypto.randomUUID()}-${file.name}`;

const { error: uploadError } = await supabase.storage
  .from("attachments")
  .upload(path, file, { contentType: file.type, upsert: false });

if (uploadError) throw uploadError;

await supabase.from("attachments").insert({ note_id: noteId, path, name: file.name });

La tabla public.attachments es tuya: guarda la relación entre la nota y la ruta, para listar los adjuntos de una nota sin recorrer Storage. Con upsert: false, subir a una ruta ocupada falla en vez de pisar el fichero anterior.

Para mostrar un fichero privado, se pide una URL firmada: una dirección con un token que caduca.

ts · enlace temporal de una hora 
const { data } = await supabase.storage
  .from("attachments")
  .createSignedUrl(path, 3600);

window.open(data.signedUrl);

La URL firmada se puede compartir mientras no caduque, sin sesión: úsala con caducidades cortas. Para un bucket público basta con getPublicUrl(path), que solo construye la dirección, sin llamar al servidor.

Subidas que decide el servidor

A veces no quieres que el cliente elija la ruta, o el usuario no tiene permiso de subida por sí mismo (un formulario de contacto con adjunto, por ejemplo). Tu servidor o una Edge Function crea una URL firmada de subida con createSignedUploadUrl(path) y se la da al cliente, que sube directamente a Storage sin que los bytes pasen por tu servidor. Tú decides la ruta y el momento; el cliente solo puede subir ahí.

Ficheros grandes: subidas reanudables y S3 #

La subida normal manda el fichero en una sola petición: para unos pocos MB, perfecto; para un vídeo de 2 GB con wifi inestable, un corte obliga a empezar de cero. Para eso Storage soporta:

  • Subidas reanudables con el protocolo TUS: el fichero va en trozos y, si la conexión cae, continúa donde se quedó. Supabase recomienda TUS a partir de unos 6 MB.
  • Protocolo S3: Storage habla la API de S3, así que herramientas como rclone, aws s3 cp o cualquier SDK de S3 pueden subir y descargar contra tu proyecto.

Imágenes transformadas y la caché #

En los planes de pago, Storage redimensiona y optimiza imágenes al vuelo: pides la miniatura en la URL y la CDN cachea el resultado.

ts · miniatura de 400 × 300 recortada 
const { data } = supabase.storage
  .from("avatars")
  .getPublicUrl(`${userId}/avatar.png`, {
    transform: { width: 400, height: 300, resize: "cover" },
  });

Te ahorra generar y guardar cada tamaño, y sirve formatos modernos como WebP a los navegadores que los aceptan. Las transformaciones se facturan por imagen original, no por cada tamaño pedido.

Sobrescribir un fichero cacheado

La CDN cachea los ficheros públicos según su cacheControl. Si subes un avatar nuevo a la misma ruta, durante un tiempo algunos usuarios seguirán viendo el viejo. La solución robusta es no sobrescribir: cada versión, en una ruta nueva (avatar-<timestamp>.png), y la tabla de perfiles apunta a la última. Además, la URL vieja deja de usarse sola.

Errores típicos #

  • Documentos privados en un bucket público. El bucket público no pide token para descargar, aunque las políticas de subida sean estrictas.
  • **Borrar la fila de storage.objects con SQL.** Los metadatos desaparecen, pero el contenido se queda huérfano en el almacenamiento. Borra siempre con la API de Storage (remove).
  • Adjuntos huérfanos. Al borrar una nota, sus ficheros no se borran solos. Una tarea programada con Cron o una Edge Function que limpie ficheros sin nota resuelve la acumulación.
  • Fiarse del tipo que dice el cliente. contentType lo manda el navegador; allowed_mime_types filtra lo declarado, no el contenido real. Subida de ficheros cuenta qué más comprobar cuando el fichero se procesa.
  • Olvidar que los backups de la base de datos no incluyen los ficheros. Lo veremos en producción.

Resumen #

Lo que te llevas

  • Cada fichero son bytes en un almacenamiento compatible con S3 más una fila en storage.objects; los permisos son políticas RLS sobre esa tabla.
  • La ruta organiza los permisos: empieza por lo que decide el acceso, como {user_id}/..., y léela con storage.foldername(name).
  • Público solo afecta a la descarga; subir, sobrescribir y borrar siempre necesitan políticas, y sobrescribir pide tres.
  • Los ficheros privados se sirven con URLs firmadas de vida corta; las subidas controladas, con URLs firmadas de subida.
  • Límite de tamaño y tipos permitidos en el bucket, TUS para ficheros grandes y rutas nuevas por versión para no pelearse con la caché.
