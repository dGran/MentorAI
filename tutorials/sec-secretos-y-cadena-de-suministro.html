Secretos y cadena de suministro

Casi todo lo que corre en producción no lo escribiste tú: llega por vendor/ y viaja junto a tus credenciales. Son los dos caminos que el atacante prefiere a buscar una inyección, y los dos se cierran con hábitos baratos.

Tu código puede estar impecable y la aplicación caer igual: por una clave de API que alguien subió al repositorio hace dos años, o por una librería de la que dependes sin saberlo y que publicó una versión maliciosa el martes. Las dos cosas tienen la misma raíz: confías en algo que no controlas.

El problema: lo que no escribiste también se ejecuta #

En un backend PHP típico, casi todo lo que corre llega por vendor/, y junto al código viajan las credenciales de la base de datos, los pagos o el correo. Por eso el atacante prefiere estos dos caminos a buscar una inyección:

  • Un secreto filtrado no necesita explotar nada. Con tu clave de pagos, el atacante es tu aplicación.
  • Una dependencia comprometida se ejecuta con los mismos permisos que tu código, dentro de tu proceso, leyendo tus variables de entorno.

La parte de infraestructura —gestores de secretos, rotar sin parar el servicio— está en Configuración y secretos fuera del código; aquí va lo que depende de la aplicación.

Dónde no van los secretos #

Hay tres sitios por donde se escapan casi todas las credenciales, y ninguno es un ataque sofisticado:

DóndePor qué es un problema
El repositorioQueda en el historial, en cada clon y en cada fork. Que el repositorio sea privado solo reduce quién lo ve hoy.
La imagen DockerCada capa se puede inspeccionar; borrar el fichero en una capa posterior no lo elimina (detalle en Imágenes pequeñas y buenas prácticas).
Los logsSe copian a otros sistemas, los lee más gente que el código y se guardan meses. Un token en un log es un token publicado.

En los logs nadie escribe una clave a propósito: se cuela al volcar un objeto entero, una petición con sus cabeceras o una traza de excepción con los argumentos de cada llamada:

php · PasarelaDePago.php (vulnerable) 
<?php

declare(strict_types=1);

final class PasarelaDePago
{
    private const API_KEY = 'clave-de-produccion-de-pagos';

    public function __construct(private LoggerInterface $logger)
    {
    }

    public function cobrar(Request $request, int $centimos): void
    {
        $this->logger->info('Cobro iniciado', [
            'headers' => $request->headers->all(),
            'apiKey' => self::API_KEY,
            'centimos' => $centimos,
        ]);
    }
}

Tres fugas en diez líneas: la clave está en el código (y por tanto en el repositorio y en la imagen), se escribe en el log, y las cabeceras volcadas incluyen el Authorization del usuario. La versión corregida recibe la clave desde fuera, la marca como sensible y registra solo lo que sirve para depurar:

php · PasarelaDePago.php (corregido) 
<?php

declare(strict_types=1);

final class PasarelaDePago
{
    private string $apiKey;

    public function __construct(
        private LoggerInterface $logger,
        #[\SensitiveParameter] string $apiKey,
    ) {
        $this->apiKey = $apiKey;
    }

    public function cobrar(string $idPedido, int $centimos): void
    {
        $this->logger->info('Cobro iniciado', [
            'pedido' => $idPedido,
            'centimos' => $centimos,
        ]);
    }
}

El atributo #[\SensitiveParameter] (desde PHP 8.2) hace que ese argumento aparezca como SensitiveParameterValue en las trazas de excepción, en lugar de su valor. La clave llega por el contenedor: en Symfony, con '%env(PAGOS_API_KEY)%' y el valor en el almacén cifrado de secrets:set; en Laravel, con config('services.pagos.key') leído del .env que nunca se versiona. Cómo se organizan esos ficheros por entorno está en Configuración y entornos, y qué campos conviene registrar, en Logs estructurados.

Se ha filtrado uno: rotar primero #

El reflejo natural al ver una clave en un commit es borrarla y reescribir el historial. Es el orden equivocado. Hay bots que rastrean los repositorios públicos y prueban las credenciales en minutos. Reescribir el historial no deshace esa copia: solo evita las siguientes.

1 Revocar y emitir otraEn el proveedor, ya: la vieja deja de valer
2 Revisar el usoRegistro de accesos del proveedor desde la fecha del commit
3 Limpiar el historialgit filter-repo y aviso al equipo para reclonar
4 Cerrar la víaEscáner en pre-commit y en CI

El paso 1 es el único que protege. Los demás miden el daño y evitan que se repita.

El paso 2 es el que más se salta: si la clave estuvo expuesta tres semanas, hay que saber quién la usó mientras valía. Para rotar sin parar el servicio, mira rotar es un requisito de diseño.

bash · limpieza, después de rotar 
echo 'clave-de-produccion-de-pagos==>***REMOVED***' > reemplazos.txt
git filter-repo --replace-text reemplazos.txt
git push --force --all

El lockfile como contrato #

composer.json dice qué rangos aceptas; composer.lock dice qué versión exacta, de qué commit, se instaló y se probó. La diferencia entre ambos ya está en Composer a fondo. Desde el punto de vista de la seguridad, el lock es un contrato: lo que llega a producción es lo que alguien revisó en un pull request, y nada más.

Se rompe ejecutando composer update donde no toca. En CI y en el despliegue solo cabe composer install, que instala exactamente el lock; un update en el build lleva a producción versiones que nadie ha visto.

El lock como contrato

  • Se versiona siempre, también en aplicaciones pequeñas
  • CI y despliegue ejecutan composer install
  • Las actualizaciones llegan en un PR propio, con su diff del lock

El lock como sugerencia

  • Está en el .gitignore «porque da conflictos»
  • El Dockerfile ejecuta composer update
  • Se actualizan dependencias de paso, dentro de un cambio de negocio

composer audit y los avisos de seguridad #

El precio del lock fijo: si una versión resulta vulnerable, sigue ahí hasta que la cambies. composer audit cruza el lock con la base de avisos de seguridad que publica Packagist y termina con un código de salida distinto de cero si encuentra alguno. Eso lo convierte en una puerta de CI:

bash · paso de CI 
composer validate --strict
composer audit --locked --no-dev

--locked audita el fichero de lock sin necesidad de haber instalado vendor/, y --no-dev se centra en lo que llega a producción (conviene otra pasada sin él: las herramientas de desarrollo también corren en CI). El audit también señala los paquetes marcados como abandonados en Packagist; si eso falla el pipeline o solo avisa lo decide la opción audit.abandoned del composer.json.

Como un aviso puede publicarse un día en que nadie toca el repositorio, al audit de cada PR se suma una ejecución programada diaria sobre la rama principal.

Abandonadas, suplantadas y de sobra #

composer audit solo conoce lo que ya se ha reportado. Hay tres riesgos que no aparecen en ninguna base de avisos:

  • Dependencias abandonadas. Nadie mantiene el paquete: un fallo descubierto mañana no tendrá parche.
  • Typosquatting. Un paquete con un nombre casi idéntico a uno popular, esperando una errata en el composer require. En Packagist la trampa suele estar en el vendor: el paquete se llama igual, pero no es de quien crees.
  • Plugins de Composer. Ejecutan código durante la instalación, en tu máquina y en CI. Por eso Composer exige autorizarlos uno a uno en allow-plugins.

La defensa común es tener menos dependencias: cada paquete es código ajeno con acceso a todo tu proceso, y trae los suyos. Antes de un composer require: ¿cuántas transitivas añade?, ¿quién lo mantiene?, ¿lo hace ya el framework?, ¿son veinte líneas que puedo escribir yo?

Bloquear versiones vulnerables antes de instalarlas

El metapaquete roave/security-advisories no instala nada: declara como conflicto cada versión con aviso conocido. Así, un composer require o un update se niega a resolver hacia una versión vulnerable, en lugar de enterarte después en el audit. Desde Composer 2.9 el propio resolvedor ya lo hace por defecto (audit.block-insecure; en 2.10, policy.advisories.block); roave sigue sirviendo con versiones anteriores.

Dependabot y Renovate: que las actualizaciones vengan solas #

Actualizar a mano se deja para «cuando haya tiempo», y el día del aviso crítico estás cuatro versiones mayores por detrás. Dependabot (integrado en GitHub) y Renovate (multiplataforma y más configurable) abren un pull request por cada actualización, con el diff del lock y las notas de la versión. Tu CI lo prueba y tú decides.

yaml · .github/dependabot.yml 
version: 2
updates:
  - package-ecosystem: "composer"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 5
    groups:
      symfony:
        patterns:
          - "symfony/*"

Agrupar los paquetes que se publican juntos, como los componentes de Symfony o de Laravel, evita veinte PR para un mismo salto. El límite de PR abiertos evita una cola tan larga que el equipo acabe ignorándola.

Errores típicos #

Los que más se repiten

  • Limpiar el historial y no rotar. La clave sigue valiendo en manos de quien la copió.
  • Un .env con valores reales en el repositorio. Lo que se versiona es el .env con valores de ejemplo; los reales viven fuera.
  • Ignorar el audit «porque es de una dependencia de desarrollo». Puede que no llegue a producción, pero se ejecuta en CI, que suele tener credenciales de despliegue.
  • Fusionar los PR de Dependabot sin leerlos. Si se aceptan solos, has automatizado la puerta de entrada que quería cerrar el lock.

Cómo detectarlo #

Cada riesgo tiene un detector barato que se puede automatizar:

bash · comprobaciones 
gitleaks git --verbose
docker history --no-trunc mi-app:latest | grep -iE 'key|token|password'
composer audit
composer outdated --direct --major-only

gitleaks revisa todo el historial y, en pre-commit, para la fuga antes de que exista; en GitHub, la push protection rechaza el push si reconoce una credencial. docker history enseña los ENV y argumentos de build de cada capa. Y composer outdated mide cuánto te has alejado de lo mantenido, la deuda que el audit no ve.

Cuándo aplicarlo #

Siempre, desde el primer commit

  • Lock versionado y composer install en CI y despliegue
  • composer audit como paso que falla el pipeline
  • Escáner de secretos en pre-commit y en CI
  • Secretos inyectados al arrancar, nunca en código ni imagen

Puede esperar si…

  • Dependabot o Renovate: el proyecto es un prototipo de vida corta
  • Gestor de secretos dedicado: un solo responsable y sin credenciales reales
  • roave/security-advisories: ya bloqueas con el audit en cada PR

Si no hay tiempo para todo, empieza por lo que más protege por minuto: el audit en CI y el escáner de secretos. Las actualizaciones automáticas, en cuanto el proyecto vaya a vivir más de unos meses.

Resumen #

Lo que te llevas

  • Los secretos se escapan por el repositorio, la imagen y los logs; #[\SensitiveParameter] los saca de las trazas.
  • Ante una filtración, rotar primero: limpiar el historial evita copias nuevas, no deshace las que ya existen.
  • El lock es un contrato: solo composer install fuera de tu máquina, y las actualizaciones en su propio PR.
  • composer audit va en CI y en una ejecución programada, porque los avisos se publican cualquier día.
  • Abandonadas, typosquatting y plugins no salen en el audit: la defensa es tener menos dependencias y revisar las que entran.
  • Dependabot y Renovate traen las actualizaciones en PR; agruparlas y limitarlas es lo que hace que se revisen.
