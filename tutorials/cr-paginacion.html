Paginación que no se degrada

LIMIT 20 OFFSET 0 es instantáneo y LIMIT 20 OFFSET 200000 tarda tres segundos sobre la misma tabla. No es un bug: es que OFFSET hace lo que su nombre no sugiere.

LIMIT 20 OFFSET 0 es instantáneo. LIMIT 20 OFFSET 200000 tarda tres segundos sobre la misma tabla y el mismo índice. No es un bug del motor: es que OFFSET hace exactamente lo que su nombre no sugiere.

Lo que hace OFFSET de verdad #

No salta a la fila 200.000. Lee 200.020 filas y descarta 200.000. El motor no tiene forma de saltar sin contar, así que el coste crece linealmente con la página: la primera es gratis, la mil es carísima.

1 Página 1Lee 20 filas. 2 ms.
2 Página 100Lee 2.020 y tira 2.000. 30 ms.
3 Página 10.000Lee 200.020 y tira 200.000. 3 s.

Y si además hay un ORDER BY sin índice, el motor ordena las 200.020 antes de tirar las primeras.

Y el problema no es solo la lentitud

Con OFFSET también se saltan y se repiten filas. Si mientras el usuario pasa de la página 3 a la 4 alguien inserta un pedido nuevo que va al principio, todo se desplaza una posición: la última fila de la página 3 vuelve a salir en la 4. En un listado da igual; en un proceso que recorre todo para exportar, has duplicado un registro y saltado otro.

Paginación por clave #

La alternativa es no contar desde el principio, sino decir «dame los 20 siguientes a partir de este». En vez de un número de página, el cliente recibe un cursor con la posición de la última fila que vio:

Por desplazamiento

  • ORDER BY creado_en DESC LIMIT 20 OFFSET 200000
  • Coste creciente con la página
  • Salta y repite filas si hay escrituras
  • Permite «ir a la página 500»

Por clave (keyset)

  • WHERE (creado_en, id) < (?, ?) ORDER BY … LIMIT 20
  • Coste constante, sea la página que sea
  • Estable frente a inserciones
  • Solo permite anterior y siguiente
sql · la comparación por tuplas 
SELECT id, total, creado_en
FROM pedidos
WHERE id_cliente = 4871
  AND (creado_en, id) < ('2026-07-14 10:32:00', 88213)
ORDER BY creado_en DESC, id DESC
LIMIT 20;

El desempate es obligatorio

Fíjate en que se ordena por creado_en y por id. Si dos pedidos comparten fecha exacta y solo ordenas por fecha, el orden entre ellos no está definido: pueden salir los dos en una página, o ninguno. La clave del cursor tiene que ser única, y la forma barata de conseguirlo es añadir la clave primaria al final.

El cursor, en la API #

El cliente no debería tener que saber qué columnas forman el cursor. Se codifica en una cadena opaca y se devuelve junto a los resultados:

php · Cursor.php 
<?php

declare(strict_types=1);

final class Cursor
{
    public function __construct(
        public readonly string $creadoEn,
        public readonly int $id,
    ) {
    }

    public static function desdeCadena(string $codificado): self
    {
        $partes = json_decode(base64_decode($codificado, true), true);

        if (!is_array($partes) || !isset($partes['f'], $partes['i'])) {
            throw new CursorInvalido($codificado);
        }

        return new self((string) $partes['f'], (int) $partes['i']);
    }

    public function aCadena(): string
    {
        return base64_encode(json_encode(['f' => $this->creadoEn, 'i' => $this->id]));
    }
}

Opaca no es lo mismo que segura: base64 se lee en un segundo. Si el cursor no debe poder manipularse —porque una fila que no le toca al usuario podría colarse— hay que firmarlo, no ocultarlo.

El COUNT también es un problema #

Aunque arregles la paginación, queda el «mostrando 20 de 1.482.303». Ese COUNT(*) con los mismos filtros recorre toda la tabla, y muchas veces tarda más que la consulta de datos.

OpciónCuándo encaja
No contarPedir 21 filas para saber si hay página siguiente. Suficiente para un scroll infinito
Contar aproximado«Más de 1.000 resultados». Con un LIMIT alto en la subconsulta
Contador mantenidoUna tabla de contadores que se actualiza al escribir. Exacto y barato de leer
Contar de verdadSolo si el filtro es muy selectivo o la tabla es pequeña

La primera fila es la que más veces resuelve el problema y la que menos se plantea: casi ningún usuario necesita saber que hay 1.482.303 resultados. Necesita saber si hay más.

Cuándo aplicarlo #

Pagina por clave cuando…

  • Es un scroll infinito o un «cargar más»
  • Un proceso recorre toda la tabla: exportar, migrar, reindexar
  • Los datos cambian mientras se pagina
  • La tabla es grande y crece

OFFSET está bien cuando…

  • El usuario necesita saltar a una página concreta
  • El total de filas es pequeño y no va a crecer
  • Es un panel interno donde nadie pasa de la página 3

Resumen #

Lo que te llevas

  • OFFSET no salta filas: las lee y las descarta. El coste crece con el número de página.
  • Además salta y repite filas cuando hay escrituras concurrentes. En un listado da igual; en una exportación has duplicado registros.
  • La paginación por clave tiene coste constante y es estable, a cambio de perder el «ir a la página 500».
  • La clave del cursor tiene que ser única: añade la clave primaria al final del ORDER BY o el orden entre empates no está definido.
  • El COUNT total suele costar más que los datos. Pedir una fila de más para saber si hay página siguiente resuelve casi todos los casos.
