sync y context: coordinación y cancelación

Cuando los channels no son la solución más limpia, el paquete sync ofrece primitivas clásicas: Mutex, RWMutex y Once. El paquete context resuelve el problema de cancelar operaciones en curso y propagar deadlines a través del call stack.

Una petición llega, tu handler consulta la base de datos y llama a dos APIs, y a mitad el usuario cierra la pestaña. En PHP ese trabajo suele seguir hasta el final sin que nadie lo espere. En Go se puede cortar toda la cadena de golpe, y proteger el estado que comparten las goroutines sin montar una arquitectura de channels para cada contador.

sync.Mutex #

Un mutex (mutual exclusion) garantiza que solo una goroutine accede a un bloque de código a la vez. El equivalente en PHP sería un lock de Redis en un sistema multi-proceso, pero aquí opera a nivel de goroutines en el mismo proceso.

go 
type Contador struct {
    mu    sync.Mutex
    valor int
}

func (c *Contador) Incrementar() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.valor++
}

func (c *Contador) Valor() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.valor
}

// Uso concurrente: seguro con Mutex
contador := &Contador{}
var wg sync.WaitGroup

for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        contador.Incrementar()
    }()
}

wg.Wait()
fmt.Println(contador.Valor())   // siempre 1000

Usa siempre defer mu.Unlock() inmediatamente después de Lock(). Así el unlock es seguro aunque la función haga un return anticipado o entre en pánico.

sync.RWMutex #

Cuando el acceso es mayoritariamente de lectura y la escritura es esporádica, sync.RWMutex permite lecturas concurrentes y escritura exclusiva:

go 
type Cache struct {
    mu    sync.RWMutex
    datos map[string]string
}

// Escritura: exclusiva
func (c *Cache) Set(clave, valor string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.datos[clave] = valor
}

// Lectura: múltiples goroutines pueden leer a la vez
func (c *Cache) Get(clave string) (string, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    valor, existe := c.datos[clave]
    return valor, existe
}

Si tienes 100 goroutines leyendo, todas pueden hacerlo en paralelo con RLock. Solo cuando alguien llame a Lock se espera a que todas las lecturas terminen.

sync.Once #

sync.Once garantiza que una función se ejecuta exactamente una vez, aunque múltiples goroutines la llamen concurrentemente. Es el patrón para inicialización lazy segura:

go 
type ConexionDB struct {
    once sync.Once
    db   *sql.DB
}

func (c *ConexionDB) obtener() *sql.DB {
    c.once.Do(func() {
        var err error
        c.db, err = sql.Open("postgres", dsn)

        if err != nil {
            panic(fmt.Errorf("conectar a base de datos: %w", err))
        }
    })

    return c.db
}

Si mil goroutines llaman a obtener() simultáneamente, la función pasada a Do solo se ejecuta una vez. Las demás esperan y luego obtienen el mismo db.

context.Context #

En PHP, si el usuario cancela una petición HTTP el proceso sigue ejecutando hasta terminar. En Go, el contexto propaga la cancelación: todas las operaciones que reciben el contexto pueden detectar cuándo se cancela y detenerse.

context.Context es una interfaz con cuatro métodos:

go 
type Context interface {
    Done() <-chan struct{}      // se cierra cuando el contexto se cancela
    Err() error                 // nil o context.Canceled o context.DeadlineExceeded
    Deadline() (time.Time, bool) // cuándo vence, si tiene deadline
    Value(key any) any          // datos inmutables asociados al contexto
}

La regla del contexto en Go: siempre es el primer parámetro de una función, y se llama ctx:

go 
func buscarUsuario(ctx context.Context, id int) (*Usuario, error) {
    // pasar el contexto a operaciones que saben respetarlo
    return db.QueryContext(ctx, "SELECT * FROM usuarios WHERE id = $1", id)
}

WithCancel y WithTimeout #

Se crean contextos derivados del padre con funciones del paquete context:

go 
// WithCancel: cancelación manual
ctx, cancel := context.WithCancel(context.Background())
defer cancel()   // siempre defer cancel para liberar recursos

// WithTimeout: se cancela automáticamente después del tiempo
ctx, cancel = context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

// WithDeadline: se cancela en un momento concreto
deadline := time.Now().Add(10 * time.Second)
ctx, cancel = context.WithDeadline(context.Background(), deadline)
defer cancel()

Ejemplo completo: petición HTTP que se cancela si tarda más de 3 segundos:

go 
func obtenerPrecio(productoID string) (float64, error) {
    ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel()

    req, err := http.NewRequestWithContext(ctx, http.MethodGet,
        "https://api.precios.com/"+productoID, nil)

    if err != nil {
        return 0, fmt.Errorf("crear petición: %w", err)
    }

    resp, err := http.DefaultClient.Do(req)

    if err != nil {
        return 0, fmt.Errorf("petición fallida: %w", err)
    }

    defer resp.Body.Close()
    // ... procesar respuesta
    return 0, nil
}

Propagación del contexto #

El contexto forma un árbol: el contexto padre se propaga a los hijos. Cuando el padre se cancela, todos los hijos también se cancelan. Esto permite cancelar toda una cadena de operaciones con una sola llamada a cancel().

go 
func procesarPedido(ctx context.Context, pedidoID int) error {
    // Crear un contexto derivado con deadline más corto para esta operación
    ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()

    // Verificar stock: respeta el contexto
    if err := verificarStock(ctx, pedidoID); err != nil {
        return fmt.Errorf("verificar stock: %w", err)
    }

    // Cobrar: respeta el mismo contexto
    if err := cobrar(ctx, pedidoID); err != nil {
        return fmt.Errorf("cobrar: %w", err)
    }

    return nil
}

// Detectar cancelación en una goroutine larga
func procesarEnBucle(ctx context.Context) {
    for {
        select {
        case <-ctx.Done():
            fmt.Println("cancelado:", ctx.Err())
            return
        default:
            hacerTrabajo()
        }
    }
}

context.Background() es el contexto raíz: nunca se cancela y no tiene deadline. Úsalo en main y en los puntos de entrada del programa. context.TODO() es para cuando aún no tienes el contexto correcto (marcar deuda técnica).

Errores típicos con sync y context

  • Copiar un struct que contiene un Mutex. Un receptor por valor (func (c Contador)) copia el lock, y cada copia bloquea su propio mutex: la protección desaparece sin error. Usa receptores por puntero; go vet lo detecta.
  • Pasar de RLock a Lock sin soltar antes. El Lock espera a que terminen todas las lecturas, incluida la tuya: deadlock. Suelta el RLock, toma el Lock y vuelve a comprobar el estado, porque otro puede haberlo cambiado entre medias.
  • Olvidar el cancel(). El contexto derivado y su temporizador viven hasta que vence el plazo o se cancela el padre. defer cancel() justo después de crearlo, siempre; go vet también avisa.
  • Recibir ctx y no usarlo. El contexto no interrumpe nada por arte de magia: solo cancela lo que lo consulta. Si tu bucle largo no mira ctx.Done() o llamas a Query en vez de QueryContext, la cancelación no llega.

Cuándo aplicarlo #

Son dos herramientas para dos problemas distintos, y conviene no mezclarlas:

  • sync.Mutex cuando varias goroutines tocan el mismo estado: un mapa en memoria, un contador, una caché. Si las lecturas superan con mucho a las escrituras y has medido contención, pasa a RWMutex; si no, el Mutex normal es más simple y a menudo igual de rápido.
  • sync.Once para inicializar algo caro una sola vez y bajo demanda. Si puedes crearlo en main e inyectarlo, mejor: es más explícito y más fácil de testear.
  • context.Context en toda función que haga E/S o pueda tardar: consultas, llamadas HTTP, esperas. Se recibe como primer parámetro y se pasa hacia abajo, aunque tú no lo uses.

Cuándo no: no uses un mutex para pasar datos de una goroutine a otra (eso es un channel), ni context.WithValue para pasar parámetros normales de una función. Los valores del contexto son para datos transversales de la petición, como un ID de traza o el usuario autenticado; lo demás va en la firma, donde el compilador lo ve.

Resumen #

Lo que te llevas

  • sync.Mutex protege secciones críticas con acceso exclusivo. Siempre defer mu.Unlock() justo después del Lock().
  • sync.RWMutex permite lecturas concurrentes (RLock/RUnlock) y escritura exclusiva (Lock/Unlock). Ideal para cachés de lectura intensiva.
  • sync.Once ejecuta una función exactamente una vez aunque múltiples goroutines la invoquen. Patrón para inicialización lazy segura.
  • context.Context propaga cancelación y deadlines por el call stack. Siempre es el primer parámetro, se llama ctx, y siempre se hace defer cancel().
  • context.WithTimeout y context.WithDeadline crean contextos que se cancelan automáticamente. El árbol de contextos: cancelar el padre cancela todos los hijos.
