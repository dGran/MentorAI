Concurrencia con threads y canales

Threads seguros en Rust gracias al sistema de tipos, paso de mensajes con canales, Mutex y RwLock, y cómo Rust garantiza ausencia de data races en compilación.

std::thread::spawn

Rust usa threads del sistema operativo (1:1 mapping). No hay un runtime de hilos ligeros como las goroutines de Go: cada thread de Rust es un thread real del OS.

use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=5 {
            println!("thread: {}", i);
            thread::sleep(Duration::from_millis(100));
        }
    });

    for i in 1..=3 {
        println!("main: {}", i);
        thread::sleep(Duration::from_millis(150));
    }

    handle.join().unwrap(); // espera a que el thread termine
}

thread::spawn recibe una closure y retorna un JoinHandle. Llamar a .join() bloquea el thread actual hasta que el spawneado termine.

La closure que pasa a spawn debe ser 'static y Send. Esto significa que no puede capturar referencias a variables locales del thread llamador (que podrían destruirse antes de que el thread termine). Si necesitas datos del entorno, muévelos con move:

fn main() {
    let mensaje = String::from("hola desde el thread");

    let handle = thread::spawn(move || {
        println!("{}", mensaje); // mensaje se movió al thread
    });

    // mensaje ya no está disponible aquí
    handle.join().unwrap();
}

Los traits Send y Sync

Los traits Send y Sync son los que hacen que la concurrencia de Rust sea segura en el tipo:

  • Send: el tipo puede moverse a otro thread. La mayoría de tipos implementan Send. Los que no: Rc<T> (el conteo de referencias no es atómico), punteros raw, algunos tipos de la GUI.
  • Sync: el tipo puede referenciarse desde múltiples threads simultáneamente. Si T: Sync, entonces &T: Send.
use std::rc::Rc;
use std::thread;

fn main() {
    let rc = Rc::new(5);

    thread::spawn(move || {
        println!("{}", rc); // error[E0277]: `Rc<i32>` cannot be sent between threads safely
    });
}

El compilador rechaza este código porque Rc<i32> no implementa Send. El error aparece en compilación, no en producción bajo carga. Este es el valor fundamental de Rust en concurrencia: las garantías son estáticas.

La implementación de Send y Sync es automática para los tipos que solo contienen tipos Send/Sync. Si defines un struct con todos los campos Send, el struct también es Send automáticamente.

Canales mpsc

std::sync::mpsc proporciona canales de paso de mensajes: Multiple Producer, Single Consumer. Un canal tiene un transmisor (tx) y un receptor (rx). Puedes clonar el transmisor para tener múltiples productores.

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    let tx1 = tx.clone();
    let tx2 = tx.clone();

    thread::spawn(move || {
        for i in 0..5 {
            tx1.send(format!("thread 1: {}", i)).unwrap();
        }
    });

    thread::spawn(move || {
        for i in 0..5 {
            tx2.send(format!("thread 2: {}", i)).unwrap();
        }
    });

    drop(tx); // cerramos el tx original para que rx.iter() sepa cuándo parar

    for mensaje in rx.iter() {
        println!("{}", mensaje);
    }
}

El canal de Rust tiene semántica de ownership: enviar un mensaje mueve el valor. El receptor es el nuevo dueño. Esto garantiza que no hay acceso concurrente al mismo dato: el sender ya no tiene el dato cuando el receiver lo recibe.

Patrón worker pool: crea N threads con un transmisor cada uno y un receptor compartido (con Arc<Mutex<Receiver>>). Distribuye trabajo enviando tareas al canal. Los threads compiten por las tareas del receptor.

Arc<Mutex<T>>: estado compartido

Cuando múltiples threads necesitan acceder y modificar el mismo dato, el patrón es Arc<Mutex<T>>:

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let resultados: Arc<Mutex<Vec<u64>>> = Arc::new(Mutex::new(Vec::new()));

    let handles: Vec<_> = (0..8u64).map(|i| {
        let resultados = Arc::clone(&resultados);
        thread::spawn(move || {
            let calculo = (0..=i).sum::();
            resultados.lock().unwrap().push(calculo);
        })
    }).collect();

    for handle in handles {
        handle.join().unwrap();
    }

    let mut datos = resultados.lock().unwrap();
    datos.sort();
    println!("{:?}", *datos);
}

El MutexGuard retornado por .lock() implementa Deref y DerefMut, así que puedes usarlo como el tipo interior. Se libera automáticamente al salir de scope.

Rayon: paralelismo de datos

Para paralelismo de datos (aplicar la misma operación sobre una colección usando todos los cores), Rayon es la solución más ergonómica. Convierte cualquier iterador secuencial en paralelo con un cambio mínimo:

use rayon::prelude::*;

fn main() {
    let datos: Vec<u64> = (1..=1_000_000).collect();

    let suma_secuencial: u64 = datos.iter().sum();
    let suma_paralela: u64 = datos.par_iter().sum(); // mismo resultado, más rápido

    println!("Secuencial: {}", suma_secuencial);
    println!("Paralela: {}", suma_paralela);

    let cuadrados: Vec<u64> = datos.par_iter().map(|&x| x * x).collect();
    println!("{} cuadrados calculados", cuadrados.len());
}

Rayon gestiona un pool de threads internamente y distribuye el trabajo automáticamente. No necesitas preocuparte por el número de threads, la división del trabajo ni la sincronización.

Rayon en Cargo.toml: rayon = "1". No es parte de la stdlib pero es la librería de facto para paralelismo de datos en Rust.

Rust vs Go en concurrencia

Rust y Go tienen modelos de concurrencia muy distintos con filosofías diferentes:

AspectoGoRust
Unidad de concurrenciaGoroutines (ligeras, M:N scheduling)Threads del OS (1:1) o tasks async (con runtime)
Coste de crear 1000 unidadesBajo (goroutines son muy baratas)Alto para threads; bajo con async tasks
Comunicación preferidaCanales ("Don't communicate by sharing memory")Canales o estado compartido (ambos idiomáticos)
Garantías de data racesPor convención y el race detector en testsGarantizado por el compilador en tiempo de compilación
GCSí (con pausas)No (destrucción determinista)
Uso típicoServicios web, concurrencia I/O intensivaServicios con latencia crítica, CPU intensivo

La diferencia clave: Go garantiza la ausencia de data races con el race detector (una herramienta que ejecutas en tests). Rust la garantiza en compilación, sin necesidad de ejecutar nada. Un bug que Go detecta en tests o producción, Rust lo detecta antes de que exista el binario.

Resumen

  • Rust usa threads del OS (1:1). Las closures pasadas a thread::spawn deben ser 'static + Send; el compilador lo verifica.
  • Los traits Send y Sync codifican la seguridad entre threads en el sistema de tipos. El compilador rechaza código que comparte tipos no-Send entre threads.
  • Los canales mpsc transfieren ownership del dato: el sender ya no tiene acceso después de enviar, garantizando ausencia de acceso concurrente.
  • Arc<Mutex<T>> es el patrón estándar para estado mutable compartido entre threads. El MutexGuard usa RAII para garantizar que el lock se libere.
  • Rayon convierte iteradores secuenciales en paralelos con .par_iter(); gestiona el pool de threads automáticamente.
  • Rust garantiza ausencia de data races en compilación; Go lo hace con el race detector en runtime. La garantía de Rust es más fuerte.
