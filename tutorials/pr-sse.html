Server-Sent Events: el que casi nadie usa

Casi todo lo que se resuelve con WebSockets es en realidad unidireccional: el servidor empuja y el cliente escucha. Para eso existe una tecnología que es HTTP normal, va sobre la infraestructura que ya tienes y reconecta sola. Y casi nadie la usa.

HTTP que no se cierra #

Un endpoint de Server-Sent Events es una respuesta HTTP corriente con un Content-Type especial y un cuerpo que no termina. El servidor va escribiendo eventos en formato de texto y el navegador los entrega conforme llegan.

bash · el formato entero 
Content-Type: text/event-stream

id: 1042
event: pedido-actualizado
data: {"id":"4871","estado":"enviado"}

: este es un comentario, sirve de latido

Eso es todo el protocolo: cuatro campos —id, event, data y retry— separados por líneas en blanco. No hay handshake de actualización, ni tramas, ni librería en el cliente: el navegador trae EventSource de serie.

La reconexión viene hecha #

Es la característica que más lo diferencia de WebSockets y la que menos se menciona. Si la conexión se corta, el navegador reconecta solo, y además manda el identificador del último evento recibido:

1 El cliente recibe hasta el evento 1042Y se le va el wifi
2 Manda Last-Event-ID: 1042Sin que tú escribas una línea
3 El servidor reanuda desde el 1043Si guardas los eventos recientes, no se pierde nada

Con WebSockets, todo esto —detectar el corte, reintentar con backoff, saber por dónde ibas— lo escribes tú.

Y hereda todo lo que ya tienes montado

Es HTTP: pasa por tu autenticación con cookies, tus cabeceras, tu proxy, tu limitador de tasa. No hay que configurar nada especial en nginx salvo desactivar el buffering, ni abrir puertos, ni tratar un protocolo aparte en el balanceador. Esa continuidad vale mucho en un sistema que ya funciona.

Sus dos limitaciones reales #

Es unidireccional. El cliente no puede mandar nada por ese canal; para eso hace un POST normal. En la práctica no molesta —enviar es puntual y recibir es continuo— y conceptualmente es incluso más limpio.

Solo texto. Para binario hay que codificar en base64, con el 33 % de sobrecoste. Si mandas audio o vídeo, este no es tu protocolo.

Y una tercera que se resolvió sola

Sobre HTTP/1.1, el límite de seis conexiones por dominio se aplicaba también a SSE: con seis pestañas abiertas, la séptima se quedaba colgada. Sobre HTTP/2 ese límite desapareció con la multiplexación. Si lees que «SSE no escala por el límite de conexiones», es información de la era HTTP/1.1.

El problema en PHP, y su salida #

Mantener una respuesta abierta ocupa un proceso de FPM, exactamente igual que el long polling. Un endpoint SSE ingenuo con doscientos usuarios conectados te deja sin workers:

php · esto ocupa un worker mientras dure 
<?php

declare(strict_types=1);

final class EventosController
{
    private const LATIDO_SEGUNDOS = 15;
    private const VIDA_MAXIMA_SEGUNDOS = 60;

    public function __invoke(): StreamedResponse
    {
        $respuesta = new StreamedResponse(function (): void {
            $fin = hrtime(true) + self::VIDA_MAXIMA_SEGUNDOS * 1e9;

            while (hrtime(true) < $fin) {
                foreach ($this->eventos->pendientes() as $evento) {
                    echo "id: {$evento->id()}\n";
                    echo "data: {$evento->json()}\n\n";
                }

                echo ": latido\n\n";
                flush();
                sleep(self::LATIDO_SEGUNDOS);
            }
        });

        $respuesta->headers->set('Content-Type', 'text/event-stream');
        $respuesta->headers->set('X-Accel-Buffering', 'no');

        return $respuesta;
    }
}

Dos detalles importantes ahí. El latido —esa línea de comentario— es lo que evita que proxies y balanceadores corten la conexión por inactividad. Y X-Accel-Buffering: no le dice a nginx que no acumule la respuesta antes de mandarla; sin eso, tus eventos llegan a ráfagas o no llegan.

La vida máxima de 60 segundos no es un parche: es el diseño

Cerrar a propósito y dejar que el navegador reconecte convierte un problema —ocupar un worker— en un ciclo controlado, y aprovecha justo la reconexión automática que SSE te regala. Aun así, para cientos de conexiones simultáneas la salida real es sacar el endpoint de FPM: un runtime asíncrono como RoadRunner, o un componente aparte.

Cuándo aplicarlo #

SSE cuando…

  • El flujo es del servidor al cliente y ya está
  • Quieres reconexión y reanudación sin escribirlas
  • Valoras que sea HTTP y herede tu autenticación y tus proxies
  • Notificaciones, paneles, progreso de tareas, respuestas de IA

No encaja cuando…

  • El cliente manda mensajes continuamente
  • Mueves datos binarios
  • Necesitas latencia por debajo de decenas de milisegundos
  • Tu stack es FPM y no puedes añadir otro runtime

Resumen #

Lo que te llevas

  • SSE es HTTP normal con un cuerpo que no termina: cuatro campos de texto y EventSource ya viene en el navegador.
  • La reconexión con reanudación desde el último evento viene hecha. Con WebSockets todo eso lo escribes tú.
  • Hereda tu autenticación, tus proxies y tu limitador de tasa, porque no deja de ser una petición HTTP.
  • El latido evita que los proxies corten por inactividad, y X-Accel-Buffering: no evita que nginx acumule los eventos.
  • Cerrar a propósito cada minuto y dejar que reconecte convierte el problema del worker ocupado en un ciclo controlado.
