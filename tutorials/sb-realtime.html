Realtime: cambios, broadcast y presencia

Dos personas editan la misma libreta y cada una ve aparecer las notas de la otra sin recargar. Alguien está escribiendo y sale su avatar arriba. Supabase Realtime da eso con unas líneas, sobre WebSockets que no tienes que operar. Lo que sí tienes que elegir es cuál de sus tres modos usar, porque escalan de forma muy distinta.

La app de notas ya comparte notas entre usuarios. Lo que falta es que el cambio de uno llegue al instante a los demás. Si los conceptos de WebSocket y conexión persistente son nuevos para ti, WebSockets los explica fuera de Supabase.

Tres modos para tres problemas #

Realtime es un servidor que mantiene una conexión WebSocket con cada cliente. Los clientes se apuntan a canales (un nombre, como notebook:42) y por cada canal pueden usar tres cosas:

ModoQué transportaEjemplo en la app de notas
Postgres ChangesLos inserts, updates y deletes de una tabla, según los ve la base de datosVer aparecer una nota que otro acaba de crear
BroadcastMensajes efímeros que un cliente (o la base de datos) manda al canalLa posición del cursor de otro usuario, «está escribiendo…»
PresenceEl estado compartido de quién está conectado al canalLos avatares de quién tiene abierta la libreta

Entre clientes, Broadcast y Presence no tocan la base de datos: los mensajes pasan por el servidor de Realtime y se reparten a quien esté conectado en ese momento. Postgres Changes, en cambio, nace de la base de datos.

Postgres Changes: escuchar una tabla #

Primero hay que decirle a Postgres que publique los cambios de la tabla. Realtime los lee de la publicación supabase_realtime:

sql · publicar los cambios de las notas 
alter publication supabase_realtime add table public.notes;
ts · escuchar las notas de una libreta 
const channel = supabase
  .channel("notebook-42-notes")
  .on(
    "postgres_changes",
    { event: "*", schema: "public", table: "notes", filter: "notebook_id=eq.42" },
    (change) => {
      if (change.eventType === "INSERT") addNote(change.new);
      if (change.eventType === "UPDATE") updateNote(change.new);
      if (change.eventType === "DELETE") removeNote(change.old);
    },
  )
  .subscribe();

Postgres Changes respeta RLS: cada usuario solo recibe los cambios de las filas que podría leer. Y eso tiene un coste que conviene entender antes de usarlo a lo grande:

Por qué Postgres Changes no escala lejos

Para respetar RLS, cada cambio se comprueba por cada suscriptor: si 100 personas escuchan la tabla y entra un insert, son 100 comprobaciones de autorización contra la base de datos. Esas comprobaciones se procesan en orden, así que un pico de escrituras con muchos suscriptores retrasa todos los avisos. Los borrados tienen además sus rarezas: en un DELETE suele llegar solo la clave primaria de la fila borrada, no la fila entera, y los filtros como notebook_id=eq.42 no se aplican a ellos. Para pocas decenas de usuarios por tabla va de sobra; para más, la documentación de Supabase recomienda Broadcast desde la base de datos.

Broadcast: mensajes al canal #

Broadcast manda un mensaje a todos los que están en el canal, sin pasar por ninguna tabla. Entre clientes:

ts · el cursor de cada usuario, a los demás 
const room = supabase.channel("notebook:42", { config: { private: true } });

room
  .on("broadcast", { event: "cursor" }, ({ payload }) => moveCursor(payload.userId, payload.x, payload.y))
  .subscribe();

room.send({ type: "broadcast", event: "cursor", payload: { userId, x: 120, y: 340 } });

Broadcast desde la base de datos

La forma escalable de avisar de cambios en tablas es que un trigger publique el cambio en un canal. La comprobación de permisos se hace una vez, al entrar en el canal, en lugar de por cada cambio y suscriptor:

sql · cada cambio de una nota, al canal de su libreta 
create function private.broadcast_note_change()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
begin
  perform realtime.broadcast_changes(
    'notebook:' || coalesce(new.notebook_id, old.notebook_id)::text,
    tg_op,
    tg_op,
    tg_table_name,
    tg_table_schema,
    new,
    old
  );

  return null;
end;
$$;

create trigger notes_broadcast
after insert or update or delete on public.notes
for each row execute function private.broadcast_note_change();
ts · el cliente escucha el canal de la libreta 
supabase
  .channel("notebook:42", { config: { private: true } })
  .on("broadcast", { event: "INSERT" }, ({ payload }) => addNote(payload.record))
  .on("broadcast", { event: "UPDATE" }, ({ payload }) => updateNote(payload.record))
  .on("broadcast", { event: "DELETE" }, ({ payload }) => removeNote(payload.old_record))
  .subscribe();

Para mensajes que no son el cambio de una fila (un aviso de «exportación terminada», por ejemplo), realtime.send(payload, evento, canal, privado) manda un JSON cualquiera a un canal desde SQL.

Presence: quién está aquí #

Presence mantiene un estado compartido por canal: cada cliente declara el suyo con track, y todos reciben la foto completa cuando cambia. Si un cliente se desconecta (cierra la pestaña, pierde la red), el servidor lo quita solo.

ts · quién tiene abierta la libreta 
const room = supabase.channel("notebook:42", { config: { private: true } });

room
  .on("presence", { event: "sync" }, () => {
    const state = room.presenceState();
    renderAvatars(Object.values(state).flat());
  })
  .subscribe(async (status) => {
    if (status !== "SUBSCRIBED") return;

    await room.track({ userId, name: displayName, onlineAt: new Date().toISOString() });
  });

Presence es para estado pequeño que cambia poco (quién está, en qué nota). Para algo que cambia muchas veces por segundo, como la posición del ratón, usa Broadcast.

Canales privados: quién puede entrar #

Un canal público lo puede escuchar cualquiera que conozca su nombre y tenga la clave publicable. Para la app de notas, eso significa que cualquiera podría escuchar notebook:42. Los canales privados se autorizan con políticas RLS sobre la tabla realtime.messages:

sql · solo entran al canal de una libreta quienes pueden verla 
create policy "Escuchar libretas propias"
on realtime.messages for select to authenticated
using (
  realtime.messages.extension in ('broadcast', 'presence')
  and (select realtime.topic()) like 'notebook:%'
  and exists (
    select 1 from public.notebooks
    where id = split_part((select realtime.topic()), ':', 2)::bigint
      and user_id = (select auth.uid())
  )
);

create policy "Emitir en libretas propias"
on realtime.messages for insert to authenticated
with check (
  realtime.messages.extension in ('broadcast', 'presence')
  and exists (
    select 1 from public.notebooks
    where id = split_part((select realtime.topic()), ':', 2)::bigint
      and user_id = (select auth.uid())
  )
);

realtime.topic() devuelve el canal al que se intenta entrar; select controla recibir e insert controla enviar (incluido track de Presence). En el cliente, el canal se crea con private: true, y en los ajustes de Realtime se desactiva el acceso público para que nadie pueda saltarse las políticas usando un canal no privado.

Se comprueba al entrar, no en cada mensaje

Las políticas se evalúan cuando el cliente se une al canal. Si le quitas el acceso a la libreta, seguirá recibiendo mensajes hasta que su token caduque o se reconecte. Es otra razón para mantener corta la vida del access token.

Límites y buenas costumbres #

  • Conexiones simultáneas y mensajes al mes dependen del plan (200 conexiones y 2 millones de mensajes en el gratuito, con mensajes de hasta 256 KB). Cada pestaña abierta es una conexión.
  • Quita los canales que ya no usas. Al salir de una pantalla, supabase.removeChannel(channel); si no, la conexión sigue suscrita y recibiendo.
  • Al reconectar, vuelve a cargar. Mientras el cliente estuvo sin conexión se perdió los mensajes de ese rato: Realtime no se los reenvía. Tras una reconexión, pide el estado actual a la Data API.
  • Los mensajes no son la fuente de verdad. Realtime avisa; la base de datos manda. Pinta lo que llega, pero no construyas el estado solo a base de mensajes.

Cuándo aplicarlo #

NecesitasModo
Que unos pocos usuarios vean cambios de una tabla, con RLS y sin más montajePostgres Changes
Avisar de cambios de tablas a muchos suscriptoresBroadcast desde un trigger con realtime.broadcast_changes
Cursores, «está escribiendo», reacciones efímerasBroadcast entre clientes
Saber quién está conectadoPresence
Que la información llegue en minutos, no en segundosNada de tiempo real: consultar al abrir la pantalla o cada cierto tiempo

La última fila importa más de lo que parece: el tiempo real añade conexiones abiertas, reconexiones y estados a mantener. Cuándo no hace falta tiempo real ayuda a decidir si te compensa.

Resumen #

Lo que te llevas

  • Realtime tiene tres modos: Postgres Changes (cambios de tablas), Broadcast (mensajes al canal) y Presence (quién está conectado).
  • Postgres Changes necesita la tabla en la publicación supabase_realtime y respeta RLS comprobando cada cambio por suscriptor, lo que limita cuánto escala.
  • Broadcast desde un trigger con realtime.broadcast_changes es la forma escalable de avisar de cambios en tablas.
  • Presence mantiene un estado compartido pequeño y quita solo a quien se desconecta.
  • Los canales privados se autorizan con políticas sobre realtime.messages y realtime.topic(), evaluadas al entrar.
  • Realtime no reenvía los mensajes perdidos: al reconectar se recarga el estado desde la base de datos.
