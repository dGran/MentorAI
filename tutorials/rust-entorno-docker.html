Entorno Rust con Docker

Montar un entorno de desarrollo Rust completamente dockerizado: imagen oficial, volumen para las fuentes, caché de dependencias de Cargo y acceso desde el editor del host.

El primer cargo build de un proyecto con unas cuantas dependencias puede tardar minutos, y si tu entorno lo tira todo en cada docker compose up, pagarás esos minutos cada mañana. El objetivo no es solo que Rust compile dentro de un contenedor, sino que la segunda compilación sea casi inmediata y que el host siga limpio: sin rustup ni toolchains mezclados entre proyectos.

Por qué dockerizar el entorno #

Rust instala con rustup y los toolchains cambian entre proyectos (stable, nightly, versiones concretas). Con Docker, el toolchain vive en la imagen y cada proyecto lleva el suyo sin conflictos. Mismo principio que el curso de Go: el host solo necesita Docker y un editor.

Estructura del proyecto #

bash 
mi-proyecto/
├── src/
│   └── main.rs
├── Cargo.toml
├── Dockerfile.dev
└── compose.yml

Cargo gestiona las dependencias en Cargo.toml (equivalente a composer.json) y genera Cargo.lock con versiones exactas.

El Dockerfile de desarrollo #

bash 
FROM rust:1.99-slim

WORKDIR /app

RUN apt-get update && apt-get install -y \
    pkg-config \
    libssl-dev \
    && rm -rf /var/lib/apt/lists/*

ENV CARGO_HOME=/cargo-cache
ENV PATH="$CARGO_HOME/bin:$PATH"

CMD ["watchexec", "-r", "-e", "rs,toml", "--", "cargo", "run"]

La imagen oficial rust:1.99-slim incluye rustc, cargo y rustup. La variable CARGO_HOME mueve el caché fuera del contenedor (lo explicamos abajo).

Para desarrollo activo, watchexec relanza cargo run al guardar, igual que nodemon. Es lo que recomienda el propio cargo-watch, archivado y sin mantenimiento desde enero de 2025. Si prefieres una vista en la terminal con errores y tests en vivo, la otra opción que recomienda es bacon:

bash 
RUN cargo install --locked --root /usr/local watchexec-cli

Docker Compose #

bash 
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile.dev
    volumes:
      - .:/app
      - cargo-cache:/cargo-cache
    ports:
      - "3000:3000"
    environment:
      - RUST_LOG=debug

volumes:
  cargo-cache:

El volumen .:/app monta el código fuente del host dentro del contenedor, igual que en PHP/Go. Los cambios en el editor son inmediatos para watchexec.

Caché de dependencias #

Este es el punto más importante para no perder tiempo. Cargo descarga y compila dependencias la primera vez; si el volumen cargo-cache no existe, cada docker compose up recompila todo desde cero (puede tardar varios minutos).

El volumen nombrado cargo-cache persiste el directorio CARGO_HOME entre arranques. También conviene cachear el directorio target/:

bash 
volumes:
  - .:/app
  - cargo-cache:/cargo-cache
  - target-cache:/app/target   # compila incremental entre sesiones

Sin este caché, una sesión nueva descarga e compila todas las dependencias de cero. Con él, solo recompila lo que cambió.

Errores típicos al dockerizar Rust

Escuchar en 127.0.0.1 dentro del contenedor. El ports: "3000:3000" publica el puerto, pero si tu servidor hace bind a 127.0.0.1:3000 solo acepta conexiones desde dentro del propio contenedor y el navegador del host no llega. Haz bind a 0.0.0.0:3000.

Instalar herramientas donde luego monta un volumen. Con CARGO_HOME=/cargo-cache, cargo install watchexec-cli deja el binario en /cargo-cache/bin de la imagen. Un volumen nombrado vacío copia ese contenido la primera vez, pero si el volumen ya existía lo tapa y el arranque falla porque no encuentra watchexec. Instala las herramientas fuera del volumen, por ejemplo con cargo install --root /usr/local watchexec-cli.

Ficheros de root en tu máquina. En Linux el contenedor corre como root por defecto, así que lo que genera en el bind mount (Cargo.lock, un cargo new) aparece con dueño root en el host. Ejecuta el servicio con tu UID (user: en compose) y ajusta los permisos de los volúmenes.

Dejar target/ en el bind mount. Crece a varios gigas y, en macOS y Windows, la E/S compartida lo hace todo más lento. El volumen target-cache lo saca del host.

Flujo de trabajo diario #

bash 
# Primera vez o tras cambiar Dockerfile
docker compose build

# Arrancar el entorno
docker compose up

# Entrar al contenedor para comandos cargo
docker compose exec app bash

# Añadir una dependencia
docker compose exec app cargo add tokio --features full

# Ejecutar tests
docker compose exec app cargo test

# Ver logs del compilador en vivo (watchexec lo hace solo)
# Guardar cualquier .rs → cargo recompila y relanza

cargo add es el equivalente a composer require: añade la crate al Cargo.toml y actualiza el lock. Disponible desde Rust 1.62.

Cuándo aplicarlo #

Aplícalo cuando…

  • Tu equipo ya trabaja dockerizado en PHP o Go y quieres el mismo flujo: el host solo tiene Docker y el editor
  • El proyecto depende de bibliotecas del sistema (OpenSSL, libpq) y quieres las mismas versiones en local, en CI y en producción
  • Mantienes varios proyectos con toolchains distintos y no quieres que se pisen

Y elige otra cosa cuando…

  • Trabajas en macOS o Windows con un proyecto grande: la E/S del volumen compartido penaliza la compilación, y rustup en el host es bastante más rápido. rustup ya aísla la versión por proyecto con rust-toolchain.toml
  • Es un proyecto en Rust puro, sin dependencias del sistema, y trabajas solo: rustup local te ahorra una capa
  • Vas a desplegar: esta imagen de desarrollo lleva el compilador entero. Para producción, un build multi-stage que copie solo el binario a una imagen mínima

Un término medio habitual: rustup en el host para que el editor vaya fino, y el contenedor para lo que debe ser reproducible (tests, build de CI, dependencias del sistema).

Resumen #

Lo que te llevas

  • La imagen oficial rust:VERSION-slim incluye todo el toolchain; no hace falta instalar nada en el host.
  • El volumen del código (.:/app) da acceso inmediato desde el editor del host.
  • El volumen cargo-cache sobre CARGO_HOME es crítico: sin él, cada sesión recompila todas las dependencias.
  • watchexec -r -e rs,toml -- cargo run relanza el servidor al guardar, igual que nodemon en Node; cargo-watch está archivado.
  • El directorio target/ en un volumen propio acelera la compilación incremental entre sesiones.
