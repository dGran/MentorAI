Patrones creacionales: Factory, Builder y Singleton

Los patrones creacionales resuelven cómo crear objetos sin acoplar el código a clases concretas. Factory Method delega la decisión, Builder construye paso a paso, y Singleton — el más conocido y el más mal usado — gestiona una única instancia.

El problema común de los patrones creacionales: el código que usa un objeto no debería saber cómo se crea. Si lo sabe, está acoplado a la implementación concreta y cualquier cambio en la creación se propaga por todo el sistema.

Factory Method #

El problema: tienes código que necesita crear un objeto, pero el tipo concreto depende de algo externo (configuración, contexto, tipo de entrada). Si metes el new ClaseConcreto() directamente, el código queda acoplado a esa clase y cualquier variante exige modificarlo.

La solución del Factory Method: delega la creación a un método que las subclases (o implementaciones de una interfaz) sobreescriben. El código que llama trabaja con la interfaz; el método factory decide qué clase concreta instanciar.

php · NotificationFactory.php 
<?php

declare(strict_types=1);

interface Notification
{
    public function send(string $message): void;
}

class EmailNotification implements Notification
{
    public function send(string $message): void
    {
        // envía email
    }
}

class SmsNotification implements Notification
{
    public function send(string $message): void
    {
        // envía SMS
    }
}

class NotificationFactory
{
    public static function create(string $channel): Notification
    {
        return match ($channel) {
            'email' => new EmailNotification(),
            'sms'   => new SmsNotification(),
            default => throw new \InvalidArgumentException("Canal desconocido: {$channel}"),
        };
    }
}

// El código que usa la notificación no sabe qué clase concreta recibe
$notification = NotificationFactory::create($config['channel']);
$notification->send('Pedido confirmado');

El código cliente trabaja con la interfaz Notification. Añadir un nuevo canal (push, slack) es añadir una clase y ampliar el match en la factory — nada más cambia. Esto es lo que DIP recomendaba: depender de abstracciones, no de implementaciones concretas.

Simple Factory vs Factory Method

Lo del ejemplo es técnicamente una Simple Factory (un método estático que centraliza la creación). El Factory Method GoF puro delega en subclases. En la práctica, la Simple Factory resuelve el mismo problema con menos complejidad y es más frecuente en PHP. El nombre "Factory Method" se usa indistintamente para ambas formas.

Abstract Factory #

Cuando no es un solo objeto sino una familia de objetos que deben ser compatibles entre sí, el Factory Method solo no basta. Abstract Factory proporciona una interfaz para crear familias enteras de objetos relacionados sin especificar sus clases concretas.

Ejemplo clásico: un sistema que soporta varios motores de almacenamiento (MySQL, PostgreSQL). Cada motor tiene su propia implementación de conexión, constructor de consultas y gestor de transacciones — y deben ser compatibles entre sí. No puedes mezclar una conexión de MySQL con un query builder de PostgreSQL.

php · DatabaseFactory.php 
<?php

declare(strict_types=1);

interface DatabaseFactory
{
    public function createConnection(): Connection;
    public function createQueryBuilder(): QueryBuilder;
}

class MysqlFactory implements DatabaseFactory
{
    public function createConnection(): Connection
    {
        return new MysqlConnection();
    }

    public function createQueryBuilder(): QueryBuilder
    {
        return new MysqlQueryBuilder();
    }
}

class PostgresFactory implements DatabaseFactory
{
    public function createConnection(): Connection
    {
        return new PostgresConnection();
    }

    public function createQueryBuilder(): QueryBuilder
    {
        return new PostgresQueryBuilder();
    }
}

// El código de aplicación recibe la factory y crea objetos compatibles entre sí
function buildRepository(DatabaseFactory $factory): Repository
{
    $connection   = $factory->createConnection();
    $queryBuilder = $factory->createQueryBuilder();

    return new Repository($connection, $queryBuilder);
}

Cambiar el motor es cambiar qué factory se inyecta. El código de aplicación no sabe nada del motor concreto. Cruza directamente con el contenedor DI: la factory se registra en el contenedor y se inyecta donde se necesita.

Builder #

Cuando un objeto necesita muchos parámetros para construirse y algunos son opcionales, el constructor se vuelve ilegible: new Email(null, true, false, null, 'html', 3). Builder resuelve esto separando la construcción del objeto de su representación final, permitiendo construirlo paso a paso con métodos encadenados.

php · EmailBuilder.php 
<?php

declare(strict_types=1);

class EmailBuilder
{
    private string $to = '';
    private string $subject = '';
    private string $body = '';
    private string $contentType = 'text/plain';
    private array $attachments = [];

    public function to(string $address): static
    {
        $this->to = $address;

        return $this;
    }

    public function subject(string $subject): static
    {
        $this->subject = $subject;

        return $this;
    }

    public function htmlBody(string $html): static
    {
        $this->body = $html;
        $this->contentType = 'text/html';

        return $this;
    }

    public function attach(string $path): static
    {
        $this->attachments[] = $path;

        return $this;
    }

    public function build(): Email
    {
        if ($this->to === '' || $this->subject === '') {
            throw new \LogicException('to y subject son obligatorios');
        }

        return new Email($this->to, $this->subject, $this->body, $this->contentType, $this->attachments);
    }
}

// Uso: legible, autodocumentado, sin posición de parámetros
$email = (new EmailBuilder())
    ->to('user@example.com')
    ->subject('Confirmación de pedido')
    ->htmlBody('<h1>¡Gracias!</h1>')
    ->attach('/tmp/factura.pdf')
    ->build();

El Builder es omnipresente en PHP: los query builders de Doctrine o Eloquent, el HttpClientBuilder de Symfony, los form builders, los test fixtures con datos opcionales. Lo reconocerás en cualquier librería que use encadenamiento de métodos para configurar un objeto complejo antes de crearlo.

Singleton #

Singleton garantiza que una clase tiene exactamente una instancia y proporciona un punto de acceso global a ella. En el papel resuelve un problema real: recursos costosos o únicos por naturaleza (una conexión a BD, un logger, un registro de configuración).

php · Singleton clásico 
<?php

declare(strict_types=1);

class Registry
{
    private static ?self $instance = null;
    private array $data = [];

    private function __construct() {}

    public static function getInstance(): static
    {
        if (static::$instance === null) {
            static::$instance = new static();
        }

        return static::$instance;
    }

    public function get(string $key): mixed
    {
        return $this->data[$key] ?? null;
    }

    public function set(string $key, mixed $value): void
    {
        $this->data[$key] = $value;
    }
}

Por qué el Singleton se odia

El acceso global esconde dependencias. Si una clase llama a Registry::getInstance() internamente, esa dependencia es invisible desde fuera: no aparece en el constructor, no se puede sustituir en tests, no puedes inyectar una variante distinta. El Singleton viola DIP (depende de la implementación concreta) y SRP (gestiona su propio ciclo de vida además de su responsabilidad principal). En la práctica, los contenedores DI resuelven el mismo problema —una sola instancia compartida— sin estos inconvenientes.

Singleton — dependencia oculta

php 
<?php
class OrderService
{
    public function process(Order $order): void
    {
        // dependencia oculta, no testeable
        $logger = Logger::getInstance();
        $logger->info('procesando pedido');
    }
}

Inyección — dependencia explícita

php 
<?php
class OrderService
{
    public function __construct(
        private readonly LoggerInterface $logger
    ) {}

    public function process(Order $order): void
    {
        $this->logger->info('procesando pedido');
    }
}

El contenedor DI gestiona que LoggerInterface resuelva siempre a la misma instancia si así se configura — el efecto del Singleton, sin sus problemas. Conoce el patrón para reconocerlo en código legacy; en código nuevo, usa inyección de dependencias.

Resumen #

Lo que te llevas

  • Factory Method: delega la creación a un método que decide qué clase concreta instanciar. El código cliente trabaja con la interfaz.
  • Abstract Factory: crea familias de objetos relacionados que deben ser compatibles entre sí. Cambiar la factory cambia toda la familia.
  • Builder: construye objetos complejos paso a paso con métodos encadenados. Elimina constructores con muchos parámetros opcionales.
  • Singleton: una única instancia con acceso global. El problema es que oculta dependencias y dificulta los tests. En código nuevo, el contenedor DI lo reemplaza.
