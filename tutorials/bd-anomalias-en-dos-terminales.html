Anomalías de aislamiento, reproducidas en dos terminales

La tabla de niveles de aislamiento te la sabes. Lo que no dice es que el mismo «REPEATABLE READ» se comporta distinto en MySQL y en Postgres, y que en los dos deja pasar un fallo que ninguna tabla nombra. Abre dos terminales y míralo pasar.

Dos peticiones leen un saldo de 100. Una suma 50, la otra suma 30. El saldo final es 130 y nadie ha visto un error. No es un bug de tu ORM ni de PHP: es el nivel de aislamiento por defecto haciendo exactamente lo que promete, que es menos de lo que creías.

La tabla no es el motor #

En Transacciones y ACID viste las anomalías y los niveles del estándar SQL: lo mínimo que cada nivel debe impedir, no cómo lo implementa cada motor. MySQL con InnoDB y PostgreSQL usan los dos MVCC: cada transacción lee una foto de los datos en lugar de esperar a que otros terminen. Pero deciden distinto cuándo se toma esa foto, qué lecturas la ignoran y qué pasa cuando dos transacciones escriben la misma fila.

Por eso esta lección no explica: reproduce cada anomalía en dos sesiones y en los dos motores, con la salida real.

El montaje: dos sesiones, dos motores #

Levanta los dos motores y abre dos terminales por motor. A partir de aquí, «A» y «B» son esas dos sesiones.

bash · levantar MySQL 8.4 y PostgreSQL 17 
docker run -d --rm --name lab-mysql -e MYSQL_ROOT_PASSWORD=x mysql:8.4
docker run -d --rm --name lab-pg -e POSTGRES_PASSWORD=x postgres:17

docker exec -it lab-mysql mysql -uroot -px
docker exec -it lab-pg psql -U postgres
sql · el mismo esquema en los dos motores 
CREATE TABLE cuentas (id INT PRIMARY KEY, titular VARCHAR(20) NOT NULL, saldo INT NOT NULL);
INSERT INTO cuentas VALUES (1, 'Ana', 100), (2, 'Luis', 500);

CREATE TABLE medicos (id INT PRIMARY KEY, nombre VARCHAR(20) NOT NULL, de_guardia BOOLEAN NOT NULL);
INSERT INTO medicos VALUES (1, 'Alicia', TRUE), (2, 'Bruno', TRUE);

Lectura no repetible #

A lee un saldo, B lo cambia y confirma, A vuelve a leer. En Postgres, con su READ COMMITTED por defecto, cada sentencia toma una foto nueva:

sql · PostgreSQL 17, READ COMMITTED 
A> BEGIN;
A> SELECT saldo FROM cuentas WHERE id = 1;            -- 100
B> UPDATE cuentas SET saldo = 150 WHERE id = 1;       -- UPDATE 1
A> SELECT saldo FROM cuentas WHERE id = 1;            -- 150
A> COMMIT;

En MySQL, con REPEATABLE READ, la segunda lectura devuelve 100. Pero añade FOR SHARE a la misma consulta, dentro de la misma transacción:

sql · MySQL 8.4, REPEATABLE READ 
A> START TRANSACTION;
A> SELECT saldo FROM cuentas WHERE id = 1;              -- 100
B> UPDATE cuentas SET saldo = 150 WHERE id = 1;         -- 1 row affected
A> SELECT saldo FROM cuentas WHERE id = 1;              -- 100
A> SELECT saldo FROM cuentas WHERE id = 1 FOR SHARE;    -- 150
A> COMMIT;

Esa es la clave de InnoDB: tiene dos tipos de lectura. La lectura consistente (un SELECT normal) lee la foto. La lectura con bloqueo (FOR SHARE, FOR UPDATE, y lo que leen UPDATE y DELETE) lee la última versión confirmada y la bloquea. La misma transacción ve dos valores según cómo pregunte.

La foto se toma en la primera lectura, no en el BEGIN

En los dos motores, si B confirma un cambio entre tu BEGIN y tu primer SELECT, lo ves. Lo comprobamos: A abre, B pone 150, A lee 150; B pone 170, A sigue leyendo 150.

Lost update: leer, calcular, escribir #

El patrón más común en una aplicación: lees en PHP, calculas y escribes el resultado. Así suele estar escrito:

php · addFunds.php (pierde ingresos) 
<?php

declare(strict_types=1);

function addFunds(PDO $connection, int $accountId, int $amount): void
{
    $connection->beginTransaction();
    $select = $connection->prepare('SELECT saldo FROM cuentas WHERE id = ?');
    $select->execute([$accountId]);
    $balance = (int) $select->fetchColumn();

    $connection->prepare('UPDATE cuentas SET saldo = ? WHERE id = ?')->execute([$balance + $amount, $accountId]);
    $connection->commit();
}

Dos peticiones a la vez, una con +50 y otra con +30, son esto:

sql · MySQL 8.4, REPEATABLE READ 
A> START TRANSACTION;
B> START TRANSACTION;
A> SELECT saldo FROM cuentas WHERE id = 1;              -- 100
B> SELECT saldo FROM cuentas WHERE id = 1;              -- 100
A> UPDATE cuentas SET saldo = 150 WHERE id = 1;
B> UPDATE cuentas SET saldo = 130 WHERE id = 1;         -- espera al bloqueo de A
A> COMMIT;
                                                        -- B: 1 row affected (1.20 sec)
B> COMMIT;
A> SELECT saldo FROM cuentas WHERE id = 1;              -- 130

El bloqueo de fila actúa: B espera a que A confirme. Pero luego escribe el 130 que calculó con un dato viejo y los 50 de A desaparecen. Postgres en READ COMMITTED da el mismo 130; en REPEATABLE READ se niega:

sql · PostgreSQL 17, REPEATABLE READ 
A> BEGIN ISOLATION LEVEL REPEATABLE READ;
B> BEGIN ISOLATION LEVEL REPEATABLE READ;
A> SELECT saldo FROM cuentas WHERE id = 1;              -- 100
B> SELECT saldo FROM cuentas WHERE id = 1;              -- 100
A> UPDATE cuentas SET saldo = 150 WHERE id = 1;
B> UPDATE cuentas SET saldo = 130 WHERE id = 1;         -- espera
A> COMMIT;
B> ERROR:  40001: could not serialize access due to concurrent update
B> COMMIT;                                             -- ROLLBACK
A> SELECT saldo FROM cuentas WHERE id = 1;              -- 150

Es la diferencia más importante entre los dos REPEATABLE READ: Postgres no deja que una transacción modifique una fila que otra cambió después de su foto; InnoDB sí, porque su UPDATE es una lectura con bloqueo y trabaja sobre la última versión. La corrección para los dos motores es leer ya con bloqueo:

php · addFunds.php (corregido) 
<?php

declare(strict_types=1);

function addFunds(PDO $connection, int $accountId, int $amount): void
{
    $connection->beginTransaction();
    $select = $connection->prepare('SELECT saldo FROM cuentas WHERE id = ? FOR UPDATE');
    $select->execute([$accountId]);
    $balance = (int) $select->fetchColumn();

    $connection->prepare('UPDATE cuentas SET saldo = ? WHERE id = ?')->execute([$balance + $amount, $accountId]);
    $connection->commit();
}

Con FOR UPDATE, B se queda esperando en su SELECT y, cuando A confirma, lee 150, no 100. Lo vimos igual en MySQL y en Postgres, cada uno en su nivel por defecto. Si el cálculo cabe en SQL, SET saldo = saldo + 30 también da 180 en los dos, como cuenta Concurrencia. El bloqueo pesimista a fondo, con colas y SKIP LOCKED, está en Bloqueo pesimista; la alternativa sin bloqueo, en Bloqueo optimista.

Fantasmas y lecturas con bloqueo #

Un fantasma es una fila nueva que aparece al repetir una consulta con WHERE. Con SELECT COUNT(*) FROM cuentas WHERE saldo >= 100 en A y un INSERT de B en medio, esto es lo que medimos:

Lectura de A tras el INSERT de BPG READ COMMITTEDPG REPEATABLE READMySQL REPEATABLE READ
SELECT COUNT(*)322
... FOR SHAREno aplicano aplica3
UPDATE ... WHERE saldo >= 1003 filas2 filas3 filas
SELECT COUNT(*) tras ese UPDATE323

La última fila es la que sorprende. En InnoDB el UPDATE es lectura con bloqueo y alcanza la fila de B; al modificarla, pasa a ser tuya y aparece en tu foto. El fantasma se cuela por la escritura. Postgres en REPEATABLE READ no lo ve ni para leer ni para escribir.

InnoDB sí tiene una forma de cerrar la puerta: la lectura con bloqueo de un rango bloquea también los huecos.

sql · MySQL 8.4, bloqueo de rango 
A> START TRANSACTION;
A> SELECT id FROM cuentas WHERE id BETWEEN 1 AND 10 FOR UPDATE;   -- 1, 2
B> INSERT INTO cuentas VALUES (3, 'Eva', 300);                    -- espera
A> COMMIT;
                                                                  -- B: 1 row affected (3.00 sec)

SELECT index_name, lock_mode, lock_data FROM performance_schema.data_locks;
-- PRIMARY  X  supremum pseudo-record
-- PRIMARY  X  1
-- PRIMARY  X  2

El bloqueo sobre supremum pseudo-record, el final del índice, es el que deja a B esperando: nadie puede insertar detrás del 2 hasta que A termine. Si A no confirma, B se rinde a los 50 segundos de innodb_lock_wait_timeout.

Write skew: el que nadie nombra #

La regla del hospital: al menos un médico de guardia. Alicia y Bruno quieren salir a la vez. Cada uno comprueba que quedan dos y se quita a sí mismo. No escriben la misma fila, así que no hay conflicto de escritura que detectar:

sql · PostgreSQL 17 y MySQL 8.4, REPEATABLE READ 
A> BEGIN ISOLATION LEVEL REPEATABLE READ;   -- en MySQL: START TRANSACTION;
B> BEGIN ISOLATION LEVEL REPEATABLE READ;
A> SELECT COUNT(*) FROM medicos WHERE de_guardia;    -- 2
B> SELECT COUNT(*) FROM medicos WHERE de_guardia;    -- 2
A> UPDATE medicos SET de_guardia = FALSE WHERE id = 1;
B> UPDATE medicos SET de_guardia = FALSE WHERE id = 2;
A> COMMIT;
B> COMMIT;
A> SELECT COUNT(*) FROM medicos WHERE de_guardia;    -- 0

Cero médicos de guardia, en los dos motores y sin un error. Cada transacción vio datos coherentes y decidió bien con lo que vio; el resultado conjunto viola la regla. Es el write skew, y la tabla clásica no lo menciona.

SERIALIZABLE obliga a reintentar #

Repite el escenario con BEGIN ISOLATION LEVEL SERIALIZABLE en Postgres. Todo va igual hasta el segundo COMMIT:

sql · PostgreSQL 17, SERIALIZABLE 
A> COMMIT;
B> COMMIT;
ERROR:  40001: could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during commit attempt.
HINT:  The transaction might succeed if retried.

Postgres no bloquea más: vigila qué leyó y qué escribió cada transacción y, si las dependencias forman un ciclo que ningún orden en serie explicaría, aborta una. Queda un médico de guardia. B no ha fallado por un bug, sino porque otra transacción llegó antes; repetida, verá un solo médico y decidirá distinto. Por eso SERIALIZABLE sin reintento es un error 500 esperando su momento.

MySQL llega al mismo sitio por otro camino: en SERIALIZABLE, los SELECT de una transacción toman bloqueos compartidos (S en data_locks). Cada sesión espera al bloqueo de lectura de la otra y el motor rompe el ciclo: ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction. Mismo SQLSTATE, misma conclusión: reintentar.

Así se ve el reintento en la aplicación, para Postgres:

php · SerializableTransaction.php 
<?php

declare(strict_types=1);

final class SerializableTransaction
{
    private const SERIALIZATION_FAILURE = '40001';
    private const DEADLOCK_DETECTED = '40P01';
    private const MAX_ATTEMPTS = 3;
    private const BASE_BACKOFF_MICROSECONDS = 20_000;

    public function __construct(private readonly PDO $connection)
    {
    }

    public function run(callable $work): mixed
    {
        for ($attempt = 1; ; $attempt++) {
            try {
                return $this->runOnce($work);
            } catch (Throwable $exception) {
                $this->rollBackIfOpen();

                if (!$this->isRetryable($exception) || $attempt === self::MAX_ATTEMPTS) {
                    throw $exception;
                }

                usleep(self::BASE_BACKOFF_MICROSECONDS * $attempt + random_int(0, self::BASE_BACKOFF_MICROSECONDS));
            }
        }
    }

    private function runOnce(callable $work): mixed
    {
        $this->connection->beginTransaction();
        $this->connection->exec('SET TRANSACTION ISOLATION LEVEL SERIALIZABLE');
        $result = $work($this->connection);
        $this->connection->commit();

        return $result;
    }

    private function isRetryable(Throwable $exception): bool
    {
        return $exception instanceof PDOException
            && in_array($exception->getCode(), [self::SERIALIZATION_FAILURE, self::DEADLOCK_DETECTED], true);
    }

    private function rollBackIfOpen(): void
    {
        if ($this->connection->inTransaction()) {
            $this->connection->rollBack();
        }
    }
}
php · OnCallSchedule.php 
<?php

declare(strict_types=1);

final class LastDoctorOnCall extends DomainException
{
}

final class OnCallSchedule
{
    private const MINIMUM_ON_CALL = 1;

    public function __construct(private readonly SerializableTransaction $transaction)
    {
    }

    public function goOffCall(int $doctorId): void
    {
        $this->transaction->run(function (PDO $connection) use ($doctorId): void {
            $onCall = (int) $connection->query('SELECT COUNT(*) FROM medicos WHERE de_guardia')->fetchColumn();

            if ($onCall <= self::MINIMUM_ON_CALL) {
                throw new LastDoctorOnCall('No puede quedarse la guardia vacía');
            }

            $connection->prepare('UPDATE medicos SET de_guardia = FALSE WHERE id = ?')->execute([$doctorId]);
        });
    }
}

Lo ejecutamos con dos conexiones PDO contra Postgres 17: el primer intento falla con 40001; el segundo ve un solo médico y lanza LastDoctorOnCall. El trabajo va como función porque se repite la transacción entera, lecturas incluidas.

Errores típicos #

Lo que muerde en producción

  • Creer que REPEATABLE READ evita el lost update en MySQL. No lo evita: lo has visto con 130 en lugar de 180.
  • Comprobar en un SELECT normal y escribir después. En InnoDB, la comprobación lee la foto y la escritura la última versión; pueden no coincidir.
  • Subir a SERIALIZABLE sin reintento. Cambias datos corruptos por errores 40001 en los logs.
  • Hacer rollback solo ante PDOException. Si la regla lanza su propia excepción, la transacción queda abierta. Nos pasó con la primera versión del helper: el siguiente beginTransaction() falló con «There is already an active transaction».
  • Fijar el nivel en el sitio equivocado. Postgres acepta SET TRANSACTION tras el BEGIN pero no después de la primera consulta. MySQL no lo acepta ni justo después de START TRANSACTION (ERROR 1568): ahí va antes de abrirla.
  • Reintentar con efectos fuera de la base de datos. Si el trabajo envía un correo o llama a una API, se repite con él; esos efectos van tras el commit o con idempotencia.

Cómo comprobarlo #

Primero, el nivel real de tus conexiones: SELECT @@transaction_isolation en MySQL y SHOW transaction_isolation en Postgres, desde la aplicación, porque un ORM o un pool pueden cambiarlo. Segundo, qué bloquea cada consulta: en MySQL, performance_schema.data_locks con la transacción abierta. Tercero, convierte la reproducción en un test: dos conexiones PDO, el guion intercalado a mano y una aserción sobre el estado final; es determinista porque tú decides el orden. En producción, cuenta los 40001 y los 1213: si crecen, el reintento está tapando contención.

Cuándo aplicarlo #

Sube el aislamiento o bloquea cuando…

  • Lees en la aplicación, calculas y escribes el resultado (saldos, stock, contadores)
  • Una regla depende de varias filas: guardias, cupos, reservas que no se solapan
  • Un informe necesita varias consultas coherentes entre sí
  • Puedes repetir la transacción entera sin efectos externos

No hace falta cuando…

  • La escritura cabe en un UPDATE relativo o en una restricción UNIQUE o CHECK
  • Cada petición toca filas que solo son suyas
  • Son lecturas para mostrar, donde un dato de hace un segundo no rompe nada

La alternativa sencilla

Antes de cambiar el nivel de toda la conexión, materializa el conflicto: FOR UPDATE sobre las filas que decides, o sobre una fila que represente la regla (el turno de guardia). Bloqueas solo lo que importa y no necesitas reintento. Si eso provoca esperas cruzadas, sigue en Deadlocks.

Resumen #

Lo que te llevas

  • MySQL 8.4 arranca en REPEATABLE READ y PostgreSQL 17 en READ COMMITTED: el mismo código se comporta distinto según el motor.
  • InnoDB tiene dos lecturas: la consistente lee la foto; la de bloqueo, y también UPDATE y DELETE, la última versión confirmada.
  • El lost update de leer, calcular y escribir pasa en MySQL REPEATABLE READ; Postgres REPEATABLE READ lo corta con 40001. FOR UPDATE lo arregla en los dos.
  • El write skew atraviesa REPEATABLE READ en los dos motores; solo SERIALIZABLE o un bloqueo explícito lo paran.
  • SERIALIZABLE aborta en lugar de esperar: repite la transacción entera ante 40001, con rollback ante cualquier excepción.
