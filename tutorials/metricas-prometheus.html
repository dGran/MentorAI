Métricas con Prometheus

Prometheus es el sistema de métricas de facto en el ecosistema cloud-native: simple, potente y basado en el modelo pull — él va a buscar tus métricas, no tú se las envías. Entender su modelo de datos es la clave para instrumentar tu aplicación correctamente.

El segundo pilar de la observabilidad son las métricas. Mientras Sentry cubre los errores de forma especializada, Prometheus cubre el comportamiento cuantitativo del sistema: cuántas peticiones llegan, cuánto tardan y cómo evoluciona cada magnitud a lo largo del tiempo.

El modelo pull y el scraping #

La mayoría de sistemas de métricas tradicionales usan el modelo push: la aplicación envía métricas al servidor central cada cierto tiempo. Prometheus invierte esto con el modelo pull: Prometheus llama periódicamente a un endpoint /metrics de cada aplicación y recoge los datos. Este endpoint expone el estado actual de todas las métricas en el formato de texto de Prometheus.

Tu app expone GET /metrics (formato Prometheus)
↑ cada 15s Prometheus scrappe
Prometheus almacena la serie temporal en su TSDB
↓
Grafana o Alertmanager consultan vía PromQL

El intervalo de scraping por defecto es 15 segundos — configurable por target. El formato de texto que devuelve /metrics es simple:

formato de texto Prometheus en /metrics 
# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 1234
http_requests_total{method="POST",status="201"} 87
http_requests_total{method="POST",status="500"} 3

# HELP http_request_duration_seconds Request duration in seconds
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.05"} 980
http_request_duration_seconds_bucket{le="0.5"} 1230
http_request_duration_seconds_bucket{le="1.0"} 1234
http_request_duration_seconds_bucket{le="+Inf"} 1234
http_request_duration_seconds_sum 312.4
http_request_duration_seconds_count 1234

La ventaja del modelo pull: Prometheus sabe si un target está caído (no puede scrappe → alerta de target down), no hay que configurar la dirección del servidor central en cada aplicación y el endpoint /metrics es también útil para depuración manual.

Tipos de métrica #

Ya viste los cuatro tipos en el tutorial de los pilares. Aquí los concretamos con su semántica en Prometheus:

TipoSemánticaOperaciones útiles en PromQL
CounterSolo sube. Se reinicia al reiniciar el proceso.rate(), increase()
GaugeSube y baja. Valor puntual.Valor directo, avg_over_time()
HistogramDistribución en buckets predefinidos. Permite percentiles.histogram_quantile(), rate() sobre _count
SummaryPercentiles precalculados en el cliente.Valor directo. Menos flexible que histogram.

La elección entre histogram y summary es importante: los histogramas calculan percentiles en el servidor (Prometheus) sobre ventanas de tiempo arbitrarias y se pueden agregar entre múltiples instancias; los summaries los calculan en el cliente (tu app) con una ventana fija y no son agregables. Para latencia de endpoints, usa siempre histogram.

Buckets del histogram: piénsalos antes

Los buckets del histogram son fijos en tiempo de instrumentación. Si tu aplicación tarda habitualmente entre 10ms y 500ms, define buckets como [0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5] (en segundos). Si todos tus valores caen en el último bucket +Inf, el percentil 95 será siempre ese valor máximo — los buckets pierden toda utilidad.

Labels y cardinalidad #

Los labels (etiquetas) son pares clave-valor que diferencian series temporales dentro de la misma métrica. Una métrica con dos labels distintos de valores es en realidad dos series temporales distintas que Prometheus almacena y consulta por separado.

Como viste en el tutorial de los pilares, la cardinalidad es el número de combinaciones únicas de labels. Una métrica http_requests_total con labels method (5 valores), status (10 valores) y endpoint (50 rutas) genera 5×10×50 = 2.500 series temporales. Eso es manejable. Si añades user_id con 100.000 usuarios: 250 millones de series — Prometheus colapsa.

Labels de alta cardinalidad → colapso

Nunca uses como label: user_id, order_id, request_id, IPs, emails ni ningún valor que crezca sin límite. Los labels de Prometheus deben tener un conjunto acotado y pequeño de valores posibles. Los datos de alta cardinalidad van en los logs.

Labels útiles y seguros: method (GET/POST/…), status_code (200/404/500), endpoint (plantilla de ruta, no URL concreta), job (nombre del servicio), instance (nodo concreto, lo gestiona Prometheus).

Exporters: métricas del sistema #

No todo lo que quieres monitorizar es tu código: el servidor, la base de datos y el propio contenedor también producen métricas valiosas. Los exporters son procesos separados que exponen métricas de sistemas externos en formato Prometheus.

ExporterQué expone
node_exporterCPU, memoria, disco, red del servidor Linux.
mysqld_exporterQueries por segundo, conexiones, innodb, replicación.
postgres_exporterTablas bloqueadas, conexiones, vacuums, tamaño de tablas.
redis_exporterHit rate, memoria, comandos por segundo, claves.
nginx-prometheus-exporterPeticiones activas, estados de conexión, req/s.
php-fpm_exporterWorkers activos/idle, queue, slow requests.

En Docker, los exporters se añaden como servicios adicionales en el docker-compose.yml y Prometheus los scrappe igual que a tu aplicación.

Instrumentar una app PHP #

La librería más usada es promphp/prometheus_client_php. Las métricas se almacenan en un backend compartido entre todos los procesos de PHP-FPM (Redis o APCu, porque cada petición es un proceso distinto):

bash · instalar la librería 
composer require promphp/prometheus_client_php
php · registrar counter + histogram en un middleware 
<?php

use Prometheus\CollectorRegistry;
use Prometheus\Storage\Redis;

final class MetricsMiddleware
{
    private CollectorRegistry $registry;

    public function __construct()
    {
        $this->registry = new CollectorRegistry(new Redis(['host' => 'redis']));
    }

    public function process(Request $request, RequestHandler $handler): Response
    {
        $start = microtime(as_float: true);
        $response = $handler->handle($request);
        $duration = microtime(as_float: true) - $start;

        $labels = [
            'method'   => $request->getMethod(),
            'endpoint' => $request->getRoute(),
            'status'   => (string) $response->getStatusCode(),
        ];

        $this->registry
            ->getOrRegisterCounter('app', 'http_requests_total', 'Total HTTP requests', ['method', 'endpoint', 'status'])
            ->inc($labels);

        $this->registry
            ->getOrRegisterHistogram('app', 'http_request_duration_seconds', 'Request duration', ['method', 'endpoint'], [0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5])
            ->observe($duration, array_slice($labels, 0, 2));

        return $response;
    }
}
php · endpoint /metrics que scrappe Prometheus 
$registry = new CollectorRegistry(new Redis(['host' => 'redis']));
$renderer = new RenderTextFormat();

header('Content-Type: ' . RenderTextFormat::MIME_TYPE);
echo $renderer->render($registry->getMetricFamilySamples());

En producción protege el endpoint /metrics con autenticación o limítalo a la IP de Prometheus — expone información del estado interno de la aplicación.

Resumen #

Lo que te llevas

  • Modelo pull: Prometheus scrappe tu /metrics cada 15s. La app expone; Prometheus recoge. Si no puede scrappe, sabe que el target está caído.
  • Counter para totales acumulados (usa rate() en PromQL), gauge para valores puntuales, histogram para distribuciones y percentiles de latencia.
  • Labels con cardinalidad baja: method, status_code, endpoint (plantilla). Nunca user_id, order_id ni IPs — destruyen Prometheus.
  • Exporters para el sistema: node_exporter (servidor), mysqld_exporter (BD), php-fpm_exporter (workers PHP). No hace falta tocar tu código para tener métricas de infraestructura.
  • PHP-FPM es multiproceso: las métricas necesitan un backend compartido (Redis o APCu) entre procesos. Define los buckets del histogram pensando en la distribución real de tus tiempos.
