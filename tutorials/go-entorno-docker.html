Entorno Go con Docker

No instalaremos Go localmente. Un contenedor con la imagen oficial, un compose con bind mount del código y un volumen para la caché de módulos: el mismo criterio que ya aplicas con PHP, pero para Go.

Instalar Go en el portátil parece lo rápido, hasta que tu máquina, la de un compañero y CI compilan con versiones distintas y un error deja de reproducirse. Con PHP ya resolviste eso metiendo el runtime en un contenedor; aquí haces lo mismo, con dos detalles propios de Go: la caché de módulos y que cada cambio exige recompilar.

La imagen oficial de Go #

Docker Hub ofrece la imagen oficial golang en varias variantes. Para desarrollo nos interesa la completa (no slim ni alpine) porque incluye gcc y las herramientas de sistema que algunas dependencias necesitan al compilar:

bash 
golang:1.27          # imagen completa basada en Debian Trixie
golang:1.27-alpine   # imagen ligera (~250 MB frente a ~890 MB), sin gcc

Para producción usarás multi-stage y la imagen final será mínima. Para desarrollo, la imagen completa evita sorpresas con dependencias que necesitan CGO.

Estructura del proyecto #

Un proyecto Go mínimo tiene esta forma:

bash 
mi-servicio/
├── cmd/
│   └── server/
│       └── main.go       # punto de entrada
├── internal/             # código privado del proyecto
├── go.mod                # declaración del módulo y dependencias
├── go.sum                # checksums de dependencias (como composer.lock)
├── Dockerfile
├── compose.yaml
└── .air.toml             # configuración de hot reload (opcional)

La convención cmd/ es donde van los puntos de entrada (main.go). internal/ es código que no se puede importar desde fuera del árbol que cuelga de su directorio padre (con internal/ en la raíz, desde fuera del módulo): lo impone la herramienta go, no es solo una convención.

docker compose para desarrollo #

El compose de desarrollo tiene dos objetivos: montar el código fuente con un bind mount para que los cambios sean inmediatos, y separar el directorio de caché de módulos con un volumen named para no descargarlo en cada arranque.

bash 
# compose.yaml
services:
  app:
    image: golang:1.27
    working_dir: /app
    volumes:
      - .:/app                          # bind mount del código fuente
      - go-modules:/go/pkg/mod          # caché de módulos persistente
    ports:
      - "8080:8080"
    environment:
      - GOPATH=/go
    command: go run ./cmd/server/

volumes:
  go-modules:

El volumen go-modules monta en /go/pkg/mod, que es donde Go almacena los módulos descargados. Sin él, cada docker compose up descargaría todas las dependencias de nuevo.

Paralelo con PHP: es el mismo patrón que php-en-docker. El bind mount del código permite editar desde el host; el volumen de dependencias equivale a cachear el vendor/ o el caché de Composer.

La caché de módulos #

Go descarga los módulos en $GOPATH/pkg/mod la primera vez que se usan y los reutiliza. Dentro del contenedor $GOPATH es /go por defecto. Por eso el volumen monta ahí.

Para forzar la descarga de dependencias declaradas en go.mod:

bash 
docker compose run --rm app go mod download

Y para añadir una dependencia nueva desde dentro del contenedor:

bash 
docker compose run --rm app go get github.com/some/package@v1.2.3

Esto actualiza go.mod y go.sum en el host gracias al bind mount. Es el equivalente a composer require.

Errores típicos al montar el entorno

  • Escuchar en localhost dentro del contenedor. http.ListenAndServe("127.0.0.1:8080", …) solo acepta conexiones del propio contenedor y el puerto publicado no responde. Escucha en ":8080" (todas las interfaces).
  • Cachear los módulos pero no la compilación. /go/pkg/mod guarda el código descargado; los objetos compilados van a /root/.cache/go-build (go env GOCACHE). Sin un volumen ahí, cada contenedor nuevo recompila todo desde cero.
  • Acabar con go.mod y ficheros generados propiedad de root. El contenedor corre como root y lo que escribe en el bind mount queda así en el host, y luego tu editor no puede guardarlo. En Linux, añade user: "1000:1000" (tu UID y GID) al servicio, con GOCACHE y el volumen de módulos en rutas que ese usuario pueda escribir.

Hot reload con Air #

Go no tiene hot reload nativo: hay que recompilar y relanzar. Air lo hace automáticamente al detectar cambios en el código fuente.

Dockerfile de desarrollo con Air:

bash 
# Dockerfile.dev
FROM golang:1.27

WORKDIR /app

# Instala Air
RUN go install github.com/air-verse/air@latest

# Las dependencias se cachean vía volumen, no aquí
CMD ["air"]

Y el compose actualizado para usar este Dockerfile:

bash 
# compose.yaml
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile.dev
    working_dir: /app
    volumes:
      - .:/app
      - go-modules:/go/pkg/mod
    ports:
      - "8080:8080"

volumes:
  go-modules:

Air usa por defecto el fichero .air.toml. Uno mínimo:

ini 
# .air.toml
root = "."

[build]
  cmd = "go build -o /tmp/server ./cmd/server/"
  bin = "/tmp/server"
  include_ext = ["go"]
  exclude_dir = ["vendor"]

Con esto, cada vez que guardes un fichero .go, Air recompila y reinicia el proceso en menos de un segundo.

Comandos del día a día #

Con el entorno montado, estos son los comandos que usarás constantemente:

bash 
# Levantar el entorno con hot reload
docker compose up

# Ejecutar un comando único dentro del contenedor
docker compose run --rm app go test ./...
docker compose run --rm app go vet ./...
docker compose run --rm app go mod tidy

# Añadir una dependencia
docker compose run --rm app go get github.com/paquete@v1.0.0

# Entrar al contenedor
docker compose exec app bash

# Compilar el binario (dentro del contenedor)
docker compose run --rm app go build -o /tmp/servidor ./cmd/server/

go mod tidy elimina dependencias no usadas y añade las que faltan en go.sum. Equivale a limpiar el composer.lock. Ejecútalo antes de cada commit.

Cuándo aplicarlo #

Este montaje (imagen oficial, bind mount del código y volumen para la caché) es tu entorno por defecto: la versión de Go la fija el compose, no la máquina de cada uno.

  • Úsalo siempre que el proyecto se comparta o tenga servicios alrededor (base de datos, Redis, una cola): el compose los levanta juntos y CI puede usar la misma imagen.
  • Air solo compensa con un servidor que quieres ver reiniciado al guardar. Para un CLI o una librería sobra: go run o go test ./... tardan segundos y no añaden otra pieza que configurar.
  • Imagen completa para desarrollar, multi-stage para desplegar. Nunca lleves a producción la imagen golang con el código montado: pesa cientos de megas y arrastra el compilador, cuando lo único que necesitas es el binario (go-a-produccion).
  • Alpine en desarrollo solo si ninguna dependencia usa CGO. Si alguna lo necesita (un driver de SQLite, por ejemplo), la imagen basada en Debian te ahorra pelearte con gcc y musl.

Lo que no resuelve este montaje es el editor: gopls necesita un Go con el que analizar el código. Para eso, en la siguiente lección, instalas la misma versión en el host o conectas el editor al contenedor; ejecutar y testear sigue ocurriendo aquí dentro.

Resumen #

Lo que te llevas

  • La imagen golang:1.27 contiene el toolchain completo; para desarrollo vale la imagen completa.
  • Bind mount del código fuente + volumen named para /go/pkg/mod: el código cambia en tiempo real, las dependencias se cachean entre sesiones.
  • Air detecta cambios, recompila y reinicia automáticamente; ciclo de feedback de menos de un segundo.
  • go mod download prefetcha dependencias; go mod tidy limpia el módulo.
  • Todos los comandos (go test, go vet, go get) se ejecutan dentro del contenedor, nunca en el host.
