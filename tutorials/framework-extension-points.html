Cómo extender un framework sin tocar su núcleo

Symfony y Laravel ofrecen puntos de extensión formales para añadir comportamiento sin modificar su código. Tagged services y compiler passes en Symfony, service providers en Laravel, event subscribers, middleware personalizado: el catálogo completo de mecanismos de extensión.

La lección anterior mostró el ciclo completo de una petición. Esta responde la pregunta inevitable: ¿dónde meto mi código cuando quiero intervenir en ese ciclo o en el contenedor sin parchear el framework?

El principio de extensión #

Un framework bien diseñado aplica OCP (Open/Closed Principle) a sí mismo: está cerrado a la modificación, abierto a la extensión. En la práctica eso significa que tiene puntos de extensión formales — lugares definidos donde el código externo puede engancharse — en lugar de requerir que modifiques su código fuente.

Parchar el framework (nunca)

bash 
# vendor/ está en .gitignore.
# Cualquier cambio aquí se pierde
# con el siguiente composer update.
vendor/symfony/http-kernel/HttpKernel.php

Usar los puntos de extensión

bash 
src/EventListener/SecurityListener.php
src/Middleware/RateLimitMiddleware.php
src/DependencyInjection/AppExtension.php

Event subscribers #

El mecanismo más versátil: escuchar cualquier evento del ciclo del Kernel (o del dominio) e intervenir. La diferencia entre un EventListener y un EventSubscriber es pequeña pero práctica: el Subscriber declara él mismo a qué eventos se suscribe, lo que lo hace autocontenido.

php · Symfony EventSubscriber 
<?php

declare(strict_types=1);

namespace App\EventSubscriber;

use Symfony\Component\EventDispatcher\EventSubscriberInterface;
use Symfony\Component\HttpKernel\Event\RequestEvent;
use Symfony\Component\HttpKernel\KernelEvents;

final class LocaleSubscriber implements EventSubscriberInterface
{
    public function __construct(private readonly string $defaultLocale) {}

    public static function getSubscribedEvents(): array
    {
        return [
            KernelEvents::REQUEST => [['onKernelRequest', 20]],
        ];
    }

    public function onKernelRequest(RequestEvent $event): void
    {
        $request = $event->getRequest();

        if (!$request->hasPreviousSession()) {
            return;
        }

        $locale = $request->getSession()->get('_locale', $this->defaultLocale);
        $request->setLocale($locale);
    }
}

El número 20 en el array es la prioridad: mayor número = se ejecuta antes. El firewall de seguridad de Symfony escucha kernel.request con prioridad 8; un subscriber con prioridad 20 se ejecuta antes del firewall.

Listeners vs Subscribers

Si el listener responde solo a un evento, usa el atributo #[AsEventListener] directamente sobre el método — es menos código. El Subscriber conviene cuando una misma clase necesita escuchar varios eventos relacionados (por ejemplo, un "auditor" que escucha request + response + exception).

En Laravel el equivalente son los Event Listeners registrados en EventServiceProvider (o autodetectados con php artisan event:generate). La diferencia con los kernel events de Symfony es que en Laravel los eventos del framework (requests, autenticación, etc.) viajan por el mismo EventDispatcher que los eventos de dominio.

Middleware personalizado #

En la lección anterior viste cómo el Kernel despacha el kernel.controller para el security voter. El middleware es el otro mecanismo: envuelve la petición antes de que llegue al controlador, y puede cortarla (devolver una respuesta propia) o pasarla al siguiente elemento de la cadena.

php · Symfony Kernel middleware con kernel.request 
<?php

// En Symfony el "middleware" más puro es el EventSubscriber que escucha
// kernel.request con alta prioridad y puede setear una respuesta:

public function onKernelRequest(RequestEvent $event): void
{
    if ($this->isUnderMaintenance()) {
        $event->setResponse(new Response('Service unavailable', 503));
        // Al setear la respuesta, el Kernel no llega al controlador
    }
}

// El equivalente directo a Express/Laravel middleware en Symfony son
// los listeners de kernel.request que llaman a setResponse para cortarlo,
// o simplemente dejan pasar si no hacen nada.
php · Laravel Middleware 
<?php

declare(strict_types=1);

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

final class EnsureApiToken
{
    public function handle(Request $request, Closure $next): Response
    {
        if (!$request->hasValidSignature()) {
            return response()->json(['error' => 'Unauthorized'], 401);
        }

        return $next($request); // pasa al siguiente middleware o al controlador
    }
}

El middleware de Laravel es la Chain of Responsibility que viste en la lección de patrones de comportamiento: cada pieza recibe la petición, puede cortarla devolviendo una respuesta propia o pasarla llamando a $next($request). Symfony logra lo mismo con listeners de kernel.request de alta prioridad.

Tagged services (Symfony) #

¿Cómo sabe Symfony qué clases son voters de seguridad, qué clases son command handlers, qué clases son Twig extensions? A través de tags. Un tag es una etiqueta que marca un servicio para que el contenedor lo incluya en una colección.

php · Definir e inyectar tagged services 
<?php

// Cualquier clase que implemente VoterInterface recibe el tag 'security.voter'
// automáticamente por autoconfiguration. Sin configuración extra.

final class OrderVoter extends Voter
{
    // El SecurityContext inyecta todos los 'security.voter' taggeados
    protected function supports(string $attribute, mixed $subject): bool
    {
        return $subject instanceof Order;
    }

    protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token): bool
    {
        return match ($attribute) {
            'VIEW'  => $this->canView($subject, $token),
            'EDIT'  => $this->canEdit($subject, $token),
            default => false,
        };
    }
}
php · Tag propio para extensión de negocio 
<?php

// Un atributo PHP como tag de autoconfiguration
#[\Attribute(\Attribute::TARGET_CLASS)]
final class AsPaymentGateway
{
    public function __construct(public readonly string $name) {}
}

// Usar el atributo en cada implementación
#[AsPaymentGateway(name: 'stripe')]
final class StripeGateway implements PaymentGatewayInterface { /* ... */ }

#[AsPaymentGateway(name: 'paypal')]
final class PaypalGateway implements PaymentGatewayInterface { /* ... */ }

// El PaymentGatewayRegistry recibe todos los taggeados e indexa por nombre:
// $this->gateways['stripe'], $this->gateways['paypal']
// Añadir un gateway nuevo = crear la clase. Sin tocar el registry.

Tagged services = OCP aplicado al contenedor

Este es exactamente el principio Open/Closed en el contenedor: el registry está cerrado a la modificación (no hay que editar ninguna lista), pero está abierto a la extensión (añadir una clase taggeada la incorpora automáticamente). El contenedor resuelve la colección en tiempo de compilación.

Compiler passes (Symfony) #

Los tagged services son el mecanismo declarativo. Los compiler passes son el mecanismo imperativo: código PHP que se ejecuta durante la compilación del contenedor y puede leer, modificar o reconfigurar cualquier definición de servicio antes de que el contenedor se cachee.

php · CompilerPass 
<?php

declare(strict_types=1);

namespace App\DependencyInjection\Compiler;

use Symfony\Component\DependencyInjection\Compiler\CompilerPassInterface;
use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\DependencyInjection\Reference;

final class PaymentGatewayPass implements CompilerPassInterface
{
    public function process(ContainerBuilder $container): void
    {
        if (!$container->has(PaymentGatewayRegistry::class)) {
            return;
        }

        $registryDefinition = $container->findDefinition(PaymentGatewayRegistry::class);
        $taggedServices     = $container->findTaggedServiceIds('app.payment_gateway');

        foreach ($taggedServices as $serviceId => $tags) {
            $registryDefinition->addMethodCall(
                'register',
                [$tags[0]['name'], new Reference($serviceId)]
            );
        }
    }
}

// Se registra en el Kernel:
// protected function build(ContainerBuilder $container): void
// {
//     $container->addCompilerPass(new PaymentGatewayPass());
// }

Compiler pass = tiempo de compilación, no de ejecución

El código del compiler pass se ejecuta una vez cuando Symfony compila el contenedor (típicamente en el primer request o con php bin/console cache:clear). El contenedor compilado se cachea. Si el pass tiene un bug, aparece en compilación, no en runtime — lo que hace los errores más visibles y rápidos de detectar.

Service providers (Laravel) #

En Laravel el equivalente a un bundle de Symfony (o a un Extension + CompilerPass) es el Service Provider: una clase que registra servicios en el contenedor y conecta código propio con el framework.

php · Laravel ServiceProvider 
<?php

declare(strict_types=1);

namespace App\Providers;

use Illuminate\Support\ServiceProvider;

final class PaymentServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // register(): solo bindings. No uses otras abstracciones aquí:
        // el contenedor aún no está completamente construido.
        $this->app->singleton(PaymentGatewayRegistry::class, function ($app) {
            $registry = new PaymentGatewayRegistry();
            $registry->register('stripe', $app->make(StripeGateway::class));
            $registry->register('paypal', $app->make(PaypalGateway::class));
            return $registry;
        });
    }

    public function boot(): void
    {
        // boot(): todos los providers ya se han registrado.
        // Aquí puedes usar servicios de otros providers, registrar
        // routes, observers, gates, Blade directives, etc.
        Gate::define('process-payment', [PaymentPolicy::class, 'process']);
    }
}

La distinción register() / boot() resuelve el problema de orden: en register() defines bindings sin depender de otros providers; en boot() ya todos los providers se han registrado y puedes usar sus servicios. El ciclo de vida de Laravel llama a todos los register() primero y luego a todos los boot().

Cuándo usar cada mecanismo #

MecanismoFrameworkPara qué
Event Subscriber / #[AsEventListener] Symfony Intervenir en el ciclo HTTP o reaccionar a eventos de dominio sin acoplarte al emisor
Event Listener Laravel Igual que el Subscriber de Symfony; registro en EventServiceProvider o autodescubrimiento
Kernel Middleware Laravel Filtrar, transformar o cortar peticiones antes del controlador; lógica transversal sin tocar rutas
kernel.request listener de alta prioridad Symfony Equivalente funcional al middleware de Laravel; puede setear response y cortar el ciclo
Tagged services + autoconfiguration Symfony Registrar implementaciones de una interfaz sin editar ningún fichero central; OCP puro
Compiler pass Symfony Manipulación avanzada del contenedor: leer tags, inyectar colecciones, validar configuración en compilación
Service Provider register() Laravel Registrar bindings, singletons y factories; punto de entrada de cualquier paquete o módulo
Service Provider boot() Laravel Configurar el framework una vez todos los providers están listos: rutas, gates, observers, Blade

Cuándo aplicarlo

Aplícalo cuando…

  • El comportamiento es transversal: logging, autenticación, caché, rate limiting.
  • Quieres añadir comportamiento sin modificar el núcleo del framework ni código existente.

No lo uses cuando…

  • La lógica es específica de un contexto de negocio: pertenece al dominio, no a los puntos de extensión del framework.
  • El mecanismo de extensión es más complejo que el problema que resuelve.

Resumen #

Lo que te llevas

  • Los Event Subscribers (Symfony) y Event Listeners (Laravel) son el mecanismo más versátil: escuchan puntos del ciclo sin modificar el núcleo. Observer en estado puro.
  • El middleware de Laravel (Chain of Responsibility) puede cortar la petición o pasarla. En Symfony el equivalente es un listener de kernel.request con alta prioridad que llama a setResponse().
  • Los tagged services de Symfony aplican OCP al contenedor: añadir una implementación = crear la clase con el tag. Sin editar ninguna lista central.
  • Los compiler passes manipulan el contenedor en compilación, no en runtime: más potentes que los tags, pero también más complejos. El coste es en caché, no en cada petición.
  • Los service providers de Laravel centralizan bindings (register()) y configuración del framework (boot()). La separación evita dependencias circulares entre providers.
  • La regla de oro: nunca modificar vendor/. Los puntos de extensión formales existen precisamente para que no tengas que hacerlo.
