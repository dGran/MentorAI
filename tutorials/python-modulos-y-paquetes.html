Módulos y paquetes en Python

Módulos

En Python, cada fichero .py es un módulo. Cuando Python importa un módulo, ejecuta su contenido de arriba a abajo y crea un objeto módulo con todos los nombres definidos en él como atributos.

import math
import json
import os

print(math.pi)       # 3.141592653589793
print(math.sqrt(16)) # 4.0

from math import sqrt, pi
from math import sqrt as raiz_cuadrada

datos = json.loads('{"nombre": "Ana", "edad": 30}')
print(datos["nombre"])  # Ana

La diferencia con PHP: en PHP, include o require ejecuta el fichero en el scope actual. En Python, import ejecuta el módulo en su propio namespace y lo devuelve como un objeto. Si importas el mismo módulo dos veces, Python lo devuelve cacheado: el código del módulo solo se ejecuta una vez.

El acceso es siempre calificado: math.pi o from math import pi para importarlo directamente al namespace local. from math import * existe pero contamina el namespace y es desaconsejado en código de aplicación.

Paquetes y __init__.py

Un directorio con un fichero __init__.py es un paquete. El __init__.py puede estar vacío (solo marca el directorio como paquete) o puede re-exportar símbolos para simplificar el API público del paquete.

src/
└── app/
    ├── __init__.py
    ├── main.py
    ├── routers/
    │   ├── __init__.py
    │   ├── usuarios.py
    │   └── productos.py
    ├── models/
    │   ├── __init__.py
    │   └── usuario.py
    └── services/
        ├── __init__.py
        └── usuario_service.py

El __init__.py de routers/ puede re-exportar los routers para que el caller use from app.routers import router_usuarios en lugar de from app.routers.usuarios import router:

from app.routers.usuarios import router as router_usuarios
from app.routers.productos import router as router_productos

__all__ = ["router_usuarios", "router_productos"]

__all__ es una lista de strings que define qué nombres exporta el módulo cuando alguien hace from paquete import *. No afecta a los imports explícitos.

Namespace packages (PEP 420): desde Python 3.3, un directorio sin __init__.py también puede ser un paquete (namespace package). Se usan para dividir un paquete entre múltiples directorios o repositorios. En proyectos normales, incluir __init__.py es lo habitual y más explícito.

Imports absolutos y relativos

Los imports absolutos parten desde la raíz del proyecto:

from app.models.usuario import Usuario
from app.services.usuario_service import UsuarioService

Los imports relativos usan puntos para navegar desde el módulo actual:

from .models import Usuario           # módulo hermano
from ..services import UsuarioService  # paquete padre
from . import utils                    # módulo en el mismo paquete

PEP 8 recomienda imports absolutos porque son más explícitos y menos frágiles al mover ficheros. Los relativos son útiles dentro de un paquete para evitar acoplar el nombre del paquete.

El orden correcto de imports (PEP 8, también lo ordena Ruff automáticamente):

import os
import sys
from pathlib import Path

import fastapi
import httpx
from pydantic import BaseModel

from app.models.usuario import Usuario
from app.services import UsuarioService

Tres grupos separados por línea en blanco: stdlib, third-party y local.

Circular imports: el módulo A importa B, y B importa A. Python detecta el ciclo pero puede producir errores parciales dependiendo del orden. La solución habitual es mover el import al interior de la función que lo necesita, o reestructurar para eliminar el ciclo (lo cual es la causa raíz del problema).

Estructura típica de un proyecto FastAPI

src/
└── app/
    ├── __init__.py
    ├── main.py             # crea la instancia FastAPI y registra routers
    ├── config.py           # Settings con Pydantic BaseSettings
    ├── database.py         # engine y AsyncSession
    ├── routers/
    │   ├── __init__.py
    │   ├── usuarios.py     # @router.get/post/put/delete
    │   └── productos.py
    ├── models/
    │   ├── __init__.py
    │   └── usuario.py      # SQLAlchemy ORM models
    ├── schemas/
    │   ├── __init__.py
    │   └── usuario.py      # Pydantic schemas (request/response)
    └── services/
        ├── __init__.py
        └── usuario_service.py  # lógica de negocio

La separación entre models/ (ORM, estructura de la BD) y schemas/ (Pydantic, estructura de la API) es un patrón habitual en FastAPI. Evita exponer la estructura interna de la BD directamente en la API y permite que evolucionen de forma independiente.

En main.py:

from fastapi import FastAPI

from app.routers import router_usuarios, router_productos

app = FastAPI(title="Mi API")

app.include_router(router_usuarios, prefix="/usuarios", tags=["usuarios"])
app.include_router(router_productos, prefix="/productos", tags=["productos"])

Resumen

  • Un fichero .py es un módulo; un directorio con __init__.py es un paquete. Los módulos se cachean: importar el mismo módulo varias veces solo ejecuta el código una vez.
  • import módulo da acceso calificado; from módulo import nombre importa al namespace local. from módulo import * es desaconsejado.
  • Los imports absolutos son más explícitos y resistentes al refactoring; los relativos son útiles dentro de un paquete para no acoplar el nombre del paquete.
  • El orden PEP 8 de imports (stdlib → third-party → local) lo aplica Ruff automáticamente.
  • La estructura FastAPI separa models/ (ORM) de schemas/ (Pydantic) para que la BD y la API evolucionen independientemente.
