Funciones, triggers y webhooks: lógica dentro de Postgres

Sin un backend propio en medio, la base de datos asume parte del trabajo que antes hacía tu código: crear el perfil cuando alguien se registra, mantener un updated_at, avisar a otro servicio cuando cambia una fila. Postgres sabe hacer todo eso. La pregunta es cuánto meter ahí sin que se convierta en lógica escondida.

Ya usaste una función con rpc en la Data API y otra security definer para romper la recursión en RLS. Esta lección ordena todo eso: qué tipos de funciones hay, cuándo se disparan solas con un trigger y cómo hacer que un cambio en una tabla llegue a un servicio externo.

Funciones: SQL o PL/pgSQL, invoker o definer #

Una función de Postgres tiene dos decisiones importantes. La primera es el lenguaje:

  • **language sql**: una o varias consultas, sin variables ni control de flujo. El planificador puede integrarla en la consulta que la llama, así que suele ser la más rápida. Úsala siempre que te baste.
  • **language plpgsql**: el lenguaje procedural de Postgres, con variables, if, bucles y excepciones. Para lógica con pasos.

La segunda es con qué permisos corre, y es una decisión de seguridad:

security invoker (por defecto)

  • Corre con el rol de quien la llama
  • RLS se aplica dentro como en cualquier consulta
  • Es la opción segura para casi todo lo que se llama con rpc

security definer

  • Corre con el rol de quien la creó (normalmente postgres)
  • Se salta RLS y puede tocar esquemas como auth
  • Necesaria para triggers sobre auth.users y para romper recursiones; peligrosa si la puede llamar cualquiera

Una función security definer es una puerta con llave maestra. Tres reglas la mantienen cerrada:

  • **Siempre set search_path = ''** y nombres completos dentro (public.notes, no notes). Sin eso, quien la llama podría crear en otro esquema un objeto con el mismo nombre que una tabla que la función usa y hacer que la función lo use con sus privilegios. El Security Advisor marca las funciones sin search_path fijo.
  • Fuera de los esquemas expuestos, en uno como private, si no está pensada para llamarse desde la API.
  • Si tiene que ser pública, quita el permiso de ejecución a quien no lo necesite: revoke execute on function ... from public, anon;.

El trigger que crea el perfil al registrarse #

La tabla auth.users es de Auth: no la expongas ni le añadas columnas. Los datos públicos del usuario (nombre visible, avatar) van en una tabla tuya, public.profiles, con una fila por usuario. Para que esa fila exista siempre, se crea con un trigger en el momento del registro:

sql · perfiles creados automáticamente 
create table public.profiles (
  id uuid primary key references auth.users (id) on delete cascade,
  display_name text,
  avatar_path text,
  updated_at timestamptz not null default now()
);

alter table public.profiles enable row level security;

create policy "Perfiles visibles para usuarios con sesión"
on public.profiles for select to authenticated using (true);

create policy "Cada uno edita su perfil"
on public.profiles for update to authenticated
using ((select auth.uid()) = id)
with check ((select auth.uid()) = id);

create function private.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
begin
  insert into public.profiles (id, display_name)
  values (new.id, new.raw_user_meta_data ->> 'display_name');

  return new;
end;
$$;

create trigger on_auth_user_created
after insert on auth.users
for each row execute function private.handle_new_user();

raw_user_meta_data es el user_metadata que el cliente mandó al registrarse (signUp({ email, password, options: { data: { display_name: "Ana" } } })). Sirve para rellenar el perfil; no para autorizar, porque lo escribe el usuario.

Si el trigger falla, el registro falla

El trigger corre dentro de la misma transacción que crea el usuario. Un error ahí (una columna not null que el cliente no mandó, una restricción que no se cumple) hace que nadie pueda registrarse, con un error genérico de «Database error saving new user». Mantén estos triggers mínimos, tolerantes con datos que faltan y probados con db reset y un registro real en local.

Triggers para el día a día #

Además del perfil, hay tres usos de triggers que aparecen en casi todos los proyectos:

sql · updated_at automático 
create function private.touch_updated_at()
returns trigger
language plpgsql
set search_path = ''
as $$
begin
  new.updated_at = now();
  return new;
end;
$$;

create trigger notes_touch_updated_at
before update on public.notes
for each row execute function private.touch_updated_at();
  • Campos derivados: updated_at, un contador de notas por libreta, un search_vector para búsqueda de texto. Un trigger before modifica new antes de guardar.
  • Auditoría: un trigger after que copia en una tabla de historial quién cambió qué y cuándo.
  • Invariantes entre tablas que un check no puede expresar porque miran otras filas.

Lo que no conviene meter en triggers: llamadas lentas, lógica que cambia cada semana y reglas que nadie va a buscar ahí. Un trigger es invisible desde el código de la app; si alguien no sabe que existe, un update que «hace cosas raras» le costará una tarde.

Webhooks de base de datos: avisar fuera con pg_net #

A veces un cambio en una tabla tiene que llegar a otro sitio: mandar un email cuando se comparte una nota, avisar a Slack o lanzar una Edge Function. Supabase lo resuelve con Database Webhooks (en Integrations), que por debajo son un trigger que hace una petición HTTP con la extensión **pg_net**.

1 Insert en note_sharesla transacción del usuario
2 pg_net encola la peticiónnet.http_post(url, body, headers) devuelve un id al momento
3 Proceso de pg_netenvía la petición HTTP en segundo plano
4 Tu Edge Function o serviciorecibe { type, table, schema, record, old_record }

El insert no espera a la petición: pg_net la encola y la manda un proceso aparte.

sql · lo que hace un webhook por dentro 
create function private.notify_share()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
begin
  perform net.http_post(
    url := 'https://abcdefghijklmnop.supabase.co/functions/v1/notify-share',
    body := jsonb_build_object('record', to_jsonb(new)),
    headers := jsonb_build_object('Content-Type', 'application/json')
  );

  return new;
end;
$$;

Que sea asíncrono es una ventaja (el usuario no espera a Slack) y tiene dos consecuencias que hay que asumir:

  • El cambio se guarda aunque la petición falle. pg_net no reintenta. Las respuestas quedan unas horas en net._http_response, donde puedes ver los fallos, pero nadie los reprocesa por ti.
  • Si el aviso es importante, no basta. Para «este email tiene que salir sí o sí», el patrón robusto es encolar el trabajo en una tabla o en una cola dentro de la misma transacción y procesarla con reintentos. Webhooks cuenta el lado del receptor: responder rápido y deduplicar.

Extensiones: lo que ya trae tu Postgres #

Mucho de lo que en otros stacks sería un servicio aparte, en Supabase es una extensión que se activa en Database → Extensions o con create extension. Las que más se usan:

ExtensiónPara quéDónde se ve en el curso

pg_cronTareas programadasCron

pg_trgmBúsqueda aproximada por similitud de textoBuscar «recta» y encontrar «receta»

Supabase instala las extensiones en el esquema extensions para que no ensucien public ni queden expuestas en la API. Extensiones y wrappers recorre las menos conocidas.

Resumen #

Lo que te llevas

  • Las funciones language sql son las más simples y rápidas; plpgsql añade variables y control de flujo.
  • security invoker respeta RLS; security definer corre como su creador y exige search_path vacío, esquema privado y permisos de ejecución recortados.
  • El perfil de cada usuario se crea con un trigger sobre auth.users; si ese trigger falla, falla el registro.
  • Los triggers resuelven campos derivados, auditoría e invariantes, pero esconden lógica: mantenlos pocos y pequeños.
  • Los webhooks de base de datos usan pg_net: asíncronos, sin frenar la transacción y sin reintentos.
  • Muchas piezas de Supabase son extensiones de Postgres que viven en el esquema extensions.
