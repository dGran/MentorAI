Del requisito al issue: el issue como contrato

En un método de entrega, el issue no es una nota para acordarse: es el contrato. El agente que implementa lo trata como especificación, el que revisa lo usa como vara de medir y el QA ejecuta sus criterios uno a uno. Si el issue está mal escrito, todo lo que viene detrás hereda el error.

En el flujo de equipo viste la idea de que el issue es el contrato entre fases. Esta lección baja a cómo se escribe ese contrato para que funcione: qué partes tiene, cómo se redacta un bug y qué comprobaciones hay que hacer antes de crear un issue y antes de empezar a implementarlo.

Un issue, un PR razonable #

La primera decisión al convertir una idea en trabajo es el tamaño. La regla práctica: cada issue debe poder resolverse en un PR que se implementa de una vez, se prueba y se revisa. Más grande, y el PR mezcla cosas que no se pueden revisar ni revertir por separado; más pequeño, y el coste de cada ciclo completo (rama, revisión, QA, despliegue) se come el trabajo.

Si una pieza no cabe en un PR, se parte. Si dos piezas son inseparables —una no tiene sentido sin la otra—, se juntan. Y si el trabajo es demasiado grande para una sesión de trabajo, no es un issue: es una épica, con su propio plan por fases.

Las partes del contrato #

Un issue útil tiene siempre la misma estructura, porque cada fase posterior busca en él una parte distinta:

Sección Qué contiene Quién la usa
ContextoQué se quiere y por qué, en pocas líneasQuien implementa, para decidir con criterio
Criterios de aceptaciónLista de comprobaciones verificablesReview y QA: es la vara de medir
Notas técnicasCapas afectadas, decisiones ya tomadas, pistasQuien implementa, para no rediseñar lo decidido
DependenciasQué otro issue tiene que estar hecho antes, y por quéQuien elige el siguiente trabajo

La sección que más importa es la de criterios. Un criterio verificable dice qué se comprueba y qué resultado se espera; uno vago, no.

Criterio verificable

  • El listado de pedidos se ordena por fecha descendente
  • Sin sesión, GET /api/pedidos devuelve 401
  • Con el campo email vacío, el formulario muestra «El email es obligatorio» y no se envía

Criterio vago

  • El listado funciona bien
  • La API es segura
  • El formulario valida correctamente

Escribe el criterio pensando en el QA

Antes de dar por bueno un criterio, imagina a alguien con la aplicación levantada intentando comprobarlo. Si no sabe qué hacer ni qué debería ver, el criterio no es verificable todavía.

Un bug se reproduce, no se describe #

Un issue de bug sin causa ni reproducción es un síntoma, no una tarea. Antes de redactarlo hay que reproducir el fallo y, si es posible, localizar la causa en el código. Lo crucial es que la reproducción se escriba para volver a ejecutarla, no para leerla:

markdown · reproducción en un issue (proyecto ficticio «tienda») 
**Reproducción**
$ curl -s -X POST localhost:8080/api/carrito/42/cupon -d '{"codigo":"VERANO"}'
{"total": -3.50}

**Causa:** AplicaCupon.php:31 resta el descuento fijo sin comprobar que el total
no baje de cero.

El par «comando más salida de hoy» es lo que permitirá al QA, después del arreglo, ejecutar exactamente lo mismo y demostrar que el fallo se fue. Sin él, el QA solo comprobará que el camino feliz funciona, que no es lo mismo.

Contrastar con lo que ya hay #

Un issue nuevo se escribe contra el código y también contra el backlog abierto, que contiene trabajo que todavía no se ve en la rama principal. Cada tarea que vas a proponer cae en uno de tres casos:

Caso Qué significa Qué se hace
ContenidoLo que pides ya es un criterio de otro issue abiertoNo se crea: se amplía el existente o no se hace nada
ContradictorioPide lo contrario de algo que otro issue ya decidióSe para y se pregunta: es una decisión, no una tarea
AdyacenteToca lo mismo pero pide algo distintoSe crea, apuntando al otro issue como dependencia

Mencionar el issue vecino en una nota («conviene mirarlo junto al #31») no es haber contrastado: deja la decisión a quien implemente. La salida tiene que ser una de las tres.

Dependencias que se pueden consultar #

Si el issue B necesita el A, escribirlo en la descripción explica por qué, pero no permite consultarlo: para saber qué trabajo está libre habría que abrir los issues uno a uno. Por eso las dependencias se declaran además en un campo del gestor que se puede consultar («bloqueado por»), y se deja la prosa para el porqué.

Léelo de vuelta

Al crear muchas dependencias con un script, comprueba el resultado consultando el gestor, no confiando en que las llamadas no dieran error. Un bucle mal escrito puede crear solo la primera dependencia de cada issue sin fallar, y el grafo queda incompleto sin que nadie lo note.

Refinar antes de implementar #

Entre que se escribe un issue y que alguien lo toma pueden pasar semanas, y el código cambia. Antes de implementar conviene un paso corto de refinamiento: contrastar cada afirmación del issue con el código actual.

  • Datos que ya no cuadran: rutas, nombres de función o números de línea que se movieron.
  • Criterios que ya se cumplen: el caso más traicionero. Un agente que implementa un criterio que ya se cumple marca la casilla sin tocar nada, y el PR sale vacío con todo en verde.
  • Contradicciones entre la descripción y los comentarios: quien implemente leerá uno de los dos; hay que dejar claro cuál manda.
  • Alcance que se queda corto: lo que el issue no menciona pero el cambio va a necesitar.

El refinamiento corrige el issue y deja constancia con fecha y versión del código contra la que se comprobó. Si pasa mucho tiempo y ese código cambia, se vuelve a refinar.

Cuándo aplicarlo #

Escribe issues así cuando…

  • Quien implementa no es quien pidió el cambio, o es un agente
  • Habrá revisión y QA contra lo que pide el issue
  • Varias personas o agentes trabajan sobre el mismo backlog
  • El issue puede esperar semanas antes de que alguien lo tome

Puedes aligerarlo si…

  • Es un cambio tuyo de cinco minutos que vas a hacer ahora mismo
  • No hay revisión ni QA posterior que necesite criterios
  • Es una exploración sin resultado esperado definido

Resumen #

Lo que te llevas

  • Un issue debe caber en un PR que se implementa, prueba y revisa de una vez; lo que no cabe se parte o es una épica.
  • El contrato tiene contexto, criterios verificables, notas técnicas y dependencias, y cada fase usa una parte.
  • Un bug lleva su reproducción ejecutable con la salida real, para que el QA pueda demostrar que se fue.
  • Cada issue nuevo se contrasta con el backlog: contenido, contradictorio o adyacente, con una salida explícita.
  • Las dependencias van en un campo consultable, y antes de implementar se refina contra el código actual para cazar criterios que ya se cumplen.
