Pydantic v2: validación y modelos

Pydantic convierte diccionarios y datos externos en objetos Python tipados y validados. Aprenderás a definir modelos con BaseModel, añadir lógica de validación con @field_validator, restringir campos con Field, componer modelos anidados y centralizar la configuración de la aplicación con BaseSettings.

13 min Intermedio Python

En este tutorial

  1. BaseModel: la base de todo
  2. Validadores de campo
  3. Field: metadatos, restricciones y alias
  4. Modelos anidados y serialización
  5. BaseSettings para configuración
  6. Resumen

BaseModel: la base de todo

Una clase que hereda de BaseModel describe la forma que deben tener los datos. Pydantic lee las anotaciones de tipo y, en el momento de instanciar, valida cada campo y coerciona los tipos cuando puede hacerlo sin pérdida de información:

from pydantic import BaseModel


class Usuario(BaseModel):
    id: int
    nombre: str
    email: str
    activo: bool = True


usuario = Usuario(id=1, nombre="Ana", email="ana@example.com")
print(usuario.id)             # 1
print(usuario.activo)         # True
print(usuario.model_dump())   # {'id': 1, 'nombre': 'Ana', 'email': 'ana@example.com', 'activo': True}

Si pasas id="1" (string), Pydantic lo convierte a int automáticamente. Si pasas algo que no puede convertirse, lanza ValidationError con un mensaje claro que señala exactamente qué campo falló y por qué:

from pydantic import BaseModel, ValidationError


class Temperatura(BaseModel):
    valor: float
    unidad: str = "celsius"


t = Temperatura(valor="37.5")
print(t.valor)   # 37.5 — convertido de str a float

try:
    Temperatura(valor="muy_caliente")
except ValidationError as error:
    print(error.error_count())           # 1
    print(error.errors()[0]["type"])     # 'float_parsing'
    print(error.errors()[0]["loc"])      # ('valor',)

Los modelos son inmutables por defecto. Esto los hace seguros para pasar entre capas sin riesgo de mutaciones inesperadas. Si necesitas mutabilidad, actívala con model_config = ConfigDict(frozen=False).

Cambios de v1 a v2 que rompen código

Pydantic v2 reescribió el núcleo en Rust y cambió la API en varios puntos críticos. Los más frecuentes al migrar: .dict() desapareció, ahora es .model_dump(); .json() es .model_dump_json(); parse_obj() es model_validate(); schema() es model_json_schema(); @validator fue reemplazado por @field_validator (que requiere @classmethod); y @root_validator por @model_validator. También desapareció __fields__, reemplazado por model_fields.

Validadores de campo

@field_validator define lógica de validación personalizada que se ejecuta además de la validación de tipo. Recibe el valor del campo y debe devolver el valor (posiblemente transformado) o lanzar ValueError. Requiere @classmethod encima:

from pydantic import BaseModel, field_validator


class Producto(BaseModel):
    nombre: str
    precio: float

    @field_validator("nombre")
    @classmethod
    def nombre_no_vacio(cls, value: str) -> str:
        value = value.strip()

        if not value:
            raise ValueError("El nombre no puede estar vacío")

        return value

    @field_validator("precio")
    @classmethod
    def precio_positivo(cls, value: float) -> float:
        if value <= 0:
            raise ValueError("El precio debe ser mayor que cero")

        return value

Por defecto el validador recibe el valor ya convertido al tipo declarado (mode="after"). Si necesitas acceder al valor crudo antes de la conversión de tipo, usa mode="before". Un validador puede aplicarse a varios campos a la vez pasando múltiples nombres:

from pydantic import BaseModel, field_validator


class Inventario(BaseModel):
    stock_actual: int
    stock_minimo: int
    stock_maximo: int

    @field_validator("stock_actual", "stock_minimo", "stock_maximo")
    @classmethod
    def no_negativo(cls, value: int) -> int:
        if value < 0:
            raise ValueError("El stock no puede ser negativo")

        return value

Cuando la validación depende de varios campos a la vez, usa @model_validator con mode="after". En ese modo recibe la instancia ya construida (self) con todos los campos disponibles:

from pydantic import BaseModel, model_validator


class Rango(BaseModel):
    minimo: float
    maximo: float

    @model_validator(mode="after")
    def minimo_menor_que_maximo(self) -> "Rango":
        if self.minimo >= self.maximo:
            raise ValueError("El mínimo debe ser estrictamente menor que el máximo")

        return self


Rango(minimo=1.0, maximo=10.0)    # OK
Rango(minimo=10.0, maximo=1.0)    # ValidationError

Si necesitas transformar los datos antes de que se construya el modelo (por ejemplo, renombrar claves de un diccionario externo), usa @model_validator(mode="before"): en ese caso el validador recibe el dict crudo y debe devolver un dict modificado.

Field: metadatos, restricciones y alias

Field() extiende la declaración de un campo con restricciones numéricas, de longitud y metadatos que se exportan al JSON Schema. Las restricciones se validan automáticamente junto con el tipo:

from pydantic import BaseModel, Field


class Articulo(BaseModel):
    titulo: str = Field(min_length=3, max_length=200)
    precio: float = Field(gt=0.0, description="Precio en euros sin IVA")
    descuento: float = Field(default=0.0, ge=0.0, le=1.0)
    sku: str = Field(alias="codigo_externo")

Las restricciones disponibles para números son gt (mayor que), ge (mayor o igual), lt (menor que) y le (menor o igual). Para cadenas, min_length, max_length y pattern (regex).

El alias permite que el campo Python tenga un nombre diferente al que llega en los datos de entrada. Esto es útil cuando el JSON externo usa una convención de nombres distinta:

articulo = Articulo(
    titulo="Teclado mecánico",
    precio=89.99,
    codigo_externo="TEC-001",
)
print(articulo.sku)                        # TEC-001
print(articulo.model_dump())               # {'titulo': ..., 'sku': 'TEC-001', ...}
print(articulo.model_dump(by_alias=True))  # {'titulo': ..., 'codigo_externo': 'TEC-001', ...}

Si la entrada siempre usa el alias pero la salida debe usar el nombre Python, usa validation_alias en lugar de alias. Si tanto la entrada como la salida deben usar el alias, usa alias con model_config = ConfigDict(populate_by_name=True) para también poder pasar el nombre Python.

Modelos anidados y serialización

Un campo puede ser otro BaseModel. Pydantic valida los modelos anidados recursivamente, tanto si los recibes como objetos como si los recibes como diccionarios crudos:

from pydantic import BaseModel


class Direccion(BaseModel):
    calle: str
    ciudad: str
    codigo_postal: str


class Cliente(BaseModel):
    nombre: str
    direccion: Direccion
    etiquetas: list[str] = []


cliente = Cliente(
    nombre="Carlos",
    direccion={"calle": "Gran Vía 1", "ciudad": "Madrid", "codigo_postal": "28013"},
    etiquetas=["vip", "recurrente"],
)

print(cliente.direccion.ciudad)           # Madrid
print(cliente.model_dump())               # diccionario con dirección anidada
print(cliente.model_dump_json(indent=2))  # JSON formateado

Para construir un modelo a partir de un diccionario externo usa model_validate(). Para construirlo directamente desde una cadena JSON, usa model_validate_json(). Ambos validan igual que la instanciación directa:

datos = {
    "nombre": "Luisa",
    "direccion": {"calle": "Rambla 5", "ciudad": "Barcelona", "codigo_postal": "08001"},
}
cliente = Cliente.model_validate(datos)

json_raw = '{"nombre":"Pedro","direccion":{"calle":"Av. Paz","ciudad":"Sevilla","codigo_postal":"41001"}}'
cliente2 = Cliente.model_validate_json(json_raw)

schema = Cliente.model_json_schema()
print(schema["properties"]["direccion"]["$ref"])  # '#/$defs/Direccion'

model_json_schema() genera el JSON Schema completo del modelo, incluyendo los modelos anidados en $defs. FastAPI usa esto para construir la documentación OpenAPI automáticamente.

Para colecciones tipadas es suficiente con las anotaciones: list[Direccion] o dict[str, Producto]. Pydantic valida cada elemento de la colección de forma individual y lanza ValidationError indicando el índice o clave del elemento que falló.

BaseSettings para configuración

BaseSettings extiende BaseModel para leer automáticamente el valor de cada campo desde variables de entorno. Es la forma idiomática de gestionar la configuración de una aplicación sin duplicar lógica entre el .env, el sistema y los valores por defecto:

pip install pydantic-settings
from pydantic_settings import BaseSettings, SettingsConfigDict
from pydantic import SecretStr


class Configuracion(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_prefix="APP_")

    base_de_datos_url: str
    debug: bool = False
    max_conexiones: int = 10
    clave_secreta: SecretStr


config = Configuracion()
print(config.base_de_datos_url)
print(config.debug)
print(config.clave_secreta.get_secret_value())

Con env_prefix="APP_", el campo base_de_datos_url se mapea a la variable de entorno APP_BASE_DE_DATOS_URL. El fichero .env correspondiente:

APP_BASE_DE_DATOS_URL=postgresql+asyncpg://user:pass@localhost/mi_base
APP_DEBUG=false
APP_MAX_CONEXIONES=20
APP_CLAVE_SECRETA=s3cr3t-k3y!

SecretStr almacena el valor de forma que repr() lo muestra como **********. Para leerlo, llamas explícitamente a .get_secret_value(). Esto evita que claves y contraseñas aparezcan en logs accidentalmente.

El orden de precedencia es: variable de entorno del sistema → .env → valor por defecto del campo. Si un campo sin valor por defecto no está en ninguna fuente, la instanciación falla con ValidationError, detectando configuraciones incompletas en el arranque antes de procesar ninguna petición.

Singleton de configuración: en proyectos FastAPI es habitual exponer la configuración como config = Configuracion() a nivel de módulo y acceder a ella vía Depends(lambda: config). Esto permite sobreescribirla en tests inyectando una instancia con valores distintos sin tocar variables de entorno globales.

Resumen

  • BaseModel valida y coerciona tipos automáticamente en la instanciación; si algo falla, lanza ValidationError con detalle por campo.
  • @field_validator (con @classmethod obligatorio) añade lógica personalizada por campo; @model_validator(mode="after") valida con acceso a todos los campos a la vez.
  • Field() declara restricciones (gt, ge, min_length…), aliases y metadatos de documentación sin cambiar el tipo Python del campo.
  • Los modelos anidados se validan recursivamente; model_validate() acepta diccionarios crudos y model_validate_json() acepta strings JSON directamente.
  • model_dump() sustituye a .dict() de v1, y model_dump_json() sustituye a .json(). Son los métodos de serialización canónicos en v2.
  • BaseSettings unifica variables de entorno, fichero .env y valores por defecto en un único modelo validado; SecretStr protege los valores sensibles de aparecer en logs.
