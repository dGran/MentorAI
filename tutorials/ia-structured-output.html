Salida estructurada

Tu código no consume prosa: consume structs, columnas, enums. El eslabón entre «el modelo redacta bien» y «mi sistema funciona» es que la respuesta llegue con un contrato — un esquema que se cumple — y no como texto libre que parseas cruzando los dedos.

La lección anterior clasificaba tickets pidiendo «responde SOLO con una palabra» y confiando. Funciona el 98% de las veces — y ese 2% («La categoría es: facturación 😊») revienta tu match en producción un domingo. Esta lección elimina la fe de la ecuación.

El problema de parsear prosa #

Pedir JSON «por favor» en el prompt y parsear lo que llegue tiene los fallos conocidos: el modelo envuelve el JSON en explicación, o en un bloque markdown, o inventa una clave, o un enum que no existe. Puedes jugar al whack-a-mole con regex y reintentos — o usar el mecanismo que las APIs modernas traen para esto: salida estructurada, donde el esquema se declara en la petición y la plataforma restringe la generación para que la respuesta valide contra él. No es un prompt más insistente: es una garantía sintáctica.

Salida con esquema #

Conceptualmente, mandas dos cosas: la tarea y un esquema (tipos, campos obligatorios, enums cerrados). Recibes JSON que valida — sintácticamente — siempre. El clasificador de tickets, con contrato de verdad, pasa a devolver algo así:

la respuesta con contrato 
{
  "categoria": "facturacion",
  "urgencia": 3,
  "resumen": "Cliente cobrado dos veces por el pedido 8841",
  "requiere_humano": true
}

Fíjate en el salto de diseño: ya no extraes una cosa del texto — pides de una vez todos los campos que tu flujo necesita, tipados. Una llamada, un objeto, cero parseo heurístico.

En PHP: la clase es el contrato #

El SDK de Anthropic para PHP deja declarar el esquema como una clase — el mismo movimiento que un DTO con validación:

php · structured output con clase 
<?php

use Anthropic\Lib\Contracts\StructuredOutputModel;
use Anthropic\Lib\Concerns\StructuredOutputModelTrait;
use Anthropic\Lib\Attributes\Constrained;

final class TicketClasificado implements StructuredOutputModel
{
    use StructuredOutputModelTrait;

    #[Constrained(description: "Una de: facturacion, envio, producto, otro")]
    public string $categoria;

    #[Constrained(description: "1 (puede esperar) a 5 (critico)")]
    public int $urgencia;

    public string $resumen;

    public bool $requiereHumano;
}

$message = $client->messages->create(
    model: "claude-opus-5",
    maxTokens: 1024,
    messages: [["role" => "user", "content" => $textoDelTicket]],
    outputConfig: ["format" => TicketClasificado::class],
);

$ticket = $message->parsedOutput();   // instancia de TicketClasificado

Dos detalles con doctrina detrás. Las descripciones de los campos son prompt: el modelo las lee para decidir qué poner en cada campo — «1 (puede esperar) a 5 (crítico)» es la diferencia entre una urgencia calibrada y un número al azar. Y parsedOutput() te devuelve un objeto tipado: el no-determinismo queda confinado en los valores, nunca en la forma.

Tool use: estructura con otro sombrero #

Hay una segunda vía de obtener datos estructurados que ya conoces del curso de Claude Code: tool use. Defines «herramientas» con esquema (crear_ticket(categoria, urgencia)), y el modelo responde con una llamada tipada que tu código ejecuta. La frontera entre ambas es limpia:

Salida estructurada Tool use
Qué pides Un dato con forma: la respuesta final ES el JSON Que el modelo decida acciones: cada llamada es un paso
Quién controla el flujo Tú: una llamada, un resultado Compartido: el modelo elige qué herramienta y cuándo parar
Ejemplo Clasificar, extraer, puntuar «Resuelve este ticket»: consultar el pedido, emitir reembolso, responder

La regla práctica: si la respuesta es un dato, salida estructurada; si la tarea exige decidir pasos contra tus sistemas, tool use — y entonces estás construyendo un agente dentro de tu producto, con todo lo que el curso anterior te enseñó sobre permisos y verificación aplicado a tu propio código.

Lo que el esquema no garantiza #

El esquema garantiza la forma, no la verdad. urgencia: 3 valida aunque el ticket fuera crítico; un resumen puede validar y ser inexacto. Las comprobaciones que siguen siendo tuyas:

  • stopReason antes que nada. Una respuesta cortada por max_tokens o rehusada por seguridad no trae tu objeto: comprueba el motivo de parada antes de leer el contenido, siempre.
  • Validación de negocio. El esquema no sabe que un reembolso mayor que el importe del pedido es absurdo. Las reglas de dominio se validan en tu código, como con cualquier entrada externa — porque eso es esta respuesta: entrada externa.
  • Vía de escape. Dale al esquema un campo para la incertidumbre (una categoría otro, un requiereHumano). Un modelo forzado a elegir entre opciones que no encajan elige mal; con salida de emergencia, te lo señala.

Diseñar buenos esquemas #

Los mismos criterios que una API tuya, más uno propio de LLMs: enums cerrados mejor que strings libres (tu match agradece exhaustividad); campos con descripción calibrada (son prompt); y esquemas planos y pequeños — un mega-esquema de 30 campos anidados degrada la calidad de cada campo. Si necesitas mucho, considera dos llamadas especializadas en vez de una enciclopédica: es la responsabilidad única aplicada a los contratos con el modelo.

Cuándo aplicarlo #

Salida estructurada siempre que…

  • Otro código va a consumir la respuesta (o sea: casi siempre en backend)
  • Extraes campos, clasificas con enums, puntúas con rangos
  • Quieres confinar el no-determinismo a los valores

Texto libre solo cuando…

  • El destinatario es un humano leyendo (un chat, un borrador de email)
  • La «estructura» sería un único campo de prosa — no aporta nada

Resumen #

Lo que te llevas

  • Pedir JSON por favor y parsear es fe; la salida estructurada con esquema es garantía sintáctica de la plataforma.
  • En PHP el contrato es una clase (StructuredOutputModel) y las descripciones de los campos son prompt: se escriben con criterio.
  • Dato final → salida estructurada; decidir pasos contra tus sistemas → tool use (y entonces es un agente en tu producto).
  • El esquema garantiza la forma, no la verdad: stopReason primero, validación de negocio después, y una vía de escape en el esquema.
  • Esquemas pequeños, enums cerrados, descripciones calibradas: responsabilidad única también en los contratos con el modelo.
