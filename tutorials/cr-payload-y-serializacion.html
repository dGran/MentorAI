El peso de lo que mueves

Cuando el tiempo no está en la base de datos ni en tu lógica, suele estar en mover y transformar datos. Es el coste menos visible porque no aparece como una línea lenta, sino repartido.

Cuando el tiempo no está en la base de datos ni en tu lógica, suele estar en mover y transformar datos: serializar objetos que nadie mira, devolver campos que nadie usa, hidratar entidades completas para leer dos propiedades. Es el coste menos visible porque no aparece como una línea lenta, sino repartido por todas partes.

Lo más rápido es no traerlo #

SELECT * es cómodo y se paga tres veces: en la base de datos, que lee columnas que no necesitas —incluidos los TEXT gordos—; en la red, que los mueve; y en PHP, que construye objetos con ellos.

CosteQué lo produceQué hacer
Leer columnas de másSELECT * por costumbrePedir las columnas concretas; a veces basta una proyección
Hidratar entidadesEl ORM construye objetos completos con sus relacionesHidratación a array o DTO cuando solo vas a leer
Serializar de másDevolver la entidad entera «por si el cliente lo necesita»Un DTO de respuesta con lo que el cliente usa
Mover de másListados que devuelven 200 campos por filaCampos escasos: que el cliente pida lo que quiere

Leer y escribir no necesitan el mismo modelo

Una entidad del ORM está pensada para cambiar estado con garantías: seguimiento de cambios, relaciones, eventos. Para pintar un listado no necesitas nada de eso, y sí pagas por ello. Usar un DTO plano para las lecturas —una consulta que devuelve exactamente los campos de la pantalla— suele ser la mejora más grande de todo este módulo, y no es más que aplicar la separación de lectura y escritura sin montar CQRS entero.

php · una consulta para la pantalla 
<?php

declare(strict_types=1);

final class ListadoDePedidos
{
    public function ultimosDe(int $idCliente): array
    {
        return $this->conexion->fetchAllAssociative(
            'SELECT p.id, p.total_centimos, p.estado, p.creado_en, c.nombre AS cliente
             FROM pedidos p
             INNER JOIN clientes c ON c.id = p.id_cliente
             WHERE p.id_cliente = :cliente
             ORDER BY p.creado_en DESC
             LIMIT 20',
            ['cliente' => $idCliente]
        );
    }
}

Cinco columnas, un JOIN, sin entidades ni relaciones perezosas. No es «saltarse el ORM por vago»: es que el ORM resuelve un problema —escribir con consistencia— que un listado no tiene.

El coste de serializar #

Convertir objetos a JSON parece gratis y no lo es cuando hay volumen. Un serializador que usa reflexión y recorre anotaciones puede tardar un orden de magnitud más que json_encode sobre un array plano.

Caro

  • Serializador por reflexión sobre entidades con relaciones
  • Grupos de serialización resueltos en cada petición
  • Normalizar y luego codificar en dos pasadas

Barato

  • json_encode sobre arrays ya con la forma final
  • Metadatos de serialización cacheados y precalentados
  • Un DTO que ya es la respuesta, sin transformación

Y si el JSON es grande y estable, la última optimización es no volver a construirlo: cachear la cadena serializada, no el objeto. Te ahorras la serialización además de la consulta, y es el caso donde la caché rinde más.

Comprimir: casi siempre sí #

El JSON comprime extraordinariamente bien —es texto repetitivo— y la compresión es uno de los pocos intercambios que casi siempre sale a favor: gastas unos milisegundos de CPU para ahorrar cientos de milisegundos de red.

1 Respuesta JSON de 800 KBEn una conexión móvil: varios segundos
2 60 KB por el cableReducción típica del 90 % en JSON

Se activa en nginx, no en PHP: el proxy lo hace mejor y no consume tus workers.

Las dos excepciones

No comprimas lo que ya está comprimido —imágenes, vídeo, ficheros zip—: gastas CPU para no ahorrar nada. Y por debajo de un kilobyte tampoco compensa: la cabecera y el proceso cuestan más que lo que ahorras. Por eso nginx trae un gzip_min_length.

El N+1 de red #

El N+1 que todo el mundo conoce es el de la base de datos. El mismo patrón sobre llamadas HTTP es más caro —cada salto son milisegundos, no microsegundos— y mucho menos visible, porque no hay un contador de consultas que lo delate.

php · el bucle que cuesta 4 segundos 
<?php

foreach ($pedidos as $pedido) {
    $pedido['envio'] = $this->envios->consultar($pedido['id']);
}

Veinte pedidos, veinte llamadas HTTP de 200 ms: cuatro segundos. La solución es la misma que en la base de datos —pedir por lotes— y depende de que el otro servicio tenga un endpoint que acepte varios identificadores. Si no lo tiene, pedirlo es más rentable que optimizar tu lado.

Si no hay endpoint por lotes, al menos en paralelo

Veinte llamadas concurrentes tardan lo que la más lenta, no la suma. Es peor que un lote —veinte conexiones en vez de una— y muchísimo mejor que la serie. El cliente HTTP de Symfony lo hace con respuestas perezosas, como viste en la lección del presupuesto de latencia.

Cuándo aplicarlo #

Mira el payload cuando…

  • Las respuestas pesan cientos de kilobytes
  • Hay clientes móviles o con red mala
  • El perfil señala al serializador o a la hidratación del ORM
  • Un listado carga entidades completas para pintar cinco campos

No es tu cuello cuando…

  • Las respuestas son de unos pocos kilobytes
  • El tiempo está claramente en la base de datos
  • Son clientes internos en la misma red

Resumen #

Lo que te llevas

  • SELECT * se paga tres veces: leyendo columnas de más, moviéndolas y construyendo objetos con ellas.
  • Leer y escribir no necesitan el mismo modelo: un DTO plano para las lecturas suele ser la mejora más grande, y no exige montar CQRS.
  • Si el JSON es grande y estable, cachea la cadena serializada y no el objeto: te ahorras también la serialización.
  • Comprimir es de los pocos intercambios que casi siempre sale a favor, salvo con contenido ya comprimido o por debajo de un kilobyte.
  • El N+1 de red es más caro que el de base de datos y menos visible: no hay contador de consultas que lo delate.
