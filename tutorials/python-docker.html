En PHP la imagen suele ser php-fpm con un Nginx delante y poco más que decidir. En Python, la imagen base, el orden de las capas y la forma de arrancar el proceso marcan la diferencia entre una imagen de más de 1 GB y otra de unos 150 MB, entre reinstalar dependencias en cada cambio o reutilizar la caché, y entre un contenedor que para limpio y otro que Docker tiene que matar.

Elegir imagen base: slim, alpine y distroless #

Docker Hub ofrece varias variantes de la imagen oficial de Python. La elección afecta al tamaño final, a la velocidad de build y a la compatibilidad con librerías que tienen extensiones C.

Imagen Tamaño aprox. Base Shell
python:3.14 ~1,1 GB Debian (completo) Sí
python:3.14-slim ~120 MB Debian (mínimo) Sí
python:3.14-alpine ~55 MB musl libc Sí (ash)
gcr.io/distroless/python3 ~60 MB Debian (sin shell) No

slim vs alpine para Python: alpine usa musl libc en lugar de glibc. Los paquetes grandes con extensiones C (numpy, pandas, cryptography, psycopg2-binary) ya publican wheels precompilados para musl, pero algunas dependencias aún no los tienen (psycopg2 sin -binary, por ejemplo), y en alpine pip las compila desde el código fuente dentro del contenedor, lo que alarga el build y puede fallar. Además, musl difiere de glibc en rendimiento y comportamiento. slim es la elección más segura para la mayoría de proyectos Python; alpine solo merece la pena si controlas que todas tus dependencias tienen wheels para musl o son pure-Python.

Distroless elimina el shell y las utilidades del sistema, reduciendo la superficie de ataque. Es la opción más segura para producción cuando no necesitas hacer debug interactivo en el contenedor.

Ojo con la versión: gcr.io/distroless/python3 no sigue las etiquetas de la imagen oficial, sino el Python de Debian 13, que hoy es el 3.13. Un entorno virtual construido en cualquier python:*-slim no arranca ahí, ni siquiera con el 3.13: su intérprete apunta a /usr/local/bin, que en distroless no existe. Si el destino es distroless, el stage de build parte de debian:13-slim con python3-venv, que deja el mismo Python en /usr/bin.

Dockerfile multistage para FastAPI #

Un build multistage separa la instalación de dependencias (que necesita compiladores y herramientas de build) de la imagen final (que solo necesita los ficheros compilados). El resultado es una imagen de producción más pequeña y sin herramientas innecesarias.

dockerfile 
FROM python:3.14-slim AS builder
WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

FROM python:3.14-slim
RUN useradd -m -u 1000 appuser
WORKDIR /app

COPY --from=builder --chown=appuser:appuser /root/.local /home/appuser/.local
COPY . .

RUN chown -R appuser:appuser /app
USER appuser

ENV PATH=/home/appuser/.local/bin:$PATH
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

El orden de las instrucciones COPY importa para la caché de capas. Copiar requirements.txt antes que el código fuente significa que la capa de instalación de dependencias solo se invalida cuando cambia requirements.txt, no en cada cambio de código.

El fichero .dockerignore evita copiar ficheros innecesarios al contexto de build:

text 
__pycache__
*.pyc
*.pyo
.env
.env.*
.git
.pytest_cache
.mypy_cache
.ruff_cache
tests/
*.md

Para construir y ejecutar la imagen:

bash 
docker build -t mi-fastapi-app:latest .
docker run -p 8000:8000 --env-file .env mi-fastapi-app:latest

docker-compose con PostgreSQL y Redis #

Un entorno de desarrollo completo necesita la API, la base de datos y la caché. depends_on con condition: service_healthy garantiza que la API no arranca hasta que PostgreSQL esté lista para aceptar conexiones:

yaml 
services:
  api:
    build: .
    ports:
      - "8000:8000"
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
    volumes:
      - .:/app

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: myapp
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - db_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U myapp"]
      interval: 5s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    volumes:
      - redis_data:/data

volumes:
  db_data:
  redis_data:

El volumen montado en api (.:/app) es solo para desarrollo: refleja los cambios del código en tiempo real sin reconstruir la imagen. En producción, elimina ese volumen.

Comandos habituales del ciclo de desarrollo:

bash 
docker compose up -d
docker compose logs -f api
docker compose exec api python -m pytest
docker compose down -v

Errores típicos al dockerizar Python

Escuchar en 127.0.0.1. Es el host por defecto de uvicorn, y dentro del contenedor es el loopback del propio contenedor: el puerto publicado no llega a la aplicación. Arranca con --host 0.0.0.0.

CMD en forma shell. Con CMD uvicorn main:app ... el proceso puede quedar bajo /bin/sh -c, que no reenvía SIGTERM: docker stop espera el plazo de gracia y lo mata con SIGKILL, sin cierre ordenado. Usa la forma exec, CMD ["uvicorn", ...].

Olvidar el .dockerignore. Sin él, COPY . . mete en la imagen el .env, el .git y tu .venv local: más tamaño, caché invalidada en cada cambio y secretos dentro de una capa.

Desplegar el compose de desarrollo. El volumen .:/app sustituye el código de la imagen por el de tu disco. En producción lo que se despliega es la imagen, tal cual se construyó.

Variables de entorno y secretos #

Hay tres formas de pasar configuración a un contenedor, cada una con su caso de uso:

Mecanismo Cuándo usarlo
env_file: .env en compose Desarrollo local; nunca commitear el fichero
Variables de entorno en el sistema CI/CD y producción sin gestor de secretos
Docker secrets o vault Producción con alta sensibilidad (tokens, claves privadas)

La API lee las variables con pydantic-settings, sin importar de dónde vengan:

python 
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8")

    database_url: str
    redis_url: str = "redis://redis:6379/0"
    secret_key: str
    debug: bool = False

En producción, las variables se inyectan directamente en el entorno del contenedor o desde un gestor de secretos (AWS Secrets Manager, HashiCorp Vault). El código no cambia: pydantic-settings las recoge del entorno del proceso.

Nunca uses ENV SECRET_KEY=valor_real en el Dockerfile: ese valor queda grabado en el historial de capas de la imagen y cualquiera con acceso al registro puede extraerlo con docker history.

Cuándo aplicarlo #

Contenedoriza cuando…

  • El entorno tiene varios servicios (API, PostgreSQL, Redis) que todo el equipo debe levantar igual
  • Despliegas en algo que consume imágenes: Kubernetes, ECS, Cloud Run o un servidor con compose
  • Tienes dependencias con extensiones C o librerías de sistema que no quieres pelear en cada portátil
  • El build necesita compiladores que no quieres en producción: ahí entra el multistage

No hace falta, o elige otra cosa, cuando…

  • Es un script o una librería: un entorno virtual con python -m venv basta
  • Eliges alpine para ahorrar megas y dependes de paquetes con wheels solo para glibc
  • Quieres distroless pero aún necesitas entrar con un shell a depurar

Un término medio que funciona bien en local: contenedores para lo que no es tuyo (la base de datos, la caché) y la API en el host con un venv y uvicorn --reload, que itera más rápido. El Dockerfile no deja de probarse: lo construye CI en cada push, y esa es la imagen que llega a producción.

Resumen #

Lo que te llevas

  • python:3.14-slim es la imagen base más pragmática para Python: Debian mínimo, glibc compatible con wheels precompilados, sin las complicaciones de compilación de alpine.
  • El build multistage instala dependencias en una etapa builder y copia solo los artefactos a la imagen final, reduciendo tamaño y superficie de ataque.
  • Copiar requirements.txt antes del código fuente maximiza la reutilización de la caché de capas: la capa de instalación solo se reconstruye cuando cambian las dependencias.
  • depends_on con condition: service_healthy garantiza que la API no arranca hasta que PostgreSQL esté respondiendo; sin healthcheck, la API arrancaría antes de que la base de datos esté lista.
  • Nunca embeber secretos en el Dockerfile ni en la imagen: se quedan en el historial de capas. Los secretos llegan siempre por variables de entorno, env_file o un gestor de secretos.
