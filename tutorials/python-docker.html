Elegir imagen base: slim, alpine y distroless

Docker Hub ofrece varias variantes de la imagen oficial de Python. La elección afecta al tamaño final, a la velocidad de build y a la compatibilidad con librerías que tienen extensiones C.

Imagen Tamaño aprox. Base Shell
python:3.12 ~1 GB Debian (completo) Sí
python:3.12-slim ~130 MB Debian (mínimo) Sí
python:3.12-alpine ~50 MB musl libc Sí (ash)
gcr.io/distroless/python3 ~50 MB Debian (sin shell) No
slim vs alpine para Python: alpine usa musl libc en lugar de glibc. Muchos paquetes Python con extensiones C (numpy, pandas, psycopg2, cryptography) distribuyen wheels precompilados para glibc. En alpine, pip los compila desde el código fuente dentro del contenedor, lo que alarga el build y puede fallar. slim es la elección más segura para la mayoría de proyectos Python; alpine solo merece la pena si controlas que todas tus dependencias tienen wheels para musl o son pure-Python.

Distroless elimina el shell y las utilidades del sistema, reduciendo la superficie de ataque. Es la opción más segura para producción cuando no necesitas hacer debug interactivo en el contenedor.

Dockerfile multistage para FastAPI

Un build multistage separa la instalación de dependencias (que necesita compiladores y herramientas de build) de la imagen final (que solo necesita los ficheros compilados). El resultado es una imagen de producción más pequeña y sin herramientas innecesarias.

FROM python:3.12-slim AS builder
WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

FROM python:3.12-slim
RUN useradd -m -u 1000 appuser
WORKDIR /app

COPY --from=builder /root/.local /root/.local
COPY . .

RUN chown -R appuser:appuser /app
USER appuser

ENV PATH=/root/.local/bin:$PATH
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

El orden de las instrucciones COPY importa para la caché de capas. Copiar requirements.txt antes que el código fuente significa que la capa de instalación de dependencias solo se invalida cuando cambia requirements.txt, no en cada cambio de código.

El fichero .dockerignore evita copiar ficheros innecesarios al contexto de build:

__pycache__
*.pyc
*.pyo
.env
.env.*
.git
.pytest_cache
.mypy_cache
.ruff_cache
tests/
*.md

Para construir y ejecutar la imagen:

docker build -t mi-fastapi-app:latest .
docker run -p 8000:8000 --env-file .env mi-fastapi-app:latest

docker-compose con PostgreSQL y Redis

Un entorno de desarrollo completo necesita la API, la base de datos y la caché. depends_on con condition: service_healthy garantiza que la API no arranca hasta que PostgreSQL esté lista para aceptar conexiones:

services:
  api:
    build: .
    ports:
      - "8000:8000"
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
    volumes:
      - .:/app

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: myapp
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - db_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U myapp"]
      interval: 5s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    volumes:
      - redis_data:/data

volumes:
  db_data:
  redis_data:

El volumen montado en api (.:/app) es solo para desarrollo: refleja los cambios del código en tiempo real sin reconstruir la imagen. En producción, elimina ese volumen.

Comandos habituales del ciclo de desarrollo:

docker compose up -d
docker compose logs -f api
docker compose exec api python -m pytest
docker compose down -v

Variables de entorno y secretos

Hay tres formas de pasar configuración a un contenedor, cada una con su caso de uso:

Mecanismo Cuándo usarlo
env_file: .env en compose Desarrollo local; nunca commitear el fichero
Variables de entorno en el sistema CI/CD y producción sin gestor de secretos
Docker secrets o vault Producción con alta sensibilidad (tokens, claves privadas)

La API lee las variables con pydantic-settings, sin importar de dónde vengan:

from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8")

    database_url: str
    redis_url: str = "redis://redis:6379/0"
    secret_key: str
    debug: bool = False

En producción, las variables se inyectan directamente en el entorno del contenedor o desde un gestor de secretos (AWS Secrets Manager, HashiCorp Vault). El código no cambia: pydantic-settings las recoge del entorno del proceso.

Nunca uses ENV SECRET_KEY=valor_real en el Dockerfile: ese valor queda grabado en el historial de capas de la imagen y cualquiera con acceso al registro puede extraerlo con docker history.

Resumen

  • python:3.12-slim es la imagen base más pragmática para Python: Debian mínimo, glibc compatible con wheels precompilados, sin las complicaciones de compilación de alpine.
  • El build multistage instala dependencias en una etapa builder y copia solo los artefactos a la imagen final, reduciendo tamaño y superficie de ataque.
  • Copiar requirements.txt antes del código fuente maximiza la reutilización de la caché de capas: la capa de instalación solo se reconstruye cuando cambian las dependencias.
  • depends_on con condition: service_healthy garantiza que la API no arranca hasta que PostgreSQL esté respondiendo; sin healthcheck, la API arrancaría antes de que la base de datos esté lista.
  • Nunca embeber secretos en el Dockerfile ni en la imagen: se quedan en el historial de capas. Los secretos llegan siempre por variables de entorno, env_file o un gestor de secretos.
