Necesitas el clúster kind de la lección 2 y Docker. Todo lo demás se construye aquí. Al terminar habrás hecho, en pequeño, lo mismo que hace el pipeline de tu empresa en grande.

La app y su imagen #

Una app mínima pero con las dos rutas que k8s necesita: la de negocio y la de salud.

php · index.php — la app del taller 
<?php

$ruta = $_SERVER["REQUEST_URI"];

if ($ruta === "/salud") {
    http_response_code(200);
    echo "ok";
    exit;
}

$version = getenv("APP_VERSION") ?: "v1";
echo "Hola desde $version — pod: " . gethostname() . "\n";
bash · Dockerfile y build 
cat > Dockerfile <<'FIN'
FROM php:8.3-cli
COPY index.php /app/index.php
CMD ["php", "-S", "0.0.0.0:8080", "/app/index.php"]
FIN

docker build -t academia-app:v1 .

Cargar la imagen en kind #

Primer tropiezo clásico: el clúster no ve las imágenes de tu Docker local — en producción las saca de un registry (el paso «push» de tu CI). kind tiene el atajo para desarrollo:

bash · la imagen, dentro del clúster 
kind load docker-image academia-app:v1 --name academia

Si olvidas este paso verás ImagePullBackOff — y ahora sabes leerlo: el clúster busca la imagen en un registry que no la tiene. En el trabajo, ese error suele significar tag mal escrito o credenciales del registry.

El manifiesto completo #

Todo lo del curso, junto — réplicas, imagen, config, recursos y las dos probes:

yaml · app.yaml — el deployment de verdad 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: academia-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: academia-app
  template:
    metadata:
      labels:
        app: academia-app
    spec:
      containers:
        - name: app
          image: academia-app:v1
          imagePullPolicy: IfNotPresent   # usa la cargada con kind load
          ports:
            - containerPort: 8080
          env:
            - name: APP_VERSION
              value: "v1"
          resources:
            requests: { cpu: 100m, memory: 64Mi }
            limits: { memory: 128Mi }
          readinessProbe:
            httpGet: { path: /salud, port: 8080 }
            initialDelaySeconds: 2
          livenessProbe:
            httpGet: { path: /salud, port: 8080 }
            periodSeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: academia-app
spec:
  selector:
    app: academia-app
  ports:
    - port: 80
      targetPort: 8080
bash · desplegar y probar 
kubectl apply -f app.yaml
kubectl get pods                              # 3 Running
kubectl port-forward service/academia-app 8080:80 &
curl localhost:8080   # "Hola desde v1 — pod: academia-app-..."
curl localhost:8080   # repite: el hostname cambia — el Service balancea

Ese segundo curl es un momento del curso: ver el balanceo — cada petición aterriza en un pod distinto, y tú no configuraste ningún balanceador. Es el Service haciendo su trabajo.

El rolling update, en directo #

bash · desplegar la v2 sin dejar de servir 
docker build -t academia-app:v2 .            # (cambia APP_VERSION o el codigo)
kind load docker-image academia-app:v2 --name academia

# edita app.yaml: image: academia-app:v2 y APP_VERSION "v2"; entonces:
kubectl apply -f app.yaml
kubectl rollout status deployment/academia-app   # miralo pod a pod
# en otra terminal, un bucle de curls: veras v1 y v2 conviviendo unos
# segundos... y ni un solo error

El bucle de curls durante el rollout es la segunda revelación: cero peticiones fallidas mientras la flota entera cambia de versión. Eso que en el curso de infraestructura era un procedimiento (blue-green, drenar conexiones…) aquí es el comportamiento por defecto — porque la readiness probe le dice al Service cuándo cada pod nuevo merece tráfico.

Rompe la v3 y mira a las probes trabajar #

Ahora el experimento importante: una versión que arranca pero está rota — cambia /salud para que devuelva 500, constrúyela como v3, cárgala y aplícala. Lo que verás:

  • Los pods v3 arrancan… pero su readiness nunca pasa: quedan 0/1 Ready.
  • El rollout se detiene solo tras el primer pod nuevo (no sigue matando v2 sanos).
  • El tráfico sigue yendo solo a los v2: tus usuarios ni se enteraron de que desplegaste una versión rota.

Sin probes, esa v3 rota habría reemplazado a toda la flota y tirado el servicio. Con ellas, un deploy malo se convierte en un rollout atascado que nadie sufre — la diferencia entre incidente y anécdota.

rollout undo: el botón de deshacer #

bash · volver atrás en un comando 
kubectl rollout history deployment/academia-app   # las revisiones
kubectl rollout undo deployment/academia-app      # vuelve a la anterior
kubectl get pods                                  # v3 desapareciendo, v2 de vuelta

Un matiz de coherencia con la lección 2: undo es perfecto para apagar el fuego, pero deja el clúster distinto de tu git (que aún declara v3). El cierre correcto del incidente es revertir también el manifiesto en el repo — el estado deseado vuelve a tener una única fuente de verdad.

Lo que queda fuera (y cuándo te hará falta) #

Este curso te hizo usuario competente: entiendes el modelo, manejas kubectl, despliegas con seguridad y depuras lo común. El siguiente anillo existe y tiene nombres — Helm (plantillas para no repetir YAML entre entornos), operators (controllers a medida para software con estado), GitOps con ArgoCD (el apply lo hace un robot que vigila tu repo — el cierre natural de «los manifiestos viven en git»), y el service mesh. Ninguno cambia el modelo que ya tienes: todos son capas sobre el mismo bucle de reconciliación, y se aprenden en días cuando el trabajo los ponga delante.

Cuándo aplicarlo #

Ya estás listo para…

  • Trabajar con soltura en un equipo que despliega en k8s
  • Leer y modificar los manifiestos de tu empresa con criterio
  • Depurar los fallos comunes (ImagePullBackOff, CrashLoop, probes, OOM)
  • Reproducir en kind cualquier duda antes de tocar el clúster real

Sigue sin ser tu trabajo…

  • Administrar el clúster (nodos, red, upgrades): ese es el oficio de plataforma
  • Montar k8s para un proyecto que cabría en un compose: el criterio de infra sigue vigente

Resumen #

Lo que te llevas

  • El ciclo completo: build → kind load (o push a registry) → apply → rollout status. ImagePullBackOff = el clúster no encuentra tu imagen.
  • El Service balancea sin que configures nada: cada curl aterriza en un pod distinto.
  • Un rolling update con readiness probe sirve cero errores durante el cambio de flota — y detiene solo el despliegue de una versión rota.
  • rollout undo apaga el fuego; revertir el manifiesto en git cierra el incidente — una sola fuente de verdad.
  • Helm, operators y GitOps son capas sobre el mismo bucle: con este modelo, se aprenden cuando hagan falta.
