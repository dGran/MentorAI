ADR y RFC: dejar las decisiones por escrito

Alguien pregunta por qué los importes van en céntimos y nadie del equipo actual lo sabe. La decisión se tomó, pero se tomó en una reunión. Un ADR de una página habría contestado en un minuto; un RFC habría dejado claro qué se descartó y por qué.

El código dice qué hace el sistema. Los tests dicen qué tiene que seguir haciendo. Ninguno de los dos dice por qué se eligió así y qué se descartó por el camino. Esa tercera pieza es la que más rápido se pierde, y la más cara de reconstruir.

Por qué las decisiones se pierden #

En la tienda, los pedidos guardan los importes como enteros en céntimos. Lo decidió hace dos años alguien que ya no está, tras un descuadre de un céntimo que costó una semana encontrar (el porqué técnico, en números en coma flotante). Hoy alguien nuevo ve int $precio, lo encuentra raro y abre un PR para pasarlo a float, «que se lee mejor en las plantillas».

El problema no es la persona nueva: hace lo razonable con la información que tiene. El problema es dónde vivía el porqué:

  • En una reunión, que no deja rastro buscable.
  • En un hilo de chat, enterrado entre cientos de mensajes.
  • En un commit, que explica el cambio pero no las alternativas.
  • En la cabeza de alguien, que un día se va.

Sin el porqué, a cada decisión antigua le quedan dos destinos malos: se respeta a ciegas aunque ya no tenga sentido, o se revierte a ciegas y se repite el error que la motivó. Escribirla corta los dos.

El ADR: una decisión, una página #

Un ADR (Architecture Decision Record) es un documento corto que registra una decisión con su contexto y sus consecuencias. La forma más extendida la propuso Michael Nygard en 2011, en el artículo «Documenting Architecture Decisions», y cabe en cinco apartados:

ApartadoQué lleva
TítuloNúmero y frase corta: «3. Importes en céntimos enteros».
EstadoPropuesto, aceptado, obsoleto o sustituido por otro ADR.
ContextoLas fuerzas en juego, contadas sin tomar partido: qué pasaba, qué limitaba.
DecisiónLo que se hará, en voz activa y frases completas.
ConsecuenciasTodo lo que cambia después, también lo malo.

El apartado que más se descuida es el último. Un ADR que solo lista ventajas es un folleto: quien lo lea dentro de dos años necesita saber qué coste se aceptó a sabiendas.

markdown · docs/adr/0003-importes-en-centimos-enteros.md (proyecto ficticio «tienda») 
# 3. Importes en céntimos enteros

Fecha: 2024-03-02
Estado: Aceptado

## Contexto

La tienda calcula totales, descuentos e IVA por línea. Con float, la suma
de las líneas redondeadas no siempre cuadra con el total del pedido: en
febrero hubo un descuadre de un céntimo que tardamos una semana en
encontrar. La pasarela de pagos ya recibe los importes en céntimos.

## Decisión

Guardaremos y operaremos todo importe como un entero en céntimos (int en
PHP, BIGINT en la base de datos). Solo la capa de presentación lo formatea.

## Consecuencias

- Desaparecen las diferencias de redondeo entre las líneas y el total.
- Cada nombre lleva su unidad: precioUnitarioEnCentimos, totalEnCentimos.
- Plantillas y exportaciones dividen entre 100 al mostrar; hay que
  revisarlas todas en la migración.
- Si vendemos en una moneda sin céntimos, esta decisión se revisa.

MADR (Markdown Architectural Decision Records; en la versión 3 se llamó «Any Decision Records») es una plantilla más estructurada que añade lo que Nygard deja implícito: los criterios que pesaron en la decisión, las opciones consideradas con sus pros y contras, y cómo se confirmará que se cumple. Úsala cuando la decisión tuvo rivales serios; para decisiones de un párrafo, la de Nygard basta.

Dónde viven: en el repo y numerados #

Los ADR van en el repositorio, en una carpeta como docs/adr/, en Markdown. Se versionan con el código que justifican, se revisan en el mismo PR y se encuentran con grep; una wiki aparte envejece sola.

Se numeran en orden y el número no se reutiliza, como ya proponía Nygard. El número es un identificador estable para citarlo desde el código o un PR («eso lo cubre el 0003»).

El código que no explica su porqué #

Esta es la línea de pedido de la tienda antes del ADR. Funciona, pero nada en ella dice que el entero es deliberado ni en qué unidad está:

php · src/Pedidos/LineaPedido.php (antes) 
<?php

declare(strict_types=1);

namespace Tienda\Pedidos;

final class LineaPedido
{
    public function __construct(
        private readonly string $sku,
        private readonly int $unidades,
        private readonly int $precio,
    ) {
    }

    public function total(): int
    {
        return $this->unidades * $this->precio;
    }
}

Después, la unidad está en el nombre y la clase apunta a la decisión. La referencia no repite el razonamiento, que vive en un solo sitio: solo dice dónde buscarlo.

php · src/Pedidos/LineaPedido.php (después) 
<?php

declare(strict_types=1);

namespace Tienda\Pedidos;

/**
 * @see docs/adr/0003-importes-en-centimos-enteros.md
 */
final class LineaPedido
{
    public function __construct(
        private readonly string $sku,
        private readonly int $unidades,
        private readonly int $precioUnitarioEnCentimos,
    ) {
    }

    public function totalEnCentimos(): int
    {
        return $this->unidades * $this->precioUnitarioEnCentimos;
    }
}

Ahora el PR que pasa a float se responde con un enlace, no con una discusión de memoria. Y si el contexto ha cambiado de verdad, ese PR deja de ser un cambio de tipo y pasa a ser un ADR nuevo.

El RFC: pedir opinión antes de decidir #

El ADR registra una decisión tomada. Cuando la decisión todavía no está tomada y necesita la opinión de otros, lo que se escribe antes es un RFC (Request for Comments) o documento de diseño. El nombre viene de las RFC de Internet, la primera de 1969; en un equipo es más modesto: un documento que pide críticas antes de gastar el esfuerzo.

ADR

  • Registra una decisión ya tomada
  • Una página, lectura de un minuto
  • Se queda en el repo para siempre

RFC

  • Abre una decisión que aún no se ha tomado
  • Más largo: opciones, costes y dudas
  • Se cierra con una resolución, que suele acabar en un ADR

Lo que lo hace útil es que obliga a separar el problema de la solución favorita del autor. Si no puedes escribir dos opciones honestas con sus costes, aún no entiendes el problema.

markdown · docs/rfc/0004-reintentos-de-cobro.md (proyecto ficticio «tienda») 
# RFC 4: Reintentos de cobro cuando falla la pasarela

Estado: En discusión
Decide: responsable de pagos
Revisan: Lucía (pagos), Marcos (almacén), soporte
Comentarios hasta: 2026-10-24

## Problema

El 2 % de los cobros falla por un timeout de la pasarela. Hoy el pedido
queda en «pago pendiente» y el cliente reintenta a mano; algunos pagan dos
veces porque el primer cobro sí había entrado.

## Opciones

A. Reintentar en el momento, tres veces. Coste: poco código; el cliente
   espera más y el riesgo de doble cobro sigue si no hay idempotencia.
B. Cobro asíncrono con clave de idempotencia y cola de reintentos.
   Coste: una cola nueva y un estado más en el pedido; unas dos semanas.
C. No hacer nada y conciliar a mano cada lunes. Coste: horas de soporte
   y devoluciones; cero desarrollo.

## Propuesta

B, empezando por la clave de idempotencia, que ya corta el doble cobro.

## Preguntas abiertas

- ¿Admite la pasarela claves de idempotencia en todos los métodos de pago?
- ¿Cuánto puede esperar un pedido en «cobrando» antes de liberar el stock?

Fíjate en la opción C: «no hacer nada» casi siempre es una opción real, con su coste, y escribirla evita que la propuesta se compare solo contra alternativas peores. Cómo contar esos costes a quien decide es el tema de comunicar trade-offs.

Pedir y cerrar la discusión #

Un RFC sin cierre se convierte en un hilo eterno. Tres datos en la cabecera lo evitan:

  • A quién se pide opinión, con nombres. «Comentad lo que queráis» produce silencio o cuarenta comentarios de estilo.
  • Hasta cuándo. Una fecha concreta, de unos días a una semana según el alcance.
  • Quién decide. Consenso no significa unanimidad: se escucha a todos y decide una persona o un rol con nombre.

Una forma práctica es abrir el RFC como PR contra docs/rfc/: los comentarios quedan en las líneas que discuten, como en una code review. Al llegar la fecha, quien decide escribe la resolución en el documento, cambia su estado y la decisión se registra como ADR. Un RFC rechazado también se guarda: es la respuesta a «¿por qué no hicimos B?».

Cambiar de opinión sin borrar #

Un año después, la tienda empieza a vender en yenes, que no tienen céntimos: se cumple la consecuencia que el 0003 dejó anotada. Lo tentador es editar el 0003 y cambiar la decisión. No se hace: un ADR aceptado es un registro histórico, y reescribirlo borra justo lo que se quería conservar.

Se escribe el 0011, «Importes en la unidad mínima de cada moneda», con estado aceptado y una línea «Sustituye a 0003». En el 0003 solo se toca el estado: «Sustituido por 0011». Quien llegue al viejo sabe que ya no manda y adónde ir; quien lea el nuevo sabe de dónde viene.

Aplicar el 0011 ya es otro trabajo. Si toca código sin tests, empieza fijando lo que hace hoy con tests de caracterización; y si se aplaza, el código que aún sigue el 0003 es deuda técnica con nombre y número, que es la forma más fácil de negociarla.

1 RFC en discusiónOpciones, costes y fecha de cierre
2 ADR aceptadoLa decisión y sus consecuencias
3 Un ADR nuevo lo sustituyeEl viejo sigue ahí, con su nuevo estado

El ciclo de vida de una decisión: nada se borra, solo cambia de estado.

Errores típicos #

Lo que convierte los ADR en papel muerto

  • Escribirlos a posteriori, en bloque. Reconstruyen el qué, pero el contexto real ya se ha olvidado.
  • Un ADR por cada cosa. Si hay cien, nadie lee ninguno.
  • Consecuencias solo positivas. Sin el coste aceptado, el lector no distingue un efecto previsto de un fallo.
  • Editar un ADR aceptado para cambiar la decisión. Se pierde la historia. Se sustituye con uno nuevo.
  • Un RFC sin fecha ni responsable. La discusión no se cierra y la decisión la acaba tomando quien implementa primero.
  • Un RFC con una sola opción. Es un anuncio con formato de pregunta: los demás no tienen con qué comparar.

Cómo comprobarlo #

La prueba de fuego es humana: pregunta a alguien recién llegado por qué una decisión rara es así. Si llega al ADR desde el código en cinco minutos, funciona. Lo mecánico se vigila desde la terminal:

bash · revisar los ADR de la tienda 
grep -L '^Estado:' docs/adr/*.md

grep -rhoE 'docs/adr/[0-9]{4}-[a-z0-9-]+\.md' src | sort -u | while read -r adr; do
  [ -f "$adr" ] || echo "Referencia rota: $adr"
done

git log --diff-filter=D --name-only --oneline -- docs/adr

Las órdenes listan los ADR sin estado, las referencias del código a ADR inexistentes y los ADR borrados, que debería salir vacía. En la review, la pregunta es otra: si el cambio contradice un ADR, ¿trae el que lo sustituye?

Cuándo aplicarlo #

Escribe un ADR o un RFC cuando…

  • La decisión es cara de revertir: esquema de datos, formato de un contrato, una dependencia central
  • Alguien razonable, sin el contexto, la desharía
  • Se descartaron alternativas serias y el porqué no se ve en el código
  • Afecta a varios equipos o a más de un repositorio (aquí, RFC primero)

No hace falta cuando…

  • El cambio se revierte en una tarde sin efectos fuera del módulo
  • Es la convención por defecto del framework y nadie la discute
  • Es una regla de estilo que ya aplica una herramienta

La alternativa sencilla

Para decisiones pequeñas basta un commit que explique el porqué y un nombre que lleve la intención. Si se discute en cada PR, merece su ADR. Y el mismo hábito de escribir sin buscar culpables lo tienes en el post mortem.

Resumen #

Lo que te llevas

  • El código dice qué hace; el ADR, por qué se eligió así y qué coste se aceptó.
  • Un ADR es una página: título numerado, estado, contexto, decisión y consecuencias, también las malas. MADR añade criterios y opciones comparadas.
  • Viven en el repo, numerados sin reutilizar números, y el código los cita.
  • El RFC va antes de decidir: problema, opciones con sus costes (incluida «no hacer nada»), propuesta y preguntas abiertas.
  • Toda discusión necesita a quién se pregunta, hasta cuándo y quién decide. La resolución acaba en un ADR.
  • Un ADR aceptado no se edita para cambiar la decisión: se escribe otro que lo sustituye y el viejo solo cambia de estado.
