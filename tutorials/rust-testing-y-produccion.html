Testing y despliegue a producción en Rust

Tests unitarios e integración con cargo test, benchmarks, y cómo construir una imagen Docker mínima con un binario Rust estático.

El compilador de Rust atrapa muchos fallos que en PHP solo descubre un test, pero no sabe si tu lógica de negocio hace lo que debe. Y cuando todo pasa, desplegar ya no es subir ficheros a un servidor con PHP-FPM: es un binario y una imagen que puede pesar menos que el vendor/ de un proyecto Symfony.

Tests unitarios #

Rust integra el sistema de tests en el propio lenguaje, sin crates externas. Los tests unitarios viven en el mismo fichero que el código que testean, dentro de un módulo con #[cfg(test)]:

rust 
pub struct Carrito {
    items: Vec<(String, f64)>,
}

impl Carrito {
    pub fn new() -> Self {
        Self { items: Vec::new() }
    }

    pub fn añadir(&mut self, nombre: &str, precio: f64) {
        assert!(precio >= 0.0, "precio negativo");
        self.items.push((nombre.to_string(), precio));
    }

    pub fn total(&self) -> f64 {
        self.items.iter().map(|(_, precio)| precio).sum()
    }

    pub fn esta_vacio(&self) -> bool {
        self.items.is_empty()
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn carrito_vacio_tiene_total_cero() {
        let carrito = Carrito::new();
        assert_eq!(carrito.total(), 0.0);
    }

    #[test]
    fn añadir_item_actualiza_total() {
        let mut carrito = Carrito::new();
        carrito.añadir("Teclado", 89.99);
        carrito.añadir("Ratón", 29.99);
        assert!((carrito.total() - 119.98).abs() < 1e-9);
    }

    #[test]
    fn carrito_nuevo_esta_vacio() {
        let carrito = Carrito::new();
        assert!(carrito.esta_vacio());
    }

    #[test]
    #[should_panic(expected = "precio negativo")]
    fn precio_negativo_produce_panic() {
        let mut carrito = Carrito::new();
        carrito.añadir("Producto", -10.0);
    }
}

Los atributos de test más usados:

  • #[test]: marca una función como test.
  • #[should_panic]: el test pasa si la función entra en panic. Con expected = "..." verifica además el mensaje.
  • #[ignore]: excluye el test del run normal; se ejecuta con cargo test -- --ignored.
bash 
cargo test                         # ejecuta todos los tests
cargo test carrito                 # filtra por nombre
cargo test -- --nocapture          # muestra los println! de los tests
cargo test -- --test-threads=1     # secuencial (útil si comparten estado)

Para tests async con Tokio:

rust 
#[cfg(test)]
mod tests {
    use super::*;

    #[tokio::test]
    async fn obtener_usuario_existente() {
        let pool = crear_pool_test().await;
        let repo = SqlxUsuarioRepository::new(pool);

        let resultado = repo.buscar_por_id(1).await.unwrap();
        assert!(resultado.is_some());
    }
}

Tests de integración #

Los tests de integración viven en el directorio tests/ en la raíz del proyecto, separados del código fuente. Cada fichero en ese directorio es un crate independiente que importa tu librería:

bash 
mi-proyecto/
├── src/
│   ├── lib.rs
│   └── carrito.rs
└── tests/
    ├── carrito_integracion.rs
    └── api_integracion.rs
rust 
use mi_proyecto::Carrito;

#[test]
fn flujo_completo_de_compra() {
    let mut carrito = Carrito::new();
    assert!(carrito.esta_vacio());

    carrito.añadir("Teclado", 89.99);
    carrito.añadir("Ratón", 29.99);
    assert!(!carrito.esta_vacio());
    assert!((carrito.total() - 119.98).abs() < 1e-9);
}

Para tests de integración de una API HTTP con Axum, se levanta el router directamente con axum_test o tower::ServiceExt:

rust 
use axum::body::Body;
use axum::http::{Request, StatusCode};
use tower::ServiceExt;

#[tokio::test]
async fn health_check_devuelve_ok() {
    let app = crear_app(estado_test().await);

    let respuesta = app
        .oneshot(
            Request::builder()
                .uri("/health")
                .body(Body::empty())
                .unwrap(),
        )
        .await
        .unwrap();

    assert_eq!(respuesta.status(), StatusCode::OK);
}

Mocking y dobles de test #

Rust no tiene mocking automático por reflexión como PHPUnit. La estrategia es diseñar para la testeabilidad: inyectar dependencias vía traits y crear implementaciones fake para los tests.

rust 
use async_trait::async_trait;

#[async_trait]
pub trait EmailService: Send + Sync {
    async fn enviar(&self, destinatario: &str, asunto: &str) -> Result<(), String>;
}

pub struct ServicioRegistro<E: EmailService> {
    email_service: E,
}

impl<E: EmailService> ServicioRegistro<E> {
    pub fn new(email_service: E) -> Self {
        Self { email_service }
    }

    pub async fn registrar(&self, email: &str) -> Result<(), String> {
        self.email_service
            .enviar(email, "Bienvenido")
            .await
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    use std::sync::Mutex;

    struct EmailFake {
        enviados: Mutex<Vec<String>>,
    }

    impl EmailFake {
        fn new() -> Self {
            Self { enviados: Mutex::new(Vec::new()) }
        }

        fn emails_enviados(&self) -> Vec<String> {
            self.enviados.lock().unwrap().clone()
        }
    }

    #[async_trait]
    impl EmailService for EmailFake {
        async fn enviar(&self, destinatario: &str, _asunto: &str) -> Result<(), String> {
            self.enviados.lock().unwrap().push(destinatario.to_string());
            Ok(())
        }
    }

    #[tokio::test]
    async fn registrar_envía_email_de_bienvenida() {
        let fake = EmailFake::new();
        let servicio = ServicioRegistro::new(fake);

        servicio.registrar("usuario@ejemplo.com").await.unwrap();

        // No hay acceso al fake después de moverlo al servicio.
        // La alternativa es usar Arc si necesitas inspeccionar el fake.
    }
}

La crate mockall ofrece generación automática de mocks con macros si prefieres no escribir los fakes a mano.

Benchmarks con Criterion #

Criterion es la herramienta estándar para benchmarks estadísticos en Rust. Los benchmarks viven en el directorio benches/:

rust 
use criterion::{criterion_group, criterion_main, Criterion};
use std::hint::black_box;

fn benchmark_total_carrito(c: &mut Criterion) {
    let mut carrito = Carrito::new();
    for i in 0..1000 {
        carrito.añadir(&format!("Item {}", i), i as f64);
    }

    c.bench_function("total de 1000 items", |b| {
        b.iter(|| black_box(carrito.total()))
    });
}

criterion_group!(benches, benchmark_total_carrito);
criterion_main!(benches);

En Cargo.toml:

rust 
[dev-dependencies]
criterion = { version = "0.8", features = ["html_reports"] }

[[bench]]
name = "carrito"
harness = false
bash 
cargo bench                        # ejecuta todos los benchmarks
cargo bench -- "total de 1000"    # filtra por nombre

Criterion ejecuta cada benchmark múltiples veces, calcula la media y la desviación estándar, y detecta regresiones comparando con una ejecución anterior. Genera un informe HTML en target/criterion/.

black_box, de std::hint (el de Criterion está deprecado), previene que el compilador optimice el código bajo test y lo elimine, lo que daría mediciones falsas.

Compilación para producción #

El binario de debug (cargo build) incluye símbolos de depuración y no está optimizado. Para producción:

bash 
cargo build --release

El binario resultante está en target/release/. Con --release, el compilador aplica todas las optimizaciones de LLVM. La diferencia de rendimiento es sustancial.

Para reducir el tamaño del binario, en Cargo.toml:

rust 
[profile.release]
opt-level = 3        # máxima optimización (por defecto en release)
lto = true           # link-time optimization: más lento de compilar, binario más pequeño y rápido
codegen-units = 1    # una sola unidad: permite más optimizaciones cross-módulo
strip = true         # elimina símbolos de debug del binario final

Para compilar un binario estático (sin dependencias de libc del sistema), compilar para la target x86_64-unknown-linux-musl:

bash 
rustup target add x86_64-unknown-linux-musl
cargo build --release --target x86_64-unknown-linux-musl

El binario resultante no depende de ninguna librería del sistema operativo. Se puede copiar a cualquier máquina Linux x86-64 y ejecutar directamente.

Diferencia con Go: en Go los binarios son estáticos por defecto. En Rust el binario dinámico vincula a la glibc del sistema. El target musl produce el equivalente al binario estático de Go.

Docker multistage #

La imagen Docker de producción no necesita las herramientas de compilación. Con multistage build se compila en una imagen con Rust y se copia solo el binario a una imagen mínima:

bash 
FROM rust:1.99-slim AS builder

WORKDIR /app

COPY Cargo.toml Cargo.lock ./

RUN mkdir src && echo "fn main() {}" > src/main.rs
RUN cargo build --release --locked

COPY src ./src
RUN touch src/main.rs && cargo build --release --locked

FROM debian:trixie-slim AS runtime

RUN apt-get update && apt-get install -y \
    ca-certificates \
    && rm -rf /var/lib/apt/lists/*

COPY --from=builder /app/target/release/mi-servicio /usr/local/bin/mi-servicio

EXPOSE 8080
CMD ["mi-servicio"]

El truco de compilar primero con un main.rs vacío permite que Docker cachee la compilación de dependencias. Las dependencias solo se recompilan cuando cambia Cargo.lock, no cuando cambia el código fuente.

Si usas el target musl para un binario estático, la imagen final puede ser scratch (imagen vacía), que es la imagen Docker más pequeña posible:

bash 
FROM rust:1.99-slim AS builder

RUN rustup target add x86_64-unknown-linux-musl
RUN apt-get update && apt-get install -y musl-tools

WORKDIR /app
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo "fn main() {}" > src/main.rs
RUN cargo build --release --locked --target x86_64-unknown-linux-musl

COPY src ./src
RUN touch src/main.rs && cargo build --release --locked --target x86_64-unknown-linux-musl

FROM scratch

COPY --from=builder /app/target/x86_64-unknown-linux-musl/release/mi-servicio /mi-servicio

EXPOSE 8080
ENTRYPOINT ["/mi-servicio"]

La imagen final con scratch puede pesar menos de 10 MB para un servicio típico. La imagen equivalente en PHP con FPM raramente baja de 100 MB.

Errores típicos

  • Olvidar que los tests corren en paralelo. cargo test ejecuta cada test en su propio hilo a la vez. Si comparten una base de datos, un fichero o variables de entorno, fallan de forma intermitente. Aísla los datos por test o limita con -- --test-threads=1.
  • Medir rendimiento con el binario de debug. cargo run sin --release puede ir varias veces más lento: los tiempos que saques no dicen nada de producción. cargo bench ya compila optimizado.
  • Usar scratch y llamar a HTTPS. La imagen vacía no trae certificados raíz y las conexiones TLS fallan. Copia el bundle de ca-certificates desde el builder o usa rustls con los certificados embebidos.
  • Confiar en que #[tokio::test] reproduce producción. Por defecto usa un runtime de un solo thread; para probar concurrencia real usa #[tokio::test(flavor = "multi_thread")].

Cuándo aplicarlo #

Qué usar en cada caso…

  • Tests unitarios en el propio módulo para lógica pura: cálculos, validaciones, conversiones
  • Tests en tests/ para la API pública del crate y los endpoints HTTP de punta a punta
  • Fakes a mano detrás de un trait cuando la dependencia es pequeña; mockall cuando el trait tiene muchos métodos
  • Criterion solo en el código caliente que vas a optimizar, para medir antes y después

Qué evitar…

  • Testear lo que ya garantiza el sistema de tipos: que un campo exista o que una función no devuelva null
  • Mockear la base de datos en todo: para queries SQL, un test contra una BD real en Docker detecta mucho más
  • Benchmarks de todo el proyecto por si acaso: cuestan mantenerlos y nadie mira los informes
  • Elegir scratch y musl sin pensar: sin certificados ni zona horaria, y el allocator de musl rinde peor con muchas asignaciones

Para la imagen, debian:trixie-slim (la misma Debian que el builder rust:1.99-slim) con el binario de glibc es la opción por defecto: pequeña, con ca-certificates y sin sorpresas. Baja a scratch con musl cuando el tamaño o la superficie de ataque importen de verdad y hayas comprobado que el servicio no echa nada en falta.

Resumen #

Lo que te llevas

  • Los tests unitarios viven en el mismo fichero bajo #[cfg(test)]. Los tests de integración en el directorio tests/. No se necesita ninguna crate externa para el sistema básico de tests.
  • Los dobles de test se implementan manualmente creando structs que implementan el trait de la dependencia. La crate mockall automatiza esto si hay muchos mocks.
  • Criterion proporciona benchmarks estadísticos con detección de regresiones y reportes HTML. Los benchmarks viven en el directorio benches/.
  • cargo build --release habilita todas las optimizaciones de LLVM. Las opciones lto, codegen-units=1 y strip en el perfil release reducen el tamaño y mejoran el rendimiento.
  • El target musl genera binarios estáticos sin dependencias del sistema operativo, equivalentes a los binarios de Go. Permiten imágenes Docker basadas en scratch.
  • El multistage build de Docker con caché de dependencias separa la etapa de compilación de la imagen de runtime, produciendo imágenes mínimas y builds incrementales rápidos.
