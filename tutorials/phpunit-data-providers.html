Data providers: tests parametrizados

La misma lógica con diez entradas distintas no son diez tests copiados: es un test y una tabla de casos. El data provider es la herramienta de PHPUnit para esa tabla — y bien usado, convierte los casos límite en una lista que se lee de un vistazo.

Hay una señal inequívoca de que necesitas un data provider: tres métodos de test idénticos salvo por los números. La lógica de la prueba es una; lo que varía son los datos. Separarlos es el mismo principio de no repetirte aplicado a los tests.

El test copiado y pegado #

Supón un servicio que calcula el descuento por volumen de un pedido. Quieres probar varios tramos, y la primera tentación es esta:

php · el patrón que pide a gritos un provider 
#[Test]
public function sin_descuento_por_debajo_de_100(): void
{
    $this->assertSame(0, (new VolumeDiscount())->percentFor(9900));
}

#[Test]
public function cinco_por_ciento_desde_100(): void
{
    $this->assertSame(5, (new VolumeDiscount())->percentFor(10000));
}

#[Test]
public function diez_por_ciento_desde_500(): void
{
    $this->assertSame(10, (new VolumeDiscount())->percentFor(50000));
}

Funciona, pero tiene los problemas de todo copia-pega: si mañana cambia la forma de llamar al servicio tocas N sitios, añadir un caso cuesta un método entero, y la vista de pájaro ("¿qué tramos estamos cubriendo?") no existe — está repartida en metros de código idéntico.

El data provider #

Un data provider es un método estático que devuelve conjuntos de argumentos; PHPUnit ejecuta el test una vez por conjunto, como si fueran tests separados. Se conecta con el atributo #[DataProvider]:

php · un test, todos los tramos 
use PHPUnit\Framework\Attributes\DataProvider;
use PHPUnit\Framework\Attributes\Test;

final class VolumeDiscountTest extends TestCase
{
    #[Test]
    #[DataProvider('tramos')]
    public function aplica_el_descuento_por_tramo(int $subtotalCents, int $expectedPercent): void
    {
        $discount = new VolumeDiscount();

        $this->assertSame($expectedPercent, $discount->percentFor($subtotalCents));
    }

    public static function tramos(): iterable
    {
        yield [9900, 0];
        yield [10000, 5];
        yield [49900, 5];
        yield [50000, 10];
    }
}

Reglas de la mecánica: el provider es public static (PHPUnit lo llama antes de instanciar la clase), devuelve un iterable de arrays, y cada array son los argumentos del test en orden. En versiones antiguas verás la anotación @dataProvider en el docblock: es lo mismo con la sintaxis previa a los atributos.

Fíjate en qué ganó el test: añadir un tramo es una línea, la llamada al servicio vive en un solo sitio, y los cuatro casos se leen como lo que son — una tabla de decisión. Cada caso sigue contando como test individual: si falla uno, los demás se ejecutan igualmente.

Datasets con nombre #

El ejemplo anterior tiene un defecto que descubrirás el día que falle: PHPUnit reporta el caso como with data set #2, y toca contar yields para saber cuál es. La solución es nombrar cada dataset con una clave:

php · el fallo se explica solo 
public static function tramos(): iterable
{
    yield 'justo por debajo del primer tramo' => [9900, 0];
    yield 'frontera exacta del 5%' => [10000, 5];
    yield 'justo por debajo del 10%' => [49900, 5];
    yield 'frontera exacta del 10%' => [50000, 10];
}

Ahora un fallo dice aplica_el_descuento_por_tramo with data set "frontera exacta del 5%" — el diagnóstico viene incluido en el nombre. El coste es teclear una frase; el beneficio aparece justo cuando peor estás (algo se ha roto). Nómbralos siempre.

Los casos límite, en tabla #

El data provider cambia algo más profundo que la sintaxis: convierte "¿qué casos pruebo?" en una pregunta con sitio propio. Y la respuesta sistemática son los límites, porque los bugs viven en las fronteras, no en el centro del rango:

Tipo de casoEjemplos a cubrir
Fronteras exactasEl valor donde cambia el comportamiento, y el inmediatamente anterior (10000 y 9900).
El cero y lo vacío0, "", array vacío, colección sin elementos.
Negativos e inválidos¿Qué hace un subtotal negativo? Si debe lanzar, eso es otro test (lo vemos en la lección de excepciones).
Extremos del tipoValores enormes, strings larguísimos, PHP_INT_MAX si aplica.
El caso normalUno o dos representativos del centro del rango. No veinte.

El provider como documentación

Un provider con datasets bien nombrados es la especificación del comportamiento en formato tabla: cualquiera que lo lea sabe qué hace la función en cada frontera sin abrir la implementación. Es el tipo de test que no estorba: documenta comportamiento, no implementación.

Cuándo no usarlo #

Dos abusos convierten la herramienta en un problema. El primero: lógica en el provider. Si el provider calcula los valores esperados con condicionales o, peor, reproduce la fórmula que estás probando, ya no pruebas nada — comparas la implementación consigo misma. Los datos del provider se escriben literales, calculados a mano o con una fuente independiente.

El segundo: el provider cajón de sastre. Si los casos no comparten la misma aserción —unos devuelven valor, otros lanzan excepción, otros tocan un colaborador— es que son comportamientos distintos, y cada comportamiento merece su propio test con su propio nombre. La señal: parámetros que solo usan algunos datasets, o un test lleno de if según el caso. Un test parametrizado prueba una regla con N entradas, no N reglas con una tabla.

Resumen #

Lo que te llevas

  • Tests idénticos salvo los datos = un test + un data provider. Añadir un caso pasa a costar una línea.
  • Mecánica: método public static que devuelve iterable de arrays, conectado con #[DataProvider]; cada dataset cuenta como test independiente.
  • Nombra siempre los datasets (yield 'caso' => [...]): el fallo se explica solo, justo cuando más lo necesitas.
  • Los bugs viven en las fronteras: fronteras exactas, cero/vacío, negativos y extremos antes que veinte casos normales.
  • Sin lógica en el provider (datos literales) y sin cajones de sastre: una regla por test parametrizado.
