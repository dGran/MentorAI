Grafana: dashboards

Grafana es la capa de visualización que une los tres pilares: conecta Prometheus para las métricas, Loki para los logs y Tempo para las trazas — y los presenta en un mismo panel. El resultado es un observatorio desde el que ver el estado del sistema sin cambiar de herramienta.

Prometheus almacena; PromQL consulta; Grafana visualiza. Pero Grafana no es solo un envoltorio de Prometheus: puede conectarse a docenas de fuentes de datos distintas y, sobre todo, permite cruzar en un mismo dashboard métricas de Prometheus con logs de Loki — el cruce entre los dos pilares que acelera el diagnóstico de incidentes.

Fuentes de datos #

Una fuente de datos en Grafana es la configuración de conexión a un sistema externo. Se configura en Connections → Data Sources. Para el stack de observabilidad habitual:

FuenteLenguaje de consultaQué visualizas
PrometheusPromQLMétricas: latencia, tasa de error, uso de recursos.
LokiLogQLLogs: eventos, errores, flujo de peticiones.
TempoTraceQLTrazas distribuidas: tiempo por span y servicio.
Alertmanager—Estado de alertas activas.

Una vez configuradas, puedes mezclar fuentes en el mismo dashboard. La potencia real está en la correlación: en un panel de logs (Loki) puedes hacer clic en un error y saltar a las trazas (Tempo) del mismo request id — todo sin salir de Grafana.

Tipos de panel #

Cada panel es una visualización de una o varias consultas. Los más útiles:

PanelCuándo usarlo
Time seriesEvolución temporal de métricas: latencia, req/s, uso de CPU. El panel por defecto para series temporales.
StatUn número en grande: tasa de error actual, percentil 99 ahora mismo, uptime. Vista rápida de un KPI.
TableComparativa entre endpoints, instancias o servicios. Ordenable por columna.
Gauge / Bar gaugeValor dentro de un rango conocido: utilización de workers (0-100%), porcentaje de error.
LogsPanel nativo de Loki: muestra el flujo de logs en tiempo real con resaltado por nivel.
HeatmapDistribución de latencias a lo largo del tiempo. Ideal para histogramas de Prometheus.

La tentación es usar muchos tipos distintos. La realidad: Time series + Stat + Table cubren el 90% de los casos. Añade tipos exóticos solo cuando añaden información que el usuario necesita y no puede obtener de otra forma.

Variables de dashboard #

Las variables permiten que el mismo dashboard funcione para distintos valores — un filtro interactivo que el usuario selecciona con un desplegable y que se inyecta en todas las consultas del dashboard.

Se definen en Dashboard Settings → Variables. Tipos comunes:

  • Query: obtiene los valores posibles de Prometheus o Loki. Ejemplo: label_values(http_requests_total, endpoint) lista todos los endpoints que tienen datos.
  • Custom: valores fijos definidos a mano. Ejemplo: production,staging para seleccionar el entorno.
  • Interval: rango de tiempo para usar en rate(). Permite al usuario elegir entre 5m, 15m, 1h.
PromQL · consulta con variable de Grafana 
# $endpoint y $interval son variables del dashboard
# el usuario las selecciona desde los desplegables
rate(http_request_duration_seconds_count{endpoint="$endpoint"}[$interval])

Con variables bien diseñadas, un único dashboard de "salud de endpoints" sirve para investigar cualquier endpoint, en cualquier ventana de tiempo, sin duplicar dashboards.

Organización y estructura #

Un Grafana sin organización se convierte rápido en un cajón de sastre. La convención más práctica es crear dashboards orientados a audiencias, no a fuentes de datos:

Por fuente (confuso)

  • "Dashboard de Prometheus"
  • "Dashboard de Loki"
  • El usuario no sabe cuál mirar durante un incidente.

Por audiencia o propósito

  • "Salud del servicio API" (métricas RED + logs de error)
  • "Infraestructura" (CPU, memoria, disco, BD)
  • "Debugging de incidente" (logs + trazas + métricas correlacionados)

Usa filas dentro de un dashboard para separar secciones colapsables. La primera fila suele ser el resumen ejecutivo (stats grandes de salud), las siguientes el detalle. Quien mira durante un incidente va de arriba hacia abajo: primero confirma que hay un problema, luego busca el detalle.

Buenas prácticas #

PrácticaPor qué
Unidades explícitas en cada eje (segundos, req/s, bytes)Sin unidades, el número no significa nada.
Thresholds visuales en stat panels (verde/amarillo/rojo)El cerebro procesa color más rápido que un número.
Dashboards en código (JSON/Terraform/Grafonnet)Version control, revisión en PR, reproducible en otro entorno.
Enlazar desde una alerta al dashboard relevanteCuando llega la alerta, el oncall sabe exactamente dónde mirar.
No más de 20-25 paneles por dashboardDashboards con 50 paneles no los mira nadie; ralentizan el navegador.
Usar variables en lugar de duplicar dashboardsUn dashboard por entorno es 3× el trabajo de mantenimiento.

Grafana Community Dashboards

Antes de construir un dashboard desde cero, busca en grafana.com/grafana/dashboards. Existen dashboards mantenidos por la comunidad para node_exporter, MySQL, PHP-FPM, nginx y decenas de servicios más. Impórtalos, adáptalos a tu stack y usa ese tiempo en los dashboards que son propios de tu negocio.

Cuándo aplicarlo #

Úsalo cuando…

  • Necesitas visualizar métricas de negocio específicas de tu aplicación que ningún dashboard genérico cubre.
  • On-call necesita un panel que concentre el estado del sistema en 5-8 paneles clave, sin ruido.
  • Quieres variables de dashboard para filtrar por entorno, servicio o región con un selector.

No lo uses cuando…

  • Existe un dashboard de la comunidad para esa tecnología (PostgreSQL, Redis, nginx): importa y adapta, no reinventes.
  • El dashboard acumula más de 8-10 paneles que nadie mira en producción: recorta y prioriza los que importan en un incidente.
  • La visualización es puntual y no repetitiva: una query ad hoc en la vista Explore de Grafana es suficiente.

Resumen #

Lo que te llevas

  • Grafana conecta Prometheus (PromQL) y Loki (LogQL) en un mismo dashboard. La correlación entre fuentes acelera el diagnóstico de incidentes.
  • Time series, Stat y Table cubren el 90% de los casos. Añade Heatmap para distribuciones de latencia y Logs para el flujo en tiempo real.
  • Variables de dashboard: un único dashboard parametrizado es mejor que N dashboards por entorno o servicio. Las de tipo Query se auto-populan desde Prometheus.
  • Organiza por audiencia o propósito, no por fuente de datos. Resumen arriba, detalle abajo. Thresholds de color para lectura rápida durante incidentes.
  • Dashboards en código (JSON versionado) y enlazados desde las alertas. Los de Grafana Community son un buen punto de partida para infraestructura estándar.
