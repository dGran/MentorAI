Code review: darla y recibirla

Un PR con cuarenta comentarios sobre comas y ninguno sobre el reembolso que se cobra dos veces. Otro que lleva cuatro días esperando un «LGTM». Los dos tienen revisión; ninguno, una review que sirva.

La review es la única fase en la que alguien que no escribió el código lo lee entero antes de que llegue a producción. Bien hecha, caza el fallo caro y reparte el conocimiento del sistema. Mal hecha, es un peaje lento que todo el mundo aprende a esquivar.

Para qué sirve (y para qué no) #

Una review persigue tres cosas: que el cambio sea correcto, que el diseño no deje al sistema peor de lo que estaba y que al menos otra persona entienda lo que entra. Esa tercera se olvida y es la que más rinde: el día que el autor esté de vacaciones, alguien más sabrá cómo funciona.

Igual de importante es lo que no es:

Lo que no es

  • QA: el revisor no ejecuta cada caso a mano; eso lo hacen los tests y la fase de QA.
  • Un examen: no se trata de pillar al autor ni de demostrar cuánto sabe el revisor.
  • Un linter humano: sangrías y comas las corrige una herramienta.

Lo que sí es

  • Una segunda lectura con contexto de negocio.
  • El sitio donde salen los casos límite que el autor no vio.
  • Una forma de repartir quién conoce cada parte del código.

La review de código generado por agentes tiene reglas propias en Implementar y revisar sin autocertificar y en Criterio y riesgos. Aquí hablamos de personas revisando a personas.

Qué mirar primero #

La atención se agota antes que el diff, así que lo que más cuesta arreglar después va primero.

OrdenQué mirasPregunta guía
1. CorrecciónCasos límite, errores, concurrencia, permisos¿Qué pasa con un pedido ya cancelado, con dos clics seguidos, con otro usuario?
2. DiseñoResponsabilidades, acoplamiento, dónde vive cada regla¿Este cambio encaja en el sistema o abre un camino paralelo?
3. TestsQue prueben comportamiento y cubran lo que se cambióSi rompo la regla nueva, ¿algún test se pone rojo?
4. LegibilidadNombres, tamaño de métodos, intención¿Lo entenderá quien lo lea dentro de un año?
5. EstiloFormato, orden de imports, comillas¿Por qué no lo detecta ya el linter?

El estilo es la última fila a propósito. Si un comentario de formato se repite, la respuesta no es repetirlo en cada PR sino añadir la regla al linter o al formateador del proyecto. Para los tests, el criterio es el de Tests que no estorban; para la legibilidad, el vocabulario de code smells ahorra párrafos: «huele a feature envy» se entiende a la primera.

Comentarios accionables #

Un comentario útil tiene tres partes: qué ves, por qué importa y cuánto importa. Sin el porqué, el autor obedece sin entender o discute sin datos. Sin la gravedad, no sabe si puede mergear. Tres etiquetas bastan para la gravedad:

EtiquetaSignificaQué hace el autor
[bloquea]Fallo de corrección, seguridad o un diseño que costará caro deshacerLo resuelve antes del merge o argumenta por qué no aplica
[sugerencia]Mejora razonable, pero el cambio ya es aceptable sin ellaDecide; si no la aplica, basta con decirlo
[pregunta]El revisor no entiende algo y no presupone que esté malContesta; si la respuesta no es obvia, quizá falta un nombre mejor o un test

Hay convenciones públicas más ricas, como Conventional Comments, con etiquetas como suggestion, issue, question o nitpick y la decoración (blocking) o (non-blocking). Da igual cuál uses mientras el equipo comparta una.

Un caso de la tienda. Este PR añade la cancelación de pedidos:

php · src/Order/CancelOrder.php (en review) 
<?php

declare(strict_types=1);

namespace Tienda\Order;

final class CancelOrder
{
    public function __construct(
        private readonly OrderRepository $orders,
        private readonly PaymentGateway $payments,
    ) {
    }

    public function __invoke(int $orderId): void
    {
        $order = $this->orders->find($orderId);
        $this->payments->refund($order->paymentId(), $order->total());
        $order->cancel();
        $this->orders->save($order);
    }
}

Comentario que no ayuda

  • «Esto está mal.»
  • «¿Por qué no usas un evento?»
  • «Yo lo haría de otra forma.»

Comentario accionable

  • «[bloquea] Si el pedido ya está cancelado o enviado, se reembolsa igual: un doble clic en «Cancelar» devuelve el dinero dos veces. ¿Comprobamos el estado antes de llamar a la pasarela? Un test con un pedido ya cancelado lo cubriría.»
  • «[pregunta] ¿La pasarela admite una clave de idempotencia? Si sí, pasar el id del pedido nos protege también de reintentos de red.»

El autor resuelve el caso secuencial con una guarda y un test; dos peticiones simultáneas pasarían ambas la guarda, y eso lo cierra la clave de idempotencia de la pregunta (o un bloqueo optimista), que confirma en el hilo:

php · src/Order/CancelOrder.php (tras la review) 
<?php

declare(strict_types=1);

namespace Tienda\Order;

final class CancelOrder
{
    public function __construct(
        private readonly OrderRepository $orders,
        private readonly PaymentGateway $payments,
    ) {
    }

    public function __invoke(int $orderId): void
    {
        $order = $this->orders->find($orderId);

        if (!$order->isCancellable()) {
            throw new OrderNotCancellable($orderId);
        }

        $this->payments->refund($order->paymentId(), $order->total());
        $order->cancel();
        $this->orders->save($order);
    }
}

Fíjate en lo que no hizo el revisor: no reescribió la clase en el comentario ni impuso su diseño. Señaló el riesgo, propuso una salida y dejó al autor elegir cómo cerrarlo. Y decir lo que está bien resuelto también es un comentario útil.

Tamaño y tiempo de respuesta #

En cincuenta líneas el revisor encuentra el doble reembolso; en dos mil, aprueba por agotamiento. La guía pública de review de Google lo dice en cifras orientativas: unas cien líneas suelen ser un tamaño razonable y mil, casi siempre demasiadas. Cómo partir el trabajo en PRs pequeños lo verás en Partir y estimar.

El otro eje es el tiempo. Un PR esperando bloquea al autor, que cambia de tarea y pierde el contexto. Un acuerdo sencillo funciona: primera respuesta en el mismo día laborable, aunque sea para decir «lo miro mañana a primera hora».

Recibir una review sin defenderse #

El comentario es sobre el código, no sobre ti, aunque a las seis de la tarde no lo parezca. Tres hábitos:

  • Lee antes de contestar. La pregunta útil es «¿tiene razón en algo?», no «¿cómo le demuestro que se equivoca?».
  • Una pregunta del revisor es un aviso del futuro. Si quien revisa no entendió algo, el siguiente lector tampoco. Mejor un nombre más claro o un test que una respuesta en el hilo.
  • Cierra cada hilo. «Hecho en el commit tal», «No lo aplico porque…» o «Lo apunto en el issue #N».

Es la misma lógica que el postmortem sin culpables: se discute qué falló, no quién, porque señalar personas solo consigue que el problema se esconda.

Desacuerdos: se escalan o se apuntan #

Dos personas razonables pueden no ponerse de acuerdo. Lo que no funciona es resolverlo por desgaste, con réplicas cada vez más largas:

1 Dos rondas en el hilo sin acercarseSe deja de escribir
2 ¿Bloquea el merge?Si no, decide el autor y se apunta en un issue si merece volver
3 Conversación de diez minutosEn voz, con el código delante
4 Se escalaA quien responde de ese módulo; si es una decisión de diseño, va a un ADR

El resultado se anota en el PR: la próxima persona que pregunte encontrará el porqué.

Si el desacuerdo es de fondo, como «¿colas o llamadas síncronas?», el PR ya no es el sitio. Esa decisión merece quedar por escrito con sus alternativas, que es justo lo que cubre ADR y RFC, y explicarla con sus costes, que es lo que verás en Comunicar trade-offs.

Antes de pedir review #

Antes de pedir review, relee tu diff como si fuera ajeno y repasa esta lista:

bash · antes de pedir review 
git fetch origin
git diff --stat origin/main...HEAD
git diff origin/main...HEAD
vendor/bin/phpunit
vendor/bin/phpstan analyse
  • El diff solo trae lo que dice el título, sin refactors de paso.
  • El tamaño es razonable o la descripción explica por qué no se pudo partir.
  • La descripción dice qué, por qué y cómo se comprobó, con enlace al issue.
  • Los checks están en verde, y lo que no se pudo ejecutar se dice.
  • Señalas dónde mirar: «la parte delicada es la guarda de CancelOrder».
  • Los commits cuentan una historia legible; si no, ordénalos antes (merge y rebase, deshacer en Git).

Errores típicos #

Lo que convierte la review en un peaje

  • Revisar el estilo y saltarse la lógica. Veinte comentarios de formato y el doble reembolso dentro.
  • Todo bloquea. Si cada preferencia personal impide el merge, el autor deja de distinguir lo grave de lo opinable.
  • Aprobar sin leer. Un «LGTM» en dos minutos sobre ochocientas líneas no es una review, es una firma.
  • Rediseñar en el PR. Pedir otra arquitectura con el código escrito tira el trabajo; eso se habla antes.
  • Ampliar el alcance. «Ya que estás, arregla también…» agranda el PR. Lo de fuera va a un issue.

Cómo comprobarlo #

Con la CLI de GitHub ves el tamaño de los últimos PRs y cuándo llegó su primera review:

bash · tamaño y primera review de los últimos PRs 
gh pr list --state merged --limit 20 \
  --json number,additions,deletions,createdAt,reviews \
  --jq '.[] | {number, lineas: (.additions + .deletions), abierto: .createdAt, primera_review: (.reviews[0].submittedAt // "sin review")}'

Tres señales a vigilar, sin convertirlas en objetivos que se maquillan:

  • Horas hasta la primera respuesta. Si pasa a menudo de un día, falla el reparto.
  • Rondas por PR. Muchas suelen indicar PRs grandes o desacuerdos sin escalar.
  • Proporción de comentarios por gravedad. Si casi todo es estilo, falta una regla en el linter; si casi todo bloquea, falta acordar qué bloquea.

Cuándo aplicarlo #

Review completa cuando…

  • El cambio toca dinero, permisos, datos personales o migraciones.
  • Alguien más tendrá que mantener ese código.
  • El autor es nuevo en esa parte del sistema.

Basta algo más ligero cuando…

  • Es una errata en un texto o un cambio de dependencia ya probado por CI.
  • Es un hotfix con producción caída: se mergea con una lectura rápida y se revisa a fondo después.

La alternativa cuando una review asíncrona no encaja es el pair programming: la revisión ocurre mientras se escribe. Cuesta dos personas a la vez, pero ahorra el ida y vuelta en cambios delicados. Si no conoces algún término de esta lección, lo tienes en el glosario de jerga.

Resumen #

Lo que te llevas

  • La review busca corrección, buen diseño y conocimiento compartido; no es QA ni un examen.
  • Primero corrección y diseño; el estilo repetido se lleva al linter.
  • Cada comentario dice qué, por qué y su gravedad: bloquea, sugerencia o pregunta.
  • PRs pequeños y primera respuesta en el día valen más que una review perfecta tres días tarde.
  • Tras dos rondas sin acuerdo se habla en voz; lo que no bloquea se apunta y lo de fondo va a un ADR.
