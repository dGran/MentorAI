Muestreo: por qué la misma pregunta da dos respuestas

El modelo no elige la siguiente palabra: reparte probabilidades entre todas, y luego alguien tira un dado trucado. Entender ese dado explica por qué dos ejecuciones del mismo prompt difieren, qué cambia de verdad al tocar la temperatura y por qué un sistema serio no se apoya en que la respuesta salga igual.

En Cómo piensa un LLM apareció de pasada «esa pizca de azar». Esta lección la desmonta: de dónde sale, qué parámetros la controlan, y por qué la variación no es un fallo que se arregla, sino una propiedad con la que hay que diseñar.

Del cálculo a las probabilidades #

Tras pasar por todas sus capas, el modelo produce una puntuación para cada token del vocabulario: decenas o cientos de miles de números (uno por token del vocabulario), llamados logits. Una puntuación alta significa «este token encaja bien aquí»; una baja, «encaja mal». Todavía no son probabilidades: pueden ser negativas y no suman nada en concreto.

Una función llamada softmax las convierte en una distribución de probabilidad: todas positivas, sumando 1, y conservando el orden. Con eso el modelo ya no dice «la siguiente palabra es return», sino «return con un 65 %, throw con un 24 %, echo con un 11 %…».

1 LogitsUna puntuación por token del vocabulario: return 2,0 · throw 1,0 · echo 0,2 …
2 SoftmaxLas convierte en probabilidades que suman 1, respetando el orden
3 MuestreoSe elige un token al azar según esas probabilidades
4 Siguiente vueltaEl token elegido se añade al texto y se repite todo para el siguiente

La respuesta entera es una cadena de estas elecciones: una diferencia en un token temprano cambia todo lo que viene detrás.

Temperatura y top-p #

La temperatura se aplica antes del softmax: divide todos los logits por un número. Con temperatura baja, las diferencias se agrandan y el favorito se lleva casi toda la probabilidad; con temperatura alta, se aplanan y los tokens menos probables tienen más opciones.

Temperatura Efecto en la distribución Comportamiento
Cercana a 0El favorito se queda prácticamente con todoRespuestas conservadoras y repetitivas
1La distribución que aprendió el modelo, sin tocarEquilibrio entre lo probable y lo variado
Mayor que 1Se aplana: opciones raras ganan pesoMás creatividad, y más disparates

El otro parámetro habitual es top-p (o nucleus sampling): antes de tirar el dado, se descartan los tokens menos probables y solo se sortea entre los que, sumados, alcanzan una probabilidad p (por ejemplo, el 90 %). Recorta la cola de opciones absurdas sin hacer rígida la respuesta. Algunos proveedores ofrecen también top-k, que se queda con los k tokens más probables.

JavaScript · temperatura aplicada a tres logits 
const logits = { return: 2.0, throw: 1.0, echo: 0.2 };

function probabilities(temperature) {
  const weights = Object.entries(logits).map(([token, logit]) => [token, Math.exp(logit / temperature)]);
  const total = weights.reduce((sum, [, weight]) => sum + weight, 0);

  return Object.fromEntries(weights.map(([token, weight]) => [token, (weight / total).toFixed(2)]));
}

console.log(probabilities(0.2)); // { return: '0.99', throw: '0.01', echo: '0.00' }
console.log(probabilities(1));   // { return: '0.65', throw: '0.24', echo: '0.11' }
console.log(probabilities(2));   // { return: '0.50', throw: '0.30', echo: '0.20' }

Ejecútalo tú

El reto práctico del curso amplía este código para sortear diez mil veces con cada temperatura y contar cuántas sale cada token. Ver los números cambiar asienta la intuición mejor que cualquier explicación.

Por qué ni a temperatura cero #

Con temperatura cero (no se puede dividir entre cero: los proveedores la interpretan como «elige siempre el favorito») el modelo debería dar siempre la misma respuesta. Sin embargo, no hay garantía, por varias razones:

  • El lote cambia los decimales. El proveedor procesa tu petición agrupada con otras, y muchas operaciones de GPU dan resultados ligeramente distintos según el tamaño del lote. Como la suma en coma flotante no es exactamente asociativa, otro orden de cálculo cambia los últimos decimales, y cuando dos tokens están casi empatados, ese decimal decide.
  • Un decimal se amplifica. Basta con que cambie una sola elección al principio para que el resto de la respuesta tome otro camino.
  • El modelo detrás puede cambiar. Un alias como «el último modelo» puede apuntar a otra versión mañana.

La reproducibilidad no se compra con un parámetro

Bajar la temperatura reduce la variación, pero no la elimina. Si un proceso necesita el mismo resultado dos veces, ese resultado no debe depender de que el modelo lo repita: debe guardarse, o calcularse con código.

Lo que el proveedor ya no deja tocar #

En los primeros años de las APIs de LLM, la temperatura era el mando que todo el mundo ajustaba. Con los modelos actuales, sobre todo los que razonan antes de responder, varios proveedores han restringido o fijado estos parámetros: en algunos modelos o modos ya no se puede cambiar la temperatura, y la API rechaza con un error cualquier valor distinto del de por defecto. El proveedor no siempre explica el motivo; lo que importa en la práctica es que ese mando ya no está.

Dos consecuencias prácticas. La primera: un código antiguo que envía temperature puede dar error con un modelo nuevo; revisa la documentación al migrar. La segunda: si tu diseño dependía de «temperatura 0 para que sea estable», con estos modelos esa palanca ya no existe y necesitas otra estrategia.

Dato que caduca

Qué parámetros acepta cada modelo cambia entre versiones. Esta lección explica la mecánica, que es estable; para saber qué admite el modelo que usas hoy, la fuente es la documentación del proveedor.

Diseñar alrededor de la variación #

Si la salida varía, el sistema tiene que funcionar igual con cualquiera de las salidas razonables. Las técnicas que funcionan son las mismas que verás en un buen método de trabajo con agentes:

  • Gates deterministas. Lo que decide si algo está bien es un test, un validador o un comando con código de salida, no la opinión del modelo. El modelo propone; el gate dispone.
  • Salida estructurada y validada. Pide JSON con un esquema y valídalo; si no cumple, reintenta. Muchos proveedores ofrecen además salida estructurada nativa, que restringe el muestreo a los tokens que respetan el esquema: el formato queda garantizado salvo que la respuesta se corte por el límite de tokens, y el contenido sigue necesitando validación.
  • Guardar lo que debe repetirse. Un resultado que se necesita igual mañana se escribe en un fichero o una base de datos en lugar de pedirlo otra vez.
  • Evaluar con varias ejecuciones. Para saber si un prompt funciona, ejecútalo muchas veces sobre un conjunto de casos y mide el porcentaje de aciertos. Una prueba que salió bien una vez dice muy poco.
  • Aprovechar la variación cuando ayuda. Generar varias propuestas y elegir la mejor, o pedir el mismo análisis dos veces y comparar, convierte la variación en una herramienta.

Cuándo aplicarlo #

Diseña contra la variación cuando…

  • La salida del modelo alimenta código que espera un formato
  • Un proceso automático decide algo a partir de la respuesta
  • Necesitas comparar resultados entre ejecuciones o entre modelos
  • Migras a un modelo nuevo con parámetros de muestreo distintos

La variación no estorba si…

  • Es una conversación de exploración o una lluvia de ideas
  • Una persona lee y juzga cada respuesta
  • Hay un gate posterior que valida el resultado igualmente

Resumen #

Lo que te llevas

  • El modelo puntúa cada token (logits), softmax los convierte en probabilidades y se sortea el siguiente token; la respuesta es una cadena de sorteos.
  • La temperatura afila o aplana la distribución; top-p y top-k recortan las opciones improbables antes de sortear.
  • Ni a temperatura cero hay garantía de repetir la salida: el tamaño del lote en el servidor cambia decimales que deciden empates.
  • Algunos modelos actuales fijan o restringen estos parámetros: la documentación del proveedor manda sobre la costumbre.
  • Los sistemas fiables no dependen de que el modelo repita: usan gates deterministas, salida validada, resultados guardados y evaluaciones con muchas ejecuciones.
