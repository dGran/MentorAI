Presupuesto de latencia: repartir los milisegundos

«Rápido» no es un objetivo, es una opinión. Un presupuesto de latencia hace dos cosas que ninguna otra herramienta: te dice cuándo has terminado de optimizar y qué no te puedes permitir añadir.

«Rápido» no es un objetivo, es una opinión. Un presupuesto de latencia convierte esa opinión en un número repartido entre las piezas del sistema, y hace dos cosas que ninguna otra herramienta hace: te dice cuándo has terminado de optimizar, y te dice qué no te puedes permitir añadir.

El número no lo eliges tú #

El presupuesto sale del comportamiento de las personas, no de lo que te parezca razonable como programador. Los umbrales de percepción llevan estudiados desde los años sesenta y apenas han cambiado:

TiempoCómo se percibeQué implica
~100 msInstantáneoEl objetivo de una interacción directa: un filtro, un autocompletado
~1 sSe nota, pero no rompe el hilo de pensamientoObjetivo razonable para navegar entre páginas
~10 sSe pierde la atenciónHace falta feedback: barra de progreso o hacerlo asíncrono

El objetivo se fija sobre un percentil, siempre

«La búsqueda responde en 300 ms» es una frase incompleta y por eso inservible. La versión útil es «el p95 de la búsqueda está por debajo de 300 ms». Sin percentil no se puede verificar, no se puede alertar y todo el mundo entiende una cosa distinta.

Repartir el presupuesto #

Una vez tienes el número de arriba, se reparte hacia abajo entre todo lo que ocurre en esa petición. El ejercicio es revelador porque casi siempre descubres que ya lo tienes gastado:

1 Presupuesto total: 800 ms (p95)Lo que promete el endpoint
2 Red y TLS: 150 ms · nginx y cola: 50 msNo lo controla tu código, pero se gasta igual
3 Base de datos: 200 ms · servicio de precios: 250 msLo que esperas fuera
4 Tu lógica: 150 msY ahí tiene que caber todo lo demás

Con este reparto, añadir una llamada síncrona de 300 ms no es «una mejora pequeña»: es romper el compromiso.

Esa última frase es el valor real del ejercicio. Sin presupuesto, cada llamada nueva parece barata en aislamiento y el endpoint se degrada por acumulación durante meses sin que nadie pueda señalar el commit culpable.

El presupuesto fija los timeouts #

Aquí es donde el presupuesto deja de ser un ejercicio de documentación y se convierte en configuración. Si tu endpoint promete 800 ms, un timeout de 5 s contra el servicio de precios es una mentira: cuando ese timeout se agote, hace rato que incumpliste.

php · PresupuestoDePeticion.php 
<?php

declare(strict_types=1);

final class PresupuestoDePeticion
{
    private readonly float $limite;

    public function __construct(float $milisegundos)
    {
        $this->limite = hrtime(true) + $milisegundos * 1e6;
    }

    public function restanteEnSegundos(): float
    {
        return max(0.0, ($this->limite - hrtime(true)) / 1e9);
    }

    public function agotado(): bool
    {
        return $this->restanteEnSegundos() <= 0.0;
    }
}

Con ese objeto viajando por el caso de uso, cada llamada saliente usa como timeout lo que queda, no una constante suya. Si la base de datos tardó más de lo previsto, el servicio de precios recibe menos margen y falla antes en vez de reventar el presupuesto entre los dos.

Los reintentos gastan del mismo presupuesto

Tres intentos con timeout de 300 ms y esperas entre medias no son 300 ms: son más de un segundo. Si el presupuesto no contempla los reintentos, la política de resiliencia y la promesa de latencia se contradicen, y la que gana es la que está en el código.

Lo que no depende, en paralelo #

Cuando el presupuesto no cuadra, la primera pregunta no es «¿cómo hago esto más rápido?» sino «¿por qué está en serie?». Tres llamadas independientes de 200 ms cuestan 600 ms encadenadas y 200 ms lanzadas a la vez.

En PHP esto es menos automático que en otros lenguajes, pero está disponible: curl_multi por debajo, o el cliente HTTP de Symfony, que devuelve respuestas perezosas y solo bloquea cuando lees el contenido. El patrón es lanzar todas y recorrer después:

php · en paralelo, no en serie 
<?php

$respuestas = [];

foreach ($identificadores as $id) {
    $respuestas[$id] = $this->http->request('GET', "/precios/{$id}");
}

$precios = [];

foreach ($this->http->stream($respuestas) as $respuesta => $trozo) {
    if ($trozo->isLast()) {
        $precios[] = $respuesta->toArray();
    }
}

El primer bucle no espera a nada: solo encola. El segundo consume conforme van llegando. El coste total pasa de ser la suma a ser el máximo, que en un presupuesto apretado suele ser la diferencia entre cumplir y no cumplir.

Cuándo aplicarlo #

Fija un presupuesto cuando…

  • El endpoint está en el camino crítico de algo que importa
  • Vas a añadir una dependencia nueva y quieres saber si cabe
  • El rendimiento se degrada poco a poco y nadie sabe por qué
  • Negocias un SLA o tienes que decidir cuándo parar de optimizar

No hace falta cuando…

  • Es un proceso por lotes sin nadie esperando
  • Es una pantalla interna que usan cuatro personas al día
  • Vas tan sobrado que el margen no es una restricción real

Resumen #

Lo que te llevas

  • Un objetivo de latencia sin percentil no se puede verificar ni alertar, y cada uno entiende una cosa distinta.
  • Repartir el presupuesto te dice qué no te puedes permitir añadir. Sin él, cada llamada nueva parece barata en aislamiento.
  • Un timeout mayor que el presupuesto es una mentira: cuando salta, hace rato que incumpliste.
  • Pasar el tiempo restante a cada llamada saliente hace que el sistema degrade en orden en vez de reventar el presupuesto entre todos.
  • Ante un presupuesto que no cuadra, la primera pregunta es por qué está en serie: en paralelo el coste pasa de la suma al máximo.
