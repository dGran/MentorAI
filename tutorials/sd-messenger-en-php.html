Symfony Messenger de punta a punta

Hasta aquí las colas han sido diagramas: quién reparte, qué se garantiza, dónde acaban los mensajes que fallan. Esta lección las monta en PHP con Symfony Messenger, desde el primer mensaje hasta el worker que sobrevive a un despliegue. Todo lo que verás se ha ejecutado en una app Symfony 8.1 mínima, con PHP 8.5 y el transport Doctrine sobre SQLite.

Antes de esta lección

Parte de Colas y topics (qué es un broker y cuándo compensa) y de las garantías de entrega: Messenger entrega al menos una vez, así que el handler tiene que ser idempotente. Los reintentos y el transport de fallidos tienen su propia lección, colas de muertos y reproceso, y aquí no se repiten.

La petición que espera a un PDF #

Confirmar un pedido es escribir una fila. Generar la factura en PDF y mandarla por correo es otra cosa: tarda, depende de un SMTP ajeno y puede fallar. Si las dos van en la misma petición, el cliente espera al PDF y un correo caído tumba la confirmación.

php · antes: ConfirmarPedido.php 
<?php

declare(strict_types=1);

namespace App\Pedido;

final readonly class ConfirmarPedido
{
    public function __construct(
        private Pedidos $pedidos,
        private Facturas $facturas,
    ) {
    }

    public function __invoke(int $idPedido): void
    {
        $this->pedidos->confirmar($idPedido);
        $this->facturas->generarYEnviar($idPedido);
    }
}

El porqué de sacarlo fuera no es solo la latencia. Es que la confirmación deja de depender del correo: si el SMTP está caído, el pedido se confirma igual y la factura sale cuando vuelva.

Mensaje, handler y bus #

Messenger reparte el trabajo en tres piezas. El mensaje es un objeto inmutable que describe qué hay que hacer. El handler sabe hacerlo. El bus los une: recibe el mensaje y decide si lo ejecuta ya o lo manda a un transport.

php · src/Message/EnviarFactura.php 
<?php

declare(strict_types=1);

namespace App\Message;

final readonly class EnviarFactura
{
    public function __construct(
        public int $idPedido,
    ) {
    }
}

El mensaje lleva el id, no la entidad. Viaja serializado y puede esperar minutos en la cola: el handler debe leer el pedido tal como está cuando lo procesa, no como estaba al encolarlo.

php · src/MessageHandler/EnviarFacturaHandler.php 
<?php

declare(strict_types=1);

namespace App\MessageHandler;

use App\Message\EnviarFactura;
use App\Pedido\Facturas;
use App\Pedido\Pedidos;
use Symfony\Component\Messenger\Attribute\AsMessageHandler;

#[AsMessageHandler]
final readonly class EnviarFacturaHandler
{
    public function __construct(
        private Pedidos $pedidos,
        private Facturas $facturas,
    ) {
    }

    public function __invoke(EnviarFactura $mensaje): void
    {
        $pedido = $this->pedidos->buscar($mensaje->idPedido);

        if ($pedido->facturaEnviada()) {
            return;
        }

        $this->facturas->generarYEnviar($pedido);
        $this->pedidos->marcarFacturaEnviada($pedido);
    }
}

#[AsMessageHandler] registra la clase sin tocar configuración, y el tipo del argumento de __invoke dice qué mensaje atiende. El if es el consumidor idempotente de las garantías de entrega: si el worker muere tras marcar la factura y antes de confirmar el mensaje, este vuelve y el if lo descarta. Entre enviar y marcar queda una ventana pequeña: un correo no se deshace.

php · después: ConfirmarPedido.php 
<?php

declare(strict_types=1);

namespace App\Pedido;

use App\Message\EnviarFactura;
use Symfony\Component\Messenger\MessageBusInterface;

final readonly class ConfirmarPedido
{
    public function __construct(
        private Pedidos $pedidos,
        private MessageBusInterface $bus,
    ) {
    }

    public function __invoke(int $idPedido): void
    {
        $this->pedidos->confirmar($idPedido);
        $this->bus->dispatch(new EnviarFactura($idPedido));
    }
}

El mismo bus, síncrono o asíncrono #

Ese dispatch no decide nada por sí mismo. Si el mensaje no está enrutado a ningún transport, el bus llama al handler en ese momento, dentro de la petición: es un bus síncrono con otra sintaxis. En la prueba, sin la línea de routing, la factura salía antes de que el comando imprimiera «Pedido confirmado».

Síncrono (sin routing)

  • El handler corre dentro del dispatch
  • Una excepción del handler llega a quien despacha
  • No hace falta worker
  • Útil para empezar o para casos de uso internos

Asíncrono (enrutado a un transport)

  • El dispatch solo guarda el mensaje
  • Quien despacha nunca ve los errores del handler
  • Sin worker, el mensaje espera para siempre
  • Reintentos y fallidos pasan a ser cosa del worker

Pasar de una columna a otra es una línea de YAML, y esa es la ventaja de empezar con el bus aunque todo sea síncrono.

Enrutar a un transport: Doctrine o AMQP #

yaml · config/packages/messenger.yaml 
framework:
    messenger:
        transports:
            async: '%env(MESSENGER_TRANSPORT_DSN)%'
        routing:
            'App\Message\EnviarFactura': async

when@test:
    framework:
        messenger:
            transports:
                async: 'in-memory://'
bash · .env y preparación 
MESSENGER_TRANSPORT_DSN=doctrine://default

php bin/console messenger:setup-transports
php bin/console messenger:stats

Con doctrine://default la cola es la tabla messenger_messages de tu propia base de datos. Con amqp://… es RabbitMQ, que necesita la extensión amqp de PHP y el paquete symfony/amqp-messenger. El handler y el dispatch no cambian.

CriterioDoctrineAMQP (RabbitMQ)
Infraestructura nuevaNinguna: tu base de datosUn broker que operar
Cómo se entera el workerConsulta la tabla cada --sleep (1 s por defecto); en PostgreSQL, LISTEN/NOTIFYEl broker le empuja los mensajes
Transacción con tus datosSí, si comparten conexiónNo: es otro sistema
VolumenModesto; la tabla es un punto calienteAlto y con muchos consumidores
EnrutadoPor nombre de cola, poco másExchanges, claves y prioridades

La tercera fila es la que más pesa y menos se cuenta. Con Doctrine, un dispatch dentro de una transacción que acaba en rollback desaparece con ella: lo comprobamos y la cola quedó a cero. Es un outbox gratis. Con AMQP el mensaje ya salió al broker aunque tu transacción se deshaga, y vuelves a tener la doble escritura de esa lección.

El worker y sus límites #

Un mensaje asíncrono solo se procesa si alguien lo consume. Ese alguien es messenger:consume, un proceso PHP de larga vida que lee, despacha al handler y confirma.

bash · consumir 
php bin/console messenger:consume async -vv
php bin/console messenger:consume async --limit=1000 --time-limit=3600 --memory-limit=256M

Los tres límites existen por lo que cuenta Workers en PHP: un proceso que vive horas acumula memoria y estado. Ninguno mata el proceso a medias; el worker termina el mensaje en curso, sale con código 0 y deja que alguien lo relance.

OpciónSale cuando…Mensaje en el log
--limit=NHa procesado N mensajesmaximum count of N messages processed
--time-limit=SLleva S segundos en marchatime limit of Ss exceeded
--memory-limit=MTras un mensaje, la memoria supera Mmemory limit of … bytes exceeded

Reiniciar los workers al desplegar #

Un worker carga el código al arrancar y no lo vuelve a leer. Despliegas la versión nueva y los workers siguen ejecutando la vieja, con handlers que quizá ya no casan con tu esquema. Por eso el despliegue termina avisándoles:

bash · al final del despliegue 
php bin/console cache:warmup --env=prod
php bin/console messenger:stop-workers

stop-workers no mata procesos: deja una marca en la caché de la app y cada worker, al acabar su mensaje, la ve y sale limpio. En la prueba, el log decía Worker stopped because a restart was requested y el contenedor salió con código 0. Relanzarlo es trabajo del supervisor: una unidad de systemd con Restart=always, como la de systemd para servicios, o Supervisor. En Kubernetes, el reinicio progresivo del Deployment hace el papel de stop-workers.

Errores típicos #

Lo que se rompe en producción

  • Supervisor sin autorestart=true. Su valor por defecto es unexpected, y la salida limpia (código 0) de un límite o de stop-workers cuenta como esperada: el worker no vuelve. Con systemd pasa lo mismo con Restart=on-failure.
  • Varios servidores y caché local. La marca de stop-workers vive en cache.app; si cada máquina tiene la suya en disco, solo se reinician los workers de la máquina donde lo lanzaste. Hace falta una caché compartida, como Redis.
  • Matar en vez de parar. Sin la extensión pcntl, un SIGTERM corta el handler a medias. Con ella, el worker termina el mensaje antes de salir, si el orquestador le da tiempo de gracia.
  • Renombrar la clase del mensaje con mensajes en cola. El transport guarda el mensaje serializado con el nombre de la clase; tras el renombrado, el worker falla con Could not decode Envelope. Vacía la cola antes o mantén la clase vieja un despliegue más.

Cómo comprobarlo #

En los tests no quieres un worker ni una base de datos: quieres saber que confirmar un pedido encola la factura, no que la envía. El transport in-memory:// del bloque when@test guarda los mensajes en un array, y Symfony lo vacía entre tests de KernelTestCase. El test pide ConfirmarPedido al contenedor, así que algún controlador o comando tiene que inyectarlo: si nadie lo usa, Symfony lo elimina al compilar.

php · tests/ConfirmarPedidoTest.php 
<?php

declare(strict_types=1);

namespace App\Tests;

use App\Message\EnviarFactura;
use App\Pedido\ConfirmarPedido;
use Symfony\Bundle\FrameworkBundle\Test\KernelTestCase;
use Symfony\Component\Messenger\Transport\InMemory\InMemoryTransport;

final class ConfirmarPedidoTest extends KernelTestCase
{
    public function testConfirmarEncolaLaFacturaSinEnviarla(): void
    {
        self::bootKernel();
        $confirmarPedido = self::getContainer()->get(ConfirmarPedido::class);

        $confirmarPedido(42);

        $transport = self::getContainer()->get('messenger.transport.async');
        self::assertInstanceOf(InMemoryTransport::class, $transport);
        self::assertCount(1, $transport->getSent());
        self::assertEquals(new EnviarFactura(42), $transport->getSent()[0]->getMessage());
    }
}

El handler se prueba aparte, como una clase normal: lo instancias con dobles y llamas a __invoke. En un entorno real, messenger:stats te dice cuántos mensajes esperan en cada transport, y debug:messenger qué handler atiende cada mensaje. Una cola que solo crece es un worker caído.

Cuándo aplicarlo #

Messenger asíncrono cuando…

  • El trabajo es lento o depende de un tercero: correos, PDF, APIs
  • La respuesta al usuario no necesita el resultado
  • Quieres reintentos sin escribirlos tú
  • Ya usas Symfony; con Doctrine no añades infraestructura

No lo hagas asíncrono cuando…

  • El usuario necesita el resultado en la misma respuesta
  • Nadie va a operar ni vigilar los workers
  • Es una tarea periódica, no una reacción a algo que pasó
  • El volumen y el fan-out piden un registro de eventos

Las alternativas: para lo periódico, un timer de systemd o un cron; para muchos consumidores o rebobinar, el registro de eventos de Colas y topics. Y si el volumen crece pero no necesitas rebobinar, cambiar el DSN a RabbitMQ no toca tu código.

Resumen #

Lo que te llevas

  • Mensaje inmutable con ids, handler con #[AsMessageHandler] e idempotente, y un dispatch que no sabe si es síncrono.
  • Sin routing el handler corre dentro del dispatch; enrutado, el mensaje espera a un worker.
  • Doctrine no añade infraestructura y comparte transacción con tus datos; AMQP escala y enruta mejor, pero reabre la doble escritura.
  • --limit, --time-limit y --memory-limit reciclan el worker con salida limpia; el supervisor debe relanzarlo también entonces.
  • Cada despliegue acaba en messenger:stop-workers, con caché compartida si hay varias máquinas.
  • En tests, in-memory:// comprueba que se encola sin enviar nada.
