Sagas: transacciones largas con compensación

Una saga cambia «todo o nada a la vez» por «todo, o deshago lo que ya hice». La parte difícil no es el camino feliz: son las compensaciones que fallan, los pasos irreversibles y el aislamiento que pierdes.

Una saga cambia «todo o nada a la vez» por «todo, o deshago lo que ya hice». Cada paso confirma por su cuenta y libera sus bloqueos; si uno falla, se ejecutan las compensaciones de los anteriores en orden inverso. Es la forma práctica de coordinar una operación larga entre servicios, y la parte difícil no es el camino feliz.

Pasos y compensaciones #

Cada paso de la saga tiene una operación y su contraria. Confirmar un pedido, con tres servicios implicados, se ve así:

PasoOperaciónCompensación
1Reservar stockLiberar la reserva
2Cobrar la tarjetaEmitir un reembolso
3Crear el envíoCancelar el envío
1 Reservar stockOK
2 CobrarOK
3 Crear envíoERROR: no hay reparto a esa zona
4 Reembolsar y liberar stockEn orden inverso al que se hicieron

No hay rollback: hay operaciones nuevas que dejan el sistema en un estado aceptable.

Compensar no es deshacer

Un ROLLBACK borra la historia: nadie supo nunca que aquello pasó. Una compensación añade historia: el cliente ve el cargo y el reembolso en su extracto, y recibe dos correos. Diseñar una saga es aceptar que los estados intermedios son visibles y que el negocio tiene que estar de acuerdo con eso.

Coreografía u orquestación #

Hay dos formas de decidir cuál es el paso siguiente, y la elección envejece muy distinto:

Coreografía

  • Cada servicio escucha eventos y reacciona
  • Nadie manda: el flujo emerge de las suscripciones
  • Fácil de arrancar, sin pieza central
  • Pero: el flujo no está escrito en ningún sitio
  • Pero: depurar «por qué se paró» es arqueología

Orquestación

  • Un orquestador conoce los pasos y los va llamando
  • El flujo se lee en una clase
  • El estado de cada saga es consultable
  • Pero: una pieza más que mantener
  • Pero: tiende a acumular lógica de negocio

Para tres pasos, la coreografía va bien. A partir de cinco o seis, con ramas y condiciones, nadie sabe ya cuál es el flujo completo y cada cambio da miedo. La orquestación cuesta más al principio y se paga sola en cuanto el proceso importa de verdad.

Un orquestador con estado #

La clave está en que la saga persista su estado: si el proceso muere a mitad, alguien tiene que poder retomarla. Sin eso, tienes un método largo con try/catch, no una saga.

php · SagaConfirmarPedido.php 
<?php

declare(strict_types=1);

final class SagaConfirmarPedido
{
    public function avanzar(EstadoSaga $saga): void
    {
        $paso = $this->pasos[$saga->indicePaso()];

        try {
            $paso->ejecutar($saga->contexto());
            $saga->marcarPasoCompletado();
        } catch (PasoFallido $fallo) {
            $saga->marcarCompensando($fallo->motivo());
        }

        $this->repositorio->guardar($saga);
    }

    public function compensar(EstadoSaga $saga): void
    {
        foreach ($saga->pasosCompletadosEnOrdenInverso() as $paso) {
            $this->pasos[$paso]->compensar($saga->contexto());
            $saga->marcarPasoCompensado($paso);
            $this->repositorio->guardar($saga);
        }
    }
}

El guardar después de cada paso es lo que hace que esto funcione: si el proceso se cae entre el paso 2 y el 3, el estado en base de datos dice exactamente dónde estaba, y un proceso de recuperación la retoma.

Las tres partes difíciles #

1. Compensaciones que también fallan. ¿Y si el reembolso da error? No puedes compensar la compensación. Se resuelve reintentando indefinidamente —las compensaciones deben ser idempotentes y estar diseñadas para acabar saliendo— y, si se agotan los intentos, escalando a una persona. Una saga sin ruta de escalado manual está incompleta.

2. Pasos que no se pueden compensar. Un correo enviado no se desenvía. La técnica es ordenar los pasos poniendo los irreversibles al final, cuando ya no puede fallar nada por delante. Si el correo es el paso 2 de 5, muévelo al 5.

3. La falta de aislamiento

Es lo que más sorprende. Durante la saga hay estados intermedios visibles: el stock está reservado y el pago hecho, pero el pedido «no existe» todavía. Otra operación concurrente puede ver ese estado y decidir sobre él. Las transacciones de verdad te daban aislamiento; una saga, no. Se mitiga con estados explícitos («reservado», «pendiente de confirmar») que digan al resto del sistema que ahí no se toca.

Cuándo aplicarlo #

Monta una saga cuando…

  • La operación cruza servicios con bases de datos distintas
  • Algún paso es una API externa que no habla XA
  • Los pasos tardan: envíos, revisiones, confirmaciones humanas
  • Cada paso tiene una compensación con sentido de negocio

No la montes cuando…

  • Todo cabe en una transacción local: úsala, es más simple y más fuerte
  • No existe compensación razonable para algún paso central
  • El negocio no acepta que se vean estados intermedios
  • Es un caso puntual: a veces una tarea manual sale más barata

Resumen #

Lo que te llevas

  • Una saga cambia «todo o nada a la vez» por «todo, o deshago lo hecho»: cada paso confirma y libera sus bloqueos.
  • Compensar no es deshacer: añade historia en vez de borrarla. El cliente ve el cargo y el reembolso, y el negocio tiene que aceptarlo.
  • Coreografía para tres pasos; orquestación en cuanto haya ramas, porque si no el flujo no está escrito en ningún sitio.
  • Si la saga no persiste su estado tras cada paso, no es una saga: es un método largo con try/catch que se pierde al reiniciar.
  • Pierdes el aislamiento: los estados intermedios son visibles y otra operación puede decidir sobre ellos. Hazlos explícitos.
