Un agente dentro de tu producto

Un agente es un bucle: el modelo pide una herramienta, tu código la ejecuta y le devuelve el resultado, hasta que el modelo termina. Escribirlo cuesta diez líneas. Que no se coma tu presupuesto, no repita un reembolso y deje rastro de lo que hizo cuesta más, y de eso va esta lección.

En salida estructurada viste el tool use de una vuelta: el modelo devuelve una llamada tipada y tu código la consume. Aquí el resultado vuelve al modelo y el modelo decide el siguiente paso. Es el mismo bucle que mueve a Claude Code (el agente por dentro), pero ahora el harness lo escribes tú, en tu backend, con el dinero y los datos de tu empresa.

De una vuelta a un bucle #

El caso del curso: un ticket dice «me cobrasteis dos veces el pedido 8841». Resolverlo exige consultar el pedido, ver los cargos, decidir si procede un reembolso, emitirlo y redactar la respuesta. Con un flujo fijo, tú escribes ese orden en código. Con un agente, das al modelo las herramientas (consultar_pedido, emitir_reembolso) y él decide cuáles usar y cuándo parar.

Esa flexibilidad es la gracia y el riesgo. Las vueltas ya no las decide tu código, y cada una cuesta una llamada al modelo, segundos de un worker y, si la herramienta escribe, un efecto real. Un modelo atascado repitiendo la misma consulta convierte un ticket en una factura. Por eso el bucle de producción no es un while (true): es un bucle con presupuesto.

El bucle en la API #

La API de Claude no ejecuta tus herramientas ni guarda la conversación: cada vuelta es una llamada normal a messages con el historial completo, como en la primera lección. Lo que cambia son tres piezas:

1 Pides con toolsEl historial más las definiciones de cada herramienta: nombre, descripción, input_schema
2 El modelo pide herramientasUno o varios bloques tool_use con id, name e input
3 Devuelves tool_resultUn mensaje user con un tool_result por cada tool_use, enlazado por tool_use_id
4 stop_reason: end_turnEl modelo responde sin pedir nada más: fin del bucle

El bucle de tool use: el modelo decide, tu servidor ejecuta.

Las reglas del formato que más muerden:

  • Un tool_result por cada tool_use. Si el modelo pide varias herramientas a la vez, todas las respuestas van juntas en el siguiente mensaje user.
  • Los tool_result van primero. Cualquier texto tuyo va detrás de ellos en ese mensaje, nunca delante.
  • Los fallos de la herramienta se devuelven, no se lanzan. Con is_error: true y un mensaje claro («el pedido 8841 no existe»), el modelo corrige o se lo explica al cliente.
  • Hay más stop_reason que tool_use y end_turn. max_tokens puede cortar un tool_use a medias y refusal llega como un 200.

¿Y el tool runner del SDK?

El SDK de PHP trae un tool runner, en beta, que hace este bucle por ti y acepta maxIterations. La propia documentación recomienda el bucle manual cuando necesitas registro propio, aprobación humana o ejecución condicional, que es lo que pide producción.

Del while (true) al bucle con límites #

La primera versión que sale, y que funciona en la demo:

php · antes: el bucle de la demo 
<?php

function resolverTicket(Anthropic\Client $client, Herramientas $herramientas, string $peticion): string
{
    $historial = [["role" => "user", "content" => $peticion]];

    while (true) {
        $message = $client->messages->create(
            model: "claude-opus-5-5",
            maxTokens: 4096,
            tools: $herramientas->definiciones(),
            messages: $historial,
        );

        $historial[] = ["role" => "assistant", "content" => $message->content];

        if ($message->stopReason !== "tool_use") {
            return $message->content[0]->text;
        }

        $resultados = [];

        foreach ($message->content as $block) {
            if ($block->type === "tool_use") {
                $resultados[] = [
                    "type" => "tool_result",
                    "tool_use_id" => $block->id,
                    "content" => $herramientas->ejecutar($block->name, $block->input),
                ];
            }
        }

        $historial[] = ["role" => "user", "content" => $resultados];
    }
}

Cuatro problemas: no hay techo, así que si el modelo nunca deja de pedir herramientas el bucle no acaba; cualquier stopReason distinto de tool_use pasa por respuesta final, incluidos un corte y un rechazo; una excepción de la herramienta tumba la ejecución en vez de llegar al modelo; y no queda rastro. La versión de producción aísla la llamada al modelo tras un PasoDelModelo (un doble en los tests) y el bucle lleva la cuenta:

php · después: el bucle con presupuesto 
<?php

declare(strict_types=1);

use Anthropic\Messages\ToolUseBlock;

final class AgenteDeSoporte
{
    private const MAX_VUELTAS = 8;
    private const MAX_TOKENS_POR_EJECUCION = 150_000;
    private const SEGUNDOS_POR_EJECUCION = 90;

    public function __construct(
        private readonly PasoDelModelo $modelo,
        private readonly CatalogoDeHerramientas $herramientas,
        private readonly TrazaDelAgente $traza,
    ) {}

    public function resolver(string $idDeEjecucion, string $peticion): ResultadoDelAgente
    {
        $historial = [["role" => "user", "content" => $peticion]];
        $tokensGastados = 0;
        $fechaLimite = microtime(true) + self::SEGUNDOS_POR_EJECUCION;

        for ($vuelta = 1; $vuelta <= self::MAX_VUELTAS; $vuelta++) {
            $message = $this->modelo->siguiente($historial);
            $tokensGastados += $message->usage->inputTokens + $message->usage->outputTokens;
            $this->traza->registrarRespuesta($idDeEjecucion, $vuelta, $message);
            $historial[] = ["role" => "assistant", "content" => $message->content];

            if ($message->stopReason === "end_turn") {
                return ResultadoDelAgente::terminado($message);
            }

            if ($message->stopReason !== "tool_use") {
                return ResultadoDelAgente::interrumpido($message->stopReason);
            }

            if ($this->seAgotoElPresupuesto($vuelta, $tokensGastados, $fechaLimite)) {
                return ResultadoDelAgente::presupuestoAgotado($vuelta, $tokensGastados);
            }

            $historial[] = [
                "role" => "user",
                "content" => $this->ejecutarHerramientas($idDeEjecucion, $vuelta, $message->content),
            ];
        }

        return ResultadoDelAgente::presupuestoAgotado(self::MAX_VUELTAS, $tokensGastados);
    }

    private function seAgotoElPresupuesto(int $vuelta, int $tokensGastados, float $fechaLimite): bool
    {
        return $vuelta >= self::MAX_VUELTAS
            || $tokensGastados > self::MAX_TOKENS_POR_EJECUCION
            || microtime(true) > $fechaLimite;
    }

    private function ejecutarHerramientas(string $idDeEjecucion, int $vuelta, array $bloques): array
    {
        $resultados = [];

        foreach ($bloques as $block) {
            if (!$block instanceof ToolUseBlock) {
                continue;
            }

            $resultados[] = $this->ejecutarUna($idDeEjecucion, $vuelta, $block);
        }

        return $resultados;
    }

    private function ejecutarUna(string $idDeEjecucion, int $vuelta, ToolUseBlock $block): array
    {
        try {
            $salida = $this->herramientas->ejecutar($block->name, $block->input, $idDeEjecucion);
            $this->traza->registrarHerramienta($idDeEjecucion, $vuelta, $block, $salida, esError: false);

            return ["type" => "tool_result", "tool_use_id" => $block->id, "content" => $salida];
        } catch (HerramientaFallida $exception) {
            $this->traza->registrarHerramienta($idDeEjecucion, $vuelta, $block, $exception->getMessage(), esError: true);

            return [
                "type" => "tool_result",
                "tool_use_id" => $block->id,
                "content" => $exception->getMessage(),
                "is_error" => true,
            ];
        }
    }
}

La llamada real queda en una clase pequeña, con su propio timeout por petición:

php · la llamada al modelo, aislada 
<?php

declare(strict_types=1);

use Anthropic\Client;
use Anthropic\Messages\Message;

final class PasoConClaude implements PasoDelModelo
{
    private const MODELO = "claude-opus-5-5";
    private const SEGUNDOS_DE_TIMEOUT_POR_LLAMADA = 60.0;

    public function __construct(
        private readonly Client $client,
        private readonly CatalogoDeHerramientas $herramientas,
        private readonly string $instrucciones,
    ) {}

    public function siguiente(array $historial): Message
    {
        return $this->client->messages->create(
            model: self::MODELO,
            maxTokens: 4096,
            system: $this->instrucciones,
            tools: $this->herramientas->definiciones(),
            messages: $historial,
            requestOptions: ["timeout" => self::SEGUNDOS_DE_TIMEOUT_POR_LLAMADA],
        );
    }
}

Los límites, uno a uno #

LímiteContra qué protegeCómo se fija
VueltasEl modelo que se atasca repitiendo la misma consultaDesde la traza real: si casi todo acaba en 3-4 vueltas, un techo de 8 da margen
TokensLa facturaSuma inputTokens y outputTokens del usage de cada respuesta
TiempoEl worker bloqueadoUna fecha límite por ejecución, más el timeout de cada llamada al modelo
HerramientasEl efecto duplicado y la dependencia lentaTimeout propio y clave de idempotencia en las que escriben

El límite de tokens tiene trampa: cada vuelta reenvía el historial entero, así que la vuelta 8 paga otra vez las siete anteriores y el coste crece más deprisa que las vueltas. Es la aritmética de la lección de coste, multiplicada. Por eso las herramientas devuelven solo lo que el modelo necesita para decidir: un estado y un importe, no el pedido entero en JSON.

Las herramientas que escriben son las delicadas. Si el worker muere tras emitir el reembolso, la cola reintenta el trabajo y el modelo vuelve a pedirlo. Si la herramienta no es idempotente, el cliente recibe el reembolso dos veces. La clave se deriva de la ejecución y de la acción, nunca del id del tool_use, porque un reintento genera ids nuevos:

php · una herramienta que escribe, idempotente y con timeout 
<?php

declare(strict_types=1);

final class EmitirReembolso
{
    public const DEFINICION = [
        "name" => "emitir_reembolso",
        "description" => "Reembolsa total o parcialmente un pedido del cliente de esta conversación. " .
            "Úsala solo tras consultar el pedido con consultar_pedido. El importe va en céntimos " .
            "y no puede superar el importe pagado. Devuelve el id y el estado del reembolso.",
        "strict" => true,
        "input_schema" => [
            "type" => "object",
            "properties" => [
                "pedido_id" => ["type" => "string"],
                "importe_en_centimos" => ["type" => "integer"],
            ],
            "required" => ["pedido_id", "importe_en_centimos"],
            "additionalProperties" => false,
        ],
    ];

    private const SEGUNDOS_DE_TIMEOUT = 5.0;

    public function __construct(private readonly PasarelaDePago $pasarela) {}

    public function __invoke(array $input, string $idDeEjecucion): string
    {
        $claveDeIdempotencia = hash("sha256", "{$idDeEjecucion}:reembolso:{$input["pedido_id"]}");

        $reembolso = $this->pasarela->reembolsar(
            pedidoId: $input["pedido_id"],
            importeEnCentimos: $input["importe_en_centimos"],
            claveDeIdempotencia: $claveDeIdempotencia,
            segundosDeTimeout: self::SEGUNDOS_DE_TIMEOUT,
        );

        return "Reembolso {$reembolso->id}: {$reembolso->estado}";
    }
}

Dos detalles más. strict: true hace que el input cumpla siempre el esquema, así que no te llega un importe como texto; lo que no garantiza es que el importe sea correcto, y esa validación de negocio sigue siendo tuya. Y qué herramientas das, con qué permisos y sobre los datos de quién, es la otra mitad del diseño: está en la lección de seguridad.

Cuando se agota el presupuesto #

Agotar un límite es un resultado previsto, con estado propio (presupuestoAgotado), no una excepción genérica. Lo que haces con él:

  • No reintentar en automático. El mismo ticket con el mismo modelo suele atascarse en el mismo sitio: pagarías dos veces el mismo bucle.
  • Pasárselo a una persona con la traza. El agente ya consultó el pedido y vio los cargos: quien lo retome no empieza de cero.
  • Avisar al cliente con honestidad. «Lo revisa una persona» antes que una respuesta improvisada sobre una ejecución a medias.

La tasa de ejecuciones que agotan el presupuesto es una métrica: si sube tras cambiar prompt o modelo, algo se ha roto aunque nada haya fallado.

Registrar cada paso #

Si un cliente pregunta por qué se le reembolsaron 40 €, «lo decidió el modelo» no es respuesta. Cada ejecución lleva un id y cada vuelta deja una línea:

CampoPara qué
Id de ejecución y número de vueltaReconstruir la secuencia completa de un ticket
Herramienta, entrada y si fue errorSaber qué se pidió y qué devolvió tu código
stopReason y usagePor qué paró y cuánto costó cada vuelta
Duración de cada herramientaEncontrar la dependencia lenta antes de que llegue al timeout
Modelo y versión del promptComparar antes y después de un cambio

La entrada de las herramientas lleva datos de clientes, así que se redacta como cualquier log (logging seguro). Y sus casos reales alimentan el golden set con el que evalúas el agente.

Errores típicos #

Lo que rompe un agente en producción

  • Ejecutar herramientas en la última vuelta. Un reembolso cuyo resultado el modelo ya no verá.
  • Responder solo al primer tool_use. Con llamadas en paralelo, el resto queda sin tool_result y la API devuelve 400.
  • Un único timeout. El de la llamada al modelo no protege de una herramienta colgada.
  • Herramientas con más permisos que la tarea. Un agente de soporte con una conexión de escritura a toda la base de datos es el exceso de agencia que OWASP lista como LLM06:2025.
  • Correrlo dentro de la petición web. Va a un worker de cola, como cualquier llamada al modelo.

Cómo comprobarlo #

Los límites se prueban sin llamar a la API: un doble de PasoDelModelo que siempre pide una herramienta debe hacer que el bucle pare en la vuelta 8, y uno que devuelve max_tokens debe acabar en un estado de interrupción, no de éxito.

php · el límite de vueltas, probado sin API 
<?php

declare(strict_types=1);

use PHPUnit\Framework\TestCase;

final class AgenteDeSoporteTest extends TestCase
{
    public function testSeDetieneEnLaVueltaMaximaSiElModeloNuncaTermina(): void
    {
        $traza = new TrazaEnMemoria();
        $agente = new AgenteDeSoporte(
            new ModeloQueSiemprePideHerramienta(),
            new CatalogoDeHerramientasFalso(),
            $traza,
        );

        $resultado = $agente->resolver("ejecucion-1", "Reembólsame el pedido 8841");

        self::assertTrue($resultado->agotoElPresupuesto());
        self::assertCount(8, $traza->respuestas());
    }
}

Igual se prueba que una herramienta que lanza su excepción llega al modelo como is_error. En producción, vigila por caso de uso las vueltas y los tokens por ejecución y el porcentaje que agota el presupuesto.

Cuándo aplicarlo #

La pregunta previa es si los pasos se pueden escribir de antemano. Si se pueden, un flujo fijo de llamadas (clasificar con salida estructurada, consultar el pedido en tu código, redactar con otra llamada) es más barato, más rápido y se prueba como cualquier código. Anthropic lo plantea igual: la solución más simple primero, y autonomía solo cuando la tarea la pida.

Un agente encaja cuando…

  • Los pasos dependen de lo que se va descubriendo y no caben en un diagrama fijo
  • El número de pasos varía mucho de un caso a otro
  • Un error es detectable y reversible, o hay una persona antes del efecto

Mejor un flujo fijo cuando…

  • Siempre son los mismos pasos en el mismo orden
  • Necesitas latencia y coste predecibles por petición
  • Una acción irreversible quedaría sin revisión humana

Y hay término medio: un flujo fijo donde solo el paso que de verdad decide es un agente pequeño con herramientas de lectura.

Resumen #

Lo que te llevas

  • Un agente es un bucle: stop_reason: tool_use, tu código ejecuta, devuelves un tool_result por cada tool_use, hasta end_turn.
  • El bucle de producción tiene presupuesto: vueltas, tokens y tiempo, y cualquier otro stopReason es una interrupción, no un éxito.
  • Las herramientas tienen timeout propio, devuelven sus fallos con is_error y, si escriben, son idempotentes con una clave de la ejecución.
  • Agotar el presupuesto es un estado previsto: sin reintento automático, a una persona y con la traza de cada paso.
  • Si los pasos se pueden escribir de antemano, un flujo fijo de llamadas gana al agente en coste, latencia y pruebas.
