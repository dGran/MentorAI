Auth en el servidor: SSR, cookies y roles

En una app que solo corre en el navegador, la sesión vive en localStorage y todo funciona. En cuanto un servidor renderiza páginas o tu propio backend recibe peticiones, aparece la pregunta de verdad: ¿cómo sabe el servidor quién es el usuario, y de qué se puede fiar?

En Auth viste los dos tokens de la sesión y cómo supabase-js los gestiona en el navegador. Aquí los llevamos al servidor: renderizado en servidor (SSR) con frameworks como Next.js, SvelteKit o Nuxt, y backends propios, en PHP o en lo que sea, que reciben el token y tienen que validarlo.

El servidor no ve localStorage #

Con SSR, la primera petición de una página la atiende un servidor, que tiene que saber quién eres antes de mandar el HTML: para pintar tus notas, o para redirigirte al login. Pero localStorage solo existe en el navegador, y el navegador no lo manda en las peticiones.

Lo que el navegador sí manda en cada petición son las cookies. Por eso, en apps con servidor, la sesión de Supabase se guarda en cookies, y el paquete **@supabase/ssr** se encarga de leerlas y escribirlas de forma que navegador y servidor compartan la misma sesión.

1 NavegadorcreateBrowserClient guarda la sesión en cookies
2 Servidor (proxy o middleware)lee las cookies, valida el token y lo refresca si va a caducar
3 Página renderizada en el servidorcreateServerClient consulta como ese usuario: RLS aplica

El navegador y el servidor leen la misma sesión porque viaja en cookies.

Los dos clientes de @supabase/ssr #

El cliente del servidor necesita que le digas cómo leer y escribir cookies en tu framework. En Next.js (App Router) queda así:

ts · lib/supabase/server.ts 
import { createServerClient } from "@supabase/ssr";
import { cookies } from "next/headers";

export async function createClient() {
  const cookieStore = await cookies();

  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
    {
      cookies: {
        getAll() {
          return cookieStore.getAll();
        },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) => cookieStore.set(name, value, options));
          } catch {
            // Un Server Component no puede escribir cookies: las renueva el proxy.
          }
        },
      },
    },
  );
}
ts · lib/supabase/client.ts (navegador) 
import { createBrowserClient } from "@supabase/ssr";

export const createClient = () =>
  createBrowserClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
  );

Un cliente de servidor se crea por petición: cada una trae las cookies de un usuario distinto. Guardarlo en una variable global del módulo mezclaría las sesiones de usuarios diferentes.

El proxy que refresca la sesión

Los Server Components no pueden escribir cookies, así que alguien tiene que renovar el token antes de que caduque. En Next.js lo hace el fichero proxy.ts (se llamaba middleware.ts hasta Next.js 16), que se ejecuta antes de cada petición: crea un cliente de servidor, llama a supabase.auth.getClaims() (que refresca si hace falta) y devuelve la respuesta con las cookies nuevas.

Devuelve la respuesta que tiene las cookies

El error clásico del proxy es construir una respuesta nueva (una redirección, por ejemplo) y devolver esa en lugar de la que recibió las cookies renovadas en setAll. El navegador no recibe los tokens nuevos, el refresh token ya usado deja de valer y el usuario «pierde la sesión» sin motivo aparente. La guía de SSR de Supabase para cada framework trae el proxy completo; cópialo tal cual y modifica solo lo marcado.

getClaims, getUser y getSession: de qué fiarse #

supabase-js tiene tres formas de preguntar por el usuario, y en el servidor la diferencia es de seguridad:

MétodoQué hace¿Fiable en el servidor?
getSession()Lee la sesión de donde esté guardada (las cookies) sin validarlaNo. Las cookies las manda el cliente y pueden estar manipuladas
getClaims()Verifica la firma del token y devuelve sus claims; refresca si va a caducarSí. Con claves asimétricas lo verifica en local, sin ir a Auth
getUser()Pregunta al servidor de Auth por el usuario actualSí, y además trae datos frescos; cuesta una petición de red

Para proteger una página o decidir qué mostrar, usa getClaims(). Usa getUser() cuando necesites saber algo que pudo cambiar después de emitirse el token, como si el usuario sigue existiendo o si cambió su email.

ts · proteger una página en el servidor 
const supabase = await createClient();
const { data } = await supabase.auth.getClaims();

if (!data?.claims) redirect("/login");

const { data: notes } = await supabase.from("notes").select("id, title");

Fíjate en que la consulta de notas ni siquiera necesita filtrar por usuario: el cliente de servidor manda el token de las cookies, y RLS hace el resto, igual que en el navegador.

Verificar el token desde cualquier backend #

Si tienes tu propio backend (una API en PHP, Go o Python), el frontend le manda el access token en la cabecera Authorization y tu backend tiene que verificarlo. Cómo depende de con qué firma Auth los tokens:

Claves asimétricas (recomendado)

  • Auth firma con una clave privada (ES256 o RS256) que nunca sale de Supabase
  • Las claves públicas se publican en https://<ref>.supabase.co/auth/v1/.well-known/jwks.json
  • Tu backend descarga ese JWKS, lo cachea y verifica en local, sin secretos compartidos
  • Se pueden rotar sin cortar sesiones

Secreto compartido (antiguo)

  • Auth firma con HS256 y un secreto que tu backend también tiene que conocer
  • Quien tenga el secreto puede fabricar tokens válidos de cualquier usuario
  • Rotarlo invalida todas las sesiones a la vez

Los proyectos nuevos usan claves asimétricas, y los antiguos pueden migrar desde Project Settings → JWT Keys. En PHP, con una librería JWT que soporte JWKS, verificar es una línea más la caché de las claves:

php · verificar el access token en un backend PHP 
<?php

declare(strict_types=1);

use Firebase\JWT\JWK;
use Firebase\JWT\JWT;

$jwks = json_decode($cachedJwksJson, true, flags: JSON_THROW_ON_ERROR);
$claims = JWT::decode($accessToken, JWK::parseKeySet($jwks));

if ($claims->aud !== 'authenticated') {
    throw new InvalidTokenAudience($claims->aud);
}

$userId = $claims->sub;

JWT::decode comprueba firma y caducidad; la audiencia la compruebas tú. Con el $userId verificado, tu backend tiene dos formas de hablar con la base de datos: reenviar el mismo token a la Data API (RLS se aplica como si consultara el usuario) o conectarse directamente y filtrar él. La primera mantiene una sola fuente de permisos; la segunda te obliga a replicarlos en tu código.

Roles en el token: el hook de access token #

Una app con roles (admin, editor, lector) necesita que las políticas sepan el rol de quien consulta. Consultar una tabla de roles en cada política funciona, pero se ejecuta en cada fila de cada consulta. La alternativa es meter el rol en el JWT una sola vez, al emitirlo, con el Custom Access Token Hook:

sql · el rol del usuario como claim del token 
create table public.user_roles (
  user_id uuid primary key references auth.users (id) on delete cascade,
  role text not null check (role in ('admin', 'editor'))
);

create function public.custom_access_token_hook(event jsonb)
returns jsonb
language plpgsql
stable
as $$
declare
  claims jsonb := event -> 'claims';
  user_role text;
begin
  select role into user_role from public.user_roles where user_id = (event ->> 'user_id')::uuid;

  claims := jsonb_set(claims, '{user_role}', coalesce(to_jsonb(user_role), 'null'::jsonb));

  return jsonb_set(event, '{claims}', claims);
end;
$$;

grant execute on function public.custom_access_token_hook to supabase_auth_admin;
revoke execute on function public.custom_access_token_hook from authenticated, anon, public;
grant select on table public.user_roles to supabase_auth_admin;

Se activa en Authentication → Hooks, y a partir de ahí las políticas leen el rol del token: (select auth.jwt() ->> 'user_role') = 'admin'. La tabla user_roles necesita además RLS y una política que deje leer a supabase_auth_admin, el rol con el que corre el hook.

El rol del token llega tarde

El claim se calcula al emitir el token. Si cambias el rol de alguien, lo verá en su próximo refresco, como mucho una hora después con la configuración por defecto. Para quitar permisos de inmediato, la política tiene que consultar la tabla y no el token.

Errores típicos #

  • **Confiar en getSession() en el servidor.** Sus datos vienen de cookies que controla el cliente.
  • Un cliente de servidor compartido entre peticiones. Mezcla sesiones de usuarios distintos.
  • Cachear en una CDN páginas que dependen del usuario. La página de Ana se sirve a Luis. Las respuestas con datos de usuario llevan Cache-Control: private o no se cachean.
  • Usar la clave secreta en el SSR «para que funcione». Las consultas se saltan RLS y el servidor acaba enseñando datos de otros.
  • Verificar el JWT sin comprobar la audiencia y la caducidad, o con el secreto antiguo copiado en diez servicios.

Cuándo aplicarlo #

Tu appQué necesitas
SPA que solo corre en el navegador (Vite, React, Vue)supabase-js normal; la sesión en localStorage basta

Backend propio que recibe peticiones del frontendVerificar el JWT con el JWKS y reenviarlo a la Data API o filtrar tú
Roles que las políticas consultan muchoHook de access token, asumiendo el retraso hasta el refresco

Resumen #

Lo que te llevas

  • Con SSR la sesión viaja en cookies; @supabase/ssr da un cliente de navegador y otro de servidor que se crea por petición.
  • Un proxy o middleware refresca el token en cada petición y tiene que devolver la respuesta que lleva las cookies renovadas.
  • En el servidor, getSession() no es fiable; getClaims() verifica la firma y getUser() pregunta a Auth.
  • Las claves asimétricas permiten verificar el token en cualquier backend con el JWKS público, sin compartir secretos.
  • El hook de access token mete el rol en el JWT para que las políticas lo lean sin consultar tablas, a cambio de que los cambios lleguen en el siguiente refresco.
