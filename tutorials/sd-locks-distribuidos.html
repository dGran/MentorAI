Locks distribuidos: el que casi siempre está mal

«Que solo un proceso haga esto a la vez» parece un problema de cinco líneas con Redis. La versión de cinco líneas está mal de una forma que no se ve hasta que factura dos veces al mismo cliente.

«Que solo un proceso haga esto a la vez» parece un problema de cinco líneas con Redis. Y la versión de cinco líneas está mal de una forma que no se ve hasta que factura dos veces al mismo cliente. Esta lección va de por qué está mal y de qué hacer al respecto.

El intento de cinco líneas #

Casi todo el mundo escribe esto la primera vez, y en el 95 % de las ejecuciones funciona:

php · el bloqueo que parece bien 
<?php

if (!$redis->set('bloqueo:facturacion', '1', ['NX', 'EX' => 60])) {
    return;
}

$this->facturar();

$redis->del('bloqueo:facturacion');

El NX hace que solo lo consiga el primero, y el EX evita que el bloqueo se quede para siempre si el proceso muere. Dos aciertos. Y aun así tiene dos fallos serios.

Fallo 1: borras el bloqueo de otro

Si tu proceso tarda más de 60 s, el bloqueo caduca y lo coge otro. Cuando el tuyo termina, ejecuta ese del y borra el bloqueo del segundo, que sigue trabajando. Entra un tercero. Ahora hay tres facturando a la vez y el bloqueo no ha «fallado» en ningún momento visible.

Se arregla marcando el bloqueo con un valor único y borrando solo si sigue siendo el tuyo, de forma atómica. En Redis eso significa un script Lua, porque comprobar y borrar en dos comandos tiene la misma carrera que intentabas evitar:

php · BloqueoConDueño.php 
<?php

declare(strict_types=1);

final class BloqueoConDueno
{
    private const SOLTAR_SI_ES_MIO = <<<'LUA'
        if redis.call("get", KEYS[1]) == ARGV[1] then
            return redis.call("del", KEYS[1])
        end
        return 0
        LUA;

    public function tomar(string $clave, int $segundos): ?string
    {
        $testigo = bin2hex(random_bytes(16));

        if (!$this->redis->set($clave, $testigo, ['NX', 'EX' => $segundos])) {
            return null;
        }

        return $testigo;
    }

    public function soltar(string $clave, string $testigo): void
    {
        $this->redis->eval(self::SOLTAR_SI_ES_MIO, [$clave, $testigo], 1);
    }
}

Fallo 2: el que no se arregla #

El testigo evita que borres el bloqueo de otro, pero no evita que dos procesos se crean dueños a la vez. Y esto no tiene arreglo con más código:

1 El proceso A coge el bloqueo60 s de caducidad
2 A se queda parado 70 sÉl no lo sabe: para él no ha pasado el tiempo
3 B coge el bloqueo legítimamenteEmpieza a facturar
4 A despierta y sigue facturandoConvencido de que tiene el bloqueo. Dos a la vez.

Ningún componente ha fallado. El bloqueo hizo su trabajo. Y aun así hubo dos.

La razón de fondo es de la primera lección: los relojes y las pausas no son fiables. Un proceso no puede saber cuánto tiempo estuvo detenido, así que no puede saber si su bloqueo sigue vivo. Redlock, el algoritmo que usa varios Redis independientes, tampoco resuelve esto — su discusión pública es un clásico del tema— porque el problema no está en el almacén del bloqueo, está en el que lo sostiene.

La única salida real: que el recurso también se defienda

El bloqueo entrega un número que crece con cada concesión (un token de barrera). El recurso —tu base de datos— guarda el último número que aceptó y rechaza cualquier escritura con uno menor. Así, cuando A despierta con el token 7 y el recurso ya vio el 8, su escritura se rechaza. Es la única forma de estar seguro, y exige cooperación del recurso.

Casi siempre hay una salida mejor #

Antes de montar nada de lo anterior, merece la pena mirar si el problema se puede reformular. Casi siempre se puede, y sale más barato:

En vez de bloquear…Haz esto
Para que no se procese dos vecesQue la operación sea idempotente: da igual cuántas veces corra
Para que solo un worker toque un pedidoParticiona por clave: los mensajes de ese pedido van al mismo consumidor
Para actualizar un contador sin perder incrementosUPDATE ... SET n = n + 1: la base de datos ya lo serializa
Para evitar dos escrituras concurrentesBloqueo optimista: una columna de versión y reintento si cambió
Para que un cron no se solape consigo mismoUn bloqueo local en el fichero, si solo corre en una máquina

El bloqueo optimista de la cuarta fila merece un momento: en vez de impedir que otro entre, dejas que entren los dos y detectas el conflicto al escribir. Un UPDATE ... WHERE version = 3 que afecta a cero filas te dice que alguien se te adelantó, y reintentas con el dato fresco. Sin bloqueos, sin caducidades y sin el problema de arriba.

Cuándo aplicarlo #

Un bloqueo con caducidad basta cuando…

  • Es una optimización: evitar trabajo duplicado, no corrupción
  • Que se ejecute dos veces es molesto pero no rompe nada
  • Es un cron pesado y lo que quieres es no gastar el doble

Necesitas algo más fuerte cuando…

  • Una ejecución doble corrompe datos o cobra dos veces
  • No puedes acotar cuánto tarda la sección crítica
  • La corrección depende de que sea uno y solo uno
  • → Token de barrera con recurso cooperativo, o consenso de verdad

Resumen #

Lo que te llevas

  • Soltar el bloqueo sin comprobar que sigue siendo tuyo borra el de otro y encadena una cascada de solapamientos invisibles.
  • Comprobar y borrar tiene que ser atómico: en Redis, un script Lua, porque en dos comandos vuelve la carrera.
  • El fallo que no se arregla con código: una pausa larga hace que dos procesos se crean dueños a la vez sin que nada haya fallado.
  • La única garantía real es el token de barrera: el recurso guarda el último número aceptado y rechaza los anteriores.
  • Casi siempre hay salida mejor: idempotencia, particionar por clave o bloqueo optimista con una columna de versión.
