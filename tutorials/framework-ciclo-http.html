El ciclo HTTP de un framework: de nginx al controlador y vuelta

¿Qué pasa exactamente entre que el navegador envía una petición y tu controlador la recibe? El recorrido completo: nginx, PHP-FPM, el front controller, el Kernel, el router, los eventos y la respuesta. Sin magia.

Cuando usas un framework a diario puedes vivir sin saber qué hay detrás. Pero cuando algo falla en un lugar inesperado, cuando necesitas intervenir en el ciclo o cuando lees código del framework, ese conocimiento vale más que cualquier otra cosa.

Antes de PHP: nginx y FPM #

El recorrido empieza antes de que tu código exista. El navegador abre una conexión TCP al servidor, envía la petición HTTP y nginx la recibe. Nginx no ejecuta PHP: actúa como proxy inverso y reenvía la petición a PHP-FPM a través del protocolo FastCGI.

1 NavegadorHTTP/2 sobre TCP
2 nginxSirve estáticos, reenvía el resto a FPM
3 PHP-FPMPool de workers, asigna uno libre
4 index.phpEl front controller: el único punto de entrada

Nginx gestiona conexiones; FPM gestiona procesos PHP. Tu código empieza en index.php.

PHP-FPM mantiene un pool de procesos PHP siempre listos. Cuando llega una petición, asigna un worker libre — un proceso que ya tiene PHP cargado en memoria — y le pasa la petición vía FastCGI. Cuando el worker termina, vuelve al pool disponible para la siguiente petición.

Esto explica algo importante sobre PHP: cada petición empieza desde cero. No hay estado compartido entre peticiones en el mismo proceso (salvo que uses APCu o similar). La memoria del proceso se limpia al acabar. Es la diferencia fundamental con los modelos de servidor persistente (Go, Node, Java) que ya viste en el tutorial sobre procesos e hilos.

El front controller #

Nginx está configurado para reenviar todas las peticiones que no sean ficheros estáticos al mismo fichero PHP: public/index.php. Da igual que el navegador pida /users, /orders/42 o /api/health: siempre llega a index.php.

bash · nginx.conf (fragmento) 
location / {
    # Si el fichero o directorio existe, sírvelo directamente
    try_files $uri $uri/ /index.php$is_args$args;
}

location ~ \.php$ {
    fastcgi_pass php-fpm:9000;
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    include fastcgi_params;
}

Este es el patrón Front Controller: un único punto de entrada que centraliza el arranque y delega el procesamiento. La alternativa —un fichero PHP por URL— era el enfoque anterior a los frameworks: users.php, orders.php, login.php. El front controller lo unifica todo.

php · public/index.php (Symfony simplificado) 
<?php

use App\Kernel;
use Symfony\Component\HttpFoundation\Request;

require_once dirname(__DIR__) . '/vendor/autoload.php';

$kernel   = new Kernel($_SERVER['APP_ENV'], (bool) $_SERVER['APP_DEBUG']);
$request  = Request::createFromGlobals();
$response = $kernel->handle($request);
$response->send();
$kernel->terminate($request, $response);

Todo el framework cabe en cinco líneas visibles: arrancar el kernel, crear la Request a partir de los superglobales PHP ($_GET, $_POST, $_SERVER…), procesarla, enviar la respuesta y llamar al terminate para limpiar (cerrar conexiones, flush de logs).

El Kernel #

El Kernel::handle() es el corazón del framework. Implementa el patrón Template Method: define la secuencia fija y delega cada paso. En Symfony, la secuencia real de HttpKernel::handle() es:

1 kernel.requestEvento: sesión, firewall, locale…
2 RouterResuelve URL → controlador + parámetros
3 kernel.controllerEvento: security voters, param conversion…
4 ControladorTu código: lógica de negocio, devuelve Response
5 kernel.responseEvento: cache headers, compresión…
6 Response → clientesend() escribe headers y body

El Kernel orquesta la secuencia; los eventos son los puntos de extensión.

Si en cualquier punto del ciclo se lanza una excepción, el Kernel la captura y dispara el evento kernel.exception. Los listeners de ese evento (el ExceptionListener de Symfony, tu propio handler) convierten la excepción en una respuesta HTTP apropiada — 404, 500, o lo que toque. Si ningún listener la maneja, el Kernel lanza de nuevo la excepción.

Routing: URL a controlador #

El router recibe la petición y devuelve un array de atributos: qué controlador ejecutar, qué parámetros extrajo de la URL y cualquier metadato adicional de la ruta.

php · Symfony routing 
<?php

// Symfony: el atributo #[Route] se lee en tiempo de compilación del contenedor
#[Route('/orders/{id}', name: 'order_show', methods: ['GET'])]
public function show(int $id): Response { /* ... */ }

// El router compila todas las rutas en una estructura de árbol (RadixTree)
// y la cachea. En producción no hay regex en caliente: es una búsqueda en árbol.

// Lo que el router devuelve para GET /orders/42:
// [
//   '_controller' => 'App\Controller\OrderController::show',
//   '_route'      => 'order_show',
//   'id'          => '42',
// ]

En Laravel el mecanismo es equivalente: las rutas definidas en routes/web.php o routes/api.php se compilan en una estructura interna. El Router de Laravel también cachea el árbol de rutas para producción (php artisan route:cache).

Por qué route:cache es importante

Sin caché, el router lee y parsea los atributos #[Route] de cada controlador en cada petición usando Reflection — lento. Con caché, lee un fichero PHP compilado. En producción, siempre php artisan route:cache (Laravel) o el warm-up del contenedor en Symfony.

Eventos del ciclo HTTP #

Los eventos del Kernel son el mecanismo de extensión principal. Cada punto crítico del ciclo dispara un evento; cualquier código del proyecto (o de un bundle/package) puede escucharlo sin modificar el núcleo.

Evento SymfonyEquivalente LaravelCuándoPara qué
kernel.request handle en Middleware Antes del routing Iniciar sesión, detectar locale, comprobar mantenimiento
kernel.controller Route middleware Controlador resuelto, antes de ejecutarlo Security voters, conversión de parámetros, rate limiting
kernel.view — El controlador devolvió algo que no es Response Serializar arrays a JSON, renderizar vistas
kernel.response Terminate middleware Response creada, antes de enviarla Añadir headers de caché, compresión, CORS
kernel.exception Exception handler Excepción no capturada Convertir excepción en respuesta HTTP apropiada
kernel.terminate Terminable middleware Respuesta ya enviada al cliente Flush de logs, métricas, limpieza post-petición

Resolución del controlador #

Una vez el router ha devuelto _controller = 'App\Controller\OrderController::show', el framework necesita instanciar el controlador e inyectarle sus dependencias. Aquí entra el contenedor DI.

php · ControllerResolver (simplificado) 
<?php

// El ControllerResolver obtiene el callable del controlador
$controllerCallable = $resolver->getController($request);

// El ArgumentResolver resuelve los argumentos del método
// Combina parámetros de ruta, query string, body, servicios del contenedor...
$arguments = $argumentResolver->getArguments($request, $controllerCallable);

// La llamada real al controlador
$response = $controllerCallable(...$arguments);

El ArgumentResolver es lo que hace funcionar la "magia" de los controladores de Symfony: puedes declarar el tipo de un argumento como OrderRepository $repository y el framework lo inyecta desde el contenedor; puedes declarar int $id y lo extrae de la ruta; puedes declarar Request $request y lo pasa directamente. Cada estrategia de resolución es un ArgumentValueResolverInterface — Strategy aplicado.

php · Controlador con inyección automática 
<?php

declare(strict_types=1);

class OrderController
{
    // El contenedor inyecta OrderRepository en el constructor (autowiring)
    public function __construct(
        private readonly OrderRepository $orders
    ) {}

    #[Route('/orders/{id}', methods: ['GET'])]
    public function show(
        int $id,            // ArgumentResolver: lo extrae de la ruta
        Request $request    // ArgumentResolver: lo pasa directamente
    ): Response {
        $order = $this->orders->findById($id);

        if ($order === null) {
            throw new NotFoundHttpException("Order {$id} not found");
        }

        return $this->json($order);
    }
}

La respuesta de vuelta #

El controlador devuelve una Response (o algo que el kernel.view convierte en una). El Kernel dispara kernel.response para que los listeners añadan headers, y luego llama a $response->send().

php · Response::send() (simplificado) 
<?php

public function send(): static
{
    $this->sendHeaders();  // HTTP/1.1 200 OK + todos los headers
    $this->sendContent();  // el body (echo del contenido)

    if (\function_exists('fastcgi_finish_request')) {
        fastcgi_finish_request(); // cierra la conexión con FPM, libera el worker
    }

    return $this;
}

fastcgi_finish_request() es importante: cierra la conexión con el cliente y libera el worker de FPM antes de que PHP termine de ejecutar. Lo que viene después (kernel.terminate: logs, métricas, emails en cola) se ejecuta sin que el usuario espere. Es el mecanismo que hace posible procesar trabajo post-petición sin afectar al tiempo de respuesta percibido.

kernel.terminate: trabajo post-petición gratuito

Si envías emails, escribes logs detallados o actualizas analíticas en kernel.terminate, el usuario ya recibió su respuesta. El coste de esas operaciones no aparece en el tiempo de respuesta. Para trabajo más pesado o que no puede fallar, las colas asíncronas (Messenger/Queue) son la alternativa correcta.

Cuándo aplicarlo

Aplícalo cuando…

  • Debugueas un middleware que no se ejecuta o un evento del kernel que no dispara.
  • Optimizas el rendimiento de cada request e intervenir en el pipeline marca la diferencia.
  • Implementas seguridad o comportamiento transversal a nivel de pipeline HTTP.

No lo uses cuando…

  • Desarrollas features de negocio normales: basta con conocer rutas, controladores y servicios.
  • Este nivel de detalle no aporta nada a la tarea; la abstracción del framework ya es suficiente.

Resumen #

Lo que te llevas

  • Nginx reenvía todas las peticiones no-estáticas al front controller (index.php). PHP-FPM mantiene workers listos; cada petición arranca desde cero.
  • El Kernel es un Template Method: fija la secuencia (request→router→controller→response) y delega cada paso. Las excepciones fluyen a kernel.exception.
  • El router compila rutas en una estructura de árbol cacheada. En producción no hay regex en caliente: es una búsqueda eficiente en árbol compilado.
  • Los eventos del kernel (kernel.request, kernel.controller, kernel.response…) son Observer: puntos de extensión sin tocar el núcleo.
  • El ArgumentResolver inyecta parámetros de ruta, Request y servicios del contenedor en el método del controlador mediante Strategy.
  • fastcgi_finish_request() cierra la conexión con el cliente antes de kernel.terminate: el trabajo post-petición no afecta al tiempo de respuesta percibido.
