gRPC: RPC con contrato y streaming

gRPC es llamar a un método de otro proceso como si fuera local, con un contrato verificado y sobre HTTP/2. Suena a volver a las RPC de los noventa y hay una diferencia importante: esta vez el contrato es explícito y nadie finge que la red no existe.

La comparación general ya está escrita

Cuándo elegir REST, RPC o GraphQL se decide en REST vs RPC vs GraphQL, del curso de APIs. Aquí vamos a lo concreto de gRPC: qué aporta como protocolo y dónde duele.

El contrato genera el código #

Defines el servicio y sus mensajes en un fichero, y un generador produce el cliente y el esqueleto del servidor en cada lenguaje. Ese paso es lo que cambia la experiencia: no escribes clientes HTTP ni parseas respuestas.

ini · precios.proto 
service Precios {
  rpc Consultar (PeticionPrecio) returns (RespuestaPrecio)
  rpc ConsultarVarios (stream PeticionPrecio) returns (stream RespuestaPrecio)
}

message PeticionPrecio {
  string id_producto = 1
}

message RespuestaPrecio {
  int64 centimos = 1
  string moneda = 2
}
ModoFormaPara qué
UnarioPetición → respuestaEl caso normal, como una llamada HTTP
Servidor en flujoPetición → muchas respuestasSuscribirse a actualizaciones
Cliente en flujoMuchas peticiones → una respuestaSubir datos por lotes
BidireccionalLos dos a la vezConversación continua entre servicios

El streaming viene de serie porque HTTP/2 multiplexa: no hay que montar nada aparte, es otra firma en el mismo fichero. Esa es la diferencia práctica más grande frente a una API REST, donde mantener un flujo abierto exige SSE o WebSockets.

Qué aporta de verdad #

A favor

  • Contrato verificado: un campo mal escrito no compila
  • Clientes generados en todos los lenguajes del equipo
  • Streaming sin infraestructura extra
  • Menos CPU y menos bytes que JSON
  • Plazos y cancelación integrados en el protocolo

En contra

  • No se puede llamar desde un navegador sin un proxy
  • No se depura con curl ni mirando la pestaña de red
  • Cachear por HTTP deja de aplicar: todo son POST
  • Otra herramienta más: generadores en el pipeline
  • El soporte en PHP es de segunda: extensión C y ergonomía pobre

Los plazos son lo mejor de gRPC y casi nadie lo cuenta

El cliente manda cuánto está dispuesto a esperar, y ese plazo viaja con la llamada a través de toda la cadena. Si el servicio A da 2 s y su llamada a B ya consumió 1,5 s, B recibe 500 ms de plazo, no un timeout suyo inventado. Es el presupuesto de latencia de la lección de rendimiento, implementado en el protocolo.

La realidad en PHP #

Conviene ser honesto: PHP es un ciudadano de segunda en gRPC. El cliente necesita una extensión de C, y hacer de servidor gRPC en PHP no es viable con el modelo de FPM, porque el proceso muere al terminar la petición y no puede mantener flujos abiertos.

1 PHP como clienteFunciona: extensión instalada y clases generadas
2 PHP como servidor unarioPosible con RoadRunner o similar, no con FPM
3 PHP con streamingEn la práctica, no. Ese servicio se escribe en Go

Es una razón legítima para que un servicio concreto no sea PHP, y una mala razón para reescribirlo todo.

Desde el navegador hace falta un proxy

Los navegadores no exponen el control de HTTP/2 que gRPC necesita. Se usa gRPC-Web con un proxy que traduce, y en esa traducción se pierden modos de streaming. Si tu consumidor principal es una interfaz web, gRPC te está complicando la vida para nada.

Cuándo aplicarlo #

gRPC cuando…

  • Es comunicación entre servicios propios, no con navegadores
  • Hay varios lenguajes y quieres un contrato único
  • El volumen justifica el ahorro de CPU y bytes
  • Necesitas streaming bidireccional de verdad

REST sobre JSON cuando…

  • La consume un navegador o un cliente externo
  • Quieres aprovechar la caché HTTP
  • Valoras poder depurar con curl
  • Tu stack es PHP y no quieres piezas de otro lenguaje

Resumen #

Lo que te llevas

  • El contrato genera el código de las dos partes: un campo mal escrito deja de ser un bug en producción y pasa a ser un error de compilación.
  • El streaming viene de serie porque HTTP/2 multiplexa: es otra firma en el mismo fichero, no infraestructura aparte.
  • Los plazos viajan con la llamada por toda la cadena: es el presupuesto de latencia implementado en el protocolo.
  • Desde el navegador hace falta un proxy y se pierden modos de streaming: si tu consumidor es una web, gRPC estorba.
  • PHP sirve como cliente y no como servidor con streaming: es una razón legítima para que un servicio concreto sea Go.
