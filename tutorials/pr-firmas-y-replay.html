Firmar y verificar: HMAC, replay y secretos

Tu endpoint de webhooks está en internet y cualquiera puede llamarlo. Sin firma, un POST con un JSON bien formado basta para que des un pedido por pagado. Verificar la firma no es opcional, y hay cuatro detalles donde la implementación se estropea sin que se note.

HMAC, en una frase #

Emisor y receptor comparten un secreto. El emisor calcula un hash del cuerpo mezclado con ese secreto y lo manda en una cabecera; el receptor repite la operación y compara. Si coinciden, el mensaje viene de quien dice y nadie lo ha tocado.

php · verificar una firma 
<?php

declare(strict_types=1);

final class VerificadorDeFirma
{
    private const MARGEN_SEGUNDOS = 300;

    public function esValida(string $cuerpo, string $firma, int $marcaDeTiempo): bool
    {
        if (abs(time() - $marcaDeTiempo) > self::MARGEN_SEGUNDOS) {
            return false;
        }

        $esperada = hash_hmac('sha256', $marcaDeTiempo . '.' . $cuerpo, $this->secreto);

        return hash_equals($esperada, $firma);
    }
}

La última fila es la que más veces rompe una integración

Si el framework parsea el JSON antes de que veas el cuerpo, y tú vuelves a serializarlo para firmar, el orden de las claves o el escapado de los caracteres pueden ser distintos y el hash no cuadra nunca. Hay que leer el cuerpo tal cual llegó, antes de cualquier transformación.

La firma no impide la repetición #

Una firma válida lo es para siempre. Si alguien captura una petición legítima —«reembolsa 50 € a esta cuenta»— y la reenvía diez veces, las diez firmas son correctas, porque el mensaje es idéntico.

1 Marca de tiempo dentro de la firmaCon un margen corto: la petición caduca
2 Identificador único registradoUn evento ya visto se descarta aunque su firma sea válida
3 La ventana de repetición se cierraY el registro solo tiene que guardar unos minutos

Es la misma deduplicación de la lección anterior, cumpliendo ahora una función de seguridad además de una de corrección.

Rotar el secreto sin cortar #

Un secreto compartido acaba teniendo que cambiarse, y si rotarlo implica que las firmas dejen de validar durante unos minutos, no se va a hacer. La solución es la misma de siempre: aceptar dos secretos a la vez durante la transición.

El receptor prueba con el actual y, si falla, con el anterior. Cuando el emisor confirma que ya firma con el nuevo, se retira el viejo. Por eso los proveedores serios mandan varias firmas en la misma cabecera: están rotando y tú ni te enteras.

Un secreto por integración, nunca uno compartido

Si usas el mismo secreto con todos tus clientes, cualquiera de ellos puede firmar mensajes haciéndose pasar por otro. Y rotarlo obliga a coordinar con todos a la vez. Uno por integración cuesta lo mismo de gestionar y acota el daño de una filtración a un solo cliente.

Cuando HMAC no basta #

Su límite estructural es que el secreto lo tienen los dos: el receptor puede fabricar mensajes indistinguibles de los del emisor. Para la mayoría de las integraciones da igual — pero si necesitas no repudio, que el emisor no pueda negar que lo mandó, hace falta firma asimétrica: el emisor firma con su clave privada y tú verificas con la pública.

HMAC basta cuando…

  • Es una integración bilateral y os fiais el uno del otro
  • Lo que quieres es autenticar el origen y detectar manipulación
  • Simplicidad y velocidad importan

Firma asimétrica cuando…

  • Necesitas no repudio con valor probatorio
  • Hay muchos receptores y no quieres compartir secreto con todos
  • Hay requisitos legales o de cumplimiento

Y una regla que se salta mucha gente

La firma se verifica antes de deserializar el cuerpo, no después. Parsear JSON de un origen no autenticado es darle trabajo a tu servidor a cambio de nada, y expone tu parser a entradas maliciosas. Primero se comprueba quién llama, y luego se mira qué dice.

Cuándo aplicarlo #

Firma obligatoria cuando…

  • El endpoint está expuesto en internet
  • El evento desencadena algo con consecuencias: cobros, envíos, permisos
  • El emisor es un tercero
  • Siempre, básicamente: el coste es una función de cuatro líneas

Puede bastar otra cosa cuando…

  • Es tráfico interno con TLS mutuo, que ya autentica
  • Hay una lista blanca de IP fiable y el evento es informativo
  • Es un entorno de pruebas sin datos reales

Resumen #

Lo que te llevas

  • Se compara con hash_equals: una comparación normal termina en el primer byte distinto y ese tiempo filtra información.
  • Se firma el cuerpo en crudo: deserializar y volver a serializar cambia los bytes y el hash no cuadra nunca.
  • Una firma válida lo es para siempre: contra la repetición hacen falta marca de tiempo dentro de la firma e identificador registrado.
  • Aceptar dos secretos durante la transición es lo que hace posible rotar sin cortar. Y uno por integración, nunca compartido.
  • Se verifica antes de deserializar: parsear JSON de un origen no autenticado es trabajo gratis para un atacante.
