Caché HTTP: ETag, Cache-Control y CDN

La caché más rápida es la petición que no se hace. HTTP lleva desde 1997 con un sistema de caché completo y estandarizado que todos los navegadores y todas las CDN implementan, y que la mayoría de las aplicaciones desaprovecha por poner mal cuatro cabeceras.

Esto amplía, no repite

Los fundamentos del protocolo están en HTTP a fondo. Aquí interesa el uso práctico: qué directiva pones en cada tipo de respuesta y por qué una CDN se comporta distinto que un navegador.

Frescura y validación #

El modelo de HTTP responde a dos preguntas distintas, y confundirlas es la fuente de casi todos los errores:

Frescura: ¿puedo usarlo sin preguntar?

  • Cache-Control: max-age=3600
  • Ahorra la petición entera
  • Cero latencia: no sale de la máquina
  • El precio: no puedes cambiar de opinión

Validación: ¿sigue siendo válido?

  • ETag y If-None-Match
  • Ahorra el cuerpo, no la petición
  • Una ida y vuelta, pero un 304 vacío
  • Siempre correcto: preguntas cada vez
php · responder con ETag 
<?php

$respuesta = new JsonResponse($producto);

$respuesta->setEtag(md5($producto->actualizadoEn()->format('U') . $producto->version()));
$respuesta->setPublic();
$respuesta->setMaxAge(60);

if ($respuesta->isNotModified($peticion)) {
    return $respuesta;
}

return $respuesta;

isNotModified() compara el ETag con el If-None-Match que mandó el cliente y, si coinciden, vacía el cuerpo y devuelve un 304. El ahorro es de ancho de banda y de serialización, no de latencia: la petición se hace igual.

El ETag no debe calcularse sobre el cuerpo

Si haces md5($json) tienes que producir el JSON entero para saber si hace falta enviarlo: te ahorras el ancho de banda y no el trabajo. Calcúlalo sobre algo barato que cambie con el dato —la fecha de actualización, un número de versión— y podrás devolver el 304 sin tocar la base de datos.

Las directivas que de verdad usas #

DirectivaQué dice
publicCualquier caché puede guardarlo, incluida la CDN
privateSolo el navegador del usuario. Obligatorio si hay datos personales
no-storeNo guardar en ningún sitio. Para lo sensible de verdad
no-cacheGuardar sí, pero revalidar siempre antes de usar. El nombre engaña
max-age=NSegundos que es fresco para el navegador
s-maxage=NLo mismo, pero para cachés compartidas. Gana sobre max-age en la CDN
stale-while-revalidate=NSirve viejo hasta N segundos mientras refresca por detrás
immutableNo revalides nunca. Para ficheros con hash en el nombre

no-cache no significa «no caches»

Significa «guárdalo, pero pregúntame antes de servirlo». El que no guarda nada es no-store. Confundirlos en una respuesta con datos bancarios es un incidente de seguridad, no una errata: la respuesta acaba en el disco del navegador y en cualquier proxy del camino.

La combinación que resuelve la mayoría de las APIs de lectura pública es corta:

bash · la cabecera que quieres 
Cache-Control: public, max-age=60, s-maxage=600, stale-while-revalidate=86400

El navegador lo considera fresco un minuto; la CDN, diez. Y durante un día entero después de caducar, la CDN puede seguir sirviendo lo viejo mientras refresca por detrás: si tu servidor se cae, los usuarios no se enteran.

Vary: la cabecera que se olvida #

Una caché indexa por URL. Si tu respuesta depende de algo que no está en la URL —el idioma en Accept-Language, el formato en Accept, si el usuario ha iniciado sesión— tienes que declararlo, o la caché servirá la versión equivocada a todo el mundo.

bash · declarar de qué depende 
Vary: Accept-Language, Accept-Encoding

Nunca Vary: User-Agent

Hay millones de cadenas de user agent distintas, así que estarías creando una entrada de caché por navegador y versión: la tasa de acierto se desploma a casi cero y la CDN deja de servirte para nada. Si necesitas variar por dispositivo, normaliza a dos o tres valores en el borde, no varíes por la cadena completa.

Lo que cambia con una CDN delante #

Una CDN es una caché compartida repartida por el mundo. Eso trae dos ventajas y una responsabilidad:

Las ventajas son la cercanía —servir desde 20 ms en vez de 150— y la agregación: mil usuarios pidiendo lo mismo se convierten en una sola petición a tu servidor. Con s-maxage alto, tu origen atiende una fracción minúscula del tráfico real.

La responsabilidad es que es compartida. Cualquier respuesta marcada public que contenga algo de un usuario concreto se le servirá al siguiente. La regla es simple y no admite excepciones: si la respuesta depende de quién pregunta, va private, y si es sensible, no-store.

Y una última nota operativa: purgar no es instantáneo. Una purga tarda en propagarse a todos los nodos, así que no puedes contar con ella para corregir un error inmediatamente. Para contenido que cambia, la alternativa fiable es no purgar nunca: poner un hash en el nombre del fichero y cambiar la URL, que invalida por construcción.

Cuándo aplicarlo #

Caché HTTP cuando…

  • La respuesta es igual para muchos usuarios
  • Son activos estáticos: ahí es obligatorio, con hash e immutable
  • Es una API de lectura pública: catálogo, precios, contenidos
  • Quieres que un pico no llegue a tu origen

private o no-store cuando…

  • La respuesta lleva datos de una persona concreta
  • Es información financiera o de salud
  • Es una respuesta a una escritura
  • Ante la duda: el fallo por defecto debe ser no cachear

Resumen #

Lo que te llevas

  • Frescura ahorra la petición entera; validación con ETag ahorra solo el cuerpo. Son cosas distintas y se combinan.
  • Calcula el ETag sobre algo barato, no sobre el cuerpo: si tienes que generar el JSON para saber si enviarlo, no has ahorrado trabajo.
  • no-cache guarda y revalida; el que no guarda es no-store. Confundirlos con datos sensibles es un incidente.
  • Si la respuesta depende de algo que no está en la URL, decláralo en Vary. Nunca por User-Agent.
  • Purgar una CDN no es instantáneo: para contenido que cambia, poner un hash en la URL invalida por construcción.
