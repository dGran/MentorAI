Captura de errores con Sentry

Los logs te dicen que algo falló. Sentry te dice exactamente qué, dónde, cuántas veces y para quién — y agrupa ocurrencias del mismo error para que no te inunden la bandeja. Es la diferencia entre enterarte de un bug por un usuario enfadado y enterarte tú antes.

Sentry es un rastreador de errores: captura excepciones no controladas (y las que tú quieres capturar explícitamente), las agrupa, las enriquece con contexto y las presenta de forma que puedas priorizar y diagnosticar. A diferencia de los logs, está optimizado específicamente para excepciones en producción.

Qué es Sentry y qué resuelve #

El problema con los errores en producción es doble: primero, hay que detectarlos antes de que los usuarios los reporten; segundo, hay que diagnosticarlos rápido. Un stack trace en un log de texto ayuda con lo segundo pero no con lo primero — un log no te notifica, no cuenta cuántos usuarios se vieron afectados ni te muestra la tendencia.

Sentry resuelve los dos: un hook de excepción que captura automáticamente cualquier excepción no controlada, la envía a Sentry con su stack trace, contexto y metadatos, y la agrupa con otras ocurrencias del mismo error. Ves en tiempo real cuántas veces ocurre, si está empeorando o mejorando y qué usuarios se vieron afectados.

Excepción en producción
↓ hook automático
SDK envía evento a Sentry (async, no bloquea la respuesta)
↓
Sentry agrupa con el issue existente (o crea uno nuevo)
↓
Notificación al equipo + dashboard actualizado

Integración del SDK en PHP #

La instalación es un composer install y una llamada de inicialización:

bash · instalar el SDK 
composer require sentry/sentry-php
php · inicialización en el bootstrap de la aplicación 
\Sentry\init([
    'dsn'         => $_ENV['SENTRY_DSN'],
    'environment' => $_ENV['APP_ENV'],
    'release'     => $_ENV['APP_VERSION'] ?? null,
    'traces_sample_rate' => 0.1,
]);

Con esto, todas las excepciones no controladas se envían automáticamente. El dsn (Data Source Name) es la URL de tu proyecto en Sentry — vive como variable de entorno, nunca hardcodeado. environment separa los errores de producción de los de staging. release permite ver si un error apareció o desapareció en una versión concreta.

En Symfony el paquete sentry/sentry-symfony lo integra como bundle; en Laravel existe sentry/sentry-laravel. Ambos registran el hook automáticamente y exponen configuración vía .env.

Para capturar excepciones explícitamente — errores de negocio que quieres rastrear aunque estén controlados —:

php · captura explícita con contexto 
try {
    $this->gateway->charge($order);
} catch (GatewayTimeoutException $exception) {
    \Sentry\captureException($exception);
    throw new PaymentUnavailableException($exception);
}

Agrupación de errores: fingerprinting #

Si un bug dispara 500 excepciones por hora, no quieres 500 notificaciones: quieres un único issue que se actualiza con el contador. Sentry agrupa ocurrencias del mismo error mediante fingerprinting: un algoritmo que calcula una huella a partir del tipo de excepción, el mensaje y el stack trace.

El algoritmo por defecto funciona bien la mayoría de veces. Los casos donde falla son los mensajes que incluyen datos variables:

Mensajes con datos variables fragmentan los issues

throw new NotFoundException("Order 8421 not found") y throw new NotFoundException("Order 8422 not found") producen dos issues distintos aunque son el mismo bug. El mensaje debe ser constante: "Order not found", con el id en el contexto de la excepción.

Cuando necesitas agrupar de forma personalizada, Sentry permite definir el fingerprint explícitamente antes de capturar:

php · fingerprint personalizado vía beforeSend 
\Sentry\init([
    'dsn'        => $_ENV['SENTRY_DSN'],
    'before_send' => function (\Sentry\Event $event): ?\Sentry\Event {
        $exception = $event->getExceptions()[0] ?? null;

        if ($exception?->getType() === GatewayTimeoutException::class) {
            $event->setFingerprint(['gateway-timeout']);
        }

        return $event;
    },
]);

Contexto de usuario y tags #

Saber que se lanzó una excepción es útil; saber que afectó a 47 usuarios distintos y que todos son del plan premium es más útil. Sentry enriquece cada evento con el contexto que tú le añadas.

El contexto de usuario se configura una vez al inicio de la petición, habitualmente en el middleware de autenticación:

php · identificar al usuario en Sentry 
\Sentry\configureScope(function (\Sentry\State\Scope $scope) use ($user): void {
    $scope->setUser([
        'id'    => $user->id(),
        'email' => $user->email(),
        'plan'  => $user->plan(),
    ]);
    $scope->setTag('tenant', $user->tenantSlug());
});

Los tags son campos indexados que permiten filtrar issues en Sentry: "muéstrame solo los errores del tenant acme" o "cuántos issues afectan al plan enterprise". Úsalos para los atributos de alta cardinalidad baja (plan, entorno, versión, región) — no para datos únicos por petición como el request_id, que va en el contexto.

Breadcrumbs: el camino hasta el error #

Muchas veces el stack trace no basta para entender un error: sabes dónde explotó pero no qué hizo el sistema los segundos previos. Los breadcrumbs son una pista de eventos ordenados cronológicamente que Sentry adjunta al issue — las últimas acciones antes del error.

Sentry registra breadcrumbs automáticamente para algunos eventos (queries de Doctrine, peticiones HTTP de Guzzle, logs de Monolog si integras el handler). Puedes añadir los tuyos propios:

php · breadcrumb manual en un punto clave del flujo 
\Sentry\addBreadcrumb(new \Sentry\Breadcrumb(
    level:    \Sentry\Breadcrumb::LEVEL_INFO,
    type:     \Sentry\Breadcrumb::TYPE_DEFAULT,
    category: 'checkout',
    message:  'Payment initiated',
    metadata: ['order_id' => $order->id(), 'amount_cents' => $order->totalCents()],
));

Cuando el error llega, Sentry muestra la secuencia de breadcrumbs: "usuario aplicó cupón → inició pago → llamada al gateway → timeout → excepción". En cinco segundos entiendes el flujo completo sin reproducir el problema.

Sentry no reemplaza los logs

Sentry está optimizado para excepciones y su contexto inmediato. Los logs siguen siendo el lugar de los eventos normales de operación (petición procesada, job completado) y del flujo de negocio detallado. Usados juntos: Sentry te avisa del error y te da el contexto inmediato; los logs te dan el historial completo.

Cuándo aplicarlo #

Úsalo cuando…

  • Necesitas capturar excepciones no manejadas con stack trace completo y contexto de usuario.
  • Quieres alertas en tiempo real cuando aparece un tipo de error nuevo en producción.
  • Necesitas saber exactamente en qué línea de código ocurrió el fallo.

No lo uses cuando…

  • Necesitas correlacionar errores con métricas de negocio (latencia, throughput): ahí Prometheus y Grafana.
  • El sistema tiene múltiples servicios y necesitas trazas distribuidas: ahí Datadog o New Relic.
  • Quieres monitorizar tendencias de rendimiento; Sentry rastrea errores, no degradación gradual.

Resumen #

Lo que te llevas

  • Sentry captura excepciones automáticamente, las agrupa y notifica. El DSN va en variable de entorno; environment y release separan contextos y versiones.
  • Fingerprinting agrupa ocurrencias del mismo error. Mensajes con datos variables fragmentan issues — el mensaje debe ser constante, los datos van en el contexto.
  • Contexto de usuario al inicio de la petición: cuántos usuarios afectados, de qué plan o tenant. Tags para atributos de cardinalidad baja.
  • Breadcrumbs: la secuencia de eventos previos al error. Sentry registra algunos automáticamente; añade los tuyos en los puntos clave del flujo.
  • Sentry y los logs son complementarios: Sentry para excepciones y su contexto inmediato; logs para el historial de operación completo.
