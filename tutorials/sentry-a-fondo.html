Sentry a fondo

Sentry hace más que capturar excepciones: sabe en qué versión apareció un error, puede medir la latencia de tus endpoints como trazas distribuidas y te deja configurar alertas que avisas cuando algo empeora. El reto es no ahogarte en notificaciones.

Este tutorial asume que ya tienes el SDK integrado del tutorial anterior y te adentra en las funcionalidades que convierten Sentry en una herramienta de observabilidad real, no solo en un buzón de excepciones.

Releases y regresiones #

Un release en Sentry es una versión identificada de tu aplicación. Cuando configuras el campo release en la inicialización del SDK, Sentry puede decirte en qué versión apareció un issue por primera vez, en cuáles se vio y si en la versión actual ya no ocurre.

La funcionalidad más valiosa es la detección de regresiones: si marcas un issue como resuelto y vuelve a aparecer en una versión posterior, Sentry lo reabre automáticamente y notifica. Sin releases, un issue resuelto puede volver sin que nadie se entere.

bash · crear release desde CI/CD (sentry-cli) 
sentry-cli releases new "$VERSION"
sentry-cli releases set-commits "$VERSION" --auto
sentry-cli releases finalize "$VERSION"

El set-commits asocia commits al release: Sentry puede mostrar qué commits entraron en la versión donde apareció el error — en muchos casos el culpable salta a la vista.

Entornos: separar ruido de señal #

El campo environment permite filtrar la vista de Sentry por entorno. Mezclar los errores de staging con los de producción destruye la señal: staging tiene errores esperados de datos de prueba que contaminarían las alertas de producción.

La convención es configurar alertas y notificaciones solo para el entorno production. En staging deja que los errores se registren para depurar, pero sin disparar notificaciones al equipo. En local o CI, desactiva Sentry completamente o usa un DSN de proyecto de desarrollo separado.

php · desactivar Sentry fuera de producción 
\Sentry\init([
    'dsn'         => $_ENV['APP_ENV'] === 'production' ? $_ENV['SENTRY_DSN'] : null,
    'environment' => $_ENV['APP_ENV'],
    'release'     => $_ENV['APP_VERSION'] ?? null,
]);

Con dsn: null el SDK queda en modo noop: todas las llamadas se ignoran sin lanzar errores, así el código de tu aplicación no cambia entre entornos.

Performance monitoring #

Sentry puede actuar también como sistema de trazas distribuidas: mide el tiempo de cada operación dentro de una petición (una transacción en su terminología) y subdivide ese tiempo en spans — consultas a la BD, llamadas HTTP a servicios externos, renders de templates.

El resultado es una vista similar a la que viste en el tutorial de trazas distribuidas: una línea de tiempo que muestra dónde se fue el tiempo en cada petición. Los SDKs de Symfony y Laravel instrumentan automáticamente las queries de Doctrine/Eloquent, los middlewares y las llamadas HTTP salientes.

Para instrumentar operaciones propias:

php · span manual para medir una operación crítica 
$span = \Sentry\startSpan(
    new \Sentry\Tracing\SpanContext('payment.gateway.charge')
);

try {
    $result = $this->gateway->charge($order);
    $span->setStatus(\Sentry\Tracing\SpanStatus::ok());
    return $result;
} catch (\Throwable $exception) {
    $span->setStatus(\Sentry\Tracing\SpanStatus::internalError());
    throw $exception;
} finally {
    $span->finish();
}

Sampling: no envíes todo #

Para errores, Sentry envía el 100% de los eventos — quieres enterarte de cada excepción. Para transacciones de performance, enviar el 100% de las peticiones en un sistema con miles de req/s es caro e innecesario: una muestra representativa es suficiente para detectar tendencias de latencia.

El traces_sample_rate que viste en la inicialización controla esa muestra. Un valor de 0.1 envía el 10% de las transacciones. En producción con tráfico alto, valores entre 0.01 y 0.1 suelen dar una señal estadísticamente sólida con un coste razonable.

Sampling dinámico con tracesSampler

Si quieres siempre trazar las peticiones lentas pero muestrear las rápidas, usa traces_sampler como función: recibe el contexto de la petición y devuelve la tasa de sampling. Puedes devolver 1.0 para peticiones de checkout y 0.01 para las de healthcheck.

Alertas con criterio #

Sentry permite configurar alertas que se disparan cuando un issue supera umbrales: "avísame si este error ocurre más de 100 veces en 10 minutos" o "avísame si la tasa de errores supera el 1% de las peticiones".

Las alertas más útiles son las basadas en síntomas de usuario, no en causas técnicas internas:

Alertas sobre causas

  • Alerta cuando NullPointerException aparece.
  • Alerta cuando QueryException aparece.
  • Alerta para cada nueva excepción.
  • Mucho ruido, muchas notificaciones.

Alertas sobre síntomas

  • Alerta cuando la tasa de error supera el 1%.
  • Alerta cuando un issue nuevo afecta a más de 10 usuarios.
  • Alerta cuando un issue resuelto regresa (regresión).
  • Menos notificaciones, más accionables.

Reducir el ruido #

El mayor riesgo de Sentry es la fatiga de alertas: si notifica demasiado, el equipo empieza a ignorarlo — y ese día que hay un error real, nadie actúa. Estas son las palancas para reducir el ruido:

PalancaQué hace
Inbound filtersIgnora errores de bots, crawlers o IPs conocidas de tests.
Rate limitingCap de eventos por proyecto/hora para no agotar la cuota con un loop de errores.
Ignorar issuesMarca como ignorado un error que es esperado y no tiene solución (librería de terceros, deprecation warnings).
before_send hookFiltra o modifica eventos antes de enviarlos: descarta excepciones de tipos esperados o elimina campos sensibles del payload.
Alertas con thresholdNo notificar la primera ocurrencia sino cuando supera N ocurrencias — evita ruido de errores esporádicos.
php · filtrar excepciones esperadas en before_send 
'before_send' => function (\Sentry\Event $event): ?\Sentry\Event {
    $exception = $event->getExceptions()[0] ?? null;

    $ignoredTypes = [
        NotFoundException::class,
        ValidationException::class,
        AuthorizationException::class,
    ];

    if (in_array($exception?->getType(), $ignoredTypes, strict: true)) {
        return null;
    }

    return $event;
},

Devolver null desde before_send descarta el evento: no se envía a Sentry y no consume cuota. Las excepciones de negocio esperadas (no encontrado, validación fallida) no son bugs — no deben llenar el dashboard de Sentry.

Cuándo aplicarlo #

Úsalo cuando…

  • Necesitas reconstruir el flujo exacto antes del error: los breadcrumbs son insustituibles.
  • Los bugs son difíciles de reproducir y necesitas el contexto completo del usuario en el momento del fallo.
  • Quieres identificar en qué deploy se introdujo una regresión usando releases.

No lo uses cuando…

  • La app es pequeña, con pocos usuarios y los errores son fáciles de reproducir localmente: el nivel básico basta.
  • No tienes tiempo de configurar contexts y releases; el SDK básico ya aporta valor sin estas funciones.
  • El problema es una degradación gradual de rendimiento, no una excepción: ahí Performance monitoring o métricas.

Resumen #

Lo que te llevas

  • Releases: en qué versión apareció el error y si regresó tras marcarlo resuelto. Créalos desde CI con sentry-cli asociando commits.
  • Entornos separados: alertas solo en production. DSN null en local y CI para evitar ruido y coste.
  • Performance monitoring: Sentry mide transacciones y spans igual que un sistema de trazas. Con sampling entre 1% y 10% según el tráfico.
  • Alertas sobre síntomas (tasa de error, usuarios afectados, regresiones), no sobre tipos de excepción concretos.
  • Reduce el ruido con before_send para filtrar excepciones esperadas. La fatiga de alertas es el mayor riesgo de cualquier sistema de notificaciones.
