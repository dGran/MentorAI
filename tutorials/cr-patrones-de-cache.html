Cache-aside, write-through y read-through

Hay tres formas de que un dato acabe en la caché, y la diferencia entre ellas no es de estilo: cambia quién sufre el primer acceso, qué pasa si la caché se cae y si puedes perder una escritura. Elegir por costumbre es cómo se acaba con una caché que devuelve datos que ya no existen.

Cache-aside: el que usas ya #

La aplicación consulta la caché; si no está, va a la fuente y guarda el resultado. Es el 90 % de lo que se ve en producción, y con razón: es simple y la caché es prescindible.

php · CatalogoCacheado.php 
<?php

declare(strict_types=1);

final class CatalogoCacheado implements Catalogo
{
    private const TTL_SEGUNDOS = 600;

    public function porCategoria(int $idCategoria, string $idioma): array
    {
        $clave = ClaveDeCache::paraCatalogo($idCategoria, $idioma, 1);
        $enCache = $this->cache->get($clave);

        if ($enCache !== null) {
            return $enCache;
        }

        $productos = $this->origen->porCategoria($idCategoria, $idioma);

        $this->cache->set($clave, $productos, self::TTL_SEGUNDOS);

        return $productos;
    }
}

Fíjate en que implementa la misma interfaz

Ese decorador es la forma limpia de cachear: quien usa Catalogo no sabe que hay caché, y quitarla es cambiar un cableado en el contenedor. La alternativa —meter los if de caché dentro del repositorio— mezcla dos responsabilidades y hace imposible testear una sin la otra.

Write-through y read-through #

Los otros dos mueven la responsabilidad de sitio:

PatrónCómo funcionaLo que gana y lo que arriesga
Cache-aside La aplicación mira, falla y rellena Simple; la caché puede caerse sin romper nada. El primer lector paga
Read-through La propia caché sabe ir a buscar el dato La aplicación no ve la caché. Necesita una capa que lo soporte
Write-through Al escribir, se actualizan fuente y caché a la vez Nunca sirve datos viejos; cada escritura cuesta más y son dos sistemas

Write-behind: el que casi nunca compensa

Existe un cuarto: escribir solo en la caché y volcar a la base de datos después, en segundo plano. Es rapidísimo y significa que una caída de Redis pierde escrituras confirmadas. Solo tiene sentido para datos que puedes permitirte perder —contadores de visitas, telemetría—, nunca para nada que el usuario crea guardado.

Al escribir: ¿actualizas la caché o la borras? #

Esta pregunta parece menor y es donde vive la carrera de datos más común de todas. La respuesta corta es borrar, y conviene ver por qué.

1 A lee el dato y falla en cachéVa a la base de datos y obtiene «precio = 10»
2 B escribe «precio = 12» y actualiza la cachéLa caché queda con el valor 12: correcto
3 A escribe en caché lo que leyó: 10La caché queda con el valor viejo. Y sin caducar.

El dato incorrecto se queda hasta que expire el TTL. Si el TTL era una hora, una hora sirviendo un precio que no existe.

Borrar en vez de actualizar no elimina la carrera del todo, pero reduce muchísimo la ventana: el siguiente lector encuentra vacío y va a la fuente. Y el orden importa —se escribe en la base de datos primero y se borra la caché después—: al revés, un lector puede rellenar la caché con el valor viejo entre el borrado y el COMMIT.

php · escribir y luego invalidar 
<?php

declare(strict_types=1);

final class ActualizarPrecio
{
    public function __invoke(int $idProducto, int $precioEnCentimos): void
    {
        $this->conexion->transactional(function () use ($idProducto, $precioEnCentimos): void {
            $this->productos->actualizarPrecio($idProducto, $precioEnCentimos);
        });

        $this->cache->delete(ClaveDeCache::paraProducto($idProducto));
    }
}

El borrado va fuera de la transacción

Si borras dentro y la transacción hace rollback, has invalidado una caché que era correcta —molesto pero inofensivo—. Peor es lo contrario: borrar antes del COMMIT deja una ventana en la que un lector rellena la caché con el valor viejo, que sí es un dato incorrecto persistente.

Qué pasa cuando la caché falla #

Una caché es una optimización, así que su caída debería degradar el rendimiento, no tumbar la aplicación. En la práctica hace falta escribirlo explícitamente:

Caché como optimización

  • Un error al leer se traga y se va a la fuente
  • Timeout corto: 50-100 ms, no segundos
  • Un cortacircuitos delante evita insistir si está caída
  • Se registra, pero no se propaga al usuario

Caché como dependencia dura

  • La excepción de Redis sube hasta el controlador
  • Sin timeout: cada petición espera lo que haga falta
  • Redis se cae y la web devuelve 500
  • Has convertido una mejora en un punto único de fallo

Cuidado, eso sí, con el otro extremo: si tu base de datos solo aguanta porque la caché absorbe el 95 % de las lecturas, «degradar» significa que toda esa carga cae de golpe sobre ella. Esa situación no se arregla tragando excepciones; se arregla sabiendo que existe y teniendo un plan, que es de lo que va la lección de la estampida.

Cuándo aplicarlo #

Cache-aside cuando…

  • Es el caso normal: empieza siempre aquí
  • Quieres poder quitar la caché sin tocar el dominio
  • Toleras que el primer lector pague el fallo

Write-through cuando…

  • Servir un dato viejo es inaceptable aunque sea un segundo
  • Las escrituras son pocas y las lecturas muchísimas
  • Asumes que la escritura falla si falla la caché

Resumen #

Lo que te llevas

  • Cache-aside es el patrón por defecto, y un decorador sobre la misma interfaz lo mantiene fuera del dominio.
  • Al escribir se borra la entrada, no se actualiza: actualizar deja una carrera que puede fijar el valor viejo hasta que expire el TTL.
  • Primero el COMMIT, después el borrado: al revés, un lector rellena la caché con el dato viejo en la ventana intermedia.
  • Write-behind pierde escrituras confirmadas si la caché cae: solo para datos que puedes permitirte perder.
  • Un fallo de caché debe degradar, no romper: timeout corto, error tragado y registrado. Si no, has creado un punto único de fallo.
