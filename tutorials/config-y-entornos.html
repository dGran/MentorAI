Configuración y entornos: la regla 12-factor

La contraseña de la base de datos no es código, la URL de la API de pagos no es código, el modo debug no es código. Y sin embargo, en miles de repos, viven dentro del código. Este artículo es sobre la línea que separa ambas cosas y sobre qué pasa cuando se cruza.

Configuración es todo aquello que varía entre entornos mientras el código permanece idéntico: credenciales, URLs de servicios, flags de comportamiento. La definición parece obvia, pero tiene una consecuencia afilada: si algo varía entre entornos y está escrito en el código, tienes un problema esperando fecha.

La config no es código #

El síntoma más reconocible de la línea cruzada es este condicional, que existe en más producciones de las que nadie admite:

php · el olor a config dentro del código 
if ($hostname === 'servidor-produccion-3') {
    $databasePassword = 'Pr0d2024!';
}

if ($environment === 'staging') {
    $paymentApiUrl = 'https://sandbox.pagos.com';
}

Los problemas vienen en racimo. La contraseña está en el historial de git para siempre (ni borrándola del fichero desaparece del historial). Añadir un entorno nuevo exige tocar código y redesplegar. El código conoce por su nombre a servidores concretos, que cambiarán. Y cualquiera con acceso de lectura al repo tiene las llaves de producción.

La dirección correcta es una sola: el código pregunta por su configuración al entorno donde corre, en lugar de saberla. El mismo binario, la misma imagen, el mismo commit — y lo que cambia de un sitio a otro entra desde fuera.

La regla 12-factor #

El nombre viene de The Twelve-Factor App, un manifiesto de 2011 escrito por gente de Heroku con doce principios para aplicaciones desplegables en la nube. Ha envejecido notablemente bien —los contenedores materializaron medio manifiesto—, y su factor III es el que nos ocupa: "almacena la configuración en el entorno".

El manifiesto propone además un test práctico que vale como definición operativa: ¿podrías hacer público el repositorio ahora mismo sin comprometer ninguna credencial? Si la respuesta es no, hay config (o peor, secretos) donde no debe.

Config de entorno ≠ config de aplicación

No todo lo que llaman "config" varía entre entornos. Las rutas, la definición de servicios del contenedor o el mapeo del ORM son config de aplicación: idénticas en todos los entornos, versionadas con el código, donde deben estar. La regla 12-factor aplica solo a lo que cambia entre dev, staging y producción.

Variables de entorno y .env #

El mecanismo universal para "entrar desde fuera" son las variables de entorno: pares nombre-valor que el sistema operativo asocia al proceso al arrancarlo. Todo las entiende —cualquier lenguaje, Docker, systemd, tu CI—, no viven en ningún fichero del repo y cada entorno define las suyas. En PHP se leen con getenv() o $_ENV:

php · la app pregunta al entorno, y falla pronto si falta 
final class EnvironmentConfiguration
{
    public static function requireVariable(string $name): string
    {
        $value = getenv($name);

        if ($value === false || $value === '') {
            throw new MissingEnvironmentVariable($name);
        }

        return $value;
    }
}

$databaseUrl = EnvironmentConfiguration::requireVariable('DATABASE_URL');

¿Y los famosos ficheros .env? Son un atajo para desarrollo local: exportar quince variables a mano cada mañana es inviable, así que una librería (o el propio framework) lee un fichero KEY=valor y puebla el entorno al arrancar. La disciplina que los acompaña es innegociable:

.env.example — al repo

  • Lista qué variables necesita la app.
  • Valores de ejemplo o vacíos, jamás reales.
  • Documentación viva: clonas, copias a .env, rellenas.

.env — jamás al repo

  • Tus valores reales, locales, con credenciales.
  • Va en .gitignore desde el primer commit.
  • Si un .env con secretos tocó el historial: rota los secretos.

En producción, lo limpio es que el .env ni exista: las variables las inyecta la plataforma — el environment: de docker-compose, la definición del servicio, el orquestador. El fichero es la muleta de desarrollo, no el mecanismo.

Un build, muchos entornos #

Aquí la regla 12-factor se encuentra con el pipeline. Si la configuración entra por el entorno, entonces el artefacto que construyes es único y neutro: la misma imagen corre en staging y en producción, y solo cambian las variables que recibe al arrancar. La alternativa —hornear la config dentro con un "build de staging" y un "build de producción"— rompe la promesa central de la entrega continua: lo que probaste ya no es lo que despliegas.

Este principio decide dónde se resuelve la configuración: en tiempo de arranque, no de build. Al construir la imagen no se copia ningún .env ni se ejecuta nada que fije credenciales en una capa (recuerda de las buenas prácticas de Docker: lo que entra en una capa, se queda). La imagen sabe qué variables necesita; sus valores los pone cada entorno.

Los secretos, aparte #

Dentro de la configuración hay una subespecie con reglas más duras: los secretos — contraseñas, claves de API, tokens de firma. Un secreto filtrado no se "corrige": se rota (se invalida y se emite uno nuevo), porque no hay forma de saber quién lo copió mientras estuvo expuesto. De ahí las tres reglas:

ReglaPor qué
Nunca en el repo, ni privadoEl historial de git es para siempre, y el acceso de lectura se regala con facilidad (CI, herramientas, ex-compañeros).
Nunca en logs ni en trazas de errorEl volcado de la excepción que imprime $_ENV entero acaba en un sistema de logs que lee media empresa.
Almacén dedicado con acceso controladoLos Secrets del CI para el pipeline; un gestor (Vault, Secrets Manager) o los secrets del orquestador para producción.

El commit con la contraseña no se borra: se rota

Si un secreto llegó a un commit —aunque lo elimines en el siguiente—, hay bots escaneando repos públicos que lo encontraron en minutos, y en uno privado sigue visible para cualquiera con acceso al historial. Reescribir el historial no revoca nada: asume que está comprometido y rótalo. Luego, si quieres, limpia el historial.

Errores que acaban en incidente #

Cuatro patrones de configuración que se repiten en las historias de terror:

El default peligroso. getenv('APP_ENV') ?: 'dev' parece inofensivo hasta que a una máquina de producción se le olvida definir la variable y arranca en modo desarrollo: debug activado, errores con stack trace al navegador, cachés desactivadas. La regla del código de arriba: para config crítica, faltar = no arrancar. Un error ruidoso en el deploy es infinitamente más barato que un modo debug silencioso en producción.

Debug encendido en producción. El caso particular tan frecuente que merece mención propia: páginas de error con rutas, consultas SQL y variables de entorno a la vista de cualquier usuario. Es una filtración de información de manual — de las que abren la puerta al resto del Top 10 de OWASP.

La config dispersa. Mitad en variables de entorno, mitad en un fichero parameters.php que alguien edita a mano por SSH, mitad en la base de datos. Cuando algo falla, nadie sabe qué configuración está corriendo de verdad. Un solo mecanismo de entrada y un solo punto del código que lee el entorno (el resto recibe valores por inyección, sin getenv() espolvoreado por el dominio).

El entorno "casi" igual. Staging apuntando a la API de pagos real "solo mientras probamos una cosa". Los datos de producción copiados a un entorno con contraseñas débiles. La paridad entre entornos es de forma, no de contenido: misma estructura de config, valores estancos — lo de cada entorno no sale de él.

Resumen #

Lo que te llevas

  • Configuración es lo que varía entre entornos con el código idéntico; si está escrita en el código, es un incidente con fecha pendiente.
  • Factor III del manifiesto 12-factor: la config vive en el entorno. Test rápido: ¿podrías hacer el repo público ahora mismo?
  • .env es la muleta de desarrollo local (en .gitignore); .env.example documenta las variables; en producción las inyecta la plataforma.
  • Un solo build para todos los entornos: la config se resuelve al arrancar, nunca al construir la imagen.
  • Los secretos van en almacenes dedicados y, si se filtran, se rotan; y la config crítica que falta debe impedir el arranque, no activar un default.
