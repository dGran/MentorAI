Servidores web con Axum

Axum sobre Tokio: rutas, extractores, middleware, manejo de errores tipado y cómo estructurar una aplicación web real en Rust.

Con Symfony, que un controlador reciba el usuario, el body validado y el repositorio es cosa del contenedor y de la reflexión en runtime. Axum consigue lo mismo con el sistema de tipos: lo que el handler pide en sus parámetros es lo que el framework extrae. Si un parámetro no es un extractor válido, no compila; si el request no encaja, Axum responde con un 4xx antes de entrar en el handler. Menos magia y más errores en compilación, a cambio de escribir más explícito.

¿Qué es Axum? #

Axum es el framework web oficial del ecosistema Tokio. A diferencia de frameworks más mágicos como Laravel, Axum es deliberadamente explícito: los handlers son funciones async normales, el enrutamiento se configura con código en lugar de anotaciones, y la inyección de dependencias ocurre a través del sistema de tipos.

Comparación con Symfony desde la perspectiva de un PHP developer:

ConceptoSymfonyAxum
RutasAtributos #[Route] o YAMLCódigo Rust con Router::new().route()
ControllersClases con métodos anotadosFunciones async normales
Inyección de dependenciasContainer de SymfonyExtractores tipados en parámetros
MiddlewareEvent listeners, KernelTower layers
Validación del requestSymfony ValidatorSerde + validator crate

Hello world con Axum #

rust 
use axum::{routing::get, Router};
use tokio::net::TcpListener;

async fn raiz() -> &'static str {
    "Hola desde Axum"
}

#[tokio::main]
async fn main() {
    let app = Router::new().route("/", get(raiz));

    let listener = TcpListener::bind("0.0.0.0:3000").await.unwrap();
    println!("Escuchando en http://localhost:3000");

    axum::serve(listener, app).await.unwrap();
}

Cargo.toml para este ejemplo:

rust 
[dependencies]
axum = "0.7"
tokio = { version = "1", features = ["full"] }

El handler raiz es una función async normal que retorna algo que implementa IntoResponse. Los &str, String, Json<T>, tuplas (StatusCode, body), etc., implementan IntoResponse. No hay una clase especial de "Response".

Extractores #

Los extractores son el mecanismo central de Axum para obtener datos del request en el handler. Cada extractor es un tipo que implementa el trait FromRequest o FromRequestParts. El framework los evalúa automáticamente basándose en los tipos de los parámetros de la función.

rust 
use axum::{
    extract::{Path, Query},
    routing::get,
    Router,
};
use serde::Deserialize;

#[derive(Deserialize)]
struct FiltrosUsuario {
    pagina: Option<u32>,
    limite: Option<u32>,
    activo: Option<bool>,
}

async fn listar_usuarios(
    Query(filtros): Query<FiltrosUsuario>,
) -> String {
    format!(
        "Página: {}, límite: {}",
        filtros.pagina.unwrap_or(1),
        filtros.limite.unwrap_or(20)
    )
}

async fn obtener_usuario(Path(id): Path<u32>) -> String {
    format!("Usuario {}", id)
}

#[tokio::main]
async fn main() {
    let app = Router::new()
        .route("/usuarios", get(listar_usuarios))
        .route("/usuarios/:id", get(obtener_usuario));

    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}

Axum verifica en compilación que cada parámetro del handler es un extractor válido, pero no que Path<u32> case con un parámetro :id de la ruta: si el segmento no se puede parsear como u32, el error llega en runtime como una respuesta 400 (y 500 si la ruta no declara ese parámetro).

JSON request/response #

rust 
use axum::{extract::Json, http::StatusCode, routing::post, Router};
use serde::{Deserialize, Serialize};

#[derive(Deserialize)]
struct CrearUsuarioRequest {
    nombre: String,
    email: String,
}

#[derive(Serialize)]
struct UsuarioResponse {
    id: u32,
    nombre: String,
    email: String,
}

async fn crear_usuario(
    Json(request): Json<CrearUsuarioRequest>,
) -> (StatusCode, Json<UsuarioResponse>) {
    let usuario = UsuarioResponse {
        id: 1,
        nombre: request.nombre,
        email: request.email,
    };

    (StatusCode::CREATED, Json(usuario))
}

El extractor Json<T> deserializa el cuerpo del request como JSON al tipo T (usando Serde). Si la deserialización falla, Axum retorna automáticamente un 422 si el JSON no encaja con T (400 si está mal formado y 415 si falta Content-Type: application/json), con el mensaje de error.

Para retornar JSON, envuelve el valor en Json(valor). Axum serializa el valor con Serde y añade el header Content-Type: application/json.

Estado de la aplicación #

El estado compartido (pool de BD, config, clientes HTTP) se inyecta con el extractor State. El estado debe ser Clone, porque Axum lo clona para cada request. Usa Arc<T> para hacer el clone barato.

rust 
use axum::{extract::State, routing::get, Router};
use std::sync::Arc;

struct AppState {
    nombre_servicio: String,
    version: String,
}

async fn estado_handler(State(state): State<Arc<AppState>>) -> String {
    format!("{} v{}", state.nombre_servicio, state.version)
}

#[tokio::main]
async fn main() {
    let estado = Arc::new(AppState {
        nombre_servicio: "mi-api".to_string(),
        version: "1.0.0".to_string(),
    });

    let app = Router::new()
        .route("/estado", get(estado_handler))
        .with_state(estado);

    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}

En un servicio real, el AppState contiene el pool de conexiones a la base de datos, el cliente HTTP reutilizable y la configuración de la aplicación.

Middleware con tower #

Axum está construido sobre tower, una librería de middleware componible. El middleware se aplica con ServiceBuilder::new().layer(...) o con los métodos .layer() del Router.

rust 
use axum::{routing::get, Router};
use tower_http::{cors::CorsLayer, trace::TraceLayer};

#[tokio::main]
async fn main() {
    let app = Router::new()
        .route("/", get(|| async { "hola" }))
        .layer(TraceLayer::new_for_http())
        .layer(CorsLayer::permissive());

    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}

La crate tower-http proporciona middleware HTTP comunes:

  • TraceLayer: logging estructurado de requests con tracing.
  • CorsLayer: cabeceras CORS configurables.
  • CompressionLayer: compresión gzip/brotli del response.
  • TimeoutLayer: timeout global por request.
  • SetRequestIdLayer: añade un ID único a cada request.

Para middleware de autenticación propio, implementas el trait tower::Layer o usas axum::middleware::from_fn:

rust 
use axum::{middleware, response::{IntoResponse, Response}, extract::Request};

async fn autenticar(
    request: Request,
    next: middleware::Next,
) -> Response {
    let token = request.headers().get("Authorization");

    if token.is_none() {
        return (axum::http::StatusCode::UNAUTHORIZED, "Sin token").into_response();
    }

    next.run(request).await
}

let app = Router::new()
    .route("/privado", get(handler_privado))
    .layer(middleware::from_fn(autenticar));

Manejo de errores #

En Axum, los handlers retornan tipos que implementan IntoResponse. Para errores tipados, defines tu propio tipo de error que implemente IntoResponse:

rust 
use axum::{extract::Path, http::StatusCode, response::{IntoResponse, Response}, Json};
use serde_json::json;
use thiserror::Error;

#[derive(Error, Debug)]
pub enum ApiError {
    #[error("recurso no encontrado")]
    NoEncontrado,

    #[error("acceso denegado")]
    Unauthorized,

    #[error("error interno: {0}")]
    Interno(#[from] anyhow::Error),
}

impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        let (status, mensaje) = match &self {
            ApiError::NoEncontrado => (StatusCode::NOT_FOUND, self.to_string()),
            ApiError::Unauthorized => (StatusCode::UNAUTHORIZED, self.to_string()),
            ApiError::Interno(_) => (StatusCode::INTERNAL_SERVER_ERROR, "Error interno".to_string()),
        };

        (status, Json(json!({ "error": mensaje }))).into_response()
    }
}

async fn handler_con_error(Path(id): Path<u32>) -> Result<Json<String>, ApiError> {
    if id == 0 {
        return Err(ApiError::NoEncontrado);
    }

    Ok(Json(format!("usuario_{}", id)))
}

Este patrón hace el manejo de errores completamente tipado: el compilador garantiza que todos los errores posibles se conviertan a una respuesta HTTP correcta. No hay una ruta de error implícita que puedas olvidar.

Errores típicos

  • Poner el extractor del body en cualquier posición. Json, String o Bytes consumen el cuerpo y solo pueden ir como último parámetro. Si no, el handler deja de implementar Handler y el error de compilación no lo dice tan claro.
  • Usar unwrap() dentro de un handler. Un panic no se convierte en un 500 como una excepción no capturada en Symfony: la conexión se corta. Devuelve tu tipo de error con IntoResponse, o añade CatchPanicLayer de tower-http como red de seguridad.
  • Suponer que todo body inválido da 422. El rechazo de Json distingue: sin Content-Type: application/json responde 415, con JSON mal formado 400, y con JSON válido que no encaja en el tipo, 422.
  • Ignorar el orden de las capas. Con Router::layer, la última capa añadida envuelve a las anteriores y se ejecuta primero; con ServiceBuilder se ejecutan de arriba abajo. Un middleware de auth puesto en el sitio equivocado puede quedar por fuera del timeout o de las trazas.

Cuándo aplicarlo #

Axum encaja cuando…

  • Construyes una API HTTP o un microservicio donde latencia, memoria o coste por instancia importan
  • El resto del servicio ya vive sobre Tokio: sqlx, reqwest, colas
  • Quieres que cada endpoint declare en su firma qué extrae (path, query, body, estado) y que el compilador compruebe que son extractores válidos
  • Necesitas middleware reutilizable del ecosistema tower: timeouts, trazas, CORS, compresión

Mejor otra cosa cuando…

  • Es una aplicación con panel de administración, formularios y plantillas: Laravel o Symfony te dan mucho más hecho
  • El equipo no conoce Rust y el cuello de botella no es el rendimiento
  • Hablas gRPC entre servicios: tonic es la opción natural, sobre la misma base de Tokio
  • Necesitas un ORM con migraciones, eventos y admin de serie: en Rust tendrás que montarlo por piezas

La alternativa más directa dentro de Rust es actix-web, igual de madura y con su propio modelo. Axum suele ganar por integrarse con tower y con el resto del ecosistema Tokio sin adaptadores. Un buen primer paso desde PHP es sacar a Axum el endpoint caliente que más CPU consume y dejar el resto donde está.

Resumen #

Lo que te llevas

  • Axum usa funciones async normales como handlers: no hay clases controller, el enrutamiento es código Rust explícito.
  • Los extractores inyectan datos del request en los parámetros del handler, tipados: Path, Query, Json, State, HeaderMap. El compilador comprueba que cada parámetro es un extractor válido; si el request no encaja, Axum responde con un 4xx en runtime antes de entrar en el handler.
  • Json<T> como parámetro deserializa el body; Json(valor) como retorno serializa la respuesta. Serde hace el trabajo.
  • El estado compartido (BD, config) se pasa con Arc<AppState> y se extrae con el extractor State.
  • tower-http proporciona middleware HTTP comunes (logging, CORS, compresión); middleware::from_fn permite middleware custom conciso.
  • Los errores tipados que implementan IntoResponse garantizan que todos los casos de error producen una respuesta HTTP correcta verificada por el compilador.
