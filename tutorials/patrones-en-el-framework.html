Patrones en el framework: dónde los usas sin saberlo

Symfony y Laravel no inventaron su arquitectura. La construyeron sobre los patrones GoF. Reconocerlos es la diferencia entre usar un framework y entenderlo — y entre copiar código de la documentación y saber qué está pasando.

La mejor prueba de que has entendido un patrón es reconocerlo cuando lo ves. Esta lección cierra el curso leyendo Symfony y Laravel con los ojos de los patrones GoF: cada pieza importante del framework corresponde a uno o varios de los que has visto.

El contenedor DI #

El contenedor de inyección de dependencias de Symfony (symfony/dependency-injection) o el Service Container de Laravel es, en su núcleo, una combinación de varios patrones:

PatrónCómo aparece en el contenedor
Abstract Factory El contenedor es una factory que crea objetos a partir de definiciones. Cambiar la configuración (binding de interfaz a implementación) cambia qué familia de objetos se instancia.
Singleton (gestionado) Los servicios con ciclo de vida shared: true (Symfony) o bindings normales (Laravel) garantizan una sola instancia sin los problemas del Singleton manual: la dependencia es visible en el constructor.
Proxy Los servicios lazy: true en Symfony generan un proxy que implementa la misma interfaz pero no instancia el servicio real hasta la primera llamada. Lazy loading sin que el código cliente lo sepa.
php · Symfony services.yaml 
<?php
// Laravel: binding de interfaz a implementación (Abstract Factory)
$this->app->bind(PaymentGateway::class, StripeAdapter::class);

// Cambiar de Stripe a PayPal en un fichero:
$this->app->bind(PaymentGateway::class, PaypalAdapter::class);

// Singleton gestionado: una sola instancia compartida, dependencia visible
$this->app->singleton(CacheStore::class, RedisCacheStore::class);

El ciclo HTTP #

Cuando una petición HTTP llega a Symfony o Laravel, pasa por una cadena de procesamiento antes de llegar al controlador y después de que el controlador devuelve una respuesta. Esto es Chain of Responsibility en su forma más reconocible.

1 RequestLlega del servidor web
2 Middleware stackAuth, CORS, rate limit, logging…
3 ControladorFactory Method resuelve qué controlador
4 ResponseEventos de respuesta notifican listeners

Un ciclo HTTP completo usa cuatro patrones GoF distintos.

El HttpKernel de Symfony implementa el Template Method: el método handle() es el template que define la secuencia (request → resolve controller → call controller → response), y las partes variables (qué controlador, qué middleware) se resuelven por delegación.

El router es un Strategy: decide qué controlador ejecuta cada URL. Puedes cambiar el motor de routing (anotaciones, YAML, atributos PHP 8) sin cambiar el código que llama al router.

EventDispatcher #

Symfony EventDispatcher y el Event System de Laravel son Observer con un intermediario centralizado. En vez de que el sujeto gestione su lista de observadores, un dispatcher actúa de broker: el emisor publica, el dispatcher resuelve qué listeners reciben el evento.

php · EventDispatcher en Symfony 
<?php

declare(strict_types=1);

// El emisor (Observer GoF: el "sujeto") publica al dispatcher
class OrderService
{
    public function confirm(Order $order): void
    {
        $order->markAsConfirmed();
        // No sabe quién escucha — no gestiona ninguna lista
        $this->dispatcher->dispatch(new OrderConfirmed($order->id()));
    }
}

// Los listeners (Observer GoF: los "observadores") se registran desde configuración
#[AsEventListener(event: OrderConfirmed::class)]
class SendConfirmationEmail
{
    public function __invoke(OrderConfirmed $event): void
    {
        // reacciona al evento
    }
}

// El propio Symfony usa esta misma infraestructura internamente:
// kernel.request, kernel.response, kernel.exception — todos son Observer

Los eventos del kernel de Symfony (kernel.request, kernel.response, kernel.exception) son el mismo patrón: el framework es el sujeto, tus listeners son los observadores.

Otras capas del framework #

Parte del frameworkPatrón GoFPor qué
FormBuilder de Symfony / Form facade de Laravel Builder Construye un objeto Form complejo paso a paso con encadenamiento de métodos (add(), setData(), getForm()).
Doctrine Repository Facade + Proxy Facade sobre la capa de persistencia. El Identity Map de Doctrine actúa como Proxy: la primera carga va a BD, las siguientes devuelven el objeto en memoria.
Twig / Blade (herencia de plantillas) Template Method {% block content %} es exactamente un paso variable del Template Method: la plantilla base define la estructura, las hijas rellenan los bloques.
Symfony Messenger / Laravel Queue Command Los mensajes son Commands serializados y ejecutados de forma asíncrona. El bus despacha; el handler ejecuta.
Symfony Security Voters Chain of Responsibility Cada voter decide si puede votar sobre el permiso. Si no puede, pasa al siguiente. El resultado final consolida todos los votos.
Doctrine Lifecycle Callbacks / Eloquent Observers Observer prePersist, postLoad en Doctrine o creating, saved en Eloquent: el modelo es el sujeto; los listeners reaccionan sin que el modelo los conozca.

El mapa completo #

Una de las habilidades que separa a un desarrollador senior de un junior no es conocer más APIs sino entender por qué están diseñadas así. Cuando lees la documentación de Symfony sobre los security voters y piensas "esto es Chain of Responsibility", o cuando ves que Doctrine cachea entidades y piensas "esto es Proxy con Identity Map" — estás leyendo el framework, no solo usándolo.

Cómo seguir profundizando

La mejor práctica después de este curso: cuando uses una parte del framework que no entiendes del todo, busca qué patrón GoF está detrás y lee el código fuente del framework con esos ojos. El código del contenedor de Symfony, del router de Laravel o del EventDispatcher ya no te parecerá magia.

Resumen #

Lo que te llevas

  • El contenedor DI es Abstract Factory + Singleton gestionado + Proxy lazy. El binding de interfaz a implementación es el mismo problema que Abstract Factory resuelve.
  • El ciclo HTTP es Chain of Responsibility (middleware) + Template Method (HttpKernel) + Strategy (router) + Observer (eventos de kernel).
  • EventDispatcher es Observer con broker centralizado. Los eventos del kernel usan la misma infraestructura que tus domain events.
  • FormBuilder → Builder. Doctrine Repository → Facade + Proxy. Twig herencia → Template Method. Messenger → Command. Security voters → Chain of Responsibility.
  • Reconocer patrones en el código del framework es la diferencia entre usar una herramienta y entenderla.
