Estampida de caché, avalancha y penetración

La caché funciona semanas. Un martes caduca una entrada muy pedida, mil peticiones fallan a la vez y todas van a calcular lo mismo. No falló nada: hizo justo lo que le pediste.

La caché funciona perfectamente durante semanas. Un martes a las nueve caduca una entrada muy solicitada, mil peticiones fallan a la vez, mil hilos van a la base de datos a calcular exactamente lo mismo, y el sistema se cae. No falló nada: la caché hizo justo lo que le pediste.

Tres fallos con nombre propio #

Se confunden a menudo y tienen soluciones distintas:

NombreQué pasaCuándo
Estampida
(stampede)		 Muchas peticiones fallan sobre la misma clave y todas recalculan Al caducar una entrada muy pedida
Avalancha
(avalanche)		 Fallan muchas claves distintas a la vez Al reiniciar Redis, o al caducar en bloque lo que se creó junto
Penetración
(penetration)		 Se pide algo que no existe, no se cachea nada y siempre se va a la fuente Con identificadores inválidos, a veces a propósito

La penetración es también un vector de ataque

Si tu caché solo guarda respuestas positivas, alguien pidiendo /productos/999999991, …2, …3 atraviesa la caché en todas las peticiones y golpea la base de datos directamente. La defensa es cachear también el «no existe», con un TTL corto para que un producto recién creado no tarde en aparecer.

Que solo uno recalcule #

La solución directa a la estampida: el primero que detecta el fallo coge un bloqueo corto y recalcula; los demás esperan un poco y vuelven a mirar la caché.

php · CacheConBloqueo.php 
<?php

declare(strict_types=1);

final class CacheConBloqueo
{
    private const ESPERA_BLOQUEO_SEGUNDOS = 5;

    public function obtener(string $clave, callable $calcular, int $ttl): mixed
    {
        $valor = $this->cache->get($clave);

        if ($valor !== null) {
            return $valor;
        }

        $testigo = $this->bloqueo->tomar('recalculo:' . $clave, self::ESPERA_BLOQUEO_SEGUNDOS);

        if ($testigo === null) {
            usleep(50_000);

            return $this->cache->get($clave) ?? $calcular();
        }

        try {
            $valor = $calcular();
            $this->cache->set($clave, $valor, $ttl);

            return $valor;
        } finally {
            $this->bloqueo->soltar('recalculo:' . $clave, $testigo);
        }
    }
}

Fíjate en el ?? $calcular() del final

Si el que tenía el bloqueo tarda o muere, los que esperan no se quedan colgados: calculan ellos. Es peor para la base de datos que esperar, y mucho mejor que un timeout en cascada. Una caché no debe poder bloquear peticiones indefinidamente ni aunque su bloqueo falle.

Recalcular antes de que caduque #

La técnica más elegante evita el problema en vez de gestionarlo: en lugar de esperar a que la entrada caduque, cada lector decide con una probabilidad creciente si la refresca él, y esa probabilidad sube conforme se acerca la caducidad.

1 Faltan 10 minutos para caducarNadie refresca. Se sirve de caché.
2 Falta 1 minutoUna de cada mil peticiones decide refrescar por su cuenta
3 La entrada se renueva antes de caducarCon una sola petición pagando el coste, y sin que nadie espere

Se llama probabilistic early expiration. Symfony Cache lo implementa con el parámetro beta de get().

La gracia es que nunca hay un instante en que la entrada esté vacía: siempre hay valor servible, y la renovación ocurre en segundo plano desde el punto de vista del usuario. Con beta = 1.0 tienes el comportamiento por defecto de Symfony; subirlo hace que se refresque antes, bajarlo lo acerca a la caducidad estricta.

Servir viejo mientras se revalida #

La variante más robusta, y la que salva el día cuando la fuente está caída: guardas el valor con dos tiempos —uno de frescura y otro de caducidad real, más largo—. Entre los dos, sirves el valor viejo y lanzas la actualización aparte.

Lo que ganas

  • Nadie espera nunca a que se recalcule
  • Si la fuente está caída, sigues sirviendo algo
  • El pico de carga desaparece por completo

Lo que aceptas

  • Alguien verá un dato deliberadamente viejo
  • Necesitas un mecanismo para refrescar en segundo plano
  • Más memoria: guardas entradas pasadas su frescura

Es el mismo stale-while-revalidate que existe en la caché HTTP, que verás en la lección de caché HTTP y CDN. La idea se repite porque funciona: casi siempre es mejor un dato de hace cinco minutos que una espera de tres segundos.

Cuándo aplicarlo #

Protege contra estampida cuando…

  • Una sola clave concentra muchísimas lecturas
  • Recalcular cuesta caro: una agregación, una API externa
  • La base de datos no aguantaría si la caché fallara de golpe
  • Ya te ha pasado: es un fallo que se repite

No hace falta cuando…

  • Las lecturas están repartidas entre miles de claves
  • Recalcular cuesta poco: la fuente aguanta el pico
  • El TTL con aleatoriedad ya evita la caducidad en bloque

Resumen #

Lo que te llevas

  • Estampida es muchas peticiones sobre la misma clave; avalancha es muchas claves a la vez; penetración es pedir lo que no existe.
  • Cachear también el «no existe», con TTL corto, cierra la penetración, que además es un vector de ataque barato.
  • Con bloqueo, quien espera debe poder calcular por su cuenta si el bloqueo falla: una caché no puede colgar peticiones.
  • La expiración temprana probabilística evita el problema en vez de gestionarlo: nunca hay un instante sin valor servible.
  • Servir viejo mientras se revalida es lo más robusto, y encima te cubre si la fuente está caída.
