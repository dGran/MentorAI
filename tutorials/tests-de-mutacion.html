Mutation testing con Infection

Una suite en verde con un 100 % de cobertura puede dejar pasar un >= cambiado por un >. El mutation testing mete esos fallos a propósito y mira si tus tests los cazan: mide lo que la cobertura no puede, si las aserciones comprueban algo.

Tu suite pasa en verde con un 100 % de cobertura. Cambia un >= por un > en la regla de envío gratis y relánzala: si sigue en verde, ese 100 % no protegía la regla. El mutation testing hace eso mismo, automático y cientos de veces.

La cobertura no mira las aserciones #

Ya viste en tests que no estorban que la cobertura dice qué se ejecutó, no qué se comprobó, y en el informe de cobertura que una línea verde es un techo optimista. Este es el siguiente paso: dejar de adivinar si tus tests comprueban algo y medirlo.

El ejemplo es una regla pequeña y realista: el envío es gratis a partir de 50 €, y si no cuesta 4,99 €.

php · src/ShippingCost.php 
<?php

declare(strict_types=1);

namespace App;

final class ShippingCost
{
    private const int FREE_SHIPPING_THRESHOLD_CENTS = 5000;
    private const int FLAT_RATE_CENTS = 499;

    public function forCartTotal(int $cartTotalCents): int
    {
        if ($cartTotalCents >= self::FREE_SHIPPING_THRESHOLD_CENTS) {
            return 0;
        }

        return self::FLAT_RATE_CENTS;
    }
}
php · antes: tests/ShippingCostTest.php 
<?php

declare(strict_types=1);

namespace App\Tests;

use App\ShippingCost;
use PHPUnit\Framework\Attributes\Test;
use PHPUnit\Framework\TestCase;

final class ShippingCostTest extends TestCase
{
    #[Test]
    public function charges_the_flat_rate_on_small_carts(): void
    {
        self::assertSame(499, new ShippingCost()->forCartTotal(1000));
    }

    #[Test]
    public function ships_big_carts_for_free(): void
    {
        self::assertSame(0, new ShippingCost()->forCartTotal(9000));
    }
}

Dos tests con aserciones de verdad. PHPUnit 13 con pcov informa de 100 % de líneas, y aun así nadie ha comprobado un carrito de 50 € justos, justo donde se equivoca quien implementa la regla.

Qué es un mutante #

Un mutante es una copia de tu código con un único cambio pequeño, del tipo que podría colar un despiste: >= por >, un return borrado, un + por un -, un public que pasa a protected. Cada regla que genera un tipo de cambio se llama mutador.

La herramienta lanza tus tests contra cada mutante. La lógica es la inversa de lo habitual: aquí quieres que los tests fallen, porque eso demuestra que notan el cambio.

ResultadoQué significa
Muerto (.)Algún test falla con el cambio. Bien: tu suite lo detecta.
Escapado (M)Todos los tests pasan con el cambio. Falta una aserción o el mutante es equivalente.
No cubierto (U)Ningún test ejecuta esa línea. Lo mismo que el rojo del informe de cobertura.
Timeout (T) o error (E)El mutante cuelga o revienta el proceso. Cuenta como detectado.

Infection con PHPUnit #

En PHP la herramienta es Infection. Necesita cobertura para saber qué tests pasan por cada línea, así que el contenedor de desarrollo debe tener pcov o Xdebug, como ya pedía medir la cobertura. Con la imagen oficial php:8.5-cli:

bash · dentro del contenedor de desarrollo 
pecl install pcov && docker-php-ext-enable pcov
composer require --dev phpunit/phpunit infection/infection

Composer pide permiso para el plugin infection/extension-installer: acéptalo para que quede en allow-plugins del composer.json, o en CI la instalación sin interacción fallará. La configuración va en infection.json5, en la raíz:

json5 · infection.json5 
{
    "$schema": "vendor/infection/infection/resources/schema.json",
    "source": {
        "directories": ["src"]
    },
    "logs": {
        "text": "infection.log",
        "html": "infection.html"
    },
    "mutators": {
        "@default": true
    }
}

source dice qué mutar (nunca vendor/) y @default activa los mutadores estándar. Infection lee tu phpunit.xml, lanza la suite una vez para medir cobertura y después lanza contra cada mutante los tests que cubren la línea mutada:

MSI y covered MSI #

Infection resume el resultado en tres porcentajes. Desde la versión 0.31 no muta el código sin cubrir salvo que pases --with-uncovered, y por eso la salida anterior solo enseña dos.

MétricaCálculoQué te dice
MSIDetectados / todos los mutantesLa nota global, castigando también lo que nadie ejecuta.
Mutation Code CoverageCubiertos / todosLa cobertura vista desde los mutantes.
Covered Code MSIDetectados / cubiertosLa calidad de las aserciones donde sí hay tests.

Para verlo, añade a la clase un método expressSurchargeFor() sin test y lanza con --with-uncovered: siete mutantes, cinco muertos, uno escapado y uno sin cubrir. MSI 71 %, cobertura 85 %, covered MSI 83 %. El covered MSI no se mueve porque mide otra cosa: si lo que pruebas lo pruebas bien.

Cuál mirar

El covered MSI es el que la cobertura no te puede dar: cuánto de lo «probado» se comprueba de verdad. El MSI global mezcla eso con la cobertura.

Leer un superviviente #

Cada mutante escapado obliga a una decisión. La pregunta es: ¿existe una entrada con la que el código original y el mutante se comporten distinto?

Si existe, falta un test. En el envío, la entrada es 5.000 céntimos: el original devuelve 0 y el mutante 499. Es un test de frontera de los de siempre:

php · después: el test que mata al mutante 
<?php

declare(strict_types=1);

namespace App\Tests;

use App\ShippingCost;
use PHPUnit\Framework\Attributes\Test;
use PHPUnit\Framework\TestCase;

final class ShippingCostThresholdTest extends TestCase
{
    #[Test]
    public function ships_for_free_exactly_at_the_threshold(): void
    {
        self::assertSame(0, new ShippingCost()->forCartTotal(5000));
    }
}

Si no existe esa entrada, el mutante es equivalente: el cambio no altera el comportamiento observable y ningún test podrá matarlo. Mira este:

php · src/ParcelWeight.php 
<?php

declare(strict_types=1);

namespace App;

final class ParcelWeight
{
    /** @param list<int> $parcelWeightsInGrams */
    public function totalInGrams(array $parcelWeightsInGrams): int
    {
        if ($parcelWeightsInGrams === []) {
            return 0;
        }

        return array_sum($parcelWeightsInGrams);
    }
}

Infection borra el return 0; (mutador ReturnRemoval) y el mutante escapa: con un array vacío, array_sum() ya devuelve 0. El mutante no señala un test que falte, sino código que sobra. Quita la guarda y el mutante desaparece: la clase queda en una línea y el covered MSI vuelve al 100 %.

Falta un test

  • Hay una entrada que distingue original y mutante
  • Suele ser una frontera, un signo o un valor de retorno
  • Se arregla con una aserción, no tocando producción

Mutante equivalente

  • Ninguna entrada los distingue
  • Primero intenta simplificar: a menudo es código redundante
  • Si no se puede, ignóralo en infection.json5 por mutador y método

Para ignorarlo, cada mutador admite una lista ignore con Clase::método: "ReturnRemoval": { "ignore": ["App\\ParcelWeight::totalInGrams"] } dentro de mutators. Con nombre y apellidos, nunca apagando el mutador entero.

En CI: umbral y solo lo cambiado #

--min-msi y --min-covered-msi hacen que Infection salga con código 1 si el porcentaje queda por debajo, y eso rompe el job. Pasar la suite entera en cada PR es caro, así que lo habitual es mutar solo lo que cambia la rama:

bash · solo las líneas tocadas respecto a main 
vendor/bin/infection --threads=max \
    --git-diff-lines --git-diff-base=origin/main \
    --min-covered-msi=80 --ignore-msi-with-no-mutations

--git-diff-filter=AM muta los ficheros añadidos o modificados; --git-diff-lines afina a las líneas añadidas o modificadas. Con --ignore-msi-with-no-mutations, un PR que en src/ solo cambia un docblock no falla por tener cero mutantes: sin la opción, un covered MSI de 0 % sobre nada rompe el job. En GitHub Actions, Infection detecta el entorno y anota los supervivientes en el diff del PR.

yaml · .github/workflows/mutation.yml (paso) 
- uses: actions/checkout@v5
  with:
    fetch-depth: 0
- uses: shivammathur/setup-php@v2
  with:
    php-version: '8.4'
    coverage: pcov
- run: composer install --no-progress
- run: vendor/bin/infection --threads=max --git-diff-lines --git-diff-base=origin/main --min-covered-msi=80 --ignore-msi-with-no-mutations

El resto del pipeline lo tienes en CI para PHP.

El coste en tiempo #

Infection ejecuta los tests que cubren cada línea mutada, una vez por mutante. El coste crece con mutantes × tests que los cubren, no con el tamaño de la suite a secas. Medido en un contenedor con 12 núcleos, sobre diez clases como la del ejemplo y 40 tests con 100 ms de preparación cada uno (lo que tarda un test que toca disco o base de datos):

EjecuciónTiempo
PHPUnit, la suite completa4 s
Infection, 70 mutantes, --threads=139 s
Infection, --threads=413 s
Infection, --threads=max10 s

Unas diez veces la suite en un hilo. Con una suite de cinco minutos, eso es casi una hora: de ahí el filtro por diff en cada PR y la pasada completa en una ejecución nocturna. Si tus tests son lentos por clase, --only-covering-test-cases ejecuta solo los métodos que cubren la línea, no la clase entera.

Errores típicos #

Dónde se tuerce

  • Perseguir el 100 % de MSI. Es la misma ley de Goodhart que con la cobertura: acabas con tests que fijan detalles internos para matar mutantes que no importan.
  • Matar mutantes atándote a la implementación. Probar un método por reflexión para matar un PublicVisibility estorba más que el mutante.
  • Lanzarlo sin driver de cobertura. Sin pcov ni Xdebug no hay mapa de qué test cubre qué, y Infection no puede trabajar.
  • Probar el filtro por diff con ficheros nuevos sin git add. --git-diff-filter lee git diff: los ficheros sin seguimiento no cuentan y te dirá que no hay nada que mutar.
  • Leer el MSI sin --with-uncovered como si fuera global. Desde 0.31 lo no cubierto queda fuera y el número sale más alto de lo que es.

Cómo comprobarlo #

Tras añadir el test de frontera, relanza y exige el máximo para confirmar que no queda nada vivo:

bash · el umbral como prueba 
vendor/bin/infection --threads=max --min-covered-msi=100
echo $?

Con el test de los 5.000 céntimos, todos los mutantes mueren y el código de salida es 0. Quita ese test y vuelve a 1. Abre infection.html para ver cada mutante sobre el código fuente, igual que el informe de cobertura.

Cuándo aplicarlo #

Pásalo cuando…

  • El código decide dinero o permisos: precios, descuentos, impuestos, quién puede hacer qué
  • La cobertura ya es alta y quieres saber si esos tests comprueban algo
  • Revisas un PR con tests nuevos: filtra por diff y mira si los supervivientes señalan aserciones flojas
  • Heredas una suite y necesitas saber cuánto puedes fiarte de ella antes de refactorizar

No compensa cuando…

  • La cobertura es baja: el rojo del informe ya te dice dónde faltan tests, y es más barato
  • Es código pegamento sin decisiones: controladores finos, DTO, configuración
  • La suite tarda tanto que una pasada completa bloquearía cada PR

La alternativa barata ya la conoces: cobertura para encontrar huecos y revisar qué afirma cada test. Infection es la segunda capa, donde un >= mal puesto cuesta dinero.

Resumen #

Lo que te llevas

  • La cobertura mide qué se ejecuta; el mutation testing mide si los tests notan un cambio en el código.
  • Un mutante muere si algún test falla y escapa si todos pasan. Timeouts y errores cuentan como detectados.
  • Infection necesita pcov o Xdebug; desde 0.31 solo muta lo cubierto salvo --with-uncovered. El covered MSI mide la calidad de las aserciones.
  • Ante un superviviente: si hay una entrada que lo distingue, falta un test; si no, es equivalente y a menudo señala código que sobra.
  • Cuesta varias veces la suite (unas diez en el ejemplo medido): en CI, --git-diff-lines con --min-covered-msi, y la pasada completa fuera del PR.
