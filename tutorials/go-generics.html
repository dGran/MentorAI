Generics: funciones y tipos parametrizados

Antes de Go 1.18 había que duplicar funciones para cada tipo o usar any y perder la seguridad de tipos. Los generics permiten escribir código que funciona con cualquier tipo que cumpla una restricción, verificada en tiempo de compilación.

Tienes la misma función escrita tres veces, para int, float64 y string, o una sola con any que solo falla en ejecución. Los generics resuelven ese dilema, pero en Go se usan con mucha más mesura que en Java o TypeScript. Saber cuándo no usarlos es la mitad de la lección.

El problema antes de generics #

Imagina que quieres una función que devuelva el mayor de dos valores. Antes de Go 1.18, necesitabas una función por tipo o usar any perdiendo los checks del compilador:

go 
// Opción 1: duplicar para cada tipo (no escala)
func maxInt(a, b int) int {
    if a > b {
        return a
    }
    return b
}

func maxFloat64(a, b float64) float64 {
    if a > b {
        return a
    }
    return b
}

// Opción 2: any (pierde seguridad de tipos)
func maxAny(a, b any) any {
    // necesitas type assertions: frágil y verboso
    return a   // imposible implementar correctamente
}

Con generics, una sola función sirve para todos los tipos numéricos:

go 
func max[T int | float64](a, b T) T {
    if a > b {
        return a
    }
    return b
}

max(3, 5)       // T inferido como int
max(3.0, 5.0)   // T inferido como float64

Funciones genéricas #

Los parámetros de tipo van entre corchetes, antes de los parámetros normales:

go 
// [T any]: T puede ser cualquier tipo
func Contiene[T comparable](slice []T, elemento T) bool {
    for _, v := range slice {
        if v == elemento {
            return true
        }
    }
    return false
}

// El compilador infiere T del argumento
Contiene([]int{1, 2, 3}, 2)         // true
Contiene([]string{"a", "b"}, "c")   // false

// También puedes especificarlo explícitamente
Contiene[int]([]int{1, 2, 3}, 2)

Un caso muy útil: transformar un slice:

go 
func Map[T, U any](slice []T, fn func(T) U) []U {
    resultado := make([]U, len(slice))

    for i, v := range slice {
        resultado[i] = fn(v)
    }

    return resultado
}

precios := []float64{10.0, 20.0, 30.0}
conIVA := Map(precios, func(p float64) float64 { return p * 1.21 })
// [12.1 24.2 36.3]

nombres := []string{"ana", "luis", "eva"}
longitudes := Map(nombres, func(s string) int { return len(s) })
// [3 4 3]

Restricciones de tipo #

La restricción define qué tipos puede tomar T. Las restricciones son interfaces — pero las interfaces para generics pueden listar tipos concretos con |:

go 
// Restricción: solo enteros con signo
type Entero interface {
    int | int8 | int16 | int32 | int64
}

func Suma[T Entero](valores []T) T {
    var total T

    for _, v := range valores {
        total += v
    }

    return total
}

Suma([]int{1, 2, 3})    // 6
Suma([]int64{10, 20})   // 30

El operador ~ incluye todos los tipos cuyo tipo subyacente es el especificado. Útil cuando trabajas con tipos definidos sobre primitivos:

go 
type Celsius float64

type Numerico interface {
    ~int | ~float64   // ~ incluye tipos basados en int o float64
}

func Doblar[T Numerico](v T) T {
    return v * 2
}

Doblar(5)               // 10 (int)
Doblar(3.14)            // 6.28 (float64)
Doblar(Celsius(20.0))   // Celsius(40.0) — funciona gracias a ~

Tipos genéricos #

No solo las funciones pueden ser genéricas. Los tipos también:

go 
// Cola genérica tipada
type Cola[T any] struct {
    elementos []T
}

func (c *Cola[T]) Encolar(v T) {
    c.elementos = append(c.elementos, v)
}

func (c *Cola[T]) Desencolar() (T, bool) {
    if len(c.elementos) == 0 {
        var zero T
        return zero, false
    }

    v := c.elementos[0]
    c.elementos = c.elementos[1:]
    return v, true
}

func (c *Cola[T]) Tamaño() int {
    return len(c.elementos)
}

// Uso
colaPedidos := Cola[int]{}
colaPedidos.Encolar(1)
colaPedidos.Encolar(2)
pedido, ok := colaPedidos.Desencolar()   // 1, true

El paquete constraints #

El paquete golang.org/x/exp/constraints (experimental pero estable en la práctica) y la propia stdlib ofrecen restricciones predefinidas:

go 
import "golang.org/x/exp/constraints"

// constraints.Ordered: cualquier tipo comparable con <, >, <=, >=
func Min[T constraints.Ordered](a, b T) T {
    if a < b {
        return a
    }
    return b
}

// comparable: builtin de Go — tipos que soportan == y !=
// any: builtin de Go — cualquier tipo (alias de interface{})

Errores típicos

  • Usar == o < con [T any]. No compila: any no promete esas operaciones. Pide comparable para == y cmp.Ordered para ordenar; desde Go 1.21 está en la stdlib y ya no hace falta golang.org/x/exp/constraints.
  • Métodos con parámetros de tipo propios. func (c *Cola[T]) Map[U any](...) no compila: un método solo puede usar los parámetros de su tipo. Escríbelo como función libre, MapCola[T, U any](c *Cola[T], ...).
  • Generics donde basta una interfaz. Si el cuerpo solo llama a métodos, un parámetro de tipo interfaz hace lo mismo con menos ruido en la firma.

Cuándo aplicarlo #

La regla que funciona: escribe primero la versión concreta y generaliza cuando aparezca la segunda copia casi idéntica. Un parámetro de tipo que solo se instancia con un tipo es complejidad sin retorno.

SituaciónRecomendación
Funciones que operan sobre colecciones (map, filter, reduce)Generics: código una vez, funciona para todos los tipos
Estructuras de datos reutilizables (cola, pila, caché)Tipos genéricos
Polimorfismo de comportamiento (distintas implementaciones)Interfaces, no generics
Lógica de negocio específicaTipos concretos; generics añaden complejidad sin beneficio

La guía del equipo de Go: usa generics cuando escribirías el mismo código varias veces para distintos tipos, pero no cuando las interfaces ya cubren el caso. Los generics son para la capa de infraestructura y utilidades, no para la lógica de dominio.

Antes de escribir tu propio helper, mira los paquetes slices y maps de la stdlib (desde Go 1.21): slices.Contains, slices.Index, slices.Sort o slices.Max ya cubren lo que la mayoría de proyectos reescribía a mano.

Y si tu función solo llama a métodos de T, no necesitas generics: func Enviar[T Notificador](n T) hace lo mismo que func Enviar(n Notificador) y se lee peor. Los generics ganan cuando el tipo concreto importa en la salida: un []T que devuelves, o una Cola[T] que no obliga al llamador a hacer type assertions.

Resumen #

Lo que te llevas

  • Los generics, introducidos en Go 1.18, permiten funciones y tipos parametrizados por tipo: una implementación sirve para varios tipos.
  • Los parámetros de tipo van en [T restricción] antes de los parámetros normales. El compilador infiere el tipo de los argumentos.
  • Las restricciones son interfaces que pueden incluir tipos concretos (int | float64) o usar ~ para incluir tipos derivados.
  • comparable permite usar == y !=; any acepta cualquier tipo; constraints.Ordered permite comparaciones de orden.
  • Usa generics para colecciones y estructuras de datos reutilizables; usa interfaces para polimorfismo de comportamiento.
