git bisect: encontrar el commit que lo rompió

«En la 1.4 funcionaba» y desde entonces hay cientos de commits. Leer diffs no escala; partir el historial por la mitad, sí. git bisect hace esa búsqueda por ti y, con un test de PHPUnit, la hace sola mientras te tomas el café.

En Deshacer y rescatar aprendiste a revertir un commit. Esta lección resuelve el paso anterior: averiguar cuál revertir cuando sabes que algo se rompió, pero no cuándo.

El problema: «antes funcionaba» #

Un cliente avisa de que el total del carrito sale un céntimo más caro con el descuento del 15 %. La versión v1.4 calculaba bien; la rama main de hoy, no. Entre medias hay semanas de trabajo de todo el equipo.

Las salidas intuitivas no funcionan. Repasar git log -p (lo viste en los comandos del día a día) es leer cientos de diffs buscando uno que, casi siempre, parece inocente: un «refactor» sin cambio de comportamiento aparente. Depurar el código actual tampoco basta: te dice qué está mal, no qué cambio lo introdujo ni por qué alguien lo hizo así. Y ese porqué, que está en el mensaje y en la PR del commit culpable, es lo que te deja arreglarlo sin romper lo que aquel cambio buscaba.

Búsqueda binaria en el historial #

Si un commit conocido es bueno y otro posterior es malo, el fallo entró en algún punto entre los dos. Pruebas el commit de en medio: si está bien, el culpable está en la mitad más reciente; si está mal, en la más antigua. Cada prueba descarta la mitad de los candidatos, así que el número de pasos crece con el logaritmo en base 2 del tamaño del rango, no con el tamaño.

1 Marcas un commit bueno y uno malov1.4 bien, main mal
2 Lo pruebas y lo marcasgood o bad: descartas la mitad
3 Queda un solo candidato«is the first bad commit»

Cada vuelta divide el rango entre dos.

Commits en el rangoPruebas, más o menos
164
1.00010
100.00017

La condición es que el fallo aparezca una vez y se quede: bueno antes, malo después. Si el bug va y viene a lo largo del historial, bisect encontrará un punto de cambio, no necesariamente el que buscas.

Bisect a mano #

Cuatro órdenes bastan. start abre la sesión, bad y good marcan los extremos y, desde ahí, git deja en tu árbol de trabajo el commit que toca probar (en detached HEAD). Pruebas, marcas y repites.

bash · una sesión manual 
git bisect start
git bisect bad            # el commit actual (main) está mal
git bisect good v1.4      # esta etiqueta estaba bien
# Bisecting: 8 revisions left to test after this (roughly 3 steps)

# pruebas el commit que git ha sacado y lo marcas
git bisect good           # o git bisect bad

# al final: "6218b1b... is the first bad commit"
git bisect reset          # vuelve a la rama donde empezaste

git bisect start HEAD v1.4 hace lo mismo en una línea: primero el malo, luego uno o varios buenos. Y no olvides el reset: hasta que lo ejecutas sigues en mitad de la búsqueda, en un commit suelto.

Automatizarlo con bisect run #

Probar a mano es lento y propenso a errores. Si puedes expresar «está roto» como un comando, git bisect run lo ejecuta en cada paso y decide por su código de salida:

Código de salidaQué entiende bisect
0Commit bueno.
125No se puede probar: lo salta (skip).
1–127, salvo 125Commit malo.
128 o másAborta la búsqueda.

Encaja con PHPUnit sin adaptar nada: sale con 0 si todo pasa, con 1 si un test falla y con 2 si hay un error. Volvamos al carrito. Así era el cálculo en v1.4:

php · src/Carrito.php (antes: v1.4) 
<?php

declare(strict_types=1);

namespace Tienda;

final class Carrito
{
    /** @var list<int> */
    private array $lineasEnCentimos = [];

    public function anadir(int $precioEnCentimos, int $unidades = 1): void
    {
        $this->lineasEnCentimos[] = $precioEnCentimos * $unidades;
    }

    public function total(int $porcentajeDescuento = 0): int
    {
        $subtotal = array_sum($this->lineasEnCentimos);
        $descuento = (int) round($subtotal * $porcentajeDescuento / 100);

        return $subtotal - $descuento;
    }
}

Y así quedó tras un commit titulado «refactor: descuento con aritmética entera». Una sola línea, con aspecto de mejora:

php · src/Carrito.php (después: main) 
<?php

declare(strict_types=1);

namespace Tienda;

final class Carrito
{
    /** @var list<int> */
    private array $lineasEnCentimos = [];

    public function anadir(int $precioEnCentimos, int $unidades = 1): void
    {
        $this->lineasEnCentimos[] = $precioEnCentimos * $unidades;
    }

    public function total(int $porcentajeDescuento = 0): int
    {
        $subtotal = array_sum($this->lineasEnCentimos);
        $descuento = intdiv($subtotal * $porcentajeDescuento, 100);

        return $subtotal - $descuento;
    }
}

intdiv trunca: el 15 % de 1999 son 299,85 céntimos, que round dejaba en 300 y intdiv deja en 299. Los tests que ya había usaban importes redondos y siguieron en verde. El primer paso es escribir el test que reproduce el bug:

php · tests/DescuentoRegresionTest.php (sin commitear) 
<?php

declare(strict_types=1);

namespace Tienda\Tests;

use PHPUnit\Framework\TestCase;
use Tienda\Carrito;

final class DescuentoRegresionTest extends TestCase
{
    public function testRedondeaElDescuentoAlCentimo(): void
    {
        $carrito = new Carrito();
        $carrito->anadir(1999);

        self::assertSame(1699, $carrito->total(15));
    }
}

Ese fichero no se commitea todavía. Los ficheros sin seguimiento sobreviven a cada checkout de bisect, así que el mismo test se ejecuta contra el código de cada commit, también contra los antiguos donde no existía. Si lo commitearas en main, desaparecería al saltar al pasado. Con eso, la búsqueda entera es una línea:

bash · bisect run con PHPUnit 
git bisect start HEAD v1.4
git bisect run vendor/bin/phpunit tests/DescuentoRegresionTest.php

# running 'vendor/bin/phpunit' 'tests/DescuentoRegresionTest.php'
# ...
# 6218b1bb4a1ee11906dd585635b2b28743717f1a is the first bad commit
#     refactor: descuento con aritmética entera
#  src/Carrito.php | 2 +-
# bisect found first bad commit

git bisect reset

En el repo de prueba de esta lección, 17 commits candidatos se resolvieron en 4 ejecuciones del test. Lo que te llevas no es solo el hash: es el mensaje del commit, su autor y su PR, que explican qué pretendía el cambio.

Commits que no se pueden probar #

En la vida real hay commits rotos por otra causa: un «wip» con un error de sintaxis, una migración a medias. Si los marcas como malos, engañas a la búsqueda; si los marcas como buenos, también. Para eso está git bisect skip: «este no lo sé, prueba otro cercano». En modo automático, el equivalente es salir con 125. Como PHPUnit no lo hace por sí solo, se envuelve en un script:

bash · bisect.sh (sin commitear) 
#!/usr/bin/env bash

for fichero in src/*.php; do
    php -l "$fichero" > /dev/null || exit 125
done

vendor/bin/phpunit tests/DescuentoRegresionTest.php

Se lanza con chmod +x bisect.sh y git bisect run ./bisect.sh. Saltar tiene un precio: si el commit saltado está pegado al culpable, bisect no puede separarlos y te entrega la lista de sospechosos en vez de uno:

bash · cuando lo saltado roza al culpable 
There are only 'skip'ped commits left to test.
The first bad commit could be any of:
a29d861e45484b9d67519677ab296d72f9fb076c
170352d28ef6cfbc212a637cd0663f44c8aea183
We cannot bisect more!

Dos o tres sospechosos se revisan a mano en un minuto. Si sabes de antemano que un tramo entero no compila, sáltalo de golpe con rango: git bisect skip v2.5..v2.6.

Equivocarse y rehacer: log y replay #

En una sesión manual basta un good donde tocaba bad para que bisect acabe señalando un commit inocente, y no hay deshacer paso a paso. Lo que sí hay es un diario: git bisect log imprime la sesión como órdenes que se pueden volver a ejecutar.

bash · corregir una marca equivocada 
git bisect log > bisect.log
# edita bisect.log y borra la línea de la marca equivocada
#   git bisect start 'HEAD' 'v1.4'
#   git bisect good f74cb38027b09be2b15fc7fbf63b38d3a413aee3
#   git bisect bad 32188682de0ab10d7b72b57420d43d35ed8ed763
git bisect reset
git bisect replay bisect.log   # rehace la sesión sin la marca equivocada

El mismo fichero sirve para pasarle la búsqueda a un compañero o adjuntarla a la incidencia: con replay, quien lo reciba llega al mismo punto sin repetir las pruebas, si está en el mismo HEAD: el log guarda 'HEAD', no el hash.

Errores típicos #

Lo que hace que bisect señale al commit equivocado

  • Un test que falla por otro motivo. Si usa una clase que en los commits antiguos no existe, PHPUnit sale con 2, bisect lo cuenta como malo y la búsqueda se tuerce. Prueba solo lo que ya existía en el commit bueno.
  • Commitear el test o el script. Desaparecen al saltar a commits antiguos. Déjalos sin seguimiento hasta terminar.
  • Marcar como malo lo que no compila. Eso es skip o un 125, no un bad.
  • Un script que no arranca. Sin permiso de ejecución o con un comando que no existe, el shell sale con 126 o 127. Si pasa en la primera prueba, git la repite en el commit bueno y, si allí también falla, aborta («bogus exit code 127 for good revision»); si aparece más tarde (un vendor/bin/phpunit que no existe en un commit antiguo), lo cuenta como malo.
  • Olvidar el reset. Te quedas en detached HEAD y lo siguiente que commitees no cuelga de ninguna rama.

Cómo comprobarlo #

Bisect es tan fiable como tu criterio de «malo», así que valida el criterio antes y el resultado después. Antes de lanzar run, ejecuta el script en los dos extremos: debe salir con 0 en el bueno y con algo distinto de 0 en el malo. Después, confirma que el commit señalado es la frontera exacta: falla en él y pasa en su padre.

bash · validar el criterio y el veredicto 
git switch --detach v1.4 && ./bisect.sh; echo "salida: $?"      # 0
git switch --detach 6218b1b~1 && ./bisect.sh; echo "salida: $?"  # 0
git switch --detach 6218b1b && ./bisect.sh; echo "salida: $?"    # 1
git switch main
git show 6218b1b                 # el porqué del cambio

Con la frontera confirmada, arreglas en main y commiteas el test de regresión junto al arreglo. Si el commit ya está compartido y lo quieres deshacer entero, git revert 6218b1b.

Cuándo aplicarlo #

Tira de bisect cuando…

  • Tienes un commit que funcionaba y otro que no, y muchos commits entre ellos
  • El fallo se reproduce con un comando: un test, un curl, un script
  • Necesitas el porqué del cambio, no solo el parche
  • Una prueba de rendimiento empeoró entre dos versiones

No te ayuda cuando…

  • El fallo es intermitente: un test inestable da veredictos al azar
  • Depende de datos o de configuración de producción, no del código
  • Nunca funcionó: no hay commit bueno del que partir
  • El rango son tres commits: léelos

La alternativa, con pocos commits o un fallo que no sabes reproducir, es git log -p -S intdiv o git blame sobre la línea sospechosa: más rápido si intuyes dónde mirar. Para algo que no es un bug (cuándo se volvió lento un endpoint), git bisect start --term-old=rapido --term-new=lento cambia good/bad por palabras que no confunden.

Resumen #

Lo que te llevas

  • Bisect es una búsqueda binaria entre un commit bueno y uno malo: mil commits se resuelven en unas diez pruebas.
  • start, bad, good y reset para la sesión manual; run la automatiza con el código de salida de un comando.
  • 0 es bueno, 1-127 malo, 125 salta el commit; lo que no se puede probar va a skip, nunca a bad.
  • El test de regresión y el script se quedan sin commitear durante la búsqueda, y se validan antes en los dos extremos.
  • git bisect log guarda la sesión y replay la rehace, también para corregir una marca equivocada.
