Worktrees: varias ramas a la vez

Estás a mitad de una funcionalidad y llega un bug urgente. Con git worktree no aparcas nada: abres la rama del arreglo en otra carpeta del mismo repositorio y tu trabajo a medias se queda exactamente donde estaba.

Un repositorio Git normal tiene una sola carpeta de trabajo, y en ella solo cabe una rama a la vez. Un worktree es otra carpeta enganchada al mismo repositorio, con su propia rama. Dos ramas abiertas, dos editores, dos servidores levantados, y un único historial debajo.

El problema: una sola carpeta para todo #

En Deshacer y rescatar viste la salida clásica cuando te interrumpen: git stash, cambias de rama, arreglas, vuelves y git stash pop. Funciona, pero tiene letra pequeña que se nota en un proyecto PHP real:

  • Los ficheros nuevos no se aparcan sin -u, y el pop puede chocar si tu rama avanzó mientras tanto (un pull o un rebase).
  • Cambiar de rama cambia el código, pero no vendor/. Si la rama del arreglo tiene otro composer.lock, toca composer install al ir y otra vez al volver. Lo mismo con migraciones aplicadas a la base de datos local o con la caché de Symfony.
  • Pierdes el contexto: el IDE reindexa, los tests que tenías a medias ya no son los de esa carpeta y el contenedor sirve código de otra rama.

La causa de fondo es una sola: todas esas cosas viven en la carpeta, y la carpeta solo puede estar en una rama. La solución es tener más carpetas.

Una carpeta por rama #

Lo que ya sabes de ramas no cambia: una rama es un puntero a un commit. Lo nuevo es que el repositorio (la carpeta .git con objetos y referencias) puede tener varios directorios de trabajo. El original se llama main worktree; los que añades son linked worktrees, y en ellos .git no es una carpeta sino un fichero de una línea que apunta al repositorio principal.

1 tienda/.gitobjetos, ramas, tags, config y hooks: uno solo
2 tienda/ en feature/factura-pdfsu HEAD, su índice, su vendor/
3 tienda-hotfix/ en hotfix/ivasu HEAD, su índice, sin vendor/ hasta que lo instales

Un commit hecho en cualquier carpeta aparece al instante en las demás, porque el historial es el mismo.

No es una copia: no se clona nada ni se duplican objetos. Crear un worktree cuesta lo que escribir los ficheros de esa rama en disco.

add, list, remove y prune #

ComandoQué hace
git worktree add ../tienda-hotfix -b hotfix/iva mainCrea la carpeta con una rama nueva que parte de main.
git worktree add ../tienda-factura feature/factura-pdfAbre en otra carpeta una rama que ya existe.
git worktree listLista cada carpeta con su commit y su rama; marca las locked y las prunable.
git worktree remove ../tienda-hotfixBorra la carpeta y su registro. La rama no se toca.
git worktree pruneLimpia el registro de carpetas que ya no existen en disco.

Así cambia la interrupción del bug urgente:

bash · antes: aparcar y reconstruir 
git stash -u
git switch -c hotfix/iva main
composer install
# arreglo, commit, push
git switch feature/factura-pdf
composer install
git stash pop
bash · después: otra carpeta y nada que aparcar 
git worktree add ../tienda-hotfix -b hotfix/iva main
cd ../tienda-hotfix
composer install
# arreglo, commit, push; la carpeta tienda/ sigue intacta
cd ../tienda
git worktree remove ../tienda-hotfix

Si borras la carpeta a mano en vez de usar remove, Git sigue teniéndola registrada: git worktree list la marca como prunable y git worktree prune la olvida. Git también la limpia solo con el tiempo (gc.worktreePruneExpire).

La misma rama no puede estar en dos carpetas

Es la regla que más sorprende al principio, y tiene sentido: si dos carpetas estuvieran en la misma rama, un commit en una movería el puntero y la otra quedaría con ficheros que ya no corresponden a su HEAD. Git lo impide al crear el worktree, al hacer git switch y al borrar la rama:

bash · Git 2.53, la rama ya está abierta en otra carpeta 
$ git switch feature/factura-pdf
fatal: 'feature/factura-pdf' is already used by worktree at '/home/ana/tienda-factura'

$ git branch -D feature/factura-pdf
error: cannot delete branch 'feature/factura-pdf' used by worktree at '/home/ana/tienda-factura'

Si solo quieres mirar un commit sin rama, git worktree add --detach ../revision main crea la carpeta en HEAD separado y no bloquea ninguna rama.

Qué se comparte y qué no #

La regla general: lo que está en el repositorio es común; lo que describe «dónde estoy y qué tengo a medias» es de cada carpeta; y lo que Git no rastrea no existe en la carpeta nueva.

Cosa¿Compartida?Consecuencia
Objetos (commits, ficheros)SíNo ocupa el doble ni hay que hacer fetch por carpeta.
Ramas, tags y refs/stashSíEl stash de una carpeta aparece en git stash list de todas.
.git/config y hooksSíUn hook de pre-commit corre igual en todas las carpetas.
HEAD e índice (staging)NoCada carpeta tiene su rama y su git add.
Estado de bisectNoPuedes bisecar en una carpeta mientras trabajas en otra.
vendor/, .env.local (o .env si no se versiona), var/NoLa carpeta nueva nace sin ellos: hay que instalar y configurar.

Esa última fila es la que más tiempo cuesta: el worktree solo contiene lo que está en el commit. Sin composer install no hay autoload, y sin tu fichero de entorno local la aplicación no arranca o, peor, arranca contra otra base de datos sin que te des cuenta.

Docker Compose con varios worktrees #

Si levantas el proyecto con Docker, dos carpetas son dos stacks, y Compose los distingue por el nombre de proyecto. Por defecto es el nombre de la carpeta, así que tienda y tienda-hotfix ya no chocan en contenedores, redes ni volúmenes (tienda-hotfix_dbdata es otra base de datos). Lo que sí choca es el puerto del host:

yaml · compose.yaml con el puerto parametrizado 
services:
  app:
    image: php:8.5-cli
    command: php -S 0.0.0.0:8000 -t /app
    volumes:
      - ./:/app
    ports:
      - "${APP_PORT:-8080}:8000"
bash · cada worktree con su nombre y su puerto 
cd ../tienda-hotfix
printf 'COMPOSE_PROJECT_NAME=tienda-hotfix\nAPP_PORT=8091\n' > .env.docker
docker compose --env-file .env.docker up -d

# sin APP_PORT distinto, el segundo stack no arranca:
# Bind for 0.0.0.0:8080 failed: port is already allocated

Fijar COMPOSE_PROJECT_NAME en el .env de cada carpeta (en Symfony ese .env está versionado: usa docker compose --env-file .env.docker o -p) te protege del caso traicionero: dos worktrees con el mismo nombre de carpeta en rutas distintas (~/a/api y ~/b/api) comparten proyecto api, y el segundo up no falla: recrea el contenedor del primero montando el código del segundo.

Errores típicos #

Lo que muerde a quien empieza con worktrees

  • Creer que remove protege tus ficheros ignorados. Se niega si hay cambios o ficheros sin rastrear, pero vendor/ y el .env.local (o el .env, si no lo versionas) están en .gitignore y los borra sin preguntar. Si ese .env.local tenía credenciales que no guardas en otro sitio, se han ido.
  • Montar solo el worktree en un contenedor y usar Git dentro. El fichero .git apunta al repositorio principal, que no está montado: git status responde fatal: not a git repository. Monta el repositorio principal en la misma ruta que tiene en el host, o ejecuta Git desde el host.
  • Borrar la carpeta y creer que la rama se fue con ella. remove no toca ramas: bórrala tú con git branch -d cuando esté integrada.
  • Olvidar que hooks y config son comunes. Un git config core.hooksPath hecho en una carpeta cambia todas.

Cómo comprobarlo #

Tres preguntas antes de fiarte: qué carpetas hay, en qué rama está cada una y a qué repositorio pertenecen.

bash · inventario y diagnóstico 
git worktree list
# /home/ana/tienda         d5abffc [main]
# /home/ana/tienda-hotfix  604df71 [hotfix/iva]

git worktree prune --dry-run -v
git branch
# + hotfix/iva   el + marca una rama abierta en otro worktree

git rev-parse --git-dir --git-common-dir
docker compose config | head -1
# name: tienda-hotfix

En un worktree, --git-dir devuelve su carpeta privada (.git/worktrees/tienda-hotfix) y --git-common-dir el repositorio compartido; en la carpeta original, ambos dicen .git. Y docker compose config te dice qué nombre de proyecto usará up antes de levantar nada.

Cuándo aplicarlo #

Worktree cuando…

  • Te interrumpen con un arreglo y tu rama tiene trabajo a medias, ficheros nuevos o dependencias distintas
  • Revisas una PR ejecutándola en local sin desmontar lo tuyo
  • Un git bisect o una suite lenta tienen que correr mientras sigues programando
  • Comparas dos ramas levantadas a la vez, cada una en su puerto

No compensa cuando…

  • El cambio de rama es de cinco minutos y sin cambios en composer.lock: git stash basta
  • El proyecto usa submódulos: la documentación de Git desaconseja varios checkouts de un superproyecto
  • Necesitas config, hooks o remotos distintos, o aislar un experimento que puede romper el repositorio

La alternativa es un clon aparte (git clone otra vez). Duplica objetos (salvo al clonar desde una ruta local, que usa enlaces duros) y cada clon hace su propio fetch, pero no comparte nada: ni ramas, ni stash, ni hooks, y la misma rama puede estar abierta en los dos. Elige clon cuando lo que quieres es aislamiento; elige worktree cuando quieres dos vistas del mismo trabajo.

Resumen #

Lo que te llevas

  • Un worktree es otra carpeta del mismo repositorio con su propia rama: cambias de tarea cambiando de carpeta, sin stash.
  • add, list, remove y prune cubren el ciclo; una rama solo puede estar abierta en una carpeta.
  • Se comparten objetos, ramas, stash, config y hooks; cada carpeta tiene su HEAD e índice, y nace sin vendor/ ni .env.local.
  • Con Docker, cada worktree lleva su COMPOSE_PROJECT_NAME y su puerto; si buscas aislamiento total, un clon aparte.
