Vectores e IA: búsqueda semántica con pgvector

Buscar «cómo hacer pan» y encontrar la nota titulada «Masa madre: proporciones», aunque no comparta ni una palabra. Eso es búsqueda semántica, y en Supabase no necesita una base de datos vectorial aparte: es una columna más en tu tabla de notas, con tus políticas de seguridad aplicadas.

Si los embeddings son nuevos para ti, Embeddings y RAG explica qué son y para qué sirven. Esta lección los lleva a Supabase: dónde se guardan, cómo se generan, cómo se busca rápido y cómo se mantienen al día sin que nadie se acuerde de recalcularlos.

pgvector: una columna con significado #

Un embedding es una lista de números que representa el significado de un texto: textos parecidos dan listas cercanas. La extensión **pgvector** añade a Postgres el tipo vector y operadores para medir distancias:

sql · activar la extensión y añadir la columna 
create extension if not exists vector with schema extensions;

alter table public.notes add column embedding extensions.vector(384);

El número entre paréntesis es la dimensión, y la fija el modelo que genera los embeddings: 384 para gte-small, 1536 para muchos modelos de OpenAI. Todos los vectores de la columna tienen que venir del mismo modelo: dos modelos distintos no comparten espacio, y compararlos no tiene sentido aunque tuvieran la misma dimensión.

OperadorDistanciaCuándo
<=>CosenoLa opción por defecto para texto: mide el ángulo, no la longitud
<#>Producto interior (negativo)Con vectores normalizados da el mismo orden que el coseno y es algo más rápida
<->Euclídea (L2)Cuando el modelo lo recomienda o la magnitud importa

Generar los embeddings #

Los embeddings los calcula un modelo. Tienes dos opciones desde una Edge Function:

  • El modelo integrado de Supabase. El Edge Runtime trae gte-small (384 dimensiones) sin clave ni coste por llamada aparte del de la función.
  • Una API externa (OpenAI, Voyage, Cohere…) con su clave en los secretos de la función. Modelos más grandes y mejores en algunos idiomas, con coste por token.
ts · embedding con el modelo integrado 
const session = new Supabase.ai.Session("gte-small");

const embedding = await session.run(text, { mean_pool: true, normalize: true });

Con normalize: true los vectores salen con longitud 1, y entonces coseno y producto interior ordenan igual. Elige uno y úsalo de forma coherente en la búsqueda y en el índice.

Buscar: una función que respeta RLS #

La búsqueda es una función SQL que recibe el embedding de la consulta y devuelve las notas más cercanas:

sql · las notas más parecidas a una consulta 
create function public.match_notes(
  query_embedding extensions.vector(384),
  match_count int default 10
)
returns table (id bigint, title text, similarity float)
language sql
stable
security invoker
set search_path = ''
as $$
  select
    n.id,
    n.title,
    1 - (n.embedding operator(extensions.<=>) query_embedding) as similarity
  from public.notes n
  where n.embedding is not null
  order by n.embedding operator(extensions.<=>) query_embedding
  limit least(match_count, 50);
$$;

Como el search_path está vacío, el operador se escribe con su esquema: operator(extensions.<=>). Lo importante es security invoker: la búsqueda pasa por las mismas políticas RLS que cualquier consulta. Un usuario solo encuentra entre las notas que puede leer, las suyas y las compartidas con él, sin una línea extra. Con una base de datos vectorial separada tendrías que copiar allí los permisos y mantenerlos sincronizados.

ts · buscar desde la app 
const { data: embeddingData } = await supabase.functions.invoke("embed", { body: { text: query } });

const { data: notes } = await supabase.rpc("match_notes", {
  query_embedding: embeddingData.embedding,
  match_count: 10,
});

Índices: de recorrer todo a buscar aproximado #

Sin índice, cada búsqueda calcula la distancia con todas las filas: con unos miles de notas va bien; con millones, no. Los índices vectoriales hacen búsqueda aproximada: devuelven casi siempre los más cercanos, mucho más rápido.

sql · índice HNSW para distancia coseno 
create index on public.notes using hnsw (embedding extensions.vector_cosine_ops);

HNSW (recomendado)

  • Un grafo por capas que se recorre de lo general a lo concreto
  • Buena precisión y velocidad sin ajustar casi nada
  • Se puede crear con la tabla vacía: se mantiene al insertar
  • Construirlo y mantenerlo consume más memoria

IVFFlat

  • Agrupa los vectores en listas y busca solo en las más cercanas
  • Más ligero de construir
  • Hay que crearlo después de cargar datos representativos, o agrupa mal
  • Menos precisión para la misma velocidad

El índice tiene que usar la misma familia de operador que la consulta: un índice vector_cosine_ops solo acelera órdenes por <=>. Si buscas con <#>, necesitas vector_ip_ops.

Embeddings que se mantienen solos #

Una nota editada cuyo embedding no se recalcula se vuelve invisible a la búsqueda, o peor, aparece por lo que decía antes. Calcular el embedding dentro de la petición de guardado hace lenta cada edición y falla si el modelo no responde. El patrón que propone Supabase reutiliza todo lo visto en el curso:

1 Insert o update de la notaun trigger limpia embedding y encola { id } si cambió el texto
2 Cola embedding_jobslos trabajos pendientes, con reintentos
3 Cronllama a la Edge Function worker
4 Edge Functiongenera los embeddings y actualiza las notas

Cada pieza ya la conoces: trigger, cola, Cron y Edge Function.

El trigger solo encola si cambiaron title o body, no por cualquier update. Y como el trabajo llega por una cola, si el modelo falla un rato los mensajes vuelven a la cola y se procesan después, sin perder ninguno.

Búsqueda híbrida: palabras y significado #

La búsqueda semántica falla donde la de texto acierta: un código de producto, un nombre propio, un término exacto. La de texto falla donde la semántica acierta: sinónimos y paráfrasis. La búsqueda híbrida ejecuta las dos y combina los rankings, normalmente con Reciprocal Rank Fusion (RRF): cada resultado suma puntos según su posición en cada lista.

sql · columna de texto completo para combinar con la vectorial 
alter table public.notes add column fts tsvector
  generated always as (to_tsvector('spanish', title || ' ' || body)) stored;

create index on public.notes using gin (fts);

Una función hybrid_search hace las dos consultas como subconsultas, cruza los resultados por id y ordena por la suma de 1 / (k + posición) de cada lista. La documentación de Supabase trae la función completa; la idea es esa.

Del buscador al asistente: RAG #

Con la búsqueda hecha, un asistente que responde preguntas sobre tus notas está a un paso: una Edge Function recibe la pregunta, busca las 5 notas más parecidas con match_notes (actuando como el usuario, así que solo ve las suyas) y se las pasa a un modelo de lenguaje con la pregunta. Eso es RAG, y RAG y fine-tuning cuenta cuándo compensa y cuándo hay alternativas más simples.

Cuándo aplicarlo #

pgvector en Supabase encaja cuando…

  • Los textos a buscar ya viven en tu base de datos
  • La búsqueda tiene que respetar permisos por usuario
  • Hablamos de miles a unos pocos millones de vectores
  • Quieres combinar significado con filtros SQL normales (por libreta, por fecha)

Piénsalo antes si…

  • Son cientos de millones de vectores con mucho tráfico de búsqueda: el índice compite por memoria con tus consultas
  • Tus usuarios buscan códigos y términos exactos: la búsqueda de texto completo de Postgres basta
  • No tienes forma de evaluar si los resultados son buenos: mide antes de añadir complejidad

Resumen #

Lo que te llevas

  • pgvector añade el tipo vector y los operadores <=> (coseno), <#> (producto interior) y <-> (euclídea); la dimensión la fija el modelo.
  • Todos los vectores de una columna vienen del mismo modelo; los embeddings se generan en una Edge Function, con gte-small integrado o una API externa.
  • La búsqueda es una función SQL security invoker: respeta RLS sin replicar permisos.
  • HNSW es el índice por defecto; el operador del índice tiene que coincidir con el de la consulta.
  • Trigger, cola, Cron y Edge Function mantienen los embeddings al día sin frenar las escrituras.
  • La búsqueda híbrida combina texto completo y vectores con RRF.
