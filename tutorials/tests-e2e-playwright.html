Tests end-to-end con Playwright

Todos tus tests unitarios pasan, la integración con la base de datos también, y el botón de «Añadir» no hace nada porque alguien renombró un campo del formulario. Solo un test que abre el navegador y lo pulsa, como haría tu usuario, lo habría visto.

Un test end-to-end recorre la aplicación entera por la misma puerta que el usuario: navegador, HTML, JavaScript, rutas, PHP, base de datos y vuelta. Es caro, así que escribes pocos, y esos pocos tienen que ser fiables.

Lo que ningún otro test ve #

En La pirámide de tests viste los tres niveles. El unitario prueba una clase con dobles; el de integración, tu repositorio contra una base de datos real, como en PHPUnit con base de datos. Ninguno de los dos carga la página. Queda fuera lo que se rompe al unir piezas: el name del input que ya no lee el controlador, el JavaScript que no carga, la sesión que no se guarda.

El e2e lo cubre todo de una vez, y por eso mismo cuesta: segundos por test en vez de milisegundos, un navegador que levantar y más motivos para fallar. De ahí la cúspide estrecha: un e2e por camino crítico (registrarse, comprar, pagar), no uno por variación. Las variaciones (el IVA de cada país, los mensajes de validación) bajan a unitarios, donde cuestan cien veces menos.

Playwright contra tu app en Docker #

Playwright controla Chromium, Firefox y WebKit desde Node. Que tu app sea PHP da igual: el test solo habla HTTP y DOM. Lo cómodo son dos servicios en Compose: la app y la imagen oficial de Playwright, con los navegadores ya instalados.

yaml · compose.yaml 
services:
  app:
    image: php:8.5-cli
    working_dir: /app
    command: php -S 0.0.0.0:8000 -t public
    environment:
      APP_ENV: test
      PHP_CLI_SERVER_WORKERS: 4
    volumes:
      - ./app:/app
    healthcheck:
      test: ["CMD", "php", "-r", "exit(file_get_contents('http://localhost:8000/health') === 'ok' ? 0 : 1);"]
      interval: 2s
      retries: 10

  e2e:
    image: mcr.microsoft.com/playwright:v1.62.1-noble
    working_dir: /e2e
    environment:
      BASE_URL: http://app:8000
      CI: ${CI:-}
    volumes:
      - ./e2e:/e2e
    depends_on:
      app:
        condition: service_healthy
    ipc: host
    init: true
    command: sh -c "npm ci && npx playwright test"

Cuatro detalles con motivo. El healthcheck pide una ruta /health que solo responde ok, así los tests no arrancan hasta que PHP acepta peticiones. La etiqueta de la imagen tiene que coincidir con la versión de @playwright/test de tu package.json: si no, Playwright no encuentra los navegadores. ipc: host lo recomienda la documentación para Chromium, que sin él puede quedarse sin memoria. Y PHP_CLI_SERVER_WORKERS deja que el servidor integrado atienda varias peticiones a la vez; sin él, los tests en paralelo hacen cola.

js · e2e/playwright.config.js 
const { defineConfig, devices } = require('@playwright/test');

module.exports = defineConfig({
  testDir: './tests',
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,
  reporter: [['list'], ['html', { open: 'never' }]],
  use: {
    baseURL: process.env.BASE_URL ?? 'http://localhost:8000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },
  projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }],
});

baseURL apunta al servicio app de la red de Compose, así que los tests escriben rutas relativas y valen igual en local y en CI.

Localizadores por rol, no por CSS #

Un selector CSS como form .btn.btn-primary describe la maquetación, no lo que ve el usuario. El día que alguien cambia la clase del botón, el test se rompe sin que la funcionalidad haya cambiado: es el test frágil de Tests que no estorban. Playwright propone buscar como busca una persona: por rol accesible y nombre (getByRole), por etiqueta del campo (getByLabel) o por texto (getByText).

Eso exige que el HTML diga lo que es, y ahí entra tu PHP. Esta plantilla funciona en pantalla, pero no tiene etiqueta ni botón de verdad:

php · TaskForm.php (antes) 
<?php

declare(strict_types=1);

function renderTaskForm(int $listId): string
{
    return <<<HTML
        <form action="/lists/{$listId}/tasks" method="post">
          <input name="title" placeholder="Nueva tarea">
          <div class="btn btn-primary" onclick="submitTask()">Añadir</div>
        </form>
        HTML;
}

Aquí getByLabel('Nueva tarea') no encuentra nada (un placeholder no es una etiqueta) y getByRole('button', { name: 'Añadir' }) tampoco: un div no es un botón. El arreglo es pequeño:

php · TaskForm.php (después) 
<?php

declare(strict_types=1);

function renderTaskForm(int $listId): string
{
    return <<<HTML
        <form action="/lists/{$listId}/tasks" method="post">
          <label>Nueva tarea <input name="title" required></label>
          <button class="btn btn-primary">Añadir</button>
        </form>
        <p role="status"></p>
        HTML;
}

De regalo, el formulario ahora funciona con lector de pantalla. Si un localizador por rol no encuentra tu elemento, muchas veces el fallo es de accesibilidad.

El orden de preferencia

Rol con nombre, etiqueta, texto. getByTestId queda para lo que no tiene rol ni texto estable, como un gráfico; el CSS, como último recurso.

Esperas automáticas, no sleeps #

El segundo enemigo es el tiempo. Al pulsar «Añadir», el formulario envía la tarea por fetch y la pinta cuando el servidor responde. Este test, con los localizadores de antes, falla aunque la funcionalidad vaya bien:

js · e2e/tests/fragil.spec.js (antes) 
test('añade una tarea', async ({ page }) => {
  await page.goto('/lists/1');
  await page.locator('input[name=title]').fill('Comprar pan');
  await page.locator('form .btn.btn-primary').click();

  const count = await page.locator('ul.tasks > li').count();
  expect(count).toBe(1);
});

count() mira el DOM una sola vez, en el instante del clic, y la tarea aún no ha llegado: recibe 0. La tentación es meter page.waitForTimeout(500). Con un servidor que tarda 400 ms, esperar 300 sigue fallando y esperar 600 pasa en tu portátil y falla en un CI cargado. Una espera fija siempre es demasiado corta o demasiado larga.

Playwright lo resuelve de dos formas. Las acciones (click, fill) esperan solas a que el elemento sea accionable: visible, habilitado y, para el clic, quieto. Y las aserciones web, las que llevan await expect(locator), reintentan hasta que se cumplen o vence su plazo, 5 segundos por defecto:

js · e2e/tests/tareas.spec.js (después) 
const { test, expect } = require('@playwright/test');

test.beforeEach(async ({ page, request }, testInfo) => {
  const response = await request.post('/test/lists', {
    data: { name: `Compra ${testInfo.testId}-${testInfo.repeatEachIndex}-${testInfo.retry}` },
  });
  expect(response.status()).toBe(201);
  const { id } = await response.json();
  await page.goto(`/lists/${id}`);
});

test('añade una tarea a la lista', async ({ page }) => {
  await page.getByLabel('Nueva tarea').fill('Comprar pan');
  await page.getByRole('button', { name: 'Añadir' }).click();

  await expect(page.getByRole('status')).toHaveText('Tarea añadida');
  await expect(page.getByRole('listitem')).toHaveText(['Comprar pan']);
});

toHaveText espera a que la lista tenga exactamente esa tarea. Si llega en 50 ms, el test sigue a los 50 ms; si no llega nunca, falla a los 5 segundos con un mensaje que dice qué esperaba y qué vio.

Datos aislados por test #

En PHPUnit aislabas cada test con una transacción y un rollback. Aquí no sirve: el navegador habla con la app por HTTP, en otro proceso y con otra conexión, y no ve lo que tu test haya abierto en una transacción. Si todos usan la lista 1, el primero pasa y los siguientes encuentran las tareas del anterior; en paralelo, depende de quién llegue antes.

La salida es que cada test cree sus propios datos, con nombres únicos, y no dependa de ningún otro. La forma más rápida es un endpoint de preparación que solo existe en el entorno de test:

php · public/index.php (fragmento) 
<?php

declare(strict_types=1);

$method = $_SERVER['REQUEST_METHOD'];
$path = parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH);

if ($method === 'POST' && $path === '/test/lists' && getenv('APP_ENV') === 'test') {
    $payload = json_decode(file_get_contents('php://input'), true, flags: JSON_THROW_ON_ERROR);
    $database->prepare('INSERT INTO lists (name) VALUES (?)')->execute([$payload['name']]);
    http_response_code(201);
    header('Content-Type: application/json');
    echo json_encode(['id' => (int) $database->lastInsertId()]);

    return;
}

El beforeEach lo llama con request, el cliente HTTP de Playwright, y navega a la lista nueva. Preparar datos por API es mucho más rápido que rellenar formularios. La guarda de APP_ENV no es opcional: sin ella, cualquiera crea listas en producción.

En CI, con trazas y capturas #

En CI se ejecuta lo mismo que en local, con dos cambios que ya hace la configuración cuando existe la variable CI: reintentos y forbidOnly, que hace fallar la suite si alguien se dejó un test.only. Si ya tienes el pipeline de CI para un proyecto PHP, el job de e2e se añade aparte:

yaml · .github/workflows/e2e.yml 
name: e2e

on: [push, pull_request]

jobs:
  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - run: docker compose run --rm e2e
        env:
          CI: true
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with:
          name: playwright-report
          path: e2e/playwright-report/
          retention-days: 30

El if: ${{ !cancelled() }} es lo importante: sin él, el paso de subir el informe se salta justo cuando hay fallos, que es cuando lo necesitas. El informe HTML incluye la captura de cada fallo (screenshot: 'only-on-failure') y la traza del primer reintento (trace: 'on-first-retry'). La traza graba el DOM, la red y la consola de cada acción; se abre con npx playwright show-trace y ahorra reproducir el fallo en local.

Tests inestables #

Un test flaky falla a veces sin que cambie el código. Es el peor tipo de test: enseña al equipo a pulsar «reintentar» y a ignorar el rojo. Con reintentos activos, Playwright lo marca como flaky en vez de ocultarlo: falló y luego pasó. Las causas se repiten:

CausaSíntomaRemedio
Esperas fijas o lecturas instantáneasFalla más en CI que en localAserciones web con await expect(locator)
Datos compartidos entre testsFalla según el orden o en paraleloDatos propios con nombre único por test
Dependencias externas realesFalla cuando la pasarela de pago tardaUn sandbox propio o interceptar con page.route
Fechas, zonas horarias, animacionesFalla a medianoche o en otra máquinaFijar reloj, timezoneId y locale en la configuración
Localizadores ambiguosPulsa el primer «Guardar» de dosAcotar dentro de un contenedor con getByRole

Los reintentos son un diagnóstico, no un arreglo: un test inestable se investiga con su traza o se aparta con un issue.

Errores típicos #

Lo que convierte una suite e2e en un estorbo

  • Usar el e2e para probar variaciones. Veinte e2e del formulario de alta, uno por regla de validación, son el cono de helado. Las reglas van a unitarios; el e2e prueba que el alta funciona.
  • Leer el DOM sin esperar. expect(await locator.count()).toBe(1) mira una vez; await expect(locator).toHaveCount(1) reintenta. Se parecen mucho y no se comportan igual.
  • Depender del orden de los tests. Un test que da por hecho que otro ya creó al usuario se rompe al ejecutarlo solo o en paralelo.
  • Subir los reintentos hasta que pase. Tapa la causa y alarga cada ejecución en rojo.

Cómo comprobarlo #

Que un test pase una vez no dice que sea estable. Repítelo en paralelo: si comparte datos o depende del tiempo, falla aquí y no en el CI de la semana que viene.

bash · terminal 
docker compose run --rm e2e npx playwright test --repeat-each=20 --workers=4
docker compose run --rm e2e npx playwright test --retries=2 --fail-on-flaky-tests

--repeat-each ejecuta cada test N veces. --fail-on-flaky-tests hace que un test que solo pasa al reintentar cuente como fallo. Y para saber que el test sirve, rompe a propósito la funcionalidad (el name del input) y mira que falla con un mensaje que entiendes.

Cuándo aplicarlo #

Un e2e cuando…

  • Es un camino crítico del negocio: alta, login, compra, pago
  • El fallo estaría en la unión de piezas: formulario, JavaScript y controlador
  • Quieres un smoke test tras desplegar que confirme que la app arranca

No hace falta cuando…

  • Pruebas una regla de cálculo o de validación
  • Es una API sin interfaz: basta un test HTTP de integración
  • La pantalla cambia cada semana y nadie mantendrá el test

La alternativa más barata

Si lo que quieres comprobar es que un endpoint responde bien, un test funcional del framework (WebTestCase en Symfony, $this->getJson() en Laravel) recorre rutas, controlador y base de datos sin navegador, en milisegundos. Sube a Playwright solo cuando el JavaScript o el HTML forman parte de lo que puede romperse.

Resumen #

Lo que te llevas

  • El e2e es el único test que prueba la unión de todas las piezas; por eso es valioso y por eso es caro. Uno por camino crítico, no uno por variación.
  • Playwright corre en Node contra tu app PHP: dos servicios en Compose, con la imagen oficial en la misma versión que @playwright/test.
  • Localiza por rol, etiqueta y texto. Si no encuentras un elemento así, probablemente el HTML no es accesible.
  • Nada de esperas fijas: las acciones y await expect(locator) esperan solas hasta su plazo.
  • Cada test crea sus datos con nombre único; el rollback por transacción no llega al navegador.
  • En CI, reintentos con traza en el primero, capturas al fallar y el informe subido con !cancelled().
