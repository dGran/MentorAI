Búsqueda full-text en MySQL y Postgres

El buscador de casi todos los proyectos empieza con un LIKE '%texto%'. Funciona con mil filas y se arrastra con un millón, y además no entiende de plurales ni de relevancia. Las dos bases de datos que ya usas traen un buscador de verdad dentro: veamos cómo se activa y hasta dónde llega.

Un usuario escribe «zapatilla impermeable» en el buscador de tu tienda. Con LIKE no aparece nada, porque el producto se llama «Zapatillas de running trail» y la descripción dice «impermeables». Con búsqueda full-text sale el primero. La diferencia no es de sintaxis: es otra estructura de datos.

Por qué LIKE no escala #

En Índices y B-tree viste que un B-tree está ordenado por el principio del valor. LIKE 'Zapa%' sabe por dónde entrar; LIKE '%running%' no, porque la palabra puede estar en cualquier posición. Así que el motor lee la tabla entera. Esto es lo que devuelve MySQL 8.4 sobre una tabla de 50.006 productos con índice en nombre:

sql · mysql 8.4 
EXPLAIN ANALYZE
SELECT id, nombre FROM productos
WHERE nombre LIKE '%running%' OR descripcion LIKE '%running%';

-> Filter: ((productos.nombre like '%running%') or (productos.descripcion like '%running%'))
     (cost=5341 rows=10469) (actual time=64.1..64.1 rows=4 loops=1)
    -> Table scan on productos  (cost=5341 rows=49885)
         (actual time=0.0314..25.7 rows=50006 loops=1)

Lee 50.006 filas para devolver 4. En Postgres 17 pasa lo mismo: Seq Scan con Rows Removed by Filter: 50004 (allí LIKE distingue mayúsculas: usa ILIKE). Es la consulta que Encontrar la consulta culpable te enseña a cazar, y el coste crece en línea recta con la tabla.

Y no es solo rendimiento: LIKE compara caracteres, así que no junta «zapatilla» con «zapatillas» ni ordena por relevancia.

El índice invertido #

La búsqueda full-text le da la vuelta al problema. En lugar de recorrer los textos buscando la palabra, guarda de antemano, para cada palabra, en qué filas aparece. Buscar pasa a ser consultar un diccionario.

1 Texto«Zapatillas impermeables para correr»
2 Tokenszapatillas · impermeables · para · correr
3 Términosminúsculas, sin palabras vacías y, en Postgres, reducidas a su raíz
4 Índice invertidotérmino → filas donde aparece

El mismo proceso se aplica a lo que escribe el usuario: por eso «zapatilla» encuentra «zapatillas».

La clave está en el paso 3. Las palabras vacías (stopwords) como «de» se descartan porque no distinguen nada. Reducir a la raíz (stemming) junta «impermeable» e «impermeables» en un término. Cada motor hace este paso a su manera, y de ahí salen sus sorpresas.

FULLTEXT en MySQL #

En InnoDB se crea un índice FULLTEXT sobre las columnas de texto y se consulta con MATCH ... AGAINST. Las columnas del MATCH tienen que coincidir con las del índice.

sql · mysql 8.4 
ALTER TABLE productos ADD FULLTEXT INDEX ft_productos (nombre, descripcion);

EXPLAIN ANALYZE
SELECT id, nombre FROM productos
WHERE MATCH(nombre, descripcion) AGAINST ('running');

-> Filter: (match productos.nombre,productos.descripcion against ('running'))
     (cost=1.1 rows=1) (actual time=0.0309..0.0549 rows=4 loops=1)
    -> Full-text index search on productos using ft_productos (nombre='running')
         (cost=1.1 rows=1) (actual time=0.0197..0.0432 rows=4 loops=1)

De 64 ms a 0,05 ms, y el EXPLAIN clásico muestra type: fulltext. Hay dos modos de consulta:

ModoCómo se escribeQué hace
Natural (por defecto)AGAINST ('running impermeable')Cualquier palabra suma; devuelve filas con al menos una y calcula la relevancia.
BooleanoAGAINST ('+running -mochila' IN BOOLEAN MODE)+ obliga, - excluye, * busca por prefijo y las comillas buscan la frase exacta.

Con los datos de ejemplo, '+running -mochila' descarta la mochila aunque diga «running». '"running trail"' solo encuentra las zapatillas. Y aquí sale la primera limitación: InnoDB no reduce palabras a su raíz. AGAINST ('auricular') no encuentra «Auriculares»; hace falta 'auricular*' en modo booleano. A cambio, con la collation por defecto (utf8mb4_0900_ai_ci) no distingue acentos: «montana» encuentra «montaña».

La segunda limitación es el tamaño mínimo de palabra. innodb_ft_min_token_size vale 3 por defecto, así que «HD» nunca llega al índice y AGAINST ('hd') no devuelve nada. Además, la lista de stopwords por defecto es inglesa, pero incluye de, la y en. La variable es de solo lectura (SET GLOBAL falla con ERROR 1238): se cambia en la configuración, se reinicia y se reconstruye el índice.

ini · my.cnf 
[mysqld]
innodb_ft_min_token_size = 2
sql · tras reiniciar 
ALTER TABLE productos
  DROP INDEX ft_productos,
  ADD FULLTEXT INDEX ft_productos (nombre, descripcion);

tsvector y GIN en Postgres #

Postgres separa las dos piezas. tsvector es el documento ya procesado y tsquery es la consulta procesada. El operador @@ dice si casan. La configuración 'spanish' aplica stopwords y raíces en castellano:

sql · postgres 17 
SELECT to_tsvector('spanish', 'Zapatillas impermeables para correr por montaña');
-- 'corr':4 'imperm':2 'montañ':6 'zapatill':1

SELECT websearch_to_tsquery('spanish', 'running -mochila "trail running"');
-- 'running' & !'mochil' & 'trail' <-> 'running'

«para» y «por» han desaparecido y el resto se ha quedado en su raíz. websearch_to_tsquery entiende la sintaxis de un buscador web (comillas, -, OR) y nunca da error de sintaxis; to_tsquery('spanish', 'zapatilla impermeable'), en cambio, falla con syntax error in tsquery. Con texto que escribe un usuario, la primera.

Para que sea rápido, el tsvector se guarda en una columna generada y se indexa con GIN, la implementación del índice invertido en Postgres. setweight marca de qué columna viene cada término: lo usará el ranking.

sql · postgres 17 
ALTER TABLE productos ADD COLUMN busqueda tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('spanish', nombre), 'A') ||
    setweight(to_tsvector('spanish', descripcion), 'B')
  ) STORED;

CREATE INDEX idx_productos_busqueda ON productos USING GIN (busqueda);

EXPLAIN ANALYZE SELECT id, nombre FROM productos
WHERE busqueda @@ websearch_to_tsquery('spanish', 'zapatilla impermeable');

 Bitmap Heap Scan on productos  (actual time=0.178..0.179 rows=1 loops=1)
   Recheck Cond: (busqueda @@ '''zapatill'' & ''imperm'''::tsquery)
   ->  Bitmap Index Scan on idx_productos_busqueda  (actual time=0.167..0.167 rows=1 loops=1)
 Execution Time: 0.218 ms

Ahí está la búsqueda del principio: «zapatilla impermeable» encuentra «Zapatillas de running trail», cuya descripción dice «impermeables». Al contrario que InnoDB, Postgres indexa «HD» sin problema, pero la configuración 'spanish' sí distingue acentos: «montana» no encuentra «montaña». Se arregla con la extensión unaccent en una configuración propia, que luego sustituye a 'spanish' en la columna generada y en la consulta:

sql · postgres 17 
CREATE EXTENSION IF NOT EXISTS unaccent;
CREATE TEXT SEARCH CONFIGURATION es_sin_acentos (COPY = spanish);
ALTER TEXT SEARCH CONFIGURATION es_sin_acentos
  ALTER MAPPING FOR hword, hword_part, word WITH unaccent, spanish_stem;

Ranking: ordenar por relevancia #

Hay que poner arriba lo que más se parece. En MySQL, el propio MATCH ... AGAINST en el SELECT devuelve la relevancia. En Postgres se calcula con ts_rank. Misma búsqueda, «running impermeable», en los dos motores:

ProductoMySQL (modo natural)Postgres (running OR impermeable)
Chaqueta impermeable de montaña60.91830.4559
Zapatillas de running trail16.77650.4255
Calcetines de running16.77650.3040
Mochila de hidratación para correr16.77650.1216

MySQL premia que «impermeable» sea rara y aparezca dos veces en la chaqueta, pero trata igual las tres filas con «running». Postgres, además, sabe que en los calcetines «running» está en el nombre (peso A) y en la mochila solo en la descripción (peso B). Por defecto, A pesa 1.0 y B 0.4. Los números no se comparan entre motores: solo ordenan dentro de una consulta.

Un término frente a todos

websearch_to_tsquery une las palabras con &: «running impermeable» exige las dos. El modo natural de MySQL las une con un «o». Por eso la tabla usa OR en Postgres: para comparar lo mismo.

En PHP: antes y después #

El cambio es pequeño: la consulta usa el índice y el orden sale de la relevancia.

php · antes: LIKE 
<?php

declare(strict_types=1);

final class ProductSearch
{
    public function __construct(private readonly PDO $pdo)
    {
    }

    public function search(string $term): array
    {
        $statement = $this->pdo->prepare(
            'SELECT id, nombre FROM productos
             WHERE nombre LIKE :term OR descripcion LIKE :term
             LIMIT 20'
        );
        $statement->execute(['term' => '%' . $term . '%']);

        return $statement->fetchAll(PDO::FETCH_ASSOC);
    }
}
php · después: MySQL 
<?php

declare(strict_types=1);

final class MySqlProductSearch
{
    public function __construct(private readonly PDO $pdo)
    {
    }

    public function search(string $term): array
    {
        $statement = $this->pdo->prepare(
            'SELECT id, nombre,
                    MATCH(nombre, descripcion) AGAINST (:rankedTerm) AS relevancia
             FROM productos
             WHERE MATCH(nombre, descripcion) AGAINST (:filteredTerm)
             ORDER BY relevancia DESC
             LIMIT 20'
        );
        $statement->execute(['rankedTerm' => $term, 'filteredTerm' => $term]);

        return $statement->fetchAll(PDO::FETCH_ASSOC);
    }
}
php · después: Postgres 
<?php

declare(strict_types=1);

final class PostgresProductSearch
{
    public function __construct(private readonly PDO $pdo)
    {
    }

    public function search(string $term): array
    {
        $statement = $this->pdo->prepare(
            "SELECT id, nombre, ts_rank(busqueda, consulta) AS relevancia
             FROM productos, websearch_to_tsquery('spanish', :term) AS consulta
             WHERE busqueda @@ consulta
             ORDER BY relevancia DESC
             LIMIT 20"
        );
        $statement->execute(['term' => $term]);

        return $statement->fetchAll(PDO::FETCH_ASSOC);
    }
}

En MySQL el término va en modo natural a propósito: en modo booleano, un - o un * que teclee el usuario cambiaría la búsqueda.

Errores típicos #

Lo que suele fallar

  • Omitir la configuración en Postgres. to_tsvector(texto) sin primer argumento usa default_text_search_config, que en la imagen oficial de Docker es pg_catalog.english: raíces inglesas sobre texto español.
  • Consultar otra expresión distinta de la indexada. Con el GIN sobre busqueda, un WHERE to_tsvector('spanish', nombre) @@ ... hace Parallel Seq Scan: el planificador solo usa el índice si la expresión coincide.
  • Repetir un parámetro con nombre. Con PDO::ATTR_EMULATE_PREPARES a false, usar :term dos veces en la misma consulta de MySQL lanza SQLSTATE[HY093]: Invalid parameter number. Por eso el ejemplo usa dos nombres.
  • Esperar que las palabras cortas se encuentren. En MySQL, «HD», «4K» o «TV» no llegan al índice con el mínimo de 3.
  • Dar por exacto el stemming. En Postgres, «auriculares» se queda en 'auricular', pero la consulta «auricular» se reduce a 'auricul' y no lo encuentra.

Cómo comprobarlo #

Primero, el plan. En MySQL busca type: fulltext o Full-text index search; en Postgres, Bitmap Index Scan sobre el índice GIN. Si aparece un Table scan o un Seq Scan, el índice no se está usando.

Después, mira qué términos se guardaron: explica por qué algo no aparece.

sql · inspeccionar los términos 
-- MySQL: qué palabras hay en el índice de una tabla
SET GLOBAL innodb_ft_aux_table = 'tienda/productos';
SELECT DISTINCT word, doc_count
FROM INFORMATION_SCHEMA.INNODB_FT_INDEX_TABLE
WHERE word IN ('running', 'hd', 'de', 'para');
-- para: 5, running: 4 (ni 'hd' ni 'de')

-- Postgres: cómo queda un texto y una consulta
SELECT to_tsvector('spanish', 'Auriculares inalámbricos'),
       to_tsquery('spanish', 'auricular');
-- 'auricular':1 'inalambr':2 | 'auricul'

Las filas recién insertadas en MySQL pueden estar aún en INNODB_FT_INDEX_CACHE y no en INNODB_FT_INDEX_TABLE: mira las dos.

Cuándo compensa OpenSearch #

El full-text de la base de datos cubre el buscador de un panel, un blog o un catálogo mediano. Un motor como OpenSearch compensa cuando la búsqueda es el producto, no un extra:

Lo que ganas

  • Relevancia ajustable: BM25 por defecto, con pesos por campo y por consulta que se cambian sin migrar.
  • Facetas: los contadores «Talla M (120)» salen de agregaciones en la misma petición.
  • Tolerancia a erratas, sinónimos y analizadores por idioma configurables.
  • Volumen: millones de documentos repartidos en varios nodos sin cargar la base de datos principal.

Lo que pagas

  • Un servicio más que desplegar, vigilar y actualizar.
  • Sincronizar los datos: cada cambio en la base de datos tiene que llegar al índice.
  • Consistencia eventual: un producto recién editado tarda en verse en el buscador.

La sincronización es la parte cara. Si la haces desde el código, apóyate en el patrón outbox para no perder cambios cuando falla la escritura en el índice.

Cuándo aplicarlo #

Full-text en la base de datos cuando…

  • Buscas palabras dentro de textos largos: nombres, descripciones, artículos.
  • El LIKE '%x%' ya aparece como lento en el log o en el EXPLAIN.
  • Quieres ordenar por relevancia sin añadir infraestructura.

No hace falta cuando…

  • Buscas por el principio del valor (un código, un email, un SKU): basta un B-tree y LIKE 'x%'.
  • La tabla tiene unos cientos de filas y nunca crecerá.
  • Necesitas facetas, erratas y relevancia afinada a gran escala: eso es un motor aparte.

La alternativa sencilla

Si los usuarios buscan códigos o nombres exactos que empiezan por lo que escriben, un índice B-tree con LIKE 'texto%' resuelve el caso sin full-text. Y si ya estás en Postgres y lo que necesitas es tolerar erratas en textos cortos, mira la extensión pg_trgm, cuyo índice GIN también acelera LIKE '%x%', antes de montar un motor aparte.

Resumen #

Lo que te llevas

  • LIKE '%x%' recorre la tabla entera: el B-tree no sirve si el comodín va delante.
  • El full-text usa un índice invertido (término → filas); texto y consulta se normalizan igual.
  • MySQL: FULLTEXT + MATCH ... AGAINST, modo natural o booleano, sin raíces y con un mínimo de 3 caracteres por palabra.
  • Postgres: columna tsvector generada con 'spanish', índice GIN y websearch_to_tsquery para el texto del usuario.
  • Ordena por relevancia: MATCH en el SELECT en MySQL, ts_rank con pesos por columna en Postgres.
  • OpenSearch compensa con facetas, erratas, relevancia afinada o mucho volumen, si aceptas sincronizar otro almacén.
