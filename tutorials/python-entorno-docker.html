Entorno de desarrollo Python con Docker

Imagen oficial Python, Dockerfile de desarrollo con uvicorn, Compose con hot-reload, gestión de dependencias con uv y caché de paquetes entre sesiones.

En PHP el contenedor de desarrollo suele ser una imagen con FPM y Composer; en Python cambian las piezas y las trampas: logs que no salen, builds que tardan diez minutos por la imagen base equivocada o dependencias instaladas en un sitio y buscadas en otro. Aquí montas un entorno que arranca con un comando y se comporta igual en cualquier máquina.

Estructura del proyecto #

Un proyecto FastAPI dockerizado tiene una estructura previsible. La separación entre código fuente, tests y configuración de despliegue hace que cada parte tenga un lugar obvio:

bash 
my-api/
├── src/
│   ├── __init__.py
│   ├── main.py
│   ├── routers/
│   ├── models/
│   └── schemas/
├── tests/
│   └── conftest.py
├── pyproject.toml
├── uv.lock
├── Dockerfile.dev
├── compose.yml
└── .env

src/ como raíz del código de aplicación evita ambigüedades de imports. pyproject.toml es el estándar moderno (PEP 517/518) que unifica lo que antes repartían setup.py, requirements.txt y setup.cfg. uv.lock fija versiones exactas igual que composer.lock en PHP o go.sum en Go.

Dockerfile de desarrollo #

El Dockerfile de desarrollo prioriza velocidad de iteración sobre tamaño de imagen:

bash 
FROM python:3.14-slim

WORKDIR /app

RUN pip install uv

COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-install-project

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

CMD ["uv", "run", "uvicorn", "src.main:app", \
     "--reload", "--host", "0.0.0.0", "--port", "8000"]

Tres decisiones importantes aquí:

  • python:3.14-slim frente a python:3.14-alpine: slim usa glibc; alpine usa musl libc. Los paquetes grandes con extensiones C (NumPy, Pillow, pandas, cryptography) ya publican wheels para musl, pero algunas dependencias aún no los tienen y se compilan desde fuente, multiplicando el tiempo de build; además, musl difiere de glibc en rendimiento y comportamiento. slim es la elección pragmática para la mayoría de proyectos.
  • PYTHONDONTWRITEBYTECODE=1: elimina los archivos .pyc dentro del contenedor. En un entorno efímero no aportan nada y ensucian el sistema de ficheros.
  • PYTHONUNBUFFERED=1: fuerza que stdout y stderr se escriban inmediatamente sin buffer. Sin esto, los logs de la aplicación no aparecen en docker compose logs hasta que el buffer se llena.

Copiar pyproject.toml y uv.lock antes del código fuente aprovecha la caché de capas de Docker: si solo cambia el código, la capa de instalación de dependencias no se reconstruye. Por eso esa capa lleva --no-install-project: instala solo las dependencias, porque el código del propio proyecto aún no está en la imagen y, sin el flag, uv sync falla intentando construirlo.

Compose con hot-reload #

bash 
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile.dev
    volumes:
      - .:/app
      - uv_cache:/root/.cache/uv
    ports:
      - "8000:8000"
    env_file: .env
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: ${DB_NAME}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ${DB_NAME}"]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
  uv_cache:

El volume .:/app monta el directorio del host dentro del contenedor. Cualquier cambio en el código fuente es visible inmediatamente; uvicorn con --reload detecta los cambios y reinicia el servidor sin reconstruir la imagen.

El volume uv_cache persiste la caché de paquetes de uv entre reinicios del contenedor. La primera vez que se instalan las dependencias uv las descarga; las siguientes las lee desde la caché del volumen. El resultado es que uv add dentro del contenedor tarda segundos, no minutos.

depends_on con condition: service_healthy garantiza que la aplicación no intenta conectarse a Postgres antes de que esté lista para aceptar conexiones. El equivalente naïve —arrancar los dos servicios en paralelo y esperar a que la app reintente— produce errores en el arranque difíciles de diagnosticar.

Errores típicos al montar el entorno

  • Tapar el .venv de la imagen con el bind mount. uv sync crea el entorno en /app/.venv durante el build, y el volumen .:/app lo oculta con tu carpeta del host. uv run vuelve a sincronizar y deja un .venv de Linux en tu proyecto. Se evita con un volumen anónimo - /app/.venv o sacando el entorno de /app con UV_PROJECT_ENVIRONMENT.
  • Arrancar uvicorn sin --host 0.0.0.0. Por defecto escucha en 127.0.0.1, que dentro del contenedor solo es el propio contenedor: el puerto publicado responde con la conexión cerrada aunque el servidor esté vivo.
  • Editar pyproject.toml a mano y reconstruir. uv sync --frozen instala lo que dice uv.lock sin comprobar si está al día, así que la dependencia nueva no llega y salta un ModuleNotFoundError. Usa uv add, o uv lock tras editar.

uv como gestor moderno #

uv fue creado por Astral (los mismos de Ruff) y está escrito en Rust. La diferencia de velocidad frente a pip es real: instalar FastAPI con todas sus dependencias pasa de ~15 segundos con pip a menos de 1 segundo con uv en caché.

Operaciónpip / venvuv
Crear entorno virtualpython -m venv .venvuv venv
Añadir dependenciapip install X && pip freezeuv add X
Instalar de lockfilepip install -r requirements.txtuv sync --frozen
Ejecutar scriptsource .venv/bin/activate && python script.pyuv run python script.py
Ejecutar testssource .venv/bin/activate && pytestuv run pytest

uv add actualiza pyproject.toml y uv.lock atómicamente. No hay el problema clásico de instalar con pip y olvidarse de actualizar requirements.txt.

Flujo de trabajo #

El flujo diario con este setup:

bash 
docker compose up -d

docker compose exec app uv add httpx

docker compose exec app uv run pytest -x

docker compose logs -f app

docker compose down

No hace falta activar ningún virtual environment en el host. Todo sucede dentro del contenedor. El editor apunta al intérprete del contenedor (vía Dev Containers en VS Code o el intérprete remoto en PyCharm Professional).

Si el contenedor no arranca: docker compose logs app muestra el error. Los problemas más comunes son uv.lock desincronizado con pyproject.toml (solucionado con uv sync dentro del contenedor) o variables de entorno faltantes en .env.

Cuándo aplicarlo #

Dockeriza el entorno cuando…

  • El proyecto depende de servicios (Postgres, Redis) que todo el equipo tiene que levantar igual
  • Ya despliegas en contenedores y quieres que desarrollo y producción partan de la misma imagen base
  • Usas paquetes con extensiones C que piden librerías de sistema: se instalan una vez en el Dockerfile, no en cada portátil
  • Trabaja más de una persona y el «en mi máquina funciona» ya os ha costado una tarde

Quédate en el host cuando…

  • Es un script suelto o una CLI personal: uv run con su .venv local arranca al instante
  • Estás explorando datos en un notebook: el entorno local con uv da menos fricción
  • Tu editor no sabe usar el intérprete del contenedor y no vas a configurarlo: perderás autocompletado

Este Dockerfile es de desarrollo: --reload y el código montado como volumen no van a producción. Allí toca una imagen construida en varias etapas, con el código copiado dentro y sin recarga. Si el proyecto crece hasta convertirse en un servicio, empieza en el contenedor; migrar un script de host a Docker a mitad de camino es fácil, pero hacerlo con tres servicios y un equipo esperando, no.

Resumen #

Lo que te llevas

  • python:3.14-slim es la imagen base recomendada: tiene glibc (compatibilidad con wheels binarios) y es significativamente más pequeña que la imagen completa.
  • PYTHONDONTWRITEBYTECODE=1 y PYTHONUNBUFFERED=1 son las dos variables de entorno que todo Dockerfile Python debería tener.
  • Montar el código con un volume y usar uvicorn --reload da hot-reload sin reconstruir la imagen en cada cambio.
  • uv es 10-100× más rápido que pip; un volume Docker para su caché elimina las descargas repetidas entre sesiones.
  • depends_on: condition: service_healthy con un healthcheck en Postgres evita race conditions en el arranque.
