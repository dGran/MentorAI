Deadlocks: leer el log y evitarlos

Un día aparece en el log un «Deadlock found when trying to get lock» y nadie sabe de dónde sale. No es un fallo del motor: es tu código pidiendo filas en un orden que se cruza. Aquí lo provocas a propósito, lees lo que el motor deja escrito y aprendes a que no vuelva o a sobrevivirlo.

Un deadlock es un ciclo de esperas: A tiene lo que B necesita y al revés, así que el motor mata a una. Evitarlos del todo no siempre se puede; reducirlos y reintentar bien, sí.

Un error que nadie escribió #

La idea ya la tienes de Transacciones y ACID y de concurrencia: dos transacciones se bloquean mutuamente y el motor rompe el empate. Lo que falta es lo operativo. El error solo aparece con carga real y casi nunca se reproduce en local. Por eso lo primero es saber provocarlo y leer lo que el motor guarda: ese registro dice qué dos sentencias se cruzaron y sobre qué índice.

Todo lo de esta lección está ejecutado en MySQL 8.4 con InnoDB y en PostgreSQL 17, en Docker, con la misma tabla de dos cuentas.

Provocar uno en dos sesiones #

Abre dos terminales contra el mismo motor. Una transferencia va de la cuenta 1 a la 2 y otra, a la vez, de la 2 a la 1. Cada una bloquea primero la fila de su origen:

sql · MySQL 8.4 y Postgres 17 · preparación 
CREATE TABLE cuentas (id INT PRIMARY KEY, titular VARCHAR(40) NOT NULL, saldo INT NOT NULL);
INSERT INTO cuentas VALUES (1, 'Ana', 1000), (2, 'Bruno', 1000);
PasoSesión ASesión B
1BEGIN;
UPDATE cuentas SET saldo = saldo - 100 WHERE id = 1;
2BEGIN;
UPDATE cuentas SET saldo = saldo - 50 WHERE id = 2;
3UPDATE cuentas SET saldo = saldo + 50 WHERE id = 1; se queda esperando a A
4UPDATE cuentas SET saldo = saldo + 100 WHERE id = 2; cierra el ciclo

En el paso 4 una de las dos recibe el error:

salida · MySQL 8.4 
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
salida · Postgres 17 
ERROR:  deadlock detected
DETAIL:  Process 109 waits for ShareLock on transaction 743; blocked by process 102.
Process 102 waits for ShareLock on transaction 744; blocked by process 109.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,1) in relation "cuentas"

En la aplicación importa el SQLSTATE: 40001 en MySQL y 40P01 en Postgres. La otra sesión confirma.

Leer el deadlock en MySQL #

InnoDB guarda el último deadlock en SHOW ENGINE INNODB STATUS, sección LATEST DETECTED DEADLOCK. Este es el del ejemplo, sin los volcados hexadecimales de cada registro:

salida · MySQL 8.4 · SHOW ENGINE INNODB STATUS\G 
LATEST DETECTED DEADLOCK
------------------------
*** (1) TRANSACTION:
TRANSACTION 1816, ACTIVE 1 sec starting index read
LOCK WAIT 3 lock struct(s), heap size 1128, 2 row lock(s), undo log entries 1
UPDATE cuentas SET saldo = saldo + 50 WHERE id = 1

*** (1) HOLDS THE LOCK(S):
RECORD LOCKS ... index PRIMARY of table `banco`.`cuentas` trx id 1816 lock_mode X locks rec but not gap
 0: len 4; hex 80000002; asc     ;;

*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... index PRIMARY of table `banco`.`cuentas` trx id 1816 lock_mode X locks rec but not gap waiting
 0: len 4; hex 80000001; asc     ;;

*** (2) TRANSACTION:
TRANSACTION 1815, ACTIVE 2 sec starting index read
LOCK WAIT 3 lock struct(s), heap size 1128, 2 row lock(s), undo log entries 1
UPDATE cuentas SET saldo = saldo + 100 WHERE id = 2

*** (2) HOLDS THE LOCK(S):
RECORD LOCKS ... index PRIMARY of table `banco`.`cuentas` trx id 1815 lock_mode X locks rec but not gap
 0: len 4; hex 80000001; asc     ;;

*** (2) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... index PRIMARY of table `banco`.`cuentas` trx id 1815 lock_mode X locks rec but not gap waiting
 0: len 4; hex 80000002; asc     ;;

*** WE ROLL BACK TRANSACTION (2)

Se lee en cuatro pasadas:

  • La sentencia de cada transacción es la que esperaba, no la que cogió el bloqueo que retiene; esa no sale.
  • El índice (index PRIMARY) dice por dónde entró el bloqueo. La clave primaria en una consulta que filtraba por otra columna delata un índice que falta.
  • El modo: locks rec but not gap es la fila sola; locks gap before rec e insert intention son huecos entre filas, la firma de las lecturas con bloqueo de más.
  • La clave va en hexadecimal: 80000001 es el entero 1 con el bit de signo invertido.

El problema es que INNODB STATUS solo guarda el último. Para tener el historial, activa innodb_print_all_deadlocks (viene a OFF) y cada deadlock irá al log de errores:

ini · my.cnf 
[mysqld]
innodb_print_all_deadlocks = ON
log_error_verbosity = 3

Sin verbosidad 3, el log sale sin cabeceras

Con el log_error_verbosity = 2 por defecto, en 8.4 el volcado aparece en el log, pero las líneas que lo anuncian ([Note] ... Transactions deadlock detected) y la que dice a quién se deshizo (WE ROLL BACK TRANSACTION) son notas y se filtran. Te quedan bloques de transacciones sueltos sin saber cuál murió.

Leer el deadlock en Postgres #

Postgres escribe cada deadlock en el log del servidor con las dos sentencias, que no aparecen en el mensaje al cliente: de ahí el HINT. Si además activas log_lock_waits (en 17 viene a off), registra toda espera que pase de deadlock_timeout, que por defecto es 1s, y verás las esperas largas aunque no acaben en ciclo:

sql · Postgres 17 
ALTER SYSTEM SET log_lock_waits = on;
SELECT pg_reload_conf();
salida · log de Postgres 17 
LOG:  process 109 detected deadlock while waiting for ShareLock on transaction 743 after 1000.107 ms
DETAIL:  Process holding the lock: 102. Wait queue: .
ERROR:  deadlock detected
DETAIL:  Process 109 waits for ShareLock on transaction 743; blocked by process 102.
        Process 102 waits for ShareLock on transaction 744; blocked by process 109.
        Process 109: UPDATE cuentas SET saldo = saldo + 50 WHERE id = 1;
        Process 102: UPDATE cuentas SET saldo = saldo + 100 WHERE id = 2;
STATEMENT:  UPDATE cuentas SET saldo = saldo + 50 WHERE id = 1;

El ShareLock sobre una transacción es normal: quien quiere una fila ya modificada espera a que acabe la transacción que la tocó. Una espera larga sin ciclo deja still waiting for ShareLock ... after 1000.105 ms.

Qué víctima elige cada motor #

MySQL 8.4 (InnoDB)

  • Detecta el ciclo en el momento en que se forma (innodb_deadlock_detect, a ON).
  • Deshace la transacción más pequeña, contada por filas insertadas, cambiadas o borradas.
  • Deshace la transacción entera, no solo la sentencia.

Postgres 17

  • Quien espera revisa si hay ciclo tras deadlock_timeout.
  • Si lo encuentra, se aborta a sí mismo, sin mirar cuánto trabajo lleva. Cada proceso revisa una sola vez: cae el primero cuya revisión ya encuentra el ciclo, que es quien lo cerró si se cerró pasado el deadlock_timeout del primero en esperar.
  • La transacción queda abortada y rechaza todo hasta el ROLLBACK.

Con una transacción que antes insertaba 200 filas (5.000 en Postgres), MySQL deshizo la ligera y Postgres abortó la pesada: fue la primera en esperar y el ciclo se cerró antes de que venciera su deadlock_timeout.

Las causas típicas #

Orden distinto. Es el ejemplo de arriba: dos caminos de código bloquean las mismas filas en orden opuesto. Pasa con transferencias o con un servicio que bloquea pedido y luego cliente mientras otro hace lo contrario.

Índices que faltan. En MySQL un UPDATE bloquea lo que recorre, no lo que cambia. Con pedidos.cliente_id sin índice, UPDATE pedidos ... WHERE cliente_id = 1 recorre toda la tabla y deja bloqueada cada fila; otra sesión que actualizaba solo el cliente 2 esperó hasta su Lock wait timeout exceeded. Con el índice creado, pasó sin esperar. Más filas bloqueadas, más ciclos (índices en la práctica).

Lecturas con bloqueo de más. El patrón «compruebo si existe con FOR UPDATE y, si no, inserto» en el REPEATABLE READ por defecto de MySQL. Sobre una fila que no existe, el SELECT ... FOR UPDATE bloquea el hueco donde iría, y dos sesiones pueden tener ese hueco a la vez. Cuando las dos insertan, cada una espera a la otra:

salida · MySQL 8.4 · fragmento de LATEST DETECTED DEADLOCK 
INSERT INTO stock VALUES ('B-200', 1)
*** (1) HOLDS THE LOCK(S):
... index PRIMARY of table `banco`.`stock` trx id 1878 lock_mode X locks gap before rec
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
... index PRIMARY of table `banco`.`stock` trx id 1878 lock_mode X locks gap before rec insert intention waiting

En READ COMMITTED el mismo guion no hace deadlock: la segunda recibe 1062 Duplicate entry, un error que puedes tratar. Mejor aún, deja que la clave única decida con un INSERT ... ON DUPLICATE KEY UPDATE en lugar de leer antes.

Las curas, en PHP #

Este código bloquea en el orden de los argumentos y, si falla, la transferencia se pierde.

php · transfer.php (antes) 
<?php

declare(strict_types=1);

function transfer(PDO $connection, int $fromId, int $toId, int $amount): void
{
    $connection->beginTransaction();

    $connection->prepare('UPDATE cuentas SET saldo = saldo - ? WHERE id = ?')->execute([$amount, $fromId]);
    $connection->prepare('UPDATE cuentas SET saldo = saldo + ? WHERE id = ?')->execute([$amount, $toId]);

    $connection->commit();
}

La primera cura es el orden consistente: bloquear siempre por id ascendente, sea cual sea el sentido. Entre transferencias ya no hay ciclo: la segunda espera y sigue. Es el mismo FOR UPDATE de bloqueo pesimista, con el orden como regla. La transacción la abre quien llama: el reintento de más abajo.

php · transfer.php (después) 
<?php

declare(strict_types=1);

function transfer(PDO $connection, int $fromId, int $toId, int $amount): void
{
    $accountIds = [$fromId, $toId];
    sort($accountIds);

    $lockAccount = $connection->prepare('SELECT id FROM cuentas WHERE id = ? FOR UPDATE');

    foreach ($accountIds as $accountId) {
        $lockAccount->execute([$accountId]);
    }

    $connection->prepare('UPDATE cuentas SET saldo = saldo - ? WHERE id = ?')->execute([$amount, $fromId]);
    $connection->prepare('UPDATE cuentas SET saldo = saldo + ? WHERE id = ?')->execute([$amount, $toId]);
}

La segunda es la transacción corta: nada de llamadas HTTP ni cálculos pesados entre el BEGIN y el COMMIT. Cuanto más se retienen los bloqueos, más ventana para un ciclo.

La tercera es la red: un reintento acotado del bloque entero. No de la sentencia que falló, porque MySQL ya deshizo todo lo anterior y Postgres dejó la transacción inservible. Se reintenta solo ante los SQLSTATE de concurrencia, con un tope y una espera aleatoria creciente para que las dos no vuelvan a chocar al mismo ritmo:

php · DeadlockRetrier.php 
<?php

declare(strict_types=1);

final class DeadlockRetrier
{
    private const int MAX_ATTEMPTS = 3;
    private const int BASE_DELAY_MICROSECONDS = 50_000;
    private const array RETRYABLE_SQLSTATES = ['40001', '40P01'];

    public function __construct(private readonly PDO $connection)
    {
    }

    public function run(callable $unitOfWork): mixed
    {
        $attempt = 1;

        while (true) {
            $this->connection->beginTransaction();

            try {
                $result = $unitOfWork($this->connection);
                $this->connection->commit();

                return $result;
            } catch (Throwable $exception) {
                $this->connection->rollBack();

                if (!$this->isRetryable($exception) || $attempt === self::MAX_ATTEMPTS) {
                    throw $exception;
                }

                usleep(random_int(1, 2 ** $attempt) * self::BASE_DELAY_MICROSECONDS);
                $attempt++;
            }
        }
    }

    private function isRetryable(Throwable $exception): bool
    {
        return $exception instanceof PDOException
            && in_array($exception->errorInfo[0] ?? null, self::RETRYABLE_SQLSTATES, true);
    }
}
php · uso 
<?php

declare(strict_types=1);

$retrier = new DeadlockRetrier($connection);
$retrier->run(fn (PDO $connection) => transfer($connection, $fromId, $toId, $amount));

Se mira errorInfo[0], el SQLSTATE, y no el código del driver: con pdo_pgsql, errorInfo[1] vale 7 para cualquier error. 40001 es también el fallo de serialización de Postgres, que se reintenta igual. Probado en dos procesos con la versión «antes»: sin reintento, uno falla; con él, uno termina al segundo intento.

Si usas un framework

En Laravel, DB::transaction($callback, 3) ya reintenta el bloque ante errores de concurrencia. Doctrine DBAL convierte el 1213 y el 40P01 en DeadlockException, que implementa RetryableException, pero no reintenta: y wrapInTransaction del ORM cierra el EntityManager al fallar, así que el reintento necesita uno nuevo. El encaje con la unidad de trabajo está en transacciones en el ORM.

Errores típicos #

Lo que convierte un deadlock en un incidente

  • Reintentar la última sentencia en vez del bloque: en MySQL aplicas medio cambio sin la otra mitad.
  • Tratar el 1205 como un deadlock. Lock wait timeout exceeded deshace solo la sentencia (comprobado: el cambio anterior seguía ahí). Si lo reintentas, haz ROLLBACK antes.
  • Efectos fuera de la base de datos dentro del bloque. Si el bloque manda un correo y se reintenta, sale dos veces. Sácalo con un outbox o hazlo idempotente.
  • Reintentos sin tope: esconden el problema y multiplican la carga.
  • Apagar innodb_deadlock_detect para «quitar» deadlocks: el ciclo sigue ahí y acaba en el Lock wait timeout, a 50 s por defecto (comprobado: con la detección apagada, las dos sesiones recibieron el 1205).

Cómo comprobarlo #

Primero, cuántos hay: los dos motores llevan un contador acumulado.

sql · MySQL 8.4 y Postgres 17 
SELECT NAME, COUNT FROM information_schema.INNODB_METRICS WHERE NAME = 'lock_deadlocks';

SELECT datname, deadlocks FROM pg_stat_database WHERE datname = current_database();

Después, quién bloquea a quién mientras la espera ocurre:

sql · MySQL 8.4 y Postgres 17 
SELECT waiting_pid, waiting_query, blocking_pid, blocking_query, wait_age FROM sys.innodb_lock_waits;

SELECT pid, pg_blocking_pids(pid) AS bloqueado_por, left(query, 60) AS query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

Y la prueba que vale: el guion de dos sesiones con tus consultas reales. Si tras la cura el segundo proceso espera y termina, el ciclo ya no existe.

Cuándo aplicarlo #

Cuándo sí

  • El contador de deadlocks sube o el log los muestra con carga real.
  • Varias rutas de código bloquean las mismas tablas.
  • Cualquier transacción que escriba con concurrencia: el reintento acotado es barato.

Cuándo no

  • Transacciones de una sola sentencia sobre una fila, como UPDATE ... SET x = x - 1: sin un segundo bloqueo que pedir, el ciclo de esta lección no se forma.
  • Procesos batch de un solo trabajador sobre su propio rango.

Si hay una fila caliente y los reintentos se disparan, cambia de estrategia: el bloqueo optimista no retiene bloqueos y una cola con SKIP LOCKED reparte el trabajo.

Resumen #

Lo que te llevas

  • Un deadlock se reproduce con dos sesiones y dos filas en orden opuesto; hazlo con tus consultas antes de tocar nada.
  • MySQL guarda solo el último en LATEST DETECTED DEADLOCK; para el historial, innodb_print_all_deadlocks y verbosidad 3. Postgres lo escribe siempre en el log; log_lock_waits añade las esperas largas.
  • InnoDB detecta al instante y deshace la transacción más pequeña; Postgres revisa una vez tras deadlock_timeout y cae el primero cuya revisión encuentra el ciclo.
  • Causas habituales: orden distinto, índices que faltan y FOR UPDATE sobre filas que no existen.
  • Curas: orden consistente, transacciones cortas y reintento acotado del bloque entero ante 40001 y 40P01.
