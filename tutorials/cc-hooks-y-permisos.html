Hooks y permisos

«De ahora en adelante, haz siempre X» dicho en el chat es una promesa del modelo — y el modelo es probabilístico. Este módulo empieza por la alternativa seria: permisos que filtran lo que puede ejecutarse y hooks que interceptan cada acción con un script tuyo. Automatización de la que se cumple siempre.

La frontera de permisos apareció en la primera lección como concepto. Aquí se convierte en configuración concreta: las listas y modos que deciden qué se ejecuta sin preguntar, y los hooks — el mecanismo que mete tu código dentro del bucle del agente.

Dos capas deterministas #

Recuerda la jerarquía: una instrucción en rules se cumple casi siempre; un mecanismo del harness, siempre. Claude Code te da dos de esos mecanismos, complementarios:

  • Permisos: filtros declarativos sobre qué herramientas y comandos pueden ejecutarse, y cuáles piden confirmación.
  • Hooks: scripts tuyos que el harness ejecuta en momentos fijos del bucle (antes de una herramienta, después, al terminar el agente) y que pueden observar, modificar el veredicto o bloquear.

La diferencia práctica: los permisos deciden con patrones («este comando sí, este no»); los hooks deciden con lógica («ejecuta este script y que él diga»). Lo segundo llega donde los patrones no llegan.

Permisos: qué puede ejecutarse #

El sistema de permisos vive en la configuración del proyecto (.claude/settings.json, versionada) y la personal. Las piezas: listas allow (pasa sin preguntar), deny (se rechaza siempre) y ask, con patrones por herramienta:

.claude/settings.json · permisos 
{
  "permissions": {
    "allow": [
      "Bash(vendor/bin/phpunit *)",
      "Bash(node scripts/validar.js)",
      "Bash(git status)", "Bash(git diff *)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Read(.env*)",
      "Bash(git push --force *)"
    ]
  }
}

Fíjate en Read(.env*): los permisos no solo acotan ejecución, también lectura — un secreto que el agente no lee es un secreto que no puede acabar en un log ni en un diff. Encima de las listas hay modos de sesión: del más conservador (todo pregunta) al de confianza plena para entornos desechables, pasando por el modo plan de la lección 3, que es un modo de permisos con nombre propio.

Afinar la lista: menos fricción, mismo control #

El objetivo del ajuste fino es que las confirmaciones que te pida la herramienta sean solo las que informan de algo. Si apruebas veinte veces al día phpunit, la confirmación ya no te protege: te entrena a pulsar «sí» sin leer — la fatiga de alertas del curso de observabilidad, aplicada aquí. El ciclo sano: lo aprobado rutinariamente pasa a allow; lo peligroso, explícitamente a deny; y la pregunta queda reservada para lo genuinamente excepcional.

Hooks: tu código en el bucle #

Un hook es un comando tuyo registrado en un punto del ciclo de vida del agente. Los dos más usados: antes de ejecutar una herramienta (puede vetar la acción) y después (puede reaccionar al resultado: formatear el fichero recién editado, lanzar un lint). El harness le pasa al script los datos del evento (qué herramienta, con qué argumentos) y el código de salida del script decide.

1 El modelo pide una herramientaPor ejemplo: Edit sobre src/Kernel.php.
2 Tu script decideSale 0 → adelante. Sale con error → acción bloqueada, y el motivo vuelve al modelo.
3 Hook post-herramientaReacciona al hecho consumado: formatear, validar, avisar.

El hook corre fuera del modelo: no se le puede convencer, olvidar ni compactar.

Un hook que bloquea de verdad #

Ejemplo con sustancia: en esta academia, el catálogo se genera del manifest y nadie debe editar a mano ciertos ficheros generados. Una rule lo dice — y un hook lo garantiza:

bash · hooks/protege-generados.sh 
#!/bin/bash
# Recibe en stdin el JSON del evento; jq extrae el fichero a editar
fichero=$(jq -r ".tool_input.file_path // empty")

if [[ "$fichero" == *"search-index.js" ]]; then
  echo "search-index.js es GENERADO: ejecuta scripts/generar-indice.js" >&2
  exit 2   # bloquea la accion; el mensaje vuelve al modelo
fi

exit 0

El detalle elegante: al bloquear, el mensaje de error vuelve al contexto del modelo, que corrige el rumbo solo («ah, tengo que regenerarlo con el script»). El hook no solo protege: enseña en el momento exacto del error, que es cuando las lecciones entran.

Los hooks también son superficie

Un hook es código que se ejecuta con tus permisos en cada acción del agente: un hook lento hace lenta toda la sesión, y un hook con un bug puede bloquearlo todo o — peor — dejar pasar lo que debía vetar. Se versionan, se revisan y se prueban como el código que son.

Qué automatizar con cada pieza #

Con rules, permisos y hooks sobre la mesa, el reparto queda así: las rules dan criterio y contexto (el porqué, el cómo se hace aquí); los permisos definen el perímetro (qué ni siquiera se intenta); los hooks imponen los invariantes con lógica (formatos, ficheros intocables, validaciones automáticas tras cada edición). La pregunta guía: ¿el coste de que esto falle una vez es asumible? Si no lo es, no puede vivir solo en una rule.

Cuándo aplicarlo #

Permisos y hooks cuando…

  • Algo no debe pasar nunca (deny) o debe pasar siempre (hook post-edición)
  • Apruebas lo mismo por enésima vez: a la lista allow
  • Hay secretos que el agente no necesita leer
  • Un invariante del proyecto merece garantía, no promesa

Señales de mal uso

  • Modo «todo permitido» en un entorno que no es desechable
  • Hooks tan estrictos que el agente no puede trabajar (todo bloqueado)
  • Meter criterio en hooks: la lógica de negocio del flujo va en rules/skills, el hook solo impone
  • Confirmaciones rutinarias que ya nadie lee

Resumen #

Lo que te llevas

  • «Hazlo siempre» dicho en el chat es una promesa probabilística: la automatización seria vive en permisos y hooks, que el harness ejecuta.
  • Permisos: allow/deny/ask con patrones, versionados en el repo; también acotan lectura (secretos fuera del contexto).
  • Una confirmación rutinaria ya no protege: lo rutinario a allow, lo peligroso a deny, la pregunta para lo excepcional.
  • Un hook es tu script dentro del bucle: veta, valida o reacciona, y su mensaje de bloqueo enseña al modelo en el momento del error.
  • Reparto: rules = criterio, permisos = perímetro, hooks = invariantes impuestos. Si fallar una vez no es asumible, no basta una rule.
