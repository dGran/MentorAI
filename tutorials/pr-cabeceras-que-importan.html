Las cabeceras que de verdad cambian el comportamiento

Hay decenas de cabeceras y la mayoría no cambian nada. Un puñado pequeño decide si la respuesta se cachea, si el navegador ejecuta lo que le mandas y qué se rompe con un proxy en medio.

Hay decenas de cabeceras HTTP y la mayoría no cambian nada en tu día a día. Un puñado pequeño sí: deciden si la respuesta se cachea, si el navegador ejecuta lo que le mandas, si otro dominio puede leerte y qué se rompe cuando hay un proxy en medio.

Las que negocian el contenido #

CabeceraQué hace
AcceptQué formatos entiende el cliente, con preferencias
Content-TypeQué manda de verdad este mensaje. En una respuesta, es obligatorio y se olvida
Accept-EncodingQué compresiones acepta: gzip, br
Content-LengthCuánto ocupa. Si falta, se usa codificación por trozos

Devolver JSON con Content-Type: text/html

Es más común de lo que parece, sobre todo en respuestas de error generadas fuera del framework. El cliente intenta parsear como JSON, falla, y el mensaje de error que ves no tiene nada que ver con la causa. Cuando una integración «devuelve basura», mira primero el Content-Type.

CORS: el que más tiempo hace perder #

Lo primero que hay que entender es que CORS no protege tu servidor: protege al usuario impidiendo que una web maliciosa lea respuestas de otro dominio usando sus cookies. Tu API recibe la petición igual — es el navegador el que decide si deja que el JavaScript vea la respuesta.

1 Petición simpleGET o POST con formulario: va directa, y el navegador filtra la respuesta
2 PreflightUn OPTIONS previo preguntando si se permite
3 Y solo entonces la realDos idas y vueltas en vez de una, salvo que caches el preflight

Access-Control-Max-Age cachea el preflight y ahorra esa ida y vuelta en las siguientes peticiones.

Allow-Origin: * con credenciales no funciona, y es a propósito

El navegador rechaza esa combinación: si permitieras cualquier origen y el envío de cookies, cualquier web podría leer datos de tus usuarios autenticados. Con credenciales hay que devolver el origen concreto, y si aceptas varios, eco del Origin validado contra una lista blanca — nunca eco a secas.

Cuatro cabeceras de seguridad #

bash · las que valen la pena 
Content-Security-Policy: default-src 'self'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Strict-Transport-Security: max-age=31536000

Content-Security-Policy es la que más aporta y la más difícil de desplegar: declara de dónde puede cargarse cada tipo de recurso, y es la defensa de fondo contra XSS. Se despliega en modo informe primero, se miran las violaciones reales durante unos días y solo después se aplica.

nosniff impide que el navegador adivine el tipo de un fichero ignorando tu Content-Type, que es como un fichero subido por un usuario acaba ejecutándose como script. Y Referrer-Policy evita que la URL completa —con sus identificadores y sus tokens— viaje a terceros cuando alguien pincha un enlace saliente.

Las que ya no hace falta poner

X-XSS-Protection está obsoleta y algunos navegadores la ignoran o la consideran contraproducente; X-Frame-Options la sustituye frame-ancestors dentro de CSP. Copiar listas de cabeceras de artículos viejos añade ruido sin aportar nada.

Las que se rompen con un proxy delante #

En cuanto hay una CDN o un balanceador, tu aplicación deja de ver la petición original. Esto ya salió en la lección de nginx y merece la vuelta desde el lado del protocolo, porque son cuatro datos y los cuatro se pierden:

Lo que deja de ser ciertoQuién lo dice
La IP del clienteX-Forwarded-For o Forwarded
Que la petición vino por HTTPSX-Forwarded-Proto
El dominio que pidió el usuarioX-Forwarded-Host
El puerto originalX-Forwarded-Port

El segundo es el que produce el bug más desconcertante: tu aplicación cree que la petición llegó por HTTP —porque el último salto lo fue— y genera todas las URL absolutas con http://. El resultado son redirecciones infinitas, o recursos bloqueados por contenido mixto, en un sitio que sirve HTTPS perfectamente.

Cuándo aplicarlo #

Repasa las cabeceras cuando…

  • Montas una API que van a consumir desde un navegador
  • Metes una CDN o un balanceador por primera vez
  • Una integración recibe algo que no sabe interpretar
  • Haces una revisión de seguridad

No te pelees con ellas cuando…

  • Es una API interna que solo consumen servidores
  • El framework ya las gestiona y no has tocado nada
  • Estarías copiando una lista de un artículo de hace ocho años

Resumen #

Lo que te llevas

  • CORS no protege tu servidor: protege al usuario. La petición te llega igual; es el navegador quien filtra la respuesta.
  • Un preflight añade una ida y vuelta; Access-Control-Max-Age la cachea y se ahorra en las siguientes.
  • Comodín en el origen con credenciales lo rechaza el navegador a propósito: haría que cualquier web leyera datos de tus usuarios.
  • CSP es la que más aporta y se despliega en modo informe antes de aplicarla. X-XSS-Protection ya no se pone.
  • Olvidar X-Forwarded-Proto genera URL con http:// en un sitio que sirve HTTPS: redirecciones infinitas y contenido mixto.
