Strategy y Observer: comportamiento intercambiable y eventos

Strategy encapsula un algoritmo en un objeto para intercambiarlo sin tocar el código que lo usa — el OCP llevado a la práctica. Observer desacopla al emisor de sus receptores: uno publica, muchos escuchan, ninguno se conoce.

Estos dos patrones son los más frecuentes en código de producción moderno. Strategy aparece cada vez que tienes un condicional que elige entre variantes de comportamiento. Observer aparece cada vez que algo ocurre y otros partes del sistema deben enterarse sin que la fuente sepa quiénes son.

Strategy #

El problema: tienes un algoritmo que varía según el contexto — el descuento de un pedido cambia según el tipo de cliente, el método de envío de una notificación cambia según la preferencia del usuario, el formato de exportación cambia según lo que pida el cliente de la API. El código que orquesta esa lógica acaba lleno de if y switch que crecen cada vez que aparece una variante nueva.

Strategy extrae cada variante de comportamiento a su propia clase que implementa una interfaz común. El contexto recibe la estrategia correcta por inyección de dependencias y la llama sin saber cuál es.

php · DiscountStrategy.php 
<?php

declare(strict_types=1);

interface DiscountStrategy
{
    public function calculate(int $totalCents): int;
}

class NoDiscount implements DiscountStrategy
{
    public function calculate(int $totalCents): int
    {
        return 0;
    }
}

class PercentageDiscount implements DiscountStrategy
{
    public function __construct(
        private readonly int $percentage
    ) {}

    public function calculate(int $totalCents): int
    {
        return (int) ($totalCents * $this->percentage / 100);
    }
}

class FlatDiscount implements DiscountStrategy
{
    public function __construct(
        private readonly int $discountCents
    ) {}

    public function calculate(int $totalCents): int
    {
        return min($this->discountCents, $totalCents);
    }
}

// El contexto no sabe qué estrategia tiene; solo la llama
class Order
{
    public function __construct(
        private readonly int $totalCents,
        private readonly DiscountStrategy $discount
    ) {}

    public function finalTotal(): int
    {
        return $this->totalCents - $this->discount->calculate($this->totalCents);
    }
}

Añadir un nuevo tipo de descuento es añadir una nueva clase — nada más. Ni Order ni ningún otro código existente cambia. Esto es exactamente OCP: abierto a extensión (nueva clase), cerrado a modificación (código existente intacto).

Strategy vs condicionales #

No todo condicional necesita un Strategy. La regla práctica: cuando el condicional tiene más de dos o tres ramas que representan comportamientos genuinamente distintos y es probable que crezca, Strategy vale la pena. Cuando es una condición simple y estable, un if es más claro.

Sin Strategy — crece con el negocio

php 
<?php
// Cada nuevo tipo de cliente = modificar este método
public function discount(string $type, int $total): int
{
    if ($type === 'vip') {
        return (int) ($total * 0.20);
    }

    if ($type === 'regular') {
        return (int) ($total * 0.05);
    }

    return 0;
}

Con Strategy — extensible sin modificar

php 
<?php
// Nuevo tipo de cliente = nueva clase, nada más cambia
public function discount(DiscountStrategy $strategy, int $total): int
{
    return $strategy->calculate($total);
}

El condicional no desaparece del todo: alguien tiene que decidir qué Strategy usar. Ese condicional se mueve a la Factory o al contenedor DI — donde vive la lógica de construcción, no la lógica de negocio.

Observer #

El problema: cuando algo ocurre en el sistema (un pedido se confirma, un usuario se registra, una factura se genera), varias partes del sistema necesitan reaccionar. Si el objeto que genera el evento llama directamente a cada uno de los que deben reaccionar, queda acoplado a todos ellos. Añadir una reacción nueva exige modificar el emisor.

Observer define una relación de suscripción: el sujeto (emisor) mantiene una lista de observadores y los notifica cuando ocurre algo. El emisor no sabe quiénes son los observadores; los observadores no saben nada del emisor salvo el evento que reciben.

php · OrderObserver.php 
<?php

declare(strict_types=1);

// El evento: lo que ocurrió
final class OrderConfirmed
{
    public function __construct(
        public readonly int $orderId,
        public readonly string $customerEmail,
        public readonly int $totalCents
    ) {}
}

// La interfaz del observador
interface OrderObserver
{
    public function onOrderConfirmed(OrderConfirmed $event): void;
}

// Dos observadores independientes
class SendConfirmationEmail implements OrderObserver
{
    public function onOrderConfirmed(OrderConfirmed $event): void
    {
        // envía email de confirmación
    }
}

class UpdateInventory implements OrderObserver
{
    public function onOrderConfirmed(OrderConfirmed $event): void
    {
        // actualiza stock
    }
}

// El emisor notifica sin saber quiénes escuchan
class OrderService
{
    /** @var OrderObserver[] */
    private array $observers = [];

    public function subscribe(OrderObserver $observer): void
    {
        $this->observers[] = $observer;
    }

    public function confirm(Order $order): void
    {
        $order->markAsConfirmed();

        $event = new OrderConfirmed($order->id(), $order->customerEmail(), $order->totalCents());

        foreach ($this->observers as $observer) {
            $observer->onOrderConfirmed($event);
        }
    }
}

Añadir una nueva reacción (generar factura, notificar al almacén, actualizar analytics) es crear un nuevo observador y suscribirlo — sin tocar OrderService.

Observer y eventos de dominio #

El Observer del GoF es el antepasado directo de los sistemas de eventos modernos. Symfony's EventDispatcher, los listeners de Laravel, los domain events de DDD — todos son variantes del mismo patrón con nomenclatura y abstracciones distintas.

Observer GoF vs eventos de dominio

En el Observer clásico, el sujeto gestiona la lista de observadores. En los sistemas de eventos modernos, un dispatcher centralizado actúa de intermediario: el emisor publica un evento al dispatcher sin saber nada de los listeners; el dispatcher los resuelve. El resultado es el mismo desacoplamiento con más flexibilidad para registrar listeners desde configuración.

php · Symfony EventDispatcher 
<?php

declare(strict_types=1);

// En Symfony: el emisor no sabe nada de los listeners
class OrderService
{
    public function __construct(
        private readonly EventDispatcherInterface $dispatcher
    ) {}

    public function confirm(Order $order): void
    {
        $order->markAsConfirmed();
        $this->dispatcher->dispatch(new OrderConfirmed($order->id(), $order->customerEmail(), $order->totalCents()));
    }
}

// Cada listener se registra en services.yaml con #[AsEventListener]
#[AsEventListener]
class SendConfirmationEmailListener
{
    public function __invoke(OrderConfirmed $event): void
    {
        // envía email
    }
}

Cuándo aplicarlo

Aplícalo cuando…

  • Strategy: el algoritmo varía y necesita ser intercambiable en tiempo de ejecución.
  • Observer: múltiples objetos deben reaccionar a un evento sin que el emisor los conozca.
  • Command: quieres encapsular operaciones para encolarlas, deshacerlas o auditarlas.
  • Template Method: el esqueleto del proceso es fijo pero ciertos pasos varían entre implementaciones.

No lo uses cuando…

  • Strategy para una condición simple y estable: un if es más directo y legible.
  • Observer si solo hay un receptor: la llamada directa comunica la intención mejor.

Resumen #

Lo que te llevas

  • Strategy: encapsula variantes de comportamiento en clases separadas con interfaz común. El contexto no sabe cuál usa — solo la llama.
  • Strategy elimina condicionales de comportamiento. El condicional de selección se mueve a la Factory o al contenedor, no desaparece.
  • Observer: el emisor notifica a una lista de observadores sin saber quiénes son. Añadir una reacción nueva no modifica el emisor.
  • Los sistemas de eventos (Symfony EventDispatcher, domain events) son Observer con un dispatcher centralizado. Mismo patrón, más flexibilidad de registro.
