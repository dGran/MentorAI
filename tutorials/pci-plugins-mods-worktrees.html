Plugins, mods y worktrees

Cuando la configuración de un proyecto funciona, el siguiente paso es compartirla sin copiar carpetas a mano, verla en vivo mientras el agente trabaja y poder lanzar varias sesiones a la vez sin que se pisen. Para eso están los plugins, los mods y los worktrees.

Las tres piezas resuelven problemas que aparecen al escalar: los plugins reparten un kit de configuración entre proyectos y personas, los mods cambian lo que hace y muestra Claude Code durante la sesión, y los worktrees dan a cada sesión su propia copia del repositorio.

Plugins #

Un plugin es un paquete instalable que agrupa piezas de configuración: skills, comandos, subagentes, hooks y servidores MCP. Sirve para compartir un «kit» completo entre proyectos y personas sin copiar carpetas a mano.

texto · estructura de un plugin 
mi-plugin/
├── .claude-plugin/
│   └── plugin.json      # nombre, versión, descripción, autor
├── skills/              # skills del plugin
├── commands/            # comandos personalizados
├── agents/              # subagentes
├── hooks/               # configuración de hooks
└── .mcp.json            # servidores MCP que trae

No hace falta que tenga todas las carpetas: un plugin puede traer solo una skill o solo unos hooks.

Marketplaces

Los plugins se distribuyen a través de marketplaces: un repositorio Git con un archivo de catálogo que lista los plugins disponibles. Hay marketplaces públicos y se puede montar uno privado para la empresa en GitLab o GitHub.

  • /plugin abre el gestor: añadir marketplaces, instalar, activar, desactivar o actualizar plugins.
  • Los plugins instalados se pueden activar por proyecto o a nivel de usuario.

Para qué te sirve

  • Configuración de equipo reutilizable: las rules de arquitectura, la skill de retro, el subagente de QA, los hooks de PHPStan y Deptrac y los MCP comunes, empaquetados en un plugin que cualquier repo de la empresa instala de una vez.
  • Versionado: actualizar el plugin actualiza a todos, en lugar de mantener copias en cada repositorio.
  • Separar lo común de lo específico: lo compartido por todos los proyectos va al plugin; lo de cada proyecto, en su .claude/.
  • Alternativa a tus dotfiles: tu configuración personal (skill de commits, preferencias) también podría empaquetarse como plugin privado.

Precauciones con los plugins

Un plugin puede traer hooks y MCPs que ejecutan código en tu máquina: instala solo de fuentes de confianza y revisa el contenido (ver prompt injection en criterio y riesgos). Y cada plugin activo añade skills, herramientas y descripciones al contexto: activa solo los necesarios.

Mods #

Un mod es un plugin de Claude Code que, en lugar de lanzar scripts externos, ejecuta funciones en JavaScript o TypeScript dentro del propio proceso de Claude Code, durante toda la sesión. Puede engancharse a sus eventos para dibujar en pantalla (encima del prompt o en un panel lateral), bloquear o reescribir llamadas a herramientas y cambiar lo que muestra la interfaz. Llegaron con Claude Code 2.1.287, en octubre de 2026, y según la cobertura del lanzamiento vienen activados por defecto.

Mod vs. hook

Hook de settingsMod
Cómo se ejecutaLanza un programa aparte en cada eventoFunciones JS/TS cargadas dentro de Claude Code toda la sesión
Qué puede hacerBloquear, validar, devolver errores al agenteLo mismo, y además dibujar paneles, barras, avisos y reescribir llamadas
Dónde vivesettings.jsonDentro de un plugin (su hooks/hooks.json apunta al archivo JS/TS)

Un mod es, por tanto, un tipo de plugin: se instala igual, desde un marketplace o con /plugin.

Ejemplos oficiales

Anthropic publica tres mods de ejemplo, sin soporte, en su repositorio claude-code-playground:

  • token-weather: muestra una «previsión» del uso de la ventana de contexto encima del prompt.
  • blast-radius: retiene un comando arriesgado (rm -rf, force push), muestra qué cambiaría y pide confirmar o cancelar.
  • replay-theater: añade /replay para repasar paso a paso las ediciones del último turno.

La comunidad añade otros: explorador de archivos junto a la conversación, detección de conflictos entre sesiones paralelas, visibilidad de subagentes o convertir correcciones repetidas en instrucciones guardadas.

Mods de la comunidad: nombres orientativos

Salvo los tres oficiales, son mods de terceros recogidos de catálogos comunitarios; los nombres y lo que hacen pueden cambiar. Hay catálogos con miles de mods que indican a qué puede acceder cada uno antes de instalarlo, como awesome-claude-code-mods. Fuentes del glosario original sobre mods: StationX, Firecrawl, MindStudio y la documentación oficial de Claude Code.

Los más interesantes para un flujo de trabajo con agentes: collision-guard si trabajas con varias sesiones o worktrees; un panel de subagentes si los usas; un medidor de contexto y coste (flightdeck, cctop) para decidir cuándo compactar o abrir sesión nueva; cache-tax o cache-warmer si haces pausas largas en sesiones grandes.

Para qué te puede servir

  • Ver el consumo de contexto en tiempo real.
  • Protecciones visuales ante comandos destructivos, complementarias a deny y hooks.
  • Detectar conflictos si trabajas con varias sesiones o worktrees.
  • Hacer más visible lo que hacen los subagentes.

Precauciones con los mods

Se ejecutan con tus permisos y dentro de Claude Code: pueden leer y modificar lo que pasa en la sesión, y la propia Anthropic advierte de que pueden leer tu clave de API. No son un sandbox. Antes de cargarlo, revisa sus hooks y llamadas, y pruébalo solo para una sesión con --plugin-dir antes de añadirlo de forma permanente. Hay miles publicados: aplica los mismos criterios que con MCPs y skills de terceros. Y un mod como blast-radius reconoce el riesgo por el texto del comando: las restricciones duras siguen siendo las reglas deny de permisos.

Worktrees: varias sesiones sin pisarse #

Un worktree de Git es una copia de trabajo adicional del mismo repositorio, en otra carpeta y con otra rama, que comparte el historial. Permite tener varias sesiones de agente trabajando en paralelo en tareas distintas sin pisarse los archivos.

  • Git puro: git worktree add ../mi-proyecto-feature-x -b feature-x crea la carpeta con su rama; en ella se abre otra sesión de Claude Code.
  • Soporte en Claude Code: se puede arrancar una sesión directamente en un worktree nuevo con la opción --worktree, y los subagentes pueden configurarse para trabajar aislados en su propio worktree. Conviene confirmar los detalles en la documentación de la versión que uses.
  • Ojo con Docker: cada worktree es otra carpeta, así que puede necesitar sus propios contenedores, puertos o base de datos para no chocar con los demás.
  • Limpieza: git worktree remove al terminar, o se acumulan carpetas y ramas.

Los comandos de Git, cómo se comparten los objetos y cómo levantar cada worktree con su propio Docker Compose, en git worktrees.

Cuándo aplicarlo #

Úsalo cuando…

  • Varios repos comparten rules, skills y hooks: un plugin en un marketplace privado evita mantener copias
  • Quieres ver el contexto y el coste en vivo para decidir cuándo compactar: un mod medidor
  • Lanzas dos sesiones a la vez sobre el mismo repo: un worktree por sesión

No lo uses cuando…

  • Solo tienes un proyecto: la carpeta .claude/ del repo basta
  • No has leído qué hace un mod o plugin de terceros: ejecuta código con tus permisos
  • La segunda sesión necesita la misma base de datos que la primera sin aislarla: se pisarán igual

Resumen #

Lo que te llevas

  • Un plugin empaqueta skills, comandos, subagentes, hooks y MCP; se reparte por marketplaces y se gestiona con /plugin.
  • Un mod es un plugin que corre JS/TS dentro de Claude Code: dibuja paneles y puede bloquear o reescribir llamadas. Corre con tus permisos y no es un sandbox.
  • Plugins y mods de terceros se revisan antes de instalar, como cualquier código.
  • Un worktree da a cada sesión su carpeta y su rama; con Docker, también sus contenedores y puertos.
